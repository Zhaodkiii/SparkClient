# 任务通知需求

> 文档性质：任务模块接入本地通知的需求与详细设计文档。本文基于 SparkClient 当前任务模块和用药提醒实现整理，只定义需求、数据契约、流程、边界、测试和实施顺序，不实现任何客户端或服务端代码。  
> 适用范围：SparkClient iOS 客户端；服务端以现有 `SparkService/task_system` 为目标改造范围，但 SparkService 源码当前不在本工作区，服务端文件位置属于现有文档已确认、源码未复核的建议落点。

## 一、模块目标

任务模块需要正式接入通知能力。任何来源创建的任务，只要创建成功，均默认开启通知并尝试在当前设备创建本地通知。用户可在任务详情页关闭或重新开启该任务的通知，开关结果同步到服务端并通过任务列表、任务详情和增量同步接口回传给其他客户端。

本需求的核心规则如下：

1. 不区分本人任务和非本人任务。
2. 不区分任务创建来源；手动、AI、报告、会话卡片等创建路径统一默认开启通知。
3. 所有任务类型统一支持通知；医疗、运动、饮食任务都创建通知。
4. 新建任务的 `notification_enabled` 默认值为 `true`。
5. 创建页不提供通知开关，避免用户在创建时额外决策。
6. 任务详情页提供通知开关，可关闭或重新开启。
7. 服务端 `notification_enabled` 是任务级通知意愿的唯一事实源。
8. iOS 系统通知权限是设备能力，不与 `notification_enabled` 混为一个字段。
9. 首期到点提醒使用客户端本地通知，不新增服务端 APNs 到点推送，避免与本地通知重复。
10. 完成、跳过、失败终结、取消或删除任务后，清理对应的待发送和已送达通知。

目标闭环：

```text
创建任务
  ↓
服务端保存 notification_enabled=true
  ↓
客户端根据任务时间创建本地通知
  ↓
到点提醒
  ↓
点击通知进入任务详情
  ↓
用户执行任务或在详情关闭通知
  ↓
服务端状态与本机通知同步更新
```

## 三、服务端通知开关与同步契约

### 需求说明

服务端任务对象增加 `notification_enabled` 字段，表达“该任务是否允许各客户端在本机创建通知”。字段属于任务业务状态，不属于某台设备，也不等于 iOS 系统通知权限。

### 基础要求与业务规则

1. 字段名固定为 `notification_enabled`。
2. 类型为 `Boolean`，数据库非空，默认 `true`。
3. 历史任务迁移后统一回填 `true`，保持当前客户端“pending 任务自动注册通知”的既有行为。
4. `POST /api/v1/tasks/` 未传该字段时，服务端按 `true` 创建。
5. 客户端创建任务时仍应显式提交 `notification_enabled: true`，减少不同服务端版本的默认值歧义。
6. `PATCH /api/v1/tasks/{task_id}/` 支持单独更新该字段。
7. `GET /api/v1/tasks/`、任务详情响应、创建/更新响应和 `GET /api/v1/tasks/sync/` 必须返回该字段。
8. `notification_enabled=false` 不修改任务状态、不删除任务、不删除执行记录。
9. 重新开启通知时只影响未来提醒，不补发已经错过的通知。
10. 服务端字段变更必须更新 `updated_at`，确保增量同步能够发现。
11. 不增加“本人/非本人”授权字段，不走成员归属判断。
12. 首期不因 `notification_enabled=true` 直接发送 APNs；服务端仅同步意愿和任务事实，避免远程推送与本地通知同时到达。

建议数据库定义：

```python
notification_enabled = models.BooleanField(default=True, db_index=True)
```

建议创建请求：

```json
{
  "member": 509,
  "title": "晚饭后散步",
  "description": "散步 30 分钟",
  "type": 1,
  "status": 0,
  "start_time": "2026-08-16T19:30:00+08:00",
  "due_time": "2026-08-16T20:30:00+08:00",
  "repeat_type": 1,
  "priority": 1,
  "business_type": "exercise",
  "business_id": "",
  "notification_enabled": true,
  "extra": {},
  "task_exercise": {
    "exercise_type": "walking",
    "duration_min": 30,
    "intensity": "medium",
    "description": "散步 30 分钟",
    "source": "manual",
    "extra": {}
  }
}
```

建议关闭通知请求：

```http
PATCH /api/v1/tasks/123/
Content-Type: application/json

{
  "notification_enabled": false
}
```

建议任务响应片段：

```json
{
  "id": 123,
  "member": 509,
  "status": 0,
  "start_time": "2026-08-16T19:30:00+08:00",
  "due_time": "2026-08-16T20:30:00+08:00",
  "repeat_type": 1,
  "notification_enabled": false,
  "notification_id": "task_265_123",
  "updated_at": "2026-08-16T10:20:30+08:00"
}
```

### 验收标准

- 新建任务未传字段时返回 `notification_enabled=true`。
- 创建、更新、列表、详情和同步响应中的字段值一致。
- 关闭开关会更新 `updated_at`，其他设备增量同步能收到变化。
- 历史任务迁移后字段非空且为 true。
- 旧客户端忽略新增字段时，任务 CRUD 不受影响。

### 技术细节与设计代码位置

客户端需在 `HealthTask` 增加 `notificationEnabled`；JSON 继续使用项目默认 snake_case 解码。为了兼容灰度期间旧服务端缺失字段，客户端建议使用默认 true 的 Codable 包装或自定义解码，不能因字段缺失导致整个任务列表解码失败。

`TaskCreatePayload` 增加非可选 `notificationEnabled: Bool`，固定传 true；`TaskUpdatePayload` 增加可选 `notificationEnabled: Bool?`，只有详情开关或明确编辑时才传值，避免普通编辑覆盖远端较新的通知偏好。

## 四、任务创建后默认创建通知

### 需求说明

任务创建成功后，所有任务类型、所有来源和所有成员统一尝试在当前设备创建通知。通知创建必须发生在服务端返回真实任务 ID 后，禁止为本地草稿或预览卡片提前注册系统通知。

### 基础要求与业务规则

#### 4.1 覆盖的创建来源

- 手动创建。
- AI JSON 生成后创建。
- 对话任务卡片保存。
- 报告、体检计划或其他业务模块调用 `TaskManager.createTaskReturningTask` 创建。
- 服务端同步到当前设备的新任务。

所有入口必须收口到同一规则：

```text
task.status == pending
AND task.notificationEnabled == true
AND 有可用触发时间
AND 系统通知权限允许
= 当前设备注册本地通知
```

#### 4.2 触发时间优先级

当前任务模型只有医疗任务拥有独立 `taskMedical.reminderTime`，因此首期不新增第二个全局通知时间字段，统一按以下顺序取值：

```text
task.taskMedical.reminderTime
  ?? task.startTime
  ?? task.dueTime
```

业务规则：

1. 医疗任务优先使用医疗提醒时间。
2. 运动和饮食任务默认使用开始时间。
3. 开始时间缺失时使用截止时间。
4. `notification_enabled=true` 但三个时间都为空时，服务端创建请求应返回字段校验错误；正常创建流程必须保证至少一个可用时间。
5. 非重复任务的触发时间已经过去时，不立即补弹旧通知；页面显示“提醒时间已过”，等待用户编辑时间。
6. daily 和 weekly 延续当前任务重复语义，分别按时分、星期及时分创建重复日历触发器。
7. 任务时间或重复规则修改后，先取消旧请求，再以服务端最新任务重建。

#### 4.3 系统通知权限

任务默认开启是业务意愿，系统权限是设备能力，两者独立：

- `notification_enabled=true` 且系统已授权：创建本地通知。
- `notification_enabled=true` 且权限未决定：首次创建任务成功后展示应用内说明，用户确认后请求系统权限。
- `notification_enabled=true` 且权限已拒绝：任务仍创建成功，开关仍保持开启；详情页展示“系统通知未开启”，并提供前往系统设置入口。
- 用户稍后恢复系统权限：App 前台恢复或任务同步时批量补建通知。

#### 4.4 通知数量保护

iOS 对待发送本地通知数量有限。业务上所有任务都默认开启，但设备投影不能无限注册：

1. 候选集合为当前账号所有 `pending && notification_enabled` 且存在未来触发时间的任务。
2. 按下一次触发时间从近到远排序。
3. 建议最多注册 48 条，给用药提醒和其他业务通知预留系统余量。
4. 超出部分仍保持 `notification_enabled=true`，但标记为“等待补齐”，不篡改服务端字段。
5. 创建、完成、取消、关闭通知、前台恢复和增量同步后重新计算，自动把后续任务补入。
6. 详情页应区分“已开启并已调度”和“已开启，等待系统补齐”，避免用户误解。

### 验收标准

- 任一任务类型通过任一正式创建入口保存后，响应字段默认为 true。
- 服务端返回真实任务后才创建本地通知。
- 医疗任务使用 reminderTime，其他任务优先使用 startTime。
- 权限拒绝不影响任务创建，也不把服务端字段改成 false。
- 超出设备上限时任务仍保持开启，并能在名额释放后自动补齐。
- 本地预览模式不创建通知，只有“保存为真实任务”成功后创建。

### 技术细节与设计代码位置

当前 `TaskManager.createTaskReturningTask` 已在服务端创建成功后调用 `TaskNotificationManager.registerTaskNotification`，可作为收口点。改造后不能只判断 `status == pending`，还必须判断 `notificationEnabled` 和权限状态。

建议参考用药提醒的职责拆分，新增任务提醒编译/同步协调能力，或至少在 `TaskManager` 内保持单一 `reconcileNotification(for:)` 入口，避免 `loadInitial`、`syncIncremental`、`createTaskReturningTask` 和 `updateTask` 分别复制判断。

## 五、任务详情通知开关

### 需求说明

任务详情页新增“任务通知”区域，允许用户关闭或重新开启当前任务的通知。创建页不展示该开关，新任务始终默认开启。

### 基础要求与业务规则

#### 5.1 页面位置与展示

通知区域放在任务详情的“基本信息”卡片之后、“业务面板”之前，包含：

```text
任务通知                         [开关]
提醒时间：今天 19:30
状态：已安排 / 系统通知未开启 / 等待补齐 / 提醒时间已过
```

状态文案规则：

| 服务端开关 | 系统权限 | 本地请求 | 展示状态 |
| --- | --- | --- | --- |
| false | 任意 | 无 | 通知已关闭 |
| true | denied | 无 | 已开启，系统通知未开启 |
| true | authorized | pending 存在 | 已安排提醒 |
| true | authorized | 因上限未注册 | 已开启，等待补齐 |
| true | authorized | 时间已过 | 已开启，提醒时间已过 |
| true | authorized | 注册失败 | 已开启，创建通知失败，可重试 |

#### 5.2 关闭通知

关闭采用本地即时生效、服务端失败补偿：

```text
用户关闭开关
  ↓
UI 进入 saving(false)
  ↓
立即移除本机 pending + delivered 通知
  ↓
PATCH notification_enabled=false
  ├─ 成功：更新 TaskManager 中任务并保持关闭
  └─ 失败：开关回滚为 true，重新注册本地通知并提示保存失败
```

关闭只影响通知，不改变任务 `status`，也不创建执行记录。

#### 5.3 重新开启通知

```text
用户开启开关
  ↓
PATCH notification_enabled=true
  ↓
更新本地任务
  ↓
检查系统权限和可用时间
  ├─ 可调度：创建通知
  ├─ 未决定：展示说明后申请权限
  ├─ 已拒绝：保持开关开启并提示去系统设置
  └─ 时间已过/缺失：保持开关开启并提示编辑时间
```

服务端写入成功但本地通知创建失败时，不回滚服务端开关；这是“业务意愿已开启、设备投影失败”的部分成功状态。页面提供重试入口，App 前台恢复时再次补齐。

#### 5.4 并发和重复点击

1. 保存期间禁用开关，避免连续 PATCH。
2. 以服务端最后响应为准；旧请求响应不得覆盖新操作。
3. 可使用任务级 serial key：`task.notification.toggle.{taskID}`。
4. 增量同步与本地切换并发时，当前进行中的用户操作优先；完成后再合并更新版本。
5. 重复设置相同值必须幂等，不重复创建多个本地通知。

#### 5.5 重复任务

当前客户端任务模型未单独暴露 `TaskPlan` 标识，因此本期 `notification_enabled` 按当前 `Task` 记录生效：

- 对 `repeatType=none`，关闭当前一次通知。
- 对 `daily/weekly`，关闭该 Task 对应的整个重复通知请求。
- 后续服务端若明确区分任务实例和计划，再增加“仅本次 / 整个计划”的通知开关范围；本期不虚构计划级接口。

### 验收标准

- 详情页能看到服务端真实开关值和本机调度状态。
- 关闭后 pending 和 delivered 通知立即清理。
- 服务端关闭失败时开关回滚，用户看到明确错误。
- 开启后权限拒绝时开关仍为开启，并提供系统设置入口。
- 重复点击不会创建重复通知。
- 关闭通知不会完成、取消或删除任务。

### 技术细节与设计代码位置

`TaskDetailView` 当前已经有基本信息卡片、业务面板和执行操作，适合新增独立 `taskNotificationSection`。状态和 mutation 不应直接写在 View 中，建议由 `TaskManager.setNotificationEnabled(taskID:enabled:)` 统一执行网络更新、任务合并、本地通知注册/清理和错误补偿。

## 六、通知内容、标识和点击路由

### 需求说明

任务通知必须能被统一通知代理识别，前台只展示应用内 banner，用户点击系统通知或应用内 banner 后进入对应任务详情，而不是只打开首页。

### 基础要求与业务规则

#### 6.1 通知文案

建议首期文案：

```text
标题：任务提醒
正文：你有一个待完成任务：晚饭后散步
```

任务标题可能包含健康信息，后续可增加隐私设置；本期延续当前 `TaskNotificationManager` 已有文案，不在 payload 中放完整描述、执行记录或关联医疗内容。

#### 6.2 通知标识

当前 `task_{taskID}` 缺少账号隔离。建议统一为：

```text
task_{accountID}_{taskID}
```

如果服务端返回 `notification_id`，也必须满足账号级唯一；客户端不能直接信任空值或跨账号重复值。

#### 6.3 userInfo

建议本地通知 payload：

```json
{
  "type": "task_reminder",
  "route": "task_detail",
  "account_id": 265,
  "member_id": 509,
  "task_id": 123,
  "notification_id": "task_265_123",
  "scheduled_at": "2026-08-16T19:30:00+08:00"
}
```

仅保存路由所需最小字段，不把 payload 当作任务详情事实源。

#### 6.4 点击路由

```text
点击任务通知
  ↓
PushAdapter 读取 userInfo
  ↓
识别 type=task_reminder
  ↓
校验当前账号 == account_id
  ↓
切换到 member_id 对应成员上下文
  ↓
从 TaskManager 查找 task_id
  ├─ 未加载：先同步/按 ID 拉取
  ├─ 已取消或无权限：提示任务不可用
  └─ 可用：打开 TaskDetailView(taskID)
```

前台收到通知时：

1. `PushAdapter.willPresent` 不展示系统 banner。
2. 通过 `NotificationClient` 展示可点击应用内 banner。
3. 点击应用内 banner走相同任务 LaunchIntent。
4. 如果当前已经打开该任务详情，只刷新任务，不重复压入路由。

当前 `NotificationEnvelope` 已支持 `open_task(task_id)`，但 `HandleRemoteNotificationUseCase` 尚未把该目的地落到任务详情路由；本需求需要补齐这一消费链路。

### 验收标准

- 通知 ID 包含账号和任务 ID，可按账号批量清理。
- 前台不会同时出现系统 banner 和应用内 banner。
- 冷启动、后台点击、前台 banner 点击都进入同一任务详情。
- 账号不匹配、任务不存在、成员无权限时不展示任务内容。
- 点击通知后从服务端或本地任务事实源加载详情，不直接信任 payload 文案。

### 技术细节与设计代码位置

可复用 `PushAdapter` 的统一 delegate、`NotificationClient` 应用内 banner、`NotificationEnvelope.openTask` 白名单动作和现有 `AppRouteStore`。建议新增 `TaskReminderLaunchPayload` / `TaskReminderLaunchIntent`，其模式与用药提醒一致，但不需要剂次数组和成员归属判断。

## 七、通知同步、重建与清理

### 需求说明

本地通知是服务端任务状态在单台设备上的投影。创建、编辑、同步、执行和账号生命周期变化后，都必须通过统一协调逻辑对齐。

### 基础要求与业务规则

#### 7.1 必须触发对齐的事件

| 事件 | 期望行为 |
| --- | --- |
| 创建任务成功 | 默认开启并注册通知 |
| 编辑标题 | 更新通知正文 |
| 编辑时间/重复规则 | 删除旧请求并创建新请求 |
| 详情关闭通知 | 清理 pending 和 delivered，服务端同步 false |
| 详情开启通知 | 服务端同步 true，按权限和时间注册 |
| 初始加载 | 批量重建当前账号可见任务通知 |
| 增量同步 | 按服务端开关和状态增删改通知 |
| 完成任务 | 清理任务通知 |
| 跳过/失败并终结任务 | 清理任务通知；若业务仍为 pending 则按真实状态处理 |
| 取消/删除任务 | 清理 pending 和 delivered |
| 前台恢复 | 检查权限、时间变化和待补齐任务 |
| 时区变化 | 按当前本地时区重建 |
| 账号切换/退出 | 清理旧账号全部任务通知 |

#### 7.2 批量重建顺序

```text
读取当前账号最新任务
  ↓
筛选 pending && notification_enabled
  ↓
计算每个任务下一次提醒时间
  ↓
过滤时间缺失或已过期的一次性任务
  ↓
按下一次提醒时间排序并截取可调度数量
  ↓
清理当前账号旧任务通知
  ↓
注册新集合
  ↓
记录成功数、失败数、等待补齐数和最近重建时间
```

#### 7.3 失败保护

1. 任务列表或增量同步请求失败时，不用空集合清除现有通知。
2. 只有拿到可信任务快照后才执行全量重建。
3. 单条注册失败不阻止其他任务注册。
4. 服务端开关同步成功、本地注册失败属于部分成功，保留 true 并等待重试。
5. 服务端关闭失败时执行补偿，恢复本地通知。
6. 批量重建过程中 App 退后台不应留下“旧通知全删、新通知只注册一半”的不可恢复状态；需要记录重建结果并在下次前台继续。

### 验收标准

- 初始加载和增量同步都尊重 `notification_enabled`。
- 服务端同步失败不会错误清空全部本地通知。
- 标题、时间和重复规则变化后旧通知被替换。
- 完成、取消和关闭通知后，通知中心不残留可点击旧通知。
- 账号切换后不会收到旧账号任务通知。
- 时区变化后任务按新的本地时间触发。

### 技术细节与设计代码位置

当前 `TaskManager` 在四处直接调用 `TaskNotificationManager`，已经具备基本对齐点，但缺少统一条件、权限、账号清理和批量上限。建议收口为 `TaskNotificationSyncCoordinator` 或 `TaskManager.reconcileNotifications(...)`，并参考 `MedicationReminderSyncCoordinator` 的可信快照、防抖、前台重建和错误保留策略。

## 八、整体业务流程

### 8.1 创建任务成功路径

```text
TaskCreateView / 会话任务卡片 / 其他业务入口
  ↓
构造 TaskCreatePayload(notification_enabled=true)
  ↓
TaskService POST /api/v1/tasks/
  ↓
服务端保存 Task.notification_enabled=true
  ↓
返回带真实 task_id 的 HealthTask
  ↓
TaskManager 合并任务
  ↓
检查 pending + enabled + 时间 + 系统权限
  ↓
TaskNotificationManager 创建本地通知
  ↓
列表和详情展示“通知已开启/已安排”
```

### 8.2 详情关闭成功路径

```text
用户在 TaskDetailView 关闭通知
  ↓
立即移除本机通知
  ↓
PATCH notification_enabled=false
  ↓
服务端更新 updated_at
  ↓
客户端合并响应
  ↓
其他设备通过 /tasks/sync/ 收到 false
  ↓
其他设备清理对应本地通知
```

### 8.3 失败、重试和恢复

- 创建任务失败：不创建本地通知，不保留草稿通知 ID。
- 任务创建成功但通知注册失败：任务创建仍成功，详情显示失败状态并允许重试。
- 关闭服务端同步失败：回滚开关并恢复通知。
- 开启服务端同步成功但系统权限拒绝：开关保持开启，引导系统设置。
- 增量同步失败：保留当前通知，下一次前台或手动刷新重试。
- 点击已失效通知：清理该通知并提示任务不可用。

### 8.4 取消、并发和幂等

- 保存任务过程中用户取消页面：未获得服务端 task_id，不创建通知。
- 同一任务相同 notification ID 重复注册时先移除旧请求再新增。
- 同一任务通知开关更新使用任务级串行键，后发意图覆盖先发意图。
- App 多处同时触发重建时合并/防抖，只允许一个可信快照执行。
- 服务端 PATCH 相同值应幂等。

## 九、状态模型

| 状态 | 进入条件 | 用户可见结果 | 退出条件 |
| --- | --- | --- | --- |
| 默认开启 | 新任务创建，服务端返回 true | 通知开关开启 | 开始权限和调度检查 |
| 权限未决定 | 系统状态 notDetermined | 应用内权限说明 | 用户继续或跳过 |
| 系统权限拒绝 | iOS denied | 开关开启，提示系统通知未开启 | 用户前往设置并授权 |
| 调度中 | 正在添加/替换本地请求 | 开关禁用，可显示加载状态 | 成功或失败 |
| 已安排 | pending request 存在 | 显示下一次提醒时间 | 触发、编辑、关闭、执行 |
| 等待补齐 | 开启但因数量限制未注册 | 显示等待补齐 | 名额释放或前台重建 |
| 时间已过 | 一次性触发时间早于当前时间 | 提示编辑任务时间 | 用户修改时间或关闭通知 |
| 注册失败 | `UNUserNotificationCenter.add` 失败 | 提示重试 | 重试成功或关闭通知 |
| 关闭同步中 | 用户关闭，PATCH 未完成 | 开关关闭且禁用 | 服务端成功或回滚 |
| 已关闭 | 服务端 false | 无本地通知 | 用户重新开启 |
| 已终结 | completed/canceled 或明确终结 | 无本地通知 | 无；如任务重新打开则重新评估 |
| 账号不匹配 | 点击通知账号与当前账号不同 | 不展示任务详情 | 切换正确账号后重新加载 |

## 十、数据与持久化

| 数据 | 所有者 | 存储位置 | 生命周期 | 清理时机 |
| --- | --- | --- | --- | --- |
| `notification_enabled` | 服务端任务域 | `Task` 表 | 与任务一致 | 任务删除 |
| 任务时间和重复规则 | 服务端任务域 | `Task` / 业务子表 | 与任务一致 | 任务删除 |
| `notification_id` | 服务端或客户端稳定规则 | Task 响应/本地请求标识 | 任务通知生命周期 | 任务删除或账号清理 |
| pending 本地通知 | iOS 系统 | `UNUserNotificationCenter` | 到点、替换或清理 | 完成、取消、关闭、账号退出 |
| delivered 本地通知 | iOS 通知中心 | `UNUserNotificationCenter` | 用户或 App 清理 | 完成、取消、关闭、失效点击 |
| 调度诊断状态 | 客户端运行时/可选本地诊断 | Task 通知协调器 | 当前账号会话 | 退出登录或重新计算 |
| 系统通知权限 | iOS | 系统设置 | App 安装期间 | 用户在系统设置修改 |

数据边界：

1. `notification_enabled` 是账号共享的任务偏好，其他设备应同步。
2. pending/delivered 是设备级状态，不上传为业务事实。
3. 不区分本人或家庭成员；只要当前账号可以访问任务，就参与本机通知候选集合。
4. 当前方案允许同一账号多设备分别提醒；跨设备主设备去重不在本期范围。
5. 退出登录必须清理当前账号前缀下的任务通知。

## 十一、错误模型

| 错误类别 | 触发条件 | 是否重试 | 用户反馈 | 清理/补偿动作 |
| --- | --- | --- | --- | --- |
| 创建任务失败 | POST 失败、字段校验失败 | 按网络层策略或用户重试 | 任务保存失败 | 不创建通知 |
| 缺少提醒时间 | enabled=true 且无可用时间 | 用户修正后重试 | 请设置任务时间 | 不创建通知 |
| 通知权限未决定 | 首次创建后未授权 | 用户触发 | 展示权限说明 | 不影响服务端 true |
| 通知权限拒绝 | 系统 denied | 前台检查/用户设置后重试 | 系统通知未开启 | 保留服务端 true |
| 本地注册失败 | center.add 抛错或数量限制 | 是 | 创建通知失败/等待补齐 | 保留任务与服务端 true |
| 关闭同步失败 | PATCH false 失败 | 是 | 关闭通知失败 | 回滚 true 并恢复通知 |
| 开启同步失败 | PATCH true 失败 | 是 | 开启通知失败 | 保持 false，不注册通知 |
| 增量同步失败 | `/tasks/sync/` 失败 | 是 | 沿用现有同步错误提示 | 保留旧通知 |
| payload 无效 | 缺 task_id/account_id | 否 | 通知不可用 | 删除该本地通知 |
| 账号不匹配 | 点击其他账号通知 | 切换账号后可恢复 | 该提醒属于其他账号 | 不打开详情 |
| 任务不存在/无权限 | 点击后查询 404/403 | 否 | 任务已失效或无权限 | 删除该通知 |
| 并发响应乱序 | 快速切换开关 | 自动处理 | 无额外弹窗 | 丢弃旧 revision 响应 |

## 十二、与其他模块的接口边界

### 本模块负责

- 任务级通知开关的展示和更新。
- 默认开启规则。
- 服务端字段同步。
- 本地通知创建、替换、补齐和清理。
- 系统通知权限状态展示。
- 通知点击进入任务详情。
- 账号级隔离、失败补偿和诊断日志。

### 本模块不负责

- 判断任务应不应该创建。
- 自动完成、跳过或失败任务。
- 从通知 Action 直接写执行记录。
- 区分本人和非本人任务。
- 服务端 APNs 到点推送。
- 多设备主设备选择和跨设备去重。
- 修改医疗医嘱或任务时间。
- 复杂安静时段、稍后提醒和通知分组策略。

### 上游调用方

- `TaskCreateView` 手动/AI 创建。
- 会话任务卡片保存流程。
- 报告或体检计划转任务流程。
- `TaskDetailView` 通知开关。
- `TaskExecutionRecorder` 完成/跳过/失败流程。
- App 登录、前台恢复和账号切换生命周期。

### 下游依赖

- `TaskService` 和 SparkService task API。
- `UNUserNotificationCenter`。
- `PushAdapter`、`NotificationClient` 和 `HandleRemoteNotificationUseCase`。
- `LaunchIntentCoordinator`、`AppRouteStore` 和任务详情路由。

### 输入和输出契约

输入：服务端 `HealthTask`、当前账号 ID、系统通知权限、当前时间和日历。

输出：本地 `UNNotificationRequest` 集合、详情页通知状态、通知点击 LaunchIntent、日志和错误反馈。

## 十五、当前实现、缺口与演进

### 当前实现

1. `TaskNotificationManager` 已能使用 `UNCalendarNotificationTrigger` 创建、更新和删除任务通知。
2. `TaskManager` 已在初始加载、增量同步、创建、更新、完成和取消时处理通知。
3. 任务通知当前已覆盖所有 pending 任务，没有本人/非本人判断。
4. `PushAdapter` 已统一接管系统通知前台和点击回调。
5. `NotificationEnvelope` 已定义 `openTask(taskID)` 白名单动作。

### 当前缺口

1. 服务端和客户端任务模型没有 `notification_enabled`。
2. 详情页不能关闭或重新开启通知。
3. 当前所有 pending 任务无条件注册，无法同步用户意愿。
4. 创建页只有医疗任务有显式提醒时间；通用任务缺少通知状态说明。
5. 任务通知没有 userInfo，点击后不能稳定进入任务详情。
6. 通知 ID 缺少账号前缀，账号切换存在残留风险。
7. 没有显式权限协调、数量保护、可信快照重建和失败补偿。
8. 没有任务通知专项测试。
9. 服务端源码不在当前工作区，字段落点、`TaskNotification` 关系和迁移必须在 SparkService 工程二次核对。

### 建议演进顺序

1. 服务端增加字段、迁移、serializer 和 sync 契约。
2. 客户端模型/payload 兼容新字段，所有创建入口显式默认 true。
3. `TaskManager` 收口通知对齐规则，完成账号级 ID 和批量重建。
4. 详情页增加通知状态和开关，落地失败补偿。
5. 补任务通知 payload、LaunchIntent 和任务详情路由。
6. 补权限说明、系统设置入口和前台应用内 banner。
7. 完成服务端、客户端和手工验收测试。
8. 后续再评估隐私文案、多设备去重、服务端 APNs 兜底和计划级开关，不混入本期。

## 十六、整体验收标准

- [ ] 所有新建任务默认 `notification_enabled=true`。
- [ ] 手动、AI、会话卡片和其他真实创建入口遵循相同规则。
- [ ] 医疗、运动、饮食任务都能创建通知，不区分本人或非本人。
- [ ] 创建页不提供关闭入口，详情页可以关闭和重新开启。
- [ ] 详情开关通过服务端字段同步，其他设备增量同步后能执行相同开关结果。
- [ ] 系统权限拒绝不会导致任务创建失败，也不会把服务端字段错误改成 false。
- [ ] 任务标题、时间或重复规则变化后，本地通知被正确替换。
- [ ] 完成、取消、关闭或任务失效后，pending 和 delivered 通知均清理。
- [ ] 通知点击能校验账号和成员，并进入对应任务详情。
- [ ] 前台只展示应用内 banner，不重复展示系统 banner。
- [ ] 通知 ID 支持账号级清理，退出登录和账号切换无残留。
- [ ] 超过设备通知容量时有排序、等待补齐和可见状态，不静默丢失。
- [ ] 服务端请求失败、本地注册失败和并发切换都有明确补偿和重试策略。
- [ ] 新旧服务端灰度期间字段缺失不会导致任务列表解码失败。
- [ ] 服务端和客户端均有针对默认值、同步、开关、权限、路由和清理的测试证据。
