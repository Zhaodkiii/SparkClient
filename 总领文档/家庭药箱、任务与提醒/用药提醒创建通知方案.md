# 用药提醒创建通知方案

> 文档性质：基于当前 SparkClient 代码的功能审计与实现方案。本文只分析“用药计划如何创建、更新和清理本地通知”，不修改业务代码。\n+
## 一、模块目标

把已保存的 `RemoteMedicationPlan` 编译为当前设备未来一段时间内的本地用药通知，并保证计划变更、用药打卡、账号切换、权限变化和时区变化不会产生明显的旧通知或重复通知。

首版推荐采用：

```text
服务端保存用药计划/记录
        ↓
客户端查询当前账号可提醒计划与记录
        ↓
MedicationReminderScheduleCompiler 编译未来 7 天
        ↓
同一成员同一分钟聚合为一条通知
        ↓
UNUserNotificationCenter 注册本地通知
        ↓
点击后进入用药执行中心并定位成员、日期、剂次
```

服务端 APNs 不作为首版到点提醒通道；现有 APNs/远程通知能力保留给成员协同和资源变更等场景。

## 三、创建通知能力分析

### 3.1 计划与记录作为编译输入

#### 需求说明

只有满足以下条件的计划才进入编译：`status == active`、`reminderEnabled == true`、存在提醒时间、计划未结束；计划频次由 `frequencyType`、`everyNDays`、`weeklyWeekdays`、`startDate`、`endDate` 和 `reminderTimes` 共同决定。

#### 基础要求与业务规则

- `RemoteMedicationRecord` 是服药事实，已完成剂次不能再次生成提醒。
- 通知只是提示，不是服药事实；用户点击后仍需在执行中心保存记录。
- `startDate` 必须作为 every-n-days 的周期锚点，不能以当前日期重新计算周期。
- 结束日期建议按“包含结束日”解释，并由 `MedicationExecutionPlanner` 与提醒编译器保持一致。
- 当前账号、成员访问权限和计划级本机授权由服务端聚合接口共同决定，客户端不应自行放宽范围。

#### 技术细节与设计代码位置

现有 `listMedicationReminderEnabledPlans` 请求 `/api/v1/medical/medication-reminders/enabled-plans/`，支持日期窗口和 `include_records`；`MedicationReminderSyncCoordinator.loadSnapshots` 使用 `includeRecords = true`，随后把每个成员组转换为编译输入。

#### 验收标准

- 关闭提醒、停用计划、已结束计划不会生成通知。
- 已完成剂次不会生成新的通知。
- every-n-days、weekly、多提醒时间点的结果与执行中心展示一致。
- 服务端查询失败时不能用不完整快照覆盖现有通知。

### 3.2 未来窗口编译与聚合

#### 需求说明

当前窗口为从 `now` 到未来 7 天，最多限制为 14 天；同一成员同一分钟的多个剂次聚合成一条通知，以减少系统通知数量和打扰。

#### 基础要求与业务规则

- 事件按 `scheduledAt` 从近到远排序。
- 全局最多注册 48 条；超出时保留较近的通知，并记录截断日志。
- 事件 ID 必须可重复计算，至少包含账号、成员、触发分钟和剂次集合摘要。
- `UNCalendarNotificationTrigger` 使用本地年月日时分，不依赖到点时的网络。

#### 技术细节与设计代码位置

`MedicationReminderScheduleCompiler` 生成 `MedicationReminderEvent`；`MedicationReminderNotificationManager.register` 将事件转换为 `UNNotificationRequest`，payload 只保存账号、成员、通知 ID、计划 ID、剂次序号和 scheduledAt，不放诊断等敏感医疗详情。

#### 验收标准

- 相同输入重复编译得到语义一致的事件集合。
- 同成员同一分钟只有一条系统通知。
- 48 条上限触发时不崩溃，日志可定位被截断数量。
- 默认通知文案不显示药品名，账号偏好开启后才允许显示药品名。

### 3.3 通知注册、更新与清理

#### 需求说明

计划变化不能只新增通知，必须以当前账号最新快照进行重建，清理旧的 pending 和 delivered 通知。

#### 基础要求与业务规则

统一重建入口为 `MedicationReminderSyncCoordinator`：

- 创建/编辑/删除/停用计划后重建。
- 执行中心完成或跳过剂次后，先按账号、成员、时间和剂次清理，再重建。
- 前台恢复、冷启动、时区变化后按需重建。
- 退出登录或切换账号前清理旧账号通知。
- 权限拒绝时计划仍可保存，但必须向用户展示提醒不可用状态。

#### 技术细节与设计代码位置

`MedicationReminderNotificationManager.rebuild` 先调用 `removeAllMedicationNotifications(forAccountID:)`，再逐条 `center.add`；`handleDoseCompleted` 调用 `removeNotifications` 清理当前剂次并触发即时重建。

#### 验收标准

- 编辑提醒时间后，旧时间通知不再存在。
- 关闭提醒、删除或停用计划后，pending 和 delivered 都清理。
- 打卡一个剂次不影响同成员同计划其他未来剂次。
- 网络失败时保留旧通知，避免一次临时失败造成整组提醒消失。

## 四、整体业务流程

### 4.1 创建/编辑计划后的通知流程

```text
用户在 MedicationPlanForm 修改提醒开关/频次/时间
  ↓
保存计划到服务端成功
  ↓
HomeMedicalRouteSupport 或 MedicationReminderPostSaveController 发起 plan_changed
  ↓
SyncCoordinator 取消旧的防抖任务并立即重建
  ↓
检查系统通知权限
  ├─ 未授权：停止注册，保留计划，提示用户开启权限
  └─ 已授权
       ↓
查询 enabled-plans + 窗口内 records
       ├─ 查询失败：保留旧通知并记录日志
       └─ 查询成功
            ↓
按成员编译未来 7 天剂次
            ↓
过滤已完成剂次并按成员/分钟聚合
            ↓
限制最多 48 条
            ↓
清理当前账号旧 pending/delivered 通知
            ↓
注册新 UNNotificationRequest
```

### 4.2 点击通知流程

```text
用户点击本地通知
  ↓
HandleRemoteNotificationUseCase 解析 type=medication_reminder
  ↓
生成 MedicationReminderLaunchIntent
  ↓
校验当前登录账号 == payload.accountID
  ↓
等待 memberID 可用并切换成员
  ↓
等待医疗首页数据完成
  ↓
路由到 medicationPlans + MedicationExecutionInitialFocus
  ↓
执行中心定位 scheduledAt 和 planID/doseSequence
  ↓
打开 MedicationExecutionLogSheet
```

## 五、状态模型

| 状态 | 来源 | 处理 |
| --- | --- | --- |
| 未决定权限 | iOS `notDetermined` | 先展示应用内说明，再请求系统权限 |
| 已授权 | `authorized/provisional/ephemeral` | 允许编译和注册 |
| 已拒绝 | `denied` | 不注册；引导系统设置；计划仍可保存 |
| 查询中 | SyncCoordinator 重建任务 | 防止并发重建，保留当前通知 |
| 查询失败 | enabled-plans 请求异常 | 保留旧通知，记录原因，等待下一次前台/手动重建 |
| 已注册 | 本地 pending request 存在 | 等待系统触发 |
| 已送达 | delivered request 存在 | 点击或清理后结束 |
| 已完成/跳过 | RemoteMedicationRecord 已保存 | 清理匹配剂次通知 |
| 账号不匹配 | payload.accountID 不同 | 不打开医疗内容，提示提醒属于其他账号 |
| 成员不可用 | 成员不存在或无权限 | 终止路由并提示提醒已不可用 |

## 六、数据与持久化

### 6.1 数据归属

- 服务端：`MedicationPlan` 和 `MedicationRecord` 是事实源。
- 本地系统：`UNNotificationRequest` 是设备级的临时提醒投影，不是医疗数据事实源。
- 本地偏好：药品名是否显示按账号写入 `UserDefaults`。
- 通知 payload：只保存跳转所需的最小定位数据。

### 6.2 账号与成员隔离

通知 ID 和 payload 都含 `accountID`；成员 ID 用于路由和清理。退出登录、账号切换时必须清理旧账号通知，避免共享设备泄漏或误提醒。

### 6.3 时区

当前实现以 `Calendar.current` 编译，并在 `rebuildIfStale` 中检测 `TimeZone.current.identifier` 变化后重建。建议继续保持“按设备当前本地时间提醒”，但编译器内部不应再使用未注入的 `Calendar.current`/`Date()` 判断计划有效期，应统一使用 `MedicationReminderCompileInput.calendar` 与 `input.now`，以便测试和避免边界漂移。

## 七、错误模型与当前缺口

### 7.1 当前已覆盖

- 权限未授权时不注册。
- enabled-plans 查询失败时保留旧通知。
- 通知数量超限时按时间截断并记录日志。
- payload 解析失败的通知可标记为 invalid。
- 账号不匹配、成员不可用时不进入医疗页面。

### 7.2 建议优先修正

1. `MedicationReminderScheduleCompiler.eligiblePlans` 使用 `Calendar.current` 和 `Date()`，与传入测试时钟不一致；应改为使用输入的 `calendar` 和 `now`。
2. `MedicationReminderNotificationManager.register` 的触发器使用 `Calendar.current`，应使用事件生成时的时区/日历语义，并增加跨夏令时测试。
3. `groupHash` 使用 Swift `Hasher`；其哈希结果不保证跨进程稳定。虽然重建前会清理旧通知，但管理、诊断和跨版本一致性更适合使用 SHA-256 或确定性字符串编码。
4. 48 条是业务保护阈值，不应默认为系统能力上限；需要在管理页明确“部分远期提醒未注册”或增加补齐动作，否则用户可能误以为全部提醒已覆盖。
5. 当前自动化测试目录只有通用通知 envelope 测试，必须补充编译器、通知管理器和点击路由测试。
6. 服务端授权接口已存在，后续应明确“本人计划”和“非本人计划”的授权失败/撤销后是否立即清理本机通知，避免客户端展示旧授权结果。

## 八、与其他模块的接口边界

本模块负责：提醒规则编译、本地通知注册/清理、通知权限、通知点击后的执行中心定位。

本模块不负责：修改医嘱、自动生成服药事实、判断漏服、发送首版 APNs、跨设备主设备选举、药物相互作用判断。

上游调用方：用药计划表单、用药列表、成员医疗档案、用药执行中心、App 生命周期和账号会话。

下游依赖：MedicalQueryAPI、MedicationExecutionPlanner、UNUserNotificationCenter、LaunchIntentCoordinator、AppRouteStore。

## 九、测试策略

### 9.1 单元测试

- daily / weekly / every-n-days 的日期展开。
- startDate、endDate、时区和夏令时边界。
- 已完成剂次过滤、跳过状态、多个 reminderTimes。
- 同成员同一分钟聚合，不同成员不聚合。
- 通知 ID 的确定性和账号/成员隔离。
- 超过 48 条的截断策略。

### 9.2 集成/组件测试

- `NotificationManager` 注册、重建、单条清理、账号清理、delivered 清理。
- 权限状态到重建行为的映射。
- 服务端查询失败保留旧通知；成功后替换旧通知。
- 打卡后只删除匹配剂次。

### 9.3 手工验收

- 冷启动、后台点击、前台 banner 点击三条路径。
- 账号切换、退出登录、成员无权限。
- 修改提醒时间、关闭计划、删除计划。
- 无网时到点提醒；点击后离线进入执行中心的降级表现。
- 通知中显示药品名开关关闭/开启。

## 十、实施顺序建议

1. 先补纯函数编译器测试，并统一 `input.now`/`input.calendar`。
2. 补通知管理器抽象和可测试的 fake notification center。
3. 补计划变更、打卡、账号生命周期的集成测试。
4. 明确通知管理页的“pending/delivered/invalid/截断”用户语义。
5. 最后再评估 APNs 兜底、多设备去重和家属代提醒，不与本地通知首版混做。

## 十一、整体验收标准

- 用药计划保存成功后，授权设备能注册未来窗口内的本地提醒。
- 提醒到点无需网络即可触发。
- 编辑、关闭、删除、停用计划不会留下旧通知。
- 打卡/跳过当前剂次后不再重复提醒，其他剂次不受影响。
- 同成员同一分钟通知聚合，默认不泄露药品名称。
- 点击通知能校验账号、切换成员并打开执行中心记录 Sheet。
- 账号切换和退出登录不会显示旧账号的医疗提醒。
- 时区变化后按新本地时间重建。
- 服务端暂时不可用时不以空数据覆盖已有提醒。
- 规则编译、通知注册、权限、点击路由和账号隔离均有自动化或可重复手工验收证据。
