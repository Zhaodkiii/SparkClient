## 一、模块目标

本模块负责把用户在作曲器中的文本、附件、小任务和健康资源引用，编排成一次可取消的本地优先发送流程：附件先上传并可选 OCR，用户消息落库，助手消息通过 `MessageRunActor` 流式写入，再经 Outbox / `ChatSyncEngine` 上送到远端，并在入站合并后按需下载附件。

当前实现形态是 **本地优先落库 + 流式 AI 编排 + Outbox 异步写回 + REST 增量同步 / WebSocket 提示 + 附件下载任务表**：

```text
HanlinChatInputView / ChatView
        ↓
ChatDetailViewModel.sendCurrentDraft
        ↓
SendChatMessageUseCase.execute
   ├─ FileTransferService.upload + OCROrchestrator
   ├─ ChatRepository.appendMessage（用户消息 deliveryState=.pending）
   ├─ MessageRunActor.startAssistantMessage（.sending）
   └─ ChatOrchestrator.generateReply → 流式 ChatRunEvent
        ↓
MessageRunActor.apply / finalize → deliveryState=.pending
        ↓
ChatSyncSupervisor（DB 变更防抖）→ ChatSyncEngine.pushOutboxOnly
        ↓
ChatOutboxPipeline → SparkChatRemoteAPI.push / pushBlockUpdates
        ↓
入站：pull → ChatInboundPipeline → upsert + 附件下载 Job
        ↓
ChatAttachmentPipeline.processPendingJobs → FileTransferService.download
```

目标边界：

- 负责发送校验、附件预处理与发送时兜底上传、用户/助手消息写入、流式块修订、投递状态、Outbox 上送、入站合并触发的附件下载。
- 不负责会话列表投影、消息窗口滚动策略、AI 网关 SSE 细节、工具授权弹窗、问报告选择器 UI。
- Guest 聊天（`GuestChatView` / `GuestAIChatClient`）是独立简化路径，不经过本管线的 Core Data Outbox；本文仅标注边界，不展开 Guest 实现。

## 三、消息发送编排

### 需求说明

用户在会话详情点击发送后，客户端必须完成输入校验、模型解析、附件就绪、用户消息本地持久化、助手流式生成与最终快照返回，并允许用户中途取消。

### 基础要求与业务规则

- 入口：`ChatDetailViewModel.startSendingCurrentDraft` → `sendCurrentDraft`；UI 绑定 `HanlinChatInputView.onSend` / `ChatView`。
- 发送互斥：`stateStore.isSending == true` 或已有 `currentGenerationTask` 时不得开启新一轮生成。
- 输入合法性：`sanitizedInput`、`composerAttachments`、`smallTask`、`healthResourceRefs` 至少一项非空；否则抛 `ChatFeatureError.emptyInput`。
- 附件阻塞：`hasBlockingPreparedAttachmentWork` 为 true 时禁止发送；发送按钮同步禁用。
- 问报告校验：发送前执行 `HealthResourceSendValidator.validate`（`maxRefs = 5`、线程必须有有效 `memberID`、每条 ref 的 `memberID` 必须一致且 `resourceID > 0`）；失败用通知提示，不进入 UseCase。
- 模型解析：作曲器选中模型 → 线程已有模型 → 场景默认；找不到 chat 场景模型抛 `AIConfigError.missingModelForScenario(.chat)`。
- 线程解析：已有 `threadID` 则加载并设为 active；否则用 active 线程；再否则 `createThread`（标题取输入前缀 18 字，图片投递模式取 `catalogSnapshot.defaultThreadImageDeliveryModeRaw`）。
- 用户消息 `deliveryState = .pending`，`clientMessageID` 新建，`modelName = "user"`；助手消息由 `MessageRunActor.startAssistantMessage` 以 `.sending` 写入。
- 取消：`AIRuntimeCancellationToken`；用户取消后 `finalizeInterruptedAssistantMessage`，把 `assistantStatusCard` 写入同一助手消息并改为 `.pending`。

### 验收标准

- 有文本、仅附件、仅小任务、仅健康资源 refs 均可成功进入发送。
- 附件仍在上传/OCR/失败态时点击发送无效果，且发送按钮不可用。
- 用户消息落库后草稿清空，消息列表立即可见用户气泡。
- 助手流式过程中 UI 通过 DB 通知刷新，不依赖 `onAssistantPartial` 直推（当前 VM 传入 `nil`）。
- 取消后助手消息保留已生成内容与中断状态卡，且不再处于 `.sending`。
- 重复点击发送不会并行启动两次 `execute`。

### 技术细节与设计代码位置

#### `execute` 主链路（真实步骤）

```text
1. trim userInput；空输入守卫
2. aiConfigCenter.currentSnapshot / effectiveScenarioBundles
3. resolveThread → preferredModelName → resolvedRow
4. 可选 updateThreadGenerationConfig（仅当模型名变化）
5. effectiveChatImageDeliveryMode + chatMultimodalCapabilities
   → deliverMultimodal = directMultimodal && supportsMultimodal && 有附件
6. 遍历 composerAttachments：复用 prepared 或 upload+OCR → [ChatAttachment]
7. 组装 userBlocks（见下方顺序）→ appendMessage(.user, .pending)
8. loadMessages(history) → startAssistantMessage(.sending)
9. onUserMessagePersisted(snapshot)
10. memberContextSummary（有 health refs 时强制 ""）
11. ChatOutboundContextAssembler 组装 userQuestionForAI + healthResourceContext
12. orchestrator.generateReply(..., onPartial → messageRunActor.apply)
13. finalizeAssistantBlocks + 可选 finishReasonNotice
14. 返回 ChatThreadSnapshot
```

| 顺序 | 条件 | block.kind | 关键字段 |

## 四、作曲器附件预处理、上传与 OCR

### 需求说明

用户从相册、相机或文件选择器加入附件后，应在发送前完成 OSS/文件服务上传与 OCR（图片/文档），以便发送时可复用 `ChatPreparedAttachment`，并让 AI 在本地 OCR 模式下获得文本。

### 基础要求与业务规则

- 选择入口：`HanlinAttachmentSheet`（相册/相机/文件）→ `enqueueComposerAttachments`。
- 预处理阶段机：`pending → uploading → ocring → success | failed`。
- 上传统一走 `FileTransferService.upload`，`businessType = "chat_attachment"`，`businessId = previewID.uuidString`，`isPublic = false`。
- 图片：`OCROrchestrator.recognize(..., options: .fastPreview)`。
- 非图片文档：写临时文件后 `ocrDocumentExtractor.extractText`。
- 成功后写入 `ChatPreparedAttachment(previewID, kind, record, ocrText)`。
- 发送时若已有 prepared，直接 `ChatSendAttachmentAssembly.makeAttachment`；否则 UseCase 内兜底再上传+OCR（并回调上传进度）。UseCase 兜底路径对非图片 OCR 返回空文本引擎 `"none"`（与 VM 文档 OCR 不完全对称）。
- `ChatAttachment.url` 存远端 https（`publicHTTPSURLForObjectKey`）；本地 `file://` 不得写回该字段。

### 验收标准

- 选图后立刻显示上传进度；OCR 完成前发送按钮保持禁用。
- 预处理成功后发送不再重复上传（复用 `preparedAttachments`）。
- 预处理失败显示 `errorMessage`；**failed 也会阻塞发送**，需删除该附件或等待用户处理。
- 取消正在预处理的附件任务时清理进度与 prepared 状态。
- 落库后的附件块包含 `fileId` / `fullCacheKey` / `fileMd5`。

### 技术细节与设计代码位置

#### 阻塞发送判定（真实逻辑）

```text
hasBlockingPreparedAttachmentWork(threadID):
  if draft.attachments.isEmpty → false
  for attachment in draft.attachments:
    state = preparedStates[attachment.id]
    if state == nil → continue          // 尚无状态记录：不阻塞
    if state.phase == .success → continue
    else → true                         // pending/uploading/ocring/failed 均阻塞
  return false
```

## 五、流式助手 Run 与块写入

### 需求说明

一次 AI 回复的所有增量文本、推理、工具行与富卡片副作用，必须串行写入同一 `assistantClientMessageID`，通过稳定 block id + revision 合并，避免影分身卡片或旧流覆盖新文本。

### 基础要求与业务规则

- `MessageRunActor` 是单次 run 的唯一写入入口；UI 不直接改工具卡。
- `startAssistantMessage`：空 blocks、`deliveryState = .sending`，`id == clientMessageID == assistantClientMessageID`。
- `ChatRunEvent`：`assistantPartial` / `richBlockReady` / `toolSideEffect` / `finalizeAssistantBlocks`。
- Partial 默认 50ms（`50_000_000` ns）防抖落库；`generateStructuredHealthCard` 工具 partial 立即 flush。
- 流式块 `markPendingForSync: false`；定稿文本/非文本块与 ready 富块 `markPendingForSync: true`。
- `finalizeAssistantBlocks` 后助手消息改为 `.pending`，由 Outbox 接管；push 成功后 `.sent`。
- 结构化健康卡片 ready：若父消息已是 `.sent`，`requeueSentMessageForFullPush` 改回 `.pending`；并调用注入的 `pushOutbox`。
- 助手结束后按 `ChatMedicalDisclaimerTrigger` 追加免责声明块（`deliveryState != .sending` 时才追加）。
- 中断：flush partial → `assistantStatusCard` → `.pending`。

### 验收标准

- 同一 `toolCallID` 只对应一套稳定 tool / presentation block id。
- 迟到的健康卡片只能更新自身 revision，不能复制第二张卡。
- 流式过程中消息保持 `.sending`；完成后不为 `.sending`。
- 取消后消息仍可被 Outbox 上送（若有可同步内容）。

### 技术细节与设计代码位置

#### `ChatStableBlockID` 键模板

| 方法 | key 模板 |
| --- | --- |
| `textSegment(messageID:index:)` | `chat.message.{uuid}.block.text.{index}` |
| `reasoning(messageID:)` | `...block.reasoning` |
| `tool(messageID:toolCallID:)` | `...tool.{toolCallID}.row` |
| `rich(messageID:toolCallID:kind:)` | `...tool.{toolCallID}.rich.{kind}` |
| `rich(messageID:kind:)` | `...rich.{kind}` |
| `healthResource(...)` | `...health.{type}.{id}.{memberID}` |

算法：双 FNV 风格 hash → 16 字节 → UUID（version nibble `0x50`，variant `0x80`）。同输入永远同 UUID，保证跨流式/跨设备幂等 upsert。

#### revision 与 orderKey

- `revision`：单调本地修订号；`upsertMessageBlock` 忽略过期 revision。注释原文：`Monotonic local revision used by idempotent DB upserts.`
- `orderKey`：展示序，不依赖数组合并时机。默认：reasoning `900`、text `1000`、tool `2000`、富卡 `2100`、医疗风险 `2900`、免责 `3100`。
- 工具插入会切分文本段：`AssistantRunState.orderKeyForToolCall` 完成当前文本段后，tool 与后续文本各占一段 orderKey（步进 `1000`）。
- 工具展示块 orderKey = `toolOrderKey + 100`。

#### Partial 文本增量

`AssistantRunState.consumeAnswer` 优先按前缀差分追加；若流式重置则用 commonPrefix / suffix-prefix overlap（阈值 ≥ 64）避免重复拼接。

- `ToolSideEffectBlockMapper`

- `AssemblyProducts`：`pushOutbox: { try await chatSyncEngine.pushOutboxOnly() }`

## 六、Outbox 上送与投递状态

### 需求说明

本地已定稿或待同步的消息/块必须可靠上送到聊天远端 API，并依据 ACK 更新 `serverMessageID`、投递状态与块同步标记。

### 基础要求与业务规则

- Outbox 消息：`loadOutboxMessages` 谓词 `deliveryState == pending`，默认 limit 50。
- Pending blocks：`isPendingSync == YES`，且父消息 `deliveryState` 为 `sent` **或** `pending`（整包重推时父消息可能仍是 pending）。
- 上送顺序：先整包 `remoteAPI.push`，再 `pushBlockUpdates`。
- 单条：`markSending` → push → `applyPushAck` → `markSent` + `markMessageBlocksSynced`；失败 `markFailed`。
- block 推送遇到后端 `msg == "message_not_found"` 且 `data.client_message_id` 可解析时，父消息重新 `.pending`。
- 自动触发：`sparkChatDatabaseDidChange`；消息变更且 `affectsThreadList` 时 700ms 防抖 `pushOutboxOnly`；线程变更防抖 `pushSingleThread` + `syncNow`。

### 验收标准

- AI 定稿后无需用户手动同步即可进入 Outbox 上送。
- push 失败消息变为 `.failed`，可通过重试改回 `.pending`。
- 同一全局 scope 的并发上送由 `ChatSyncEngine` single-flight 合并。
- 结构化健康卡片晚到 ready 后仍能上送完整 blocks。

### 技术细节与设计代码位置

#### `pushOutbox` 伪代码

```text
pending = outboxStore.pending(limit: 50)
hasPendingBlocks = pendingBlocks(limit: 1) 非空
if pending.isEmpty && !hasPendingBlocks → return

for message in pending: markSending(.sending)

reload = repository.loadMessages(clientMessageIDs: pendingIDs)  // 必须重载最新 blocks
payload = map reload → [ChatRemoteMessageDTO]  // 附带线程采样字段
ack = remoteAPI.push(messages: payload)
applyPushAck(ack, pending: reload, pendingBlocks: [])
for message in reload: markSent(.sent) + markMessageBlocksSynced(all block ids)

pendingBlocks = outboxStore.pendingBlocks(limit: 100)
if 非空:
  ack2 = remoteAPI.pushBlockUpdates(...)
  markBlocksSynced
  applyPushAck(ack2, pending: [], pendingBlocks: ...)
  on failure → requeueMessagesForBlockPushFailure
```

#### `applyPushAck`

```text
for acceptedMessages[clientId]:
  applyPushMessageAck(clientId, serverMessageId, serverUpdatedAt)
  track max serverUpdatedAt per thread

for pendingBlocks matching acceptedBlockUpdates:
  applyPushMessageAck(clientId, serverMessageID: nil, serverUpdatedAt)
  track max per thread

for each thread maxDate:
  exclusiveDate = date + 0.001s
  saveMessageSyncCursor(ISO8601(exclusiveDate), for: threadID)
```

游标推进使用 **开区间**（+1ms），避免下次 pull 重复拿到刚 ACK 的同一条。

## 七、入站同步与附件下载管线

### 需求说明

打开会话、手动刷新或实时提示后，客户端拉取远端增量，与本地合并，并为可下载附件登记后台任务，最终由 `ChatAttachmentPipeline` 落盘到文件缓存。

### 基础要求与业务规则

- 对外入口：`ChatSyncSupervisor`：`syncNow`（仅上送）、`syncNowWithPull`、`refreshThreadListIncremental`、`pullThreadMessagesIncrementalOnOpen`、`kickAttachmentDrain`、`startRealtimeSync`。
- 进入会话：本地无消息 → `cursor = nil`；否则优先持久化消息游标，缺失时回退 `latestServerActivity` ISO8601。
- 列表刷新：只拉线程元数据，不拉正文，不主动上送 Outbox。
- 入站：`ChatInboundPipeline.applyRemoteMessages` → `ChatMergeEngine.resolve` → `upsertRemoteMessages`。
- 远端缺失线程在打开路径跳过，不把本地清空。
- Realtime hint 后**仅上送**，不拉取（当前策略）。
- 附件下载：pending → processing → cachedURL 命中或 download → completed / failed；**不**改写消息内 `ChatAttachment.url`。

### 验收标准

- 打开已有远端会话能看到增量消息且不重复造影。
- 本地较新消息不会被过期远端快照覆盖；用户图远端更富时可偏好远端。
- 下载失败标记 failed，不阻塞其他 job；登录后 `kickAttachmentDrain` 可继续消化。

### 技术细节与设计代码位置

#### 分页常量

```text
threadPageLimit = 100
messagePageLimit = 200
maxPagesPerRun = 20
```

`pullAndMerge`：有 `hasMore` 且页数 < 20 且 cursor **前进** 才继续；cursor 不变则停止，防死循环。

#### `enqueueAttachmentDownloadJobs` 现状

- Store 协议支持 `upsertRemoteMessages(..., enqueueAttachmentDownloadJobs:)`。
- `true` 时 `insertImageDownloadJobsIfNeeded`：仅处理 `imageGallery` / `fileAttachments` 中 `isChatImageLike` 且有有效 HTTPS 下载 URL 的附件；按 `imageDownloadDedupeKey` 去重。
- **当前 `ChatSyncEngine.pullAndMerge` 恒传 `false`**；协议 extension 默认也是 `false`。仓库内无生产调用点传 `true`。
- **当前缺口**：入站后自动入队下载能力已实现但未打开；UI 侧仍可通过 `FileTransferService` 按需下载预览。

#### 合并规则（`ChatMergeEngine`）

```text
resolve(local, remote):
  if shouldPreferRemoteUserImageSyncData → remote（再保留本地 healthResource 块）
  else 按 serverUpdatedAt 取胜者（都有则较新胜；仅远端有则远端；仅本地有则本地；都无则远端）
  winner.mergingRemotePreservingLocalHealthResourceBlocks(local)

shouldSkipApplyingRemote:
  远端用户图更富 → 不跳过
  本地 serverUpdatedAt 更新 → 跳过
```

用户图富信息分：HTTPS URL +8；否则 `fullCacheKey` / `fileMd5` / `fileId` 各 +2；OCR `text` +1。

#### 附件下载 Job 消费

```text
jobs = loadPendingAttachmentDownloadJobs(limit)
for job:
  update state = processing
  managedFile = attachment.managedFileRecordForDownload()  // 需可解析 HTTPS
  if cachedURL(file) → completed + localFileURLString
  else download(file) → completed
  on error → failed
```

## 八、失败重试、重生成与错误展示

### 需求说明

投递失败的用户消息应可重试上送；AI 生成失败或用户需要换答时，应能在不清空历史的前提下重生成最近一轮助手回复。

### 基础要求与业务规则

- `retryFailedMessage`：把指定 `clientMessageID` 标为 `.pending`（不主动 `pushOutboxOnly`）。
- `retryLatestConversationFailure`：优先指定/最近失败用户消息；否则清助手错误卡并 `regenerateLatestAssistantReply`。
- `executeRegenerateReply`：历史过滤 `.failed`，取最近非 tombstone 用户消息重放；新建助手 `clientMessageID`；从用户块反解 health refs。
- 发送失败：`shouldRenderAssistantErrorCard` 时写错误展示；`notificationClient.error`。
- `ChatFeatureError`：`emptyInput` / `threadNotFound` / `syncFailed(String)`。

### 验收标准

- 失败用户消息可一键重回 Outbox，无需重新输入。
- 重生成不会再次插入重复用户消息。
- 网络类失败有用户可见错误反馈；取消不算失败 toast。

### 技术细节与设计代码位置

- `ChatDetailViewModel.retryFailedMessage` / `retryLatestConversationFailure` / `regenerateLatestAssistantReply`
- `SendChatMessageUseCase.executeRegenerateReply`
- `RetryFailedMessageUseCase.swift`
- **缺口**：retry 后依赖 Supervisor 防抖或外部 sync；若变更事件 `affectsThreadList == false`，可能短暂滞留

## 九、整体业务流程

```text
用户点击发送
  ↓
前置检查（isSending、草稿内容、附件 phase、健康资源校验）
  ↓
创建 cancellationToken + assistantClientMessageID
  ↓
SendChatMessageUseCase
  ├─ 解析线程 / 模型 / 系统提示 / 图片投递模式
  ├─ 附件：复用 prepared 或 upload+OCR
  ├─ appendMessage（user, .pending）
  ├─ MessageRunActor.startAssistantMessage（.sending）
  ├─ onUserMessagePersisted → 清草稿、刷新列表
  └─ ChatOrchestrator.generateReply（流式）
        ↓
MessageRunActor.apply(partial/tool/rich) → Core Data
        ↓
finalize → .pending + markPendingForSync
        ↓
DB 变更通知 → ChatSyncSupervisor 防抖 → pushOutboxOnly
        ↓
ChatOutboxPipeline.push → ACK → .sent
```

### 成功路径

1. 附件预处理完成 → 发送 → 用户气泡立即出现。
2. 助手流式输出 → 定稿 → Outbox 上送成功 → `.sent`。
3. 其他设备消息经打开会话 pull 合并；附件下载能力已实现但入站默认未入队（见 §七）。

### 失败、重试和恢复

| 阶段 | 失败表现 | 恢复 |
| --- | --- | --- |
| 附件预处理 | phase=failed（阻塞发送） | 删除该附件或重新选择 |
| UseCase 上传/OCR | 抛错，发送中止 | 上传发生在 `appendMessage` **之前**，失败时通常无半截用户消息 |
| AI 生成 | 错误卡 + toast | 重生成或重试最近失败 |
| Outbox push | deliveryState=failed | `RetryFailedMessageUseCase` → 再 push |
| block_updates message_not_found | 父消息重新 pending | 下一轮整包 push |
| 入站 pull | 保留本地窗口 | 再次打开/手动刷新 |
| 附件下载 | job=failed | `kickAttachmentDrain` / 下次 drain |

### 取消、并发和幂等

- 取消：token.cancel + task.cancel → `finalizeInterruptedAssistantMessage`。
- 发送互斥：VM 层 `isSending` / `currentGenerationTask`。
- 同步互斥：`ChatSyncEngine` 按 `.global` / `.thread(id)` single-flight。
- 块幂等：稳定 UUID + revision；`upsertMessageBlock` 忽略过期 revision。
- 消息幂等：`clientMessageID` 作为 Outbox / 入站合并主键。
- 附件下载幂等：`dedupeKey`（`imageDownloadDedupeKey`）。

## 十、状态模型

### 10.1 投递与 UI 状态

| 状态 | 进入条件 | 用户可见结果 | 退出条件 |
| --- | --- | --- | --- |
| 作曲器空闲 | 非发送、无阻塞附件 | 可编辑、可点发送（有内容时） | 选附件 / 点发送 |
| 附件 uploading/ocring/failed | enqueue 或失败 | 进度/错误；发送禁用 | success 或删除附件 |
| isSending | sendCurrentDraft 开始 | 输入区发送中；可取消 | defer 复位 |
| 用户消息 pending | appendMessage | 用户气泡已显示 | Outbox sent / failed |
| 助手 sending | startAssistantMessage | 流式气泡 | finalize / 中断 / 错误卡 |
| 助手 pending | 定稿或中断收尾 | 完整/部分回复 | Outbox sent / failed |
| 消息 failed | push 失败 | 可重试标记 | retry → pending |
| 消息 sent | push ACK | 正常历史消息 | 晚到块可能重新 pending |
| 附件 job processing | drain 取到 pending | 通常无显式 UI | completed / failed |

### 10.2 `ChatDeliveryState` 完整语义

| Case | rawValue | 含义（代码注释） |
| --- | --- | --- |
| `pending` | pending | 待发送（已加入队列，尚未开始发送） |
| `sending` | sending | 发送中（正在上传/请求接口/流式返回） |
| `sent` | sent | 已发送（服务器已接收） |
| `failed` | failed | 发送失败 |
| `read` | read | 已读（仅用于对话同步场景） |

Outbox 只捞 `pending`。助手流式用 `sending`；定稿后回到 `pending` 再由 Outbox 变成 `sending→sent`。

### 10.3 Block / 附件 / Job 状态机

```text
ChatMessageBlockStatus:  pending → streaming → ready
                                   ↘ failed

ChatComposerAttachmentPhase:
  pending → uploading → ocring → success
                     ↘ failed

ChatAttachmentDownloadJobRecord.State:
  pending → processing → completed
                      ↘ failed
```

## 十二、错误模型

| 错误类别 | 触发条件 | 是否重试 | 用户反馈 | 清理动作 |
| --- | --- | --- | --- | --- |
| emptyInput | 无文本/附件/任务/refs | 否 | 「请输入消息后再发送。」 | 无 |
| 附件阻塞 | 任一附件 phase ≠ success（含 failed） | 否（等待/删附件） | 发送按钮禁用 | 无 |
| HealthResource 校验失败 | refs>5 / 无成员 / 成员不一致 / 非法 ref | 否 | info toast | 不进入发送 |
| missingModelForScenario | 无 chat 模型 | 否 | error toast / 错误卡 | 结束 isSending |
| threadNotFound | 线程丢失 | 否 | 「对话线程不存在，请重新创建。」 | 结束发送 |
| CancellationError | 用户取消 | 否 | 无错误 toast | 中断收尾助手消息 |
| 上传/OCR/网络 | FileTransfer / OCR 失败 | 用户可再发 | toast / phase=failed | 预处理失败保留错误态 |
| AI Runtime 失败 | 网关/编排错误 | 可重生成 | 错误卡 + toast | 助手非 sending |
| Outbox push 失败 | remoteAPI.push 错 | 是（retry） | 消息 failed | markFailed |
| block_updates message_not_found | 父消息远端不存在 | 自动 requeue 父消息 pending | 日志 warning | 整包再推 |
| 入站合并冲突 | 本地较新 | 跳过覆盖 | 保留本地 | shouldSkipApplyingRemote |
| 附件下载失败 | download 错 / 无 managedFile | 可再次 drain | 日志 warning | job=failed |
| Realtime 失败 | WS hint 处理错 | 后台 | 日志 | 不推进错误游标 |

## 十三、与其他模块的接口边界

## 十六、当前实现、缺口与演进

### 当前实现

- 本地优先发送 + 流式 Actor 落库 + Outbox REST 上送已接通。
- 附件发送前预处理（上传+OCR）与发送时兜底上传并存。
- Supervisor 对本地 DB 变更防抖自动上送；打开会话增量拉取。
- 取消生成会收尾助手消息而非丢弃整条 run。
- 组合根将 `pushOutboxOnly` 注入 `MessageRunActor`，支持富卡片 ready 后立即上送。
- Core Data 已具备附件下载任务表与 `insertImageDownloadJobsIfNeeded`。

### 当前缺口

- 发送 / Outbox / 附件下载缺少专项单元测试。
- Realtime hint 后不再拉取，多端近实时到达依赖用户打开会话或手动刷新。
- **入站 `enqueueAttachmentDownloadJobs` 恒为 false**：后台下载管线实现存在但同步路径未打开。
- `RetryFailedMessageUseCase` 只改状态，不主动 `pushOutboxOnly`。
- Guest 聊天未纳入同一 Outbox 管线。
- 全量 `pushThreads` 在部分引擎路径被注释。
- UseCase 兜底 OCR 对非图片附件不如 VM 预处理完整（空 OCR）。

### 建议演进

- 明确打开入站附件入队（`enqueueAttachmentDownloadJobs: true`）或删除死代码路径，避免文档/实现漂移。
- 为 Outbox 增加显式 `retry + pushOutboxOnly` 串联。
- 恢复或明确 realtime 拉取策略，并写进游标语义测试。
- 补齐发送管线单元测试后再考虑 Sync 子模块抽出。
- Guest 若需多端同步，再评估接入同一 Repository/Outbox。
