# 体检报告需求

> 关联文档：[首页医疗接口.md](./首页医疗接口.md)（complete-data 拉取与卡片投影）、[首页医疗数据缓存.md](./首页医疗数据缓存.md)（`healthExamReports` 字段回写）。本文覆盖 **体检报告** 本身的列表、明细懒加载、详情、上传识别落库、删除/归档/分享，以及与聊天「问报告」的消费边界。  
> **UI/模型细节**：见下文「二点五」（页面设计、跳转、卡片、公共组件、数据模型字段表）。  
> 注意：本模块与「医疗检查报告（`examination_report`）」不同；后者走 `ExaminationReports` 路径。成员设置里的「体检档案 / ExamArchive」是基于体检报告派生异常项与随访计划的旁路流程，见第十三节边界。

## 一、模块目标

体检报告模块负责当前选中成员的体检报告全生命周期客户端能力：

- 从首页 `complete-data.healthExamReports` 直出列表首屏（含附件摘要，不含明细行）。
- 列表页按报告懒加载 `med-exam-details`，回写首页缓存。
- 卡片摘要展示、进入详情只读页。
- 拍照/选图上传 → OCR/AI 抽取 → 预提交校验 → 专用工作流落库。
- 删除、归档/取消归档、分享链接生成。
- 作为聊天「问报告」与健康资源引用的一类 `health_exam_report` 数据源。

业务价值：

1. 把家庭成员的体检机构报告结构化入库，支持指标明细与异常标记。
2. 与首页聚合缓存联动，避免进入列表时重复全量拉取。
3. 复用统一医疗文档上传管线，但保存走体检专用 workflow，不创建病历组合包。

**模块边界（摘要）**

| 负责 | 不负责 |
| --- | --- |
| 体检报告列表 / 详情 / 明细懒加载 | 检查报告（`examination_report`）列表与分类详情 |
| 体检文档上传识别与 `health-exams/save` | OCR/OSS/AI Runtime 基础设施本体 |
| 删除、归档、分享 | 成员 ExamArchive 引导与 AI 体检计划生成主流程 |
| 向首页缓存回写 `healthExamReports` | complete-data 服务端聚合实现 |
| 为 Chat 问报告提供可选资源叶节点 | Chat 推理编排与工具调用本身 |

### 2.3 目录职责与依赖方向

```text

        ↓

列表底部上传
        ↓
MedicalDocumentUploadViewModel
        ↓ 抽取 HealthExamRecognitionDraft
DefaultTypedMedicalDocumentSaver.saveHealthExamReport
        ↓
SparkMedicalWorkflowAPI.saveHealthExam
        → POST /api/v1/medical/workflows/health-exams/save/

        ↓
SparkMedicalWorkflowAPI.delete / MedicalArchiveMutationService
```

- 当前没有单独的「体检报告 Repository / UseCase」层；列表与详情直接依赖 Query/Workflow API 与上传 ViewModel。
- Domain 实体 `HealthExamReport` / `MedExamDetail` 存在，但列表 UI 主路径消费的是 `RemoteHealthExamReportWithAttachments` DTO；`domainModel` 映射在 `MedicalRemoteDTO+Domain.swift`。
- 依赖方向：`Features/Home` 与 `Features/MedicalDocumentUpload` → `Core/Networking` / `Core/Domain`；Chat 只读消费，不反向驱动体检写路径。

### 2.5.3 列表卡片细节（`ExamReportCard`）

卡片容器：

- 圆角 12 continuous；`ultraThinMaterial` + systemBackground 0.72 叠层。
- 描边 white 0.2；阴影 black 0.05 / radius 2 / y 2。
- 展开动画：spring response 0.3 / damping 0.7。

结构分区：

```text
ExamReportCard
├── headerSection（padding 16）
│   ├── 日期 yyyy/MM/dd + calendar 图标 + 「体检」badge
│   ├── trailing「查看详情」/ loading Progress
│   ├── 机构名 building.2（可选）
│   └── MedicalAttachmentListView（有附件时默认展开）
├── statsSection（padding 16）
│   ├── 项目数（蓝）
│   ├── 正常数（绿）= max(总数 - 异常数, 0)
│   └── 异常数（红）= flag.isPotentiallyAbnormal
├── loadingSection（明细加载中）
└── otherRiskSection
    └── 非异常明细最多 6 条 → HealthExamRiskItemCard
        若无非异常明细：用 summary 兜底一条 medium 风险卡
```

导航门禁：`canNavigateToDetail = (medExamDetails?.isEmpty == false)`；加载中或无明细时详情入口禁用/半透。

异常判定（列表卡片统计，复用检查报告扩展）：

`String.isPotentiallyAbnormal`（`ExaminationReportDetailSupport.swift`）命中：高/低/异常/阳性/abnormal/positive/high/low/↑/↓。

> 注意：列表卡片的「异常」用 `isPotentiallyAbnormal`；详情页风险分级用 `inferredRiskLevel`。两套启发式不完全相同，跨端对齐时需分别实现或统一产品规则。

高风险区块 `highRiskSection`：**当前实现中大段注释关闭**，不以高风险列表为主视觉。

私有展示模型（卡片内）：

| 类型 | 字段 |

| `HealthExamRiskItem` | title, category, result, recommendation?, severity |
| `HealthExamRiskSeverity` | high / medium / low / none |

## 九、整体业务流程

```text
首页卡片 Kind.healthExamReports
  ↓
注入 completeData.healthExamReports
  ↓
HealthExamReportsListPage（首屏直出）
  ↓
卡片可见 → MedExamDetailLazyLoadViewModel.loadDetailsIfNeeded
  ↓
listMedExamDetails(business_type=health_exam_report)
  ↓
回写 reports + onReportsUpdated → 首页缓存
  ↓
有明细 → HealthExamRecognitionResultView（detail）
  ↓
删除 / 归档 / 分享（可选）

并行：底部上传
  ↓
prepareAndStart(kind: healthExamReport)
  ↓
OCR + healthExamExtraction → HealthExamRecognitionDraft
  ↓
预提交校验
  ↓
workflows/health-exams/save/
  ↓
（建议）刷新列表或回写缓存 ← 当前需结合上传完成后的全局刷新行为验收
```

### 成功路径

1. 首页 complete-data 成功 → 进入列表立即有摘要卡片。
2. 明细懒加载成功 → 统计与详情可点。
3. 下拉刷新成功 → 列表与首页字段更新。
4. 上传保存成功 → 服务端产生新体检报告 ID。
5. 删除/归档成功 → 列表与缓存一致，UI dismiss/移除。

### 失败、重试和恢复

| 步骤 | 失败表现 | 恢复 |
| --- | --- | --- |
| 下拉刷新 | toast 错误，保留旧列表 | 用户再次下拉 |
| 明细懒加载 | 日志 warning，详情入口仍禁用 | 滚动触发可再试（`medExamDetails` 仍为 nil） |
| 删除/归档 | toast 错误，留在详情页 | 用户重试 |
| 分享 | alert 文案 | 用户重试 |
| 上传/抽取/保存 | 由上传管线错误态处理 | 重新上传或修正草稿 |

### 取消、并发和幂等

- 明细加载：同 ID `loadingIDs` 防并发重复。
- 删除/归档：本地 `isDeleting` / `isUpdatingArchiveState` 防重复提交。
- 归档列表不注册 `onReportsUpdated`，避免归档数据写回活跃首页缓存。
- 服务端删除/归档幂等性：客户端未额外做客户端幂等键；依赖后端。

## 十、状态模型

| 状态 | 进入条件 | 用户可见结果 | 退出条件 |
| --- | --- | --- | --- |
| 列表空（活跃） | 缓存无报告 | EmptyState 引导 | 刷新有数据 / 上传成功后刷新 |
| 列表有摘要无明细 | complete-data 直出 | 卡片摘要；详情禁用；可显示 loading | 明细加载完成或失败 |
| 明细加载中 | `loadingIDs` 含该 ID | Progress / 「查看详情」loading | 成功回填或 catch |
| 明细就绪 | `medExamDetails != nil` | 统计与可进详情 | 刷新重置明细后回到无明细 |
| 归档模式加载中 | 进入归档页 `.task` | 空或刷新中 | `replaceReports` |
| 详情只读 | 从卡片导航 | 识别结果同构 UI + 菜单 | dismiss / 删除 / 归档移出列表 |
| 识别确认中 | 上传管线 recognition 模式 | 可编辑草稿页 | 保存成功或取消上传 |
| 删除中 / 归档中 | 菜单确认后 | 菜单禁用 | 成功 dismiss 或失败 toast |

## 十一、数据与持久化

> 字段级模型定义见上文「2.5.5 数据模型详解」。本节只描述归属与生命周期。

| 数据 | 所有者 | 存储位置 | 生命周期 | 清理时机 |
| --- | --- | --- | --- | --- |
| `RemoteHealthExamReportWithAttachments` 列表 | 首页 `HomeViewModel` + 列表 VM | 进程内 complete-data / VM `reports` | 当前选中成员会话内 | 成员切换、强制刷新、登出 |
| `medExamDetails` | 同上（字段级） | 挂在报告 DTO 上 | 随报告缓存；刷新列表后通常清空需重载 | 列表 replaceReports |
| 领域实体 `HealthExamReport` | 映射层 | 非列表主路径 | 按调用方 | — |
| 抽取草稿 `HealthExamRecognitionDraft` | 上传 ViewModel | 内存 | 单次上传会话 | 上传结束/取消 |
| 附件文件 | File/OSS 模块 | 远端文件 + 本地临时 | 绑定 `fileIds` 到报告 | 报告删除时由后端策略处理（客户端未单独清理确认） |
| 分享链接 | Share API | 远端 shareCode | 有 `expiresAt` | 过期由服务端 |

账号/成员边界：所有列表与保存以当前 `memberID` 为准；切换成员必须换新 complete-data，不得串用体检列表。

敏感字段：`summary`、明细 `resultValue`/`diagnosis`/`flag`、`rawOCR`、附件 URL —— 按医疗隐私处理；分享走服务端 share ticket。

## 十二、错误模型

| --- | --- | --- | --- | --- |
| 缺成员上下文 | memberID == nil | 否（先选成员） | 上传禁用；刷新跳过日志 | 无 |
| 网络/业务错误 · 刷新 | list API 失败 | 用户手动 | error toast | 保留旧列表 |
| 网络错误 · 明细 | listMedExamDetails 失败 | 滚动可再触发 | 无强提示 | 保持 `medExamDetails == nil` |
| 删除失败 | delete API | 是 | error toast | 不 dismiss |
| 归档失败 | setArchived | 是 | error toast | 本地归档态不改 |
| 分享失败 | createShare | 是 | alert | 无 shareContext |
| 预提交校验失败 | 草稿缺必填 | 用户修正 | 校验问题列表 | 不调用 save |
| 保存失败 | saveHealthExam | 是 | 上传管线错误 | 不产生本地假 ID |
| 鉴权失效 | 401 | 走全局会话 | 全局处理 | 非本模块单独清理 |

## 十三、与其他模块的接口边界

### 本模块负责

- 体检报告列表 UI、明细懒加载、详情只读、删除/归档/分享入口。
- 以 `healthExamReport` 类型触发上传识别，并调用 `health-exams/save`。
- 向首页回写 `healthExamReports`（活跃模式）。

### 本模块不负责

- 检查报告（影像/检验/病理等）列表与分类详情页。
- OCR 引擎、OSS 凭证、AI Provider 配置本体。
- 成员 ExamArchive（异常项预览、确认、AI 计划）完整引导流——虽依赖体检报告 ID，归属成员医疗设置。
- complete-data 的服务端聚合与 ETag 策略细节（见首页医疗接口文档）。

### 上游调用方

- 首页医疗卡片与 `HomeMedicalRouteSupport`。
- 聊天问报告 / 健康资源详情。
- （旁路）成员 ExamArchive 流程读取已有体检报告。

### 下游依赖

- `SparkMedicalQueryAPI` / `SparkMedicalWorkflowAPI` / Share API。
- `MedicalDocumentUploadViewModel` 与 Typed Saver/Extractor/Resolver。
- `MemberContextStore`、`FileTransferService`、`NotificationClient`、`Logger`。
- 首页 `updateMedicalCompleteData`。

### 输入和输出契约

| 方向 | 契约 |

| 输入 · 列表 | `RemoteMemberCompleteData?`、`archiveMode`、依赖注入 API/服务 |

| 输入 · 保存 | `HealthExamRecognitionDraft` + envelope（OCR/文件） |

## 十六、当前实现、缺口与演进

### 当前实现

- 列表 + 首页缓存首屏 + 字段回写。
- 明细懒加载与卡片统计。
- 详情复用识别结果 UI；删除、归档、分享可用。
- 上传走 typed medical document 管线 + 专用 `health-exams/save`。
- Chat 问报告可消费体检资源。

### 当前缺口

- 详情菜单「导出」「编辑」为占位空按钮。
- 无列表/懒加载/删除归档专项自动化测试。
- 领域实体 `HealthExamReport` 未成为列表主数据源（DTO 直通 UI）。
- 上传保存成功后如何精确 upsert 进当前列表/首页缓存：需结合上传完成回调的全局行为再验收（本文不把未确认回写写成已实现）。
- 高风险区块 UI 在 `ExamReportCard` 中大段注释关闭，当前主要展示「其他关注项 / summary 兜底」。

### 建议演进

1. 补齐详情编辑（更新 workflow）与导出，去掉空菜单或隐藏未实现项。
2. 上传成功后明确 `upsertReport` / 局部刷新契约，避免依赖整页重进。
3. 为懒加载与 payload 构建补单元测试。
4. 若跨端对齐，与 HarmonyOS 体检列表/明细协议字段保持同一 `business_type` 语义。

## 十七、整体验收标准

- [ ] 首页 → 体检列表首屏直出 complete-data，不重拉聚合接口。
- [ ] 明细按需加载一次并回写首页缓存；失败可恢复且不污染已有摘要。
- [ ] 筛选/搜索本地正确；活跃与归档缓存隔离。

- [ ] 成员切换后不出现上一成员的体检数据。
