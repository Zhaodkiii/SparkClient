# 医院演示客户端产品与接入方案

> 阶段：需求确认 / UI 原型（不实施代码）  
> 更新日期：2026-09-01  
> 后端契约单一事实源：`SparkService/总领文档/医院智能体与医生工作台/服务端数据模型与接口契约.md`

服务端已由 Django App `hospital_care` 统一交付患者医院 API 和医生工作台 API；iOS 不为该 App 建立平行协议或自定义业务码。

## 0. 已确认流程：对话 Tab 到医生智能体会话

本节逐条记录本轮确认结果，是本期 iOS 患者端的唯一入口流程。后文如仍出现“医院 Tab 为咨询主入口、最近会话列表、列表内成员切换、症状导诊、会话页挂号”等旧设想，均不作为本期实现要求。

### 0.1 入口与范围

1. 复用现有“对话”Tab，不新增医院咨询主 Tab。
2. “院内名医 / 普通对话”分段放在对话导航栏标题区域：`.toolbar` 内的 `ToolbarItem(placement: .principal)` 使用现有 SwiftUI `Picker`；默认打开“院内名医”，编辑态沿用现有标题、不显示 Picker。
3. 本期名医页固定为当前演示医院，不提供医院切换。
4. 本期仅允许按医生、科室浏览；不提供“哪里不舒服”的症状导诊入口。

### 0.2 院内名医目录

1. 列表主体是医生智能体目录，不是历史会话列表。
2. 顶部提供“全部 + 科室”横向筛选；科室来自固定医院的已启用科室。
3. 搜索仅匹配医生姓名、职称、科室；不按症状、历史消息或普通会话内容搜索。
4. 每张卡片展示一位医生的一个患者可用智能体：头像、姓名、职称、科室、AI 标识、擅长摘要与服务边界。
5. 同一医生存在多个智能体时，患者目录只展示其**最新已发布**智能体；其他智能体仅保留医院后台/内部用途。
6. 排序先按“当前成员是否已有该医生智能体的最近会话”分组，已咨询医生在前；每组内按医院后台配置顺序。
7. 不展示最近消息、时间、未读数、历史会话条目或后台“重点患者”标记。
8. 卡片 CTA：没有可续聊会话时显示“开始咨询”；有最近会话时显示“继续咨询”。点击卡片本体和 CTA 的结果一致。

### 0.3 进入、创建与续聊

1. 点击医生卡后，先以现有当前成员解析该医生智能体的最近医院会话。
2. 有最近会话：直接打开该 `threadID`，不新建会话。
3. 没有会话：调用医院会话创建接口，创建时写入 `agent_id + member_id`，并交给现有 ChatView。
4. 成员切换继续完全复用现有输入框内能力；名医列表和会话导航栏不新增成员选择控件。
5. 患者端不提供历史会话入口。新建咨询后旧会话仍由服务端既有模型留存，但不在本期患者端展示或切回。
6. ChatView 右上角既有“新建对话”按钮保持原位置与交互；当当前会话绑定医生智能体时，新线程必须自动继承该 `agent_id`，并使用输入框当时的 `member_id` 创建医院会话。

### 0.4 会话首屏与医生详情

1. 医生智能体新会话不插入通用科普问题/健康数据 `ChatGuideCard`。
2. 复用现有 system 消息插入机制，服务端写入一张医生智能体身份卡：头像、医生姓名、职称、科室与“医生智能体”标识。
3. 点击身份卡本体、头像或姓名，进入轻量医生详情页。
4. 轻量详情页展示头像、姓名、职称、科室、擅长方向与医院介绍；底部只提供“咨询医生智能体”，不扩展出诊、挂号、评价或真人问诊服务。
5. 会话页不新增挂号/就医入口；风险等级与行动建议完全复用当前已有工具及其消息卡逻辑。

### 0.5 服务端契约收敛项

患者端不能本地猜测“最新发布智能体”或搜索字段。`hospital_care` 患者目录需要保证：

- 每位医生只返回一个最新 `published` 智能体；
- `keyword` 覆盖医生姓名、职称、科室，而非仅智能体名称；
- 当前成员医院会话列表可供客户端计算“是否有最近可续聊会话”，但这些会话不渲染为名医页的历史列表。

## 1. 设计结论

医院 Demo 应在 SparkClient 现有家庭健康与 AI 对话底座上增加“医院服务入口”，而不是做一款彼此割裂的新 App：

- 首页提供医院官方身份、当前就诊人、挂号、AI 导诊、报告解读和线上问诊入口。
- 对话列表的首屏入口改造为“院内医生智能体”，并保留最近会话。
- 医生智能体是医生/科室维护的 AI 助手，不用医生姓名冒充真人医生。
- 进入对话后复用现有 ChatThread、ChatMessage、MessageBlock、AI Runtime、知识库、记忆和同步管线。
- 医生接管后，消息仍进入同一时间线，但显示“真人医生”身份。
- 医院医生智能体的新会话首条系统卡展示医生/智能体简介，并可进入完整医生简介页；不再展示通用健康数据引导卡。
- Demo 挂号没有真实 HIS 时只做演示或跳转，不能伪造成功订单。

### 1.1 患者身份与成员复用

本方案不在 iOS 增加 Patient、PatientStore 或“当前患者”第二事实源：

- 登录账号继续由现有会话体系管理。
- 登录账号下当前选中的 Member 就是医院首页、挂号、AI 导诊和对话中的当前患者。
- UI 可以根据医院语境显示“当前患者”或“当前就诊人”，但点击切换时直接进入现有成员选择流程。
- 切换完成后继续使用现有 memberID；所有患者相关请求都从同一个成员上下文读取。
- 历史 ChatThread 继续绑定创建时的 memberID。切换成员不会修改或迁移已有会话，新咨询使用新的当前 memberID。

## 2. 参考图的采用与调整

两张附件仅作为 UI 参考，不作为需求指令。

### 2.1 医生智能体列表参考

采用：头像、AI 标识、医生姓名、职称、科室、医院、擅长方向、咨询入口和筛选芯片。

调整：

- 医院专属 Demo 不使用“百大名医、院士团队”等未经授权的营销称号。
- 把“医生本人”和“医生 AI 助手”分为两个明确概念。
- 卡片只展示医院已审核信息；咨询量无真实统计时不展示虚构数字。
- 筛选优先按科室、服务状态、医生姓名，而不是泛平台榜单。

### 2.2 医院首页参考

采用：医院品牌头部、当前患者身份卡、四个主操作、门诊服务网格。

调整：

- 首要动作改成 `预约挂号 / AI 导诊 / 报告解读 / 线上问诊`。
- “出示就诊码”等功能只有真实医院接口时展示；Demo 用“演示患者”标签。
- 首页下半部分增加科室和院内医生智能体，不让用户再绕到独立搜索页。

## 3. 与当前客户端的复用映射

| 目标能力 | 当前事实源 | 接入策略 |
| --- | --- | --- |
| 当前就诊人 / 患者 | Member / MemberContext / Home | 当前选中 Member 直接作为患者；切换患者等同于切换成员 |
| 对话线程 | `Core/Domain/Entities/ChatThread.swift` | 仍是唯一线程对象；医院上下文使用服务端扩展读模型 |
| 会话列表 | `ChatConversationListPage`、`ChatListViewModel`、`ChatThreadListItem` | 复用最近会话、搜索、未读和同步；在上方增加院内智能体目录入口 |
| 对话页 | Features/Chat | 复用消息、附件、流式 Block、风险卡片和同步 |
| 医生直接消息 | ChatMessage + 目标 sender/displayRole | 保留 ChatMessageRole/AIRuntimeRole；新增 otherUser 展示角色并关联医生快照 |
| 医生简介系统卡 | 目标 system ChatMessage + `hospital_doctor_intro_card` Block | 由服务端创建并随现有同步下发；不复制 ChatMessage 或本地伪造资料 |
| AI 配置 | `AllModels`、AISettings、AIRuntime | 只承载运行配置；不得把 AllModels 当医生实体 |
| 知识库 | Features/Knowledge + 服务端 KnowledgeBase | 进入医生智能体会话后，只读同步该智能体已关联的医院知识；仅在当前智能体作用域检索，不进入个人知识库 Tab，不参与普通 AI 对话 |
| 记忆 | Features/Memory + AIMemory | 继续是患者个人记忆，按授权参与当前会话 |
| 报告解读 | 医疗档案、上传、健康资源上下文 | 从首页快捷入口复用现有流程 |
| 医疗风险提示 | 现有风险消息块 / 工具 | 复用渲染，增加医院行动入口 |

当前没有可验证的医院、科室、医生和挂号领域实现，因此这些属于 Demo 新增业务层，不应写进现有 ChatThread 的本地 AI 参数中冒充完整领域模型。

## 5. 客户端读模型

以下是 UI 所需目标读模型名称，不代表本轮新增 Swift 代码。

### 5.1 HospitalHomeSnapshot

- hospital：id、name、logo、grade、serviceMode、demoFlag。
- currentMemberSummary：直接复用当前成员 id 和脱敏展示；该成员就是当前患者。
- primaryActions：挂号、AI 导诊、报告解读、线上问诊及可用状态。
- departments：科室简表。
- featuredAgents：医生智能体卡片。
- notices：医院公告或 Demo 说明。

### 5.2 DoctorAgentCard

- agentID、doctorID、departmentID。
- doctorDisplayName、title、avatarURL。
- agentName、AI 助手标识、publicSummary。
- departmentName、specialties。
- publicationStatus、availability。
- CTA：问 AI 助手 / 查看详情；真人问诊必须使用不同 CTA。

### 5.3 HospitalConversationContext

- threadID、hospital、department、doctor、agent。
- serviceStatus、doctorAttention（患者端不展示内部关注等级）。
- riskSignalSummary、actionGuidance。
- doctorJoined、endedAt、endReason。
- registrationEntry capability。

### 5.4 MessageActorPresentation

- actorType：patient / aiAgent / doctor / system。
- displayName、avatar、badge、credentialSummary。
- AI 与医生采用不同配色、标签和辅助文案。

### 5.5 DoctorPublicProfile 与 HospitalDoctorIntroCardPayload

- DoctorPublicProfile：医生最新已审核资料，提供专业方向、专业擅长、个人简介和可验证的诊疗经验。
- HospitalDoctorIntroCardPayload：会话创建时的医生/智能体资料快照，作为 system MessageBlock 渲染；不代表医生发言。
- 详情页读取最新 published profile；首条系统卡保留发送时快照。完整规则见 `医生简介与智能体首条系统卡需求.md`。

具体字段、同步、AIRuntime 映射和兼容门槛见 `医生直接消息与对方用户角色方案.md`。核心约束是 `otherUser` 只属于 UI 展示角色，不加入 AIRuntimeRole；医生消息依靠 sender.doctor 与 AI 消息区分。

## 6. 核心状态机

### 6.1 医院会话

```text
未创建
  -> AI 服务中
      -> 待医生接管
          -> 医生已接管
              -> 已结束
      -> 已结束
```

客户端不自行推导服务状态，以服务端 `ClinicalConversationBinding` 快照为准。WebSocket/同步先到消息、状态后到时，UI 可短暂显示“状态同步中”，不能猜测医生已接管。

### 6.2 挂号

```text
能力加载中
  -> demo：演示科室/医生/日期 -> 演示确认（不产生真实挂号）
  -> redirect：显示跳转目标 -> 离开 App -> 返回后仅显示“已跳转”
  -> integrated：号源 -> 确认 -> 下单 -> 支付/结果（需真实接口）
  -> unavailable：说明暂未开通 + 返回咨询
```

Demo 不能把 redirect 后的返回当成成功，也不能本地生成真实挂号号。

## 7. AI 与真人医生体验规则

- 智能体卡片名称建议“张医生 AI 助手”，副标题“由张医生/心内科团队维护”。
- 首次进入必须展示能力边界和紧急情况说明，用户确认后开始。
- AI 消息显示 `AI 助手`，医生消息显示 `真人医生`；头像相同也必须有文字标签。
- 医生智能体会话的首条资料卡显示 `系统简介` / `AI 助手`，不能显示为真人医生消息；资料卡不会替代风险免责声明。
- 医生接管产生系统事件：“张医生已加入本次会话”。
- AI 风险提示包含风险级别、依据摘要、建议行动、时间紧迫性和一键就医入口。
- 高风险时主 CTA 是急诊/120/医院路线，不用“继续问 AI”作为唯一动作。
- 已结束会话输入框禁用，展示“重新咨询”和“预约挂号”。

## 8. 页面状态要求

每个网络页面必须具备：首次加载、下拉刷新、空数据、离线缓存、部分模块失败、鉴权失效、医院停用、智能体下架、患者无权限、服务结束等状态。

特殊状态：

- 智能体下架但已有历史会话：历史可读，不允许新建。
- 医生资料更新：历史医生消息使用发送时快照，详情页使用最新资料。
- 当前成员/患者切换：调用现有成员切换；新建咨询必须重新确认，不得把 A 成员上下文带给 B，也不得改绑 A 的历史会话。
- 风险卡片离线：保留已同步行动建议和生成时间，提示可能不是最新状态。

## 9. Demo 数据约束

- 医院、医生头像和姓名必须是医院授权或清晰标注的虚构演示资料。
- 患者、报告、病历、处方全部使用合成数据。
- 所有 Demo 页头或设置页可查看“演示环境”说明。
- 预置 3 个科室、每科 1–2 个智能体、三档风险脚本和医生接管脚本。
- 不用虚构“85.8 万人咨询”“三甲”等数据提升演示效果。

## 10. 后续实施目录建议

```text
SparkClient/Projects/Features/HospitalCare/

```

Chat 只消费 HospitalConversationContext 和 MessageActorPresentation；医院 API 路径、DTO 和映射集中在 HospitalCare/Infrastructure。此处仅是未来目录方案，本轮不创建代码目录。

## 11. 验收口径

1. 用户可在 3 步内从首页进入某位医生的 AI 助手并发出首问。
2. 对话列表能看到院内智能体目录和最近医院会话。
3. AI、真人医生、患者和系统事件在任何主题下都能明确区分。
4. 切换家庭成员不会串会话、知识或记忆。
5. 中高风险脚本能给出明确行动，且不出现确诊承诺。
6. 医生端发送、关注、结束后，客户端状态通过既有同步链路一致。
7. Demo 挂号全程不产生“真实成功”的误导。
8. 新医院 Tab 使用未占用 RootTab rawValue，不破坏历史 selectedTab 持久化。
9. 医院对话列表首次出现时停留在列表，不自动创建或进入会话。

## 12. 知识库同步与异常边界确认

院内医生智能体会话使用“在线咨询优先、医院知识静默同步”的策略：

```text
进入 ChatView
-> 立即展示并允许在线咨询
-> 先使用缓存 Manifest 和本地检索
-> 后台请求 conversation context 最新 Manifest
-> 按 knowledge_base_id + 独立 cursor 增量拉正文、切块、向量、删除标记
-> 成功后原子替换
-> 失败则清空当前 agent scope，本次在线咨询不受影响
```

最终约束：

- 同步全程无患者可见进度、成功或失败提示。
- Manifest 由 conversation context 返回；数据按知识库 ID 直接公开只读拉取，不使用会话 grant。
- cursor 作用域为 `account + hospital + agent + knowledge_base`，与个人 cursor/Outbox 完全隔离。
- 向量必须与当前正文 revision 一致；待生成、过期或维度不匹配时只做关键词/全文检索。
- 解绑和删除在下一次 Manifest/增量同步时清理当前 agent scope。
- 智能体下架后历史可读、发送禁用、知识同步停止。
- context 失败时打开缓存会话并允许尝试原 thread 在线发送，绝不转换为普通 AI 对话。
- 医院目录数据使用账号级内存 cache-first + 后台静默刷新；医院列表失败自动回普通对话。
- 成员权限撤回后展示设备缓存是 Demo 决策，属于正式上线阻断风险。

字段、接口、缓存模型、错误矩阵和验收详见《医院演示客户端落地需求》第 11–18 节。
