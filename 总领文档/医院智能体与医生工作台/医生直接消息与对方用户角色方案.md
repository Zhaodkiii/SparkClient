# 医生直接消息与对方用户角色方案

> 阶段：目标设计，尚未实现  
> 更新日期：2026-09-01  
> 范围：iOS 患者端 + 医院后台 + SparkService 统一消息契约  
> 本文只维护方案，不修改 Swift、Python、Vue、数据库或配置。

> 已确认入口关系：患者从“对话 → 院内名医”直接进入医生智能体会话；名医目录不展示历史会话。医生直接消息仅在进入后的既有 ChatView 时间线内按本文规则显示，不改变名医卡片的结构或排序。

## 1. 结论

医生在医院后台可以直接向患者当前会话发送消息。患者 iOS 端应把该消息展示为“对方用户”，并关联、展示真实医生信息。

但不能直接向现有 `ChatMessageRole` 或 `AIRuntimeRole` 添加 `otherUser`：

- `ChatMessageRole` 当前只有 `system / user / assistant`，并通过 `runtimeRole` 一一映射到 AI Runtime。
- `AIRuntimeRole` 是大模型 API 标准角色，只有 `system / user / assistant / tool`。
- 当前 ChatOrchestrator、消息统计、气泡左右布局和 AI 操作都依赖上述角色。

因此采用“双角色模型”：

| 角色层 | 作用 | 枚举 / 字段 | 是否新增 `otherUser` |
| --- | --- | --- | --- |
| 模型协议角色 | AI 上下文和现有同步协议 | `ChatMessageRole`、`AIRuntimeRole`、服务端 `ChatMessage.role` | 否，保持不变 |
| 发言者身份 | 记录真实发言人 | 服务端 `ChatMessageAttribution.actor_type` + sender | 记录 doctor |
| iOS 展示角色 | 决定气泡方向、头像、身份和菜单 | 目标 `ChatMessageDisplayRole` | 是，增加 `otherUser` |

医生消息的最终语义是：

```text
ChatMessage.role = assistant          # 兼容现有 LLM / 同步协议
sender.actorType = doctor             # 真实发言者
displayRole = otherUser               # iOS 患者端展示角色
sender.doctor = 医生信息快照           # 姓名、职称、医院、科室、头像
```

## 3. iOS 目标领域模型

### 3.1 ChatMessageDisplayRole

这是客户端展示角色，不参与网络编码和 AI Runtime 请求：

| 值 | 语义 | 页面位置 |
| --- | --- | --- |
| `currentUser` | 当前登录账号代表当前成员发出的消息 | 右侧 |
| `otherUser` | 对方真人用户；本方案首个类型为医生 | 左侧，显示真人身份 |
| `assistant` | AI 智能体生成的消息 | 左侧，显示 AI 标识 |
| `system` | 接管、结束、风险流程等系统事件 | 居中或弱展示 |

### 3.2 ChatMessageSender

ChatMessage 目标增加可选 sender 值对象：

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| actorType | patient / doctor / aiAgent / system | 服务端真实发言类型 |
| actorID | String? | 发言主体稳定 ID；不用于授权判断 |
| displayName | String? | 发送时展示名快照 |
| avatarURL | String? | 头像快照 |
| doctor | DoctorMessageProfile? | actorType=doctor 时存在 |
| agentID | UUID? | actorType=aiAgent 时存在 |

### 3.3 DoctorMessageProfile

| 属性 | 类型 | 用途 |
| --- | --- | --- |
| doctorID | UUID | 医生档案主键 |
| displayName | String | 医院审核姓名 |
| title | String? | 职称 |
| hospitalName | String | 医院名称 |
| departmentName | String | 科室名称 |
| avatarURL | String? | 医生头像 |
| verified | Bool | 当前消息关联的医生身份是否有效 |

以上是消息发送时快照，用于历史消息稳定展示；医生最新详情仍从 DoctorProfile 接口读取。快照不是第二套医生主数据。

### 3.4 展示角色解析

| 条件 | displayRole |
| --- | --- |
| sender.actorType=patient 且 actorID=当前登录 userID | currentUser |
| sender.actorType=doctor | otherUser |
| sender.actorType=aiAgent | assistant |
| sender.actorType=system | system |
| 旧消息无 sender 且 role=user | currentUser |
| 旧消息无 sender 且 role=assistant | assistant |
| 旧消息无 sender 且 role=system | system |

客户端不能仅根据 actorID 判断权限；这里只用于展示，服务端权限仍是唯一事实源。

医院医生智能体首条资料卡也是 `system` 展示角色：它承载 `hospital_doctor_intro_card`，只展示医生/智能体公开快照和“查看医生简介”入口，不能渲染成 `otherUser` 或 `assistant` 气泡。详见 `医生简介与智能体首条系统卡需求.md`。

## 4. 服务端统一消息契约

### 4.1 同步消息目标字段

现有 ChatRemoteMessage 增加可选 `sender`：

```text
sender
├── actor_type: patient | doctor | ai_agent | system
├── actor_id: string | null
├── display_name: string | null
├── avatar_url: string | null
├── agent_id: uuid | null
└── doctor: null | {
      doctor_id,
      display_name,
      title,
      hospital_name,
      department_name,
      avatar_url,
      verified
    }
```

字段由 ChatMessageAttribution 和 DoctorProfile 统一生成；后台发送接口与患者同步接口必须消费同一序列化服务，不能各自拼装医生信息。

### 4.2 医生后台直接发送

```text
医生登录医院后台
-> 打开被授权的患者会话
-> 输入并发送
-> 服务端验证 HospitalStaffMembership、DoctorProfile、医院、科室、会话分配和未结束状态
-> 在患者原 ChatThread 下写 ChatMessage(role=assistant)
-> 同事务写 ChatMessageAttribution(actor_type=doctor, actor_user, doctor_profile)
-> 写 AdminAuditLog
-> 通过现有同步 / WebSocket 通知患者端
-> iOS 收到 role=assistant + sender.doctor
-> 解析 displayRole=otherUser
-> 显示医生消息
```

医生不能调用患者普通 chat push API：该 API 的 owner 是患者账号。医院后台必须调用医院范围的专用写接口，由服务端在授权后代写患者 Thread。

### 4.3 后台发送接口

目标接口继续使用已设计的医院命名空间：

```text
POST /api/hospital/v1/doctor/conversations/{thread_id}/messages/
```

请求最小字段：client_message_id、纯文本/受支持 blocks、预期 conversation version。医生身份、医院、科室不能由请求 body 自报，必须从登录 membership 与服务端会话分配解析。

响应返回新消息完整快照，包括 sender；随后患者端通过现有 pull/WS 收到同一 server_message_id，必须幂等合并。

## 5. iOS 消息展示

### 5.1 气泡布局

```text
┌─────────────────────────────────────┐
│ [张医生头像] 张医生 · 主任医师       │
│ [真人医生] 心内科 · 天长市中医院     │
│ ┌─────────────────────────────────┐ │
│ │ 请尽快到急诊就医，不要自行驾车。 │ │
│ └─────────────────────────────────┘ │
│                              10:32  │
└─────────────────────────────────────┘
```

- `otherUser` 左对齐，但不能复用 AI 头像和 AI 标签。
- 医生消息显示 `真人医生`、姓名、职称、科室和医院。
- 点击医生身份区域进入医生详情；点击消息只执行通用复制/选择操作。
- 朗读、翻译、保存知识等是否开放按通用能力判断，不能因为底层 role=assistant 自动获得 AI 专属菜单。

### 5.2 UI 判断迁移

| 当前判断 | 目标判断 |
| --- | --- |
| `role == user` 决定右对齐 | `displayRole == currentUser` |
| `role == assistant` 显示 AI 气泡 | `displayRole == assistant` |
| 非 user 全部左对齐 | otherUser/assistant 左对齐，system 单独布局 |
| assistant 自动显示 AI 菜单 | sender.actorType=aiAgent 才显示 AI 专属操作 |
| assistant 消息数 | AI 消息只统计 actorType=aiAgent，医生消息单独统计 |

## 6. AI 上下文映射

医生发言进入后续 AI 上下文时使用 `AIRuntimeRole.assistant`，表示服务方已经给出的回复；不新增 AIRuntimeRole.otherUser。

必须同时满足：

- 用户消息继续映射 user。
- 医生消息映射 assistant，但保留 sender 信息仅供业务/UI/审计。
- AI 自动生成的新消息仍是 assistant + aiAgent sender。
- 如果医生接管后禁止 AI 自动回复，服务端根据 conversation status 停止 Run，而不是依靠角色枚举猜测。

## 7. 本地持久化与兼容

- ChatMessage 本地模型目标增加可选 sender。
- CoreData ChatMessageEntity 增加可选 `senderSnapshotData`，编码完整 sender 值对象，供离线历史展示。
- 老数据没有 sender 时按 role 兼容解析，不迁移伪造医生身份。
- senderSnapshotData 只保存展示快照，不保存医生证件、手机号、工号或后台 user token。
- 消息替换、块合并、远端覆盖等 ChatMessage 重建路径必须完整保留 sender，避免刷新后医生身份丢失。

## 8. 版本兼容门槛

旧版 iOS 只认识 role=assistant，会把医生消息误显示为 AI。为避免身份误导：

1. 患者端完成 sender_v1 解析和医生气泡上线前，生产环境禁止开启医生直接发送。
2. 服务端通过客户端能力或最低版本判断 `message_sender_v1`。
3. 不支持的客户端应收到“请升级后查看真人医生回复”的系统通知，而不是把医生原文伪装成 AI 消息。
4. Demo 环境必须固定使用支持 sender_v1 的客户端版本。

## 9. 验收

1. 后台医生只能向本人获授权且未结束的会话发送。
2. 服务端同事务生成 ChatMessage、Attribution 和审计记录。
3. iOS 将医生消息解析为 otherUser，左侧展示医生实名信息和真人标识。
4. AI 消息仍显示 AI 助手，不与医生消息混淆。
5. 医生消息不出现 AI 专属重新生成、工具详情或模型信息。
6. 同一 server_message_id 经 WS 和 pull 重复到达只保留一条。
7. 离线重启后医生快照仍可展示。
8. 切换成员不会把消息移到另一位患者；历史 Thread 仍按原 memberID 展示。
9. 旧消息无 sender 时保持现有显示，不推断为医生。
10. 不支持 sender_v1 的客户端不会把医生消息错误标成 AI。
