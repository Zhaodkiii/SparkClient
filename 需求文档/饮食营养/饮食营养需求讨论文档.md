# 饮食营养需求讨论文档

> 文档性质：需求讨论稿。本文只讨论业务功能、产品形态、数据边界、用户场景和待确认问题，不涉及具体技术实现和代码改动。

## 一、业务背景

当前 AI 对话已经支持用户进行健康咨询，并逐步接入医疗档案、检查报告、体检报告、用药记录等健康资料。

为了提升 AI 对用户饮食管理、营养分析、减脂增肌、慢病饮食管理等场景的支持能力，需要新增“饮食营养”模块，让用户可以记录饮食、查看营养总览，并在 AI 对话过程中快速选择已记录的饮食数据、饮食计划、营养报告等信息发送给 AI。

AI 可以结合以下数据给出个性化建议：

1. 饮食记录和营养摄入。
2. Apple 健康中的能量消耗、营养摄入、运动数据。
3. 体检指标，例如血糖、血脂、尿酸、肝肾功能、BMI。
4. 疾病档案，例如糖尿病、高血压、高脂血症、肾病、痛风。
5. 用药情况，例如降糖药、降压药、降脂药、利尿剂等。
6. 用户目标，例如减脂、增肌、控糖、控盐、孕期营养、术后恢复。

### Q：这个功能到底要解决什么？

A：不是简单做一个“食物热量记录器”，而是把“饮食数据”接入到健康档案和 AI 对话里，让 AI 可以基于用户真实饮食和健康状态给出更有针对性的分析。

核心价值：

1. 用户能快速记录饮食。
2. 用户能看到当天摄入、剩余、消耗和三大营养素。
3. AI 能读取用户选择的饮食记录进行分析。
4. 对本人用户，可以与 Apple 健康互通，减少重复录入。
5. 对家庭成员，饮食数据进入服务端成员档案，支持照护场景。

## 二、信息架构

### Q：首页入口放在哪里？

A：建议在首页健康资料入口中新增“饮食营养”一级模块，与医疗档案并列或作为健康管理的一部分。

当前结构：

```text
用户
🏥 医疗档案
├─ 病例
├─ 检查
├─ 体检
├─ 用药
```

新增后建议：

```text
用户
🏥 医疗档案
├─ 病例
├─ 检查
├─ 体检
├─ 用药

🍎 饮食营养
├─ 总结
├─ 营养
```

### Q：“饮食营养”下第一期应该放哪些内容？

A：按参考图，第一期模块只保留两个：

| 模块 | 作用 | 参考图 |
| --- | --- | --- |
| 总结 | 展示今日营养总览：已食用、剩余、已消耗，以及碳水、蛋白质、脂肪进度 | 图 1 |
| 营养 | 展示早餐、午餐、晚餐、小吃四个餐次；每个餐次展示已摄入/目标、已记录食物、添加入口 | 图 2 |

建议第一期先做最小闭环：

1. `总结`：今日摄入、剩余、消耗、三大营养素进度。
2. `营养`：早餐、午餐、晚餐、小吃四个餐次。
3. 餐次内支持添加食物记录。
4. 支持图片识别和手动录入。
5. 支持把记录发送给 AI 分析。
6. 本人支持写入和读取 Apple 健康营养数据。

饮食计划、营养报告不作为第一期“饮食营养”下的一级模块入口；后续可作为 AI 分析结果、详情页子能力或二期功能再讨论。

### Q：`总结` 模块具体展示什么？

A：`总结` 对齐参考图 1，是用户进入饮食营养后最先看到的今日总览卡片。重点是“今天吃了多少、还剩多少、消耗多少、三大营养素是否达标”。

页面结构建议：

```text
总结                                      详细信息
┌────────────────────────────────────────┐
│                                        │
│  369              1,626             411│
│ 已食用             剩余             已消耗│
│              半圆/圆环进度              │
│                                        │
│ 碳水化合物        蛋白质              脂肪│
│ ━━━━━──          ━───               ━── │
│ 69 / 243克       10 / 97克          9 / 64克│
└────────────────────────────────────────┘
```

字段说明：

| 字段 | 展示 | 说明 |
| --- | --- | --- |
| 标题 | `总结` | 模块标题，左上大字 |
| 右上入口 | `详细信息` | 进入今日/周期营养详情页 |
| 已食用 | `369` | 今日已摄入热量，单位默认 kcal，可在文案中省略单位 |
| 剩余 | `1,626` | 今日剩余热量，作为视觉中心 |
| 已消耗 | `411` | 今日活动/运动消耗 |
| 圆环进度 | 中央半圆或圆环 | 表达已摄入占目标进度，绿色为已摄入，浅灰为剩余 |
| 碳水化合物 | `69 / 243克` | 已摄入 / 目标 |
| 蛋白质 | `10 / 97克` | 已摄入 / 目标 |
| 脂肪 | `9 / 64克` | 已摄入 / 目标 |

交互建议：

1. 点击 `详细信息`：进入营养详情页，展示今日来源、餐次明细、Apple 健康来源、服务端记录来源。
2. 点击 `已食用`：可筛选查看今日摄入记录。
3. 点击 `已消耗`：可查看 Apple 健康消耗来源，例如活动能量、运动记录。
4. 点击三大营养素进度：可查看对应营养素来源和趋势。

设计注意：

1. `剩余` 是视觉中心，字号最大。
2. `已食用` 和 `已消耗` 放在左右两侧，避免抢主视觉。
3. 三大营养素用横向进度条，不使用复杂图表。
4. 单位统一使用 `克`，热量单位在详情或说明中标注为 `千卡/kcal`。
5. 卡片四周保留明显边框或浅灰分隔，和截图一致，整体干净、扫描成本低。

### Q：`营养` 模块具体展示什么？

A：`营养` 对齐参考图 2，是按餐次记录和添加食物的入口。重点是“每餐吃了多少、记录了什么、快速添加”。

页面结构建议：

```text
营养                                           更多
┌────────────────────────────────────────┐
│ ◯ 早餐 →                         +     │
│   369 / 598千卡                         │
│   Scrambled Eggs, Banana, Bana...       │
├────────────────────────────────────────┤
│ ◯ 午餐 →                         +     │
│   0 / 798千卡                           │
├────────────────────────────────────────┤
│ ◯ 晚餐 →                         +     │
│   0 / 499千卡                           │
├────────────────────────────────────────┤
│ ◯ 小吃 →                         +     │
│   0 / 100千卡                           │
└────────────────────────────────────────┘
```

每个餐次行包含：

| 元素 | 展示 | 说明 |
| --- | --- | --- |
| 餐次图标 | 早餐咖啡、午餐餐盘、晚餐沙拉、小吃苹果 | 图标放在圆形进度环中 |
| 餐次名称 | `早餐 →` | 点击餐次名称或整行进入餐次详情 |
| 热量 | `369 / 598千卡` | 当前餐次已摄入 / 餐次目标 |
| 食物摘要 | `Scrambled Eggs, Banana...` | 只展示 1 行，过长截断 |
| 添加按钮 | 黑色圆形 `+` | 直接添加该餐次食物 |
| 右上入口 | `更多` | 进入更多餐次记录、历史记录或完整列表 |

交互建议：

1. 点击餐次行：进入该餐次详情，查看已记录食物、营养明细、图片和来源。
2. 点击 `+`：直接打开添加食物流程，并默认带入该餐次。
3. 点击 `更多`：进入完整饮食记录列表，可切换日期、查看历史餐次。
4. 餐次图标外圈显示该餐次热量进度，已摄入为绿色，未摄入为浅灰。
5. 餐次没有记录时，不显示“已记录食物”占位，只展示热量 `0 / 目标千卡` 和添加按钮。

设计注意：

1. 四个餐次固定顺序：早餐、午餐、晚餐、小吃。
2. 每行高度稳定，避免有食物摘要和无食物摘要时布局跳动太大。
3. `+` 按钮要足够大，作为主要操作入口。
4. 食物摘要可以中英文混排，来源于用户录入、识别结果或食物标准名。
5. `更多` 不进入饮食计划/营养报告，而是进入营养记录的完整列表或历史视图。

## 三、核心功能一：食物记录 / 热量追踪

### Q：记录方式有哪些？

A：建议支持多种记录方式，按优先级分期：

| 记录方式 | 说明 | 第一阶段建议 |
| --- | --- | --- |
| 拍照识别 | 用户拍食物照片，AI/OCR/视觉模型识别食物和份量，生成营养估算 | 建议第一期做 |
| 手动录入食品名称 | 用户输入“鸡蛋、米饭、牛奶”等，系统匹配食物库或 AI 估算 | 建议第一期做 |
| 语音输入 | 用户说“早餐吃了两个鸡蛋一杯牛奶” | 可与手动输入共用识别能力 |
| 快捷复用 | 复用昨天早餐、常吃食物、收藏餐 | 第二阶段 |
| 扫码录入 | 扫包装食品条码 | 后续 |
| 从外卖/小票导入 | OCR 小票或外卖订单 | 后续 |

### Q：拍照识别应该识别什么？

A：

1. 食物名称。
2. 估算份量，例如一碗、100g、一个、250ml。
3. 餐次，例如早餐、午餐、晚餐、小吃。
4. 营养估算：热量、碳水、蛋白质、脂肪。
5. 置信度和不确定项。

需要注意：拍照识别很难准确判断重量，必须允许用户编辑。

### Q：手动录入食品名称怎么做？

A：建议支持两种输入：

```text
简单食品：鸡蛋、米饭、牛奶、苹果
自然语言：早餐吃了两个鸡蛋、一杯牛奶、一片吐司
```

手动录入后，不直接保存。系统应先把用户输入交给 AI 进行整理和结构化识别，由 AI 返回一个可确认的记录草稿：

```text
早餐
- 鸡蛋 2 个
- 牛奶 250 ml
- 吐司 1 片
估算：369 kcal
碳水 69g / 蛋白质 10g / 脂肪 9g
```

用户确认后才正式保存。

推荐流程：

```text
用户输入食品名称或自然语言
  -> AI 整理食物项、份量、餐次、热量和三大营养素
  -> 返回饮食记录草稿
  -> 用户检查、修改份量或删除错误食物
  -> 用户确认
  -> 保存到服务端
  -> 如果成员是本人且用户授权，再同步写入 Apple 健康营养摄入
```

草稿需要支持用户编辑，因为 AI 可能无法准确判断份量、烹饪方式或品牌食品热量。

草稿至少包含：

1. 餐次。
2. 食物名称。
3. 份量和单位。
4. 估算热量。
5. 碳水、蛋白质、脂肪。
6. AI 识别来源文本。
7. 是否需要用户确认的不确定项。

### Q：点击餐次 `+` 后的食物添加页面怎么设计？

A：参考截图，点击早餐/午餐/晚餐/小吃右侧黑色圆形 `+` 后，打开对应餐次的食物添加页面。页面目标是让用户快速找到食物、低成本添加到当前餐次，并在底部统一完成保存。

页面结构：

```text
      0                         早餐

┌────搜索────┐ ┌────相机────┐ ┌────条形码──┐ ┌────输入────┐ ┌更多┐
│    🔍      │ │    📷      │ │    barcode │ │    Tt      │ │ …  │
└────────────┘ └────────────┘ └────────────┘ └────────────┘ └────┘

┌────────────────────────────────────────┐
│ 🔍 您早餐吃了什么？                     │
└────────────────────────────────────────┘

┌────────────── 食物 ˅ ──────────────┐ ┌──── 经常 ˅ ────┐

Coffee                         2千卡      ＋
1杯 (237毫升)
────────────────────────────────────────
Banana                       134千卡      ＋
1整个，普通 (150克)
────────────────────────────────────────
Scrambled Eggs               100千卡      ＋
1个鸡蛋 (47克)
────────────────────────────────────────

┌────────────────────────────────────────┐
│                  完成                  │
└────────────────────────────────────────┘
```

### Q：顶部数字 `0` 表示什么？

A：表示当前本次添加流程中已选择的食物数量，或已添加条目数量。

建议规则：

1. 初始为 `0`。
2. 用户点击食物右侧 `+` 后，数量递增。
3. 如果支持同一食物多次添加，可以显示总份数或总条目数，具体口径需要统一。
4. 数字圆环可用绿色边框，呼应营养进度颜色。

### Q：顶部标题显示什么？

A：显示当前餐次，例如：

```text
早餐 / 午餐 / 晚餐 / 小吃
```

从哪个餐次点 `+` 进入，就默认添加到哪个餐次。用户不需要再选择餐次，降低操作成本。

### Q：快捷操作区包含什么？

A：快捷操作区放在页面顶部，是食物添加的功能入口。

| 操作 | 展示 | 作用 |
| --- | --- | --- |
| 搜索 | 放大镜，默认选中 | 通过食物名称搜索和选择标准食物 |
| 相机 | 相机图标 | 拍照识别食物 |
| 条形码 | 条形码图标 | 扫包装食品条码，后续能力 |
| 输入 | 文本图标，可带“新的”角标 | 自然语言输入，例如“两个鸡蛋一杯牛奶” |
| 更多 | `…` | 收纳低频/拓展功能 |

`更多` 中可收纳：

1. 批量添加。
2. 自定义食物。
3. 自定义菜谱。
4. 导入历史餐单。
5. 复用昨天同餐。
6. 收藏食物。
7. 从 AI 对话生成。

设计原则：高频入口直接露出，低频能力放进 `更多`，避免主界面信息过载。

### Q：搜索栏怎么设计？

A：搜索栏是当前截图中的核心输入入口。

占位文案按餐次动态变化：

```text
早餐：您早餐吃了什么？
午餐：您午餐吃了什么？
晚餐：您晚餐吃了什么？
小吃：您吃了什么小吃？
```

交互建议：

1. 默认选中搜索模式时，搜索栏高亮绿色边框。
2. 输入关键词后实时过滤食物列表。
3. 搜索无结果时，提供“创建自定义食物”或“用 AI 估算”。
4. 搜索结果优先展示常用食物、最近添加、完全匹配项。

### Q：筛选区怎么设计？

A：搜索栏下方放两个下拉筛选：

```text
食物 ˅     经常 ˅
```

建议含义：

| 筛选 | 说明 |
| --- | --- |
| 食物 | 类型筛选，例如食物、菜谱、品牌食品、自定义 |
| 经常 | 排序/来源筛选，例如经常、最近、收藏、推荐 |

第一期可以先展示静态筛选入口，不必做复杂分类，但交互位置先预留。

### Q：食物列表区怎么设计？

A：食物列表是核心内容区。每一条食物都要足够简洁，让用户不需要额外计算就能判断是否添加。

每条食物包含：

| 内容 | 示例 | 说明 |
| --- | --- | --- |
| 食物名称 | `Coffee` / `Banana` / `Scrambled Eggs` | 可中英文，优先展示用户语言；标准食物可保留英文名 |
| 标准份量 | `1杯 (237毫升)` / `1个鸡蛋 (47克)` | 降低用户估算门槛 |
| 热量 | `2千卡` / `134千卡` | 右侧展示，便于快速扫描 |
| 添加按钮 | 绿色描边圆形 `+` | 点击后加入当前餐次 |

设计原则：

1. 信息极简：名称、份量、热量、添加按钮。
2. 份量标准化：让用户知道默认添加的是多少。
3. 列表分隔线清晰，方便快速浏览。
4. 右侧热量和 `+` 按钮对齐，形成稳定扫描线。
5. 食物名称过长时单行截断，份量另起一行。

### Q：点击食物右侧 `+` 后发生什么？

A：

1. 当前食物按标准份量加入本次待保存列表。
2. 左上数量加 1。
3. 底部 `完成` 按钮进入可用状态。
4. 可给 `+` 按钮一个轻量反馈，例如短暂变为勾选或数字。
5. 如果用户需要改份量，可点击食物行进入份量编辑，或点击已添加项进入编辑。

待确认：

1. 同一食物重复点击 `+` 是新增一条，还是增加份数？
2. 是否需要在列表页直接显示已添加数量，例如 `+` 变成 `1`？
3. 是否需要支持左上数量点击查看本次已选清单？

### Q：底部 `完成` 按钮怎么设计？

A：`完成` 固定在底部，不随列表滚动消失。

行为：

1. 未添加任何食物时，按钮可以禁用或低亮。
2. 添加至少一个食物后，按钮可点击。
3. 点击 `完成` 后，保存本次录入数据到当前餐次。
4. 保存成功后返回营养首页或餐次详情。

设计原因：

1. 用户在列表任意位置都能一键完成。
2. 符合移动端拇指操作习惯。
3. 避免用户添加多个食物后还要回到顶部保存。

### Q：这个页面第一期包含哪些能力？

A：建议第一期做：

1. 搜索。
2. 相机。
3. 输入。
4. 更多入口占位。
5. 食物标准列表。
6. 食物右侧 `+` 添加。
7. 底部固定 `完成`。

条形码、批量添加、自定义菜谱、导入历史餐单可以先放在 `更多` 或作为后续能力。

### Q：是否要区分早餐、午餐、晚餐、小吃？

A：需要。餐次是看板和 AI 分析的重要维度。

第一期建议固定四类：

1. 早餐。
2. 午餐。
3. 晚餐。
4. 小吃 / 加餐。

后续可扩展：

1. 夜宵。
2. 运动前/运动后补给。
3. 自定义餐次。

### Q：餐次如何自动判断？

A：可以按时间默认推断，但允许用户修改。

建议默认规则：

| 时间 | 默认餐次 |
| --- | --- |
| 05:00 - 10:30 | 早餐 |
| 10:30 - 14:30 | 午餐 |
| 14:30 - 20:30 | 晚餐 |
| 其他时间 | 小吃 |

注意：不同用户作息不同，后续可支持自定义餐次时间。

## 四、核心功能二：数据存储讨论

### Q：饮食记录应该存在哪里？

A：建议采用“服务端为主、Apple 健康为辅、本地不存饮食业务数据”的策略。

```text
服务端：饮食记录事实源
Apple 健康：本人营养摄入与能量消耗的系统健康库
本地：不新增饮食业务缓存，仅允许项目已有公共请求缓存
```

原因：

1. 服务端需要支持多设备、家庭成员、AI 对话引用、饮食计划和报告。
2. Apple 健康只能代表当前 iPhone 当前用户，不能表达家庭成员完整资料。
3. Apple 健康不适合保存食物照片、餐次、食物明细、AI 识别来源、成员关系。
4. 本地长期存储会导致多设备不一致，第一原则应以服务端为主。

### Q：服务端应该保存哪些饮食数据？

A：建议服务端保存完整饮食记录：

1. 成员 ID。
2. 日期和时间。
3. 餐次：早餐、午餐、晚餐、小吃。
4. 食物项列表。
5. 每个食物的名称、份量、单位、估算营养。
6. 总热量、碳水、蛋白质、脂肪。
7. 图片附件 ID，关联饮食图片。
8. 记录来源：拍照识别、手动录入、AI 对话、Apple 健康导入。
9. AI 识别置信度和用户是否编辑。
10. 是否已写入 Apple 健康。
11. Apple 健康同步状态。

### Q：饮食图片存在哪里？

A：图片应走现有附件/OSS 流程，服务端饮食记录只关联附件 ID。

```text
饮食图片 -> 上传 OSS -> 服务端文件记录 -> 饮食记录关联 file_id
```

不要把图片直接塞进饮食记录 JSON。

### Q：本地要不要存饮食数据？

A：不要。饮食营养业务数据只存在两个地方：

```text
服务端
Apple 健康
```

客户端本地不单独建立饮食记录缓存、不保存最近几天饮食记录、不保存离线 outbox，也不把本地作为任何饮食数据事实源。

允许存在的本地数据只有项目中已经具备的公共请求缓存，例如网络层请求缓存、图片临时缓存、系统级 URL cache 等。这类缓存是通用基础设施，不是饮食营养模块自己的业务存储。

边界：

1. 饮食记录、食物明细、餐次、图片关联、营养汇总：以服务端为主。
2. 本人营养摄入、能量消耗：按 Apple 健康能力读取/写入。
3. 本地不维护饮食记录业务表。
4. 本地不维护饮食记录离线队列。
5. 本地不作为跨设备同步依据。
6. 页面打开需要数据时，优先请求服务端；如命中项目公共请求缓存，可作为网络层优化使用。

因此可以表达为：

```text
饮食营养业务数据 = 服务端 + Apple 健康
本地 = 仅使用项目已有公共请求缓存，不新增饮食业务缓存
```

## 五、Apple 健康数据边界

### Q：哪些内容可以写入 Apple 健康？

A：Apple 健康适合写入营养摄入的数值项，不适合保存完整饮食记录。

第一期建议写入：
| 应用字段 | Apple 健康字段 | 单位 |
| --- | --- | --- |
| 能量 / 热量摄入 | Dietary Energy Consumed | kcal |
| 蛋白质 | Dietary Protein | g |
| 碳水化合物 | Dietary Carbohydrates | g |
| 总脂肪 | Dietary Fat Total | g |

后续可扩展：

1. 膳食纤维。
2. 糖。
3. 钠。
4. 胆固醇。
5. 饮水量。

### Q：哪些内容不能只靠 Apple 健康保存？

A：

1. 食物名称。
2. 食物照片。
3. 餐次。
4. 食物份量和单位。
5. AI 识别过程。
6. 用户编辑记录。
7. 家庭成员归属。
8. 饮食计划和营养报告。

这些必须在服务端保存。

### Q：本人和其他成员怎么区分？

A：这是本需求最重要的边界之一。

| 成员类型 | 服务端保存 | Apple 健康写入 | Apple 健康读取 |
| --- | --- | --- | --- |
| 本人 | 是 | 是 | 是 |
| 家庭成员/他人 | 是 | 否 | 否 |

原因：

1. Apple 健康是当前设备当前用户的健康库。
2. App 不能把妈妈、孩子、伴侣的饮食数据写入本机用户的 Apple 健康。
3. 家庭成员饮食数据只能进入服务端成员档案。

### Q：本人记录时，先写服务端还是先写 Apple 健康？

A：建议业务上以服务端为主，Apple 健康为同步目标。

推荐流程：

```text
用户确认饮食记录
  -> 保存到服务端
  -> 如果成员是本人且用户授权 Apple 健康
       -> 写入 Apple 健康
       -> 回写服务端 sync 状态
```

好处：

1. 即使 Apple 健康授权失败，服务端记录仍存在。
2. 多设备和 AI 对话仍能看到记录。
3. Apple 健康写入状态可以在服务端跟踪。

### Q：如果 Apple 健康写入成功，但服务端保存失败怎么办？

A：正常流程下不存在这种情况。

规则必须固定为：

```text
服务端保存成功
  -> 才允许写入 Apple 健康
```

如果服务端保存失败：

1. 不写入 Apple 健康。
2. 提示用户保存失败。
3. 用户可重试保存。
4. 不进入 Apple 健康同步流程。

因此不会出现“Apple 健康已经写入成功，但服务端没有记录”的数据状态。

### Q：如何读取 Apple 健康中的其它渠道营养摄入？

A：本人看板需要合并：

```text
服务端饮食记录
+ Apple 健康中其它 App / 手动录入的营养摄入
+ Apple 健康中的能量消耗
```

合并时要区分来源：

1. 服务端记录：应用内创建的完整饮食记录。
2. Apple 健康记录：其它渠道或系统健康中已有的营养数据。
3. 应用写入 Apple 健康的记录：应该避免重复计算。

### Q：如何避免服务端记录和 Apple 健康记录重复计算？

A：需要给应用写入 Apple 健康的样本打来源标记或保存映射。

讨论方案：

1. 写入 Apple 健康时，在 metadata 中保存 app record ID。
2. 服务端记录保存 Apple Health sync ID / sync status。
3. 读取 Apple 健康时，识别由本 App 写入的样本，不再作为“外部额外摄入”重复累加。
4. 无法识别来源时，按时间和数值做弱去重，但要谨慎，避免误删其它 App 数据。

第一期建议目标：

```text
本人看板 = 服务端饮食记录 + Apple 健康外部来源营养摄入 + Apple 健康能量消耗
```

其中“外部来源营养摄入”不包含本 App 已同步到 Apple 健康的样本。

### 讨论工单：Apple 健康为什么会重复上传，应该如何处理？

背景日志：

```text
POST /api/v1/nutrition/apple-health/energy-burn-imports/ status=200
body.code=40901
body.msg=duplicate_apple_health_sample
body.data.duplicates=[
  {
    "apple_health_id": "3C8BBFB8-885D-44E1-93C7-E8A3692829F3",
    "record_id": 82,
    "duplicate": true
  }
]

响应解码成功 type=RemoteAppleHealthImportResponse keys=root=[code,data,msg] data=[duplicates,imported]
HealthKit 同步失败 memberID=10 date=2026-06-18 error=duplicate_apple_health_sample
```

### Q：为什么会出现重复上传？

A：Apple 健康同步天然会重复触发，重复上传不是异常，而是同步模型里必须接受的常态。

常见原因：

1. 用户多次进入饮食营养首页，每次首页都尝试同步当天 Apple 健康数据。
2. App 冷启动、前台恢复、切换成员、刷新看板时，可能重复执行同一天同步。
3. Apple 健康查询通常按日期范围读取样本，客户端每次会重新拿到当天全部 sample，而不是只拿新增 sample。
4. 客户端没有长期保存饮食业务数据，也不应该本地持久化一套 Apple Health 已同步清单，因此不能只靠本地判断是否传过。
5. 服务端才是主数据源，必须承担最终幂等去重责任。
6. 多设备、重装 App、清缓存后，本地状态会丢失，但 Apple 健康样本仍然存在，重新上传同一个 `apple_health_id` 是合理行为。
7. 网络超时或客户端未收到响应时，用户/系统重试也会造成同一批样本再次提交。

因此，重复上传不是“客户端不该发生”的问题，而是“服务端必须幂等处理，客户端必须把重复视为同步结果”的问题。

### Q：什么才是重复样本的唯一标识？

A：建议使用 `member_id + apple_health_id` 作为幂等键。

说明：

1. `apple_health_id` 对应 HealthKit sample UUID。
2. 同一个 HealthKit sample 被重复上传时，UUID 不变。
3. 加上 `member_id` 是为了成员数据隔离，避免不同成员之间误判。
4. 能量消耗记录可映射到 `NutritionEnergyBurnRecord.apple_health_id`。
5. 外部营养摄入可映射到 Apple Health 导入记录或对应 `NutritionIntake.apple_health_id`。

### Q：服务端应该怎么处理重复上传？

A：服务端应该把重复上传当成幂等成功，而不是业务失败。

建议规则：

1. 如果样本不存在：创建正式记录，放入 `data.imported`。
2. 如果样本已存在：不重复创建，不重复计入统计，放入 `data.duplicates`。
3. 如果一批数据里有新增也有重复：新增的进入 `imported`，重复的进入 `duplicates`，整体仍然是成功。
4. 如果一批数据全部重复：不创建新记录，返回 `imported=[]`、`duplicates=[...]`，整体仍然是成功。
5. 真正失败只包括：无权限、非本人成员、参数格式错误、服务端异常、数据越权等。

推荐响应语义：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "imported": [],
    "duplicates": [
      {
        "apple_health_id": "3C8BBFB8-885D-44E1-93C7-E8A3692829F3",
        "record_id": 82,
        "duplicate": true
      }
    ]
  }
}
```

HTTP 状态建议：

| 场景 | HTTP | code | 说明 |
| --- | --- | --- | --- |
| 全部新增 | `201` | `0` | 创建成功 |
| 部分新增、部分重复 | `200` 或 `201` | `0` | 同步处理成功 |
| 全部重复 | `200` | `0` | 幂等成功，无新增 |
| 参数错误 | `400` | 非 0 | 真失败 |
| 无成员权限 | `403` | 非 0 | 真失败 |
| 非本人成员触发 Apple 健康同步 | `403` | 非 0 | 真失败 |

### Q：为什么不建议服务端返回 `code=40901`？

A：因为当前项目统一响应规则是 `code != 0` 表示业务失败。

如果重复样本返回：

```json
{
  "code": 40901,
  "msg": "duplicate_apple_health_sample",
  "data": {
    "imported": [],
    "duplicates": [...]
  }
}
```

客户端即使已经成功解码 `data`，统一解码器仍会把它抛成错误，于是出现：

```text
响应解码成功 type=RemoteAppleHealthImportResponse
HealthKit 同步失败 error=duplicate_apple_health_sample
```

这会带来三个问题：

1. 日志误导：用户数据已经幂等处理成功，却记录为同步失败。
2. UI 误导：后续如果接入错误态，可能错误提示用户同步失败。
3. 架构污染：客户端可能被迫在某个接口里特判 `40901`，破坏统一响应语义。

### Q：客户端应该怎么处理？

A：客户端应该保持简单：只负责按触发时机读取 Apple 健康样本并上传，收到成功响应后记录 `imported/duplicates` 数量。

客户端建议：

1. 进入本人饮食营养首页时，可以触发当天 Apple 健康同步。
2. 前台恢复或用户手动刷新时，可以重新同步当天数据。
3. 客户端不需要长期保存“哪些 HealthKit UUID 已同步”的业务清单。
4. 客户端收到 `code=0` 后，根据 `data.imported.count` 和 `data.duplicates.count` 打日志。
5. `duplicates.count > 0` 不展示错误，不进入失败分支。
6. 只有真正网络失败、无权限、参数错误、非本人成员等才进入失败日志。

客户端日志建议：

```text
HealthKit 能量消耗上报完成 memberID=10 date=2026-06-18 samples=82 imported=0 duplicates=82
```

而不是：

```text
HealthKit 同步失败 memberID=10 date=2026-06-18 error=duplicate_apple_health_sample
```

### Q：客户端要不要避免重复上传？

A：可以做轻量优化，但不能依赖它保证正确性。

可选优化：

1. 单次 App 生命周期内，同一个 `memberID + date` 不重复并发同步。
2. 同步中状态加锁，避免用户连续刷新造成并发上传。
3. 同一天短时间内重复进入页面，可以做节流。
4. 如果 Apple 健康支持 anchor query，后续可讨论增量读取。

但第一期不建议为了避免重复上传而引入本地持久同步表，因为：

1. 当前原则是不新增饮食业务本地事实源。
2. 本地状态无法覆盖重装、多设备、服务端已删除等情况。
3. 服务端仍然必须幂等，客户端本地去重只能减少请求量，不能作为正确性依据。

### Q：这个问题的最终结论是什么？

A：重复上传是正常现象，重复计入才是问题，重复被当成失败也是问题。

最终口径：

```text
客户端可以重复上传同一天 Apple 健康样本
-> 服务端按 member_id + apple_health_id 幂等去重
-> 重复样本进入 data.duplicates
-> 响应 code 仍为 0
-> 客户端记录 imported/duplicates 数量
-> 不展示失败、不触发错误态
```

这个讨论结论对应后续实施工单：`NUTRITION-000022 Apple 健康重复样本幂等导入误报失败修正`。

### Q：能量消耗从哪里来？

A：能量消耗建议优先读取 Apple 健康。

来源包括：

1. Apple Watch / iPhone 的活动能量。
2. 静息能量。
3. 运动记录。
4. 其它健康 App 写入的能量消耗。

服务端是否保存能量消耗要谨慎：

1. 可以缓存每日汇总，便于 AI 分析和多设备展示。
2. 但原始活动数据仍以 Apple 健康为准。
3. 对非本人成员，如果没有设备数据，只能手动记录或不展示消耗。

## 六、核心功能三：看板

### Q：今日看板展示什么？

A：看板要让用户一眼看到当天饮食情况：

```text
┌──────────────────────────┐
│ 周六                     │
├──────────────────────────┤
│      今日营养总览         │
│                          │
│ 已摄入   剩余   已消耗    │
│ 369     1626    411      │
│                          │
│ 碳水 蛋白质 脂肪          │
│ 69/243                  │
│ 10/97                   │
│ 9/64                    │
└──────────────────────────┘
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| 已摄入 | 当日饮食热量摄入 |
| 剩余 | 今日目标热量 - 已摄入 + 已消耗，可讨论具体公式 |
| 已消耗 | Apple 健康读取的活动/运动消耗，或总消耗的一部分 |
| 碳水 | 已摄入 / 目标 |
| 蛋白质 | 已摄入 / 目标 |
| 脂肪 | 已摄入 / 目标 |

### Q：剩余热量怎么计算？

A：这是需要产品确认的关键问题。

方案 A：简单目标法

```text
剩余 = 今日摄入目标 - 已摄入
```

优点：简单稳定。

缺点：没有体现运动消耗。

方案 B：运动补偿法

```text
剩余 = 今日摄入目标 - 已摄入 + 已消耗
```

优点：运动后剩余额度增加，符合部分用户直觉。

缺点：可能鼓励用户“运动后多吃”，对减脂用户不一定合适。

方案 C：按目标策略配置

```text
减脂：剩余 = 摄入目标 - 已摄入 + 已消耗 * 0.3
维持：剩余 = 摄入目标 - 已摄入 + 已消耗 * 0.5
增肌：剩余 = 摄入目标 - 已摄入 + 已消耗 * 0.7
```

建议：第一期先用方案 A 或 B，并在文案里明确口径。长期建议根据用户目标配置。

### Q：餐次列表怎么展示？

A：按早餐、午餐、晚餐、小吃展示：

```text
┌──────────────────────────┐
│ 早餐      369/598        │
│ 已记录食物               │
│                      +   │
├──────────────────────────┤
│ 午餐      0/798          │
│                      +   │
├──────────────────────────┤
│ 晚餐      0/499          │
│                      +   │
├──────────────────────────┤
│ 小吃      0/100          │
│                      +   │
└──────────────────────────┘
```

每个餐次需要：

1. 当前餐次已摄入热量。
2. 餐次目标热量。
3. 已记录食物摘要。
4. `+` 添加入口。
5. 点击餐次进入详情。

### Q：餐次目标怎么来？

A：可以按全天目标分配。

默认分配建议：

| 餐次 | 占比 |
| --- | --- |
| 早餐 | 30% |
| 午餐 | 40% |
| 晚餐 | 25% |
| 小吃 | 5% |

用户可后续自定义。

1. 减脂。
2. 维持体重。
3. 增肌。
4. 控糖。
5. 控盐。
6. 控脂。

### 讨论工单：饮食目标如何设计？

背景参考：目标设置页可参考“我的目标”页面形态。

```text
我的目标

起始体重            65.0 千克   >
目标体重            60.0 千克   >

```

### Q：目标设置页应该解决什么问题？

A：目标设置页不是单纯填写数字，而是决定看板所有“目标值”和“剩余值”的来源。

它至少影响：

1. 今日卡路里目标。
2. 今日剩余热量。
3. 碳水、蛋白质、脂肪目标。
4. 早餐、午餐、晚餐、小吃的餐次目标。
5. AI 分析时对“吃多/吃少/蛋白质不足”的判断。
6. 后续饮食计划、减脂/增肌建议和慢病饮食建议。

### Q：目标设置应该分成哪些层？

A：建议分三层，避免第一期就把目标系统做得过重。

| 层级 | 作用 | 第一阶段建议 |
| --- | --- | --- |
| 目标模式 | 用户想达成什么，例如减重、维持、增重、控糖 | 必做 |
| 能量目标 | 每日卡路里目标、每周体重变化目标 | 必做 |
| 营养目标 | 碳水、蛋白质、脂肪比例或克数 | 必做默认，可自定义 |

长期可扩展第四层：慢病专项目标，例如控盐、低嘌呤、低糖、低脂、肾病低蛋白。

### Q：目标模式有哪些？

A：第一期建议先支持常见目标，慢病目标作为标签或后续扩展。

| 目标 | 说明 | 影响 |
| --- | --- | --- |
| 减重 | 希望降低体重 | 每日热量低于维持热量 |
| 维持体重 | 保持当前体重 | 每日热量接近维持热量 |
| 增重/增肌 | 希望增加体重或肌肉 | 每日热量高于维持热量，蛋白质目标更高 |
| 控糖 | 控制碳水波动 | 碳水比例和餐次分布更谨慎 |
| 控盐 | 控制钠/盐摄入 | 后续需要钠和盐目标 |
| 控脂 | 控制脂肪和饱和脂肪 | 脂肪目标更谨慎 |
| 自定义 | 用户手动指定热量和营养目标 | 不自动计算或只提供建议 |

第一期页面上可以先展示：`减重`、`维持体重`、`增重/增肌`、`自定义`。控糖、控盐、控脂先作为 AI 分析或后续营养目标扩展。

### Q：页面字段怎么设计？

A：参考图中的字段建议如下：

| 字段 | 示例 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| 目标 | 减重 | 必填 | 决定热量缺口/盈余策略 |
| 起始体重 | 65.0 千克 | 建议填 | 用于展示目标进度和计算体重变化 |
| 当前体重 | 65.0 千克 | 建议补充 | 如果和起始体重不同，看板和目标进度更准确 |
| 目标体重 | 60.0 千克 | 减重/增重必填 | 用于目标进度，不直接等于每日热量 |
| 活跃水平 | 低 | 必填 | 用于估算维持热量 |
| 每周目标 | -0.50 千克 | 减重/增重必填 | 控制热量缺口/盈余速度 |
| 卡路里目标 | 1,584 千卡 | 必填 | 可自动计算，也允许手动覆盖 |
| 步数目标 | 10,000 | 可选 | 参考图中的“设置目标”，建议明确命名为步数目标 |
| 营养目标 | 默认 | 必填 | 默认比例或自定义碳水/蛋白质/脂肪 |

说明：参考图里的“设置目标 10,000”语义不够清晰，饮食模块内建议改成 `步数目标` 或 `活动目标`，避免和“目标设置”重复。

### Q：活跃水平怎么设计？

A：第一期建议用用户能理解的低/中/高，不要暴露复杂运动系数。

| 活跃水平 | 文案 | 适用人群 |
| --- | --- | --- |
| 低 | 久坐、很少运动 | 办公、日常步数较少 |
| 中 | 每周轻中度运动 | 每周运动 1-3 次 |
| 高 | 经常运动或体力活动多 | 每周运动 4 次以上或体力劳动 |

后续如果需要更精确，可以扩展为：

1. 久坐。
2. 轻度活跃。
3. 中度活跃。
4. 高度活跃。
5. 极高活跃。

### Q：每周目标怎么限制？

A：每周目标直接影响热量缺口，必须限制范围，避免过激目标。

建议范围：

| 目标模式 | 每周目标范围 | 推荐默认 |
| --- | --- | --- |
| 减重 | `-0.25` 到 `-1.00` 千克/周 | `-0.50` 千克/周 |
| 维持 | `0` | `0` |
| 增重/增肌 | `+0.10` 到 `+0.50` 千克/周 | `+0.25` 千克/周 |

安全提示：

1. 超过范围时不建议允许保存。
2. 低体重、孕期、儿童、慢病人群应提示谨慎。
3. 每周目标只是估算，不应承诺实际体重变化。

### Q：卡路里目标怎么计算？

A：第一期可以使用“系统建议 + 用户可覆盖”的方式。

计算逻辑建议：

```text
基础代谢 BMR
-> 根据活跃水平估算维持热量 TDEE
-> 根据每周目标换算每日热量差
-> 得到每日卡路里目标
```

示例：

```text
减重 0.50 千克/周
约等于每周 3,850 kcal 缺口
约等于每日 550 kcal 缺口

卡路里目标 = 维持热量 - 550
```

注意：

1. 具体公式可后续在数据详设/服务端详设中确定。
2. 第一阶段如果用户基础资料不完整，可以使用默认目标。
3. 自动生成的卡路里目标必须允许用户手动调整。
4. 手动调整后要标记为“自定义卡路里目标”，避免下次被自动覆盖。

### 讨论工单：参考 YAZIO 热量摄入计算器，目标计算流程可以怎么优化？

参考页面：https://www.yazio.com/en/calorie-intake-calculator

### Q：YAZIO 计算器的核心流程是什么？

A：它的核心不是复杂表单，而是把热量目标拆成一个用户容易理解的估算流程。

可借鉴流程：

```text
基础身体信息
-> 性别 / 年龄 / 身高 / 当前体重
-> 活动水平
-> 计算基础代谢 BMR
-> 计算维持热量 TDEE
-> 根据目标模式生成建议热量
-> 用户确认或手动调整
```

这个流程的好处：

1. 用户知道“卡路里目标”不是凭空来的。
2. 可以解释为什么同样体重，不同活动水平目标不同。
3. 自动计算结果可以作为建议值，而不是强制值。
4. 后续 AI 解释目标时有依据，例如“你的目标基于低活跃水平和每周减重 0.5kg 计算”。

### Q：YAZIO 这类计算器真正优秀的部分是什么？

A：优秀点不是“有四个网页计算器”，而是它把同一套人体模型拆成了四个用户问题入口。

参考入口：

| 入口 | 用户真正想问的问题 | 底层模型 |
| --- | --- | --- |
| BMI | 我现在偏瘦、正常、超重还是肥胖？ | 身高 + 体重 |
| 理想体重 | 我的目标体重大概应该在哪个范围？ | 身高 + BMI 健康区间 / 理想体重公式 |
| 每日卡路里摄入 | 我每天应该吃多少？ | BMR + 活跃水平 + 目标修正 |
| 卡路里消耗 | 我每天大概消耗多少？运动消耗如何理解？ | BMR + 活跃水平 + 活动/运动估算 |

可以融入项目的优秀设计：

1. **统一人体模型**：不要每个页面自己算一遍身高、体重、年龄、活动水平。
2. **多个入口共用结果**：目标页、总结页、AI 对话都读同一套计算结果。
3. **结果可解释**：展示“为什么是这个结果”，而不是只给数字。
4. **范围优先于单点**：理想体重更适合给范围，不要给一个看似精确的唯一值。
5. **估算和事实分开**：BMR/TDEE/BMI 是估算；饮食记录、Apple 健康消耗是事实数据。
6. **逐步披露复杂度**：普通用户看到建议值，高级用户或详情页再看 BMR/TDEE/BMI。

### Q：我们项目中应该怎么融入这四类计算器？

A：不建议第一期做四个独立计算器页面。建议做成“目标设置和总结页里的统一健康评估模块”。

产品形态建议：

```text
我的目标
-> 重新计算卡路里目标
-> 展示计算结果
   - BMI：当前身体状态
   - 理想体重范围：建议目标区间
   - 维持热量 TDEE：不增不减大概需要多少
   - 建议摄入：结合目标后的每日卡路里
   - 消耗说明：基础代谢 + 日常活动 + Apple 健康运动消耗
-> 用户确认使用建议
```

首页/总结页可以弱展示：

1. 当前 BMI 标签，例如 `正常`、`超重`。
2. 当前目标是否在理想体重范围内。
3. 今日已摄入、已消耗、剩余是否合理。

AI 对话可以使用：

1. “你的目标体重在健康范围内/偏激进”。
2. “今天消耗主要来自 Apple 健康活动记录”。
3. “当前摄入目标是基于低活跃水平和减重目标计算”。

### Q：BMI 在项目里怎么使用？

A：BMI 适合作为状态标签，不适合作为唯一健康判断。

计算：

```text
BMI = 体重kg / (身高m * 身高m)
```

展示建议：

```text
BMI：23.9
状态：正常
```

注意：

1. BMI 不区分肌肉和脂肪，健身人群可能偏高但不一定不健康。
2. 儿童、孕期、特殊疾病人群不应只用成人 BMI 判断。
3. 第一阶段只作为辅助标签，不直接驱动强制目标。

### Q：理想体重怎么设计？

A：理想体重建议输出范围，不输出一个绝对值。

第一期建议使用 BMI 健康区间反推：

```text
理想体重下限 = 18.5 * 身高m * 身高m
理想体重上限 = 24.0 * 身高m * 身高m
```

也可以保留 Broca 公式作为参考值：

```text
Broca 参考体重 = 身高cm - 100
```

产品上建议展示为：

```text
建议体重范围：56.3 - 73.0kg
当前目标体重：60.0kg，位于建议范围内
```

不要把“理想体重”做成强提醒，避免用户误以为系统在医学诊断。

### Q：卡路里消耗计算器如何融入？

A：项目里已经有 Apple 健康能量消耗同步，所以“消耗计算器”不应替代 Apple 健康事实数据。

建议分层：

| 类型 | 来源 | 用途 |
| --- | --- | --- |
| BMR | 公式估算 | 解释基础代谢 |
| TDEE | BMR * 活跃系数 | 目标计算、维持热量解释 |
| Apple 健康活动消耗 | HealthKit | 本人今日事实消耗 |
| 手动消耗记录 | 服务端 `NutritionEnergyBurnRecord` | 家庭成员或未接 HealthKit 场景 |

看板里的 `已消耗` 应优先使用事实数据：

```text
本人：Apple 健康活动消耗 + 已同步服务端消耗
家庭成员：手动能量消耗记录
```

TDEE 主要用于目标计算和解释，不直接等于今日运动消耗。

### Q：第一期要不要做四个独立计算器页面？

A：不建议。

第一期建议：

1. 不做独立的 `BMI 计算器` 页面。
2. 不做独立的 `理想体重计算器` 页面。
3. 不做独立的 `每日卡路里摄入量计算器` 页面。
4. 不做独立的 `卡路里消耗计算器` 页面。

而是把它们融入：

| 模块 | 融入方式 |
| --- | --- |
| 我的目标 | 重新计算时展示 BMI、理想体重范围、维持热量、建议摄入 |
| 总结详细页 | 展示当前 BMI 标签、目标体重是否在建议范围内 |
| 营养看板 | 已摄入、已消耗、剩余仍按业务数据展示 |
| AI 对话 | 作为解释上下文，帮助 AI 判断目标是否合理 |

后续如果产品需要“健康计算工具箱”，再把同一套计算结果拆成独立入口，不重新做公式。

### Q：我们当前目标页可以吸收哪些设计？

A：建议吸收“轻量计算 + 可解释 + 可覆盖”的思路。

目标设置页补充：

| 字段 | 当前是否已有 | 建议 |
| --- | --- | --- |
| 性别 | 成员档案可能已有 | 不在目标页重复展示，计算时从成员档案读取 |
| 年龄 | 成员出生日期可推导 | 不手填，服务端按生日计算 |
| 身高 | 成员档案可能缺失 | 如果缺失，目标页引导补充 |
| 当前体重 | 已建议增加 | 必须参与重新计算 |
| 活跃水平 | 已有低/中/高 | 第一阶段保持低/中/高，后续可扩展“很高” |
| 目标模式 | 已有 | 决定热量缺口或盈余 |
| 每周目标 | 已有 | 决定减重/增重速度 |
| 卡路里目标 | 已有 | 计算结果，可手动覆盖 |

第一期页面不建议变成很长的问卷。更好的方式是：

1. `我的目标` 页面仍保持列表形态。
2. 点击 `重新计算卡路里目标` 时，如果缺少身高、当前体重等必要字段，再进入补充页。
3. 计算结果页展示“建议目标 + 计算依据 + 使用/取消”。
4. 用户使用建议后，写入 `卡路里目标` 草稿。

### Q：卡路里重新计算结果应该怎么展示？

A：不要只给一个数字，要给“为什么是这个数字”。

建议展示：

```text
建议卡路里目标：1,584 千卡/天

计算依据：
- 当前体重：65.0 千克
- 活跃水平：低
- 目标：减重
- 每周目标：-0.50 千克
- 估算维持热量：2,134 千卡/天
- 每日热量缺口：约 550 千卡

使用建议目标
保留当前目标
```

这样用户会更信任系统建议，也更容易发现基础资料是否填错。

### Q：卡路里目标计算的完整算法流程是什么？

A：建议第一期采用“基础代谢 BMR -> 维持热量 TDEE -> 目标热量差 -> 每日目标”的流程。

完整流程：

```text
1. 收集用户资料
   性别、年龄、身高、当前体重、活跃水平、目标模式、每周目标

2. 计算基础代谢 BMR
   BMR = 身体在静息状态下每天大约消耗多少热量

3. 根据活跃水平计算维持热量 TDEE
   TDEE = BMR * 活跃系数

4. 根据目标模式和每周目标计算每日热量差
   减重：每日热量差为负数
   维持：每日热量差为 0
   增重/增肌：每日热量差为正数

5. 得到建议卡路里目标
   建议卡路里目标 = TDEE + 每日热量差

6. 做安全边界保护
   过低、过高、过快减重都要提示或禁止保存

7. 用户确认或手动覆盖
   用户使用建议值：保存为系统计算目标
   用户手动修改：保存为自定义卡路里目标
```

示例：

```text
当前体重：65kg
活跃水平：低
目标：减重
每周目标：-0.50kg

系统估算：
BMR = 约 1,420 kcal
TDEE = BMR * 1.2 = 约 1,704 kcal
每周 -0.50kg ≈ 每周 3,850 kcal 缺口
每日热量差 = -3,850 / 7 = -550 kcal

建议卡路里目标 = 1,704 - 550 = 1,154 kcal
如果低于安全阈值，系统需要上调到最低建议值或提示风险
```

注意：上面的数字只是说明算法链路，实际结果取决于用户性别、年龄、身高、体重和采用的公式版本。

### Q：BMR 用什么公式？

A：第一期建议使用 `Mifflin-St Jeor` 公式，行业里比较常见，也便于解释。

```text
男性：
BMR = 10 * 体重kg + 6.25 * 身高cm - 5 * 年龄 + 5

女性：
BMR = 10 * 体重kg + 6.25 * 身高cm - 5 * 年龄 - 161
```

如果性别未知：

1. 优先提示用户补充。
2. 如果必须给默认目标，可以使用保守默认目标，不做精确计算。
3. 不建议静默假设为男性或女性。

### Q：TDEE 怎么计算？

A：TDEE 是维持当前体重的大致每日热量消耗。

```text
TDEE = BMR * 活跃系数
```

活跃系数建议：

| 活跃水平 | 系数 | 说明 |
| --- | --- | --- |
| 低 | `1.2` | 久坐、很少运动 |
| 中 | `1.375` | 每周轻中度运动 |
| 高 | `1.55` | 经常运动 |
| 很高 | `1.725` | 体力劳动或高频训练，第一期可不展示 |

第一期 UI 只需要低/中/高，数据层预留很高。

### Q：每周目标怎么换算成每日热量差？

A：使用常见估算：`1kg 体重变化 ≈ 7700 kcal`。

```text
每周热量差 = 每周目标kg * 7700
每日热量差 = 每周热量差 / 7
```

示例：

```text
每周目标 = -0.50kg
每周热量差 = -0.50 * 7700 = -3850 kcal
每日热量差 = -3850 / 7 = -550 kcal
```

目标模式对应：

| 目标模式 | 每日热量差 |
| --- | --- |
| 减重 | 负数 |
| 维持 | `0` |
| 增重/增肌 | 正数 |
| 自定义 | 用户手动指定，可不按每周目标计算 |

### Q：最终卡路里目标怎么得到？

A：

```text
建议卡路里目标 = TDEE + 每日热量差
```

例如：

```text
TDEE = 2134 kcal
每日热量差 = -550 kcal
建议卡路里目标 = 1584 kcal
```

保存时要区分两个状态：

1. `系统计算目标`：用户点击“使用建议目标”，后续资料变化时可以提示重新计算。
2. `自定义目标`：用户手动改过卡路里，后续不要静默覆盖。

### Q：算法需要哪些边界保护？

A：必须加边界，不然目标会被算得过激。

建议规则：

1. 每周减重默认不超过 `-1.00kg/周`。
2. 每周增重默认不超过 `+0.50kg/周`。
3. 维持体重时每日热量差固定为 `0`。
4. 建议卡路里目标不能小于安全下限。
5. 如果基础资料缺失，不做精确计算，改为提示补充资料或使用默认目标。
6. 孕期、哺乳期、儿童青少年、慢病饮食用户需要额外提示，不建议直接套普通减重算法。

安全下限第一期可以先使用产品规则配置，不写死在客户端。服务端返回结果时带上是否触发风险提示。

### Q：活跃水平是否要从低/中/高扩展？

A：第一期 UI 保持低/中/高更简单，但数据设计建议预留更细粒度。

建议映射：

| UI 展示 | 数据值 | 说明 |
| --- | --- | --- |
| 低 | `low` | 久坐、很少运动 |
| 中 | `medium` | 每周轻中度运动 |
| 高 | `high` | 经常运动 |
| 很高 | `very_high` | 体力劳动或高频训练，第一期可不展示 |

第一期只展示前三项，数据层保留 `very_high` 不会增加用户复杂度，但能给后续健身用户留空间。

### Q：是否需要展示 BMR / TDEE？

A：第一期不需要在主页面直接展示，但重新计算结果里可以展示“估算维持热量”。

建议：

1. `BMR` 不直接暴露给普通用户，避免理解成本。
2. `TDEE/维持热量` 可以展示，因为它解释了卡路里目标的来源。
3. 数据层保存 `bmr_kcal`、`tdee_kcal` 和 `formula_version`，方便排障和后续解释。
4. AI 对话可以读取这些字段，用自然语言解释目标。

### Q：目标计算的边界提醒怎么设计？

A：目标计算必须是健康建议，不是承诺。

提示文案建议：

```text
热量目标为估算值，会受到体重变化、运动量、疾病、用药和记录准确性的影响。
如果你处于孕期、哺乳期、儿童青少年阶段，或有慢病饮食限制，建议咨询专业医生或营养师。
```

触发场景：

1. 用户选择过低卡路里目标。
2. 用户选择过快减重。
3. 用户选择低碳水、控糖、控盐、控脂等模式。
4. 用户基础资料缺失导致只能使用默认值。

### Q：营养目标怎么设计？

A：营养目标决定碳水、蛋白质、脂肪的每日目标。

建议支持两种模式：

| 模式 | 说明 | 适合 |
| --- | --- | --- |
| 默认 | 根据目标模式自动分配三大营养素 | 大多数用户 |
| 自定义 | 用户手动设置比例或克数 | 健身、控糖、慢病管理用户 |

默认比例建议：

| 目标模式 | 碳水 | 蛋白质 | 脂肪 | 说明 |
| --- | --- | --- | --- | --- |
| 减重 | 45% | 25% | 30% | 提高蛋白质，控制总热量 |
| 维持 | 50% | 20% | 30% | 均衡饮食 |
| 增肌 | 45% | 30% | 25% | 提高蛋白质 |
| 控糖 | 40% | 25% | 35% | 控制碳水，需风险提示 |
| 自定义 | 用户设置 | 用户设置 | 用户设置 | 比例合计必须为 100% |

克数换算：

```text
碳水克数 = 卡路里目标 * 碳水比例 / 4
蛋白质克数 = 卡路里目标 * 蛋白质比例 / 4
脂肪克数 = 卡路里目标 * 脂肪比例 / 9
```

### Q：餐次目标怎么跟随目标变化？

A：餐次目标应该由全天卡路里目标和餐次分配比例计算。

默认分配建议仍沿用看板章节：

| 餐次 | 占比 |
| --- | --- |
| 早餐 | 30% |
| 午餐 | 40% |
| 晚餐 | 25% |
| 小吃 | 5% |

例如卡路里目标为 `1,584 kcal`：

| 餐次 | 目标 |
| --- | --- |
| 早餐 | 475 kcal |
| 午餐 | 634 kcal |
| 晚餐 | 396 kcal |
| 小吃 | 79 kcal |

后续可以支持用户自定义餐次分配，比如不吃早餐、训练日晚餐更高等。

### Q：目标数据是成员维度还是账号维度？

A：建议目标是成员维度。

原因：

1. 家庭成员可能有不同年龄、性别、体重、疾病和饮食目标。
2. 用户本人和妈妈/孩子的热量目标不能共用。
3. AI 分析需要结合具体成员的目标，而不是当前登录账号的目标。

成员差异：

| 成员类型 | 是否支持目标 | Apple 健康关系 |
| --- | --- | --- |
| 本人 | 支持完整目标 | 可结合 Apple 健康活动消耗 |
| 家庭成员 | 支持服务端目标 | 不读写当前设备 Apple 健康 |

### Q：目标页面入口放在哪里？

A：建议至少提供三个入口：

1. `总结` 卡片右上 `详细信息` 页面内，展示当前目标并可进入编辑。
2. 饮食营养首页右上更多菜单，进入 `我的目标`。
3. 首次进入饮食营养时，如果没有目标，弹出轻量引导或使用默认目标。

第一期不建议强制用户必须设置目标后才能使用。可以先用默认目标，让用户后续编辑。

### Q：目标变更后历史数据怎么办？

A：目标变更不应该改写历史饮食记录，只影响目标展示和后续分析。

建议规则：

1. 饮食记录是事实数据，不随目标变化。
2. 今日和未来看板使用最新目标。
3. 历史日期如果需要精确复盘，后续可保存每日目标快照。
4. 第一期可以暂不做每日目标快照，历史页按当前目标或服务端默认目标展示，并在后续讨论。

### Q：第一期目标能力做到什么程度？

A：建议第一期目标能力控制范围：

必须做：

1. 支持目标模式：减重、维持、增重/增肌、自定义。
2. 支持卡路里目标。
3. 支持营养目标：默认/自定义。
4. 支持活跃水平。
5. 支持餐次目标自动分配。
6. 看板、餐次、详情页都使用目标数据。

可以延后：

1. 复杂医学目标，例如肾病低蛋白、痛风低嘌呤。
2. 周/月目标趋势。
3. 每日目标快照。
4. AI 自动生成目标并一键应用。
5. 多套目标模板。
6. 训练日/休息日不同目标。

### Q：目标设置完整流程应该怎么走？

A：目标设置要形成“进入页面 -> 调整目标 -> 重新计算 -> 保存 -> 看板刷新”的闭环。

建议流程：

```text
饮食营养首页 / 总结详细页
-> 我的目标
-> 设置目标模式、体重、活跃水平、每周目标
-> 进入卡路里目标 / 营养目标 / 步数目标等子页面
-> 子页面保存后回写当前目标草稿
-> 我的目标保存
-> 服务端保存成员目标
-> 返回最新目标
-> 刷新总结、营养、餐次详情和 AI 可用上下文
```

第一期建议采用“目标草稿”模式：

1. 进入 `我的目标` 时加载成员当前目标。
2. 页面内所有修改先写入本次目标草稿。
3. `卡路里目标`、`卡路里分布`、`营养目标` 子页面点击保存后，只回写草稿并返回上一页。
4. `我的目标` 页面点击保存后，才整体提交服务端。
5. 如果用户从某个详情页直接进入子页面，且没有父级草稿，则子页面保存可以直接提交目标更新。

这样做的好处：

1. 避免用户在多个子页面改了一半就产生不完整目标。
2. 服务端只接收一次完整目标，校验更简单。
3. 看板刷新时只需要基于一次目标版本变化处理。

### Q：我的目标页面完整操作是什么？

A：`我的目标` 是目标系统的总入口，负责组织目标模式、身体数据、能量目标和营养目标。

页面结构参考：

```text
我的目标

目标                减重        >
起始体重            65.0 千克   >
当前体重            65.0 千克   >
目标体重            60.0 千克   >
活跃水平            低          >
每周目标            -0.50 千克  >
卡路里目标          1,584 千卡  >
步数目标            10,000      >
营养目标            默认        >

保存
```

按钮与点击：

| 区域 | 点击行为 | 打开方式 |
| --- | --- | --- |
| 返回 | 如果有未保存修改，提示是否放弃 | Navigation pop |
| 目标 | 选择减重、维持、增重/增肌、自定义等目标模式 | Navigation push 或 Sheet |
| 起始体重 | 修改目标周期开始体重 | 表单页或输入弹窗 |
| 当前体重 | 修改当前体重 | 表单页或输入弹窗 |
| 目标体重 | 修改目标体重 | 表单页或输入弹窗 |
| 活跃水平 | 选择低/中/高 | 选择页 |
| 每周目标 | 选择每周变化值 | 选择页 |
| 卡路里目标 | 进入卡路里目标页 | Navigation push |
| 步数目标 | 修改每日步数目标 | 输入页，可延后 |
| 营养目标 | 进入营养目标页 | Navigation push |
| 保存 | 校验并保存完整目标 | 提交服务端 |

关键规则：

1. 切换 `目标`、`活跃水平`、`每周目标` 后，卡路里目标应提示“目标已变化，建议重新计算”。
2. 如果用户手动改过卡路里目标，再切换目标模式，不应静默覆盖，必须让用户确认是否重新计算。
3. 当前体重可以来自用户手动输入，也可以后续读取 Apple 健康体重；第一期先支持手动输入。
4. 家庭成员的目标只存服务端，不读取当前设备 Apple 健康体重。

### Q：卡路里目标页面如何设计？

A：`卡路里目标` 页面负责管理每日热量目标，以及它和周末目标、餐次分布的关系。

页面结构参考：

```text
卡路里目标

提示：请注意，禁食倒计时可能会影响您的卡路里目标。
提示：如果想在周末多吃点，可以设置周末热量目标。

卡路里目标（千卡）       1584
重新计算卡路里目标
周末热量目标             >
卡路里分布               >

保存
```

字段说明：

| 字段 | 说明 | 第一阶段 |
| --- | --- | --- |
| 卡路里目标 | 每日基础热量目标，单位 kcal | 必做 |
| 重新计算卡路里目标 | 根据目标模式、当前体重、活跃水平、每周目标重新计算 | 必做 |
| 周末热量目标 | 周末可使用不同热量目标 | 可展示入口，功能可延后 |
| 卡路里分布 | 早餐/午餐/晚餐/小吃比例 | 必做 |

操作规则：

1. 用户可以直接编辑 `卡路里目标（千卡）`。
2. 点击 `重新计算卡路里目标` 后，按当前目标草稿重新计算建议热量。
3. 如果重新计算结果与用户手动值不同，展示确认提示，避免覆盖用户自定义值。
4. 点击 `卡路里分布` 进入餐次分布页面。
5. 点击保存后，回写当前目标草稿中的 `daily_energy_kcal` 和相关标记。

校验规则：

1. 卡路里目标必须大于 0。
2. 建议设置合理上下限，避免输入极端值。
3. 低于安全阈值时不建议直接保存，需展示风险提示。
4. `减重` 模式下热量目标不应高于维持热量太多；`增重/增肌` 模式下不应低于维持热量太多。

### Q：卡路里分布页面如何设计？

A：`卡路里分布` 决定全天热量如何分配到早餐、午餐、晚餐、小吃。

页面结构参考：

```text
卡路里分布

提示：请注意，禁食倒计时可能会影响您的卡路里分布。

早餐        475 千卡        30%  >
午餐        634 千卡        40%  >
晚餐        396 千卡        25%  >
小吃         79 千卡         5%  >

合计                         100%

保存
```

按钮与点击：

| 区域 | 点击行为 |
| --- | --- |
| 返回 | 返回卡路里目标页 |
| 右上重置 | 恢复默认比例 `30/40/25/5` |
| 早餐/午餐/晚餐/小吃 | 修改单个餐次比例 |
| 保存 | 校验合计为 100% 后保存 |

计算规则：

```text
餐次热量目标 = 全天卡路里目标 * 餐次比例
```

示例：

```text
全天目标 1584 kcal
早餐 30% = 475 kcal
午餐 40% = 634 kcal
晚餐 25% = 396 kcal
小吃 5% = 79 kcal
```

校验规则：

1. 四个餐次比例合计必须等于 100%。
2. 任一餐次比例不能为负数。
3. 如果用户不吃早餐，可以允许早餐为 0%，但必须把比例分配到其他餐次。
4. 保存后，饮食首页 `营养` 卡片和餐次详情页目标值必须同步更新。

### Q：营养目标页面如何设计？

A：`营养目标` 页面负责三大营养素比例，以及比例换算出的克数和热量。

页面结构参考：

```text
营养目标

营养                低碳水化合物  >

碳水化合物          174 克（713 千卡）     45%  >
蛋白质               97 克（396 千卡）     25%  >
脂肪                 51 克（475 千卡）     30%  >

合计                                      100%
```

按钮与点击：

| 区域 | 点击行为 |
| --- | --- |
| 返回 | 返回我的目标 |
| 右上重置 | 恢复当前营养模式默认比例 |
| 营养 | 选择默认、低碳水、高蛋白、自定义等模式 |
| 碳水化合物 | 修改碳水比例或克数 |
| 蛋白质 | 修改蛋白质比例或克数 |
| 脂肪 | 修改脂肪比例或克数 |

默认模式建议：

| 模式 | 碳水 | 蛋白质 | 脂肪 | 说明 |
| --- | --- | --- | --- | --- |
| 默认 | 50% | 20% | 30% | 均衡饮食 |
| 减重 | 45% | 25% | 30% | 参考图中的低碳水配置 |
| 高蛋白 | 40% | 30% | 30% | 增肌或蛋白不足用户 |
| 低碳水 | 35%-45% | 25% | 30%-40% | 需要风险提示 |
| 自定义 | 用户设置 | 用户设置 | 用户设置 | 合计必须 100% |

换算规则：

```text
碳水 kcal = 全天卡路里目标 * 碳水比例
蛋白质 kcal = 全天卡路里目标 * 蛋白质比例
脂肪 kcal = 全天卡路里目标 * 脂肪比例

碳水克数 = 碳水 kcal / 4
蛋白质克数 = 蛋白质 kcal / 4
脂肪克数 = 脂肪 kcal / 9
```

示例：

```text
全天目标 1584 kcal
碳水 45% = 713 kcal = 178 g 左右
蛋白质 25% = 396 kcal = 99 g 左右
脂肪 30% = 475 kcal = 53 g 左右
```

校验规则：

1. 三大营养素比例合计必须等于 100%。
2. 低碳水、控糖等模式需要展示健康风险提示。
3. 用户修改某一项克数时，应反算比例，并提示其他项目是否自动调整。
4. 第一阶段建议优先支持“改比例”，克数作为展示结果，减少联动复杂度。

### Q：目标保存后影响哪些页面和数据？

A：目标保存成功后，不只影响目标页本身，还会影响整个饮食营养模块。

影响范围：

| 页面/模块 | 影响 |
| --- | --- |
| 总结卡片 | 剩余热量、已摄入/目标、三大营养素进度 |
| 总结详细页 | 营养素摄入量、营养成分柱状图 |
| 营养卡片 | 早餐/午餐/晚餐/小吃目标热量 |
| 餐次详情页 | 当前餐次卡路里、碳水、蛋白质、脂肪目标 |
| AI 对话 | AI 判断“是否超标/不足”的目标依据 |
| Apple 健康结合 | 本人场景下可结合活动消耗计算剩余热量 |

刷新流程：

```text
目标保存成功
-> 更新成员目标版本
-> 刷新饮食看板
-> 刷新餐次目标
-> 清理或更新本地请求缓存
-> AI 上下文下次读取新目标
```

注意：

1. 饮食记录不变，变化的是目标线。
2. 今日看板应立即使用新目标。
3. 历史日期第一期可以按当前目标展示，后续再增加每日目标快照。

### Q：异常和边界状态怎么处理？

A：目标页需要把错误前置，不要等到看板展示异常才暴露问题。

建议处理：

| 场景 | 处理方式 |
| --- | --- |
| 未设置目标 | 使用默认目标，并提示可进入我的目标调整 |
| 成员资料不完整 | 允许手动设置卡路里目标，不强依赖身高/年龄/性别 |
| 重新计算缺少参数 | 提示补充当前体重、活跃水平或目标模式 |
| 比例合计不是 100% | 禁止保存，并高亮异常项 |
| 卡路里目标过低 | 展示风险提示，必要时禁止保存 |
| 网络失败 | 保留页面草稿，允许重试 |
| 切换成员 | 重新加载该成员目标，未保存草稿需提示 |
| 家庭成员 | 不读取 Apple 健康，只保存服务端目标 |

### Q：目标如何生成？

A：第一期可以让用户手动设置：

1. 每日热量目标。
2. 碳水目标。
3. 蛋白质目标。
4. 脂肪目标。

后续可以由 AI 结合：

1. 年龄、性别、身高、体重。
2. 活动水平。
3. 体检指标。
4. 疾病档案。
5. 用药情况。
6. 用户目标。

自动生成建议目标，但必须让用户确认。

## 八、AI 对话结合

### Q：AI 对话中如何使用饮食数据？

A：建议支持用户在对话中选择并发送：

1. 今日饮食记录。
2. 某一天饮食记录。
3. 某一餐。
4. 最近 7 天饮食汇总。
5. 饮食计划。
6. 营养报告。
7. Apple 健康读取到的能量消耗和营养汇总。

### Q：AI 可以回答哪些问题？

A：

1. “我今天吃得怎么样？”
2. “最近一周蛋白质够不够？”
3. “我妈妈血糖高，这样吃合适吗？”
4. “结合我的体检报告，帮我调整饮食。”
5. “减脂期间晚餐怎么吃？”
6. “今天运动消耗 411 kcal，晚饭还能吃多少？”
7. “我尿酸高，今天这些食物有没有风险？”

### Q：AI 分析需要哪些上下文？

A：按风险和必要性分层：

基础上下文：

1. 饮食记录。
2. 营养汇总。
3. 用户目标。

健康增强上下文：

1. 体检指标。
2. 疾病档案。
3. 用药情况。
4. 年龄、性别、身高、体重。

风险提示：

1. 涉及慢病饮食建议时，需要提醒仅供参考。
2. 涉及糖尿病、肾病、孕期、儿童等高风险人群时，需要更谨慎。
3. 涉及用药和饮食相互作用时，建议咨询医生或营养师。

## 九、饮食计划与营养报告

> 讨论结论：饮食计划、营养报告暂不作为“饮食营养”首页一级模块。当前一级模块只保留 `总结`、`营养`。本节仅保留为后续能力讨论。

### Q：饮食计划是什么？

A：饮食计划是面向未来的建议或安排，例如：

1. 一日三餐计划。
2. 一周减脂餐。
3. 控糖饮食计划。
4. 增肌高蛋白计划。
5. 高血压低盐饮食计划。

第一期可以只作为 AI 生成结果或收藏内容，不必复杂执行。

### Q：营养报告是什么？

A：营养报告是对一段时间饮食数据的总结，例如：

1. 本周摄入趋势。
2. 热量达标率。
3. 蛋白质不足天数。
4. 碳水偏高餐次。
5. 与体重、运动、血糖指标的关系。
6. AI 总结和建议。

报告可以作为 AI 对话的可选上下文。

## 十、成员与权限

### Q：家庭成员怎么处理？

A：家庭成员只进入服务端饮食档案，不写入当前设备 Apple 健康。

场景：

1. 用户记录妈妈早餐。
2. 数据保存到妈妈成员档案。
3. 不写入用户本人 Apple 健康。
4. AI 分析妈妈饮食时，可结合妈妈的体检、疾病、用药。

### Q：本人和家庭成员看板有什么差异？

A：

| 能力 | 本人 | 家庭成员 |
| --- | --- | --- |
| 服务端饮食记录 | 支持 | 支持 |
| Apple 健康营养读取 | 支持 | 不支持 |
| Apple 健康营养写入 | 支持 | 不支持 |
| Apple 健康能量消耗读取 | 支持 | 不支持 |
| 手动记录能量消耗 | 可选 | 可选 |
| AI 分析 | 支持 | 支持 |

## 十一、数据冲突与合并

### Q：如果服务端和 Apple 健康数据不一致，以谁为准？

A：建议分场景：

1. 应用内创建的饮食记录：服务端为准。
2. Apple 健康中其它来源营养摄入：作为补充来源。
3. Apple 健康能量消耗：Apple 健康为准。
4. 看板展示：服务端记录 + Apple 健康外部来源汇总。
5. AI 分析：展示数据来源，避免混淆。

### Q：用户删除服务端饮食记录后，要不要删除 Apple 健康数据？

A：需要讨论。

方案 A：同步删除 Apple 健康中由本 App 写入的样本。

优点：数据一致。

缺点：需要保存 HealthKit sample 标识，复杂度更高。

方案 B：只删除服务端记录，不删除 Apple 健康。

优点：简单。

缺点：Apple 健康仍保留摄入，可能看板重复或不一致。

建议：如果第一期支持写入 Apple 健康，最好同时设计删除/撤销策略，否则用户会困惑。

## 十三、第一期建议范围

### Q：第一期做哪些最合适？

A：建议第一期聚焦闭环：

1. 首页新增“饮食营养”入口。
2. 饮食看板展示今日摄入、剩余、消耗、三大营养素。
3. 早餐、午餐、晚餐、小吃四餐次。
4. 支持手动输入和拍照识别生成饮食记录草稿。
5. 服务端保存饮食记录和图片附件。
6. 本人记录支持写入 Apple 健康营养摄入。
7. 本人看板读取 Apple 健康能量消耗。
8. AI 对话可选择饮食记录发送给 AI 分析。

### Q：第一期先不做什么？

A：

1. 不做复杂食物数据库。
2. 不做条码扫描。
3. 不做外卖订单导入。
4. 不做完整一周饮食计划执行系统。
5. 不做撤销 Apple 健康写入的复杂管理，除非决定必须支持删除同步。
6. 不做家庭成员 Apple 健康写入。

## 十四、需要继续确认的问题

1. 今日“剩余”热量是否要把运动消耗加回来？
2. 活动消耗展示“活动能量”还是“总消耗”？是否包含静息能量？
3. 饮食记录删除后，是否同步删除 Apple 健康样本？
4. Apple 健康中其它 App 写入的营养摄入，是否展示明细，还是只展示汇总？
5. 服务端是否需要保存每日 Apple 健康汇总快照，便于 AI 跨设备分析？
6. 家庭成员是否需要手动记录能量消耗？
7. 食物识别失败时，是否允许直接保存图片并稍后补录？
8. 慢病饮食建议是否需要强制医疗风险提示？
9. 用户是否需要设置目标，还是先用默认目标？
10. 饮食计划和营养报告已确认不作为第一期一级入口；后续需要确认它们是放在 AI 分析结果、详情页，还是第二期独立入口。

## 十五、阶段结论

本功能值得做，但第一期要控制范围。最关键的不是“食物数据库做多全”，而是先打通：

```text
记录饮食
  -> 服务端保存
  -> 本人同步 Apple 健康营养摄入
  -> 读取 Apple 健康消耗和外部营养数据
  -> 看板展示
  -> 发送给 AI 分析
```

数据原则建议定为：

```text
服务端为主：饮食记录、食物明细、图片、成员归属、计划、报告
Apple 健康为辅：本人营养摄入写入、本人能量消耗和外部营养数据读取
本地不存饮食业务数据：只允许使用项目已有公共请求缓存
```

本人和家庭成员必须严格区分：

```text
本人：服务端 + Apple 健康
其他成员：仅服务端
```
