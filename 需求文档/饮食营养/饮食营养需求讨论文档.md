# 饮食营养需求讨论文档

> 文档性质：需求讨论稿。本文只讨论业务功能、产品形态、数据边界、用户场景和待确认问题，不涉及具体技术实现和代码改动。

## 一、业务背景

当前 AI 对话已经支持用户进行健康咨询，并逐步接入医疗档案、检查报告、体检报告、用药记录等健康资料。

为了提升 AI 对用户饮食管理、营养分析、减脂增肌、慢病饮食管理等场景的支持能力，需要新增“饮食营养”模块，让用户可以记录饮食、查看营养总览，并在 AI 对话过程中快速选择已记录的饮食数据、饮食计划、营养报告等信息发送给 AI。

AI 可以结合以下数据给出个性化建议：

1. 饮食记录和营养摄入。
2. Apple 健康中的能量消耗、营养摄入、运动数据。
3. 体检指标，例如血糖、血脂、尿酸、肝肾功能、BMI。
4. 疾病档案，例如糖尿病、高血压、高脂血症、肾病、痛风。
5. 用药情况，例如降糖药、降压药、降脂药、利尿剂等。
6. 用户目标，例如减脂、增肌、控糖、控盐、孕期营养、术后恢复。

### Q：这个功能到底要解决什么？

A：不是简单做一个“食物热量记录器”，而是把“饮食数据”接入到健康档案和 AI 对话里，让 AI 可以基于用户真实饮食和健康状态给出更有针对性的分析。

核心价值：

1. 用户能快速记录饮食。
2. 用户能看到当天摄入、剩余、消耗和三大营养素。
3. AI 能读取用户选择的饮食记录进行分析。
4. 对本人用户，可以与 Apple 健康互通，减少重复录入。
5. 对家庭成员，饮食数据进入服务端成员档案，支持照护场景。

## 二、信息架构

### Q：首页入口放在哪里？

A：建议在首页健康资料入口中新增“饮食营养”一级模块，与医疗档案并列或作为健康管理的一部分。

当前结构：

```text
用户
🏥 医疗档案
├─ 病例
├─ 检查
├─ 体检
├─ 用药
```

新增后建议：

```text
用户
🏥 医疗档案
├─ 病例
├─ 检查
├─ 体检
├─ 用药

🍎 饮食营养
├─ 总结
├─ 营养
```

### Q：“饮食营养”下第一期应该放哪些内容？

A：按参考图，第一期模块只保留两个：

| 模块 | 作用 | 参考图 |
| --- | --- | --- |
| 总结 | 展示今日营养总览：已食用、剩余、已消耗，以及碳水、蛋白质、脂肪进度 | 图 1 |
| 营养 | 展示早餐、午餐、晚餐、小吃四个餐次；每个餐次展示已摄入/目标、已记录食物、添加入口 | 图 2 |

建议第一期先做最小闭环：

1. `总结`：今日摄入、剩余、消耗、三大营养素进度。
2. `营养`：早餐、午餐、晚餐、小吃四个餐次。
3. 餐次内支持添加食物记录。
4. 支持图片识别和手动录入。
5. 支持把记录发送给 AI 分析。
6. 本人支持写入和读取 Apple 健康营养数据。

饮食计划、营养报告不作为第一期“饮食营养”下的一级模块入口；后续可作为 AI 分析结果、详情页子能力或二期功能再讨论。

### Q：`总结` 模块具体展示什么？

A：`总结` 对齐参考图 1，是用户进入饮食营养后最先看到的今日总览卡片。重点是“今天吃了多少、还剩多少、消耗多少、三大营养素是否达标”。

页面结构建议：

```text
总结                                      详细信息
┌────────────────────────────────────────┐
│                                        │
│  369              1,626             411│
│ 已食用             剩余             已消耗│
│              半圆/圆环进度              │
│                                        │
│ 碳水化合物        蛋白质              脂肪│
│ ━━━━━──          ━───               ━── │
│ 69 / 243克       10 / 97克          9 / 64克│
└────────────────────────────────────────┘
```

字段说明：

| 字段 | 展示 | 说明 |
| --- | --- | --- |
| 标题 | `总结` | 模块标题，左上大字 |
| 右上入口 | `详细信息` | 进入今日/周期营养详情页 |
| 已食用 | `369` | 今日已摄入热量，单位默认 kcal，可在文案中省略单位 |
| 剩余 | `1,626` | 今日剩余热量，作为视觉中心 |
| 已消耗 | `411` | 今日活动/运动消耗 |
| 圆环进度 | 中央半圆或圆环 | 表达已摄入占目标进度，绿色为已摄入，浅灰为剩余 |
| 碳水化合物 | `69 / 243克` | 已摄入 / 目标 |
| 蛋白质 | `10 / 97克` | 已摄入 / 目标 |
| 脂肪 | `9 / 64克` | 已摄入 / 目标 |

交互建议：

1. 点击 `详细信息`：进入营养详情页，展示今日来源、餐次明细、Apple 健康来源、服务端记录来源。
2. 点击 `已食用`：可筛选查看今日摄入记录。
3. 点击 `已消耗`：可查看 Apple 健康消耗来源，例如活动能量、运动记录。
4. 点击三大营养素进度：可查看对应营养素来源和趋势。

设计注意：

1. `剩余` 是视觉中心，字号最大。
2. `已食用` 和 `已消耗` 放在左右两侧，避免抢主视觉。
3. 三大营养素用横向进度条，不使用复杂图表。
4. 单位统一使用 `克`，热量单位在详情或说明中标注为 `千卡/kcal`。
5. 卡片四周保留明显边框或浅灰分隔，和截图一致，整体干净、扫描成本低。

### Q：`营养` 模块具体展示什么？

A：`营养` 对齐参考图 2，是按餐次记录和添加食物的入口。重点是“每餐吃了多少、记录了什么、快速添加”。

页面结构建议：

```text
营养                                           更多
┌────────────────────────────────────────┐
│ ◯ 早餐 →                         +     │
│   369 / 598千卡                         │
│   Scrambled Eggs, Banana, Bana...       │
├────────────────────────────────────────┤
│ ◯ 午餐 →                         +     │
│   0 / 798千卡                           │
├────────────────────────────────────────┤
│ ◯ 晚餐 →                         +     │
│   0 / 499千卡                           │
├────────────────────────────────────────┤
│ ◯ 小吃 →                         +     │
│   0 / 100千卡                           │
└────────────────────────────────────────┘
```

每个餐次行包含：

| 元素 | 展示 | 说明 |
| --- | --- | --- |
| 餐次图标 | 早餐咖啡、午餐餐盘、晚餐沙拉、小吃苹果 | 图标放在圆形进度环中 |
| 餐次名称 | `早餐 →` | 点击餐次名称或整行进入餐次详情 |
| 热量 | `369 / 598千卡` | 当前餐次已摄入 / 餐次目标 |
| 食物摘要 | `Scrambled Eggs, Banana...` | 只展示 1 行，过长截断 |
| 添加按钮 | 黑色圆形 `+` | 直接添加该餐次食物 |
| 右上入口 | `更多` | 进入更多餐次记录、历史记录或完整列表 |

交互建议：

1. 点击餐次行：进入该餐次详情，查看已记录食物、营养明细、图片和来源。
2. 点击 `+`：直接打开添加食物流程，并默认带入该餐次。
3. 点击 `更多`：进入完整饮食记录列表，可切换日期、查看历史餐次。
4. 餐次图标外圈显示该餐次热量进度，已摄入为绿色，未摄入为浅灰。
5. 餐次没有记录时，不显示“已记录食物”占位，只展示热量 `0 / 目标千卡` 和添加按钮。

设计注意：

1. 四个餐次固定顺序：早餐、午餐、晚餐、小吃。
2. 每行高度稳定，避免有食物摘要和无食物摘要时布局跳动太大。
3. `+` 按钮要足够大，作为主要操作入口。
4. 食物摘要可以中英文混排，来源于用户录入、识别结果或食物标准名。
5. `更多` 不进入饮食计划/营养报告，而是进入营养记录的完整列表或历史视图。

## 三、核心功能一：食物记录 / 热量追踪

### Q：记录方式有哪些？

A：建议支持多种记录方式，按优先级分期：

| 记录方式 | 说明 | 第一阶段建议 |
| --- | --- | --- |
| 拍照识别 | 用户拍食物照片，AI/OCR/视觉模型识别食物和份量，生成营养估算 | 建议第一期做 |
| 手动录入食品名称 | 用户输入“鸡蛋、米饭、牛奶”等，系统匹配食物库或 AI 估算 | 建议第一期做 |
| 语音输入 | 用户说“早餐吃了两个鸡蛋一杯牛奶” | 可与手动输入共用识别能力 |
| 快捷复用 | 复用昨天早餐、常吃食物、收藏餐 | 第二阶段 |
| 扫码录入 | 扫包装食品条码 | 后续 |
| 从外卖/小票导入 | OCR 小票或外卖订单 | 后续 |

### Q：拍照识别应该识别什么？

A：

1. 食物名称。
2. 估算份量，例如一碗、100g、一个、250ml。
3. 餐次，例如早餐、午餐、晚餐、小吃。
4. 营养估算：热量、碳水、蛋白质、脂肪。
5. 置信度和不确定项。

需要注意：拍照识别很难准确判断重量，必须允许用户编辑。

### Q：手动录入食品名称怎么做？

A：建议支持两种输入：

```text
简单食品：鸡蛋、米饭、牛奶、苹果
自然语言：早餐吃了两个鸡蛋、一杯牛奶、一片吐司
```

手动录入后，不直接保存。系统应先把用户输入交给 AI 进行整理和结构化识别，由 AI 返回一个可确认的记录草稿：

```text
早餐
- 鸡蛋 2 个
- 牛奶 250 ml
- 吐司 1 片
估算：369 kcal
碳水 69g / 蛋白质 10g / 脂肪 9g
```

用户确认后才正式保存。

推荐流程：

```text
用户输入食品名称或自然语言
  -> AI 整理食物项、份量、餐次、热量和三大营养素
  -> 返回饮食记录草稿
  -> 用户检查、修改份量或删除错误食物
  -> 用户确认
  -> 保存到服务端
  -> 如果成员是本人且用户授权，再同步写入 Apple 健康营养摄入
```

草稿需要支持用户编辑，因为 AI 可能无法准确判断份量、烹饪方式或品牌食品热量。

草稿至少包含：

1. 餐次。
2. 食物名称。
3. 份量和单位。
4. 估算热量。
5. 碳水、蛋白质、脂肪。
6. AI 识别来源文本。
7. 是否需要用户确认的不确定项。

### Q：点击餐次 `+` 后的食物添加页面怎么设计？

A：参考截图，点击早餐/午餐/晚餐/小吃右侧黑色圆形 `+` 后，打开对应餐次的食物添加页面。页面目标是让用户快速找到食物、低成本添加到当前餐次，并在底部统一完成保存。

页面结构：

```text
      0                         早餐

┌────搜索────┐ ┌────相机────┐ ┌────条形码──┐ ┌────输入────┐ ┌更多┐
│    🔍      │ │    📷      │ │    barcode │ │    Tt      │ │ …  │
└────────────┘ └────────────┘ └────────────┘ └────────────┘ └────┘

┌────────────────────────────────────────┐
│ 🔍 您早餐吃了什么？                     │
└────────────────────────────────────────┘

┌────────────── 食物 ˅ ──────────────┐ ┌──── 经常 ˅ ────┐

Coffee                         2千卡      ＋
1杯 (237毫升)
────────────────────────────────────────
Banana                       134千卡      ＋
1整个，普通 (150克)
────────────────────────────────────────
Scrambled Eggs               100千卡      ＋
1个鸡蛋 (47克)
────────────────────────────────────────

┌────────────────────────────────────────┐
│                  完成                  │
└────────────────────────────────────────┘
```

### Q：顶部数字 `0` 表示什么？

A：表示当前本次添加流程中已选择的食物数量，或已添加条目数量。

建议规则：

1. 初始为 `0`。
2. 用户点击食物右侧 `+` 后，数量递增。
3. 如果支持同一食物多次添加，可以显示总份数或总条目数，具体口径需要统一。
4. 数字圆环可用绿色边框，呼应营养进度颜色。

### Q：顶部标题显示什么？

A：显示当前餐次，例如：

```text
早餐 / 午餐 / 晚餐 / 小吃
```

从哪个餐次点 `+` 进入，就默认添加到哪个餐次。用户不需要再选择餐次，降低操作成本。

### Q：快捷操作区包含什么？

A：快捷操作区放在页面顶部，是食物添加的功能入口。

| 操作 | 展示 | 作用 |
| --- | --- | --- |
| 搜索 | 放大镜，默认选中 | 通过食物名称搜索和选择标准食物 |
| 相机 | 相机图标 | 拍照识别食物 |
| 条形码 | 条形码图标 | 扫包装食品条码，后续能力 |
| 输入 | 文本图标，可带“新的”角标 | 自然语言输入，例如“两个鸡蛋一杯牛奶” |
| 更多 | `…` | 收纳低频/拓展功能 |

`更多` 中可收纳：

1. 批量添加。
2. 自定义食物。
3. 自定义菜谱。
4. 导入历史餐单。
5. 复用昨天同餐。
6. 收藏食物。
7. 从 AI 对话生成。

设计原则：高频入口直接露出，低频能力放进 `更多`，避免主界面信息过载。

### Q：搜索栏怎么设计？

A：搜索栏是当前截图中的核心输入入口。

占位文案按餐次动态变化：

```text
早餐：您早餐吃了什么？
午餐：您午餐吃了什么？
晚餐：您晚餐吃了什么？
小吃：您吃了什么小吃？
```

交互建议：

1. 默认选中搜索模式时，搜索栏高亮绿色边框。
2. 输入关键词后实时过滤食物列表。
3. 搜索无结果时，提供“创建自定义食物”或“用 AI 估算”。
4. 搜索结果优先展示常用食物、最近添加、完全匹配项。

### Q：筛选区怎么设计？

A：搜索栏下方放两个下拉筛选：

```text
食物 ˅     经常 ˅
```

建议含义：

| 筛选 | 说明 |
| --- | --- |
| 食物 | 类型筛选，例如食物、菜谱、品牌食品、自定义 |
| 经常 | 排序/来源筛选，例如经常、最近、收藏、推荐 |

第一期可以先展示静态筛选入口，不必做复杂分类，但交互位置先预留。

### Q：食物列表区怎么设计？

A：食物列表是核心内容区。每一条食物都要足够简洁，让用户不需要额外计算就能判断是否添加。

每条食物包含：

| 内容 | 示例 | 说明 |
| --- | --- | --- |
| 食物名称 | `Coffee` / `Banana` / `Scrambled Eggs` | 可中英文，优先展示用户语言；标准食物可保留英文名 |
| 标准份量 | `1杯 (237毫升)` / `1个鸡蛋 (47克)` | 降低用户估算门槛 |
| 热量 | `2千卡` / `134千卡` | 右侧展示，便于快速扫描 |
| 添加按钮 | 绿色描边圆形 `+` | 点击后加入当前餐次 |

设计原则：

1. 信息极简：名称、份量、热量、添加按钮。
2. 份量标准化：让用户知道默认添加的是多少。
3. 列表分隔线清晰，方便快速浏览。
4. 右侧热量和 `+` 按钮对齐，形成稳定扫描线。
5. 食物名称过长时单行截断，份量另起一行。

### Q：点击食物右侧 `+` 后发生什么？

A：

1. 当前食物按标准份量加入本次待保存列表。
2. 左上数量加 1。
3. 底部 `完成` 按钮进入可用状态。
4. 可给 `+` 按钮一个轻量反馈，例如短暂变为勾选或数字。
5. 如果用户需要改份量，可点击食物行进入份量编辑，或点击已添加项进入编辑。

待确认：

1. 同一食物重复点击 `+` 是新增一条，还是增加份数？
2. 是否需要在列表页直接显示已添加数量，例如 `+` 变成 `1`？
3. 是否需要支持左上数量点击查看本次已选清单？

### Q：底部 `完成` 按钮怎么设计？

A：`完成` 固定在底部，不随列表滚动消失。

行为：

1. 未添加任何食物时，按钮可以禁用或低亮。
2. 添加至少一个食物后，按钮可点击。
3. 点击 `完成` 后，保存本次录入数据到当前餐次。
4. 保存成功后返回营养首页或餐次详情。

设计原因：

1. 用户在列表任意位置都能一键完成。
2. 符合移动端拇指操作习惯。
3. 避免用户添加多个食物后还要回到顶部保存。

### Q：这个页面第一期包含哪些能力？

A：建议第一期做：

1. 搜索。
2. 相机。
3. 输入。
4. 更多入口占位。
5. 食物标准列表。
6. 食物右侧 `+` 添加。
7. 底部固定 `完成`。

条形码、批量添加、自定义菜谱、导入历史餐单可以先放在 `更多` 或作为后续能力。

### Q：是否要区分早餐、午餐、晚餐、小吃？

A：需要。餐次是看板和 AI 分析的重要维度。

第一期建议固定四类：

1. 早餐。
2. 午餐。
3. 晚餐。
4. 小吃 / 加餐。

后续可扩展：

1. 夜宵。
2. 运动前/运动后补给。
3. 自定义餐次。

### Q：餐次如何自动判断？

A：可以按时间默认推断，但允许用户修改。

建议默认规则：

| 时间 | 默认餐次 |
| --- | --- |
| 05:00 - 10:30 | 早餐 |
| 10:30 - 14:30 | 午餐 |
| 14:30 - 20:30 | 晚餐 |
| 其他时间 | 小吃 |

注意：不同用户作息不同，后续可支持自定义餐次时间。

## 四、核心功能二：数据存储讨论

### Q：饮食记录应该存在哪里？

A：建议采用“服务端为主、Apple 健康为辅、本地不存饮食业务数据”的策略。

```text
服务端：饮食记录事实源
Apple 健康：本人营养摄入与能量消耗的系统健康库
本地：不新增饮食业务缓存，仅允许项目已有公共请求缓存
```

原因：

1. 服务端需要支持多设备、家庭成员、AI 对话引用、饮食计划和报告。
2. Apple 健康只能代表当前 iPhone 当前用户，不能表达家庭成员完整资料。
3. Apple 健康不适合保存食物照片、餐次、食物明细、AI 识别来源、成员关系。
4. 本地长期存储会导致多设备不一致，第一原则应以服务端为主。

### Q：服务端应该保存哪些饮食数据？

A：建议服务端保存完整饮食记录：

1. 成员 ID。
2. 日期和时间。
3. 餐次：早餐、午餐、晚餐、小吃。
4. 食物项列表。
5. 每个食物的名称、份量、单位、估算营养。
6. 总热量、碳水、蛋白质、脂肪。
7. 图片附件 ID，关联饮食图片。
8. 记录来源：拍照识别、手动录入、AI 对话、Apple 健康导入。
9. AI 识别置信度和用户是否编辑。
10. 是否已写入 Apple 健康。
11. Apple 健康同步状态。

### Q：饮食图片存在哪里？

A：图片应走现有附件/OSS 流程，服务端饮食记录只关联附件 ID。

```text
饮食图片 -> 上传 OSS -> 服务端文件记录 -> 饮食记录关联 file_id
```

不要把图片直接塞进饮食记录 JSON。

### Q：本地要不要存饮食数据？

A：不要。饮食营养业务数据只存在两个地方：

```text
服务端
Apple 健康
```

客户端本地不单独建立饮食记录缓存、不保存最近几天饮食记录、不保存离线 outbox，也不把本地作为任何饮食数据事实源。

允许存在的本地数据只有项目中已经具备的公共请求缓存，例如网络层请求缓存、图片临时缓存、系统级 URL cache 等。这类缓存是通用基础设施，不是饮食营养模块自己的业务存储。

边界：

1. 饮食记录、食物明细、餐次、图片关联、营养汇总：以服务端为主。
2. 本人营养摄入、能量消耗：按 Apple 健康能力读取/写入。
3. 本地不维护饮食记录业务表。
4. 本地不维护饮食记录离线队列。
5. 本地不作为跨设备同步依据。
6. 页面打开需要数据时，优先请求服务端；如命中项目公共请求缓存，可作为网络层优化使用。

因此可以表达为：

```text
饮食营养业务数据 = 服务端 + Apple 健康
本地 = 仅使用项目已有公共请求缓存，不新增饮食业务缓存
```

## 五、Apple 健康数据边界

### Q：哪些内容可以写入 Apple 健康？

A：Apple 健康适合写入营养摄入的数值项，不适合保存完整饮食记录。

第一期建议写入：
| 应用字段 | Apple 健康字段 | 单位 |
| --- | --- | --- |
| 能量 / 热量摄入 | Dietary Energy Consumed | kcal |
| 蛋白质 | Dietary Protein | g |
| 碳水化合物 | Dietary Carbohydrates | g |
| 总脂肪 | Dietary Fat Total | g |

后续可扩展：

1. 膳食纤维。
2. 糖。
3. 钠。
4. 胆固醇。
5. 饮水量。

### Q：哪些内容不能只靠 Apple 健康保存？

A：

1. 食物名称。
2. 食物照片。
3. 餐次。
4. 食物份量和单位。
5. AI 识别过程。
6. 用户编辑记录。
7. 家庭成员归属。
8. 饮食计划和营养报告。

这些必须在服务端保存。

### Q：本人和其他成员怎么区分？

A：这是本需求最重要的边界之一。

| 成员类型 | 服务端保存 | Apple 健康写入 | Apple 健康读取 |
| --- | --- | --- | --- |
| 本人 | 是 | 是 | 是 |
| 家庭成员/他人 | 是 | 否 | 否 |

原因：

1. Apple 健康是当前设备当前用户的健康库。
2. App 不能把妈妈、孩子、伴侣的饮食数据写入本机用户的 Apple 健康。
3. 家庭成员饮食数据只能进入服务端成员档案。

### Q：本人记录时，先写服务端还是先写 Apple 健康？

A：建议业务上以服务端为主，Apple 健康为同步目标。

推荐流程：

```text
用户确认饮食记录
  -> 保存到服务端
  -> 如果成员是本人且用户授权 Apple 健康
       -> 写入 Apple 健康
       -> 回写服务端 sync 状态
```

好处：

1. 即使 Apple 健康授权失败，服务端记录仍存在。
2. 多设备和 AI 对话仍能看到记录。
3. Apple 健康写入状态可以在服务端跟踪。

### Q：如果 Apple 健康写入成功，但服务端保存失败怎么办？

A：正常流程下不存在这种情况。

规则必须固定为：

```text
服务端保存成功
  -> 才允许写入 Apple 健康
```

如果服务端保存失败：

1. 不写入 Apple 健康。
2. 提示用户保存失败。
3. 用户可重试保存。
4. 不进入 Apple 健康同步流程。

因此不会出现“Apple 健康已经写入成功，但服务端没有记录”的数据状态。

### Q：如何读取 Apple 健康中的其它渠道营养摄入？

A：本人看板需要合并：

```text
服务端饮食记录
+ Apple 健康中其它 App / 手动录入的营养摄入
+ Apple 健康中的能量消耗
```

合并时要区分来源：

1. 服务端记录：应用内创建的完整饮食记录。
2. Apple 健康记录：其它渠道或系统健康中已有的营养数据。
3. 应用写入 Apple 健康的记录：应该避免重复计算。

### Q：如何避免服务端记录和 Apple 健康记录重复计算？

A：需要给应用写入 Apple 健康的样本打来源标记或保存映射。

讨论方案：

1. 写入 Apple 健康时，在 metadata 中保存 app record ID。
2. 服务端记录保存 Apple Health sync ID / sync status。
3. 读取 Apple 健康时，识别由本 App 写入的样本，不再作为“外部额外摄入”重复累加。
4. 无法识别来源时，按时间和数值做弱去重，但要谨慎，避免误删其它 App 数据。

第一期建议目标：

```text
本人看板 = 服务端饮食记录 + Apple 健康外部来源营养摄入 + Apple 健康能量消耗
```

其中“外部来源营养摄入”不包含本 App 已同步到 Apple 健康的样本。

### Q：能量消耗从哪里来？

A：能量消耗建议优先读取 Apple 健康。

来源包括：

1. Apple Watch / iPhone 的活动能量。
2. 静息能量。
3. 运动记录。
4. 其它健康 App 写入的能量消耗。

服务端是否保存能量消耗要谨慎：

1. 可以缓存每日汇总，便于 AI 分析和多设备展示。
2. 但原始活动数据仍以 Apple 健康为准。
3. 对非本人成员，如果没有设备数据，只能手动记录或不展示消耗。

## 六、核心功能三：看板

### Q：今日看板展示什么？

A：看板要让用户一眼看到当天饮食情况：

```text
┌──────────────────────────┐
│ 周六                     │
├──────────────────────────┤
│      今日营养总览         │
│                          │
│ 已摄入   剩余   已消耗    │
│ 369     1626    411      │
│                          │
│ 碳水 蛋白质 脂肪          │
│ 69/243                  │
│ 10/97                   │
│ 9/64                    │
└──────────────────────────┘
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| 已摄入 | 当日饮食热量摄入 |
| 剩余 | 今日目标热量 - 已摄入 + 已消耗，可讨论具体公式 |
| 已消耗 | Apple 健康读取的活动/运动消耗，或总消耗的一部分 |
| 碳水 | 已摄入 / 目标 |
| 蛋白质 | 已摄入 / 目标 |
| 脂肪 | 已摄入 / 目标 |

### Q：剩余热量怎么计算？

A：这是需要产品确认的关键问题。

方案 A：简单目标法

```text
剩余 = 今日摄入目标 - 已摄入
```

优点：简单稳定。

缺点：没有体现运动消耗。

方案 B：运动补偿法

```text
剩余 = 今日摄入目标 - 已摄入 + 已消耗
```

优点：运动后剩余额度增加，符合部分用户直觉。

缺点：可能鼓励用户“运动后多吃”，对减脂用户不一定合适。

方案 C：按目标策略配置

```text
减脂：剩余 = 摄入目标 - 已摄入 + 已消耗 * 0.3
维持：剩余 = 摄入目标 - 已摄入 + 已消耗 * 0.5
增肌：剩余 = 摄入目标 - 已摄入 + 已消耗 * 0.7
```

建议：第一期先用方案 A 或 B，并在文案里明确口径。长期建议根据用户目标配置。

### Q：餐次列表怎么展示？

A：按早餐、午餐、晚餐、小吃展示：

```text
┌──────────────────────────┐
│ 早餐      369/598        │
│ 已记录食物               │
│                      +   │
├──────────────────────────┤
│ 午餐      0/798          │
│                      +   │
├──────────────────────────┤
│ 晚餐      0/499          │
│                      +   │
├──────────────────────────┤
│ 小吃      0/100          │
│                      +   │
└──────────────────────────┘
```

每个餐次需要：

1. 当前餐次已摄入热量。
2. 餐次目标热量。
3. 已记录食物摘要。
4. `+` 添加入口。
5. 点击餐次进入详情。

### Q：餐次目标怎么来？

A：可以按全天目标分配。

默认分配建议：

| 餐次 | 占比 |
| --- | --- |
| 早餐 | 30% |
| 午餐 | 40% |
| 晚餐 | 25% |
| 小吃 | 5% |

## 八、AI 对话结合

### Q：AI 对话中如何使用饮食数据？

### Q：AI 可以回答哪些问题？

A：

1. “我今天吃得怎么样？”
2. “最近一周蛋白质够不够？”
3. “我妈妈血糖高，这样吃合适吗？”

### Q：AI 分析需要哪些上下文？

1. 饮食记录。

## 九、饮食计划与营养报告

> 讨论结论：饮食计划、营养报告暂不作为“饮食营养”首页一级模块。当前一级模块只保留 `总结`、`营养`。本节仅保留为后续能力讨论。

### Q：饮食计划是什么？

A：饮食计划是面向未来的建议或安排，例如：

1. 一日三餐计划。
2. 一周减脂餐。
3. 控糖饮食计划。
4. 增肌高蛋白计划。
5. 高血压低盐饮食计划。

第一期可以只作为 AI 生成结果或收藏内容，不必复杂执行。

### Q：营养报告是什么？

A：营养报告是对一段时间饮食数据的总结，例如：

1. 本周摄入趋势。
2. 热量达标率。
3. 蛋白质不足天数。
4. 碳水偏高餐次。
5. 与体重、运动、血糖指标的关系。
6. AI 总结和建议。

报告可以作为 AI 对话的可选上下文。

## 十一、数据冲突与合并

### Q：如果服务端和 Apple 健康数据不一致，以谁为准？

A：建议分场景：

1. 应用内创建的饮食记录：服务端为准。
2. Apple 健康中其它来源营养摄入：作为补充来源。
3. Apple 健康能量消耗：Apple 健康为准。
4. 看板展示：服务端记录 + Apple 健康外部来源汇总。
5. AI 分析：展示数据来源，避免混淆。

### Q：用户删除服务端饮食记录后，要不要删除 Apple 健康数据？

A：需要讨论。

方案 A：同步删除 Apple 健康中由本 App 写入的样本。

优点：数据一致。

缺点：需要保存 HealthKit sample 标识，复杂度更高。

方案 B：只删除服务端记录，不删除 Apple 健康。

优点：简单。

缺点：Apple 健康仍保留摄入，可能看板重复或不一致。

建议：如果第一期支持写入 Apple 健康，最好同时设计删除/撤销策略，否则用户会困惑。

## 十三、第一期建议范围

### Q：第一期做哪些最合适？

A：建议第一期聚焦闭环：

1. 首页新增“饮食营养”入口。
2. 饮食看板展示今日摄入、剩余、消耗、三大营养素。
3. 早餐、午餐、晚餐、小吃四餐次。
4. 支持手动输入和拍照识别生成饮食记录草稿。
5. 服务端保存饮食记录和图片附件。
6. 本人记录支持写入 Apple 健康营养摄入。
7. 本人看板读取 Apple 健康能量消耗。
8. AI 对话可选择饮食记录发送给 AI 分析。

### Q：第一期先不做什么？

A：

1. 不做复杂食物数据库。
2. 不做条码扫描。
3. 不做外卖订单导入。
4. 不做完整一周饮食计划执行系统。
5. 不做撤销 Apple 健康写入的复杂管理，除非决定必须支持删除同步。
6. 不做家庭成员 Apple 健康写入。

## 十四、需要继续确认的问题

1. 今日“剩余”热量是否要把运动消耗加回来？
2. 活动消耗展示“活动能量”还是“总消耗”？是否包含静息能量？
3. 饮食记录删除后，是否同步删除 Apple 健康样本？
4. Apple 健康中其它 App 写入的营养摄入，是否展示明细，还是只展示汇总？
5. 服务端是否需要保存每日 Apple 健康汇总快照，便于 AI 跨设备分析？
6. 家庭成员是否需要手动记录能量消耗？
7. 食物识别失败时，是否允许直接保存图片并稍后补录？
8. 慢病饮食建议是否需要强制医疗风险提示？
9. 用户是否需要设置目标，还是先用默认目标？
10. 饮食计划和营养报告已确认不作为第一期一级入口；后续需要确认它们是放在 AI 分析结果、详情页，还是第二期独立入口。

## 十五、阶段结论

本功能值得做，但第一期要控制范围。最关键的不是“食物数据库做多全”，而是先打通：

```text
记录饮食
  -> 服务端保存
  -> 本人同步 Apple 健康营养摄入
  -> 读取 Apple 健康消耗和外部营养数据
  -> 看板展示
  -> 发送给 AI 分析
```

数据原则建议定为：

```text
服务端为主：饮食记录、食物明细、图片、成员归属、计划、报告
Apple 健康为辅：本人营养摄入写入、本人能量消耗和外部营养数据读取
本地不存饮食业务数据：只允许使用项目已有公共请求缓存
```

本人和家庭成员必须严格区分：

```text
本人：服务端 + Apple 健康
其他成员：仅服务端
```
