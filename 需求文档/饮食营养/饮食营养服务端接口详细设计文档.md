# 饮食营养服务端接口详细设计文档

> 文档性质：服务端接口详细设计稿。本文基于《饮食营养客户端详细设计文档》和《饮食营养数据详设文档》，按客户端页面和业务流程反推服务端接口、请求参数、响应 DTO、处理规则和数据来源。本文不涉及代码改动。

## 一、接口设计范围

### Q：第一期服务端接口需要覆盖哪些客户端流程？

A：第一期接口围绕“饮食营养首页 -> 添加食物/识别/搜索 -> 确认保存 -> Apple 健康同步 -> 详情查看”闭环设计。

| 客户端页面/流程 | 需要的服务端能力 |
| --- | --- |
| 饮食营养首页 | 查询当天看板、餐次聚合、目标值 |
| 总结详细页面 | 查询全天营养摄入、餐次摄入、营养明细 |
| 营养详细页面 | 查询当天各餐次食物列表和餐次合计 |
| 餐次详情页 | 查询某餐次记录、食物列表、图片、营养聚合 |
| 食物添加页 | 查询推荐/常用食物，保存选择结果 |
| 食物搜索页 | 文本搜索、收藏筛选、由我创建筛选 |
| 条形码扫描页 | 扫码后用条码搜索食物 |
| 拍照识别页 | 客户端 AI Runtime 识别，生成确认前草稿；服务端不提供识别接口 |
| 自然语言输入页 | 客户端 AI Runtime 结构化用户输入，生成确认前草稿；服务端不提供识别接口 |
| 食物/菜谱确认页 | 创建正式饮食记录 |
| 自定义食物 | 创建食物定义和标准营养 |
| 自定义菜谱 | 创建菜谱、组成食物和标准营养 |
| 能量消耗页面 | 查询/创建/编辑/删除能量消耗记录 |
| Apple 健康同步 | 外部营养摄入上报、能量消耗同步、回写 HealthKit sample UUID |

## 二、通用约定

### 2.1 路径前缀

```http
/api/v1/nutrition/
```

### 2.2 统一响应

沿用项目现有接口风格：

```json
{
  "code": 0,
  "msg": "success",
  "data": {}
}
```

### 2.3 编码规范

1. 客户端必须使用项目统一 `JSONEncoder.default` / `JSONDecoder.default`，实现位置参考 `SparkClient/Projects/Foundation/Extensions/Codable+Extensions.swift`。
2. Swift DTO 字段使用驼峰命名，网络 JSON 字段使用 snake_case，由统一编码器/解码器自动转换。
3. 日期统一使用 ISO8601，由统一编码器/解码器处理。
4. 客户端不要手写 `CodingKeys` / `CodableKey`，不要为了对齐 snake_case 在 DTO 内手动声明字段映射。
5. 服务端接口字段必须保持 snake_case，避免出现同一响应里 camelCase 与 snake_case 混用。
6. 若确实出现无法由 `convertFromSnakeCase` 自动还原的缩写字段，需要优先调整字段命名；只有跨系统不可控字段才允许单独评审例外。

示例：

| 服务端 JSON 字段 | Swift DTO 字段 |
| --- | --- |
| `member_id` | `memberId` |
| `meal_type` | `mealType` |
| `energy_kcal` | `energyKcal` |
| `apple_health_id` | `appleHealthId` |
| `created_at` | `createdAt` |

### 2.4 本地化与日志约定

客户端展示文案不由服务端直接控制。服务端返回结构化状态、错误码和数据字段，客户端用本地化 key 转换成用户可见文案。

接口实现需要支持客户端核心日志追踪：

1. 所有接口响应保留请求链路中的 request id。
2. 保存类接口返回正式资源 ID，便于客户端记录“保存成功 -> HealthKit 写入 -> 回写 UUID”的完整链路。
3. AI 识别只在客户端 AI Runtime 内完成；确认保存时客户端可在 `POST /meal-records/` 中带回 `recognition_id`，便于服务端串联识别草稿与正式记录。
4. 搜索、识别、保存、Apple 健康回写接口需要在服务端记录业务日志，但不得记录完整图片、完整自然语言原文和完整敏感健康明细。
5. 错误响应使用稳定错误码，客户端根据错误码展示本地化文案。

### 2.5 权限边界

| 参数 | 说明 |
| --- | --- |
| `member_id` | 饮食营养数据归属成员 ID |
| 登录用户 | 从 JWT 获取，不由客户端传 |
| 本人成员 | 允许客户端读写 Apple 健康 |
| 非本人成员 | 只允许服务端记录，不读写 Apple 健康 |

服务端所有接口必须校验当前用户对 `member_id` 的访问权限。

## 四、看板接口

### NUTRITION-API-001 查询饮食营养首页看板

用于页面：

1. 饮食营养首页。
2. 总结模块。
3. 营养模块。
4. 总结详细页面的基础数据。

```http
GET /api/v1/nutrition/dashboard/?member_id=100&date=2026-06-01
```

请求参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `member_id` | Int | 是 | 成员 ID |
| `date` | String | 是 | 本地日期，格式 `yyyy-MM-dd` |

响应：

```json
{
  "member_id": 100,
  "date": "2026-06-01",
  "goal": {
    "energy_kcal": 1995,
    "protein_g": 97,
    "carbohydrate_g": 243,
    "fat_g": 64
  },
  "server_intake": {
    "energy_kcal": 369,
    "protein_g": 10,
    "carbohydrate_g": 69,
    "fat_g": 9
  },
  "apple_health_external_intake": {
    "energy_kcal": 0,
    "protein_g": 0,
    "carbohydrate_g": 0,
    "fat_g": 0
  },
  "apple_health_burned": {
    "energy_kcal": 411,
    "source": "client_healthkit"
  },
  "meals": [
    {
      "meal_type": "breakfast",
      "energy_kcal": 369,
      "target_energy_kcal": 598,
      "protein_g": 10,
      "target_protein_g": 29,
      "carbohydrate_g": 69,
      "target_carbohydrate_g": 73,
      "fat_g": 9,
      "target_fat_g": 19,
      "food_summary": "Scrambled Eggs, Banana",
      "record_count": 1
    }
  ]
}
```

服务端处理：

1. 校验用户是否可查看 `member_id`。
2. 读取 `NutritionGoal`，没有则返回默认目标。
3. 聚合 `NutritionIntake(business_type=nutrition_meal_record)` 得到 `server_intake`。
4. 聚合 `NutritionAppleHealthIntakeImport` 关联的 `NutritionIntake` 得到 `apple_health_external_intake`。
5. 聚合 `NutritionEnergyBurnRecord` 得到服务端已知消耗。
6. `remaining_energy_kcal` 不由服务端返回，客户端结合 Apple 健康消耗计算。
7. `meals` 必须返回四类营养和目标值，支撑客户端膳食卡片。

客户端展示对应：

| 响应字段 | 客户端展示 |
| --- | --- |
| `server_intake + apple_health_external_intake` | 总结卡片“已食用” |
| `goal` | 总结卡片“剩余”、营养素目标 |
| `apple_health_burned` | 总结卡片“已消耗”的服务端部分 |
| `meals` | 营养模块四个餐次行 |

### NUTRITION-API-003 创建饮食记录

用于页面：

1. 食物/菜谱确认页。
2. 拍照识别成功页“确认并记录”。
3. 自然语言输入确认。
4. 标准食物选择后保存。

```http
POST /api/v1/nutrition/meal-records/
```

请求：

```json
{
  "member_id": 100,
  "meal_type": "breakfast",
  "consumed_at": "2026-06-01T08:10:00+08:00",
  "source": "photo_ai",
  "source_text": "高蛋白鳕鱼卷",
  "recognition_id": "tmp_20260609_0001",
  "file_ids": [123],
  "meal_foods": [
    {
      "food_item_id": 3001,
      "serving_ratio": 1,
      "serving_quantity": 1,
      "serving_unit": "serving",
      "serving_description": "1份"
    }
  ],
  "recipes": [],
  "manual_intakes": []
}
```

响应：返回完整 `RemoteMealRecord`。

服务端处理：

1. 确认前草稿不落正式表；只有该接口成功才创建正式饮食记录。
2. 创建 `NutritionMealRecord`。
3. 创建 `NutritionMealFood`。
4. 如果选择菜谱，展开 `NutritionRecipeFood` 后创建多条 `NutritionMealFood`。
5. 根据食物/菜谱标准营养和食用比例生成 `NutritionIntake`。
6. 如果有 `manual_intakes`，直接生成餐次实际摄入。
7. 关联图片附件。
8. 返回创建后的完整记录。

### NUTRITION-API-004 编辑饮食记录

```http
PATCH /api/v1/nutrition/meal-records/{id}/
```

说明：

1. 可编辑餐次、标题、食物、份量、比例、图片。
2. 服务端重新计算该记录下的 `NutritionIntake`。
3. 已写入 Apple 健康的记录，第一期只更新服务端数据；客户端需提示用户后续 Apple 健康处理策略待补充。

### NUTRITION-API-005 删除饮食记录

```http
DELETE /api/v1/nutrition/meal-records/{id}/
```

说明：

1. 软删除 `NutritionMealRecord`。
2. 关联 `NutritionMealFood` / `NutritionIntake` 不物理删除，可通过记录软删除排除统计。
3. 已写入 Apple 健康的样本删除策略第一期待补充。

## 六、搜索与收藏接口

### NUTRITION-API-006 搜索食物/菜谱

用于页面：

1. 食物搜索页。
2. 条形码扫描成功后的结果页。
3. 空结果页。

```http
GET /api/v1/nutrition/search/?member_id=100&mode=text&q=汉堡&type=food&favorite=false&created_by_me=false
GET /api/v1/nutrition/search/?member_id=100&mode=barcode&q=6926104997449
```

请求参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `member_id` | Int | 是 | 当前选择成员 |
| `mode` | String | 是 | `text/barcode` |
| `q` | String | 是 | 文本关键词或条形码数字 |
| `type` | String | 否 | `food/recipe/all` |
| `favorite` | Bool | 否 | 只查收藏 |
| `created_by_me` | Bool | 否 | 只查用户创建 |

响应：

```json
{
  "mode": "barcode",
  "query": "6926104997449",
  "items": [
    {
      "id": "food_3001",
      "result_type": "food_item",
      "food_item": {
        "id": 3001,
        "name": "鳕鱼",
        "localized_name": "鳕鱼",
        "brand_name": "可口可乐中国",
        "barcode": "6926104997449",
        "serving_description": "1毫升",
        "is_verified": true
      },
      "recipe": null,
      "is_favorite": true,
      "is_created_by_me": false,
      "overview": {
        "energy_kcal": 10,
        "protein_g": 0,
        "carbohydrate_g": 0,
        "fat_g": 0
      },
      "score": 0.98
    }
  ]
}
```

服务端处理：

1. `mode=text`：按 `name/localized_name/brand_name` 搜索食物和菜谱。
2. `mode=barcode`：优先按 `NutritionFoodItem.barcode` 精确匹配。
3. `favorite=true`：根据 `NutritionFoodFavorite` 过滤。
4. `created_by_me=true`：按 `NutritionFoodItem.user` 或 `NutritionRecipe.user` 过滤。
5. 搜索结果必须带 `overview`，用于搜索卡片展示热量和三大营养素。
6. 没有结果时返回 `items=[]`，客户端展示空状态。

### NUTRITION-API-007 收藏/取消收藏

收藏：

```http
POST /api/v1/nutrition/favorites/
```

```json
{
  "target_type": "nutrition_food_item",
  "target_id": 3001
}
```

取消收藏：

```http
DELETE /api/v1/nutrition/favorites/?target_type=nutrition_food_item&target_id=3001
```

说明：

1. 收藏是账号维度偏好，不绑定 `member_id`。
2. 取消收藏建议软删除 `NutritionFoodFavorite`。
3. 搜索接口返回 `is_favorite`。

## 七、AI 配置约定

### 7.1 场景配置

饮食营养识别完全由客户端 AI Runtime 编排。服务端 nutrition 模块不提供 `POST /recognitions/photo/`、`POST /recognitions/text/` 识别代理或兜底接口，只负责：

1. 通过 `ai_config` 管理客户端可用的模型场景配置。
2. 保存客户端确认后的正式饮食记录。
3. 在正式记录中接收可选 `recognition_id`，用于日志串联。

需要新增场景：

| 场景 | rawValue | 用途 | 模型要求 |
| --- | --- | --- | --- |
| 营养摄入抽取 | `nutrition_intake_extraction` | 将食物描述文本或自然语言输入抽取为营养摄入草稿 JSON | 文本结构化模型 |

说明：食物图片描述不新增独立场景，复用现有 `optimization_visual` 视觉内容优化场景。

服务端改动：

1. `SparkService/ai_config/models.py` 的 `ScenarioKey` 只新增 `nutrition_intake_extraction`。
2. 后台模型配置需要确认已有 `optimization_visual` 绑定可用视觉模型，用于食物图片描述。
3. 后台模型配置支持给 `nutrition_intake_extraction` 绑定结构化文本模型。
4. 场景 key 必须与客户端 `AIScenario` rawValue 完全一致。
5. 服务端不要在 nutrition 模块内写死具体模型名，由 ai_config 统一管理。

客户端改动：

1. `SparkClient/Projects/Core/AI/AIScenario.swift` 只新增 `nutritionIntakeExtraction = "nutrition_intake_extraction"`。
2. `AIScenario.localizedTitle` 增加营养摄入抽取本地化标题。
3. 客户端通过现有 AI 配置中心解析场景可用模型。
4. 未配置视觉模型时，拍照识别返回模型不可用状态；不要降级到普通文本模型。

### 7.2 识别职责边界

拍照识别只在客户端执行：

```text
拍照/相册图片
-> 客户端使用 optimization_visual 生成食物描述文本
-> 客户端使用 nutrition_intake_extraction 生成结构化草稿
-> 用户确认
-> POST /meal-records/ 保存正式记录
```

自然语言输入只在客户端执行：

```text
用户输入文本
-> 客户端使用 nutrition_intake_extraction 生成结构化草稿
-> 用户确认
-> POST /meal-records/ 保存正式记录
```

识别失败、重试、JSON 修正重试均由客户端处理。服务端只在 `POST /meal-records/` 成功后保存正式数据，不接收识别图片描述接口，也不接收自然语言识别接口。

## 十二、错误码建议

| code | msg | 场景 | 客户端表现 |
| --- | --- | --- | --- |
| `0` | `success` | 成功 | 正常展示 |
| `40002` | `invalid_barcode` | 条形码格式不合法 | 回到扫码页提示 |
| `40003` | `nutrition_target_missing` | 目标配置缺失 | 使用默认目标 |
| `40301` | `member_permission_denied` | 无成员权限 | Toast + 返回 |
| `40401` | `nutrition_record_not_found` | 记录不存在或已删除 | 不可用态 |
| `40901` | `duplicate_apple_health_sample` | Apple 健康样本重复 | 幂等成功处理 |

## 十三、实现注意点

1. 搜索和条形码扫描只返回选择项；拍照识别、自然语言输入由客户端本地 AI Pipeline 生成草稿，确认前不创建正式饮食记录。
2. 正式饮食记录只由 `POST /meal-records/` 创建。
3. 服务端是主数据源，客户端不建饮食业务本地库。
4. Apple 健康写入发生在服务端保存成功之后。
5. `NutritionCardContainer` 是纯 UI 容器，不需要任何接口字段。
6. `NutritionMacroRatioBarChartCard` 使用客户端根据 `server_intake / goal` 计算出的百分比展示，不需要服务端单独返回柱状图数据。
7. 看板和餐次详情都可以先由服务端返回基础记录与 `intakes`，客户端聚合；如果后续性能不足，再增加服务端聚合字段。
