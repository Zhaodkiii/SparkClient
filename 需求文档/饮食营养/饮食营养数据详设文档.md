## 一、设计结论

### Q：饮食营养数据的事实源是什么？

A：饮食营养业务数据只存在两个事实源：

```text
服务端：饮食记录、营养摄入、Apple 健康外部营养导入、能量消耗记录、食物定义、菜谱/组合食物、餐次食物关联、图片关联、成员归属、AI 识别结果、Apple 健康写入标识
Apple 健康：本人营养摄入、本人能量消耗、其它 App 写入的营养数据
```

客户端本地不新增饮食业务缓存，不建饮食记录本地表，不维护离线 outbox。客户端只允许使用项目已有公共请求缓存，例如网络层缓存、图片临时缓存、系统 URL cache。

### Q：为什么服务端是主数据源？

A：

1. 饮食记录要绑定家庭成员，Apple 健康只能代表当前设备本人。
2. 饮食记录包含食物名称、餐次、照片、份量、AI 识别来源，这些 Apple 健康无法完整表达。
3. AI 对话需要按成员读取饮食记录，服务端才能提供稳定上下文。
4. 多设备和分享照护场景必须依赖服务端。

### Q：Apple 健康承担什么角色？

A：

1. 本人饮食记录保存到服务端后，可同步写入 Apple 健康营养摄入。
2. 本人看板可读取 Apple 健康能量消耗。
3. 本人看板可读取 Apple 健康中其它 App 写入的营养摄入，作为服务端饮食记录之外的补充来源。
4. 家庭成员/他人不写入、不读取 Apple 健康。

## 二、服务端模块建议

### Q：服务端应该放在哪个 App？

A：建议新增 Django app：

```text
nutrition
```

原因：

1. 饮食营养不是传统医疗病历，不建议塞进 `medical` app。
2. 它需要关联 `medical.Member`，但生命周期、页面和统计逻辑独立。
3. 后续会扩展食物库、菜谱、营养报告、目标配置，独立 app 更清晰。

如果第一期为了减少 app 数量，也可以放在 `medical` 下，但长期会让 `medical.models.py` 继续膨胀，不推荐。

### Q：服务端模型应该继承什么基类？

A：建议复用医疗域已有抽象思路，饮食记录也需要：

1. `user`：当前登录账号。
2. `member`：饮食归属成员。
3. `is_deleted/deleted_at`：软删除。
4. `created_at/updated_at`：同步和排序。

可以新建：

```python
class NutritionBaseModel(models.Model):
    user = models.ForeignKey(User, related_name="%(class)s_records", on_delete=models.CASCADE, db_index=True, db_comment="当前登录账号 ID，用于权限边界、数据归属和跨成员查询隔离")
    member = models.ForeignKey("medical.Member", related_name="%(class)s_records", on_delete=models.CASCADE, db_index=True, db_comment="饮食营养数据归属成员 ID，与账号用户不同，用于家庭成员饮食记录归属")
    is_deleted = models.BooleanField(default=False, db_index=True, db_comment="软删除标记；true 表示业务已删除但数据库保留记录，用于审计和同步删除 Apple 健康样本")
    deleted_at = models.DateTimeField(null=True, blank=True, db_comment="软删除时间；未删除时为空")
    created_at = models.DateTimeField(auto_now_add=True, db_index=True, db_comment="记录创建时间")
    updated_at = models.DateTimeField(auto_now=True, db_index=True, db_comment="记录最后更新时间，用于增量同步、列表排序和缓存失效判断")
```

也可以抽取公共软删除基类，但第一期不建议大范围重构现有 `MedicalBaseModel`。

### Q：服务端字段是否需要写数据库注释？

A：需要。饮食营养数据会长期演进，建议模型字段统一补充 `db_comment`。

1. 后端、管理后台、数据分析、排障都会直接看数据库结构，字段注释能降低理解成本。
2. 饮食营养字段中有大量业务近义词，例如 `consumed_at`、`local_day`、`source_text`、`apple_health_id`，没有注释容易被误用。
3. Apple 健康同步字段具有状态机含义，必须在数据库层明确说明。
4. 第一阶段是全新表结构，补充 `db_comment` 成本低，后续补会产生迁移噪音。

约定：

1. 所有新增服务端模型字段必须写 `db_comment`。
2. `db_comment` 用中文描述业务含义，不写 UI 展示文案。
3. 状态枚举字段需要说明状态用途，具体枚举值在 `TextChoices` 中维护。
4. JSON 字段必须说明承载边界，避免成为无约束垃圾桶。

## 三、服务端数据模型

### 3.1 NutritionMealRecord：饮食记录主表

### Q：饮食记录主表负责什么？

A：记录一次餐次内的一组食物，是“早餐/午餐/晚餐/小吃”的聚合根。

建议模型：

```python
class NutritionMealRecord(NutritionBaseModel):
    class MealType(models.TextChoices):
        BREAKFAST = "breakfast", "breakfast"
        LUNCH = "lunch", "lunch"
        DINNER = "dinner", "dinner"
        SNACK = "snack", "snack"

    class Source(models.TextChoices):
        MANUAL = "manual", "manual"
        PHOTO_AI = "photo_ai", "photo_ai"
        TEXT_AI = "text_ai", "text_ai"
        CHAT_AI = "chat_ai", "chat_ai"
        APPLE_HEALTH_IMPORT = "apple_health_import", "apple_health_import"

    meal_type = models.CharField(max_length=16, choices=MealType.choices, db_index=True, db_comment="餐次类型：早餐、午餐、晚餐、小吃；用于营养页四段餐次展示和按餐次查询")
    consumed_at = models.DateTimeField(db_index=True, db_comment="实际食用时间；由用户选择或创建记录时生成，用于时间线排序")
    local_day = models.DateField(db_index=True, db_comment="用户本地日期；用于日看板、餐次列表和按天聚合，避免每次按时区动态换算")
    title = models.CharField(max_length=128, blank=True, default="", db_comment="饮食记录标题；可为空，例如早餐、肯德基午餐、AI 识别晚餐")
    source = models.CharField(max_length=32, choices=Source.choices, default=Source.MANUAL, db_index=True, db_comment="记录来源：手动、拍照 AI、文本 AI、对话 AI、Apple 健康导入等")
    source_text = models.TextField(blank=True, default="", db_comment="AI 整理时的用户原始输入文本或识别来源摘要；非 AI 来源可为空")

    is_ai_estimated = models.BooleanField(default=False, db_index=True, db_comment="是否包含 AI 估算结果；true 表示至少存在拍照识别、文本识别或对话生成的估算数据")
    ai_confidence = models.DecimalField(max_digits=5, decimal_places=4, null=True, blank=True, db_comment="AI 对本餐识别或整理结果的整体置信度，范围 0 到 1；非 AI 来源为空")
    user_edited = models.BooleanField(default=False, db_index=True, db_comment="用户是否编辑过 AI 草稿或系统推荐值；用于后续质量评估和避免覆盖用户修正")

    extra = models.JSONField(default=dict, blank=True, db_comment="扩展字段；仅承载一期未结构化但需要保留的信息，例如微量营养素、AI 原始结构化片段、实验字段")
```

### 字段说明

| 字段 | 说明 |
| --- | --- |
| `user` | 当前账号，用于权限和查询边界 |
| `member` | 饮食记录归属成员 |
| `meal_type` | 早餐/午餐/晚餐/小吃 |
| `consumed_at` | 实际食用时间 |
| `local_day` | 用户本地日期，用于看板和日汇总 |
| `title` | 可选标题，例如“早餐”“肯德基午餐” |
| `source` | 记录来源 |
| `source_text` | AI 整理来源文本 |
| `is_ai_estimated` | 是否包含 AI 估算 |
| `ai_confidence` | AI 识别置信度，0~1 |
| `user_edited` | 用户是否编辑过 AI 草稿 |
| `extra` | 扩展字段，承接后续纤维、糖、钠等 |

### 索引建议

```python
indexes = [
    models.Index(fields=["user", "member", "local_day", "meal_type"]),
    models.Index(fields=["user", "member", "consumed_at"]),
    models.Index(fields=["member", "local_day"]),
]
```

### 设计要点

1. `local_day` 必须存，不要每次用 `consumed_at` 动态按时区换算，否则日看板和查询会复杂。
2. `NutritionMealRecord` 只保存记录基础信息，不直接承载营养摄入明细或复杂同步状态。
3. `NutritionMealRecord` 不保存 `apple_health_id`；Apple 健康写入标识属于具体营养摄入，放在 `NutritionIntake`。
4. `NutritionMealRecord` 不直接增加 `food_item_id`、`serving_ratio` 等食物字段；食物关联统一放在 `NutritionMealFood`。
5. 删除饮食记录必须软删除，方便审计和后续处理 Apple 健康侧已写入数据。

### Q：是否可以直接在 `NutritionMealRecord` 增加食物关联 ID 和食用比例？

A：不建议。最终设计保留 `NutritionMealFood`，不把食物 ID 和食用比例放到 `NutritionMealRecord`。

原因：

1. 一条饮食记录表示一次餐次，天然可能包含多个食物，例如早餐同时有鸡蛋、牛奶、吐司。
2. 如果把 `food_item_id` 放到 `NutritionMealRecord`，主表只能自然表达一个食物；后续支持多个食物时还要再拆表迁移。
3. 食用比例是“某个食物在本次餐次里的食用比例”，它属于食物关联关系，不属于餐次主记录。
4. AI 拍照识别和自然语言整理经常一次返回多个食物，需要一条餐次记录关联多条食物。
5. 用户后续编辑餐次时，可能只修改某个食物的比例或删除某个食物，独立关联表更清楚。

因此：

```text
NutritionMealRecord = 餐次基础记录
NutritionMealFood = 本餐吃了哪些食物，以及每个食物吃了多少
NutritionIntake = 根据食物标准营养 * 食用比例生成的实际摄入
```

单食物场景也走 `NutritionMealFood`，不要为了单食物做主表快捷字段。

## 四、服务端营养摄入模型

### 4.1 NutritionIntake：营养摄入明细

### Q：为什么营养摄入要单独建表？

A：饮食记录是“这顿饭发生了什么”，营养摄入是“这顿饭摄入了哪些营养值”。两者职责不同，应该拆开：

1. `NutritionMealRecord` 只保存基础记录信息，避免主表越来越胖。
2. 营养字段会持续扩展，第一期是热量、蛋白质、碳水、脂肪，后续会有糖、钠、膳食纤维、胆固醇、维生素等。
3. Apple 健康、食物库、AI 估算都围绕营养摄入值，不应该反向污染记录主表。
4. 看板统计可以按 `NutritionIntake` 聚合，字段扩展更自然。

建议模型：

```python
class NutritionIntake(models.Model):
    class NutrientType(models.TextChoices):
        ENERGY = "energy_kcal", "energy_kcal"
        PROTEIN = "protein_g", "protein_g"
        CARBOHYDRATE = "carbohydrate_g", "carbohydrate_g"
        FAT = "fat_g", "fat_g"

    business_type = models.CharField(max_length=64, db_index=True, db_comment="营养归属业务类型，例如 nutrition_meal_record、nutrition_food_item")
    business_id = models.BigIntegerField(db_index=True, db_comment="营养归属业务 ID，与 business_type 一起定位所属对象")
    nutrient_type = models.CharField(max_length=32, choices=NutrientType.choices, db_index=True, db_comment="营养类型，例如热量、蛋白质、碳水化合物、脂肪")
    value = models.DecimalField(max_digits=10, decimal_places=2, db_comment="营养摄入数值；按当前饮食记录整体计算后的值")
    unit = models.CharField(max_length=16, db_comment="营养单位，例如 kcal、g、mg")
    source = models.CharField(max_length=32, blank=True, default="", db_comment="摄入值来源，例如 food_item、manual、photo_ai、text_ai、chat_ai、system")
    confidence = models.DecimalField(max_digits=5, decimal_places=4, null=True, blank=True, db_comment="AI 估算该营养值的置信度，范围 0 到 1；非 AI 来源为空")
    apple_health_id = models.CharField(max_length=128, blank=True, default="", db_index=True, db_comment="Apple 健康写入标识；该营养摄入成功写入 Apple 健康后登记，未写入时为空")
    extra = models.JSONField(default=dict, blank=True, db_comment="营养摄入扩展字段；仅保存暂未结构化但需要保留的信息")
    created_at = models.DateTimeField(auto_now_add=True, db_index=True, db_comment="营养摄入记录创建时间")
    updated_at = models.DateTimeField(auto_now=True, db_index=True, db_comment="营养摄入记录最后更新时间")
```

### 字段说明

| 字段 | 说明 |
| --- | --- |
| `business_type` | 营养归属业务类型，例如 `nutrition_meal_record`、`nutrition_food_item` |
| `business_id` | 营养归属业务 ID，与 `business_type` 一起定位所属对象 |
| `nutrient_type` | 营养类型，例如热量、蛋白质、碳水、脂肪 |
| `value` | 摄入数值 |
| `unit` | 单位，例如 `kcal`、`g`、`mg` |
| `source` | 摄入值来源 |
| `confidence` | AI 估算置信度 |
| `apple_health_id` | Apple 健康写入标识；已写入时登记，未写入时为空 |
| `extra` | 扩展字段 |

### 索引建议

```python
indexes = [
    models.Index(fields=["business_type", "business_id", "nutrient_type"]),
    models.Index(fields=["apple_health_id"]),
]
```

### 设计要点

1. 第一阶段至少写入 `energy_kcal`、`protein_g`、`carbohydrate_g`、`fat_g` 四类。
2. 看板总摄入从 `NutritionIntake` 聚合，不再从 `NutritionMealRecord` 主表读取营养汇总。
3. 同一个 `business_type + business_id` 下同一种 `nutrient_type` 建议保持唯一，避免重复统计。
4. `NutritionIntake` 是公用营养表：`business_type=nutrition_food_item` 表示食物标准营养，`business_type=nutrition_recipe` 表示菜谱标准营养，`business_type=nutrition_meal_record` 表示餐次实际摄入，`business_type=nutrition_apple_health_intake_import` 表示 Apple 健康外部来源营养摄入。
5. 使用 `business_type/business_id` 后，后续可以自然扩展到菜谱、饮食计划、营养报告等对象。
6. 保存饮食记录时，如果用户选择已有食物，服务端按食用比例读取该食物的 `NutritionIntake`，生成新的餐次 `NutritionIntake(business_type=nutrition_meal_record, business_id=meal_record.id)`。
7. `apple_health_id` 放在餐次实际摄入对应的 `NutritionIntake`，因为 Apple 健康写入的是具体营养摄入样本，不是餐次记录本身。

## 五、服务端食物模型

### 5.1 NutritionFoodItem：食物定义

### Q：`NutritionFoodItem` 应该表示什么？

A：`NutritionFoodItem` 应该表示“可被用户选择或自定义的食物”，不是某一顿饭里的临时明细。

原因：

1. 用户需要自己添加食物，例如自制鸡胸肉饭、固定早餐、某品牌酸奶。
2. 添加页面需要标准食物、常用食物和用户自定义食物统一搜索。
3. 食物本身应该有标准份量和标准营养值，后续可被多次复用。
4. 一顿饭吃了某个食物的多少比例，应该由餐次关联表表达，而不是复制一份食物定义。

建议模型：

```python
class NutritionFoodItem(models.Model):
    user = models.ForeignKey(User, related_name="nutrition_food_items", on_delete=models.CASCADE, null=True, blank=True, db_index=True, db_comment="创建该食物的账号 ID；系统预置食物为空，用户自定义食物填写")
    name = models.CharField(max_length=128, db_comment="食物标准名称，优先保存食物库标准名或 AI 归一化后的名称，例如 Coffee")
    localized_name = models.CharField(max_length=128, blank=True, default="", db_comment="食物本地化名称，例如咖啡；用于中文界面展示和搜索")
    brand_name = models.CharField(max_length=128, blank=True, default="", db_comment="品牌名称；普通食物可为空，包装食品或连锁餐品可填写")
```

### 设计要点

1. 用户可以自己创建 `NutritionFoodItem`。
2. 系统预置食物和用户自定义食物共用一张表，通过 `user` 是否为空区分。
3. 食物标准营养值不直接放在 `NutritionFoodItem` 字段内，而是使用 `NutritionIntake(business_type=nutrition_food_item, business_id=food.id)` 保存。
4. `serving_description` 保存展示文案，避免客户端每次拼接单位。
5. 食物被餐次使用时，不修改食物本身，而是通过 `NutritionMealFood` 建立本次食用关系。
6. `barcode` 只解决第一期“一码一食物”的快速匹配；如果后续需要同一食物多个包装条码或多地区条码映射，再扩展独立条码映射表。

### 5.1.1 NutritionFoodFavorite：食物/菜谱收藏关系

建议模型：

```python
class NutritionFoodFavorite(models.Model):

    is_deleted = models.BooleanField(default=False, db_index=True, db_comment="软删除标记；取消收藏时置为 true，避免重复创建历史脏数据")

    updated_at = models.DateTimeField(auto_now=True, db_index=True, db_comment="收藏最后更新时间")
```

索引建议：

```python
indexes = [
    models.Index(fields=["user", "target_type", "target_id"]),
]
```

设计要点：

1. 搜索页 `收藏` 筛选查询该表。
2. 搜索结果 DTO 可以返回 `is_favorite`，用于卡片显示。
3. `由我创建` 筛选不需要单独表，通过 `NutritionFoodItem.user = current_user` 或 `NutritionRecipe.user = current_user` 判断。

### 5.2 NutritionMealFood：餐次食物关联

### Q：饮食记录如何关联食物？

A：新增餐次食物关联表。它表示“某顿饭吃了某个食物，以及吃了多少”。

该表需要保留，不建议合并到 `NutritionMealRecord`。

设计边界：

1. 一条 `NutritionMealRecord` 可以有 0 条、1 条或多条 `NutritionMealFood`。
2. 纯手动营养录入可以没有 `NutritionMealFood`，只生成 `NutritionIntake`。
3. 选择已有食物时必须生成 `NutritionMealFood`。
4. 每条 `NutritionMealFood` 独立保存本次食用比例和份量。

建议模型：

```python
class NutritionMealFood(models.Model):
    meal_record = models.ForeignKey(NutritionMealRecord, related_name="meal_foods", on_delete=models.CASCADE, db_index=True, db_comment="所属饮食记录 ID")
    food_item = models.ForeignKey(NutritionFoodItem, related_name="meal_foods", on_delete=models.PROTECT, db_index=True, db_comment="本次选择的食物 ID；食物定义不随餐次删除")
    serving_ratio = models.DecimalField(max_digits=8, decimal_places=4, default=1, db_comment="食用比例；全部为 1，1/5 为 0.2，2/5 为 0.4")
    serving_quantity = models.DecimalField(max_digits=10, decimal_places=2, null=True, blank=True, db_comment="本次食用份量数值；可由食物标准份量乘以 serving_ratio 得出，也允许用户手动调整")
    serving_unit = models.CharField(max_length=32, blank=True, default="", db_comment="本次食用份量单位，例如 cup、piece、g、ml")
    serving_description = models.CharField(max_length=128, blank=True, default="", db_comment="本次食用份量展示文案，例如 1/5份、半杯、2个")
    display_order = models.IntegerField(default=0, db_index=True, db_comment="餐内食物展示顺序")
    extra = models.JSONField(default=dict, blank=True, db_comment="餐次食物关联扩展字段")
    created_at = models.DateTimeField(auto_now_add=True, db_index=True, db_comment="餐次食物关联创建时间")
    updated_at = models.DateTimeField(auto_now=True, db_index=True, db_comment="餐次食物关联最后更新时间")
```

### 食用比例

用户选择食物后，需要支持：

```text
1/5、2/5、3/5、4/5、全部
```

第一期可以按固定比例提供快捷选择：

| 选项 | serving_ratio |
| --- | --- |
| `1/5` | `0.2` |
| `2/5` | `0.4` |
| `3/5` | `0.6` |
| `4/5` | `0.8` |
| `全部` | `1.0` |

### 保存规则

1. 用户选择食物并确认食用比例。
2. 服务端创建 `NutritionMealFood`，关联 `NutritionMealRecord` 和 `NutritionFoodItem`。
3. 服务端读取该食物的标准 `NutritionIntake(business_type=nutrition_food_item, business_id=food_item.id)`。
4. 按 `serving_ratio` 计算本次实际摄入。
5. 生成新的 `NutritionIntake(business_type=nutrition_meal_record, business_id=meal_record.id)`，作为这顿饭的实际营养摄入。
6. 实际摄入记录可以在 `extra` 中保留来源食物 ID，方便后续追溯“这部分营养来自哪个食物”。

示例：

```text
食物：香蕉
标准营养：134 kcal
用户选择：2/5
本次餐次生成摄入：134 * 0.4 = 53.6 kcal
```

### 5.3 NutritionRecipe：菜谱/组合食物

### Q：多个食物搭配成菜谱如何设计？

A：新增菜谱模型。菜谱表示“多个食物绑定在一起形成一个可复用组合”，例如：

```text
玉米片配牛奶
├─ 玉米片 1份
└─ 牛奶 1杯
```

不要把菜谱做成一个普通 `NutritionFoodItem`。原因：

1. 菜谱是组合对象，内部有多个食物和每个食物的默认份量。
2. 用户添加一份菜谱时，系统需要能展开成多个食物，方便后续编辑其中某个食物。
3. 菜谱可以整体复用，也可以在本次餐次中调整整体比例。
4. 菜谱标准营养可以通过组成食物汇总得到，不需要重复维护一套独立营养字段。

建议模型：

```python
class NutritionRecipe(models.Model):
    user = models.ForeignKey(User, related_name="nutrition_recipes", on_delete=models.CASCADE, null=True, blank=True, db_index=True, db_comment="创建该菜谱的账号 ID；系统预置菜谱为空，用户自定义菜谱填写")
    name = models.CharField(max_length=128, db_index=True, db_comment="菜谱名称，例如玉米片配牛奶")
    localized_name = models.CharField(max_length=128, blank=True, default="", db_index=True, db_comment="菜谱本地化名称")
    category = models.CharField(max_length=64, blank=True, default="", db_index=True, db_comment="菜谱分类，例如早餐、健身餐、低脂餐")
    serving_quantity = models.DecimalField(max_digits=10, decimal_places=2, null=True, blank=True, db_comment="菜谱标准份量数值，例如 1")
    serving_unit = models.CharField(max_length=32, blank=True, default="", db_comment="菜谱标准份量单位，例如 serving、份")
    serving_description = models.CharField(max_length=128, blank=True, default="", db_comment="菜谱标准份量展示文案，例如 1份")
    source = models.CharField(max_length=32, blank=True, default="", db_comment="菜谱来源，例如 system、user_custom、photo_ai、text_ai、chat_ai")
    is_active = models.BooleanField(default=True, db_index=True, db_comment="是否可用；系统下架或用户删除后置为 false")
    sort_weight = models.IntegerField(default=0, db_index=True, db_comment="列表排序权重")
    extra = models.JSONField(default=dict, blank=True, db_comment="菜谱扩展字段")
    created_at = models.DateTimeField(auto_now_add=True, db_index=True, db_comment="菜谱创建时间")
    updated_at = models.DateTimeField(auto_now=True, db_index=True, db_comment="菜谱最后更新时间")

class NutritionRecipeFood(models.Model):
    recipe = models.ForeignKey(NutritionRecipe, related_name="recipe_foods", on_delete=models.CASCADE, db_index=True, db_comment="所属菜谱 ID")
    food_item = models.ForeignKey(NutritionFoodItem, related_name="recipe_foods", on_delete=models.PROTECT, db_index=True, db_comment="菜谱内使用的食物 ID")
    serving_ratio = models.DecimalField(max_digits=8, decimal_places=4, default=1, db_comment="菜谱内该食物相对标准份量的比例")
    serving_quantity = models.DecimalField(max_digits=10, decimal_places=2, null=True, blank=True, db_comment="菜谱内该食物的份量数值")
    serving_unit = models.CharField(max_length=32, blank=True, default="", db_comment="菜谱内该食物的份量单位")
    serving_description = models.CharField(max_length=128, blank=True, default="", db_comment="菜谱内该食物的份量展示文案")
    display_order = models.IntegerField(default=0, db_index=True, db_comment="菜谱内食物展示顺序")
    extra = models.JSONField(default=dict, blank=True, db_comment="菜谱食物关联扩展字段")
    created_at = models.DateTimeField(auto_now_add=True, db_index=True, db_comment="菜谱食物关联创建时间")
    updated_at = models.DateTimeField(auto_now=True, db_index=True, db_comment="菜谱食物关联最后更新时间")
```

### 菜谱营养计算

菜谱标准营养仍然使用 `NutritionIntake`，不新建第二套营养表：

```text
NutritionIntake(
  business_type = "nutrition_recipe",
  business_id = recipe.id
)
```

计算规则：

1. 创建或编辑菜谱时，服务端读取每个 `NutritionRecipeFood.food_item` 的标准营养。
2. 按 `NutritionRecipeFood.serving_ratio` 计算每个食物在菜谱中的营养贡献。
3. 汇总后写入 `NutritionIntake(business_type=nutrition_recipe, business_id=recipe.id)`。
4. 菜谱本身不写热量、蛋白质、碳水、脂肪字段。

### 将菜谱加入餐次

用户选择菜谱后，需要支持整体食用比例，例如半份、1份、2份。

保存规则：

1. 用户选择 `NutritionRecipe` 和本次食用比例。
2. 服务端读取菜谱内的 `NutritionRecipeFood`。
3. 按“菜谱整体比例 * 菜谱内食物比例”展开成多条 `NutritionMealFood`。
4. 根据展开后的食物明细，生成本次餐次 `NutritionIntake(business_type=nutrition_meal_record, business_id=meal_record.id)`。
5. 可以在 `NutritionMealFood.extra` 中保留 `source_recipe_id`，用于展示“来自玉米片配牛奶”。

示例：

```text
菜谱：玉米片配牛奶
├─ 玉米片 1份，标准 120 kcal
└─ 牛奶 1杯，标准 150 kcal

用户选择：1/2份菜谱
本次餐次：
├─ 玉米片 0.5份，60 kcal
└─ 牛奶 0.5杯，75 kcal
合计：135 kcal
```

## 六、图片附件关系

### Q：饮食图片怎么关联？

A：图片仍走现有 `file_manager.ManagedFile` 和 `ManagedFileBusinessRelation`。

建议业务类型：

```text
nutrition_meal_record
nutrition_food_item
```

第一期建议只关联到 `NutritionMealRecord`：

```text
business_type = "nutrition_meal_record"
```

## 七、Apple 健康同步设计

### Q：是否需要单独保存 Apple 健康样本表？

A：第一期不需要。不要再设计 `NutritionAppleHealthSample` 这种单独样本映射表。

原因：

1. 饮食记录是业务事实，Apple 健康只是本人记录的外部同步目标，不应该反客为主。
2. 第一阶段不做复杂的 HealthKit 样本级状态机，避免模型和流程过重。
3. 如果写入 Apple 健康成功，只需要在对应 `NutritionIntake.apple_health_id` 登记健康写入标识。
4. 如果未写入 Apple 健康、用户拒绝权限、非本人记录，`apple_health_id` 保持为空即可。

### 同步规则

1. 只有本人记录才允许写入 Apple 健康。
2. 服务端 `NutritionMealRecord` 保存成功后，客户端才写入 Apple 健康。
3. Apple 健康写入成功后，客户端按营养摄入回传 `apple_health_id` 到服务端。
4. 服务端只更新对应 `NutritionIntake.apple_health_id`。
5. 客户端从 Apple 健康读取到其它来源的营养摄入后，需要上报服务端。
6. 未写入成功不登记，不额外保存失败状态。

### Apple 健康外部营养摄入上报

外部来源营养摄入不直接伪造成餐次记录，建议新增轻量导入记录：

```python
class NutritionAppleHealthIntakeImport(NutritionBaseModel):
    occurred_at = models.DateTimeField(db_index=True, db_comment="Apple 健康营养摄入样本发生时间")
    local_day = models.DateField(db_index=True, db_comment="用户本地日期；用于日看板和按天聚合")
    source_bundle_id = models.CharField(max_length=128, blank=True, default="", db_comment="Apple 健康样本来源 App bundle id")
    source_name = models.CharField(max_length=128, blank=True, default="", db_comment="Apple 健康样本来源名称")
    apple_health_id = models.CharField(max_length=128, db_index=True, db_comment="HealthKit sample UUID，用于幂等去重")
    extra = models.JSONField(default=dict, blank=True, db_comment="Apple 健康外部营养摄入扩展字段")
```

上报后营养值仍使用 `NutritionIntake`：

```text
NutritionIntake(
  business_type = "nutrition_apple_health_intake_import",
  business_id = import.id,
  source = "apple_health_import",
  apple_health_id = HealthKit sample UUID
)
```

设计要点：

1. 不把外部 Apple 健康营养摄入混入 `NutritionMealRecord`。
2. 通过 `apple_health_id` 做幂等，避免重复上报。
3. 本人看板可以合并服务端饮食记录摄入和外部 Apple 健康摄入。
4. 家庭成员不读取 Apple 健康，也不产生该类导入记录。

### Q：`apple_health_id` 应该是什么？

A：使用 HealthKit sample UUID。

建议 metadata：

```text
spark_source = "spark_client"
spark_nutrition_meal_record_id = "{meal_record_id}"
spark_nutrition_intake_id = "{intake_id}"
```

说明：

1. `apple_health_id` 不是服务端同步状态。
2. 它保存 Apple 健康写入成功后返回或可读取到的 HealthKit sample UUID。
3. 客户端回写服务端时，只回写 HealthKit sample UUID，不使用客户端自定义批次 ID。

## 八、能量消耗模型

### 8.1 NutritionEnergyBurnRecord：能量消耗记录

### Q：家庭成员是否需要手动记录能量消耗？

A：需要。第一期新增 `NutritionEnergyBurnRecord`。

设计边界：

1. 本人：支持读取 Apple 健康内的能量消耗，并同步到服务端。
2. 本人：支持手动记录能量消耗，服务端保存成功后可写入 Apple 健康。
3. 家庭成员：支持手动记录能量消耗，只保存服务端，不触发 Apple 健康写入。
4. 看板里的 `已消耗` 优先由客户端结合 Apple 健康消耗和服务端手动记录计算。

建议模型：

```python
class NutritionEnergyBurnRecord(NutritionBaseModel):
    class Source(models.TextChoices):
        MANUAL = "manual", "manual"
        APPLE_HEALTH_IMPORT = "apple_health_import", "apple_health_import"
        WORKOUT = "workout", "workout"
        AI_ESTIMATED = "ai_estimated", "ai_estimated"

    burned_at = models.DateTimeField(db_index=True, db_comment="能量消耗发生时间")
    local_day = models.DateField(db_index=True, db_comment="用户本地日期；用于日看板和按天聚合")
    energy_kcal = models.DecimalField(max_digits=10, decimal_places=2, db_comment="消耗能量，单位 kcal")
    activity_type = models.CharField(max_length=64, blank=True, default="", db_index=True, db_comment="活动类型，例如 walking、running、cycling、manual")
    duration_seconds = models.IntegerField(null=True, blank=True, db_comment="活动持续时长，单位秒；手动只填热量时可为空")
    source = models.CharField(max_length=32, choices=Source.choices, default=Source.MANUAL, db_index=True, db_comment="记录来源：手动、Apple 健康导入、运动记录、AI 估算")
    note = models.CharField(max_length=255, blank=True, default="", db_comment="备注，例如快走 30 分钟")
    apple_health_id = models.CharField(max_length=128, blank=True, default="", db_index=True, db_comment="Apple 健康样本 UUID；写入或读取 Apple 健康成功后登记，未同步时为空")
    extra = models.JSONField(default=dict, blank=True, db_comment="能量消耗扩展字段")
```

### 同步规则

1. 服务端手动创建成功后，如果成员是本人，客户端可写入 Apple 健康。
2. Apple 健康写入成功后，客户端回写 `apple_health_id = HealthKit sample UUID`。
3. 客户端从 Apple 健康读取到其它来源的能量消耗后，需要同步到服务端，`source=apple_health_import`。
4. 服务端通过 `apple_health_id` 做幂等，避免同一个 Apple 健康样本重复入库。
5. 家庭成员手动记录不写 Apple 健康，`apple_health_id` 保持为空。

### 看板计算

`remaining_energy_kcal` 不由服务端单独决定，客户端结合 Apple 健康消耗计算：

```text
remaining = 目标摄入 - 已摄入 + 已消耗
```

其中：

1. `已摄入` 来自服务端 `NutritionIntake` 聚合，以及需要上报服务端的 Apple 健康外部来源营养摄入。
2. `已消耗` 本人优先结合 Apple 健康读取结果和服务端 `NutritionEnergyBurnRecord`。
3. `已消耗` 家庭成员来自服务端 `NutritionEnergyBurnRecord` 手动记录。

## 十、食物库模型

### Q：第一期是否需要单独的食物库表？

A：不需要再单独建立 `NutritionFoodCatalog`。第一期直接用 `NutritionFoodItem` 承载系统预置食物和用户自定义食物。

原因：

1. `NutritionFoodItem` 已经可以表示可搜索、可选择、可复用的食物。
2. 系统预置食物可以 `user=null`。
3. 用户自定义食物可以 `user=当前账号`。
4. 食物标准营养值通过 `NutritionIntake(business_type=nutrition_food_item, business_id=food.id)` 保存，不需要在食物库表重复放热量、蛋白质、碳水、脂肪字段。
5. 少一张表，添加页面、搜索、常用排序、用户自建食物都走一套逻辑。

第一期用途：

1. 支撑添加页面的 `Coffee / Banana / Egg` 列表。
2. 支撑搜索。
3. 支撑常用/推荐排序。
4. 不追求完整食品数据库。
5. 支持用户自己添加食物。

## 十一、目标配置模型

### 数据结构工单：饮食目标如何落库？

目标：支撑《饮食营养需求讨论文档》中的“我的目标”页面、首页看板目标值、餐次目标、三大营养素目标和 AI 分析目标上下文。目标配置必须是成员维度，不是账号维度。

参考页面字段：

```text
我的目标

目标                减重
起始体重            65.0 千克
当前体重            65.0 千克
目标体重            60.0 千克
活跃水平            低
每周目标            -0.50 千克
卡路里目标          1,584 千卡
步数目标            10,000
营养目标            默认
```

### Q：营养目标放哪里？

A：建议服务端保存成员级目标配置，模型名为 `NutritionGoal`。

原因：

1. 看板中的 `剩余`、`已摄入 / 目标` 必须有明确目标来源。
2. 每个家庭成员可能有不同目标，不能放在账号维度。
3. Apple 健康只代表本人，但饮食目标可以服务端保存给任意成员。
4. AI 对话需要读取成员目标作为分析上下文。
5. 目标会随着时间变化，需要支持当前生效目标和后续历史目标扩展。

### 11.2 参考 YAZIO 的卡路里计算数据设计

### Q：为什么需要保存 BMR/TDEE 和计算输入快照？

A：卡路里目标不是单纯用户输入值，还可能来自系统计算。保存计算过程可以让目标可解释、可追踪、可复算。

参考 YAZIO 热量摄入计算器的流程，热量目标通常来自：

```text
性别 / 年龄 / 身高 / 当前体重
-> BMR 基础代谢
-> 活动水平
-> TDEE 维持热量
-> 目标模式和每周目标
-> 建议每日卡路里目标
```

因此 `NutritionGoal` 需要保存三类数据：

| 数据 | 字段 | 用途 |
| --- | --- | --- |
| 输入快照 | `height_cm`、`biological_sex`、`age_years`、`current_weight_kg`、`activity_level`、`weekly_weight_delta_kg` | 解释当时按什么资料计算 |
| 计算结果 | `bmr_kcal`、`tdee_kcal`、`energy_delta_kcal`、`daily_energy_target_kcal` | 展示建议目标和维持热量 |
| 计算元数据 | `calculation_formula`、`calculation_version`、`calculation_inputs` | 支撑公式升级、排障和 AI 解释 |

### Q：计算输入来自哪里？

A：优先从成员档案读取，缺失时由目标页补充。

| 输入项 | 优先来源 | 缺失处理 |
| --- | --- | --- |
| 生理性别 | 成员档案 `gender` | 使用 `unknown`，提示结果可能不准 |
| 年龄 | 成员生日推导 | 缺失时提示补充生日或使用默认目标 |
| 身高 | 成员档案或目标页补充 | 缺失时不能精准重算，提示补充 |
| 当前体重 | 目标页当前体重 | 缺失时用起始体重或提示补充 |
| 活跃水平 | 目标页 | 默认 `low` |
| 每周目标 | 目标页 | 根据目标模式使用默认 |

说明：

1. `NutritionGoal` 保存的是计算时快照，不替代成员档案。
2. 后续成员档案发生变化，不应回写历史目标。
3. 重新计算时使用最新草稿重新生成快照。

### Q：活动水平如何映射到计算系数？

A：第一期 UI 可以保持低/中/高，数据层预留很高。

建议映射：

| activity_level | UI | 说明 | 计算系数示例 |
| --- | --- | --- | --- |
| `low` | 低 | 久坐、很少运动 | `1.2` |
| `medium` | 中 | 每周轻中度运动 | `1.375` |
| `high` | 高 | 经常运动 | `1.55` |
| `very_high` | 很高 | 体力劳动或高频训练 | `1.725` |

系数是公式配置，不建议硬编码在客户端。服务端响应 `calculation_inputs` 时可以带上实际使用的系数。

### Q：计算公式如何版本化？

A：建议第一期使用公式名和版本字段，不把公式细节写死在客户端。

```json
{
  "calculation_formula": "mifflin_st_jeor",
  "calculation_version": "v1",
  "calculation_inputs": {
    "activity_factor": 1.2,
    "missing_fields": [],
    "used_default_values": false,
    "source": "goal_recalculate"
  }
}
```

字段说明：

1. `calculation_formula` 用于标记公式体系。
2. `calculation_version` 用于公式升级后仍能解释旧目标。
3. `calculation_inputs` 保存本次计算解释，不作为核心查询字段。
4. 如果用户手动覆盖目标，也仍可保留上一次计算快照，便于展示“基于系统建议修改”。

### Q：服务端计算算法完整步骤是什么？

A：建议第一期使用 `Mifflin-St Jeor + 活跃系数 + 每周体重目标换算`。

输入：

| 字段 | 单位 | 来源 |
| --- | --- | --- |
| `biological_sex` | `male/female/unknown` | 成员档案或目标草稿 |
| `age_years` | 年 | 成员生日推导 |
| `height_cm` | cm | 成员档案或目标草稿 |
| `current_weight_kg` | kg | 目标草稿 |
| `activity_level` | 枚举 | 目标草稿 |
| `goal_type` | 枚举 | 目标草稿 |
| `weekly_weight_delta_kg` | kg/周 | 目标草稿 |

步骤一：校验输入。

```text
如果缺少 current_weight_kg、height_cm、age_years、biological_sex：
  返回可计算性不足，提示补充资料

如果 biological_sex == unknown：
  不做精确 BMR，返回默认目标或要求补充
```

步骤二：计算 BMR。

```text
male:
  bmr = 10 * current_weight_kg + 6.25 * height_cm - 5 * age_years + 5

female:
  bmr = 10 * current_weight_kg + 6.25 * height_cm - 5 * age_years - 161
```

步骤三：计算 TDEE。

```text
activity_factor = factor(activity_level)
tdee = bmr * activity_factor
```

建议系数：

```json
{
  "low": 1.2,
  "medium": 1.375,
  "high": 1.55,
  "very_high": 1.725
}
```

步骤四：根据目标模式计算每日热量差。

```text
if goal_type == lose_weight:
  weekly_delta = negative value, for example -0.50
elif goal_type == maintain:
  weekly_delta = 0
elif goal_type == gain_muscle:
  weekly_delta = positive value, for example 0.25
elif goal_type == custom:
  weekly_delta = user input or 0

weekly_energy_delta = weekly_delta * 7700
daily_energy_delta = weekly_energy_delta / 7
```

说明：

1. 减重时 `daily_energy_delta` 为负数。
2. 维持时 `daily_energy_delta = 0`。
3. 增重/增肌时 `daily_energy_delta` 为正数。
4. `7700 kcal/kg` 是估算值，必须写入 `calculation_inputs` 或公式版本说明中，方便后续调整。

步骤五：得到建议热量。

```text
suggested_energy_kcal = tdee + daily_energy_delta
```

步骤六：安全边界处理。

```text
if suggested_energy_kcal < min_safe_energy_kcal:
  suggested_energy_kcal = min_safe_energy_kcal
  risk_flags append "below_safe_energy_floor"

if weekly_weight_delta_kg outside allowed range:
  return validation error or clamp by product rule
```

建议第一期不要静默修正过多数据：

1. 每周目标超范围：禁止保存，让用户重新选择。
2. 建议热量低于安全下限：可以展示“系统建议目标过低”，由服务端返回风险标记。
3. 是否自动上调到安全下限，需要产品最终确认；数据层预留 `risk_flags`。

步骤七：返回解释结果。

```json
{
  "suggested_energy_kcal": 1584,
  "bmr_kcal": 1420,
  "tdee_kcal": 2134,
  "energy_delta_kcal": -550,
  "calculation_formula": "mifflin_st_jeor",
  "calculation_version": "v1",
  "calculation_inputs": {
    "activity_factor": 1.2,
    "weekly_weight_energy_kcal_per_kg": 7700,
    "min_safe_energy_kcal": 1200,
    "risk_flags": [],
    "missing_fields": [],
    "used_default_values": false,
    "source": "goal_recalculate"
  },
  "reason": "基于减重目标、低活跃水平和每周 -0.50 千克计算"
}
```

### Q：伪代码怎么写？

A：服务端可以按下面的伪代码实现：

```python
def calculate_energy_goal(input):
    missing = validate_required_fields(input)
    if missing:
        return CalculationResult(
            can_calculate=False,
            missing_fields=missing,
            reason="缺少身高、年龄、性别或当前体重，无法精确计算"
        )

    if input.biological_sex == "male":
        bmr = 10 * input.current_weight_kg + 6.25 * input.height_cm - 5 * input.age_years + 5
    elif input.biological_sex == "female":
        bmr = 10 * input.current_weight_kg + 6.25 * input.height_cm - 5 * input.age_years - 161
    else:
        return CalculationResult(
            can_calculate=False,
            missing_fields=["biological_sex"],
            reason="缺少生理性别，无法精确计算基础代谢"
        )

    activity_factor = activity_factor_for(input.activity_level)
    tdee = bmr * activity_factor

    weekly_delta = normalized_weekly_delta(
        goal_type=input.goal_type,
        weekly_weight_delta_kg=input.weekly_weight_delta_kg
    )

    daily_energy_delta = weekly_delta * 7700 / 7
    suggested_energy = tdee + daily_energy_delta

    risk_flags = []
    if suggested_energy < min_safe_energy_kcal(input):
        risk_flags.append("below_safe_energy_floor")

    return CalculationResult(
        can_calculate=True,
        suggested_energy_kcal=round(suggested_energy, 0),
        bmr_kcal=round(bmr, 2),
        tdee_kcal=round(tdee, 2),
        energy_delta_kcal=round(daily_energy_delta, 2),
        calculation_formula="mifflin_st_jeor",
        calculation_version="v1",
        calculation_inputs={
            "activity_factor": activity_factor,
            "weekly_weight_energy_kcal_per_kg": 7700,
            "risk_flags": risk_flags,
            "missing_fields": [],
            "used_default_values": False,
            "source": "goal_recalculate",
        }
    )
```

### Q：计算结果保存到 `NutritionGoal` 时怎么处理？

A：分两种情况：

| 用户行为 | 保存方式 |
| --- | --- |
| 点击“使用建议目标” | 保存 `daily_energy_target_kcal=suggested_energy_kcal`，`is_energy_target_custom=false`，同时保存 BMR/TDEE/公式快照 |
| 手动修改目标 | 保存用户输入的 `daily_energy_target_kcal`，`is_energy_target_custom=true`，仍保留最近一次 BMR/TDEE/公式快照 |

这样可以同时满足：

1. 看板使用用户最终确认的目标。
2. 目标详情可以解释系统原始建议。
3. 后续重新计算不会静默覆盖用户手动目标。

### Q：BMI、理想体重、摄入目标、消耗估算要不要拆成四套数据模型？

A：不建议。参考 YAZIO 的优秀点是“同一人体模型，多种输出切面”，不是四套孤立模型。

第一期建议抽象为统一计算输出：

```text
NutritionBodyMetricsCalculation
  -> BMI 结果
  -> 理想体重范围
  -> 卡路里摄入建议
  -> 消耗估算解释
```

这些结果来自同一组输入：

```text
member + biological_sex + age_years + height_cm + current_weight_kg + activity_level + goal_type + weekly_weight_delta_kg
```

设计原则：

1. `NutritionGoal` 保存最终目标和最近一次计算快照。
2. BMI、理想体重、BMR、TDEE 是计算结果，不单独建事实表。
3. 事实消耗仍由 `NutritionEnergyBurnRecord` 和 Apple 健康导入承载。
4. 计算结果可以进入 DTO 和 `calculation_inputs`，用于展示和 AI 解释。
5. 后续如果需要记录每次计算历史，再另建 `NutritionGoalCalculationLog`，第一期不做。

### BMI 计算输出

```text
bmi = current_weight_kg / (height_m * height_m)
```

建议 DTO：

```swift
struct NutritionBMIResult: Codable, Sendable, Equatable {
    var value: Double
    var category: String
    var categoryText: String
}
```

分类建议第一期使用成人通用分类：

| category | 说明 |
| --- | --- |
| `underweight` | 偏瘦 |
| `normal` | 正常 |
| `overweight` | 超重 |
| `obese` | 肥胖 |
| `unknown` | 资料不足 |

注意：

1. BMI 分类阈值需要按地区/医学口径后续确认。
2. 第一阶段可以只做辅助展示，不把 BMI 作为强制目标限制。

### 理想体重输出

理想体重建议输出范围：

```text
ideal_weight_min_kg = 18.5 * height_m * height_m
ideal_weight_max_kg = 24.0 * height_m * height_m
```

可选参考值：

```text
broca_weight_kg = height_cm - 100
```

建议 DTO：

```swift
struct NutritionIdealWeightResult: Codable, Sendable, Equatable {
    var minKg: Double?
    var maxKg: Double?
    var referenceKg: Double?
    var method: String
    var targetWeightStatus: String
}
```

`targetWeightStatus` 建议：

| 值 | 说明 |
| --- | --- |
| `within_range` | 目标体重在建议范围内 |
| `below_range` | 目标体重低于建议范围 |
| `above_range` | 目标体重高于建议范围 |
| `unknown` | 无法判断 |

### 卡路里摄入建议输出

摄入建议复用已有 `NutritionEnergyCalculationResponse`：

```text
suggested_energy_kcal
bmr_kcal
tdee_kcal
energy_delta_kcal
calculation_formula
calculation_version
calculation_inputs
```

它对应 YAZIO 的每日卡路里摄入计算器，是目标系统最核心输出。

### 卡路里消耗估算输出

消耗估算不要替代事实消耗。建议只用于解释：

```swift
struct NutritionBurnEstimateResult: Codable, Sendable, Equatable {
    var bmrKcal: Double?
    var tdeeKcal: Double?
    var estimatedDailyActivityKcal: Double?
    var appleHealthActiveEnergyKcal: Double?
    var manualBurnedEnergyKcal: Double?
    var source: String
}
```

计算：

```text
estimated_daily_activity_kcal = max(tdee_kcal - bmr_kcal, 0)
```

来源说明：

1. `estimatedDailyActivityKcal` 是公式估算。
2. `appleHealthActiveEnergyKcal` 是本人 Apple 健康事实数据。
3. `manualBurnedEnergyKcal` 是家庭成员或手动记录事实数据。
4. 看板 `已消耗` 使用事实数据，目标解释使用估算数据。

建议新增统一响应，而不是四个分散接口：

用途：

2. `总结详细页` 展示 BMI/目标状态。

4. 后续如果要做独立计算器页面，也可以复用这一套响应。

### 11.3 目标设置子页面数据承载

### Q：`我的目标`、`卡路里目标`、`卡路里分布`、`营养目标` 是否要拆成多张表？

A：不建议拆表。四个页面本质都在编辑同一份成员级目标配置，统一落到 `NutritionGoal`。

对应关系：

| 页面 | 字段来源 |
| --- | --- |
| 我的目标 | `goal_type`、`start_weight_kg`、`current_weight_kg`、`target_weight_kg`、`activity_level`、`weekly_weight_delta_kg`、`daily_energy_target_kcal`、`step_target`、`nutrition_target_mode` |
| 卡路里目标 | `daily_energy_target_kcal`、`is_energy_target_custom`、`weekend_energy_target_kcal`、`is_weekend_energy_enabled`、`meal_distribution` |
| 卡路里分布 | `meal_distribution` |
| 营养目标 | `nutrition_target_mode`、`carbohydrate_ratio`、`protein_ratio`、`fat_ratio`、`carbohydrate_target_g`、`protein_target_g`、`fat_target_g` |

### 卡路里目标页字段

```json
{
  "daily_energy_target_kcal": 1584,
  "is_energy_target_custom": true,
  "is_weekend_energy_enabled": false,
  "weekend_energy_target_kcal": null,
  "meal_distribution": {
    "breakfast": 0.30,
    "lunch": 0.40,
    "dinner": 0.25,
    "snack": 0.05
  }
}
```

数据规则：

1. `daily_energy_target_kcal` 是首页、总结详细、营养卡片的全天目标来源。
2. 用户点击“重新计算卡路里目标”后，如果接受结果，`is_energy_target_custom=false`；如果手动输入，`is_energy_target_custom=true`。
3. `weekend_energy_target_kcal` 第一阶段可以预留，未启用时为空。
4. 如果后续启用周末目标，看板查询某一天时，服务端可以根据日期判断当天使用 `daily_energy_target_kcal` 还是 `weekend_energy_target_kcal`。

### 卡路里分布页字段

`meal_distribution` 保存餐次比例，不保存餐次目标热量的冗余字段。

```json
{
  "breakfast": 0.30,
  "lunch": 0.40,
  "dinner": 0.25,
  "snack": 0.05
}
```

计算规则：

```text
meal_target_energy_kcal = active_day_energy_target_kcal * meal_distribution[meal_type]
meal_target_carbohydrate_g = carbohydrate_target_g * meal_distribution[meal_type]
meal_target_protein_g = protein_target_g * meal_distribution[meal_type]
meal_target_fat_g = fat_target_g * meal_distribution[meal_type]
```

说明：

1. `active_day_energy_target_kcal` 表示当前日期实际使用的全天热量目标。
2. 第一阶段如果不启用周末目标，`active_day_energy_target_kcal = daily_energy_target_kcal`。
3. 餐次目标由服务端在看板 DTO 中计算返回，客户端不要写死 `30/40/25/5`。
4. 分布合计必须为 `1.0`，即页面展示的 `100%`。

### 营养目标页字段

```json
{
  "nutrition_target_mode": "low_carb",
  "carbohydrate_ratio": 0.45,
  "protein_ratio": 0.25,
  "fat_ratio": 0.30,
  "carbohydrate_target_g": 178.20,
  "protein_target_g": 99.00,
  "fat_target_g": 52.80
}
```

页面展示需要同时支持：

| 展示项 | 数据来源 |
| --- | --- |
| 碳水化合物百分比 | `carbohydrate_ratio * 100` |
| 蛋白质百分比 | `protein_ratio * 100` |
| 脂肪百分比 | `fat_ratio * 100` |
| 碳水化合物克数 | `carbohydrate_target_g` |
| 蛋白质克数 | `protein_target_g` |
| 脂肪克数 | `fat_target_g` |
| 碳水化合物热量 | `carbohydrate_target_g * 4` 或 `daily_energy_target_kcal * carbohydrate_ratio` |
| 蛋白质热量 | `protein_target_g * 4` 或 `daily_energy_target_kcal * protein_ratio` |
| 脂肪热量 | `fat_target_g * 9` 或 `daily_energy_target_kcal * fat_ratio` |

推荐第一阶段保存策略：

1. 服务端保存比例和克数。
2. 比例是主要输入，克数是服务端根据比例和热量目标计算后的结果。
3. 客户端页面优先编辑比例，克数作为展示值。
4. 后续如果支持直接编辑克数，服务端需要反算比例并校验合计。

### 11.4 目标保存与版本规则

### Q：目标页面保存时是更新旧记录还是新建记录？

A：建议“创建新版本，旧版本失效”。

流程：

```text
客户端提交完整 NutritionGoalUpdateRequest
-> 服务端校验成员权限
-> 服务端校验字段和比例
-> 当前 active 目标置为 is_active=false
-> 新建 NutritionGoal(is_active=true)
-> 返回新的 RemoteNutritionGoal
-> 客户端刷新看板
```

原因：

1. 目标变更不应该改写历史目标记录。
2. 后续如果做历史日期复盘，可以按 `effective_from` 找到当日目标。
3. 目标版本化比直接覆盖更利于排障和 AI 解释。

第一阶段如果为了实现简单，也可以物理更新当前目标，但文档建议按版本化设计；实现时至少保留 `effective_from/is_active` 字段，不要把路堵死。

### 11.5 目标校验规则

| 校验项 | 规则 |
| --- | --- |
| 目标归属 | `member` 必须属于当前账号有权限操作的成员 |
| 活跃目标 | 同一成员通常只能有一条 `is_active=true` |
| 卡路里目标 | `daily_energy_target_kcal > 0`，且需要限制合理上下限 |
| 周末目标 | `is_weekend_energy_enabled=true` 时，`weekend_energy_target_kcal` 必填且大于 0 |
| 餐次分布 | `breakfast + lunch + dinner + snack = 1.0` |
| 餐次比例 | 任一比例不能小于 0 |
| 营养比例 | `carbohydrate_ratio + protein_ratio + fat_ratio = 1.0` |
| 每周目标 | 减重为负，维持为 0，增重/增肌为正 |
| 目标体重 | 减重/增重模式建议填写 |

浮点校验建议：

```text
abs(sum - 1.0) <= 0.0001
```

服务端保存前应统一量化小数位，避免前端传入 `0.30000000004` 导致校验误伤。

### 索引与约束建议

```python
indexes = [
    models.Index(fields=["user", "member", "is_active"]),
    models.Index(fields=["member", "effective_from"]),
]
```

约束建议：

1. 数据库层优先保证同一成员只有一条当前有效目标。
2. 业务字段校验以 `11.5 目标校验规则` 为准。
3. 如果数据库条件唯一约束实现成本较高，第一期可先在服务层事务内保证 active 目标唯一。

### Q：目标变更后要不要保存历史？

A：建议保留历史目标，但第一期不需要单独建每日快照表。

方案：

1. `NutritionGoal` 使用 `is_active` 表示当前目标。
2. 用户修改目标时，旧目标置为 `is_active=False`，新建一条目标记录。
3. `effective_from` 记录新目标生效日期。
4. 历史饮食记录不被目标变更影响。
5. 第一期历史看板可以使用当前目标或按 `effective_from` 查当日生效目标；后续如性能不足再加 `NutritionDailyGoalSnapshot`。

不建议第一期新增 `NutritionDailyGoalSnapshot`，原因：

1. 第一阶段目标设置频率低。
2. 目标快照会增加同步和回填复杂度。
3. 看板优先保证今日体验，历史精确复盘可后续补。

### Q：看板 DTO 如何使用目标？

A：`RemoteNutritionDashboard.goal` 继续返回日目标汇总，作为首页目标数据源。

建议 `goal` 至少包含：

```json
{
  "energy_kcal": 1584,
  "active_day_energy_kcal": 1584,
  "protein_g": 99,
  "carbohydrate_g": 178,
  "fat_g": 53,
  "nutrition_target_mode": "low_carb",
  "carbohydrate_ratio": 0.45,
  "protein_ratio": 0.25,
  "fat_ratio": 0.30
}
```

说明：

1. `energy_kcal` 表示基础每日目标。
2. `active_day_energy_kcal` 表示当前查询日期实际使用的目标；第一期未启用周末目标时和 `energy_kcal` 相同。
3. 首页看板的剩余热量建议使用 `active_day_energy_kcal`。

## 十三、客户端数据模型

### Q：客户端是否建本地数据库模型？

A：不建。饮食营养客户端只定义远程 DTO、展示模型和请求模型。

不新增：

1. CoreData 饮食记录表。
2. 本地饮食记录 repository。
3. 饮食离线 outbox。

允许：

1. API DTO。
2. ViewModel 内存状态。
3. 项目已有公共请求缓存。
4. 图片临时缓存和系统缓存。

### 13.1 Remote DTO

编码解码约定：

1. 客户端 Remote DTO 全部使用项目统一 `JSONEncoder.default` / `JSONDecoder.default`，实现位置参考 `SparkClient/Projects/Foundation/Extensions/Codable+Extensions.swift`。
2. 服务端 JSON 保持 snake_case，Swift DTO 保持 camelCase，由统一编码器/解码器自动转换。
3. 日期字段统一 ISO8601，不在单个 DTO 内自定义日期解析。
4. 不要手写 `CodingKeys` / `CodableKey`，不要在每个 DTO 中手动对齐 snake_case 字段。
5. 如果字段命名无法被 `convertFromSnakeCase` 正确转换，优先调整服务端字段或 Swift 属性名；确需例外时需要在接口评审中单独说明。

## 十五、数据一致性规则

### 用户保存流程

1. 用户在 App 里添加食物、菜谱或手动营养数据。
2. App 先提交到服务端保存。
3. 服务端生成正式记录：
   - `NutritionMealRecord`
   - `NutritionMealFood`
   - `NutritionIntake`
4. 服务端保存成功后，App 才判断是否需要写 Apple 健康。
5. 如果是“本人”且用户授权了 Apple 健康，App 写入 Apple 健康。
6. Apple 健康写入成功后，App 拿到 `HealthKit sample UUID`。
7. App 把这个 UUID 回写服务端，存到对应 `NutritionIntake.apple_health_id`。
8. 如果 Apple 健康写入失败，服务端记录仍然保留，只是不登记 `apple_health_id`。

简单流程：

```text
用户确认
-> App 提交服务端
-> 服务端保存饮食记录和营养摄入
-> App 写入 Apple 健康
-> App 回写 HealthKit sample UUID 到服务端
```

服务端是主数据源，Apple 健康是本人健康数据的同步目标。

### 创建

1. 搜索、条形码扫描、拍照识别、自然语言输入都只产生选择项或草稿，确认前不创建正式饮食记录。
2. 用户确认饮食草稿后，先创建服务端 `NutritionMealRecord`。
3. 如果用户选择已有食物，服务端保存 `NutritionMealFood`，并按食用比例生成餐次 `NutritionIntake`。
4. 如果用户选择菜谱，服务端先展开 `NutritionRecipeFood`，再生成多条 `NutritionMealFood` 和餐次 `NutritionIntake`。
5. 如果用户手动录入营养值，服务端直接保存餐次 `NutritionIntake`。
6. 服务端关联图片附件。
7. 如果成员是本人，客户端再写 Apple 健康。
8. Apple 健康写入成功后，仅回写对应 `NutritionIntake.apple_health_id`。

### 编辑

1. 编辑饮食记录时，服务端更新主表、`NutritionMealFood`、菜谱展开结果和 `NutritionIntake`。
2. 看板统计从 `NutritionIntake` 重新聚合。
3. 如果该记录下的 `NutritionIntake` 已经写入 Apple 健康，第一阶段建议提示用户需要重新写入 Apple 健康，并在成功后覆盖对应摄入项的 `apple_health_id`。

### 删除

1. 服务端饮食记录软删除。
2. 如果记录下的营养摄入已写入 Apple 健康，客户端可根据 `NutritionIntake.apple_health_id` 做后续处理。
3. 第一阶段不在服务端维护样本级删除状态。

### 查询

1. 页面数据请求服务端。
2. 本人页面可同时读取 Apple 健康能量消耗和外部营养摄入。
3. 客户端展示时合并，但要区分数据来源。
4. 家庭成员页面不读 Apple 健康。

## 十六、权限规则

### 服务端权限

1. 所有饮食记录必须校验当前用户是否有该 `member` 的可见/编辑权限。
2. 创建、编辑、删除需要 `can_create/can_edit/can_delete` 或等价成员绑定权限。
3. 只允许访问当前用户绑定成员的数据。
4. 图片附件必须属于当前用户，且通过业务关系绑定到饮食记录。

### Apple 健康权限

1. 只有本人可写入 Apple 健康。
2. 家庭成员不触发 HealthKit 权限请求。
3. 用户拒绝 HealthKit 权限时，服务端记录仍然保留，`NutritionIntake.apple_health_id` 保持为空。
4. Apple 健康读取只用于本人看板。

## 十八、已确认决策

1. `apple_health_id` 使用 HealthKit sample UUID。
2. `remaining_energy_kcal` 由客户端结合 Apple 健康消耗计算。
3. Apple 健康外部来源营养摄入需要上报服务端。
4. 系统预置食物第一期由服务端内置。
5. 家庭成员需要手动记录能量消耗，需要新增 `NutritionEnergyBurnRecord`；本人支持写入 Apple 健康，支持读取 Apple 健康内的消耗并同步服务端。
6. 目标配置为成员维度；第一期即使不开放完整目标设置页，也必须能返回默认目标并支撑看板目标值。
7. 目标设置四个页面共用 `NutritionGoal`，不为 `卡路里目标`、`卡路里分布`、`营养目标` 单独建表。
8. `meal_distribution` 只保存餐次比例，餐次热量和三大营养素目标由服务端按全天目标动态计算返回。
9. 周末热量目标使用 `weekend_energy_target_kcal` 和 `is_weekend_energy_enabled` 预留；第一期可不开放完整能力。
10. 客户端目标草稿只做页面态，不做本地持久化；最终保存转换为 `NutritionGoalUpdateRequest`。
11. 目标 DTO 继续使用项目统一 camelCase/snake_case 编解码策略，不手写 `CodingKeys`。
12. 卡路里目标重新计算需要保存输入快照、BMR、TDEE、每日热量差、公式名称和公式版本，保证目标可解释、可排障、可复算。
13. 活跃水平第一期 UI 展示低/中/高，数据层预留 `very_high`，公式系数由服务端返回或配置，不在客户端硬编码。
14. 参考 YAZIO 的四类计算器在项目中不拆成四套模型；统一通过 BMI、理想体重、摄入目标、消耗估算四个输出切面表达。
15. BMI、理想体重、BMR、TDEE 属于计算结果，不是业务事实；不单独建持久事实表。
16. 卡路里消耗看板优先使用 Apple 健康或手动记录事实数据；TDEE 只用于目标解释和估算，不直接等同于今日已消耗。

```text
客户端不保存饮食业务数据
```
