# 饮食营养客户端详细设计文档

> 文档性质：客户端详细设计稿。本文基于《饮食营养需求讨论文档》和《饮食营养数据详设文档》，重点描述客户端页面、操作流程、展示内容、数据来源、按钮动作、计算规则和待补充点。本文不涉及代码改动。

## 一、客户端范围

### Q：第一期客户端要做哪些页面？

A：第一期围绕“首页入口 -> 今日看板 -> 添加记录 -> 保存 -> Apple 健康同步 -> 详情查看”形成闭环。

信息架构：

```text
用户
🏥 医疗档案
├─ 病例
├─ 检查
├─ 体检
├─ 用药

🍎 饮食营养
├─ 总结
├─ 营养
```

第一期页面：

| 页面 | 作用 |
| --- | --- |
| 饮食营养首页 | 展示 `总结` 和 `营养` 两个模块 |
| 总结详情页 | 展示今日摄入、消耗、剩余、来源明细、Apple 健康来源 |
| 餐次详情页 | 展示早餐/午餐/晚餐/小吃某一餐的记录 |
| 食物添加页 | 搜索、拍照、手动输入、选择食物/菜谱 |
| 食物/菜谱确认页 | AI 草稿、自然语言识别或复杂菜谱场景下调整份量、比例、营养估算，确认保存 |
| 饮食记录历史页 | 按日期查看历史记录 |
| 能量消耗记录页 | 查看和手动添加消耗 |

待补充：

1. 具体路由挂载位置。
2. 是否复用医疗档案成员选择组件。
3. 是否需要饮食营养独立导航栈。

| `NutritionLoadingStateView` | 骨架屏和 loading | 首页、搜索、识别 |

组件边界：

1. 页面级 View 只负责布局、导航和状态绑定。
2. `NutritionCardContainer` 只负责容器样式，不承载业务字段和点击逻辑。
3. 公共卡片只吃展示模型，不直接请求接口。
4. 搜索结果卡片不关心搜索模式，文本搜索和条形码搜索共用。
5. 相机、条形码扫描这类系统能力独立放在对应页面，不塞进食物添加页。
6. HealthKit 读写不进入 View，统一通过 `NutritionHealthKitSyncUseCase` 调用。

### Q：每个页面保存、上送和加载分别对应哪些接口与数据模型？

A：页面不直接拼接口、不直接处理 JSON。页面调用 ViewModel，ViewModel 调用 UseCase，UseCase 通过 `NutritionRepository` / `NutritionAPI` 访问服务端。所有远程 DTO 放在 `NutritionRemoteModels.swift`，展示模型放在 `NutritionDisplayModels.swift`。

### Q：哪些位置需要本地化？

A：所有用户可见文案都必须走项目本地化能力，禁止在 View、ViewModel、UseCase 中散落硬编码中文或英文。第一期重点本地化：

1. 页面标题：饮食营养、总结、营养、餐点总结、正在分析、扫描条形码、添加食物、添加或编辑详情、能量消耗。
2. 餐次名称：早餐、午餐、晚餐、小吃。
3. 操作按钮：详细信息、更多、添加更多、完成、确认并记录、重试、取消、创建项目、修改餐点、重置筛选过滤条件。
4. 字段名称：卡路里、碳水化合物、蛋白质、脂肪、已食用、剩余、已消耗。
5. 状态提示：未授权 Apple 健康、识别失败、网络异常、没有搜索结果、保存失败。
6. 单位展示：千卡、克、毫克、微克、毫升；单位拼接集中在格式化工具内，不在页面手写。

建议新增 `NutritionL10n` 或使用项目现有 `L10n.text(...)` 统一 key，key 命名按页面域划分，例如 `nutrition.home.title`、`nutrition.meal.breakfast`、`nutrition.action.confirm_record`。

### Q：核心代码和核心方法需要记录哪些日志？

A：饮食营养涉及 AI 识别、HealthKit、服务端保存和多来源聚合，必须在 UseCase/Repository 边界记录结构化日志。View 只记录必要的用户入口事件，不打印业务 JSON。

日志原则：

1. 日志放在 `NutritionDashboardUseCase`、`NutritionMealRecordUseCase`、`NutritionSearchUseCase`、`NutritionCameraRecognitionUseCase`、`NutritionHealthKitSyncUseCase`、`NutritionEnergyBurnUseCase` 和 `NutritionRepository`。
2. 日志必须包含 `memberID`、`date`、`mealType`、`requestID`、`recognitionID`、`recordID` 等可追踪字段。
3. 不记录完整图片、完整自然语言原文、完整营养明细 JSON；必要时记录长度、数量、摘要和脱敏 ID。
4. 保存链路必须记录“服务端保存成功”和“Apple 健康写入/回写成功”两个独立结果，避免把 HealthKit 失败误判为服务端保存失败。
5. Debug 日志和生产日志分级，生产只保留关键业务节点、错误和耗时。

关键日志点：

| 方法 | 日志内容 |
| --- | --- |
| `loadDashboard(memberID:date:)` | 看板加载开始/成功/失败、餐次数、总摄入、目标是否缺失 |
| `syncTodayIfNeeded(memberID:date:)` | 是否本人、HealthKit 权限、读取样本数、上报结果 |
| `search(query:mode:filters:)` | 搜索模式、关键词长度、筛选项、结果数量、耗时 |
| `recognizePhoto(...)` | 图片来源、压缩后大小、识别 ID、识别结果数量、失败原因 |
| `recognizeText(...)` | 输入长度、识别 ID、草稿项数量、失败原因 |
| `createMealRecord(...)` | 请求来源、餐次、食物数量、摄入项数量、服务端记录 ID |
| `writeIntakesAndReportIDs(...)` | HealthKit 样本数量、成功 UUID 数、回写成功/失败 |
| `createManualBurn(...)` | 消耗热量、活动类型、成员是否本人、HealthKit 写入结果 |

### 营养详细列表页编辑入口

目标页面：`NutritionDetailView`。

入口位置：页面导航栏右上角，和 `NutritionDetailView.body` 中的 `.navigationTitle(...)`、`.navigationBarTitleDisplayMode(.inline)` 同层添加 toolbar。

右上编辑入口实现要求：

1. `NutritionDetailView` 右上角展示 `编辑`。
2. `编辑` 使用 `NavigationLink` 打开 `NutritionMealFoodEditListView`。
3. 传入当前日期全部 records，而不是 `NutritionMealDetailView.detail.records`。
4. 当前 `NutritionDetailViewModel` 如只暴露 `groups`，需要新增 `records`，或调整 mapper 让 `groups` 可以回溯到原始 `RemoteMealRecord`。
5. 当前日期没有食物/记录时不展示编辑入口。
6. `NutritionMealFoodEditListView` 当前入参包含 `mealType`；从 `NutritionDetailView` 进入时是全天列表，需要让 `mealType` 支持可选，或新增 all-day 模式，避免只编辑某一个餐次。

建议代码形态：

```swift
.toolbar {
    ToolbarItem(placement: .navigationBarTrailing) {
        NavigationLink {
            NutritionMealFoodEditListView(
                records: viewModel.records,
                memberID: memberID,
                date: date,
                mealType: nil,
                dependencies: dependencies
            )
        } label: {
            Text(L10n.text("nutrition.common.edit"))
        }
        .disabled(viewModel.records.isEmpty)
    }
}
```

食物行明细编辑要求：

1. `NutritionMealFoodRowView(row:)` 外层使用 `NavigationLink`。
2. 点击后打开 `NutritionMealFoodDetailEditView`。
3. 需要通过 `food.recordID` 在当前日期 records 中找到所属 `RemoteMealRecord`。
4. 保存后更新服务端食物配比，并刷新 `NutritionDetailView` 当前日期列表。

建议代码形态：

```swift
if let record = viewModel.records.first(where: { $0.id == food.recordID }) {
```

数据来源：

1. `NutritionDetailView` 从 `GET /meal-records/` 加载当前成员、当前日期全部 `RemoteMealRecord`。

4. 创建膳食不改变当前餐次已有饮食记录，只新增菜谱定义。

创建膳食响应解码要求：

服务端 `POST /api/v1/nutrition/recipes/` 创建成功后，`data` 不是 `RemoteRecipe` 本体，而是创建结果包装对象：

```json
{
  "recipe": {
    "id": 4,
    "name": "两杯咖啡",
    "localized_name": "两杯咖啡",
    "category": "custom",
    "serving_description": "1 份膳食",
    "foods": []
  },
  "overview": {
    "energy_kcal": 3.2,
    "protein_g": 0.48,
    "carbohydrate_g": 0.0,
    "fat_g": 0.0
  },
  "intakes": []
}
```

客户端必须新增或使用专用 DTO：

```swift
struct RemoteRecipeCreateResponse: Codable, Equatable, Sendable {
    let recipe: RemoteRecipe
    let overview: RemoteNutritionOverview
    let intakes: [RemoteNutritionIntake]
}
```

解码规则：

1. `NutritionAPI.createRecipe(...)` 不要直接把响应 `data` 解码为 `RemoteRecipe`。
2. 应解码为 `RemoteRecipeCreateResponse`，再使用 `response.recipe.id` 作为正式菜谱 ID。
3. `overview` 用于创建成功后的展示刷新或日志；`intakes` 用于确认服务端已生成 `nutrition_recipe` 标准营养值。
4. 继续使用 `JSONDecoder.default`，不要为该响应手写 `CodingKeys`。
5. 如果接口响应中 `overview` 或 `intakes` 后续允许为空，需要在 DTO 中明确可选性；第一期按当前服务端返回必填处理。

## 七、食物/菜谱确认页

### Q：为什么需要确认页？

A：普通食物添加已改为“详情 sheet 可调份量 + 完成直接提交”，不再强制进入确认页。确认页保留给 AI 草稿、自然语言识别、复杂菜谱或后续需要完整核对的场景，因为这些来源的不确定性更高，必须允许用户确认。

页面展示：

1. 当前餐次。
2. AI 草稿、自然语言草稿或复杂菜谱草稿。
3. 每项的份量、单位、食用比例。
4. 营养估算：热量、碳水、蛋白质、脂肪。
5. AI 置信度和不确定提示。
6. 图片预览或用户输入摘要。

比例选择：

```text
1/5、2/5、3/5、4/5、全部
```

也可以支持手动输入：

1. 数量。
2. 单位。
3. 克重。
4. 自定义份量文案。

保存行为：

```text
用户确认
-> App 提交服务端
-> 服务端保存 NutritionMealRecord / NutritionMealFood / NutritionIntake
-> 如果本人且授权 Apple 健康，App 写入 HealthKit
-> App 回写 HealthKit sample UUID 到服务端
-> 返回饮食营养首页或餐次详情
```

接口占位：

| 动作 | 接口占位 |
| --- | --- |
| 创建饮食记录 | `POST /api/v1/nutrition/meal-records/` |
| 回写营养摄入 Apple 健康 ID | `POST /api/v1/nutrition/intakes/{id}/apple-health-id/` |
| 创建自定义食物 | `POST /api/v1/nutrition/food-items/` |
| 创建自定义菜谱 | `POST /api/v1/nutrition/recipes/` |

说明：具体接口字段以后在服务端详设文档中单独细化。

## 八、自定义食物与菜谱

### Q：用户如何添加自己的食物？

A：从食物添加页 `更多 -> 自定义食物` 进入。

自定义食物字段：

1. 食物名称。
2. 分类。
3. 标准份量。
4. 单位。
5. 克重。
6. 热量。
7. 碳水、蛋白质、脂肪。

保存后：

1. 服务端创建 `NutritionFoodItem`。
2. 服务端创建该食物的标准 `NutritionIntake`。
3. 添加页可搜索和复用。

### Q：用户如何添加菜谱？

A：从食物添加页 `更多 -> 自定义菜谱` 进入。

菜谱字段：

1. 菜谱名称，例如 `玉米片配牛奶`。
2. 菜谱分类，例如早餐。
3. 菜谱标准份量。
4. 组成食物列表。
5. 每个食物的默认份量和比例。

保存后：

1. 服务端创建 `NutritionRecipe`。
2. 服务端创建多条 `NutritionRecipeFood`。
3. 服务端按组成食物汇总菜谱标准 `NutritionIntake`。
4. 添加页可作为菜谱项搜索和选择。

### 拍照识别

打开方式：`fullScreenCover`。

入口：食物添加页快捷操作 `相机`。

流程：

```text
点击相机
-> fullScreenCover 打开相机页面
-> 拍摄或选择图片
-> 上传图片并进入识别分析
-> 视觉模型把图片整理为食物描述文本
-> 营养摄入抽取模型把描述文本抽取为结构化草稿
-> 成功：进入餐点总结页
-> 用户确认并记录
-> 保存服务端
-> 失败：展示识别失败页，可重试
```

### AI 识别 Pipeline

第一期饮食识别采用客户端 AI Runtime 编排，服务端 `ai_config` 负责下发模型配置和场景绑定，正式保存仍走服务端饮食记录接口。

场景配置：

| 场景 | 建议 rawValue | 用途 | 模型要求 |
| --- | --- | --- | --- |
| 食物图片描述 | `optimization_visual` | 复用现有视觉内容优化场景，把用户图片整理成可抽取的食物描述文本 | 必须支持视觉输入 |
| 营养摄入抽取 | `nutrition_intake_extraction` | 从食物描述文本或用户自然语言中抽取结构化营养草稿 | 文本结构化模型 |

需要同步的位置：

| 位置 | 改动 |
| --- | --- |
| `SparkService/ai_config/models.py` | `ScenarioKey` 只新增 `nutrition_intake_extraction`；图片描述复用已有 `optimization_visual` |
| `SparkClient/Projects/Core/AI/AIScenario.swift` | `AIScenario` 只新增 `nutritionIntakeExtraction = "nutrition_intake_extraction"`；图片描述复用已有 `.optimizationVisual` |
| `AISettings/AllModels.json` 或服务端模型配置种子 | 确认 `optimization_visual` 绑定可用视觉模型；新增并绑定 `nutrition_intake_extraction` 结构化文本模型 |
| `Prompts.strings` | 增加饮食识别相关 prompt，本地化管理 |

组件职责：

| 组件 | 职责 |
| --- | --- |
| `NutritionPromptFactory` | 从 `Prompts.strings` 读取并组装 prompt，不在 Swift 代码里硬编码大段提示词 |
| `NutritionFoodImageDescriber` | 使用视觉模型生成食物描述文本 |
| `NutritionIntakeStructuredExtractor` | 参考医疗结构化抽取，把文本解码为 `RemoteNutritionRecognitionDraft` |
| `DefaultNutritionRecognitionPipeline` | 编排拍照识别和自然语言识别两条链路 |
| `NutritionRecognitionError` | 统一表达模型不可用、图片质量低、AI 输出无效、JSON 解码失败等错误 |

拍照识别链路：

```text
图片 file_id / 本地图片数据
-> NutritionFoodImageDescriber
-> AIScenario.optimizationVisual
-> 食物描述文本
-> NutritionIntakeStructuredExtractor
-> AIScenario.nutritionIntakeExtraction
-> RemoteNutritionRecognitionDraft
-> 正在分析页结束 loading
-> 识别成功页
```

自然语言识别链路：

```text
用户输入文本
-> NutritionIntakeStructuredExtractor
-> AIScenario.nutritionIntakeExtraction
-> RemoteNutritionRecognitionDraft
-> 确认页
```

说明：

1. 视觉模型只负责“看图描述食物”，不要直接生成最终保存数据。
2. 结构化抽取模型负责统一输出营养草稿，拍照和文本共用同一个抽取组件。
3. 如果视觉场景没有可用模型，拍照识别直接提示“当前缺少可用视觉模型”，不要降级到普通文本模型。
4. 如果营养抽取场景没有可用模型，拍照和手动输入均提示模型不可用。
5. AI 输出必须先经过 JSON 清洗和解码；解码失败可用 retry correction prompt 重试一次。
6. 识别草稿只在客户端确认页展示，不直接创建 `NutritionMealRecord`。

提示词本地化：

| key | 用途 |
| --- | --- |
| `ai.prompt.nutrition.food_description.template` | 视觉模型：根据图片描述食物、份量、烹饪方式、可见配料 |
| `ai.prompt.nutrition.intake_extraction.template` | 文本模型：抽取餐次、食物、份量、热量、三大营养素和不确定项 |
| `ai.prompt.nutrition.extraction.retry_correction.template` | JSON 解码失败后的修正重试 |
| `ai.prompt.nutrition.extraction.not_available` | 无法识别或缺失字段占位 |

提示词要求：

1. 使用项目通用 `Prompts.strings`，至少补齐 `en.lproj`、`zh-Hans.lproj`、`zh-Hant.lproj`。
2. 食物描述 prompt 输出自然语言描述，不要求 JSON。
3. 营养抽取 prompt 输出纯 JSON，不要 Markdown、解释文字或代码块。
4. 抽取 JSON 使用 camelCase key，客户端使用统一 `JSONDecoder.default` 解码。
5. prompt 中需要明确“估算值必须可被用户确认，不确定内容放入 uncertainNotes”。
