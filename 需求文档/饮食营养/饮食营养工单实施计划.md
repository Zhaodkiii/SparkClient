# 饮食营养工单实施计划

> 文档性质：阶段实施工单。本文基于《饮食营养需求讨论文档》《饮食营养数据详设文档》《饮食营养客户端详细设计文档》《饮食营养服务端接口详细设计文档》整理，用于后续按工单拆分开发、联调、测试和验收。

## 一、实施原则

### Q：为什么要按阶段拆？

A：饮食营养同时涉及服务端数据模型、接口、客户端页面、AI 识别、Apple 健康、成员权限和日志本地化。必须先保证“服务端主数据源 + 客户端首页展示 + 保存闭环”稳定，再逐步叠加识别、HealthKit 和高级编辑能力。

核心原则：

1. 服务端是主数据源，Apple 健康是本人健康数据同步目标。
2. 客户端不新增饮食业务本地数据库，不做离线 outbox，只使用项目已有公共请求缓存和临时图片缓存。
3. 服务端 JSON 使用 snake_case，客户端 DTO 使用 camelCase，并统一使用 `JSONEncoder.default` / `JSONDecoder.default`，不要手写 `CodingKeys` / `CodableKey`。
4. 第一阶段优先做最小闭环：看板展示、食物搜索、选择食物、确认保存、详情查看。
5. AI 识别只返回草稿，用户确认前不创建正式饮食记录。
6. 本人成员才读写 Apple 健康；家庭成员只保存服务端。
7. 所有用户可见文案必须本地化；核心链路必须记录结构化日志。

## 四、详细工单

### NUTRITION-000001 服务端 nutrition 模块与基础约定

目标：在 `SparkService` 中建立饮食营养独立业务模块，承载模型、接口、服务和权限逻辑。

实现内容：

1. 新增服务端 app 或模块：建议 `nutrition`，避免继续膨胀 `medical`。
2. 增加模块路由前缀：`/api/v1/nutrition/`。
3. 建立基础目录：`models.py`、`serializers.py`、`views.py`、`services/`、`tests/`。
4. 建立统一 `NutritionBaseModel`：包含 `created_at`、`updated_at`、`is_deleted` 等公共字段。
5. 数据库字段增加 `db_comment`，对齐数据详设文档。
6. 所有接口统一使用项目现有响应结构：`code/msg/data`。
7. 统一 request id、业务日志、错误码。

验收标准：

1. 服务端启动正常，路由注册成功。
2. nutrition 模块不依赖客户端即可完成基础导入。
3. 新增模块具备测试入口。
4. 基础日志中能看到 nutrition 接口 request id。

### NUTRITION-000002 客户端 Nutrition Feature 骨架

目标：在 `SparkClient` 中新增独立 Nutrition Feature，建立 UI、Domain、Application、Infrastructure 边界。

实现内容：

1. 新增目录：`SparkClient/Projects/Features/Nutrition`。
2. 建立子目录：`Domain`、`Application`、`Infrastructure`、`Presentation`。
3. 增加 `NutritionRoute` 与 `NutritionNavigationDestination`。
4. 增加基础页面壳：`NutritionHomeView`、`NutritionHomeViewModel`、`NutritionHomeState`。
5. 增加公共组件目录：`NutritionCardContainer`、`NutritionLoadingStateView`、`NutritionEmptyStateView`。
6. 暂不实现业务缓存，不新增 CoreData 饮食表。
7. 所有用户可见文案接入本地化 key。

验收标准：

1. 首页可通过路由进入空的饮食营养首页。
2. 页面结构与现有项目 SwiftUI 风格一致。
3. 不产生本地业务数据库模型。
4. 基础页面可展示 loading、empty、error 三类状态。

### NUTRITION-000003 服务端饮食营养主数据模型

目标：实现第一期服务端核心模型和迁移。

实现内容：

1. 新增 `NutritionMealRecord`：饮食记录主表。
2. 新增 `NutritionIntake`：营养摄入明细，使用 `business_type` + `business_id` 关联不同业务对象。
3. 新增 `NutritionFoodItem`：系统预置食物和用户自定义食物。
4. 新增 `NutritionFoodFavorite`：账号维度食物/菜谱收藏。
5. 新增 `NutritionMealFood`：餐次食物关联，支持食用比例。
6. 新增 `NutritionRecipe`、`NutritionRecipeFood`：多个食物组合成菜谱。
7. 新增 `NutritionEnergyBurnRecord`：手动能量消耗和 Apple 健康能量消耗同步记录。
8. `apple_health_id` 存在于 `NutritionIntake` 和 `NutritionEnergyBurnRecord`，使用 HealthKit sample UUID。
9. 增加成员权限字段和索引，保证按用户和成员隔离。

验收标准：

1. 迁移可执行，可回滚。
2. 模型字段和数据详设文档一致。
3. 关键字段有索引和 `db_comment`。
4. 软删除和成员权限边界可用。

### NUTRITION-000004 系统预置食物与默认营养目标

目标：服务端提供第一期可用的默认食物和营养目标，支撑客户端首页与搜索。

实现内容：

1. 内置第一期系统食物：Coffee、Banana、Scrambled Eggs、Apple、Strawberries 等。
2. 每个系统食物写入标准份量、热量、碳水、蛋白质、脂肪。
3. `NutritionFoodItem` 增加 `barcode`、`is_verified`、`sort_weight`。
4. 目标值第一期使用服务端默认目标返回。
5. 餐次目标按默认比例返回：早餐、午餐、晚餐、小吃。
6. 暂不做复杂目标设置页。

验收标准：

1. 搜索空关键词或常用列表能返回系统预置食物。
2. 看板接口能返回今日目标和餐次目标。
3. 条形码字段可用于搜索匹配。
4. 客户端不需要本地写死默认目标。

### NUTRITION-000005 看板与餐次查询接口

目标：完成首页、总结、营养、详情页所需查询接口。

实现内容：

1. 实现 `GET /api/v1/nutrition/dashboard/`。
2. 实现 `GET /api/v1/nutrition/meal-records/`。
3. 看板返回 `RemoteNutritionDashboard`。
4. 餐次聚合返回 `RemoteNutritionMealDashboard`，包含热量、碳水、蛋白质、脂肪及目标值。
5. 餐次记录返回 `RemoteMealRecord`、`RemoteMealFood`、`RemoteNutritionIntake`。
6. 支持参数：`member_id`、`date`、`meal_type`、分页或日期范围。
7. 权限校验：当前用户必须具备成员查看权限。

验收标准：

1. 首页可以一次请求拿到总结模块和营养模块数据。
2. 总结详情可按餐次切换展示宏量营养进度。
3. 餐次详情可以加载食物列表和营养明细。
4. 无记录时返回空结构，不返回异常。

### NUTRITION-000006 饮食记录创建、编辑、删除接口

目标：实现用户确认饮食记录后的服务端正式保存闭环。

实现内容：

1. 实现 `POST /api/v1/nutrition/meal-records/`。
2. 实现 `PATCH /api/v1/nutrition/meal-records/{id}/`。
3. 实现 `DELETE /api/v1/nutrition/meal-records/{id}/`。
4. 创建时生成 `NutritionMealRecord`、`NutritionMealFood`、`NutritionIntake`。
5. 选择食物时，根据食物标准营养值乘以食用比例生成实际摄入。
6. 选择菜谱时，按菜谱组成食物展开或保存菜谱来源，并生成实际摄入。
7. AI 草稿确认时可带 `recognition_id`，用于日志串联。
8. 删除第一期采用软删除。

验收标准：

1. 客户端确认保存后能得到正式 `record_id` 和 `intake_id`。
2. 保存后刷新看板，摄入数据立即变化。
3. 删除后看板和餐次详情不再计入该记录。
4. 已写入 Apple 健康的记录编辑/删除能返回必要字段供客户端提示。

### NUTRITION-000007 搜索、条形码、收藏、自定义食物/菜谱接口

目标：支撑食物添加页、搜索页、条形码结果页和用户自定义内容。

实现内容：

1. 实现 `GET /api/v1/nutrition/search/`。
2. 搜索模式支持 `mode=text` 和 `mode=barcode`。
3. 结果使用 `RemoteNutritionSearchResponse` / `RemoteNutritionSearchResult`。
4. 支持筛选：收藏、由我创建、食物、菜谱。
5. 实现 `POST /favorites/` 和 `DELETE /favorites/`。
6. 实现 `POST /food-items/` 创建自定义食物。
7. 实现 `POST /recipes/` 创建自定义菜谱。
8. 搜索结果返回 `is_favorite`、`is_created_by_me`、`is_verified`。

验收标准：

1. 文本搜索能返回食物和菜谱。
2. 条形码有结果时直接复用搜索结果卡片。
3. 条形码无结果时客户端可进入创建项目流程。
4. 收藏是账号维度，不随成员切换变化。
5. 自定义食物/菜谱创建后可搜索到。

### NUTRITION-000022 Apple 健康重复样本幂等导入误报失败修正

目标：修正 Apple 健康能量消耗/营养摄入批量导入接口在“全部或部分样本已存在”时被客户端判定为失败的问题。重复样本属于幂等同步结果，不应触发首页 HealthKit 同步失败日志、错误态或降级流程。

问题现象：

```text
POST /api/v1/nutrition/apple-health/energy-burn-imports/ status=200
body.code=40901
body.msg=duplicate_apple_health_sample
body.data={
  "imported": [],
  "duplicates": [
    { "apple_health_id": "...", "record_id": 1, "duplicate": true }
  ]
}

响应解码成功 type=RemoteAppleHealthImportResponse keys=root=[code,data,msg] data=[duplicates,imported]
HealthKit 同步失败 memberID=10 date=2026-06-18 error=duplicate_apple_health_sample
```

问题分析：

1. HTTP 状态码为 `200`，说明服务端请求处理成功。
2. 响应体 `data` 可被客户端正确解码为 `RemoteAppleHealthImportResponse`，说明不是 DTO 结构问题。
3. 当前失败来自统一响应解码规则：`APIResponseDecoder.decodeWrappedData` 遇到 `code != 0` 会抛出 `SparkNetworkError.httpError`。
4. 服务端将重复 Apple Health sample 返回为 `code=40901` / `msg=duplicate_apple_health_sample`，导致客户端把“幂等重复”误认为“业务失败”。
5. Apple Health 同步是每日/进入首页可重复触发的后台同步链路，重复样本是正常结果，不应该污染用户态失败日志。
6. 如果一次批量导入中同时存在 `imported` 和 `duplicates`，当前只要有 duplicates 就可能返回非 0 code，会把“部分新增成功”也错误标记为失败。

推荐修正口径：

1. 服务端批量导入接口应把重复样本视为幂等成功。
2. `POST /api/v1/nutrition/apple-health/intake-imports/` 和 `POST /api/v1/nutrition/apple-health/energy-burn-imports/` 在重复样本场景下仍返回 `code=0`。
3. `data.imported` 表示本次新写入的数据。
4. `data.duplicates` 表示本次已存在、被跳过的数据。
5. HTTP 状态码建议保持 `200` 或 `201`：
   - 有新增 `imported.count > 0` 时可返回 `201`。
   - 全部重复但处理成功时返回 `200`。
6. `msg` 建议保持 `success`，不要用错误语义的 `duplicate_apple_health_sample` 作为失败原因。
7. 如需保留诊断信息，可在 `data.summary` 或服务端日志中记录 `duplicate_count`，不通过非 0 code 表达。

不推荐方案：

1. 不建议修改全局 `APIResponseDecoder` 允许 `40901`，因为会影响全项目业务错误语义。
2. 不建议在 `NutritionAPI` 里为 Apple Health 导入接口特判 `40901`，因为这会形成接口契约和客户端解码语义不一致。
3. 不建议客户端 catch `duplicate_apple_health_sample` 后吞掉错误作为主方案，因为此时 `APIResponseDecoder` 已把成功响应转成异常，日志和链路语义仍然不干净。

服务端涉及文件：

| 文件/模块 | 改动 |
| --- | --- |
| `SparkService/nutrition/views.py` | Apple Health 导入接口遇到 duplicates 时不再返回非 0 code；统一返回成功结构 |
| `SparkService/nutrition/services/energy_burn_service.py` | 保持 `imported` / `duplicates` 结果结构；必要时补充 summary |
| `SparkService/nutrition/tests/test_apis.py` | 增加重复导入场景测试：全部重复、部分重复、全部新增 |

客户端涉及文件：

| 文件/模块 | 改动 |
| --- | --- |
| `NutritionRemoteModels.swift` | 保持 `RemoteAppleHealthImportResponse` 结构，继续解码 `imported` / `duplicates` |
| `NutritionAPI.swift` | 不新增 40901 特判，继续使用统一 `decodeWrappedData` |
| `NutritionUseCases.swift` | 同步成功日志展示 `samples/imported/duplicates`，重复样本不应进入 catch |

验收标准：

1. 第一次上传 Apple Health 能量消耗样本时，接口返回 `code=0`，客户端日志为同步成功，`imported > 0`。
2. 第二次上传相同 Apple Health 能量消耗样本时，接口返回 `code=0`，客户端日志为同步成功，`duplicates > 0`，不出现 `HealthKit 同步失败`。

### NUTRITION-000014 AI 识别、视觉描述与营养摄入结构化抽取

目标：实现饮食营养 AI 识别草稿能力。拍照场景先使用视觉模型把图片整理为食物描述文本，再使用营养摄入抽取场景把描述文本或用户自然语言输入抽取为结构化草稿；确认前不创建正式饮食记录。

实现内容：

1. 服务端 `ai_config` 只新增营养摄入抽取场景枚举 `nutrition_intake_extraction`，对齐客户端 `AIScenario`。
2. 客户端 `AIScenario` 只新增营养摄入抽取场景；图片描述复用已有 `optimization_visual` 场景。
3. 图片描述使用已有视觉模型场景 `optimization_visual` 处理，不使用普通文本模型硬跑图片输入。
4. 客户端新增饮食提示词：食物图片描述提示词、营养摄入抽取提示词、抽取失败重试修正提示词。
5. 提示词放入项目通用 `Prompts.strings`，按 `en`、`zh-Hans`、`zh-Hant` 本地化管理，不在 Swift 代码里硬编码大段 prompt。
6. 拍照流程：图片 -> 视觉模型 -> 食物描述文本 -> 营养摄入结构化抽取 -> `RemoteNutritionRecognitionDraft`。
7. 自然语言流程：用户输入文本 -> 营养摄入结构化抽取 -> `RemoteNutritionRecognitionDraft`。
8. 参考医疗抽取，创建独立饮食抽取结构化组件，不塞进页面 ViewModel。
9. 服务端不提供识别代理/兜底接口；第一期识别只使用客户端本地 AI Runtime 编排，服务端负责模型配置和正式记录保存。
10. 草稿确认后复用 `POST /meal-records/` 保存正式记录。

建议新增客户端文件：

| 文件 | 职责 |
| --- | --- |
| `NutritionPromptFactory.swift` | 从 `Prompts.strings` 读取并组装食物描述、营养抽取、重试修正 prompt |
| `NutritionFoodImageDescriber.swift` | 使用视觉场景把图片整理为食物描述文本 |
| `NutritionIntakeStructuredExtractor.swift` | 使用营养抽取场景把文本抽取为结构化草稿 |
| `DefaultNutritionRecognitionPipeline.swift` | 编排拍照/文本两条识别链路 |
| `NutritionRecognitionModels.swift` | 定义食物描述结果、抽取中间结果、失败原因 |
| `NutritionRecognitionError.swift` | 识别、解码、重试、模型不可用等错误 |

AI 场景建议：

| 场景 | 用途 | 模型要求 |
| --- | --- | --- |
| `optimization_visual` | 图片转食物描述文本 | 复用现有视觉内容优化场景，必须支持视觉输入 |
| `nutrition_intake_extraction` | 食物描述/自然语言转营养草稿 JSON | 文本结构化模型 |

提示词 key 建议：

| key | 用途 |
| --- | --- |
| `ai.prompt.nutrition.food_description.template` | 视觉模型把图片整理成食物描述文本 |
| `ai.prompt.nutrition.intake_extraction.template` | 从食物描述或用户输入抽取结构化营养草稿 |
| `ai.prompt.nutrition.extraction.retry_correction.template` | JSON 解码失败后的重试修正 |
| `ai.prompt.nutrition.extraction.not_available` | 缺失值占位 |

抽取输出要求：

1. 返回纯 JSON，不要 Markdown、解释文字、代码块。
2. 使用 camelCase key，便于客户端统一解码。
3. 顶层输出 `title`、`mealType`、`confidence`、`overview`、`items`、`intakes`、`uncertainNotes`。
4. 至少输出 `energyKcal`、`proteinG`、`carbohydrateG`、`fatG` 四类核心营养估算。
5. 不确定的食物、份量、烹饪方式写入 `uncertainNotes`，不要编造精确值。
6. 抽取草稿只用于用户确认，不直接保存服务端。

日志要求：

1. 记录识别链路：`recognitionID`、`memberID`、`mealType`、图片 file id、场景名、模型名、耗时。
2. 视觉描述日志只记录描述长度和摘要，不记录完整图片内容。
3. 自然语言日志只记录输入长度，不记录完整用户原文。
4. 解码失败记录错误类型、重试次数和 JSON 摘要。
5. 生产环境不记录完整 prompt 和完整 AI 原始输出。

验收标准：

1. 服务端 `ScenarioKey` 和客户端 `AIScenario` 均具备 `nutrition_intake_extraction` 场景。
2. 未配置视觉模型时，拍照识别展示模型不可用提示，不走错误的文本模型。
3. 拍照后能经过“图片描述 -> 营养抽取”得到草稿或失败态。
4. 自然语言输入能直接得到结构化草稿。
5. 用户可修改草稿再确认。
6. 识别失败可重试，JSON 解码失败可触发一次修正重试。
7. 服务端不在识别阶段创建正式饮食记录。

## 九、风险与注意点

1. 不要把饮食数据落成客户端长期事实源，否则跨设备同步和 Apple 健康去重会变复杂。
2. 不要把食物标准营养值直接写死在客户端，否则系统预置食物和条形码结果无法统一管理。
3. 不要在识别阶段创建正式记录，否则用户取消或修改草稿会污染真实数据。
4. 不要手写 `CodingKeys`，当前项目已有统一 snake_case 和 ISO8601 编解码能力。
5. 不要把 HealthKit 失败当成饮食保存失败；服务端保存成功后记录即成立。
6. 不要让服务端返回用户可见中文文案；客户端负责本地化。
7. 不要在生产日志记录完整图片、自然语言全文或敏感健康明细。
