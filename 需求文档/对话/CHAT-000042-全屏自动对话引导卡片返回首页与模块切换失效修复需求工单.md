## 一、模块目标

修复“进入对话 Tab 后自动全屏打开 ChatView”场景下，系统引导卡片顶部健康数据滑块无法跳转首页的问题。

当前手动进入 ChatView 时，滑块可以沿用消息内 `NavigationLink` 进入 `ChatGuideHomeDestinationView`；但自动进入使用 `SignedInMainTabHostView` 根级 `fullScreenCover`，该宿主构造的 `ChatView` 没有注入 `guideHomeDestinationBuilder`，导致：

```text
SignedInMainTabHostView.chatFullScreenCover
  → ChatView（未传 guideHomeDestinationBuilder）
  → ChatRenderContext.guideHomeDestinationBuilder == nil
  → ChatGuideMessageCardView.homeDestinationBuilder == nil
  → ChatGuideMetricCarouselView 不创建 NavigationLink
  → 滑块仅展示，点击无跳转
```

本工单不采用“只补传一个 builder 就结束”的方案。全屏 Cover 场景的目标行为与普通 push 不同：点击系统引导卡片后，应先关闭 Cover，再切换到首页根 Tab，并进入对应的医疗、饮食或运动模块。

### 1.1 目标行为

- 自动全屏 ChatView 中，系统引导卡片滑块可点击。
- 点击后先关闭当前 `fullScreenCover`，再执行首页/模块路由。
- 医疗/身材类进入健康首页医疗工作台。
- 饮食类进入首页饮食模块。
- 运动类进入首页运动模块。
- 不在 Cover 内继续 push 一个首页页面，不保留两层导航容器。
- 手动 `NavigationDestination` 进入 ChatView 的现有引导卡片行为保持兼容。

### 1.2 非目标

| 项目 | 本工单结论 |
| --- | --- |
| 修改引导卡片数据、HealthKit 数据加载和成员绑定逻辑 | 不做 |
| 修改科普问题生成与发送链路 | 不做 |
| 修改自动进入会话的 5 分钟判断和 Thread 创建逻辑 | 不做 |
| 修改医疗详情快捷对话的上下文注入 | 不做 |
| 删除普通 ChatView 内消息 `NavigationLink` | 不做；普通 push 场景继续保留 |
| 在 fullScreenCover 内再 push 首页模块作为临时修复 | 禁止 |

## 三、全屏自动对话引导卡片跳转改造

### 3.1 需求说明

为 ChatView 增加“引导卡片目标请求”能力。普通 NavigationStack push 场景继续使用原有 `ChatGuideHomeDestinationBuilder`；根级 fullScreenCover 场景使用回调上抛，不在卡片内部创建跨根 Tab 的 `NavigationLink`。

### 3.2 基础要求与业务规则

1. 增加中立的 `ChatGuideHomeNavigationRequest`，至少包含：
   - `category: ChatGuideMetricCategory`
   - `targetModule: medical / nutrition / fitness`
   - `source: automaticFullScreenChat`
   - 可选 `threadID` 与当前 `memberID`，用于日志和恢复
2. `ChatGuideMessageCardView` / `ChatGuideMetricCarouselView` 支持两种互斥模式：
   - `homeDestinationBuilder`：普通 push 场景。
   - `onHomeNavigationRequest`：全屏自动 Chat 场景。
3. 全屏模式下，滑块页面仍保持完整点击区域、无障碍标签和当前分页交互，但点击只发出 request，不创建内部 `NavigationLink`。
4. 不允许同时注入 builder 和 fullScreen request handler 后发生双重响应；必须定义优先级并记录日志。推荐全屏 handler 优先。
5. 普通手动 ChatView 的滑块行为不改变，仍进入现有 `ChatGuideHomeDestinationView`。
6. 引导卡片下方科普问题列表不受本改造影响。

### 3.3 验收标准

- [ ] 自动恢复会话进入全屏 Chat 后，健康数据滑块可点击。
- [ ] 自动新建会话进入全屏 Chat 后，健康数据滑块可点击。
- [ ] 全屏滑块点击只产生一次 navigation request，不 push 第二层首页页面。
- [ ] 普通列表卡片进入的 ChatView 仍沿用原有 `NavigationLink` 模式。
- [ ] VoiceOver 可识别滑块为可打开对应健康模块的控件。
- [ ] 连续快速点击不会产生重复路由或多层 Cover。

### 3.4 技术细节与设计代码位置

- `ChatGuideMessageCardView.swift:1-192`：增加全屏请求回调，并向 `ChatGuideMetricCarouselView` 传递。
- `ChatGuideMetricCarouselView.swift`：在 `sectionPage(_:)` 统一处理 builder/request 两种模式。
- `ChatRenderContext.swift`：增加 `onGuideHomeNavigationRequest`，由消息渲染链路传到卡片。
- `ChatView.swift`：将入口上下文传入 `ChatRenderContext`；普通 push 不传全屏 handler。
- `SignedInMainTabHostView.swift:238-240`：全屏 Chat 构造时注入 handler，不能只补传旧 builder。

## 四、关闭 Cover 后切换首页与目标模块

### 4.1 需求说明

全屏自动 Chat 的引导卡片点击必须采用“请求 → 关闭 Cover → 根路由 → 首页模块定位”的顺序。

```text
点击引导卡片滑块
  ↓
生成 ChatGuideHomeNavigationRequest
  ↓
根宿主记录 pending home intent
  ↓
activeHomeFullScreenCover = nil
  ↓
fullScreenCover.onDismiss
  ↓
AppRouteStore.route(to: .home, replaceStack: true)
  ↓
首页宿主消费 module intent
  ↓
医疗 / 饮食 / 运动模块可见
```

### 4.2 基础要求与业务规则

1. `SignedInMainTabHostView` 持有一次性 `pendingGuideHomeNavigation`，不得由 Chat Feature 直接修改 `selectedTab`。
2. 点击后立即关闭 Cover，但不得在 Cover 仍 presented 时切 Tab。
3. `onDismiss` 只消费一次 intent；普通 heart 返回首页和引导卡片模块跳转不能互相污染。
4. 首页根 Tab 使用 `AppRoute.home` / `AppRouteStore.RootTab.healthHome`，不直接写 raw value `0`。
5. 目标模块映射必须集中定义：

| 引导卡片类别 | dashboard 首页样式 | classic 首页样式 |
| --- | --- | --- |
| medical | `.healthHome` + `HomeSection.dashboard` | `.healthHome`，进入医疗健康首页 |
| bodyManagement | `.healthHome` + `HomeSection.dashboard` | `.healthHome`，进入医疗健康首页 |
| nutrition | `.healthHome` + `HomeSection.nutrition` | `.nutrition` 根 Tab |
| movement | `.healthHome` + `HomeSection.fitness` | `.fitness` 根 Tab |

6. dashboard 样式通过 `HomeSectionPreferenceStore.shared.section` 或等价的首页 intent 设置内部 Section；不得把 `HomeSection.nutrition` 当作 `RootTab.nutrition` 使用。
7. classic 样式若饮食/运动是独立 RootTab，则路由到对应可见 RootTab；若产品最终要求强制 `.healthHome = 0`，需在首页内部提供可消费的模块 intent，不能路由到不可见 Section。
8. 医疗类别不应进入饮食或运动根 Tab；必须落在健康首页医疗工作台。
9. module intent 消费后立即清理，避免下次进入首页再次跳转。
10. 账号切换、无效类别、Cover 被系统取消时清理 pending intent。

### 4.3 验收标准

- [ ] fullScreenCover 自动 Chat 点击医疗滑块：Cover 关闭后进入健康首页医疗模块。
- [ ] fullScreenCover 自动 Chat 点击饮食滑块：dashboard 样式进入首页饮食 Section，classic 样式进入饮食 RootTab。
- [ ] fullScreenCover 自动 Chat 点击运动滑块：dashboard 样式进入首页运动 Section，classic 样式进入运动 RootTab。
- [ ] 关闭动画完成前不切换 Tab。
- [ ] 首页没有残留 ChatView、重复 NavigationStack 或重复 Cover。
- [ ] 手动 push ChatView 的滑块仍按旧逻辑打开对应页面。
- [ ] 连续执行“自动全屏 → 滑块跳转 → 返回对话 → 再次进入”不会重复消费上一次 intent。

### 4.4 技术细节与设计代码位置

- `SignedInMainTabHostView.swift`：增加全屏引导请求处理、pending intent、`fullScreenCover.onDismiss` 分支。
- `AppRouteStore.swift:61`：`.healthHome = 0` 的类型化根 Tab，不允许业务层直接写 raw value。
- `IOS26HomeView.swift:120-144`：dashboard/nutrition/fitness 首页内部分页真实映射。
- `HomeSectionPreferenceStore.swift`：首页 Section 的持久化/运行时状态入口。
- `IOS26TabBarView.swift`、`MainTabCoordinatorView.swift`：消费首页模块 intent，并确保两种宿主行为一致。
- 建议新增 `HomeNavigationIntent` 或 `ChatGuideHomeNavigationCoordinator`，避免由 NotificationCenter 传递无类型字符串。

## 五、状态模型

| 状态 | 进入条件 | 用户可见结果 | 退出条件 |
| --- | --- | --- | --- |
| `automaticChatPresenting` | 自动 Thread 已准备，根 Cover 非空 | 全屏 Chat + heart | 关闭、系统取消、卡片点击 |
| `guideHomeRequesting` | 卡片滑块点击 | Cover 开始关闭 | request 已记录 |
| `guideHomeDismissing` | pending intent 非空且 Cover 正在 dismiss | 仍显示关闭动画 | `onDismiss` |
| `routingHome` | Cover 已完全关闭 | 根 Tab 切换到首页/目标模块 | route 完成 |
| `homeIntentConsuming` | 首页宿主已收到 module intent | 医疗/饮食/运动模块可见 | intent 清理 |
| `manualChatPushed` | 普通列表/手动新建 ChatView push | ChatView + 系统返回 | 返回列表 |
| `failed` | 路由或首页模块不可用 | 保留首页或对话列表并记录错误 | 重试/重新进入 |

互斥约束：

- `guideHomeRequesting` 与普通手动 Chat push 不同时存在。
- `pendingGuideHomeNavigation` 只能由全屏自动 Chat 的卡片点击产生。
- `onDismiss` 之前不得修改 `selectedTab`。
- 同一 request ID 只能消费一次。

## 六、数据与持久化

| 数据 | 所有者 | 持久化 | 清理时机 |
| --- | --- | --- | --- |
| 引导卡片类别 | `ChatGuideMetricCategory` | 不持久化 | request 完成 |
| Chat Guide navigation request | 根宿主/协调器 | 不持久化 | onDismiss 消费或取消 |
| 根 Tab 选中态 | `AppRouteStore` | `RootTabPreferenceStore` | 下次 Tab 变更 |
| 首页内部 Section | `HomeSectionPreferenceStore` | 现有首页偏好存储 | 账号/偏好切换 |

## 七、错误、取消与恢复

| 场景 | 处理 |
| --- | --- |
| builder 缺失 | 全屏场景必须使用 request handler；普通 push 可降级纯展示并记录日志 |
| Cover 正在关闭时再次点击 | 忽略重复点击，保留首个 request |
| onDismiss 未触发 | 不切 Tab；记录宿主状态，避免提前路由 |
| 目标模块不可见 | 按当前布局选择 `.healthHome` 或可见的 nutrition/fitness RootTab |
| 账号切换 | 清理 Cover、pending intent、模块 intent |
| 系统交互取消 dismiss | 清理未提交的 intent，留在当前 Chat；不误切首页 |
| 首页路由失败 | 保留当前 Tab，记录错误，不创建第二个 ChatView |

## 十一、当前实现、缺口与演进

### 当前实现

- 引导卡片和滑块已经支持普通 `NavigationLink` builder。
- 首页模块类别映射已经存在于 `ChatGuideMetricCategory.guideHomeModule`。
- App 根宿主已经统一持有自动 Chat 的 `fullScreenCover` 和 dismiss 时序。
- `AppRouteStore` 已提供类型化根 Tab 路由。

### 当前缺口

1. 根宿主全屏 `ChatView` 未传 `guideHomeDestinationBuilder`，导致滑块无点击响应。
2. 现有 builder 是 push 页面模型，不能表达“关闭 Cover 后切根 Tab/Section”。
3. Chat 渲染上下文没有全屏引导卡片 request handler。
4. 首页 Section 与 RootTab 的切换没有统一的一次性 intent 协议。
5. 缺少自动全屏场景的 UI 测试和 dismiss 时序测试。

### 建议实施顺序

1. 定义 `ChatGuideHomeNavigationRequest` 与类别到模块映射。
2. 扩展 ChatRenderContext、引导卡片和滑块的 request 回调。
3. 在 `SignedInMainTabHostView` 注入全屏 handler，并在 dismiss 后消费 intent。
4. 接入 `AppRouteStore` 和首页 Section/RootTab 目标映射。
5. 补齐 iOS 26/经典宿主、账号切换、重复点击和系统取消测试。
