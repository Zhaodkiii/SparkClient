# CHAT-000009 P1 能力与工具分层与副作用外置需求工单

## 工单状态

已实现（2026-08-05）。

## 1. 背景

### Q：这张 P1 工单要解决什么问题？

A：在 P0 把 AI 主干统一到 `AIRuntimeService` 之后，下一步最重要的是把**能力层**和**工具层**真正拆开，并把副作用从 Runtime 核心里外置出去。

当前 `SparkClient` 虽然已经有雏形，但还存在几个偏差：

1. 聊天、问报告、知识、医疗抽取等“做什么”的决策，还没有完全被显式建模成 capability。
2. 健康读取、成员选择、问用户、知识检索等“怎么做”的动作已经有 ToolHub，但能力边界仍然有重叠。
3. 工具执行后的 UI 副作用虽然已经部分经 `MessageRunActor` 串行落库，但工具层仍然承担了过多上下文和策略判断。

这张 P1 工单要对齐 DeepTutor 的核心思想：

- `Capability = 做什么`
- `Tool = 怎么做`

并把“副作用”从 Runtime 主体里拔出去，交给专门的协调与落库链路。

### Q：为什么要参考 DeepTutor？

A：DeepTutor 的价值在于它把三件事分得比较清楚：

1. capability 负责任务编排
2. tool 负责原子执行
3. stream / side effect 负责把结果回传和落库

SparkClient 现在已经有一部分这种结构，但还没有完全收口成硬边界。P1 的目标就是把这条线明确下来。

## 2. 一句话目标

### Q：一句话需求是什么？

A：把 SparkClient 的 AI 系统从“统一 Runtime 主干”进一步推进到“能力层和工具层分离”，并把工具副作用从 Runtime 核心中外置出来，形成：

1. capability 只决定策略和任务
2. tool 只负责执行原子动作
3. side effect 只负责把工具结果安全地写入消息 / UI / 状态投影

## 3. P1 范围

### Q：P1 只做什么？

A：P1 只做以下三件事：

1. 把聊天、问报告、健康抽取等显式收敛为 capability
2. 把健康读取、知识检索、问用户、成员选择等收敛为 tool
3. 把工具执行后的副作用从 Runtime 核心里外置出去

### Q：P1 不做什么？

A：以下内容不在 P1 范围内：

1. 不重做 AI 主干统一协议
2. 不重做模型选择逻辑
3. 不重做 UI
4. 不重做知识库/RAG 具体实现
5. 不重做所有 tool 的业务实现

P1 只解决分层，不解决所有细节重写。

#### 4.1 capability 语义还不够显式

当前代码里，很多“能力层”的意图是存在的，但更多是通过布尔开关和上下文参数表达，而不是明确的 capability 策略对象。

现状相关位置：

2. `allowedToolNames` 由聊天发送链路动态拼装，但还没有成为明确的 capability policy 产物。
3. 新增能力时，容易继续往这些开关里塞逻辑，导致策略扩散。

#### 4.2 工具层还承担了部分策略与交互边界

当前 `ToolHub` 已经很接近工具层，但它仍然承担了较多职责：

- 工具 schema
- 调试路由
- Consent

- [ToolHubTaskModels.swift](/Users/hua/Documents/project/Reference/LookHealthClient/SparkClient/SparkClient/Projects/Core/AIRuntime/ToolHub/ToolHubTaskModels.swift)

偏差表现：

1. `ToolHub` 既像执行器，又像路由器，又像部分交互协调器。

虽然项目里已经有 `MessageRunActor` 和 `ToolSideEffectBlockMapper`，但从整体架构上看，工具执行后的副作用链路还没有完全被当作独立层来看待。

3. 未来如果不收口，会再次变成“工具层同时理解业务、UI、落库和权限”的混合层。

## 5. 目标架构

### Q：P1 的目标态长什么样？

A：目标架构建议是三层：

```text
Capability Layer
  → 决定“做什么”
  → 聊天、问报告、健康抽取、知识问答、任务生成

Tool Layer
  → 决定“怎么做”
  → 健康读取、知识检索、问用户、成员选择、记忆读写

Side Effect Layer
  → 决定“结果怎么写回系统”
  → MessageRunActor、UI 投影、审计、卡片落库
```

### Q：三层分别应该承担什么？

A：

#### Capability Layer

负责：

1. 选择当前任务类型
2. 决定工具白名单
3. 决定是否允许工具
4. 决定是否进入多轮 tool loop
5. 决定当前业务要产出什么类型的结果

#### Tool Layer

负责：

1. 工具 schema
2. 工具参数解析
3. 工具执行
4. Consent
5. 审计

#### Side Effect Layer

负责：

1. 把工具结果转换成消息块或 UI 事件
2. 串行写入
3. 控制幂等
4. 控制落库时机
5. 保证 UI 不直接依赖工具执行内部状态

## 8. 副作用外置

### Q：什么叫“把副作用从 Runtime 里拔出去”？

A：意思不是“不要副作用”，而是把副作用从 `ToolHub` 和 `ChatOrchestrator` 的核心职责里拿出去，放到专门的副作用层处理。

当前应该继续保留并强化的外置链路是：

```text
ToolHub
  → 产出 ToolExecutionResult / ToolSideEffect
  ↓
MessageRunActor
  → 串行写入 message blocks / UI projection
  ↓
ToolInteractionCoordinator / Presentation
  → 只负责用户交互，不参与工具执行
```

## 9. 需要替代和去除的现有写法

### Q：这次要替代哪些代码模式？

A：以下模式需要替代成 capability / tool / side effect 三层结构：

| 现有模式 | 目标模式 | 说明 |
| --- | --- | --- |
| `useTools` / `useKnowledgeBag` / `useWebSearch` 作为分散布尔开关 | capability policy | 能力策略应统一表达 |
| `allowedToolNames` 在发送链路里手工拼装 | capability 输出白名单 | 白名单应由 capability 产出 |

| feature 自己判断“这是哪种能力” | capability strategy | 判断逻辑不要散落 |

### Q：哪些代码应逐步去除或禁止回流？

A：以下写法应该被长期禁止：

1. 在 Feature 层直接拼工具 schema
2. 在 ViewModel 里决定某个 tool 属于哪种 capability
3. 在 ToolHub 里加入新的业务能力判断
4. 在聊天编排外复制工具循环
5. 在工具执行函数内部直接触碰 UI 表现层

## 10. 新的流程应该怎么走

### Q：P1 的新流程是什么？

A：推荐流程如下：

```text
1. UI / Feature 选择能力
2. capability policy 组装本轮策略
3. ChatOrchestrator 或任务入口接收 capability
4. Runtime 统一生成请求并进入 AIRuntimeService
5. 模型返回 tool_calls
6. ToolHub 执行工具
7. ToolHub 产出 ToolExecutionResult / ToolSideEffect
8. MessageRunActor 串行处理副作用
9. UI 通过消息投影和交互队列展示结果
```

### Q：不同能力怎么进同一条链路？

A：

- 聊天 capability：走 `ChatOrchestrator`
- 问报告 capability：走 report-specific capability policy，但仍复用 `AIRuntimeService`
- 医疗抽取 capability：走单次任务型 capability policy
- 知识处理 capability：走知识处理 capability policy

它们可以在入口上不同，但在 Runtime 主干上必须统一。

## 12. 落地顺序

### Q：P1 建议怎么推进？

A：建议按下面顺序推进：

1. **先显式化 capability**
   - 给聊天、问报告、医疗抽取、知识处理、任务生成定义统一策略入口

2. **再收口 tool**
   - 健康读取、知识检索、问用户、成员选择、记忆读写明确留在 ToolHub

3. **再外置副作用**
   - 工具执行后统一经 `ToolSideEffect` / `MessageRunActor` 落库

4. **最后补门禁**
   - 禁止 capability 判断继续下沉到 tool
   - 禁止 tool 继续承载 UI 和业务编排

### Q：P1 不建议做什么？

A：不建议在 P1 里做以下扩张：

1. 不要一次性把所有 feature 都改成新的 capability 类
2. 不要把 ToolHub 拆成很多过细的小对象，先把边界理清
3. 不要把 side effect 再塞回 Runtime 核心
4. 不要把 UI 交互逻辑搬进 ToolHub
