## 一、模块目标

将健康资源详情页“快捷进入对话”的 Thread 决策从“每次都创建全新对话”调整为：

1. 优先查找当前账号下、当前健康资源所属成员对应的、最近 5 分钟内活跃的 Chat Thread。
2. 命中后直接复用该 Thread，将当前健康资源追加到该 Thread 的 Composer 预览区，再全屏打开该对话。
3. 没有符合条件的活跃 Thread 时，才进入现有“检查可用模型 → 必要时引导设置 API Key → 创建新 Thread → 注入资源 → 打开对话”流程。
4. 不自动发送、不清空原草稿、不覆盖原有健康资源引用。

目标决策如下：

```text
用户在健康资源详情点击快捷对话
  ↓
校验 resourceID / memberID / resourceType
  ↓
查找同成员 5 分钟内最近活跃 Chat Thread
  ├── 命中
  │     ↓
  │   向现有草稿追加当前 HealthResourceRef
  │     ↓
  │   打开该 Thread
  │
  └── 未命中
        ↓
      进入现有创建新对话流程
        ↓
      模型检查 → API Key 设置恢复 → 新建 Thread → 注入资源 → 打开
```

### 1.1 用户价值

- 用户连续查看多份健康资料并提问时，不会在短时间内产生大量碎片化空会话。
- 5 分钟内的连续操作自然汇入同一段对话，保留问题上下文和此前已选择的健康资料。
- 家庭多成员场景下仍保持严格成员隔离，不会把甲成员资料加入乙成员会话。
- 超过活跃时窗后仍创建新对话，避免把时间跨度较大的新问题无意追加到旧上下文。

### 1.2 范围与非目标

| 项目 | 本期结论 |
| --- | --- |
| 5 分钟内同成员活跃 Thread 复用 | 必须 |
| 无命中时沿用现有新建流程 | 必须 |
| 病历、体检、检查、处方、用药计划、药箱统一生效 | 必须 |
| 复用时追加资源预览 | 必须 |
| 复用时保留原文本、附件和健康资源引用 | 必须 |
| 跨成员复用 | 禁止 |
| 自动改绑无成员或其他成员 Thread | 不做 |
| 自动发送提问 | 不做 |
| 修改服务端 API | 默认不需要 |
| 修改 5 分钟为用户可配置 | 不做 |
| 合并或删除已有 Thread | 不做 |
| 改变对话 Tab 的自动进入规则 | 不做；只共用底层选择规则 |

## 三、5 分钟活跃 Thread 选择

### 需求说明

收到健康资源快捷对话请求后，先调用公共最近活跃会话选择能力。产品规则等价于：

```swift
mostRecentActiveThreadID(within: 5 * 60, memberID: request.identity.memberID)
```

若实现希望保留现有 `mostRecentActiveThreadID(within:)` 签名，可通过选择条件对象或重载增加成员约束，但不得在健康资源编排器内复制一份不同语义的 5 分钟算法。

### 基础要求与业务规则

1. 时窗固定为 `5 * 60` 秒，使用 `TimeInterval` 常量集中定义，不在多个页面散落 magic number。
2. 判定截止时间为 `now - interval`，`latestMessageAt >= cutoff` 视为命中；恰好 5 分钟边界应包含。
3. 活跃时间沿用 `ChatThreadListItem.latestMessageAt`。
4. 当前映射事实为：存在消息时使用最新消息 `createdAt`；无消息时使用 `ChatThread.updatedAt`。
5. 候选 Thread 必须满足 `thread.scenario == .chat`。
6. 候选 Thread 必须满足 `thread.isDeleted == false` 且 `deletedAt == nil`。
7. 候选 Thread 必须满足 `thread.memberID == request.identity.memberID`。
8. `thread.memberID == nil` 不视为同成员，不自动改绑，直接跳过。
9. 其他成员 Thread 即使在 1 秒前刚活跃，也必须跳过。
10. 多个候选命中时按 `latestMessageAt` 取最大值；不要只依赖当前数组碰巧已经排序。
11. 时间比较注入 `now` 或时钟依赖，单元测试不得依赖真实等待。
12. 账号边界由当前账号级 `ChatStateStore.threadItems` 保证；退出登录或账号切换后不得读取前一账号缓存。
13. 如果 Thread 列表尚未完成本地加载，先执行已有本地加载/重载能力，再选择，不能因为列表暂时为空直接误建新 Thread。
14. 本期不为命中选择请求远端全量列表；以当前账号本地持久化列表为即时事实源，现有同步机制继续后台刷新。

### 验收标准

- [ ] 同成员 Thread 在 4 分 59 秒前活跃时被复用。
- [ ] 同成员 Thread 恰好在 5 分钟边界时被复用。
- [ ] 同成员 Thread 超过 5 分钟时不复用。
- [ ] 其他成员的更新 Thread 不会遮挡更早但仍在时窗内的同成员 Thread。
- [ ] 无成员 Thread 不会被自动改绑或复用。
- [ ] 已删除或非 `.chat` 场景 Thread 不会命中。
- [ ] 多个同成员候选时始终选择 `latestMessageAt` 最大者。
- [ ] 空 Thread 在 `updatedAt` 仍处于 5 分钟内时，按当前列表语义可被复用。

### 技术细节与设计代码位置

- 当前私有实现：`SparkClient/Projects/Features/Chat/Presentation/ChatConversationListPage.swift` 的 `mostRecentActiveThreadID(within:)`。
- 列表读模型：`SparkClient/Projects/Features/Chat/Domain/ChatMessage/ChatMessage.swift` 的 `ChatThreadListItem`。
- 时间映射：`SparkClient/Projects/Features/Chat/Infrastructure/CoreDataChatStore.swift`，当前为 `latestMessage?.createdAt ?? thread.updatedAt`。
- 建议将规则提取为 Chat 模块的纯选择器或 `ChatStateStore` 查询方法，并同时让 `ChatConversationListPage` 使用，防止两套 5 分钟定义漂移。
- 选择器建议输入：`threadItems`、`interval`、可选 `memberID`、`now`；输出 `UUID?` 或完整 `ChatThreadListItem?`。

## 四、命中活跃 Thread 后复用并追加资源

### 需求说明

命中最近活跃 Thread 后，不创建新 Thread。编排器直接把本次健康资源转换为 `HealthResourceRef`，追加到目标 Thread 的 `ChatComposerDraft.pendingHealthResourceRefs`，选中并打开该 Thread。

### 基础要求与业务规则

1. 复用路径不得调用 `CreateThreadUseCase`，不得产生新 Thread 记录或“新建 Thread”同步事件。
2. 复用路径不得调用 `markThreadAsNewlyCreated`，避免错误触发新会话 guide card 初始化。
3. 使用现有 `ChatStateStore.appendHealthResourceRefs(_:for:)`，保持 canonical identity 去重和数量上限规则。
4. 当前 Thread 已包含同一 `resourceType + resourceID + memberID` 时不重复加入。
5. 当前 Thread 已有文本草稿时保留原文本；不得清空、替换或自动拼接提问。
6. 当前 Thread 已有图片/文件附件时保留原附件。
7. 当前 Thread 已有其他同成员健康资源时保留，并追加当前资源；达到现有最多 5 个资源上限时必须返回明确结果，不能静默显示为成功但未加入。
8. 若同一资源已存在，允许直接打开 Thread，并将结果标记为 `reusedExistingReference` 或等价可观测状态。
9. 注入后必须再次校验目标 Thread 成员与资源成员一致、草稿中存在目标 ref。
10. 复用既有 Thread 时不改标题、图标、置顶状态、模型参数、角色提示词和图片传递模式。
11. 复用既有 Thread 时不自动加载并发送 AI 请求；打开后由用户决定是否输入和发送。
12. 打开前调用现有选择/消息准备能力，确保全屏 Chat 展示正确 Thread 并滚动到最新消息。
13. 同一请求连点或页面重复发通知时必须幂等；同一时刻最多执行一次 prepare。
14. 复用成功日志记录 `decision=reuse`、source、resource type/id、memberID、thread 短 ID 和活跃间隔，不记录诊断摘要、处方内容或 API Key。

### 验收标准

- [ ] 命中活跃 Thread 后 Thread 总数不增加。
- [ ] 当前资源进入原 Thread 的输入框上方预览区。
- [ ] 原有文本、附件和同成员健康资源均保留。
- [ ] 同一资源连续点击不会出现两张重复预览卡。
- [ ] 复用不会触发新会话 guide card 或重置 Thread 参数。
- [ ] 复用后全屏打开的 threadID 与命中的 Thread 一致。
- [ ] 达到健康资源上限时给出用户可理解提示，原 Thread 不受损。

### 技术细节与设计代码位置

- 主编排：`SparkClient/Projects/Features/Chat/Application/HealthResourceConversationCoordinator.swift`。
- 草稿追加：`SparkClient/Projects/Features/Chat/Presentation/ChatStateStore.swift`。
- 资源引用：`SparkClient/Projects/Features/Chat/Domain/HealthResourceRef.swift`。
- 全屏展示：`SparkClient/Projects/App/Sources/App/SignedInMainTabHostView.swift`。
- 当前编排结果只有 `ready / requiresAISettings / failed`；建议让日志或内部决策结果区分 `.reused` 与 `.created`，UI 可继续统一消费 `ready(threadID)`。

## 五、无活跃 Thread 时回退现有新建流程

### 需求说明

没有符合条件的 5 分钟活跃 Thread 时，不自行发明第二套新建逻辑，直接进入 CHAT-000037 已有创建流程。

### 基础要求与业务规则

1. 未命中候选后才调用 `ChatDetailViewModel.hasAvailableChatModel()`。
2. 无可用模型时返回 `.requiresAISettings`，不先创建空 Thread。
3. 用户在 API Key 设置页完成配置并关闭后，重新执行完整 prepare：先再次查找 5 分钟活跃 Thread，再决定复用或新建。
4. 设置期间若另一个入口已产生符合条件的同成员活跃 Thread，恢复时应复用它，不强制沿用先前“未命中”的旧结论。
5. 模型可用时调用 `ChatListViewModel.createThread(memberID:title:)`，显式绑定资源所属成员。
6. 新 Thread 创建后注入当前健康资源并验证成员/草稿一致性。
7. 新建路径继续调用 `markThreadAsNewlyCreated`，保持已有新会话初始化语义。
8. 创建后注入失败时，允许删除本次新建的空 Thread 作为补偿。
9. 新建成功日志标记 `decision=create`，与复用路径区分。
10. 因列表加载、请求并发或临界时间变化造成的候选结果变化，以真正执行注入前最后一次有效判断为准。

### 验收标准

- [ ] 没有同成员 5 分钟活跃 Thread 时创建且只创建一个新 Thread。
- [ ] 只有其他成员活跃 Thread 时走新建流程。
- [ ] 无模型时不创建 Thread，并进入现有 API Key 设置流程。
- [ ] 设置完成恢复时会重新选择，不使用过期候选快照。
- [ ] 新 Thread 绑定当前资源成员并带入预览。
- [ ] 新建后注入失败不会留下不可理解的空 Thread。

### 技术细节与设计代码位置

- 当前新建逻辑：`HealthResourceConversationCoordinator.prepare(_:)`。
- 显式成员创建：`ChatListViewModel.createThread(memberID:title:)`。
- 设置呈现与恢复：`SignedInMainTabHostView` 的 `.apiKeysSettings` HomeSheet 和 `preparePendingHealthResourceConversation()`。
- 实施时建议将编排拆成“validate → selectReusableThread → prepareExisting / prepareNew”三个私有阶段，避免嵌套条件难以测试。

## 六、成员、账号与上下文安全

### 需求说明

5 分钟复用不能削弱健康资源现有的成员隔离规则。Thread 历史消息、Composer 草稿和健康资源必须属于同一成员上下文。

### 基础要求与业务规则

1. 健康资源 `request.identity.memberID` 是复用选择的权威成员来源。
2. 不以首页当前选中成员代替资源成员。
3. 只允许 `thread.memberID == resource.memberID` 的精确匹配。
4. 禁止为复用而调用 `updateThreadMemberBinding` 修改现有 Thread 成员。
5. 禁止把无成员 Thread 自动绑定为资源成员，即使 Thread 没有消息；如未来需要该能力应另立工单并定义空会话判定。
6. 账号切换或退出登录期间取消尚未完成的 prepare，并清理 pending request。
7. 资源详情页离开后已经开始的合法请求可继续完成；但宿主销毁或账号变化后不得打开旧账号 Cover。
8. `HealthResourceSendValidator` 继续作为发送前第二道校验，不能因为选择阶段已过滤就移除。
9. 不在日志、埋点或错误信息打印健康资源正文、诊断、检查结果、处方和用药说明。

### 验收标准

- [ ] 家庭成员 A 的资料不会进入成员 B 的 5 分钟活跃 Thread。
- [ ] 首页当前选中 B、从 A 的详情点击时仍只匹配 A。
- [ ] 无成员 Thread 不被静默改绑。
- [ ] 账号切换期间不会打开上一账号 Thread。
- [ ] 发送前成员不一致仍被验证器阻止。

### 技术细节与设计代码位置

- canonical identity：`Projects/Core/HealthResource/HealthResourceIdentity.swift`。
- Thread 成员：`Projects/Core/Domain/Entities/ChatThread.swift`。
- 发送校验：`Projects/Features/Chat/Application/HealthResourceSendValidator.swift`。
- 账号级状态：`Projects/Features/Chat/Presentation/ChatStateStore.swift` 与 Chat Repository 的 owner account 隔离。

## 七、并发、幂等与失败恢复

### 需求说明

快捷入口可能被快速连点、多个详情页连续触发，或在 API Key Sheet 关闭时再次恢复。选择、注入和展示必须作为一次可控编排处理。

### 基础要求与业务规则

1. 宿主已有 `isPreparingHealthResourceConversation` 时，新请求不得并行创建或注入。
2. 应为每次请求保留 request token；相同 token 重复投递只消费一次。
3. 若产品选择“忙时忽略新请求”，必须记录 ignored 日志；若选择“最后一次覆盖”，必须明确取消前一个尚未产生副作用的请求。首期建议保持单请求、忙时忽略现状。
4. 复用路径在修改草稿前保存目标 Thread 的草稿快照或至少保存新增 ref identity。
5. 复用注入后验证失败，只移除本次新增 ref；不得删除既有 Thread、清空整个草稿或移除原有资源。
6. 新建路径失败可删除本次新 Thread，但删除前必须确认它由本次请求创建。
7. Cover 展示失败或用户立刻关闭，不回滚已经加入的草稿资源；用户再次进入 Thread 仍可继续编辑。
8. API Key 设置取消时清理 pending request，不进入新建或复用。
9. App 进入后台不应重新计算时窗并重复注入；同一次 prepare 的候选结果在原子阶段内保持稳定。
10. 若候选 Thread 在选择后、注入前被删除，重新选择一次；仍无候选则进入新建流程。

### 验收标准

- [ ] 快速点击 5 次不会创建 5 个 Thread 或追加 5 份资源。
- [ ] 复用失败不会删除既有 Thread。
- [ ] 新建失败只补偿本次创建的 Thread。
- [ ] 候选并发删除时可重新选择或安全回退新建。
- [ ] 取消 API Key 设置不会在后台继续创建对话。
- [ ] Cover 关闭后草稿资源仍保留。

### 技术细节与设计代码位置

- 宿主防重入：`SignedInMainTabHostView.isPreparingHealthResourceConversation`。
- pending request：`SignedInMainTabHostView.pendingHealthResourceConversationRequest`。
- 草稿去重与变更：`ChatStateStore.appendHealthResourceRefs`、`composerDraft(for:)`。
- 当前协调器新建失败补偿：`HealthResourceConversationCoordinator.prepare(_:)`。

## 八、整体业务流程

```text
详情页点击快捷对话
  ↓
HealthResourceConversationButton 发布 request
  ↓
SignedInMainTabHostView 接收并防重入
  ↓
HealthResourceConversationCoordinator.prepare
  ↓
请求合法性校验
  ├── 失败 → 提示，结束
  └── 成功
        ↓
      确保本地 Thread 列表已加载
        ↓
      mostRecentActiveThreadID(
        within: 5 * 60,
        memberID: resource.memberID
      )
        ├── 命中同成员 Thread
        │     ↓
        │   构造 HealthResourceRef
        │     ↓
        │   去重追加到现有 Composer 草稿
        │     ↓
        │   验证 Thread member + ref
        │     ├── 失败 → 仅回滚本次 ref，提示
        │     └── 成功 → ready(existingThreadID)
        │
        └── 未命中
              ↓
            hasAvailableChatModel
              ├── 无模型 → requiresAISettings
              │              ↓
              │            设置关闭后从选择阶段重试
              └── 有模型
                    ↓
                  显式 memberID 创建 Thread
                    ↓
                  追加并验证 ref
                    ├── 失败 → 删除本次新 Thread，提示
                    └── 成功 → ready(newThreadID)
  ↓
SignedInMainTabHostView fullScreenCover 打开 ChatView
```

## 九、状态模型

### 9.1 编排状态

| 状态 | 含义 | 用户可见结果 |
| --- | --- | --- |
| `idle` | 无请求 | 停留详情页 |
| `validating` | 校验资源身份 | 快捷按钮防重复触发 |
| `loadingThreads` | 确保本地 Thread 列表可用于选择 | 短暂加载 |
| `selectingRecentThread` | 按 5 分钟及成员规则选择 | 无中间页面 |
| `preparingExisting` | 向命中 Thread 追加 ref | 准备打开 |
| `checkingModel` | 无候选，检查新建所需模型 | 无中间页面 |
| `requiresAISettings` | 无可用模型 | 弹出提示，可进入 API Key 设置 |
| `creatingThread` | 创建显式成员新 Thread | 准备打开 |
| `readyExisting` | 既有 Thread 已准备 | 打开全屏 Chat |
| `readyNew` | 新 Thread 已准备 | 打开全屏 Chat |
| `failed` | 选择、注入或创建失败 | 保持原详情页并提示 |
| `cancelled` | 用户取消设置或账号状态变化 | 不打开 Chat |

### 9.2 状态约束

- `readyExisting` 不得伴随新建 Thread 标记。
- `readyNew` 必须有本次创建记录和显式成员绑定。
- `requiresAISettings` 只能出现在未命中可复用 Thread 的新建分支。
- `failed` 必须完成与分支相匹配的最小补偿。
- 同一时刻最多一个请求处于非终态。

## 十、数据与持久化

| 数据 | 归属 | 持久化 | 本工单处理 |
| --- | --- | --- | --- |
| `ChatThread` | Chat Repository | Core Data + 同步 | 查询、复用或创建 |
| `ChatThreadListItem.latestMessageAt` | Chat 列表读模型 | 由 Thread/Message 映射 | 作为活跃时间事实源 |
| `HealthResourceConversationRequest` | 瞬时跨模块请求 | 不持久化 | 编排结束或取消后清理 |
| `HealthResourceRef` | Composer 草稿/消息引用 | 草稿随现有机制管理 | 去重追加 |
| Composer 文本与附件 | `ChatStateStore` | 按现有草稿机制 | 复用时完整保留 |
| request token | App 宿主/编排器 | 进程内 | 防止重复消费 |
| 5 分钟常量 | Chat 选择策略 | 代码常量 | 单一事实源 |

本工单不新增服务端字段，不把“最后从健康详情进入时间”写入 Thread。活跃判断继续基于统一 `latestMessageAt`，避免形成只对快捷入口有效的第二套时间轴。

## 十一、错误模型

| 错误 | 分支 | 用户结果 | 恢复/补偿 |
| --- | --- | --- | --- |
| 资源 ID、成员 ID 或类型无效 | 校验 | 提示无法开启对话 | 不修改 Thread/草稿 |
| Thread 列表加载失败 | 选择前 | 提示稍后重试 | 不盲目创建，允许重试 |
| 候选 Thread 被并发删除 | 复用 | 重新选择一次 | 无候选则回退新建 |
| 候选成员不一致 | 复用 | 跳过候选 | 继续选择或新建 |
| 资源已存在 | 复用 | 直接打开 | 不重复添加 |
| 资源达到数量上限 | 复用/新建 | 提示先移除部分资料 | 既有草稿保持不变；新 Thread 可补偿删除 |
| 无可用 Chat 模型 | 新建 | 提示进入 API Key 设置 | 设置关闭后重新 prepare |
| 新 Thread 创建失败 | 新建 | 提示稍后重试 | 不展示 Cover |
| 新建后 ref 注入失败 | 新建 | 提示准备失败 | 删除本次新 Thread |
| 既有 Thread ref 注入失败 | 复用 | 提示准备失败 | 只回滚本次新增 ref |
| 用户取消 API Key 设置 | 新建 | 留在详情页 | 清理 pending request |
| 账号切换/退出 | 任一阶段 | 不打开旧账号 Chat | 取消任务并清理瞬时状态 |

## 十二、与其他模块的接口边界

### 12.1 本模块负责

- 根据统一 5 分钟策略选择可复用 Thread。
- 保证健康资源与 Thread 成员精确匹配。
- 在复用与新建之间编排并追加 `HealthResourceRef`。
- 返回最终 threadID 与可观测决策结果。
- 在失败时执行分支对应的最小补偿。

### 12.2 本模块不负责

- 健康资源详情数据的完整加载和编辑。
- AI 消息发送、模型推理和工具调用。
- 修改 Thread 历史消息或自动总结旧上下文。
- 跨成员合并会话、改绑 Thread 或合并 Thread。
- 对话 Tab 的 fullScreenCover 来源和主页返回交互。

### 12.3 输入与输出

| 方向 | 模型 | 说明 |
| --- | --- | --- |
| 输入 | `HealthResourceConversationRequest` | 资源 identity、展示快照、入口 source |
| 查询 | `[ChatThreadListItem]` | 当前账号本地 Thread 列表 |
| 输出 | `PreparationResult` | ready(threadID)、requiresAISettings、failed |
| 副作用 | Composer draft | 追加一条去重后的健康资源引用 |
| 可选副作用 | 新建 Thread | 仅在没有可复用候选且模型可用时发生 |
