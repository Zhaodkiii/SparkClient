## 1. 一句话目标

新会话进入后，先检查当前对话是否已绑定成员；未绑定且无法默认绑定成员时直接使用第一阶段固定三条问题，已绑定成员时首条系统引导卡片展示“科普问题生成中”状态，并使用当前对话 AI 基于该成员资料异步生成 3 个健康科普问题；用户切换当前对话绑定成员后，重新进入生成中并按新成员资料重新生成，最终回写同一张引导卡片并同步本地/服务端。

### 2.2 医疗抽取可参考模式

医疗档案抽取和 Chat 结构化健康卡片已有两类关键模式可复用：

1. Prompt 本地化：`MedicalPromptFactory` 委托 `PromptLocalizer`，`PromptLocalizer` 通过 `AIPromptL10n` 读取 `Prompts.strings`。
2. 异步卡片回写：`ToolHubGenerateStructuredHealthCard` 先返回 pending side effect，后台 Task 成功后 emit ready，失败后 emit failed；`MessageRunActor` 通过 `upsertMessageBlock(markPendingForSync:)` 回写同一消息块并走 block_updates 同步。

本工单建议复用这两个方向，但不把科普问题生成做成 ToolHub 工具。引导卡片问题生成是会话首屏 UI 初始化任务，不是 AI 回复过程中的工具调用。

## 3. 需求范围

### 3.1 引导卡片问题异步生成

需求说明：

进入新会话并插入引导卡片后，异步启动科普问题生成任务。生成期间卡片仍完整展示健康数据滑块，问题区展示加载中状态。生成成功后，用 AI 输出替换卡片内 `questions`。

基础要求与业务规则：

1. 使用当前对话 AI：优先使用当前 thread / composer 选择的模型名，交给 `AIRuntimeService` 解析；如果当前模型是本地模型，则走已有本地模型网关。
2. 不创建新的用户消息或助手消息。
3. 不阻塞新会话创建和首屏渲染。
4. 生成只针对当前会话的引导卡片；历史会话不批量补跑。
5. 同一 thread 同一 guide block 只允许一个生成任务运行。
6. 用户在生成中点击问题区时应不可点击，避免发送空问题或 preset 问题。
7. 进入会话时必须先确认当前 thread 是否绑定成员；未绑定成员时不调用 AI，直接写入固定 preset。
8. 如果默认绑定成员开关开启，不能在引导卡片刚插入后立即按 nil 判定 preset；必须等待新建 thread 完成、默认成员绑定流程执行并持久化成功后，再重新读取最新 `thread.memberID` 决定生成或 preset。
9. 生成 prompt 必须携带当前对话绑定成员的资料摘要；不使用全局选中成员替代 thread 绑定成员。

主流程：

```text
用户进入新对话
  ↓
首条 system 引导卡片已插入
  ↓
如果开启默认绑定成员：等待 thread 新建完成 -> 执行默认成员绑定 -> 等待绑定持久化/threadsChanged 刷新
  ↓
重新读取最新 thread.memberID
  ↓
无绑定成员 -> payload.questions = preset, state = fallback/preset
  ↓
有绑定成员 -> payload.questionGenerationState = generating
  ↓
ChatDetailViewModel 发现当前 thread 首条 guide card 需要生成问题
  ↓
读取绑定成员 complete-data 并构造成 AI 参考摘要
  ↓
ChatGuideQuestionGenerationUseCase 调用 AIRuntimeService
  ↓
解析 AI 返回 JSON 为 [ChatGuideQuestion]
  ↓
回写同一 chatGuideCard block
  ↓
CoreData 本地持久化 + block_updates 服务端同步
```

失败、重试和恢复：

1. AI 调用失败：回写 `ChatGuideQuestionPreset.phaseOne`，状态标记为 `fallback`。
2. JSON 解析失败：最多可按医疗抽取 retry correction 思路重试 1 次；仍失败则 fallback。
3. 用户离开会话：生成任务可继续后台完成并回写；若 ViewModel 销毁导致任务取消，下次进入检测到 `generating` 可重新触发或 fallback。
4. 账号切换：任务必须绑定 owner/thread/message/block，回写前重新加载目标消息并确认仍属于当前可访问数据。
5. 离线且当前模型不是本地模型：直接 fallback，不阻塞卡片。
6. 当前 thread 无绑定成员：直接 fallback/preset，不进入 AI 生成。
7. 默认绑定失败、首页当前无选中成员，或等待默认绑定完成后最新 `thread.memberID` 仍为空：直接 fallback/preset。
8. 绑定成员资料读取失败：可以使用固定 preset；不要用空资料强行生成个性化问题。

验收标准：

1. 插入卡片后问题区显示加载中。
2. 成功生成后卡片内出现 3 个 AI 生成问题。
3. 生成失败后出现固定三条问题。
4. 刷新、重启、远端拉取后展示最终已回写的问题。
5. 未绑定成员的对话不显示生成中，直接展示固定三条问题。
6. 默认绑定成员成功的对话，必须在重新读取到最新 `thread.memberID` 后，再按绑定成员资料生成问题。

### 3.2 payload 状态扩展

需求说明：

当前 `ChatGuideCardPayload.questions` 只能表达最终问题列表，不能表达“生成中/失败兜底/生成来源”。需要以 schema v2 方式新增问题生成状态。

建议模型：

```swift
nonisolated enum ChatGuideQuestionGenerationState: String, Codable, Equatable, Sendable {
    case preset
    case generating
    case generated
    case fallback
    case failed
}

nonisolated struct ChatGuideQuestionGenerationMeta: Codable, Equatable, Sendable {
    var state: ChatGuideQuestionGenerationState
    var source: String?
    var memberID: Int?
    var memberProfileDigest: String?
    var generatedAt: Date?
    var errorMessage: String?
}

nonisolated struct ChatGuideCardPayload: Codable, Equatable, Sendable {
    var schemaVersion: Int
    var generatedAt: Date
    var memberID: Int?
    var metricSections: [ChatGuideMetricSection]
    var questions: [ChatGuideQuestion]
    var questionGeneration: ChatGuideQuestionGenerationMeta?
}
```

插入卡片初始 payload：

```swift
ChatGuideCardPayload(
    schemaVersion: 2,
    generatedAt: now,
    memberID: memberID,
    metricSections: sections,
    questions: [],
    questionGeneration: .init(
        state: .generating,
        source: "current_chat_ai",
        memberID: memberID,
        memberProfileDigest: nil,
        generatedAt: nil,
        errorMessage: nil
    )
)
```

兼容规则：

1. `questionGeneration == nil` 的旧 payload 视为 `.preset` 或 `.generated`，按 `questions` 原样展示。
2. `questions.isEmpty && state == .generating` 时展示 skeleton/loading。
3. `state == .fallback` 时展示 preset 问题，但不把 error 暴露给用户。
4. `state == .failed && questions.isEmpty` 不应常态存在，最终必须写入 fallback。
5. `questionGeneration.memberID != thread.memberID` 时，说明当前问题不是按最新绑定成员生成，应重新进入 `generating` 并触发再生成。

验收标准：

1. 旧版本卡片仍能正常解码。
2. 新版本卡片能 round-trip 编解码。
3. UI 能区分 generating/generated/fallback。
4. payload 能记录本轮问题对应的成员 ID，支持成员切换后判断是否过期。

### 3.3 当前对话 AI 生成用例

需求说明：

新增 `ChatGuideQuestionGenerationUseCase`，使用当前会话模型生成 3 条问题。不要走 `SendChatMessageUseCase`，因为这不是用户对话消息；也不建议走 `ChatOrchestrator.generateReply` 的完整工具链，避免触发工具、知识库、联网和消息副作用。

推荐调用层级：

```text
ChatDetailViewModel
  ↓
ChatGuideQuestionGenerationCoordinator
  ↓
ChatGuideQuestionGenerationUseCase
  ↓
AIRuntimeService.generateTextStream
  ↓
ChatGuideQuestionJSONParser
```

推荐 request：

```swift
AIRuntimeTextRequest(
    scenario: .chat,
    messages: [
        AIRuntimeMessage(role: .user, content: prompt)
    ],
    tools: [],
    toolChoice: .none,
    reasoning: .disabled,
    preferredModelName: preferredModelName,
    temperature: 0.7,
    topP: 0.9,
    maxTokens: 800
)
```

模型选择规则：

1. 优先 `stateStore.composerDraft(for: threadID).runtimeFlags.selectedChatModelName`。
2. 其次 `ChatThread.currentModelName`。
3. 再次使用 AIConfigCenter 对 `.chat` 的默认模型。
4. 如果解析结果是本地模型，`AIRuntimeService` 会走 `LocalGGUFTextGateway`，这就是“本地 AI 生成”的项目内最佳接入点。

输出解析规则：

1. 要求模型返回 JSON array，仅 3 个对象。
2. 每个对象必须包含 `id`、`title`、`prompt`、`category`。
3. `title` 控制在 12 到 24 个中文字符或对应语言的短句。
4. `prompt` 可以与 title 相同，也可以更完整，但不能包含医疗诊断承诺。
5. `category` 第一阶段固定为 `popular_science`。
6. 解析后去重、裁剪到 3 条；不足 3 条时用 preset 补齐。

验收标准：

1. 当前对话选择本地模型时，问题生成调用本地模型。
2. 当前对话选择云端模型时，可走云端但仍不创建对话消息。
3. 不触发 ToolHub、不产生工具卡片、不污染当前对话历史。

### 3.4 成员绑定检查与成员切换重新生成

需求说明：

进入对话时，必须以当前 thread 的绑定成员作为科普问题生成的身份边界。用户切换当前对话绑定成员后，旧问题失效，需要根据新成员资料重新生成。

基础要求与业务规则：

1. 首次进入会话：
   - 如果 `thread.memberID != nil`，按该成员生成。
   - 如果 `thread.memberID == nil` 且默认绑定成员开关开启，先等待新建 thread 完成，再尝试绑定首页当前选中成员。
   - 默认绑定调用完成后，必须重新加载或等待 `.threadsChanged` 刷新当前 thread，再检查最新 `thread.memberID`。
   - 如果绑定后仍无成员，直接写入 preset，不启动 AI。
2. 用户手动切换当前对话成员：
   - 调用既有 `updateThreadMemberBinding(threadID:memberID:)` 后，定位首条 guide card。
   - 将 `questionGeneration.state` 改为 `generating`、`questions` 清空或保留旧问题但 UI 覆盖为 loading。
   - 使用新 `memberID` 拉取 complete-data 并重新生成。
   - 成功或 fallback 后回写同一 block，并 `markPendingForSync: true`。
3. 重新生成期间问题区展示“正在根据新成员资料生成科普问题...”。
4. 切换成员时如果新成员与 `questionGeneration.memberID` 相同，不重复生成。
5. 切换为 nil 成员时，立即回写 preset，状态为 `preset` 或 `fallback`。

推荐成员资料摘要：

优先复用 `DeepTutorQueryMemberProfileFormatter.makeAIResult(data:requestedFocus:)` 的 `content`：

```text
[成员基础资料]
- 成员ID
- 姓名
- 关系
- 性别
- 年龄
- 身高体重

[基础档案]
[健康病史与症状记录]
[生活习惯]
[过往体检档案]
[风险评估]
[服务端引导分区摘要]
[聚合统计]
```

如果不希望 Chat 直接依赖 DeepTutor 命名空间，建议抽出公共 formatter：

```text
SparkClient/Projects/Features/Chat/Application/ChatGuideMemberProfilePromptFormatter.swift
```

或移动为 Core/Medical 级公共格式化器，DeepTutor 与 Chat 共同复用。

主流程：

```text
进入会话 / thread memberID 变化
  ↓
如果默认绑定成员开启且 thread.memberID 为空
  ↓
等待默认绑定流程完成并刷新 thread
  ↓
重新检查 thread.memberID
  ↓
nil -> 回写 preset 并同步
  ↓
非 nil -> fetchMemberCompleteData(memberID)
  ↓
格式化成员资料摘要
  ↓
guide block state = generating
  ↓
AI 生成问题
  ↓
回写 generated/fallback + memberID + digest
  ↓
本地持久化 + 服务端 block_updates
```

验收标准：

1. 未绑定成员的会话直接展示固定三条问题。
2. 默认绑定成员开启时，新会话必须先完成 thread 创建和默认绑定持久化，再按最新绑定成员资料生成问题。
3. 手动切换成员后，问题区重新进入生成中。
4. 新成员生成成功后，卡片问题与 `questionGeneration.memberID` 一致。
5. 切换成员后本地和服务端均保存最新问题。

### 3.5 Prompt 本地化

需求说明：

参考医疗抽取，科普问题生成 prompt 必须进入 `Prompts.strings`，由 `PromptLocalizer` 统一读取，不能在 Swift 中硬编码完整 prompt。

建议新增方法：

```swift
extension PromptLocalizer {
    nonisolated func chatGuideQuestionGenerationPrompt(
        localeIdentifier: String,
        metricSummary: String,
        memberProfileSummary: String
    ) -> String {
        l10n.promptFormat(
            "ai.prompt.chat.guide.question_generation.template",
            fallback: "...",
            localeIdentifier,
            metricSummary,
            memberProfileSummary
        )
    }
}
```

建议 `zh-Hans` prompt 要点：

```text
你是健康科普问题推荐助手。
请基于当前对话绑定成员的健康数据摘要和成员资料，生成 3 个适合在健康对话开场展示的科普问题。

要求：
- 只返回 JSON 数组，不要 Markdown，不要解释。
- 每个对象包含 id、title、prompt、category。
- title 是短展示文案，适合按钮列表。
- prompt 是点击后发送给 AI 的完整问题。
- category 固定为 popular_science。
- 不要生成诊断结论，不要暗示用户已经患某病。
- 可以参考成员年龄、性别、生活习惯、病史、体检和用药统计，但不要暴露敏感明细。
- 问题应面向科普和健康管理，不要直接给治疗方案。
- 优先选择安全、通用、可科普的问题。

当前语言：%@
健康数据摘要：
%@
成员资料摘要：
%@
```

建议输出示例：

## 6. 状态模型

| 状态 | questions | UI | 下一步 |
| --- | --- | --- | --- |
| `generating` | 空 | loading rows | 启动或等待生成任务 |
| `generated` | AI 生成 3 条 | 可点击问题列表 | 正常发送问题 |
| `fallback` | preset 3 条 | 可点击问题列表 | 正常发送问题 |
| `preset` | preset 3 条 | 可点击问题列表 | 兼容旧卡片 |
| `failed` | 不建议停留 | loading 或 fallback | 立即转 fallback |

成员状态补充：

| 成员状态 | 处理 |
| --- | --- |
| `thread.memberID == nil` | 直接 preset，不生成 |
| 默认绑定进行中 | 等待绑定完成和 thread 刷新，不提前 preset |
| 默认绑定成功 | 重新读取最新 thread.memberID 后按绑定成员生成 |
| 默认绑定失败 | 等待结束后仍 nil 才 preset |
| `questionGeneration.memberID == thread.memberID` | 不重复生成 |
| `questionGeneration.memberID != thread.memberID` | 重新 generating 并按新成员生成 |

## 7. 数据与持久化

本地持久化：

1. 生成结果写回原 `ChatMessageBlockEntity.payloadData`。
2. block `revision` 必须递增。
3. `updatedAt` 使用回写时间。
4. `markPendingForSync: true`，进入 block_updates。
5. `questionGeneration.memberID` 必须写入本轮使用的 thread 绑定成员。
6. 可记录 `memberProfileDigest`，用于判断成员资料摘要是否变化；digest 不存敏感全文，只存 hash 或短摘要版本号。

服务端同步：

1. 如果整条 guide message 仍处于 `pending`，整消息 push 会携带最新 block。
2. 如果整条 message 已 ACK，block update 单独同步。
3. 拉取远端时按 block id 合并，不新增第二张 guide card。

AI 上下文边界：

科普问题生成不进入 Chat 历史，不创建 user/assistant message，不影响用户后续正式提问。点击问题后，才使用现有 `sendGuideQuestion` 发送 `question.prompt`。

成员资料边界：

1. AI prompt 可使用成员资料摘要，但 payload 不应长期保存完整成员资料全文。
2. payload 只保存生成问题、memberID、生成来源、时间和必要 digest。
3. 切换成员后，旧成员生成的问题应被新成员结果覆盖或 preset 覆盖。

## 8. 错误模型

| 错误 | 处理策略 |
| --- | --- |
| 当前 thread 不存在 | 不启动生成 |
| 找不到 guide block | 不启动生成 |
| 已经 generated/fallback | 不重复生成 |
| 当前模型不可用 | fallback preset |
| 本地模型加载失败 | fallback preset；记录日志 |
| 云端网络失败 | fallback preset；记录日志 |
| thread 未绑定成员且默认绑定未开启 | 直接 preset，不启动 AI |
| 默认绑定成员进行中 | 等待绑定流程完成，不提前回写 preset |
| 默认绑定成员失败或完成后仍 nil | preset |
| complete-data 拉取失败 | preset 或 fallback，不使用空资料生成 |
| 切换成员时已有生成任务 | 取消旧任务或以 generation token 忽略旧任务结果 |
| 旧成员生成任务晚于新成员完成 | 回写前校验 memberID，不一致则丢弃旧结果 |
| AI 输出非 JSON | 可重试 1 次，仍失败则 fallback |
| AI 输出不足 3 条 | 用 preset 补齐到 3 条 |
| 回写 block 失败 | 下次进入会话重新检测 generating 并重试或 fallback |

## 11. 详细落地方案

### 11.1 推荐拆分顺序

第一步先改 Domain payload，让数据结构能表达生成过程；第二步接入 ViewModel 触发器和异步生成用例；第三步补 UI loading；第四步接本地/服务端 block 回写；第五步补默认成员绑定等待、成员切换重新生成和竞态保护。

推荐开发拆分：

| 步骤 | 目标 | 涉及文件 |
| --- | --- | --- |
| 1 | 扩展 guide payload 状态，保持旧数据兼容 | `ChatGuideCardPayload.swift` |
| 2 | 插入卡片时按 memberID 初始化 questions/state | `ChatGuideCardPayloadBuilder.swift`、`ChatGuideSystemMessageFactory.swift` |
| 3 | 新增科普问题生成 use case、parser、formatter | `ChatGuideQuestionGenerationUseCase.swift`、`ChatGuideQuestionJSONParser.swift`、`ChatGuideMemberProfilePromptFormatter.swift` |
| 4 | 在 ViewModel 中扫描首条 guide card 并触发生成 | `ChatDetailViewModel.swift` |
| 5 | 等待默认成员绑定完成后再判断 thread.memberID | `ChatView.swift`、`ChatDetailViewModel.swift` |
| 6 | 卡片问题区支持 loading / generated / fallback | `ChatGuideMessageCardView.swift`、`ChatGuideQuestionRowView.swift` |
| 7 | 生成结果回写同一 block，并进入 block_updates | `CoreDataChatRepository.swift`、既有 `ChatRepository` 接口 |
| 8 | 用户切换当前对话成员时重新生成 | `ChatDetailViewModel.updateThreadMemberBinding(...)` 相关调用链 |
| 9 | 补测试和日志 | Tests、Chat log event |

### 11.2 入口触发细节

触发入口应收敛到 `ChatDetailViewModel`，SwiftUI View 只负责生命周期通知和默认绑定动作，不直接调用 AI。

推荐新增 ViewModel 方法：

```swift
@MainActor
func ensureGuideQuestionsReadyForCurrentThread(reason: ChatGuideQuestionGenerationReason) async
```

`reason` 建议包含：

```swift
enum ChatGuideQuestionGenerationReason: Sendable {
    case enterThread
    case defaultMemberBindingCompleted
    case memberBindingChanged
    case recoverGeneratingPayload
}
```

调用时机：

1. 进入对话并加载消息完成后调用一次，reason 为 `.enterThread`。
2. `applyComposerStartupMemberBindingIfNeeded()` 成功执行默认绑定后，再调用一次，reason 为 `.defaultMemberBindingCompleted`。
3. 用户主动切换当前对话成员并持久化成功后，再调用一次，reason 为 `.memberBindingChanged`。
4. 拉取历史消息发现首条 guide card 仍停留在 `generating` 时，可调用 `.recoverGeneratingPayload`。

入口必须是幂等的：多次调用只会让同一个 thread、同一个 guide block 保持一个活跃生成任务。

### 11.3 默认绑定成员等待规则

默认绑定成员开启时，新建对话不能用“刚插入卡片时 thread.memberID == nil”直接决定 preset。正确顺序应是：

```text
ChatView.onAppear / 新对话进入
  ↓
ChatDetailViewModel.loadMessagesIfNeeded(threadID)
  ↓
ChatView.applyComposerStartupMemberBindingIfNeeded()
  ↓
如果需要默认绑定：await updateThreadMemberBinding(selectedMemberID, for: threadID)
  ↓
等待 CoreDataChatStore.updateThreadMemberBinding 写入完成
  ↓
等待 stateStore.selectedThread 或 repository 重新读取得到最新 thread.memberID
  ↓
ChatDetailViewModel.ensureGuideQuestionsReadyForCurrentThread(...)
```

落地注意：

1. `applyComposerStartupMemberBindingIfNeeded()` 若发现 `chatComposerStartupPreferences.memberProfileEnabled == true`、当前 thread 未绑定、首页有 selectedMemberID，应返回“已尝试绑定/绑定成功/无可绑定成员”的结果，或由调用方在 await 后重新读取 thread。
2. `ensureGuideQuestionsReadyForCurrentThread` 内部不能只信任进入方法时传入的旧 thread snapshot；必须在关键判断前重新读取一次最新 thread。
3. 如果默认绑定任务仍在执行，guide card 可以保持 `generating` 的 loading 态，但不要立即写入 preset。
4. 如果默认绑定完成后 `thread.memberID` 仍为空，再回写 `questions = ChatGuideQuestionPreset.phaseOne`、`state = preset`。
5. 如果默认绑定成功拿到 memberID，再进入 AI 生成流程。

### 11.4 生成任务协调器

建议新增轻量 coordinator，避免 ViewModel 直接塞满任务状态：

```swift
@MainActor
final class ChatGuideQuestionGenerationCoordinator {
    private var activeTasks: [ChatGuideQuestionTaskKey: Task<Void, Never>] = [:]

    func ensureGeneration(...)
    func cancelGeneration(threadID: UUID, blockID: UUID)
    func cancelAll()
}

struct ChatGuideQuestionTaskKey: Hashable, Sendable {
    var threadID: UUID
    var messageID: UUID
    var blockID: UUID
}
```

协调器职责：

1. 根据 threadID + messageID + blockID 去重。
2. 成员切换时取消旧 task，或至少让旧 task 回写前被 token 拦截。
3. ViewModel 销毁时取消当前会话未完成任务。
4. 后台生成完成后通过 repository 回写，并触发 stateStore/UI 刷新。

建议每轮生成都携带 generation token：

```swift
struct ChatGuideQuestionGenerationToken: Equatable, Sendable {
    var threadID: UUID
    var messageID: UUID
    var blockID: UUID
    var memberID: Int
    var startedAt: Date
}
```

回写前必须重新读取当前 thread 和当前 block：

1. 当前 thread 不存在：丢弃结果。
2. 当前 thread.memberID != token.memberID：丢弃结果。
3. 当前 block 已不是 chatGuideCard：丢弃结果。
4. 当前 payload.questionGeneration.memberID != token.memberID：丢弃结果。
5. 当前 payload 已经是新一轮 `generated/fallback` 且 generatedAt 晚于 token.startedAt：丢弃结果。

### 11.5 payload 状态流转细节

推荐状态流转：

```text
新建卡片，memberID 待确定
  -> generating + questions=[]

默认绑定等待结束后仍无 memberID
  -> preset + questions=preset

拿到 memberID
  -> generating + questions=[] + questionGeneration.memberID=memberID

AI 成功
  -> generated + questions=aiQuestions + memberID + digest + generatedAt

AI 失败/解析失败/资料失败
  -> fallback + questions=preset + memberID + digest? + errorMessage

用户切换到新 memberID
  -> generating + questions=[] + questionGeneration.memberID=newMemberID

用户解绑成员
  -> preset + questions=preset + questionGeneration.memberID=nil
```

为了避免切换成员时短暂展示旧成员问题，进入 `generating` 时建议清空 `questions`。如果产品希望保留旧问题直到新问题回来，也必须让 UI 根据 `state == generating` 覆盖展示 loading，禁止点击旧问题。

### 11.6 UseCase 输入输出

推荐 use case 接口：

```swift
struct ChatGuideQuestionGenerationInput: Sendable {
    var threadID: UUID
    var messageID: UUID
    var blockID: UUID
    var memberID: Int
    var localeIdentifier: String
    var modelName: String?
    var metricSections: [ChatGuideMetricSection]

struct ChatGuideQuestionGenerationOutput: Sendable {
    var questions: [ChatGuideQuestion]
    var memberID: Int
    var memberProfileDigest: String
    var source: String
    var generatedAt: Date

```

`ChatGuideQuestionGenerationUseCase.generate(input:)` 内部顺序：

1. 调用 `HealthResourceRepository.fetchMemberCompleteData(memberID:)`。
2. 使用 `DeepTutorQueryMemberProfileFormatter.makeAIResult(data:requestedFocus:)` 生成 AI 资料摘要；`requestedFocus` 可传入“对话引导卡片健康科普问题生成”。
3. 读取 `Prompts.strings` 中的本地化 prompt 模板。
4. 注入成员资料摘要、健康数据滑块摘要、输出 JSON schema、问题数量限制。
5. 调用 `AIRuntimeService.generateTextStream` 或项目现有文本生成入口。
6. 收集完整文本，交给 `ChatGuideQuestionJSONParser` 解析。
7. 校验并归一化为 3 条 `ChatGuideQuestion`。

### 11.7 成员资料摘要与隐私边界

成员资料应只进入 AI prompt，不应长期写入 guide card payload。

建议使用的 prompt 上下文：

```text
成员资料摘要:
{DeepTutorQueryMemberProfileFormatter.makeAIResult(...).content}

当前引导卡片健康数据:
- 运动数据: 步数、热量消耗
- 身材管理: 体重、BMI、体脂率
- 饮食营养: 已食用、剩余、已消耗
- 医疗数据: 病历、体检、检查报告、服药计划
```

payload 只保存：

1. `questions`
2. `questionGeneration.state`
3. `questionGeneration.memberID`
4. `questionGeneration.memberProfileDigest`
5. `questionGeneration.generatedAt`
6. `questionGeneration.source`
7. 必要的错误分类，不保存完整错误堆栈和成员资料全文。

`memberProfileDigest` 建议由非敏感字段构造 hash，例如：

```text
memberID + completeData.updatedAt? + healthArchiveCount + examReportCount + riskAssessmentCount
```

如果 complete-data 没有稳定更新时间，可以先只用于日志和后续优化，不作为本期重新生成触发条件。

### 11.8 Prompt 本地化落地

新增 prompt key 建议：

```text
chat.guide.questions.generate.system
chat.guide.questions.generate.user
chat.guide.questions.generate.repair_json
```

`zh-Hans` prompt 约束：

```text
你是健康科普问题生成助手。请基于成员资料摘要和当前健康数据，生成 3 个适合用户点击提问的健康科普问题。

要求:
1. 只输出 JSON 数组，不输出 Markdown。
2. 每个对象必须包含 id、title、prompt、category。
3. title 不超过 18 个中文字符，适合卡片展示。
4. prompt 可以比 title 更完整，但不能给出诊断结论。
5. category 固定为 popular_science。
6. 问题应是健康科普方向，不要生成治疗方案、处方建议、疾病确诊类问题。
7. 如果成员资料不足，生成通用健康科普问题。
```

输出 schema：

```json
[
  {
    "id": "string_snake_case",
    "title": "短展示文案",
    "prompt": "点击后发送给 AI 的完整问题",
    "category": "popular_science"
  }
]
```

解析失败修复 prompt 只负责把原始输出修成合法 JSON，不重新发散生成。

### 11.9 JSON 解析与归一化

`ChatGuideQuestionJSONParser` 需要覆盖：

1. 纯 JSON 数组。
2. 被 ```json 包裹的 JSON。
3. 外层对象包裹，例如 `{ "questions": [...] }`。
4. 多于 3 条时取前 3 条。
5. 少于 3 条时用 preset 补齐。
6. `id` 为空时基于 title 生成稳定 id。
7. `category` 为空或非法时写入 `popular_science`。
8. `title` 过长时截断或回退为 prompt 的短标题。
9. `prompt` 为空时使用 title。
10. 去重：同 title 或同 prompt 只保留一条。

归一化后仍不足 3 条时，直接 fallback preset，避免 UI 出现半成品列表。

### 11.10 同一 block 回写细节

生成开始、成功、失败都应回写同一个 `chatGuideCard` block，不新增消息。

伪代码：

```swift
func updateGuideQuestionBlock(
    token: ChatGuideQuestionGenerationToken,
    mutation: (inout ChatGuideCardPayload) -> Void
) async throws {
    let thread = try await chatRepository.loadThread(id: token.threadID)
    guard thread.memberID == token.memberID else { return }

    let message = try await chatRepository.loadMessage(clientMessageID: token.messageID)
    guard var block = message.blocks.first(where: { $0.id == token.blockID }) else { return }
    guard case .chatGuideCard(var payload) = block.payload else { return }
    guard payload.questionGeneration?.memberID == token.memberID else { return }

    mutation(&payload)
    block.payload = .chatGuideCard(payload)

    try await chatRepository.upsertMessageBlock(
        clientMessageID: message.clientMessageID,
        block: block,
        markPendingForSync: true
    )
}
```

实际实现需按现有 `ChatMessageBlock` 的不可变模型风格创建 updated block，不强行改为可变对象。

### 11.11 服务端同步落地

同步沿用现有 block update 链路，不新增 API。

关键规则：

1. 如果 guide system message 尚未完成 message push，最终 push 的 message payload 应带上最新问题状态。
2. 如果 message 已经服务端确认，科普问题生成结果通过 `block_updates` 推送。
3. block update 必须只更新同一个 block id。
4. 远端拉取时如果已有本地生成结果，以现有冲突策略为准；若需要精确处理，优先保留 `updatedAt` 较新的 block。
5. 如果服务端同步失败，本地仍展示生成结果，待 outbox 重试。

### 11.12 UI 展示细节

`ChatGuideMessageCardView` 根据 `payload.questionGeneration?.state` 决定问题区：

| 状态 | UI |
| --- | --- |
| `generating` | 3 行 skeleton/loading，不可点击 |
| `generated` | 展示 AI 问题，可点击 |
| `fallback` | 展示固定问题，可点击 |
| `preset` | 展示固定问题，可点击 |
| `failed` | 不直接展示；应转 fallback |

loading 形态建议保持扁平：

```text
┌──────────────────────────────────────────────┐
│ 运动数据                       今日更新       │
│                                              │
│ 步数 10000 步        热量消耗 240 千卡        │
│                         ▁ ▃ ▆ ▇ ▅ ▁ ▂ ▃      │
├──────────────────────────────────────────────┤
│ #  正在根据成员资料生成健康科普问题...        │
│ #  正在生成第 2 个问题...                    │
│ #  正在整理可点击提问内容...                 │
└──────────────────────────────────────────────┘
●  ○  ○  ○
```

loading 文案只表达状态，不暴露模型、prompt、错误原因。生成中行不应触发 `sendGuideQuestion`。

### 11.13 成员切换重新生成细节

用户切换当前对话成员后，应立即让问题区进入新成员生成中。

推荐顺序：

```text
updateThreadMemberBinding(newMemberID)
  ↓
取消旧 memberID 的 active guide question task
  ↓
回写 guide payload:
  questions = []
  questionGeneration.state = generating
  questionGeneration.memberID = newMemberID
  ↓
markPendingForSync: true
  ↓
启动新 memberID 的生成任务
```

如果用户切换为无成员：

```text
updateThreadMemberBinding(nil)
  ↓
取消旧生成任务
  ↓
回写 guide payload:
  questions = preset
  questionGeneration.state = preset
  questionGeneration.memberID = nil
  ↓
markPendingForSync: true
```

旧任务晚返回时必须被丢弃，不能覆盖新成员问题。

### 11.15 开发验收检查清单

实现完成后逐项检查：

1. 新建未绑定成员对话：首条 guide card 直接展示固定三条问题。
2. 新建对话且默认绑定开启：等待默认绑定成功后，按最新 `thread.memberID` 生成问题。
3. 新建对话且默认绑定开启但无首页选中成员：固定三条问题。
4. 已绑定成员对话：进入后 loading，成功后展示 3 条 AI 问题。
5. 生成失败：最终展示固定三条问题，且刷新后仍展示固定问题。
6. 用户在生成中切换成员：旧任务结果不覆盖新成员问题。
7. 用户解绑成员：取消生成，回到固定三条问题。
8. 退出重进：已 generated/fallback 的卡片不重复生成。
9. 服务端同步失败：本地可见，outbox 后续可重试。
10. 远端拉取同一 guide block：不会新增第二张引导卡片。
11. 问题点击：仍调用现有 `sendGuideQuestion`，发送的是 `prompt` 不是 `title`。
12. prompt 本地化：中英文资源缺失时有可控 fallback，不崩溃。

## 14. 整体验收标准

1. 新会话进入后，引导卡片问题区先展示生成中。
2. 已绑定成员的会话使用当前对话 AI，基于该成员资料异步生成 3 个健康科普问题。
3. 生成成功后同一张卡片更新，不新增消息。
4. 生成失败后兜底固定三条问题。
5. 成功和兜底结果都本地持久化。
6. 成功和兜底结果都通过现有 block_updates 同步服务端。
7. prompt 走 `Prompts.strings` 本地化。
8. 点击生成后的问题仍沿用现有 `sendGuideQuestion` 逻辑。
9. 不污染当前对话 AI 历史，不触发 ToolHub。
10. 未绑定成员且无法默认绑定时，不显示生成中，直接展示固定三条问题。
11. 默认绑定成员开启并成功时，必须等待默认绑定完成并重新读取最新 `thread.memberID`，再按默认绑定后的成员资料生成问题。
12. 用户切换当前对话绑定成员后，问题区重新进入生成中并按新成员资料重新生成。
13. 旧成员生成任务晚返回时，不能覆盖新成员已生成的问题。
