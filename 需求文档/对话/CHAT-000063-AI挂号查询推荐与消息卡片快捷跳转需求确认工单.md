## 1. 需求背景

用户希望在现有 Chat 工具架构中新增挂号能力：AI 可以查询科室与医生，根据患者描述的症状推荐对应科室，并把结构化挂号卡片插入对话。用户点击卡片后，以通用 Sheet 承载既有演示挂号流程，并根据推荐精度跳过已经确定的页面：

- 只精确到科室：直接打开 `HospitalRegistrationServiceView`，继续选择普通号或专家医生；
- 精确到科室和医生：直接打开 `HospitalRegistrationScheduleView`，继续选择日期和时段；
- 复用现有演示挂号流程，不在本需求中另建一套挂号页面。

## 2. 用户目标与问题范围

1. 新增“查询挂号科室/医生”的只读工具。
2. 支持模型根据患者本轮症状描述给出科室推荐；医生推荐必须来自工具返回的真实目录项，不能由模型编造 ID。
3. 新增“展示挂号推荐卡”的 UI 副作用工具或等价展示能力，将稳定的医院、科室、医生标识落入消息块。
4. 点击消息卡片后，通过 Chat 宿主的通用 Sheet 打开挂号 NavigationStack。
5. 按推荐精度恢复到既有挂号流程的正确层级。
6. 明确查询工具与卡片推送工具的职责、参数、失败边界和与服务端目录的关系。

## 4. 已知偏差与风险

1. **医生语义混用**：现有 Demo 把 `HospitalAgentCard` 当作专家医生；若继续复用 `agents` API，则未发布 AI 智能体的真实医生不会出现在挂号查询结果中。
2. **医院上下文缺失**：Chat 工具上下文没有 `hospitalID`；必须定义当前医院的解析优先级，避免跨医院 ID 误跳转。
3. **推荐与查询边界**：模型可以根据症状对工具返回的候选排序和解释，但不得自行生成科室或医生 ID。
4. **卡片持久化**：卡片必须保存稳定 ID 与推荐精度；仅保存展示文字会导致历史消息重开时无法安全恢复目标页面。
5. **目标下架**：历史卡片点击时，科室或医生可能已停用；打开 Sheet 前必须重新校验并提供降级入口。
6. **演示性质**：现有日期、费用、时段和余号为本地模拟值；卡片及 Sheet 必须明确“演示挂号”，不能暗示已经锁号或预约成功。
7. **医疗安全**：症状导诊属于辅助推荐，不是诊断；急危重症描述应优先展示就医风险提示，不能只推普通挂号卡。

- 症状原文继续只存在于原对话消息及既有模型上下文，不复制到挂号卡 payload、路由快照或挂号页面参数。
- 卡片至少展示医院、科室、可选医生、简短推荐依据、“演示挂号”提示和“快速挂号”操作。

- B. 首次使用时授权一次

### 11.1 AI 查询与推荐主流程

```text
用户在任意对话中表达症状、就医意图或询问挂号
  ↓
模型判断需要了解当前医院可挂科室
  ↓
调用 query_registration_catalog(scope=departments)
  ↓
客户端读取 HospitalSelectionStore 当前医院
  ├─ 无当前医院 → 返回 HOSPITAL_NOT_SELECTED 给模型，不推卡
  └─ 有当前医院 → loadDepartments(hospitalID)
       ├─ 失败且无可用缓存 → 返回 CATALOG_UNAVAILABLE 给模型，不推卡
       └─ 成功 → 返回医院快照和科室列表，继续模型
  ↓
模型选择一个最合适的科室
  ├─ 只需科室推荐 → 调用 show_registration_recommendation
  └─ 需要进一步推荐医生
       ↓
       调用 query_registration_catalog(
         scope=doctors,
         department_id=<已查询到的科室 ID>
       )
       ↓
       模型从返回结果中选择最多一个 agent_id
       ↓
       调用 show_registration_recommendation
  ↓
展示工具按当前医院重新校验科室及可选医生归属
  ├─ 校验失败 → 返回结构化错误，不插卡
  └─ 校验成功 → 生成 registrationRecommendationCards Block
                   shouldBypassModel=true，本轮以卡片结束
```

说明：模型可以决定不推荐挂号，也可以仅给普通医疗说明。工具说明必须告诉模型“推荐前先查询目录”，但客户端不维护“本轮已查过目录”的强制状态机。现有急症风险提示工具的判断优先级不被本需求改变。

## 12. 工具职责与结构化契约

### 12.1 `query_registration_catalog`

职责：读取当前系统医院下的科室或医生目录，只向模型提供事实候选，不生成用户可见卡片。

建议 Schema：

```json
{
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "scope": {
      "type": "string",
      "enum": ["departments", "doctors"],
      "description": "查询科室或医生目录。推荐科室前先查 departments；需要医生时再按已选科室查 doctors。"
    },
    "department_id": {
      "type": "string",
      "description": "scope=doctors 时必填，必须来自本轮科室目录结果。"
    },
    "keyword": {
      "type": "string",
      "maxLength": 64,
      "description": "可选目录关键词，仅用于名称或既有目录搜索。不得传入完整症状、病史或成员隐私。"
    },
    "limit": {
      "type": "integer",
      "minimum": 1,
      "maximum": 50,
      "default": 20
    }
  },
  "required": ["scope"]
}
```

条件校验由 executor 完成：`scope=doctors` 而缺少 `department_id` 时返回参数错误。模型不传 `hospital_id`；客户端始终使用当前系统医院，避免模型携带过期医院上下文。

科室成功结果：

```json
{
  "ok": true,
  "tool": "query_registration_catalog",
  "scope": "departments",
  "hospital": {
    "id": "hospital-id",
    "name": "当前医院"
  },
  "items": [
    {
      "department_id": "department-id",
      "code": "CARDIOLOGY",
      "name": "心血管内科",
      "short_name": "心内科",
      "description": "科室目录中的公开简介"
    }
  ],
  "count": 1
}
```

医生成功结果：

```json
{
  "ok": true,
  "tool": "query_registration_catalog",
  "scope": "doctors",
  "hospital": {
    "id": "hospital-id",
    "name": "当前医院"
  },
  "department": {
    "id": "department-id",
    "name": "心血管内科"
  },
  "items": [
    {
      "agent_id": "agent-id",
      "doctor_id": "doctor-id",
      "name": "演示医生",
      "title": "主任医师",
      "specialties": ["高血压", "冠心病"],
      "avatar_url": "https://example.invalid/doctor.png"
    }
  ],
  "count": 1
}
```

执行语义：

- `shouldBypassModel=false`；`sideEffects=[]`。
- 科室复用既有 stale-while-revalidate 缓存策略。
- 按科室查询医生复用现有远端查询行为；网络失败时返回失败，不以其他医院、未过滤缓存或本地静态医生兜底。
- 返回项只包括模型选择和卡片展示需要的公开字段。
- 空列表属于成功结果，模型应说明当前医院没有可用结果；请求失败属于结构化错误。

### 12.2 `show_registration_recommendation`

职责：把已经查询并选定的一个科室和可选的一个医生转换成持久化挂号推荐卡。本工具不判断症状，也不搜索目录。

建议 Schema：

```json
{
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "department_id": {
      "type": "string",
      "description": "必填，来自 query_registration_catalog 的科室结果。"
    },
    "agent_id": {
      "type": "string",
      "description": "可选，来自该科室的 doctors 查询结果；省略时生成科室级推荐。"
    },
    "reason_summary": {
      "type": "string",
      "minLength": 1,
      "maxLength": 160,
      "description": "面向用户的简短推荐依据，不复制症状原文，不作诊断，不包含成员姓名或其他健康隐私。"
    }
  },
  "required": ["department_id", "reason_summary"]
}
```

执行器从 `agent_id` 对应目录项中派生 `doctor_id` 和展示快照，模型不单独传 `doctor_id`，从协议层避免 agent 与 doctor 组合不一致。

执行语义：

- 读取当前医院，并重新校验科室属于当前医院且处于可用状态。
- 提供 `agent_id` 时，重新校验该医生智能体已发布、医生有效且属于所选科室。
- 成功：`shouldBypassModel=true`，返回一个 `.registrationRecommendation(payload)` 副作用，不再生成普通助手正文。
- 失败：不产生副作用，将结构化失败交回运行链处理；不得形成半有效卡片。
- 不要求客户端验证“本轮是否真的执行过查询工具”，只在工具说明和模型提示词中要求先查目录。

### 12.3 统一错误结构

```json
{
  "ok": false,
  "tool": "query_registration_catalog",
  "error": {
    "code": "REGISTRATION_CATALOG_UNAVAILABLE",
    "message": "暂时无法获取当前医院的挂号目录，请稍后重试。",
    "retryable": true
  }
}
```

建议稳定错误码：

| 错误码 | 场景 | 是否重试 |
| --- | --- | --- |
| `REGISTRATION_HOSPITAL_NOT_SELECTED` | 当前账号未选择医院 | 否，需先选择医院 |
| `REGISTRATION_INVALID_SCOPE` | `scope` 非法 | 否 |
| `REGISTRATION_DEPARTMENT_REQUIRED` | 查医生但缺少科室 ID | 否 |
| `REGISTRATION_DEPARTMENT_NOT_FOUND` | 科室不存在、停用或不属于当前医院 | 否，需重查 |
| `REGISTRATION_DOCTOR_NOT_FOUND` | 医生/智能体不存在、停用或科室不匹配 | 否，需重查 |
| `REGISTRATION_EMPTY_RESULT` | 展示工具无法形成目标；查询工具的空列表不使用此错误 | 否，需换条件 |
| `REGISTRATION_CATALOG_UNAVAILABLE` | 目录接口失败且无可用缓存 | 是 |
| `REGISTRATION_CARD_WRITE_FAILED` | 消息副作用无法安全落库 | 是 |

错误结果不包含底层 URL、堆栈、账号 ID 或成员健康数据。

## 13. 消息数据模型

### 13.1 新 Block

在 `ChatMessageBlockKind` 新增：

```swift
case registrationRecommendationCards
```

Block 使用数组命名，以便保持消息块渲染层对同类卡片集合的扩展空间；本期展示工具每次只写入一张卡。

### 13.2 推荐卡 payload

建议新增 `ChatRegistrationRecommendationCardPayload`：

```swift
struct ChatRegistrationRecommendationCardPayload: Codable, Equatable, Sendable {
    let schemaVersion: Int
    let hospitalID: String
    let hospitalName: String
    let departmentID: String
    let departmentName: String
    let agentID: String?
    let doctorID: String?
    let doctorName: String?
    let doctorTitle: String?
    let doctorAvatarURL: URL?
    let reasonSummary: String
}
```

约束：

- `schemaVersion` 首版固定为 `1`。
- `hospitalID`、`departmentID` 是跳转和重校验所需稳定 ID；名称、职称和头像是历史消息展示快照。
- `agentID` 与 `doctorID` 必须同时来自服务端同一条 `HospitalAgentCard` 映射，不由模型拼装。
- payload 不保存成员 ID、症状原文、完整问诊记录、预约状态、日期或时段。
- `reasonSummary` 作为用户可见历史消息持久化；日志只记录是否存在和字符数，不记录全文。
- 新客户端遇到未来不支持的 `schemaVersion` 时展示不可交互的“该推荐需要更新客户端”状态；旧客户端对未知 Block 直接忽略，不影响整条消息其他 Block 解码。

### 13.3 工具副作用

`ToolSideEffect` 新增方案：

```swift
case registrationRecommendation(ChatRegistrationRecommendationCardPayload)
```

`ToolSideEffectBlockMapper` 将其稳定映射成 `registrationRecommendationCards`。映射和落库继续沿用 `MessageRunActor`、`ChatToolEventInterpreter` 和现有 side-effect 管线，不新增旁路消息存储。

### 13.4 路由快照

`ToolInteractionSnapshot` 新增非阻塞路由，建议只携带执行导航所需字段：

```swift
case registrationRecommendation(
    ChatRegistrationRecommendationCardPayload
)
```

该路由 `requiresForcedSheetDismiss=false`，不创建 continuation，不等待工具恢复，不写回原消息卡状态。进入 Sheet 前由点击处理器完成医院匹配和目录重校验。

### 16.1 查询工具路由

```swift
func executeQueryRegistrationCatalog(
    arguments: QueryRegistrationCatalogArguments,
    context: ToolExecutionContext
) async -> ToolExecutionResult {
    guard let hospital = hospitalSelectionStore.currentHospital else {
        return .modelVisibleFailure(
            toolName: .queryRegistrationCatalog,
            code: "REGISTRATION_HOSPITAL_NOT_SELECTED",
            message: "请先选择医院后再查询挂号目录。",
            retryable: false
        )
    }

    switch arguments.scope {
    case .departments:
        let departments = try await directoryUseCase.loadDepartments(
            hospitalID: hospital.id
        )
        return .modelVisibleJSON(
            toolName: .queryRegistrationCatalog,
            payload: RegistrationCatalogResult.departments(
                hospital: hospital,
                items: Array(departments.prefix(arguments.limit))
            ),
            shouldBypassModel: false
        )

    case .doctors:
        guard let departmentID = arguments.departmentID else {
            return .modelVisibleFailure(
                toolName: .queryRegistrationCatalog,
                code: "REGISTRATION_DEPARTMENT_REQUIRED",
                message: "查询医生前需要先选择科室。",
                retryable: false
            )
        }
        let department = try await directoryUseCase.requireDepartment(
            hospitalID: hospital.id,
            departmentID: departmentID
        )
        let doctors = try await directoryUseCase.loadAgents(
            hospitalID: hospital.id,
            departmentID: department.id,
            keyword: arguments.keyword
        )
        return .modelVisibleJSON(
            toolName: .queryRegistrationCatalog,
            payload: RegistrationCatalogResult.doctors(
                hospital: hospital,
                department: department,
                items: Array(doctors.prefix(arguments.limit))
            ),
            shouldBypassModel: false
        )
    }
}
```

### 16.2 展示推荐卡

```swift
func executeShowRegistrationRecommendation(
    arguments: ShowRegistrationRecommendationArguments,
    context: ToolExecutionContext
) async -> ToolExecutionResult {
    let hospital = try hospitalSelectionStore.requireCurrentHospital()
    let department = try await directoryUseCase.requireDepartment(
        hospitalID: hospital.id,
        departmentID: arguments.departmentID
    )
    let doctor = try await arguments.agentID.asyncMap { agentID in
        try await directoryUseCase.requireAgent(
            hospitalID: hospital.id,
            departmentID: department.id,
            agentID: agentID
        )
    }
    let payload = ChatRegistrationRecommendationCardPayload(
        schemaVersion: 1,
        hospitalID: hospital.id,
        hospitalName: hospital.name,
        departmentID: department.id,
        departmentName: department.name,
        agentID: doctor?.agentID,
        doctorID: doctor?.doctorID,
        doctorName: doctor?.name,
        doctorTitle: doctor?.title,
        doctorAvatarURL: doctor?.avatarURL,
        reasonSummary: arguments.reasonSummary.trimmed
    )
    return ToolExecutionResult(
        toolName: .showRegistrationRecommendation,
        content: .json(["ok": true]),
        shouldBypassModel: true,
        sideEffects: [.registrationRecommendation(payload)]
    )
}
```

func openRegistrationRecommendation(
    _ payload: ChatRegistrationRecommendationCardPayload
) async {
    guard let currentHospital = hospitalSelectionStore.currentHospital else {
        presentHospitalMismatch(for: payload)
        return
    }
    guard currentHospital.id == payload.hospitalID else {
        presentHospitalMismatch(for: payload)
        return
    }
    do {
        let validated = try await registrationRouteResolver.resolve(payload)
        toolInteractionCoordinator.enqueue(
            .registrationRecommendation(validated.payload)
        )
    } catch {
        presentExpiredRecommendation()
    }
}

## 18. 隐私、安全与审计

1. 查询目录的网络参数只允许医院、科室、关键词和分页；不得发送症状全文、对话全文、成员档案或健康记录。
2. 模型可基于当前对话理解症状，但传给展示工具的只是一段简短 `reason_summary`；不得复制用户原话、姓名、身份证件、联系方式或诊断结论。
3. 工具日志记录工具名、scope、医院 ID、科室 ID、可选 agent ID、结果数量、错误码和耗时；推荐摘要只记存在性与字符数。
4. 点击历史卡必须重新验证医院、科室、医生归属，防止使用过期或跨医院 ID 直接构造路由。
5. 医院切换必须由用户显式确认，禁止卡片点击后静默修改全局当前医院。
6. 不新增授权弹窗；继续使用现有登录态、患者端公开目录权限和本地 UI 工具边界。
7. 卡片和结果页持续标注演示性质，不能使用“已锁号”“预约成功入库”等暗示真实医疗服务已完成的表述。
8. 本需求不改变现有医疗风险提示和安全策略，也不增加绕开模型现有安全规则的特殊通道。

## 20. 验收标准

1. 在任何正常启用工具的对话中，模型可调用 `query_registration_catalog` 获取当前系统医院的科室；查询本身不会向对话插入卡片。
2. 模型需要医生时，必须使用已选科室 ID 再查 `scope=doctors`；返回结果来自现有 `HospitalAgentListView`。
3. 模型只能使用查询结果中的 `department_id` 和可选 `agent_id` 调用 `show_registration_recommendation`。
4. 展示成功后，对话中出现一张专用挂号推荐卡，本轮不再追加重复普通正文。
5. 卡片准确展示医院、一个首选科室、可选的一个医生和简短推荐概括，并明确为演示挂号。
6. 仅科室卡直接进入对应科室页；科室加医生卡直接进入对应日期选择页。
7. 导航由现有 `ToolInteractionCoordinator + ToolInteractionSnapshot` 的全局 Sheet 承载，不产生 Sheet 冲突或工具 continuation 泄漏。
8. 历史卡点击时会重新校验目录；医院不一致时用户可显式切换并继续，或为当前医院重新推荐。
9. 完成、取消或关闭演示挂号后，原卡片不变且仍可点击；系统不记录真实预约状态。
10. 确认页默认使用当前对话选择成员，并允许用公共成员组件切换；卡片 payload 不保存成员。
11. 查询失败会把结构化错误返回模型且不推卡；展示校验失败不会生成无效卡。
12. 不新增服务端目录或挂号接口，不新增数据库迁移，不向目录接口发送症状和成员健康数据。
13. 旧客户端可以忽略新 Block，且不会导致整条消息或会话解码失败。
14. 两个工具在客户端、服务端、工具 Manifest、AI 设置、本地化和测试中的 raw value 完全一致。

## 21. 实施顺序

1. **服务端工具枚举与配置**：先在 `SparkService/ai_config/models.py` 和工具 Manifest/测试中登记两个 raw value，保持现有目录 API 不变。
2. **客户端领域模型**：增加工具枚举、参数/结果模型、推荐卡 payload、`ToolSideEffect` 和 Block kind；先完成 Codable 与未知 Block 容错测试。
3. **目录依赖适配**：为 ToolHub 注入当前医院读取和 `LoadHospitalAgentDirectoryUseCase` 协议适配，禁止 executor 直接访问网络层。
4. **工具实现**：实现 Schema、Routing、查询 executor、展示 executor、结构化错误和提示词；验证 bypass 与副作用语义。
5. **消息管线**：打通 side effect → Block mapper → 消息落库/同步 → 渲染，补齐既有 Chat 管线测试。
6. **卡片与点击校验**：实现卡片 UI、失效状态、医院不匹配选择和重新校验；接入 `SelectHospitalUseCase`。
7. **通用 Sheet 路由**：扩展 `ToolInteractionSnapshot` 和 `ToolInteractionPresentationSheet`，按推荐粒度构造既有挂号页入口。
8. **确认页成员选择**：用 `MemberContext` 公共能力补齐确认页成员切换，确保最终结果使用用户最后选择的成员。
9. **设置与本地化**：两个工具加入医疗辅助分组，补齐简体中文、繁体中文、英文文案及工具提示。
10. **全链路验收**：执行单元、消息持久化、导航、无障碍和服务端配置测试，再按第 20 节逐项验收。

## 23. 交付结论

本需求已经具备可实施边界：模型负责理解患者表达和选择推荐方向，查询工具只提供当前医院的可用目录事实，展示工具只生成一个稳定、可持久化、可重新校验的挂号推荐卡；点击卡片后通过现有 ToolInteraction Sheet 复用演示挂号流程。服务端只需登记工具名并继续提供现有目录，不新增真实挂号能力。

工单状态可进入技术评审与排期。实施必须遵循本方案中的最终结论、工具契约和验收标准；如未来要接入真实医生目录、真实排班或预约写入，应另建需求，不在本工单上扩展。
