## 一、审计结论

当前 iOS 已经落地院内名医目录、医生智能体会话创建/续聊、会话 scope 恢复和医生介绍卡。但 Q21–Q36 所要求的“进入医生智能体会话后，静默同步该智能体关联知识库并在本地检索”尚未接入。

这不是单个页面缺失，而是完整链路缺口：

1. 患者端 conversation context 没有 Knowledge Manifest。
2. 患者端没有按 `knowledge_base_id` 直接拉取医院知识正文、切块、向量和删除标记的接口。
3. HospitalCare 没有医院知识本地仓库、Manifest 缓存、agent-scope cursor 或静默同步编排。
4. 现有 `KnowledgeSyncEngine` 是“账号级个人知识库 + Push/Outbox + 本地重建向量”，可复用增量 pull、cursor、revision、tombstone、Core Data 事务和检索算法，但不能原样当作医院只读同步引擎。
5. 智能体下架、成员权限撤回和会话 context 网络失败都还没有形成可验收的只读/可发送状态机。
6. 医院、科室只做了部分内存缓存；智能体目录没有可用的缓存读写入口，也没有 stale-while-revalidate（先缓存、后静默刷新）。

## 四、目标数据与契约设计

### 4.1 conversation context 扩展

保留现有：

```text
thread_id
hospital
agent
member_id
```

新增：

```text
capabilities
  can_read_cached_history
  can_pull_remote_messages
  can_send_message
  can_sync_knowledge
  read_only_reason          // agent_unpublished | member_access_denied | null

knowledge_manifest
  manifest_revision
  generated_at
  agent_id
  hospital_id
  knowledge_bases[]
    knowledge_base_id
    name
    revision
    vector_status           // not_built | current | stale
    indexed_revision
    cursor                  // 服务端 opaque token，iOS 不解析
    deleted
```

契约要求：

1. Manifest 只包含当前会话绑定智能体当时关联的知识库。
2. 解除关联后 `manifest_revision` 立即变化，旧知识库以解绑/tombstone 语义通知客户端。
3. 智能体下架时 Manifest 不再刷新，`can_sync_knowledge=false`。
4. 成员权限撤回时服务端返回稳定业务码，iOS 不依赖 HTTP 文案判断。
5. context 是会话状态和 Manifest 的单一事实源；本地 scope 只是首屏缓存。

### 4.2 按知识库 ID 的增量 pull

建议契约：

```text
GET /api/v1/hospital-care/knowledge-bases/{knowledge_base_id}/sync/pull/
    ?cursor={opaque_cursor}
    &limit=100

response
  knowledge_base_id
  revision
  vector_status
  indexed_revision
  cursor
  has_more
  documents[]
    id
    title
    content
    revision
    is_deleted
    updated_at
    chunks[]
      id
      sequence
      content
      content_hash
      document_revision
      vector_payload
      embedding_binding_id
```

Demo 授权口径：

- 需要登录，但不根据医生智能体绑定关系做额外读取授权。
- 只允许读取启用医院下、未删除的医院科普知识库。
- ID 不存在或已删除时返回稳定业务码/tombstone，不返回其他医院的元数据。
- 不复用现有按 `request.user` 隔离的个人知识 pull 路由；底层仍读同一套 `KnowledgeBase`/`KnowledgeDocument`。

### 4.3 iOS 本地作用域

建议默认键（Q37 尚待最终产品确认）：

```text
account_id + hospital_id + agent_id + knowledge_base_id
```

原因：

1. 解绑时可以只删当前 agent 范围，严格满足已确认的清理语义。
2. 不会让医院知识混入患者个人知识 Tab 或普通 AI 对话。
3. 账号切换可直接取消旧 generation，不会把 A 账号缓存交给 B 账号。
4. 代价是同一 KB 被多 agent 关联时会占用重复本地空间；Demo 优先保证语义清晰，后续再考虑内容寻址去重。

医院知识本地仓库必须是只读投影：

- 可复用 Core Data 容器、正文分块、向量编解码、关键词检索和余弦相似度工具。
- 不提供新建、编辑、删除、Push 和 Outbox。
- 不共用个人知识的 cursor、开机同步触发器和本地编辑通知。
- 医院向量由服务端手动构建后下发，iOS 不自动调用 embedding 模型重建。

## 五、iOS 具体落地方案

### 5.1 模块边界

在现有 `Projects/Features/HospitalCare/` 内增加知识子模块，不另建第二套 Chat：

```text
HospitalCare/
  Domain/Knowledge/
    HospitalAgentKnowledgeManifest
    HospitalKnowledgeSyncState
    HospitalKnowledgeSearchResult
  Application/Knowledge/
    RefreshHospitalAgentManifestUseCase
    SyncHospitalAgentKnowledgeUseCase
    ClearHospitalAgentKnowledgeScopeUseCase
    SearchHospitalAgentKnowledgeUseCase
  Infrastructure/Knowledge/
    HospitalKnowledgeRemoteAPI
    HospitalKnowledgeRepository
    CoreDataHospitalKnowledgeRepository
    HospitalKnowledgeSyncEngine
    HospitalKnowledgeSyncCoordinator
```

可以抽取共用的不是“个人知识业务对象”，而是：

- opaque cursor 分页驱动器。
- revision/tombstone 判定。
- single-flight 与 generation 取消。
- Core Data 事务写入和原子 scope 清理。
- chunk/vector 编码与本地检索算法。

### 5.2 进入医生智能体会话的时序

```text
打开 ChatView
  -> 立即加载本地消息和医生身份卡
  -> 本地 scope 命中时先确认为医院会话
  -> 读取本地 Manifest 和可用本地知识
  -> 页面已可交互，不等待网络
  -> 后台刷新 conversation context + Manifest
     -> 下架：切只读，取消知识同步
     -> 成员撤权：切只读，停消息/Manifest pull，保留已有缓存
     -> 网络失败：保持原医院 scope，暂停 Manifest，允许尝试原会话发送
     -> 正常：比较 manifest_revision
        -> 无变化：结束
        -> 有变化：逐 KB 增量 pull
           -> 全部成功：原子替换 Manifest，开启当前 agent 本地检索
           -> 任一失败：原子清空当前 agent 全部知识缓存
```

全过程不显示知识同步 UI。日志只记录 agent ID 脱敏前缀、revision、数量、耗时和错误码，不记录正文、向量、患者问题或 Token。

### 5.3 本地检索降级

| 状态 | 检索策略 |
| --- | --- |
| `vector_status=current` 且 `indexed_revision == revision` | 可使用服务端下发向量做本地语义检索 |
| `not_built` | 只用标题/正文/chunk 关键词检索 |
| `stale` 或 `indexed_revision != revision` | 立即禁用旧向量，只用关键词/全文 |
| 向量维度与查询向量不一致 | 丢弃该向量批次，改用关键词 |
| 同步失败后已清 agent scope | 不做本地知识检索，在线会话仍正常 |

“向量待生成/已过期”是内部状态和调试日志；Q21 已确认完全静默，患者会话页不展示该标记。

### 5.4 医院数据缓存统一改造

1. `HospitalCatalogMemoryCache` 补齐智能体目录和医生详情读写方法。
2. 缓存 key 必须带 account ID；目录 key 还要包含 hospital ID、department ID 和标准化 keyword。
3. 命中缓存立即发布 UI，同时启动 single-flight 后台刷新。
4. 刷新成功覆盖缓存和页面；失败保留旧数据，目录标记离线。
5. 不得用 ViewModel 本轮内存中的 `cards` 冒充正式缓存。
6. 登出/切换账号取消旧账号所有后台任务并清内存缓存。
7. 按最新 Q30，从当前医院列表/缓存的第一条解析演示医院，不再匹配 `000001`。

### 5.5 会话异常状态机

| 状态 | 历史展示 | 远程拉消息 | 发送 | Manifest 刷新 | 是否转普通 AI |
| --- | --- | --- | --- | --- | --- |
| 正常可用 | 本地先显示 | 是 | 是 | 是 | 否 |
| 智能体已下架 | 是 | 可拉可读历史，但不拉新 AI 会话内容 | 否 | 否 | 否 |
| 成员权限已撤回（Demo 口径） | 只显示设备旧缓存 | 否 | 否 | 否 | 否 |
| context 网络失败 + 有本地 scope | 是 | 按现有聊天缓存策略 | 允许尝试，服务端最终校验 | 否 | 否 |
| context 网络失败 + 无本地 scope | 按普通本地 Thread 先显示，不执行医院副作用 | 依旧 Chat 策略 | 不允许执行“继承医生 agent 新建” | 否 | 否 |

发送门禁不得只做按钮 `.disabled`；`sendCurrentDraftIfChatModelAvailable()` 的 action 入口也要校验 capability，防止辅助功能、快捷操作或其他 composer 路径绕过 UI。

3. 医院、科室、智能体、医生详情全部改为缓存先显示+静默刷新。
4. 智能体目录增加离线状态和开始/继续咨询门禁。

## 八、必须增加的测试

### 8.1 契约测试

- context 正确返回当前 agent 的 Manifest，不包含未关联 KB。
- 智能体解绑 KB 后 manifest revision 变化并下发解绑标记。
- 按 KB ID 可拉正文、chunk、当前向量和 tombstone。
- 知识正文 revision 大于 indexed revision 时返回 stale，不将旧向量声明为当前。
- 智能体下架返回历史可读、发送/同步不可用。
- 成员撤权返回 `MEMBER_ACCESS_DENIED`，不返新消息和 Manifest。

### 8.2 iOS 单元测试

- 缓存 Manifest 命中时首屏立即可用，网络刷新在后台进行。
- 首次无 cursor 执行全量 pull，下次从最后 cursor 增量 pull。
- 一个 KB 拉取失败会清当前 agent 全部知识，不清其他 agent/个人知识。
- 解除关联后删除当前 agent 对应的正文、chunk、vector、cursor。
- stale 向量绝不参与语义检索，关键词检索仍可用。
- 同步失败时 Chat 发送仍可用。
- 下架智能体可看历史，所有发送入口都被阻断。
- 成员撤权后只显示旧缓存，不触发远程消息或 Manifest pull。
- context 网络失败且有本地 scope 时不降级普通 AI，发送仍走原 Thread。
- 医院列表第一家被选中，不再匹配固定 code。
- 医院列表空/失败自动切普通对话，但不自动新建普通 Thread。
- 智能体目录命中缓存先显示，刷新失败保留旧卡并标离线。

### 8.3 集成验收

1. 弱网打开已咨询医生，立即看到本地历史，不出现知识同步阻塞态。
2. 后台修改正文未重建向量，客户端下次进入拉新正文并只用关键词检索。
3. 后台手动重建向量后，客户端下次进入拉取当前 vector 并启用本地语义检索。
4. 后台解除知识绑定后，客户端下次进入删除当前 agent 下该 KB 缓存。
5. 删除医院 KB 后，客户端下次增量同步消费 tombstone，不再检索已删内容。
6. 下架智能体后可打开历史，但无法发送且不再同步知识。
7. 撤回成员权限后按 Demo 口径展示已有缓存，不拉远程数据，不允许发送。
8. 完全无网且有智能体目录缓存时，可打开“继续咨询”对应的本地会话；“开始咨询”不会离线伪造 Thread。

## 九、安全与 Demo 限定

以下是用户已明确选择、但不应默认带入正式医疗产品的 Demo 风险：

1. 知识库按 ID 公开读取，不做智能体绑定授权。
2. 成员权限撤回后仍展示设备已有会话/知识缓存。
3. 同步失败清空当前 agent 全部知识，可用性优先级低于简单一致性。
4. 医院列表直接取第一家，依赖服务端排序稳定。

因此正式上线门禁必须另行评审：本工单可用于演示验收，不能单独作为生产医疗安全验收证据。

## 十一、详细落地设计

### 11.1 实现前必须遵守的业务边界

#### 11.1.1 医院知识与个人知识必须物理分区

医院知识只能在医生智能体会话中被读取，不得出现在以下位置：

- 患者的个人知识库 Tab。
- 普通 AI 对话的本地检索。
- 其他医院、其他智能体或其他成员的检索结果。
- 患者知识库列表、个人知识搜索页和个人知识统计。

建议在本地数据层中使用独立实体、独立存储前缀或独立的持久化容器。即使复用现有 `KnowledgeDocument` 和 `KnowledgeChunk` 的字段，也必须在查询时强制带上 `source_scope = hospital_agent`，不能用一个可选来源字段在业务层混查。

#### 11.1.2 “公开读取”的 Demo 含义

本工单中“医院知识库全部公开读取”的实际含义是：

- 只要用户已登录，就可读取演示医院标记为可患者使用的医院科普知识库。
- 不需要在患者端再次做智能体与 KB 的授权判断。
- 这不等于匿名访问、互联网公开下载或读取医院所有内部资料。
- 后台必须保证只将患者科普内容放入该类知识库；这个工单不负责在 iOS 端补救误上传的院内受限资料。

#### 11.1.3 医院知识库的删除和解绑不是同一件事

| 事件 | 服务端含义 | iOS 目标行为 |
| --- | --- | --- |
| 智能体解除 KB 关联 | KB 仍存在，其他智能体可继续关联 | 只删除该 agent scope 下的正文、chunk、vector、Manifest 关联和 cursor |
| KB 被后台删除 | KB 全局失效 | 各 agent 在后续同步消费 tombstone，分别清理自己的 scope |
| 智能体下架 | agent 不再接受新询问 | 历史可读，禁止发送和知识同步，不必立刻删本地历史 |
| 成员权限撤回 | 当前成员不再有远程操作资格 | Demo 保留已有本地缓存，禁止远程拉取和发送 |

### 11.2 服务端契约详细要求

#### 11.2.1 会话 context 返回完整能力状态

会话 context 应当是一次返回“会话是谁的”和“现在能做什么”，避免 iOS 根据多个接口自行拼装状态。

建议响应结构：

```json
{
  "thread_id": "uuid",
  "hospital": { "id": "uuid", "name": "...", "introduction": "..." },
  "department": { "id": "uuid", "name": "..." },
  "doctor": { "id": "uuid", "display_name": "...", "title": "...", "avatar_url": "..." },
  "agent": {
    "id": "uuid",
    "name": "...",
    "publication_status": "published",
    "updated_at": "2026-09-02T10:00:00Z"
  },
  "member_id": 1001,
  "capabilities": {
    "can_read_cached_history": true,
    "can_pull_remote_messages": true,
    "can_send_message": true,
    "can_sync_knowledge": true,
    "read_only_reason": null
  },
  "knowledge_manifest": {
    "manifest_revision": 12,
    "generated_at": "2026-09-02T10:00:00Z",
    "knowledge_bases": []
  }
}
```

字段约束：

- `can_read_cached_history` 是本地已缓存数据是否可以继续展示，不等于允许拉取远程历史。
- `can_pull_remote_messages` 是是否允许从服务端获取新的会话消息。
- `can_send_message` 是所有发送入口的统一门禁。
- `can_sync_knowledge` 是是否允许读取和更新当前 agent 的知识 Manifest。
- `read_only_reason` 必须是稳定枚举，不允许客户端解析中文错误文案。
- `knowledge_manifest = null` 只能表示该会话没有医院知识绑定；不能表示请求失败。请求失败必须走 HTTP/业务错误。

#### 11.2.2 Manifest 的生成规则

Manifest 由服务端根据当前生效绑定实时计算，不建议由 iOS 根据已缓存的智能体详情自行组装。

Manifest 至少包含：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `manifest_revision` | integer | 当前 agent 关联集合的版本；解绑、新增、顺序变更都必须变更 |
| `knowledge_base_id` | UUID | 底层 `KnowledgeBase` ID，客户端不创建新 ID |
| `name` | string | 用于调试和本地引用，不作权限判定 |
| `revision` | integer | 知识正文当前版本 |
| `vector_status` | enum | `not_built`、`current`、`stale` |
| `indexed_revision` | integer/null | 服务端已构建向量对应的正文 revision |
| `updated_at` | datetime | 该 KB 最后修改时间 |

Manifest 中不应放入：

- 医院后台登录信息、服务账号或内部权限信息。
- 与患者无关的其他智能体、其他科室或其他医院的 KB ID。
- 不必在 Manifest 中直接放所有正文；正文由 pull 接口分页返回。

#### 11.2.3 KB pull 返回结构

建议使用与现有个人知识 pull 相同的增量语义，但路由和授权范围单独。

```json
{
  "knowledge_base_id": "uuid",
  "revision": 8,
  "vector_status": "current",
  "indexed_revision": 8,
  "cursor": "opaque-token",
  "has_more": false,
  "documents": [
    {
      "id": "uuid",
      "title": "门诊就诊须知",
      "content": "...",
      "excerpt": "...",
      "revision": 3,
      "is_deleted": false,
      "updated_at": "2026-09-02T10:00:00Z",
      "chunks": [
        {
          "id": "uuid",
          "sequence": 0,
          "content": "...",
          "content_hash": "sha256",
          "document_revision": 3,
          "vector_payload": [0.01, -0.02],
          "embedding_binding_id": 123
        }
      ]
    }
  ]
}
```

返回规则：

1. 首次请求 `cursor` 为空，服务端返回该 KB 的当前全量快照。
2. 后续请求使用最后成功保存的 opaque cursor。
3. cursor 失效、过期或与 revision 不匹配时，返回稳定业务码，客户端删除该 scope cursor 后重做全量同步。
4. 正文删除必须以 `is_deleted=true` 返回 tombstone，不能只是不再返回该文档。
5. 同一个文档的 chunks 必须与其返回的 `document_revision` 一致。
6. 无向量时 `vector_payload` 返回空数组或空值，不能使用旧 revision 的向量。
7. 服务端修改正文后立即增加 revision；不等待向量生成。

#### 11.2.4 业务错误码

| 业务码 | 触发条件 | iOS 处理 |
| --- | --- | --- |
| `HOSPITAL_NOT_FOUND` | 医院不存在或已停用 | 会话不能继续作为院内会话，按医院目录失效处理 |
| `AGENT_NOT_PUBLISHED` | 智能体已下架 | 历史可读，禁止发送，停止知识同步 |
| `MEMBER_ACCESS_DENIED` | 成员权限撤回 | Demo 保留已有缓存，禁止远程消息、Manifest 和发送 |
| `HOSPITAL_KNOWLEDGE_NOT_FOUND` | KB 不存在、已删除或不可读 | 按当前 agent 的同步失败处理，清空该 scope 全部知识 |
| `HOSPITAL_KNOWLEDGE_CURSOR_INVALID` | cursor 不可继续使用 | 只清该 KB cursor，下次该 KB 全量同步 |
| `HOSPITAL_KNOWLEDGE_VERSION_CONFLICT` | 服务端发现版本不一致 | 废弃当前批次，重读 Manifest；不使用旧 vector 冒充 |
| `HOSPITAL_KNOWLEDGE_SYNC_UNAVAILABLE` | 知识同步服务暂不可用 | 清理当前 agent 知识缓存，但不阻塞在线咨询 |

HTTP 状态只用于传输层分类，业务处理以稳定错误码为准。

### 11.3 iOS 组件和职责拆分

#### 11.3.1 Domain 模型

```text
HospitalAgentKnowledgeScope
  accountID
  hospitalID
  agentID
  memberID

HospitalAgentKnowledgeManifest
  agentID
  hospitalID
  manifestRevision
  generatedAt
  items: [HospitalKnowledgeManifestItem]

HospitalKnowledgeManifestItem
  knowledgeBaseID
  name
  revision
  vectorStatus
  indexedRevision
  updatedAt
  isUnbound

HospitalKnowledgeSyncState
  idle
  loadingCachedManifest
  refreshingManifest
  syncingKnowledge
  ready
  keywordOnly
  clearedAfterFailure
  pausedByAgentStatus
  pausedByMemberAccess
  cancelledByAccountSwitch

HospitalKnowledgeSearchMode
  vector
  keyword
  unavailable
```

`memberID` 是会话与会员边界的一部分，但知识库正文本身是医院资产。建议缓存 scope 仍然带上 `memberID`，这样撤权后可以精确清理会话范围，不把成员 A 的医疗会话知识缓存视为成员 B 可用。

#### 11.3.2 Remote API 职责

`HospitalKnowledgeRemoteAPI` 只负责：

- 请求当前会话 context，或消费 context 中的 Manifest。
- 按 `knowledgeBaseID + cursor` 拉取一页只读数据。
- 传回稳定的传输错误和业务错误。
- 不保存 cursor，不决定是否清缓存，不直接操作 Core Data。

#### 11.3.3 Repository 职责

`HospitalKnowledgeRepository` 负责：

- 按 scope 保存和读取 Manifest。
- 按 scope + KB 保存最后成功 cursor。
- 原子写入 document/chunk/vector，或原子删除 scope。
- 根据 `documentRevision` 删除并重建当前 chunks。
- 无条件删除一个 agent scope 的全部医院知识。
- 提供检索：向量可用时语义检索，否则关键词/全文检索。

Repository 不负责：

- 个人知识的 Push、Outbox 和本地编辑。
- 根据用户输入自动创建医院文档。
- 没有服务端向量时自动请求 Embedding 模型。

#### 11.3.4 Coordinator 职责

`HospitalKnowledgeSyncCoordinator` 负责同步生命周期：

1. 以 `accountID + threadID` 作为会话运行单位。
2. 以 `agentID` 作为知识清理的原子范围。
3. 同一 scope 同一时刻只允许一个 Manifest 刷新和一个 KB 同步任务。
4. 切换会员、账号、Thread 或 agent 时取消旧 Task。
5. 所有异步回调写入前重新校验 generation。
6. 不向 ChatView 发送“请等待同步”的阻塞信号；ChatView 只消费可选的本地检索能力。

### 11.4 同步事务的原子性

#### 11.4.1 Manifest 和正文不能分裂成可见的部分状态

对一个 agent scope 的同步使用两个层次：

```text
remote response
  -> temporary staging
  -> validate all documents/chunks/vector revisions
  -> transaction commit documents + chunks + vectors + cursor
  -> transaction commit Manifest revision
```

如果任一文档校验失败：

- 不能只写入已经处理的前 N 个文档。
- 不能推进 cursor。
- 不能更新 Manifest 为“已成功”。
- 按 Q25 清理当前 agent scope 下已有全部医院知识。

#### 11.4.2 同步顺序

```text
1. 读取已缓存 Manifest
2. 读取当前会话 context
3. 校验 agent/hospital/member 身份和 capabilities
4. 比较 manifest_revision
5. 列出当前需要同步的 KB
6. 各 KB 使用各自 scope cursor 执行 pull
7. 所有 KB 成功后更新可检索状态
8. 任一 KB 失败则清当前 agent 全部医院知识
```

Manifest 初次加载和 KB 正文同步可以并行，但必须有最终的 manifest revision 一致性校验；不能在新 Manifest 还没有完成时把它宣告为当前可用。

#### 11.4.3 解绑后本地清理

当后台解除 agent 与 KB 的绑定后：

1. 会话下次读取到新 Manifest。
2. 找出旧 Manifest 中有、新 Manifest 中无的 KB ID。
3. 清理当前 agent + 该 KB 的正文、chunk、vector、cursor。
4. 如果新 Manifest 返回解绑 tombstone，使用 tombstone 完成同一步清理。
5. 其他 agent 对同一 KB 的缓存不得被清理。

### 11.5 会话页实际行为

#### 11.5.1 打开页面

1. `ChatView` 根据已有 scope 先确认是否为医院会话。
2. 本地消息、首条医生身份卡、本地 Manifest 可同时显示。
3. 不显示“正在同步知识库”、“还有 N 个文档”、“向量生成中”等提示。
4. 缓存未命中也不应阻塞会话页。
5. 在后台任务中刷新 context，然后再判断是否允许同步。

#### 11.5.2 发送消息

所有消息发送路径统一经过：

```text
canSendMessage == true
  -> 进入原有 Chat 发送流程
canSendMessage == false
  -> 不创建本地伪消息
  -> 不转普通 AI
  -> 展示已下架/已失去成员权限的稳定状态
```

需要同时检查：

- 普通输入框的 onSend。
- 图片、文件和附件发送。
- 快捷按钮、小任务和语音发送。
- 成员切换后发送时的最终状态。

服务端仍然是最后一道校验；客户端的 capability 不能代替服务端权限。

#### 11.5.3 会话内右上角“新建对话”

- 从医生智能体会话点击：复用现有按钮，创建新 Thread 时传入当前 `agent_id` 和输入框当前 `member_id`。
- 从下架或成员权限失效的会话点击：禁止继承创建，不创建普通 AI 会话。
- 从普通会话点击：继续原有普通新建流程。
- 创建请求失败：留在当前页面，不转普通会话，不伪造绑定。

### 11.6 缓存、切换与生命周期

#### 11.6.1 医院目录缓存

医院、科室、智能体和医生详情统一使用：

```text
read cache
  -> 有值：立即返回 UI + 启动后台刷新
  -> 无值：请求网络，成功后写入缓存
  -> 刷新失败：保留旧值，标记该页为离线数据
```

缓存内容必须包含请求参数的完整快照，不能用一个无参数 `agents` 数组复用到所有搜索和科室条件下。

#### 11.6.2 缓存键和请求取消

| 对象 | 建议缓存键 |
| --- | --- |
| 医院列表 | `accountID` |
| 科室列表 | `accountID + hospitalID` |
| 智能体目录 | `accountID + hospitalID + departmentID? + normalizedKeyword` |
| 医生详情 | `accountID + agentID` |
| 会话 Manifest | `accountID + threadID + hospitalID + agentID + memberID` |
| 医院知识正文 | `accountID + hospitalID + agentID + memberID + knowledgeBaseID + documentID` |
| 切块/向量 | 与对应正文相同，另加 `documentRevision` |

每次切换账号或成员时：

1. 递增 generation。
2. 取消旧账号/成员的目录刷新、Manifest 刷新、KB pull 和本地检索任务。
3. 不允许旧任务回调写入新账号或新成员的缓存。
4. 账号退出时清理个人知识和医院知识的内存缓存；是否清持久化数据应沿用当前账号隔离政策。

#### 11.6.3 “先缓存后刷新”与“同步失败清空”的关系

两条规则并不矛盾：

- 目录数据刷新失败：保留旧目录。
- 医院知识同步任一 KB 失败：清空当前 agent 的医院知识。

因为目录卡片和知识正文的一致性风险不同：目录旧值可用于选择医生，而同步不完整的知识不应参与当前对话检索。

### 11.7 向量与关键词检索的精确规则

#### 11.7.1 向量可用条件

只有同时满足以下条件才能返回 `vector` 搜索：

1. 当前 agent scope 同步状态为 `ready`。
2. KB 的 `vector_status == current`。
3. `indexed_revision == revision`。
4. 切块的 `documentRevision == document.revision`。
5. 向量维度和当前查询向量一致。
6. 该 chunk 不属于已删除正文。

任一条不满足，该 chunk 不能参与语义排序。

#### 11.7.2 关键词/全文降级

降级检索只能在当前 agent scope 内进行：

- 先按文档标题、正文和切块建立匹配。
- 排序结果应包含文档 ID、标题、当前 revision 和匹配位置。
- 不得混入个人知识或其他 agent 的切块。
- 检索结果可在调试日志标记 `keyword_fallback`，但不在患者端显示向量失败文案。
- 如果同步失败后 scope 已清空，直接返回 `unavailable`，不返回旧的局部结果。

#### 11.7.3 禁止患者端自动生成医院向量

现有个人知识同步引擎在正文变更后可以调度本地 embedding，医院知识不能继承该行为。

医院知识的向量来源只能是：

1. 后台人工选择已启用且支持 Embedding 的模型。
2. 服务端构建成功后写入医院 chunk。
3. iOS 通过 pull 同步 `vector_payload`。

客户端不能因为 `vector_status=not_built` 自动调用 Embedding 模型；也不能因为没有服务端向量而把旧 revision 向量当成新正文向量。

### 11.8 智能体下架、成员撤权、断网的状态详情

#### 11.8.1 下架

1. 进入会话先用本地消息和身份卡首屏展示。
2. context 返回 `publication_status != published` 或 `can_send_message=false`。
3. 禁止所有新消息发送。
4. 不再拉取新消息、Manifest 和 KB 内容。
5. 不把该会话改成普通 AI 会话。
6. “新建对话”操作显示失败或禁用，不能继承已下架 agent。

#### 11.8.2 成员权限撤回

Demo 次序：

1. 以本地缓存打开历史消息。
2. 后台 context 返回 `MEMBER_ACCESS_DENIED`。
3. 停止消息远程拉取、Manifest 刷新、KB pull 和发送。
4. 保留设备已有消息和医院知识缓存。
5. 切换成员后不得使用该成员的旧缓存。

这是用户确认的 Demo 行为，但属于正式医疗产品上线前的强制风险审查项。

#### 11.8.3 context 网络超时/失败

分两种情况：

| 条件 | 目标行为 |
| --- | --- |
| 有本地 hospital scope | 允许打开和尝试原 Thread 发送；不刷新 Manifest；不转普通 AI |
| 无本地 hospital scope，但有本地 Chat Thread | 只按普通本地 Thread 展示；不执行医院绑定新建；等待重试 context |
| 同步 KB 失败 | 清空当前 agent 知识，但在线 Chat 继续可用 |
| 普通对话网络失败 | 沿用原有 Chat 离线语义，不应因为医院知识失败修改普通对话 |

### 11.9 医院列表和院内名医目录详细改造

#### 11.9.1 医院选择

Q30 已明确“取医院列表第一家”，因此：

- 该逻辑不应使用医院 code 、固定 UUID 或医院名称匹配。
- 必须使用服务端返回顺序，缓存数组也必须保留顺序。
- 应在日志中记录选中的 hospital ID 和名称，方便演示联调检查。
- 后台如果修改首位医院，属于演示配置行为，不是 iOS 错误修复。

#### 11.9.2 医院列表失败与智能体目录失败要分开

| 失败对象 | 有缓存 | 无缓存 |
| --- | --- | --- |
| 医院列表 | 使用缓存的第一家，后台刷新失败保留院内分段 | 自动切换普通对话，不新建 Thread |
| 智能体目录 | 展示缓存卡片并标离线 | 展示重试，不伪造智能体或会话 |
| 医生详情 | 展示缓存详情，后台静默更新 | 展示加载失败和重试 |

Q31 只针对“医院列表为空或无缓存加载失败”时回退普通对话。不能把智能体目录的单次请求失败也直接解释为需要切换普通对话。

#### 11.9.3 智能体卡片“开始”与“继续”

- `继续咨询`：只要已有最近会话 ID，就可打开该本地会话；如需网络发送，发送时再由服务端校验。
- `开始咨询`：必须联网请求创建医院会话；离线不能只在本地生成一个“看起来像医生会话”的 Thread。
- 服务端创建失败时保留卡片，不改变已存在的普通会话。

### 11.10 开发实施拆分

#### Sprint 1：服务端患者契约

1. 定义 context capabilities 和 Manifest JSON 结构。
2. 实现患者端 KB ID pull 和稳定业务码。
3. 完成当前 agent 会话下的 KB 集合计算。
4. 覆盖新建、解绑、修改正文、删除、未生成向量、向量过期、下架和成员撤权测试。

#### Sprint 2：iOS 只读知识基础

1. 创建 HospitalCare 知识 Domain DTO 和 Repository 接口。
2. 抽取个人 Knowledge 引擎的通用增量 pull 基础。
3. 建立独立的医院 scope 缓存，先实现正文、chunk、vector、cursor 的只读落库。
4. 加入事务回滚、tombstone 和按 agent 原子清理。

#### Sprint 3：会话页静默同步

1. 在 ChatView 进入时启动 coordinator。
2. 优先读取本地 Manifest，不阻塞首屏。
3. 后台刷新 context，根据 capability 停止或继续同步。
4. 将同步失败、解绑、下架、撤权接入现有 Chat 发送门禁。

#### Sprint 4：检索与目录缓存

1. 接入向量有效性校验和关键词降级。
2. 补齐医院、科室、智能体、医生详情的缓存先显示+后台刷新。
3. 按 Q30 改为取医院列表第一家。
4. 按 Q31 实现医院列表无法读取时切普通对话。

#### Sprint 5：联调和回归

1. 实时修改 KB 正文，验证下一次进入会话能拉到新 revision。
2. 手动重建向量，验证客户端下一次同步才启用新 vector。
3. 解绑、删除、下架、成员撤权、断网、切换会员全量验收。
4. 出现任意跨 agent 、跨成员或跨普通对话的数据泄露时，工单不能关闭。

## 十二、当前不应实现的内容

为避免本工单扩大范围，以下暂不实现：

- 医院后台新的权限角色、审核流程和工单审批。
- 患者上传原始病历、自动脱敏或病例知识化。
- 症状导诊、风险评分 UI 改造或新的医疟诊疗建议流程。
- 患者端自动生成医院知识向量。
- 医院知识同步进度、文档数量、向量状态等患者可见 UI。
- 把医院知识添加到个人 Knowledge Tab 或普通 AI 对话。

## 十三、待产品负责人补充的唯一问题

Q37 尚未确认：同一个医院 KB 被多个医生智能体关联时，本地 cursor 是否按 agent scope 分别存储，还是按 hospital + KB 共享。

本工单默认推荐按 agent scope 分别存储，原因是解绑、清理、会话隔离和演示验收最清晰。如果后续确认改为共享，必须另行补充数据引用计数、关联解除清理、权限撤回与跨 agent 使用的一致性规则，不能只改一个 cache key。
