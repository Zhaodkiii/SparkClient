## 1. 问题描述

医院智能体创建会话接口已经返回 `initial_messages`，但患者端进入新会话后，消息列表为空或没有显示医生简介系统卡。用户实际复现路径为：

1. 创建医院智能体会话。
2. 进入会话，观察首条医生简介卡。
3. 返回会话列表。
4. 再进入另一个医院智能体并观察。
5. 返回后再次进入其他医院智能体。

现象：接口请求成功，但医生简介业务卡没有稳定插入消息列表。

本工单当前只增加临时诊断日志，不提前改变业务逻辑。待用户本地复现并回传日志后，再根据完整事件链实施最小修复。

## 5. 当前待验证原因

### 假设 A：医院初始消息没有被页面取出

如果出现 `initial_messages_mapped`，但没有 `initial_messages_taken`，说明创建用例和页面任务之间存在暂存丢失、Thread ID 不一致或页面生命周期竞争。

### 假设 B：初始消息被取出，但异步入站没有执行完成

如果有 `initial_messages_apply_start`，没有 `inbound_merge_start/end`，说明 Task 被取消、对象生命周期失效或调用链没有进入统一入站层。

### 假设 C：消息进入入站管线，但 DTO/block kind 映射丢失

如果 `raw > mapped`，或 `kinds` 中没有医院医生简介卡对应的 kind，问题在服务端 DTO 映射或 block payload 解码，而不是 UI。

### 假设 D：已经落库，但 UI 没有读取

如果 `inbound_merge_end persisted > 0` 且包含医院简介卡 kind，但没有 `database_event` 或 `ui_messages_reloaded`，问题在通知过滤、当前 Thread 判断或后台线程发布时序。

### 假设 E：多次进入导致旧任务影响新 Thread

如果旧 Thread 的 apply/reload 日志出现在新 Thread 切换之后，需要检查 `.task(id:)` 取消边界和异步闭包是否在写入错误的当前页面状态。

### 假设 F：创建响应和普通 pull 重复竞争

如果同一个新 Thread 同时出现 `initial_messages_apply_start` 和 `pull_start`，需要确认是否发生重复拉取、cursor 覆盖或合并通知顺序竞争。

## 7. 日志诊断结论

本次复现已经确认：

1. 创建 A、B、C 时，服务端均返回 `initial_messages=2`，且客户端映射数量均为 `2`。
2. 页面均成功消费对应 Thread 的初始消息，`initial_messages_taken present=true count=2`。
3. 入站消息中明确包含 `hospitalDoctorIntroCard,text`。
4. `inbound_merge_end` 明确显示 `persisted=2`，证明简介卡已写入 Core Data。
5. `initial_messages_apply_end` 之前曾显示 `local_count=0`，说明入站落库完成后 `ChatStateStore` 仍持有旧消息快照。
6. 随后的数据库通知/延迟刷新有时能将数量更新为 `2`，但 UI 更新依赖异步通知和当前 SwiftUI/UIKit 生命周期，因此产生“已落库但页面不显示或显示不稳定”的表现。
7. `No symbol named '123' found in system symbol set` 是系统符号/上下文菜单相关日志，与简介卡业务链路无关。

结论：问题不是医院简介卡生成、接口返回、DTO 映射或 Core Data 入库失败，而是初始消息专用入站路径没有在落库完成后同步刷新 `ChatStateStore`，把 UI 更新交给数据库通知导致时序不稳定。

## 11. 第二轮复现补充诊断（2026-09-05）

在第一轮增加“入站后显式重读”后，用户再次新建医院智能体会话，仍未看到简介卡。第二轮日志显示：

```text
create_response ... initial_messages=2
initial_messages_mapped ... raw=2 mapped=2
initial_messages_taken ... present=true count=2
ui_messages_reloaded ... count=0
initial_messages_apply_start ... count=2
```

但本次日志没有继续出现：

```text
apply_fetched_messages
inbound_merge_start
inbound_merge_end
initial_messages_apply_end
```

因此第二轮失败发生在初始消息已经被 `ChatView` 消费之后、进入 `ChatSyncSupervisor.applyAlreadyFetchedMessages` 之前。原实现把 `applyHospitalInitialMessages` 放在 `.task(id: currentThreadID)` 内新建的非结构化嵌套 `Task` 中：

```swift
if let hospitalInitialMessages {
    Task {
        await detailViewModel.applyHospitalInitialMessages(...)
    }
}
```

该方式使会话初始化主流程不会等待初始消息入站完成；页面切换、视图生命周期更新或并行初始化发生时，初始消息处理可能只执行到任务起点，后续时序不可由当前会话初始化流程保证。

第二轮修复将其改为当前 `.task(id:)` 内的直接 `await`：

```swift
if let hospitalInitialMessages {
    await detailViewModel.applyHospitalInitialMessages(
        hospitalInitialMessages,
        threadID: id
    )
}
```

新的确定性顺序为：

```text
消费 initial_messages
  ↓
本地首次读取（允许为空）
  ↓
直接 await 初始消息统一入站
  ↓
Core Data upsert
  ↓
显式重读当前 Thread
  ↓
ChatStateStore 已包含简介卡
  ↓
继续医院 scope/context/Manifest 初始化
```

该调整没有新增接口、存储、消息类型或状态机，只收紧现有新建医院会话初始化的并发边界。历史会话没有 `hospitalInitialMessages`，仍走原有加载和增量同步流程。
