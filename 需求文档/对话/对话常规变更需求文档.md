## 工单 `CHAT-000001`：发送前检查聊天场景模型并统一打开 API Keys 设置

### 工单状态

已实现能力补充需求归档。后续如需要改文案或统一 Sheet 接入方式，可在本工单下追加变更记录。

## 1. 背景

### Q：为什么需要在发送对话前检查聊天模型？

A：当前会话页输入区可以直接触发发送，但如果聊天场景没有可用模型，用户会在发送链路后段才遇到失败。这个反馈时机太晚，也不利于引导用户去配置模型密钥或启用模型。

现网在会话列表页新建对话时已经有类似保护：

- `ChatConversationListPage.swift:72-79`：无可用模型时弹出 `chat.list.no_available_model.*` 提示。
- `ChatConversationListPage.swift:80-91`：点击“前往设置”后用 Sheet 打开 `APIKeysSettingsView`。

会话详情页也应复用同一套文案与设置入口，在用户点击发送前先做轻量校验。

### Q：这次常规变更解决什么问题？

A：

1. 发送前即可发现“聊天场景没有可用模型”的问题。
2. 与新建会话入口保持一致的用户提示。
3. 避免进入 `SendChatMessageUseCase` 后才失败，减少无效发送状态、流式状态和错误气泡。
4. 会话内所有 Sheet 入口统一收敛到 `ToolInteractionPresentationSheet`，避免 `ChatView` 持续增加多个 `.sheet` 状态。

## 2. 目标

### Q：一句话需求是什么？

A：用户在会话内点击发送时，先检查聊天场景模型列表是否为空；如果没有可用聊天模型，则不发送消息，弹出“无可用对话模型”提示；用户点击“前往设置”后，通过会话内统一的 `ToolInteractionPresentationSheet` 打开 `APIKeysSettingsView`。

### Q：判定“没有可用聊天模型”的数据来源是什么？

A：以现有聊天场景模型列表为准：

- `AIConfigModels.swift:532-533`：`AIScenarioRemoteBundlesCollection.chat` 是聊天场景模型集合。
- `ChatDetailViewModel.swift:307-317`：`refreshChatModelPicker(for:)` 从 `effectiveScenarioBundles().chat.models` 更新 `chatScenarioModels`。
- `ChatView.swift:107`：`HanlinChatComposerView` 当前已接收 `detailViewModel.chatScenarioModels`。

需求判定建议：`detailViewModel.chatScenarioModels.isEmpty == true` 时视为当前会话没有可用聊天模型。

## 3. 交互流程

### Q：用户点击发送时的流程是什么？

A：

1. 用户点击输入区发送按钮。
2. `ChatView` 的 composer `onSend` 回调被触发。
3. 先收起键盘。
4. 检查当前聊天场景模型列表是否为空。
5. 如果不为空：继续调用 `detailViewModel.startSendingCurrentDraft()`。
6. 如果为空：不进入发送链路，弹出“无可用对话模型”提示。
7. 用户点击“前往设置”：打开 API Keys 设置页。
8. 用户点击“取消”：关闭弹窗，不发送消息。

流程示意：

```text
点击发送
  ↓
KeyboardDismissHelper.dismissKeyboard()
  ↓
chatScenarioModels 是否为空？
  ├─ 否 → detailViewModel.startSendingCurrentDraft()
  └─ 是 → showNoAvailableChatModelAlert = true
              ↓
          [前往设置] → ToolInteractionPresentationSheet → APIKeysSettingsView
          [取消]     → 关闭 Alert
```

### Q：哪些 Composer 样式需要检查？

A：都需要。

- `ChatView.swift:75-99`：`.signal` 样式的 `ChatComposerView(onSend:)`。
- `ChatView.swift:100-145`：`.hanlin` 样式的 `HanlinChatComposerView(onSend:)`。

两个入口都应走同一个发送前检查方法，避免双分支逻辑漂移。

建议抽出 `private func sendCurrentDraftIfChatModelAvailable()`，两个 `onSend` 均调用它。

## 4. 弹窗需求

### Q：弹窗文案是什么？

A：复用会话列表页现有本地化文案：

```swift
.alert(L10n.text("chat.list.no_available_model.title"), isPresented: $showNoAvailableChatModelAlert) {
    Button(L10n.text("chat.list.no_available_model.action")) {
        // 打开 API Keys 设置
    }
    Button(L10n.text("common.cancel"), role: .cancel) {}
} message: {
    Text(L10n.text("chat.list.no_available_model.message"))
}
```

当前已有文案：

| Key | 中文含义 |
| --- | --- |
| `chat.list.no_available_model.title` | 无法新建/发送对话 |
| `chat.list.no_available_model.message` | 当前没有可用的对话模型，请先配置模型密钥或启用可用于对话的模型 |
| `chat.list.no_available_model.action` | 前往设置 |
| `common.cancel` | 取消 |

### Q：标题是否要继续使用“无法新建对话”？

A：短期可复用现有 key，保证列表页和会话页体验一致；但从语义上看，会话内更准确的标题应是“无法发送消息”。如果后续希望更精确，可新增：

- `chat.detail.no_available_model.title`
- `chat.detail.no_available_model.message`
- `chat.detail.no_available_model.action`

第一期建议先复用现有 key，减少本地化改动面。

## 5. API Keys 设置页打开方式

### Q：为什么会话内不直接新增 `.sheet(isPresented:)`？

A：`ChatView` 当前已经有统一的工具/对话交互 Sheet：

- `ChatView.swift:354-391`：通过 `detailViewModel.toolInteractionCoordinator.activePresentation` 驱动 `.sheet(item:)`。
- `ChatToolInteractionSheets.swift:641-720`：`ToolInteractionPresentationSheet` 根据 `ToolInteractionSnapshot` 分发具体页面。
- `ToolInteractionCoordinator.swift:4-7`：协调器目标是串行处理同一时间只能出现一个交互窗口。

如果在 `ChatView` 里再新增一个 `showAPIKeysSettingsSheet`，会带来多个 Sheet 状态并存的问题：工具授权、问报告、系统消息设置、API 设置可能互相抢展示。会话内应统一进入 `ToolInteractionPresentationSheet`。

### Q：需要怎么接入统一 Sheet？

A：建议新增一个非阻塞展示类型：

```swift
enum ToolInteractionSnapshot {
    case apiKeysSettings
}
```

并在 `ToolInteractionCoordinator` 增加：

```swift
func presentAPIKeysSettings()
```

`apiKeysSettings` 与 `toolPreview`、`systemMessageSettings`、`askReportPicker` 一样属于“只展示，不阻塞工具执行 continuation”的 Sheet 类型。

`requiresForcedSheetDismiss` 建议返回 `false`，允许用户下滑关闭。

### Q：`ToolInteractionPresentationSheet` 里怎么展示？

A：新增 case：

```swift
case .apiKeysSettings:
    CompatibleNavigationContainer(legacyStackStyle: true) {
        APIKeysSettingsView(viewModel: aiSettingsViewModel)
            .toolbar {
                ToolbarItem(placement: .cancellationAction) {
                    Button(L10n.text("common.done")) {
                        coordinator.dismissAPIKeysSettings(id: active.id)
                    }
                }
            }
    }
```

注意：`ToolInteractionPresentationSheet` 当前没有 `AISettingsViewModel` 依赖，需要从 `ChatView` 或 `ChatDetailViewModel` 挂入。不要在 Sheet 内临时 new 一个设置 ViewModel，避免状态、加载时机和依赖来源不一致。

## 6. 状态设计

### Q：`ChatView` 需要新增哪些状态？

A：建议只新增 Alert 状态：

```swift
@State private var showNoAvailableChatModelAlert = false
```

不建议新增：

```swift
@State private var showAPIKeysSettingsSheet = false
```

原因：会话内设置页打开应走 `ToolInteractionCoordinator`，而不是 `ChatView` 本地 `.sheet`。

### Q：发送前检查方法放在哪里？

A：建议放在 `ChatView` 内，原因是：

1. `ChatView` 同时拥有 composer 回调和 `detailViewModel.chatScenarioModels`。
2. 这个检查是 UI 交互门禁，不属于真正发送业务。
3. 可以同时覆盖 `.signal` 和 `.hanlin` 两种 composer。

建议方法：

```swift
private func sendCurrentDraftIfChatModelAvailable() {
    KeyboardDismissHelper.dismissKeyboard()
    guard detailViewModel.chatScenarioModels.isEmpty == false else {
        showNoAvailableChatModelAlert = true
        return
    }
    detailViewModel.startSendingCurrentDraft()
}
```

两个 `onSend` 从：

```swift
KeyboardDismissHelper.dismissKeyboard()
detailViewModel.startSendingCurrentDraft()
```

替换为：

```swift
sendCurrentDraftIfChatModelAvailable()
```

## 8. 实现方式建议

### 8.1 ChatView 发送入口收敛

`ChatView.swift:75-146` 当前两个 composer 分支都内联调用发送。建议改为统一方法，避免后续一个入口漏检查。

关键点：

1. 先收键盘。
2. 再判断 `chatScenarioModels`。
3. 为空时只弹 Alert，不清空草稿、不上传附件、不触发发送状态。
4. 不为空时保持现有发送逻辑。

### 8.2 Alert 打开设置页

Alert 的“前往设置”按钮不直接控制本地 sheet，而是调用：

```swift
detailViewModel.toolInteractionCoordinator.presentAPIKeysSettings()
```

如果后续希望隐藏 coordinator 细节，也可以在 `ChatDetailViewModel` 增加薄封装：

```swift
func presentAPIKeysSettings() {
    toolInteractionCoordinator.presentAPIKeysSettings()
}
```

### 8.3 ToolInteractionPresentationSheet 传入 AISettingsViewModel

现网列表页 `ChatConversationListPage.swift:80-91` 直接使用 `aiSettingsViewModel` 创建 `APIKeysSettingsView`。

会话内若复用同一个页面，也需要能拿到同一个设置 ViewModel。推荐从上层注入：

```swift
ToolInteractionPresentationSheet(
    active: active,
    coordinator: detailViewModel.toolInteractionCoordinator,
    ...
    aiSettingsViewModel: aiSettingsViewModel
)
```

如果 `ChatView` 当前没有该依赖，需要从组装层补齐，而不是在子 View 内创建新实例。

## 9. 验收标准

### 功能验收

1. 当 `chatScenarioModels` 不为空时，点击发送行为与现网一致。
2. 当 `chatScenarioModels` 为空时，点击发送不进入 `startSendingCurrentDraft()`。
3. 无模型时弹出 `chat.list.no_available_model.*` 对应提示。
4. 点击“取消”关闭弹窗，草稿、附件、问报告预览保持不变。
5. 点击“前往设置”后，通过 `ToolInteractionPresentationSheet` 打开 `APIKeysSettingsView`。
6. API Keys 设置页点击“完成”后关闭 Sheet。
7. 设置页关闭后，原会话页面状态保持，不丢失输入内容。
8. `.signal` 与 `.hanlin` 两种 composer 都能触发同样检查。

### 状态验收

1. 无模型 Alert 展示期间，不创建用户消息。
2. 不启动附件上传。
3. 不启动 OCR。
4. 不启动 AI 流式请求。
5. 不新增空 assistant 占位消息。
6. 不影响工具授权、问报告、系统消息设置等已有 `ToolInteractionPresentationSheet` 队列展示。

### 回归验收

1. 会话列表页原有“无可用模型 → 前往设置”流程不受影响。
2. 已有 `ToolInteractionPresentationSheet` case：授权、问题、成员选择、工具预览、系统消息设置、问报告选择均可正常打开和关闭。
3. 配置模型后返回会话，重新刷新模型列表后可正常发送。

## 10. 风险与注意事项

### Q：只检查 `chatScenarioModels.isEmpty` 是否足够？

A：第一阶段足够，因为 `refreshChatModelPicker(for:)` 的数据源就是 `effectiveScenarioBundles().chat.models`。但需要注意：如果模型列表不为空，但实际 API Key 不可用，发送仍可能失败。这个属于运行时调用失败，不应在本需求内扩大处理范围。

### Q：如果进入会话时模型列表还没刷新完成怎么办？

A：现网 `ChatView.swift:343-349` 已在 `.task(id: threadID)` 中刷新模型选择器。发送前检查使用当前 `chatScenarioModels`。如果担心刚进入页面时列表尚未完成加载，可以在发送前补一次轻量刷新：

```swift
if detailViewModel.chatScenarioModels.isEmpty {
    _ = await detailViewModel.refreshChatModelPicker(for: threadID)
}
```

但这会把发送方法变成 async，第一期建议先根据现有刷新结果判断，除非产品明确要求“刚进入页面立即点发送也必须等待刷新完成”。

### Q：为什么不把检查放到 `SendChatMessageUseCase`？

A：`SendChatMessageUseCase` 仍然应该保留后端式防御，避免无模型时真正发送。但用户体验层面的 Alert 和设置页跳转属于 UI 门禁，放在 `ChatView` 更合适。  

最终建议是双层保护：

1. UI 层：提前提示并引导设置。
2. UseCase 层：如果仍无模型，抛出明确错误，避免异常状态。

## 工单 `CHAT-000002`：会话列表支持图标编辑与置顶排序

### 工单状态

已实现。默认直发 AI 使用压缩图；“发送原图给 AI”只作为当前会话页临时开关，不持久化。

### 1. 背景

### Q：为什么会话需要图标、编辑和置顶？

A：当前会话列表 `ChatConversationListPage` 只展示标题、时间、最近消息预览和可选图片缩略图，列表行的长按菜单与滑动操作也只支持删除。随着会话数量增加，用户需要更快地区分常用会话、重要会话和不同用途的会话。

参考 `hanlin-ai` 旧实现：

1. 列表按 `isPinned` 分组，置顶会话显示在未置顶会话上方。
2. 会话卡片展示 icon / title / 时间 / 预览。
3. 长按菜单支持编辑图标、置顶/取消置顶、删除。
4. 左滑/右滑支持快捷置顶、编辑、删除。
5. 编辑 Sheet 支持修改标题、图标、颜色。

### Q：本工单目标是什么？

A：在 SparkClient 当前会话列表中补齐会话个性化和常用会话管理能力：

1. `ChatThread` 增加会话图标相关字段。
2. 会话列表支持置顶/取消置顶。
3. 会话列表支持编辑标题、图标、颜色。
4. 列表排序支持置顶优先。
5. 客户端、服务端、CoreData、本地序列化、同步链路都能保存并恢复这些字段。

## 3. 数据模型需求

### Q：`ChatThread` 需要增加哪些字段？

A：建议最小可用字段如下：

```swift
struct ChatThread: Identifiable, Codable, Equatable, Sendable {
    let iconName: String?
    let iconColorName: String?
    let isPinned: Bool
    let pinnedAt: Date?
}
```

字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `iconName` | `String?` | SF Symbol 名称，例如 `bubble.left.circle`、`heart.text.square` |
| `iconColorName` | `String?` | 客户端约定色值 key，例如 `blue`、`green`、`pink`；避免直接存 SwiftUI `Color` |
| `isPinned` | `Bool` | 是否置顶 |
| `pinnedAt` | `Date?` | 置顶时间，用于多个置顶会话内部排序 |

### Q：为什么需要 `pinnedAt`，不能只用 `isPinned`？

A：只用 `isPinned` 可以完成置顶分组，但无法表达多个置顶会话的内部顺序。`pinnedAt` 可以让最近置顶的会话排在置顶区上方，也方便后续做“取消置顶后恢复普通排序”。

### Q：`Codable` 如何兼容旧数据？

1. 如果保持自动合成 `Codable`，新增非可选 `isPinned: Bool` 会导致旧 JSON 缺字段时解码失败。
2. 建议为 `ChatThread` 增加自定义 `init(from:)`，对旧数据默认：
   - `iconName = nil`
   - `iconColorName = nil`
   - `isPinned = false`
   - `pinnedAt = nil`
3. 或者把新增字段都设计为可选，再提供计算属性：
   - `var isPinnedForDisplay: Bool { isPinnedRaw ?? false }`

第一期建议使用自定义解码，让领域模型对外保持清晰的 `Bool`。

## 10. 风险与注意事项

### Q：这个需求最大的风险是什么？

A：不是列表 UI，而是数据一致性。`ChatThread` 是客户端、服务端、本地 CoreData、同步 outbox 都会经过的核心模型。只在 UI 层加字段会导致重启丢失、多端不同步或旧数据解码失败。

### Q：标题编辑是否会影响自动标题生成？

A：需要区分“用户手动标题”和“系统默认标题”。如果现有标题会被后续自动摘要覆盖，新增编辑后建议补一个 `titleEditedByUser` 或 `isCustomTitle` 字段。第一期如果不做该字段，就必须明确：用户编辑过标题后，后续自动标题生成不得覆盖。

## 工单 `CHAT-000003`：会话列表空结果兜底刷新与会话内增量消息同步

### 工单状态

部分实现：列表空结果兜底刷新已实现（`ChatListViewModel.refreshThreadsIfLocalEmpty`）。**会话内增量消息同步已取消**，仍沿用 `loadMessagesIfNeeded(syncRemote:)` 原有行为。

## 1. 背景

### Q：现在进入会话列表页有什么问题？

A：进入会话列表页时，当前页面优先依赖本地会话数据加载。如果最终本地数据加载完成后列表仍然为空，页面会展示空列表，但用户实际可能在服务端已有会话数据。

典型场景：

1. 新设备登录老账号。
2. 本地数据库被清空或首次安装。
3. CoreData 本地数据还没有完成从服务端恢复。
4. 上一次同步失败，但服务端实际有会话。

当前关注位置：

```text
SparkClient/Projects/Features/Chat/Presentation/ChatConversationListPage.swift:69-73
```

需求是：**最终本地数据加载后，如果列表仍为空，应认为可能存在本地缓存缺失或同步异常，需要触发一次服务器会话列表刷新 `refreshThreads()`。**

### Q：进入会话详情页有什么问题？

A：当前只有进入会话详情页后，如果服务端在当前会话下有新增消息，本地页面才需要把新增消息加载出来。

当前关注位置：

```text
SparkClient/Projects/Features/Chat/Presentation/ChatView.swift:1-814
```

需求是：**进入某个会话页面后，仅针对当前会话触发一次增量消息刷新；如果当前会话服务端有新增消息，则拉取并合并到本地消息列表。**

### Q：为什么列表页和会话页要分开处理？

A：两者解决的问题不同：

1. 列表页负责“有没有会话”和“会话摘要是否存在”。
2. 会话页负责“当前线程里的消息是否完整”。
3. 列表页不应该进入每个会话拉全量消息，否则成本太高。
4. 会话页不应该刷新所有线程，否则每次打开聊天都会触发无关同步。

因此设计上应拆成：

```text
ChatConversationListPage
  -> 本地线程列表加载完成
  -> 如果仍为空：refreshThreads()

ChatView(threadID)
  -> 页面进入当前线程
  -> 触发当前 threadID 的一次增量消息刷新
  -> 只合并新增消息
```

## 2. 目标

### Q：本工单目标是什么？

A：

1. 进入会话列表页后，先展示本地数据，保证首屏响应快。
2. 本地加载最终完成且列表为空时，自动触发一次服务端线程刷新 `refreshThreads()`。
3. 服务端刷新成功后，如果有远端会话，列表应恢复显示。
4. 服务端刷新失败时，页面应保留空态，但要有明确日志或轻量错误提示，避免静默失败。
5. 进入会话详情页后，仅对当前 `threadID` 触发一次增量消息刷新。
6. 当前会话服务端有新增消息时，应把新增消息合并到本地并展示。
7. 当前会话没有新增消息时，不改变 UI，也不打断用户输入。
8. 不能在列表页无差别拉取所有会话消息。
9. 不能在会话页反复触发无限增量刷新。

## 3. 列表页空结果兜底刷新

### Q：什么时候触发 `refreshThreads()`？

A：只在“本地最终加载完成且列表仍为空”时触发。

推荐判定：

```text
ChatListViewModel 本地加载完成
  -> visibleThreads.isEmpty == true
  -> 当前不是搜索状态
  -> 当前没有正在 refreshThreads
  -> 本次页面生命周期尚未做过空结果兜底刷新
  -> 调用 refreshThreads()
```

不建议在以下情况触发：

1. 本地还在加载中。
2. 用户正在搜索，搜索结果为空。
3. 已经触发过一次空结果兜底刷新且还未完成。
4. 列表本来有数据，只是被筛选条件过滤为空。

### Q：为什么不是每次进入列表页都刷新服务器？

A：列表页首屏应该优先使用本地缓存，避免每次进入都打网络。只有本地最终为空时，才需要判断是否是缓存缺失或同步异常。

这样能兼顾：

1. 老用户新设备：本地为空，自动拉远端。
2. 正常老设备：本地有数据，不额外刷新。
3. 真正新用户：本地为空，远端刷新后仍为空，展示正常空态。

### Q：空结果兜底刷新后 UI 怎么处理？

A：

1. 刷新中：空态区域可显示轻量 loading，例如“正在同步会话...”。
2. 刷新成功且有数据：列表展示远端会话。
3. 刷新成功但仍为空：展示正常新用户空态。
4. 刷新失败：展示空态，但允许下拉刷新或重试；日志记录失败原因。

## 4. 会话页增量消息同步

### Q：什么时候触发当前会话的增量刷新？

A：进入 `ChatView` 后，页面已经知道当前 `threadID`，并完成本地消息加载后，触发一次当前线程增量刷新。

推荐流程：

```text
ChatView.task(id: threadID)
  -> 本地 thread/messages 已加载
  -> detailViewModel.refreshChatModelPicker(for:)
  -> detailViewModel.refreshCurrentThreadMessagesIncrementallyIfNeeded()
```

增量刷新只针对当前会话：

```text
threadID = 当前页面 threadID
lastLocalMessageSyncCursor / latestMessageCreatedAt / latestMessageID
  -> 请求服务端当前 threadID 的新增消息
  -> 合并到本地
  -> UI 自动刷新
```

### Q：如何判断“当前会话有新增消息”？

A：建议使用服务端同步游标或消息时间戳，而不是只靠本地数量。

优先级：

1. 如果同步协议已有 `cursor` / `lastSyncedAt`：使用游标做增量。
2. 如果没有游标：使用当前会话本地最新消息的 `createdAt` + `messageID` 请求服务端之后的消息。
3. 如果服务端只返回线程摘要的 `latestMessageAt`：先对比摘要时间，只有服务端较新时再拉当前线程消息。

不建议：

1. 每次进入会话都全量拉消息。
2. 只按消息数量判断，因为删除、重试、失败消息会让数量不可靠。
3. 在 UI 层手动拼接远端消息，合并逻辑应走 repository/store，避免重复消息和排序错乱。

### Q：增量消息合并要注意什么？

A：

1. 以服务端消息 ID 或稳定 `clientMessageID` 去重。
2. 保持消息时间顺序。
3. 不覆盖本地正在发送中的草稿或流式消息状态。
4. 对本地 pending/failed 消息要有状态合并规则，避免服务端成功消息与本地失败消息并存。
5. 如果用户正在输入，不应因为增量刷新清空输入区。
6. 如果用户停留在底部，新消息合并后可自动滚动到底部；如果用户正在翻历史，不应强制跳到底部。

## 6. 状态与去重设计

### Q：列表页如何避免重复刷新？

A：建议在 `ChatListViewModel` 内维护：

```swift
var didAttemptEmptyListRemoteRefresh = false
var isRefreshingThreads = false
var hasFinishedInitialLocalLoad = false
```

触发条件必须同时满足：

```text

visibleThreads.isEmpty == true
isRefreshingThreads == false
didAttemptEmptyListRemoteRefresh == false
searchText.isEmpty == true
```

触发后立刻设置：

```text

```

避免网络慢时重复进入 `.task` 或 `onChange` 造成多次刷新。

### Q：会话页如何避免重复增量同步？

A：建议在 `ChatDetailViewModel` 内按 `threadID` 记录：

```swift
private var incrementallyRefreshedThreadIDs: Set<UUID>

当前 threadID 尚未刷新过
当前 threadID 不在刷新中
当前本地消息已完成初始加载
当前没有正在进行的首条消息创建流程
```

刷新完成后：

```text

```

如果刷新失败，不建议无限重试；可以保留用户手动下拉或页面重新进入时再试。

## 7. 验收标准

### 列表页验收

1. 新设备登录老账号，本地会话为空时，进入列表页会自动调用一次 `refreshThreads()`。
2. 远端有会话时，刷新完成后列表展示远端会话。
3. 远端也没有会话时，展示正常空态，不显示异常。
4. 搜索结果为空时，不触发空结果兜底 `refreshThreads()`。
5. 本地已有会话时，进入列表页不因为普通展示触发额外远端刷新。
6. 空结果兜底刷新失败时有日志，页面不崩溃。
7. 同一次页面生命周期内，空结果兜底刷新最多触发一次。

### 会话页验收

1. 进入某个会话页后，仅对当前 `threadID` 触发一次增量消息刷新。
2. 服务端当前会话有新增消息时，刷新后消息列表展示新增消息。
3. 服务端当前会话没有新增消息时，UI 不发生明显跳动。
4. 增量刷新不会重复插入同一条消息。
5. 增量刷新不会清空输入区草稿。
6. 增量刷新不会覆盖正在流式生成或发送中的消息状态。
7. 多次进入同一会话不会在短时间内反复触发增量刷新。
8. 进入 A 会话只刷新 A 的消息，不拉取 B/C 会话消息。

## 8. 风险与注意事项

### Q：这个需求最大的风险是什么？

A：最大风险是“刷新触发点过多”。如果列表页、会话页、启动同步、前台恢复都直接调用远端同步，很容易出现重复请求、状态互相覆盖和 UI 抖动。

建议原则：

1. 列表页只兜底刷新线程列表，不拉所有消息。
2. 会话页只刷新当前线程新增消息。
3. 同步合并必须在 repository/store 层去重。
4. UI 层只表达“何时需要同步”，不要自己拼接数据。
5. 所有自动刷新都要有一次性或节流控制。

## 4. 图片压缩策略

### Q：压缩目标是什么？

A：

```text
单张发送给 AI 的图片 <= 1MB
```

只约束 AI 入参使用的压缩图，不约束 OSS 原图。

### Q：怎么压缩？

A：建议压缩策略按顺序执行：

1. 读取原图尺寸和格式。
2. 优先按最大边缩放，例如最大边 `1600px` 或 `2048px`。
3. 使用 JPEG 编码，初始质量 `0.82`。
4. 如果仍超过 1MB，逐步降低质量，例如 `0.72 -> 0.62 -> 0.52`。
5. 如果质量降低后仍超过 1MB，再继续降低最大边，例如 `1600 -> 1280 -> 1024`。
6. 输出满足 `<= 1MB` 的压缩数据。

建议底线：

```text
最小质量不低于 0.45
最小最大边不低于 768px
```

如果仍超过 1MB，可以：

1. 继续使用当前最小压缩结果并打日志。
2. 或提示用户开启原图/改走 OCR。

第一期建议优先保证可发送，使用最小压缩结果并记录日志，不直接失败。

### Q：哪些图片需要压缩？

A：只压缩满足以下条件的图片：

```text
附件类型是 image
effectiveMode == directMultimodal
模型 supportsMultimodal == true
sendsOriginalImagesToAITemporarily == false
```

不压缩：

1. PDF / 文件 / 视频。
2. `localOCR` 模式，因为不向 AI 送图片像素。
3. 用户在当前会话页临时开启“发送原图给 AI”。
4. OSS 上传使用的数据。

3. 大图压缩失败不会导致整条消息发送崩溃。
4. 日志能区分 AI 使用原图还是压缩图，并记录压缩前后大小。

## 9. 风险与注意事项

### Q：这个需求最大的风险是什么？

A：最大风险是误把压缩图替换成正式附件，导致用户历史消息和 OSS 留档也变成低清图。必须明确：

```text
OSS 上传：原图
消息附件：原图
AI 入参：默认压缩图
```

### Q：压缩图会不会影响 AI 识别？

A：可能会。默认压缩是为了降低耗时和成本，但用户如果需要识别小字、报告细节、药盒标签等，可以开启“发送原图给 AI”。

设置文案应提示：

```text
关闭后可降低耗时和消耗；如需识别小字或细节，可开启原图发送。
```

### Q：是否需要对医疗报告图片默认原图？

A：第一期不建议自动判断。医疗报告图片、小票、药盒照片等是否需要原图很难可靠判断。默认仍压缩，用户可手动开启原图。后续如果要做智能策略，可以基于 OCR 质量、图片中文字密度或用户场景再扩展。

## 工单 `CHAT-000005`：首轮 LocalOCR 图片识别内容被 userInput 覆盖修复

### 工单状态

已实现（`ChatOrchestrator`：`RuntimeMessagesBuildResult`、`LastUserTurnComposition` 显式元数据、`LocalOCRContentBuildResult`、`applyOutboundUserTurn` 按 source 合并）。

## 1. 问题结论

### Q：这次问题的最终判断是什么？

A：不是 OCR 没跑完，也不是图片画廊 UI 加载问题，而是 AI 网关组包的最后一步把已经构造好的 LocalOCR 增强 user 内容覆盖成了纯文本 `userInput`。

首轮错误请求：

```text
user.content = 看看这事嘛
```

首轮应该发送：

```text
【图片附件】...
【图片识别】
胃镜报告 OCR ...
【用户输入】
看看这事嘛
```

根因位置：

```text
ChatOrchestrator.makeRuntimeMessages
  -> buildLocalOCRContent(from:)
  -> 已生成 LocalOCR 增强内容

ChatOrchestrator.applyOutboundUserTurn
  -> applyCurrentUserInput
  -> 用纯文本 userInput 替换最后一条 user.content
```

## 2. 设计目标

### Q：本详设要达成什么？

A：

1. 首轮图片 + LocalOCR + 用户文本发送时，网关 body 必须包含 OCR 增强内容。
2. `applyOutboundUserTurn` 只能“合并”本轮附加上下文，不能无条件“覆盖”最后一条 user。
3. 普通文本消息仍保持当前行为，不引入重复 user 消息。
4. 问报告/健康资料上下文、小任务文本等 outbound 变体仍能正常生效。
5. 不在 `SendChatMessageUseCase` 重复拼 OCR，组包职责继续留在 `ChatOrchestrator`。
6. 设计上避免长期依赖 `content.contains("【图片识别】")` 这类字符串魔法。

## 3. 总体方案

### Q：推荐的总体方案是什么？

A：把 `makeRuntimeMessages` 的返回值从单纯 `[AIRuntimeMessage]` 升级为“消息 + 最后一条 user 的组包元数据”，让后续 `applyOutboundUserTurn` 按元数据决定是替换、保留还是合并。

新增内部结果模型：

```swift
private struct RuntimeMessagesBuildResult {
    var messages: [AIRuntimeMessage]
    var lastUserTurn: LastUserTurnComposition?
}

private struct LastUserTurnComposition {
    let index: Int
    let source: LastUserTurnSource
    let alreadyContainsCurrentUserInput: Bool
    let hasAttachmentContext: Bool
    let hasLocalOCRContext: Bool
}

private enum LastUserTurnSource {
    case plainText
    case localOCRAttachmentEnhanced
    case directMultimodal
    case healthResourceEnhanced
    case unknownEnhanced
}
```

核心变化：

```text
旧：
makeRuntimeMessages(...) -> [AIRuntimeMessage]
applyOutboundUserTurn(userInput, context, to: messages)

新：
makeRuntimeMessages(...) -> RuntimeMessagesBuildResult
applyOutboundUserTurn(userInput, context, buildResult)
```

如果为了降低改动面，也可以保留原 `makeRuntimeMessages` 给其他调用方使用，再新增：

```swift
private func makeRuntimeMessagesWithComposition(...) -> RuntimeMessagesBuildResult
```

## 4. 关键判定

### Q：什么叫“最后一条 user 已经增强过”？

A：由构造 runtime message 的地方直接标记，而不是事后猜。

在 `makeRuntimeMessages` 遍历 `ChatMessage` 时：

```swift
if message.role == .user, messageAttachments.isEmpty == false {
    let enhancedContent = buildLocalOCRContent(from: message)
    if enhancedContent != messageText {
        let runtime = AIRuntimeMessage(role: .user, content: enhancedContent)
        markLastUser(
            source: .localOCRAttachmentEnhanced,
            hasAttachmentContext: true,
            hasLocalOCRContext: true,
            alreadyContainsCurrentUserInput: enhancedContent.contains("【用户输入】")
        )
        return runtime
    }
}
```

`contains("【用户输入】")` 在这里只用于标记事实；不作为外部修复逻辑的主要判断。更理想的是 `buildLocalOCRContent` 返回结构化结果：

```swift
private struct LocalOCRContentBuildResult {
    let content: String
    let includesUserInput: Bool
    let attachmentCount: Int
    let ocrTextCount: Int
}
```

这样 `alreadyContainsCurrentUserInput` 可以来自 builder，而不是再扫字符串。

### Q：如何处理普通文本？

A：普通文本最后一条 user 标记为：

```swift
LastUserTurnComposition(
    index: index,
    source: .plainText,
    alreadyContainsCurrentUserInput: false,
    hasAttachmentContext: false,
    hasLocalOCRContext: false
)
```

普通文本可以继续被 `userInput` 替换或补齐，因为它没有附件/OCR上下文可丢。

## 5. 合并算法

### Q：`applyOutboundUserTurn` 新算法是什么？

A：按下面顺序处理：

```text
输入：
  userInput
  healthResourceContext
  RuntimeMessagesBuildResult(messages, lastUserTurn)

步骤：
1. 标准化 userInput -> trimmedQuestion
2. 构造 outboundPrefix：
   - 如果 healthResourceContext 非空，生成健康资料上下文前缀
   - 否则为空
3. 找到最后一条 user
4. 如果没有最后 user：
   - append outboundPrefix + trimmedQuestion
5. 如果最后 user 是 localOCRAttachmentEnhanced：
   - base = existingLastUserContent
   - 如果 outboundPrefix 为空：保持 base
   - 如果 outboundPrefix 非空：prefix + base
   - 不使用 trimmedQuestion 覆盖 base
6. 如果最后 user 是 plainText：
   - base = trimmedQuestion
   - 如果 outboundPrefix 非空：prefix + base
   - 写回最后 user
7. 如果最后 user 是 unknownEnhanced：
   - 保守策略：不覆盖 existing content，只在前面合并 prefix
```

伪代码：

```swift
private static func applyOutboundUserTurn(
    userInput: String,
    healthResourceContext: String?,
    buildResult: RuntimeMessagesBuildResult
) -> [AIRuntimeMessage] {
    let question = userInput.trimmingCharacters(in: .whitespacesAndNewlines)
    let prefix = makeHealthResourceContextPrefix(healthResourceContext)
    var messages = buildResult.messages

    guard let turn = buildResult.lastUserTurn else {
        let content = merge(prefix: prefix, base: question)
        guard content.isEmpty == false else { return messages }
        messages.append(AIRuntimeMessage(role: .user, content: content))
        return messages
    }

    let existing = messages[turn.index].content
        .trimmingCharacters(in: .whitespacesAndNewlines)

    let base: String
    switch turn.source {
    case .localOCRAttachmentEnhanced, .directMultimodal, .unknownEnhanced:
        base = existing.isEmpty ? question : existing
    case .plainText:
        base = question.isEmpty ? existing : question
    case .healthResourceEnhanced:
        base = existing.isEmpty ? question : existing
    }

    let merged = merge(prefix: prefix, base: base)
    guard merged.isEmpty == false else { return messages }
    messages[turn.index] = AIRuntimeMessage(role: .user, content: merged)
    return messages
}
```

### Q：`merge(prefix:base:)` 要注意什么？

A：它必须避免重复添加上下文。

```swift
private static func merge(prefix: String, base: String) -> String {
    let p = prefix.trimmingCharacters(in: .whitespacesAndNewlines)
    let b = base.trimmingCharacters(in: .whitespacesAndNewlines)

    if p.isEmpty { return b }
    if b.isEmpty { return p }
    if b.hasPrefix(p) { return b }
    return "\(p)\n\n\(b)"
}
```

健康资料上下文建议带稳定标题：

```text
【健康资料上下文】
...
```

这样可用 `hasPrefix("【健康资料上下文】")` 做轻量去重。

## 10. 风险与注意事项

### Q：最大风险是什么？

A：最大风险是把修复做成“只要最后一条 user 有内容就永远不覆盖”，这样会导致普通文本、小任务、问报告等本轮文本变体无法生效。

必须按 source 区分：

```text
plainText：可以用 userInput 替换
localOCRAttachmentEnhanced：不能用 userInput 替换，只能合并上下文
unknownEnhanced：保守不覆盖
empty：可以写入 userInput
```

### Q：为什么不直接让 `SendChatMessageUseCase` 拼完整 OCR？

A：不建议。

原因：

1. OCR 增强串已经由 `ChatOrchestrator` 从消息块和附件构造。
2. `SendChatMessageUseCase` 负责发送业务，不应复制 provider runtime 组包格式。
3. 后续健康资料、图片、多模态、工具上下文都会进入 runtime 组包，必须集中在 `ChatOrchestrator` 管理。

### Q：字符串 marker 能不能先用？

A：可以作为短期兜底，但详设推荐显式元数据。字符串 marker 方案上线时必须在代码注释里说明是过渡方案，并补测试覆盖，避免未来本地化或格式调整后再次回归。

| `model` | 是 | 模型名 |
| `apiKey` | 是 | 临时 API Key |

也可以为了降低复杂度，第一期只支持 OpenAI Compatible：

```text
Base URL
Model
API Key
```

### Q：Key 存在哪里？

A：只保存在内存。

禁止：

1. 禁止写入 Keychain。
2. 禁止写入 UserDefaults。
3. 禁止写入 CoreData。
4. 禁止写入现有 `AIConfigCenter`。
5. 禁止进入聊天同步或日志。

推荐：

```swift
@MainActor
final class GuestChatSessionStore: ObservableObject {
    @Published var config: GuestAIConfig?
    @Published var messages: [GuestChatMessage] = []

    func reset() {
        config = nil
        messages = []
    }
}
```

其中 `GuestAIConfig.apiKey` 只存在 `GuestChatSessionStore` 的内存对象中。

### Q：日志要注意什么？

A：游客模式下不能打印完整 API Key。最多打印：

```text
provider=openai_compatible model=xxx baseURL=xxx apiKey=***
```

## 6. 游客对话页面

### Q：游客对话页面应该是什么形态？

A：简化页面，只支持文本输入和文本回复。

第一期能力：

1. 展示当前内存消息列表。
2. 用户输入文本。
3. 发送按钮。
4. 发送中 loading。
5. 助手文本回复。
6. 配置入口。
7. 清空对话。
8. 退出游客模式。

不支持：

1. 不支持图片。
2. 不支持文件。
3. 不支持 OCR。
4. 不支持问报告。
5. 不支持成员档案。
6. 不支持工具调用。
7. 不支持聊天同步。
8. 不支持本地持久化。
9. 不支持会话列表。
10. 不支持历史恢复。

### Q：消息模型怎么设计？

A：新增游客消息模型，不复用完整 `ChatMessage`：

```swift
struct GuestChatMessage: Identifiable, Equatable, Sendable {
    enum Role: Sendable {
        case user
        case assistant
        case system
    }

    let id: UUID
    let role: Role
    var text: String
    let createdAt: Date
}
```

原因：

1. `ChatMessage` 有 block、thread、附件、状态、同步等概念。
2. 游客模式只需要简单文本。
3. 独立模型能避免误接入存储和同步。

## 7. 游客 AI 调用

### Q：游客 AI 调用是否复用现有 `ChatOrchestrator`？

A：不建议第一期复用。

`ChatOrchestrator` 面向登录态完整工具/会话链路，包含工具调用、成员上下文、健康资料、附件、多模态等能力。游客模式应新增轻量 client，例如：

```swift
protocol GuestAIChatClient: Sendable {
    func send(messages: [GuestChatMessage], config: GuestAIConfig) async throws -> String
}
```

实现可以使用 OpenAI Compatible Chat Completions / Responses API 的最小文本请求。

### Q：是否允许游客工具调用？

A：第一期不允许。

原因：

1. 工具调用可能访问健康、文件、位置、日历等敏感数据。
2. 游客没有账号、成员、权限和存储上下文。
3. 审核兜底只需要证明基础 AI 文本对话可用。

因此请求体必须禁用工具：

```text
tools = nil
tool_choice = none
```

## 10. 验收标准

### 登录页验收

1. 未登录登录页展示“游客模式”入口。
2. 点击后进入游客对话页面。
3. 点击游客模式不会创建正式登录态。
4. 返回后仍停留在未登录流程。

### 配置验收

1. 游客未配置 Key 时，页面展示配置引导。
2. 用户可输入临时 API Key、模型和 Base URL。
3. 配置完成后可开始对话。
4. API Key 不写入 Keychain。
5. API Key 不写入 UserDefaults。
6. API Key 不写入 CoreData。
7. App 重启后游客配置消失。

### 对话验收

1. 游客模式支持简单文本发送。
2. 游客模式能展示 AI 文本回复。
3. 发送中有 loading 状态。
4. 发送失败有错误提示。
5. 清空对话只清空内存消息。
6. 退出游客模式后消息不进入正式会话列表。

### 隔离验收

1. 游客对话不创建 `ChatThread`。
2. 游客消息不进入 CoreData。
3. 游客消息不进入 chat sync。
4. 游客临时 Key 不影响正式 AI 设置。
5. 正式登录后的现有对话功能不受影响。
6. 游客模式不调用问报告、OCR、附件、成员档案、健康工具。

## 11. 风险与注意事项

### Q：这个需求最大的风险是什么？

A：最大风险是为了省事复用现有 `ChatView` 或 `AIConfigCenter`，导致游客未登录态进入正式会话依赖，出现鉴权失败、Key 污染、消息落库或同步污染。

必须坚持：

```text
游客 AI 设置：独立 + 内存
游客消息：独立 + 内存
游客 AI 调用：独立 + 无工具
游客页面：独立 + 简化
正式聊天：不受影响
```

### Q：为什么不存游客 Key？

A：游客模式是临时体验和审核兜底，不是正式账号能力。存储 Key 会带来隐私、安全和配置污染问题，也容易让用户误以为游客模式有持久会话能力。

### Q：是否要提醒用户？

A：建议在游客配置页展示轻量说明：

```text
游客模式仅用于临时体验。API Key 和对话内容只保存在当前运行期间，退出或重启后会清空。
```
