# CHAT-000060 医院智能体新会话首张医生简介卡即时落库流程重构需求确认工单

> 工单状态：需求确认完成，待开发  
> 当前阶段：只维护需求与技术设计，不修改业务代码  
> 适用系统：SparkClient iOS、SparkService  
> 创建日期：2026-09-05  
> 关联问题：新建医院智能体会话成功后，ChatView 消息数仍为 0，医生简介系统卡没有立即显示

## 1. 需求背景

患者从医院首页或院内名医目录点击“开始咨询”，医院智能体运行配置请求成功，医院会话创建接口也成功返回了新的 Thread；服务端创建事务同时生成医生简介系统卡和免责声明消息，但 iOS 进入 ChatView 后本地消息总数仍为 0，页面没有展示医生简介卡。

当前已经尝试在创建后增加：

- `HospitalConversationScopeStore` 进程内新建 Thread 标记；
- 新建医院 Thread 的主动增量消息同步；
- 同步完成后显式重新读取 Core Data；
- 当前 Thread 防串线判断。

这套补偿链路仍依赖创建接口之后的第二次消息 pull，而且与 ChatView 原有进入会话同步、Core Data 通知刷新、医院 context 刷新形成重复流程。用户要求放弃复杂补偿设计，参考普通新对话科普问题卡的本地幂等插入方式，重构医院新会话首卡流程。

### 3.1 普通新对话首张科普卡

普通新对话已经形成稳定的本地首卡流程：


### 3.2 医院会话创建

`ResolveOrCreateHospitalConversationUseCase.execute` 当前流程：

```text
读取医院智能体运行配置
  → POST 创建医院会话
  → 校验 agent/member/hospital/binding
  → HospitalConversationScopeStore.remember
  → 标记 scopeStore.newlyCreatedThreadIDs
  → 返回 threadID
```

创建接口客户端 DTO 目前只返回：

- `threadId`
- 精简后的 `HospitalConversationDTO`

虽然服务端响应包含医院、科室、医生和智能体资料，但当前 DTO 没有直接返回一条可写入 ChatRepository 的规范化 `ChatMessage`，因此客户端无法像普通科普卡一样在创建成功后立即落库医生简介消息。

### 3.3 服务端医生简介卡

`hospital_care/services/conversation_service.py` 的 `create_patient_conversation` 在数据库事务中：

1. 创建 `ChatThread`；
2. 创建 `ClinicalConversationBinding`；
3. 调用 `_create_doctor_intro_card` 创建 `hospital_doctor_intro_card`；
4. 创建免责声明 system message。

`_create_doctor_intro_card` 已按 Thread 和 block kind 做幂等检查。服务端是医生身份快照和简介卡内容的可信来源，这部分能力可以复用。

### 3.4 当前医院首卡补偿链路

当前分支增加了以下流程：

- `HospitalConversationScopeStore.newlyCreatedThreadIDs`
- `markNewlyCreated / isNewlyCreated / clearNewlyCreated`
- `ChatDetailViewModel.synchronizeAndReloadMessages`
- `ChatView` 医院 scope 分支内主动 await 消息 pull，再显式 reload

同时，`loadMessagesIfNeeded` 本身已经会启动一次后台 `pullThreadMessagesIncrementalOnOpen`。因此新建医院会话可能同时经历：

```text
本地加载
  → 第一次后台 pull
  → 解析医院 scope
  → 第二次 single-flight pull/等待
  → 显式 reload
  → Core Data messagesMerged 通知再次 reload
```

流程重复，首卡出现仍受第二次接口、同步游标、远端 Thread 可见时序和页面生命周期影响。

## 4. 已知偏差与根因判断

### 4.1 直接偏差

普通新对话在创建后主动把首张 system 卡写入本地消息库和页面状态；医院新对话只保存 scope 和 threadID，没有把服务端已经生成的简介卡消息直接交给本地消息库。

### 4.2 根因

根因不是智能体运行配置未加载，也不是简介卡 SwiftUI 组件不存在，而是医院会话创建结果与本地 ChatThread/ChatMessage 初始化没有形成单一事务式编排：

```text
服务端创建成功 ≠ 客户端本地 Thread/首卡已经就绪
```

客户端把首卡显示寄托在后续消息同步上，导致创建成功到首次消息 pull 之间存在空白窗口；一旦 pull 没有及时触发、没有拉到消息或页面没有正确消费合并结果，ChatView 就保持 0 条消息。

### 4.3 不应继续叠加的补偿

本次重构不继续增加：

- 新的待同步数据库表；
- 持久化状态机；
- 定时重试器；
- 简介卡专用二次拉取接口；
- 页面顶部同步状态条；
- 历史 Thread 扫描补卡；
- 多套新建标记；
- 客户端伪造与服务端不同 ID 的重复简介卡。

## 5. 初步重构目标

目标流程应压缩为：

```text
创建医院会话
  → 获得服务端可信的 Thread + 首张医生简介消息
  → 保存医院 scope
  → 使用现有 ChatRepository 幂等写入 Thread/消息
  → 使用现有 ChatStateStore 立即显示首卡
  → 清除新建标记
  → 后续消息仍走统一增量同步
```

该流程应像普通科普卡一样具有明确的本地插入入口，但医生资料必须来自服务端可信快照，不能由客户端根据零散字段随意拼装。

## 10. 一问一答确认记录

### 第 1 问：医院会话创建成功时，客户端立即落库的医生简介卡数据应从哪里取得？

为什么要问：如果客户端自己用运行配置和目录字段重新拼卡，会与服务端真实快照、消息 ID 和幂等规则产生两套事实；如果仍等待第二次消息 pull，就会回到当前 0 消息问题。这个选择决定是否需要调整创建接口响应，以及能否彻底删除专用同步补偿流程。

请选择：

- A. 创建接口直接返回服务端已经落库的规范化简介卡消息，客户端按现有远端消息合并逻辑立即写入 Core Data 和 ChatStateStore（推荐）
  服务端仍是唯一可信来源；消息 ID、Block ID 与后续同步一致。客户端不伪造消息，也不需要第二次 pull，最接近普通科普卡“创建后立即本地可见”的效果。
- B. 客户端使用创建响应中的医院、科室、医生、智能体字段自行生成本地简介卡消息
  不必扩展服务端消息响应，但客户端会拥有另一套快照组装和消息 ID 规则，后续服务端同步需要额外去重。
- C. 客户端使用已加载的 AgentRuntimeConfig 自行生成简介卡消息
  数据已经在内存中，但运行配置不是聊天消息契约，缺少完整医院快照和服务端消息标识，容易产生职责混用。
- D. 创建成功后继续同步调用现有 Thread 消息接口，等拉到简介卡后才进入 ChatView
  不改创建接口，但仍依赖第二次网络请求，弱网时进入慢，并没有真正参考普通科普卡的本地即时插入方式。

请选择 A、B、C 或 D。

#### 第 1 问确认

**已确认选择 A：创建接口返回服务端已落库的规范化医生简介卡消息。**

时序补充：医院会话创建主流程完成并返回成功后，客户端从创建响应中取得服务端已经落库的规范化简介卡消息；简介卡本地写入异步执行，不阻塞创建接口成功后的页面进入。

落地约束：

- 服务端继续在 `create_patient_conversation` 事务中创建医生简介卡，保持服务端为唯一可信来源。
- 创建接口成功响应增加已落库的规范化简介卡消息，必须携带真实服务端 message ID、client message ID、block ID、block kind、payload、时间和 revision 等现有消息合并所需字段。
- 客户端不根据运行配置、医生目录或创建响应中的零散字段重新拼装简介卡。
- 客户端创建会话成功后可以先进入 ChatView；随后异步把响应中的简介卡交给现有远端消息入站/合并流程。
- 简介卡成功写入 Core Data 后，继续通过现有消息数据库变更和 ChatStateStore 更新机制显示，不设计简介卡专用 UI 状态机。
- 响应消息和后续统一消息同步使用同一服务端消息 ID，重复合并必须是幂等更新，不能产生第二张简介卡。
- 删除“为了获取简介卡再调用一次 Thread 消息 pull”的专用流程；正常会话增量同步仍保留，用于后续消息和跨设备校准。
- 简介卡异步本地写入失败不回滚服务端已经创建成功的会话，也不在客户端伪造替代卡；错误处理方式在后续问题确认。

### 第 2 问：创建接口应只返回医生简介卡，还是同时返回创建事务生成的全部初始系统消息？

为什么要问：服务端当前在同一创建事务中生成医生简介卡和医疗免责声明。如果响应只返回简介卡，免责声明仍要等待后续消息同步，首屏消息可能分两次出现；如果统一返回全部初始消息，客户端可以一次交给现有消息合并流程，但创建响应字段会从单卡扩展为消息数组。

请选择：

- A. 返回 `initial_messages` 数组，包含医生简介卡和免责声明等本次创建产生的全部初始系统消息（推荐）
  客户端只执行一次批量消息合并，消息顺序、ID 和服务端事务结果完全一致；以后增加合法的初始化系统消息也不需要再次改接口字段。
- B. 只返回 `doctor_intro_message`
  当前目标最聚焦，但免责声明仍依赖后续同步，创建链路会同时存在“响应直入一条”和“同步补齐其他消息”两种时序。
- C. 返回简介卡消息和免责声明两个固定字段
  字段直观，但初始化消息类型增加时还要持续扩展创建接口。
- D. 只返回简介卡 block，不返回外层 ChatMessage
  响应更小，但客户端必须自行创建消息 ID、角色、时间和排序信息，会重新形成客户端伪造消息的问题。

请选择 A、B、C 或 D。

#### 第 2 问确认

**已确认选择 A：创建接口返回 `initial_messages` 数组，包含本次创建事务生成的全部初始系统消息。**

落地约束：

- `initial_messages` 至少包含医生简介系统卡和医疗免责声明，顺序与服务端 Thread 中的真实消息顺序一致。
- 数组元素复用现有聊天远端消息 DTO/canonical message 契约，不为 HospitalCare 再定义一套内容格式。
- 每条消息必须包含现有 `ChatInboundPipeline` 和 `ChatRepository` 幂等合并所需的服务端标识、客户端消息标识、角色、时间、blocks、revision 和 delivery state 等字段。
- 客户端把整个数组一次性交给现有批量消息合并入口，不分别编写“插简介卡”和“插免责声明”两套代码。
- 后续统一增量同步再次返回同一批消息时，按既有消息 ID 和 block ID 更新或忽略，不得重复展示。
- 服务端以后增加合规的初始化系统消息时，只需要加入 `initial_messages`，客户端仍按统一消息协议消费。

### 第 3 问：新建医院会话返回后，本地 ChatThread 应在什么时机建立？

为什么要问：当前日志不仅消息数为 0，标题和会话参数也处于空值，说明客户端可能只有服务端 threadID 和医院 scope，却没有完成本地 ChatThread 初始化。`initial_messages` 必须关联一个已经存在的本地 Thread 才能稳定写入 Core Data；继续等待会话列表或全局同步补 Thread，会保留竞态。

请选择：

- A. 创建响应同时返回规范化 Thread；客户端先通过现有仓储 upsert 本地 Thread 和医院 scope，再进入 ChatView，`initial_messages` 随后异步合并（推荐）
  ChatView 一打开就有正确标题、成员和基础会话配置；初始消息仍按已确认方式异步出现，不需要等待会话列表刷新。
- B. `initial_messages` 合并时，如果本地 Thread 不存在，由入站管线顺带创建 Thread
  调用入口较少，但消息合并层需要承担 Thread 创建和医院 scope 绑定职责，边界变重。
- C. 创建成功后先调用现有会话列表刷新，等列表同步创建本地 Thread，再异步合并 `initial_messages`
  可以复用列表同步，但增加第二次网络请求，仍有等待和竞态。
- D. 客户端使用固定标题“健康咨询”创建临时本地 Thread，后续同步再覆盖
  页面能快速打开，但会制造临时数据与服务端数据覆盖规则，可能出现标题和配置闪变。

请选择 A、B、C 或 D。

#### 第 3 问确认

**已确认选择 A：创建响应同时返回规范化 Thread；客户端先通过现有仓储 upsert 本地 Thread 和医院 scope，再进入 ChatView，`initial_messages` 随后异步合并。**

落地约束：

- 服务端创建响应增加可映射为现有 `ChatThread` 的规范化 Thread 数据，不只返回 threadID。
- Thread 数据至少覆盖本地会话正常展示和消息关联需要的 ID、memberID、title、role prompt、创建/更新时间、删除状态、模型与生成配置的现有规范字段。
- 客户端在统一医院会话创建 UseCase 内完成响应校验、Thread upsert 和 `HospitalConversationScopeStore.remember`。
- Thread upsert 与 scope 保存成功后才把 threadID 交给页面路由，禁止先导航后等待会话列表补齐本地 Thread。
- 不创建标题为“健康咨询”的临时 Thread，不使用空配置占位后再覆盖。
- `initial_messages` 仍按已确认方案在进入 ChatView 后异步合并，不阻塞页面导航。
- 最近会话复用路径不重新创建 Thread；只校验并恢复现有 scope，继续使用本地已有消息和正常增量同步。

### 第 4 问：`initial_messages` 异步写入成功后，应通过哪条机制更新 ChatView？

为什么要问：普通科普卡当前既写仓储又直接更新 `ChatStateStore`；远端同步则通过 `ChatInboundPipeline` 合并 Core Data，并发布 `messagesMerged` 通知让当前 Thread 重读。医院初始化消息来自服务端规范化 DTO，必须选定唯一更新通道，否则会出现“入站管线更新一次、页面手动插入一次、通知又 reload 一次”的重复流程。

请选择：

- C. 先直接插入 `ChatStateStore` 展示，再后台写 Core Data

## 11. 最终确认结论汇总

| 编号 | 最终结论 | 对实现的影响 |
| --- | --- | --- |
| Q1 | 创建接口返回服务端已落库的规范化简介卡消息 | 客户端不拼装、不伪造医生身份消息 |
| Q2 | 返回 `initial_messages` 数组 | 简介卡、免责声明等初始消息一次批量消费 |
| Q3 | 创建响应同时返回规范化 Thread | 导航前先 upsert 本地 Thread 和保存医院 scope |
| Q4 | 初始消息完全复用 `ChatInboundPipeline.applyRemoteMessages` | 只走现有 Core Data、MergePolicy 和 `messagesMerged` 刷新链路 |
| Q5 | 新建医院 Thread 首次进入跳过常规 pull | 成功路径不重复请求；历史会话不变 |
| Q6 | 初始消息合并失败时调用一次现有 Thread pull | 只有失败路径回源，不建立重试状态机 |
| Q7 | 复用并扩展 `ChatStateStore` 新建标记 | 删除 HospitalConversationScopeStore 的第二套新建标记 |
| Q8 | 医院新建上下文暂存 `initial_messages`，由 ChatView 原子消费 | 同时完成跳过 pull 与只注入一次 |
| Q9 | 扩展 `ResolveOrCreateHospitalConversationUseCase` 统一编排 | 所有医院创建入口只接收 threadID，不复制流程 |

## 12. 最终业务流程

### 12.1 新建医院智能体会话成功流程

```text
患者点击“开始咨询”或会话页“新建对话”
  ↓
ResolveOrCreateHospitalConversationUseCase.execute
  ↓
读取/校验医院智能体运行配置
  ↓
POST /api/v1/hospital-care/conversations/
  ↓
服务端事务创建：
  ChatThread
  + ClinicalConversationBinding
  + 医生简介系统消息
  + 医疗免责声明系统消息
  ↓
响应返回：
  thread
  + conversation
  + initial_messages[]
  ↓
iOS 校验 agentID/memberID/hospitalID/binding
  ↓
映射并 upsert 本地 ChatThread
  ↓
HospitalConversationScopeStore.remember
  ↓
ChatStateStore.markThreadAsNewlyCreated(
  source: hospital,
  initialMessages: initial_messages
)
  ↓
UseCase 返回 threadID
  ↓
页面导航进入 ChatView
  ↓
ChatView 原子消费医院新建上下文
  ↓
loadMessagesIfNeeded(syncRemote: false)
  ↓
页面先显示正确 Thread 标题和输入区
  ↓
异步 applyRemoteMessages(initial_messages)
  ↓
Core Data 幂等合并
  ↓
发布现有 messagesMerged
  ↓
ChatDetailViewModel 重读当前 Thread
  ↓
消息列表显示医生简介卡和免责声明
```

### 12.2 初始消息合并失败

```text
applyRemoteMessages(initial_messages) 失败
  ↓
记录脱敏错误日志
  ↓
仅调用一次 pullThreadMessagesIncrementalOnOpen(threadID)
  ↓
成功：现有入站管线落库并刷新页面
  ↓
失败：保留当前会话可用，不循环重试
```

用户再次进入、App 前台统一同步或 WebSocket 定向提示仍可按当前系统机制恢复。不得创建简介卡专用错误状态机、持久化任务或定时重试器。

### 12.3 复用最近会话

```text
医生卡存在 recentThreadID
  ↓
ResolveOrCreateHospitalConversationUseCase 校验运行配置
  ↓
恢复 HospitalConversationScope
  ↓
不创建 Thread
  ↓
不登记医院新建上下文
  ↓
进入 ChatView
  ↓
按历史会话原有流程读取本地消息并执行增量 pull
```

### 12.4 会话内右上角新建

使用当前医院会话的 agentID、hospitalID 和当前 memberID 调用同一 UseCase，`recentThreadID` 必须传 `nil`。创建、Thread upsert、scope、初始消息上下文和 ChatView 消费流程与医院首页完全一致，不保留会话页专用首卡逻辑。

## 13. 最终架构边界

### 13.1 服务端职责

- 创建真实医院 Thread、临床绑定和全部初始系统消息。
- 生成医生简介卡可信快照。
- 为 Thread、message 和 block 分配稳定标识。
- 在创建响应中返回规范化 Thread 和 `initial_messages`。
- 保持创建事务、权限校验、智能体发布状态和运行绑定校验。

### 13.2 ResolveOrCreateHospitalConversationUseCase 职责

- 获取运行配置。
- 创建或复用医院会话。
- 校验服务端响应范围。
- 将规范化 Thread upsert 到现有 ChatRepository。
- 保存医院 scope。
- 新建时登记 `ChatStateStore` 医院初始化上下文。
- 最终只向页面返回 threadID。

### 13.3 ChatStateStore 职责

- 保存进程内、一次性的“新建 Thread 初始化上下文”。
- 区分普通和医院来源。
- 医院来源暂存规范化 `initial_messages`。
- 提供按 threadID 原子消费方法。
- 超时清理未消费上下文。

### 13.4 ChatView 职责

- 在 `.task(id: currentThreadID)` 开始时消费一次初始化上下文。
- 医院新建时首次本地加载设置 `syncRemote: false`。
- 页面显示后启动初始消息入站合并。
- 普通新建时继续执行原科普卡流程。
- 历史会话继续执行原进入同步。

### 13.5 ChatInboundPipeline 职责

- 接收创建响应和正常 pull 使用的同一种远端消息领域对象。
- 批量映射、幂等合并并落库。
- 发布现有数据库变更事件。
- 不判断“医生简介卡业务”，不创建医院专用分支。

### 14.2 服务端序列化规则

- `thread` 使用 chat sync 已有 Thread serializer/canonical mapper；不得在 HospitalCare 手写不同字段语义。
- `initial_messages` 使用 chat sync 已有 message serializer，并预取 blocks，避免 N+1 查询。
- 数组只返回本次创建事务生成的初始化 system 消息，不返回用户历史消息。
- 新建响应顺序按消息创建时间、服务端 ID 或现有 canonical 排序规则稳定输出。
- 幂等重放返回同一 Thread 时，返回该 Thread 已有的初始消息，不再创建第二张简介卡。
- 创建失败保持现有稳定业务错误码，不返回半成品 `thread` 或部分消息。

### 14.3 权限与安全

- 继续执行成员访问权限、智能体发布状态、医院启用状态和运行绑定有效性校验。
- 只返回当前登录患者有权访问的 Thread 和初始化消息。
- 创建响应不得包含模型供应商 API Key、Secret、内部 Token 或后台专用配置。
- 当前运行配置日志存在敏感值明文输出风险，应在网络日志层统一按字段名脱敏；此项可作为同版本安全修复，但不影响本工单首卡主流程。

### 15.2 新建初始化上下文

设计示例：

```swift
enum NewlyCreatedThreadSource: Sendable {
    case ordinary
    case hospital(initialMessages: [RemoteChatMessage])

    let createdAt: Date

```

`ChatStateStore` 将原 `[UUID: Date]` 扩展为 `[UUID: NewlyCreatedThreadContext]`，并保留 120 秒或当前既有有效期。不得持久化 `initialMessages`。

### 15.3 原子消费 API

设计示例：

```swift

    _ threadID: UUID,
    source: NewlyCreatedThreadSource

func consumeNewlyCreatedThreadContext(
    _ threadID: UUID
) -> NewlyCreatedThreadContext?
```

消费操作在同一 MainActor 调用中完成读取和删除，确保 SwiftUI 页面重建不会重复取得同一批消息。

## 16. iOS 核心落地方案

### 16.1 ResolveOrCreateHospitalConversationUseCase

方案级伪代码：

```swift
func execute(...) async throws -> UUID {
    let runtime = try await resolveRuntimeConfig(...)

    if let recentThreadID {
        scopeStore.remember(scopeForRecentThread)
        return recentThreadID
    }

    let response = try await remoteAPI.createConversation(...)
    try validate(response, expectedScope: expectedScope, runtime: runtime)

    let thread = try threadMapper.map(response.thread)
    let messages = try messageMapper.map(response.initialMessages)

    try await chatRepository.upsertRemoteThread(thread)
    scopeStore.remember(validatedScope)

    await MainActor.run {
        chatStateStore.markThreadAsNewlyCreated(
            response.thread.id,
            source: .hospital(initialMessages: messages)
        )
    }
    return response.thread.id
}
```

约束：本地 Thread upsert 失败时不得登记上下文或返回 threadID；scope 保存和上下文登记必须发生在导航之前。

### 16.3 初始消息合并与失败兜底

方案级伪代码：

```swift
func applyHospitalInitialMessages(
    _ messages: [RemoteChatMessage],
    threadID: UUID
) async {
    do {
        try await inboundPipeline.applyRemoteMessages(
            messages,
            threadID: threadID
        )
    } catch {
        logger.warning("hospital initial message merge failed", safeMetadata)
        do {
            try await chatSyncSupervisor
                .pullThreadMessagesIncrementalOnOpen(threadID: threadID)
        } catch {
            logger.warning("hospital initial message fallback pull failed", safeMetadata)
        }
    }
}
```

这段为设计伪代码，不是当前代码修改。真实实现优先给现有 ChatSyncSupervisor/ChatSyncEngine 增加“应用已获得的远端消息”公共入口，避免 Presentation 层直接持有内部 Pipeline。

## 20. 并发、幂等与异常边界

- 创建按钮继续使用当前防重入逻辑。
- HTTP 创建继续携带 Idempotency-Key；重放必须返回同一 Thread 及同一初始化消息。
- Thread upsert 按服务端 Thread ID 幂等。
- 初始化消息按 server message ID/client message ID 幂等。
- blocks 按 block ID 和 revision 合并。
- ChatView 原子消费上下文，确保同一进程只主动提交一次 `initial_messages`。
- 初始消息任务完成时即使用户已经切换 Thread，也只写 Core Data；现有通知必须校验当前成员和 Thread 后再更新 UI。
- 首次本地加载跳过 pull 只适用于成功消费到 `.hospital(initialMessages:)` 的本次新建 Thread。
- 上下文缺失、过期或 App 已重启时按历史 Thread 处理，执行正常 pull，不猜测、不补造消息。
- 创建响应中 Thread 映射失败、本地 Thread upsert 失败或 scope 校验失败时，不进入 ChatView。
- `initial_messages` 为空视为服务端契约异常；客户端走一次失败兜底 pull并记录脱敏日志。

## 21. 测试与验收

### 21.1 服务端测试

1. 新建医院会话响应包含规范化 `thread`。
2. `initial_messages` 至少包含一张 `hospital_doctor_intro_card` 和一条免责声明。
3. 两条消息均已在数据库真实存在，响应不是临时拼装的未落库对象。
4. Thread、message、block ID 与消息同步接口返回完全一致。
5. 相同幂等请求重放不重复创建 Thread 或简介卡。
6. 医生头像、职称、科室、医院、智能体名称和详情路由来自服务端可信快照。
7. 成员越权、智能体未发布、医院停用、绑定失效时不返回 Thread 和初始消息。
8. 响应及日志不包含模型 API Key 等敏感字段。

### 21.2 iOS 单元测试

1. 新建响应可以映射为现有 ChatThread 和远端 ChatMessage。
2. UseCase 导航返回前已完成 Thread upsert 和 scope 保存。
3. 复用 recentThreadID 不登记医院新建上下文。
4. 新建路径登记 `.hospital(initialMessages:)`。
5. ChatStateStore 对上下文只允许消费一次。
6. 上下文超时后按历史会话处理。
7. 医院上下文不触发普通 ChatGuideCard。
8. 普通上下文仍按原逻辑生成科普卡。
9. 初始消息重复应用不会产生重复 message/block。
10. 初始消息合并失败只触发一次 pull。

### 21.3 iOS 集成验收

1. 从医院首页首次咨询医生智能体，进入 ChatView 后出现医生简介卡和免责声明。
2. 从院内名医目录首次咨询，结果一致。
3. 在医院会话右上角新建对话，结果一致。
4. 调试信息中的 Thread 标题、memberID 和生成配置不再是空占位。
5. 成功路径创建后不再发送简介卡专用消息 pull。
6. 初始消息合并成功后由 `messagesMerged` 驱动刷新，没有手动 reload。
7. 退出再进入同一 Thread，只执行历史会话正常增量同步，不重新注入首卡。
8. 模拟合并失败时只执行一次 Thread pull，成功后展示首卡。
9. 快速切换 Thread 不会把医生卡显示到其他会话。
10. 普通新对话科普卡及问题生成完全不受影响。

### 21.4 明确不通过条件

- 新建会话仍显示 0 条消息且没有触发初始消息合并。
- 创建成功后必须等待第二次消息接口才显示简介卡。
- 同一 Thread 出现两张医生简介卡。
- 医院新建会话出现普通科普卡。
- 历史会话被补造新的简介卡。
- 页面代码直接构造医生身份 payload 或本地消息 ID。
- 保留两套新建 Thread marker。

## 22. 实施顺序

1. 服务端复用 canonical serializer，扩展创建响应的 `thread` 和 `initial_messages`。
2. 补充服务端 API、事务消息、幂等和权限测试。

## 23. 最终方案一句话

医院会话创建接口一次返回“规范化 Thread + 服务端已落库的全部初始消息”；iOS 在导航前 upsert Thread 和 scope，把初始消息放入统一的 ChatStateStore 新建上下文，ChatView 首次进入跳过 pull并异步走现有入站合并，失败时才回源 pull 一次，同时删除现有医院专用 marker、同步后 reload 和重复拉取流程。
