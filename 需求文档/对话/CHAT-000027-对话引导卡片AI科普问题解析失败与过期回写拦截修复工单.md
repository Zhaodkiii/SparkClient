## 2. 当前实现事实

### 2.1 解析器现状

文件：`SparkClient/Projects/Features/Chat/Application/ChatGuideQuestionJSONParser.swift`

当前 raw 模型：

```swift
private struct ChatGuideRawQuestion: Decodable {
    var id: String?
    var title: String?
    var prompt: String?
    var category: String?
}
```

当前解析入口：

```swift
static func parse(_ rawText: String) throws -> [ChatGuideQuestion] {
    let jsonText = extractJSONText(from: trimmed)
    let rawQuestions = try decodeQuestions(from: jsonText)
    let normalized = normalize(rawQuestions)
    guard normalized.count >= 3 else {
        throw ChatGuideQuestionJSONParserError.insufficientQuestions
    }
    return Array(normalized.prefix(3))
}
```

已支持：

1. 纯 JSON 数组。
2. Markdown code fence 包裹 JSON。
3. `{ "questions": [...] }` 外层对象。
4. 少于 3 条时用 preset 补齐。
5. 重复 title/prompt 去重。

当前未支持：

1. `id` 为数字类型，例如 `"id": 1`。
2. 模型输出多个对象但缺少数组外层，例如 `{...}, {...}, {...}`。
3. key 或 value 前后存在非 JSON 解释文本时，从文本中截取最大 JSON 片段。
4. 解析失败时输出具体 parse error 维度，日志只能看到 `parse_failed`。

### 2.2 生成用例现状

文件：`SparkClient/Projects/Features/Chat/Application/ChatGuideQuestionGenerationUseCase.swift`

当前流程：

```text
fetchMemberCompleteData
  ↓
ChatGuideMemberProfilePromptFormatter.makeProfileSummary
  ↓
PromptLocalizer.chatGuideQuestionGenerationPrompt
  ↓
AIRuntimeService.generateTextStream
  ↓
ChatGuideQuestionJSONParser.parse(rawText)
  ↓
失败后调用 chatGuideQuestionRepairJSONPrompt 再生成一次
  ↓

```

问题点：

1. 第一次输出其实已有业务可用内容，但因为结构类型不够宽容被丢弃。
2. repair 再请求会额外消耗一次模型调用。
3. repair 输出仍可能保留数字 id，导致第二次继续失败。
4. `parseFailed` 上抛后进入 coordinator fallback。

### 2.3 异步回写现状

文件：`SparkClient/Projects/Features/Chat/Application/ChatGuideQuestionGenerationCoordinator.swift`

当前成功和 fallback 都通过 `updateGuideBlock(token:stateStore:mutate:)` 回写，回写前统一调用：

```swift
guard await validateToken(token) else {
    logger.info("chat.guide.questions.stale_result_ignored ...")
    return false
}
```

`validateToken` 关键规则：

```swift
guard thread.memberID == token.memberID else { return false }
...
if target.payload.questionGeneration?.memberID != token.memberID {
    return false
}
```

风险：

1. token 校验适合保护“旧成员生成结果不覆盖新成员”，但如果 fallback 也被同样拦截，用户可能看不到最终兜底问题。
2. 日志中先出现 `generation_fallback`，后出现 `stale_result_ignored`，说明 fallback 回写路径被 token 校验挡住了。
3. 如果当前 payload 在生成过程中被刷新成 `memberID == nil` 或 questionGeneration meta 丢失，fallback 也会失败。

## 3. 初步根因判断

### 3.1 P0 根因：AI 输出 id 为数字，解析模型只接受 String

日志中的输出：

```json
{
  "id": 1,
  "title": "久坐程序员怎么护颈椎腰椎？",
  "prompt": "作为需要中度久坐的27岁男性程序员，日常工作中可以通过哪些健康科普类的方法保护颈椎和腰椎，降低久坐带来的健康影响？",
  "category": "popular_science"
}
```

而 `ChatGuideRawQuestion.id` 是 `String?`。Swift `Decodable` 默认不会把 JSON number 自动转成 String；数组中任意一个对象字段类型不匹配，都可能导致整个 `[ChatGuideRawQuestion]` decode 失败。

结论：

这是最直接、最高优先级的 parse_failed 根因。

### 3.2 P1 根因：解析器对“近似合法 JSON”容错不足

日志 preview 看起来像数组，但存在两种可能：

1. 实际输出是合法 JSON 数组，只是 `id` 类型不匹配。
2. 日志的 `preview=[ ... ]` 外层 `[` 是日志格式，实际模型输出可能是多个 JSON 对象片段，缺少数组外层。

无论是哪种，当前解析器都偏窄。健康科普问题生成属于 UI 辅助能力，不应因为 `id` 类型、外层数组缺失这类可修复格式问题直接 fallback。

### 3.3 P1 根因：fallback 回写与 stale token 校验耦合过紧

`stale_result_ignored` 出现在 `generation_fallback` 后，说明失败兜底也被当成“生成结果”走了同样 token 校验。

合理保护边界应该是：

1. AI 生成成功结果必须严格校验 memberID，避免旧成员问题覆盖新成员。
2. fallback 也不能覆盖新成员，但当同一 block 仍在 `generating` 且 thread.memberID 仍等于 token.memberID 时，应尽量落地 preset，避免 UI 长时间 loading。
3. 如果当前 payload meta 丢失但 thread/member/block 仍匹配，可以允许 fallback 修复为稳定状态。

### 3.4 P2 根因：prompt schema 没有明确 id 类型示例

当前 prompt 只说“每个对象必须包含 id、title、prompt、category”，没有明确 `id` 必须是字符串 snake_case。

模型自然可能输出：

```json
"id": 1
```

这在人类看来合理，但不满足客户端强类型解码。

### 3.5 P0 根因补充：默认绑定完成路径可能重复触发生成并取消前一条流

新日志中同一 `thread=734A573B`、同一 `block=7D62DE81`、同一 `member=10` 连续出现两次：

```text
termination=cancelled
generation_fallback errorCategory=ai_generation_failed
```

并且取消发生在请求开始后约 0.012s，不像正常网络超时或模型失败，更像本地 Task 被主动取消。

结合当前代码，最可能路径：

```text
默认绑定成员成功
  ↓
updateThreadMemberBinding 内部 handleMemberBindingChanged 已启动生成
  ↓
ChatView.task 继续调用 ensureGuideQuestionsReadyForCurrentThread(.defaultMemberBindingCompleted)
  ↓
第二次 ensure 使用的 messages snapshot / payload state 仍是旧值，未识别 active task
  ↓
startGeneration 再次执行 activeTasks[key]?.cancel()
  ↓
第一次流式请求被取消
  ↓
取消错误被 runGeneration 当作 aiGenerationFailed 并 fallback
```

需要重点验证：

1. 两次触发使用的 `messageID/blockID` 是否完全相同。
2. 第二次触发时 `activeTasks[key]` 是否已经写入。
3. 第二次触发时 `messages` 是否来自旧 stateStore snapshot，导致 target payload 不是最新 generating。
4. Task 取消是否被错误归类为 `ai_generation_failed`，并继续执行 fallback。

### 3.6 P1 根因补充：取消错误不应等价于 AI 生成失败

当前 `ChatGuideQuestionGenerationUseCase.runGeneration` catch 任意错误后统一抛：

```swift
throw ChatGuideQuestionGenerationUseCaseError.aiGenerationFailed
```

如果上层主动取消 Task，底层网关会记录：

```text
AI 流式网关流结束，termination=cancelled
AI 流式网关网络任务已取消
```

这类取消不应进入 fallback。原因：

1. 主动取消通常代表新一轮生成已经开始，旧任务应安静退出。
2. 如果旧任务取消后又 fallback，会和新任务争抢同一 block。
3. 用户切换成员时，旧成员任务取消后 fallback 可能短暂覆盖 loading 态。

正确处理是：取消错误向上保持 cancellation 语义，coordinator 收到 cancellation 后只清理 `activeTasks`，不落 fallback。

## 4. 修复目标

1. AI 返回的 3 条问题语义可用时，客户端应最大化解析成功。
2. 数字 id、缺少数组外层、wrapped object、markdown fence 都应支持。
3. 解析失败时才调用 repair；repair 仍失败才 fallback。
4. fallback 回写应稳定落地，不能因为过度 stale 校验导致卡片卡在 generating。
5. 仍必须保证旧成员生成结果不能覆盖新成员卡片。
6. 补齐测试，用日志样例作为回归用例。
7. 本地主动取消的流式任务不应被记录为 `ai_generation_failed`，也不应触发 fallback。
8. 默认绑定成员完成路径同一 thread/block 只启动一次生成任务。

## 5. 推荐修复方案

### 5.1 解析器支持宽容 id

新增 `LossyString` 或自定义 decode：

```swift
private struct ChatGuideRawQuestion: Decodable {
    var id: String?
    var title: String?
    var prompt: String?
    var category: String?

    enum CodingKeys: String, CodingKey {
        case id
        case title
        case prompt
        case category
    }

    init(from decoder: Decoder) throws {
        let container = try decoder.container(keyedBy: CodingKeys.self)
        if let stringID = try? container.decode(String.self, forKey: .id) {
            id = stringID
        } else if let intID = try? container.decode(Int.self, forKey: .id) {
            id = String(intID)
        } else if let doubleID = try? container.decode(Double.self, forKey: .id) {
            id = String(Int(doubleID))
        } else {
            id = nil
        }
        title = try? container.decode(String.self, forKey: .title)
        prompt = try? container.decode(String.self, forKey: .prompt)
        category = try? container.decode(String.self, forKey: .category)
    }
}
```

归一化 id 时，不建议直接保留 `"1"`、`"2"` 作为最终业务 id。推荐：

```text
如果 id 是纯数字 -> 使用 title 生成 guide_xxx 稳定 id
如果 id 是非空字符串 -> 清洗为 snake_case
如果 id 为空 -> 使用 title 生成 guide_xxx
```

这样可以避免不同成员都生成 `1/2/3`，导致 UI diff 或点击状态复用混乱。

### 5.2 解析器支持缺少数组外层的对象序列

新增兜底提取：

```text
输入: {"id":1,...}, {"id":2,...}, {"id":3,...}
处理: 包裹为 [ ... ] 后再 decode
```

推荐顺序：

```text
1. 去除 markdown fence
2. 尝试原文 decode 为 array
3. 尝试原文 decode 为 wrapped questions object
4. 从文本中截取第一个 [ 到最后一个 ]，尝试 decode array
5. 从文本中截取第一个 { 到最后一个 }：
   - 先尝试 decode wrapped object
   - 再尝试包裹为 [objectSequence] decode array
6. 仍失败才 throw invalidJSON
```

对象序列包裹时要避免把单个 wrapped object 错当成 array item。先尝试 wrapped，再尝试 sequence。

### 5.3 prompt 明确输出 schema

更新 `PromptLocalizer.chatGuideQuestionGenerationPrompt` fallback 和三套 `Prompts.strings`。

中文建议补充：

```text
输出必须是一个合法 JSON 数组，根节点必须是 [...]。
id 必须是字符串，使用英文 snake_case，例如 "daily_steps_for_programmer"，不要使用数字。
不要输出 ```json 代码块，不要输出解释文字。
```

示例应包含字符串 id：

```json
[
  {
    "id": "daily_steps_for_programmer",
    "title": "每天走多少步更合适？",
    "prompt": "结合久坐办公人群的日常活动特点，科普每天走多少步更合适以及如何循序增加活动量。",
    "category": "popular_science"
  }
]
```

注意：prompt 约束只能降低概率，不能替代客户端容错。

### 5.4 repair prompt 同步强化

repair prompt 要明确：

```text
1. 根节点必须是 JSON array。
2. id 必须转为字符串 snake_case。
3. 不得输出数字 id。
4. 不要改写问题语义，只修复 JSON 格式。
```

这样可以避免 repair 后再次因为数字 id 失败。

### 5.5 fallback 回写拆分 token 校验策略

保留成功结果的严格校验：

```text
applyGenerated:
  必须 thread.memberID == token.memberID
  必须 payload.questionGeneration.memberID == token.memberID
  必须 block/message 匹配
```

fallback 建议使用“同成员宽松修复校验”：

```text
applyFallback:
  必须 thread.memberID == token.memberID
  必须 message/block 匹配
  如果 payload.questionGeneration.memberID == token.memberID -> 允许回写
  如果 payload.questionGeneration.memberID == nil 且 state == generating -> 允许修复回写
  如果 payload.questionGeneration 缺失且 questions 为空 -> 允许修复回写
  如果 payload.questionGeneration.memberID 是其他成员 -> 禁止回写
```

这样既不覆盖新成员，又能把同一成员的失败状态稳定收敛到 preset。

### 5.6 日志细化

当前只有 `parse_failed`，不足以快速定位字段类型问题。

建议新增日志字段：

```text
chat.guide.questions.parse_failed
  thread
  block
  member
  stage=initial|repair
  parserError=invalid_json|empty_output|insufficient_questions|type_mismatch_id
  rawPreviewHash
  rawLength
```

注意：

1. 不记录完整 raw output，避免成员资料间接泄露。
2. 可以记录脱敏 previewHash 和 textLen。
3. Debug 包可短 preview，但生产日志建议默认关闭。

### 5.7 默认绑定完成触发收口

推荐把“默认绑定成功后启动生成”的责任只保留在一个入口。

方案 A：由 `updateThreadMemberBinding` 负责

```text
ChatView.applyComposerStartupMemberBindingIfNeeded()
  ↓
ChatDetailViewModel.updateThreadMemberBinding(...)
  ↓
handleMemberBindingChanged(...)
  ↓
markGenerating + startGeneration
  ↓
ChatView 不再额外调用 ensureGuideQuestionsReadyForCurrentThread(.defaultMemberBindingCompleted)
```

实现口径：

1. `applyComposerStartupMemberBindingIfNeeded()` 返回 true 时，说明 `updateThreadMemberBinding` 已经处理 guide question regeneration。
2. `ChatView.task` 不再追加 `.defaultMemberBindingCompleted` 的 ensure。
3. 如果为了恢复能力仍希望调用 ensure，则 ensure 必须只做幂等检查，不得取消已有 active task。

方案 B：由 `ChatView.task` 负责

```text
updateThreadMemberBinding 只更新绑定
  ↓
ChatView.await 默认绑定完成
  ↓
ensureGuideQuestionsReadyForCurrentThread(.defaultMemberBindingCompleted)
  ↓
startGeneration
```

该方案需要调整用户主动切换成员路径，否则会丢失切换成员后立即重新生成能力。

推荐选择方案 A，因为当前 `updateThreadMemberBinding` 已经覆盖“用户主动切换成员”和“默认绑定成员”两种绑定变化，职责更集中。

### 5.8 startGeneration 不应无条件取消同 key 任务

当前逻辑：

```swift
activeTasks[key]?.cancel()
activeTasks[key] = Task { ... }
```

建议改为：

```text
如果同 key 已有 active task：
  - 同 memberID：直接 return，不重启、不 cancel
  - 不同 memberID：取消旧任务，启动新任务
```

需要让 `activeTasks` 记录 memberID：

```swift
struct ActiveGuideQuestionTask {
    var memberID: Int
    var task: Task<Void, Never>
    var startedAt: Date
}

private var activeTasks: [ChatGuideQuestionTaskKey: ActiveGuideQuestionTask] = [:]
```

幂等规则：

```text
same thread + same message + same block + same member:
  ensure 重入 -> 不做任何事

same thread + same message + same block + different member:
  member changed -> cancel old and start new
```

这能直接避免同一成员默认绑定完成后重复触发导致流被取消。

### 5.9 Cancellation 语义独立处理

新增错误类型：

```swift
enum ChatGuideQuestionGenerationUseCaseError: Error, Equatable {
    case memberProfileUnavailable
    case aiGenerationFailed
    case parseFailed
    case cancelled
}
```

`runGeneration` 建议：

```swift
do {
    return try await collectResponseText(from: try await runtime.generateTextStream(request: request))
} catch is CancellationError {
    throw ChatGuideQuestionGenerationUseCaseError.cancelled
} catch {
    if Task.isCancelled {
        throw ChatGuideQuestionGenerationUseCaseError.cancelled
    }
    throw ChatGuideQuestionGenerationUseCaseError.aiGenerationFailed
}
```

`collectResponseText` 循环中也要检查取消：

```swift
for try await event in stream {
    try Task.checkCancellation()
    ...
}
```

coordinator 中：

```text
catch cancelled:
  log generation_cancelled
  不 applyFallback
  清理 activeTasks

catch 其他错误:
  generation_fallback
  applyFallback
```

### 5.10 activeTasks 清理不能误删新任务

当前任务结束后：

```swift
await MainActor.run {
    self.activeTasks[key] = nil
}
```

如果旧 task 被取消后，新 task 已经写入同一个 key，旧 task 结束时可能把新 task 清掉。

建议清理时带 token 校验：

```swift
await MainActor.run {
    if self.activeTasks[key]?.startedAt == token.startedAt,
       self.activeTasks[key]?.memberID == token.memberID {
        self.activeTasks[key] = nil
    }
}
```

或者给 active task 增加 `taskID: UUID`，按 taskID 清理。

### 5.11 缺少 completed 事件的处理边界

日志：

```text
AI 流式推理结束但缺少 completed 事件，scenario=chat, source=proOverlay, cost=0.012s
```

当前 `collectResponseText` 支持 `completedText ?? bufferedText`，理论上如果已经收到文本 delta，即使没有 completed 也可返回。但本次 cost 仅 0.012s，大概率没有任何 delta，因此被归为生成失败。

修复后区分：

| 场景 | 处理 |
| --- | --- |
| 主动 cancel，无 delta | cancelled，不 fallback |
| 主动 cancel，有 delta | cancelled，不使用半截内容 |
| 网络中断，无 delta | ai_generation_failed，fallback |
| 网络中断，有完整 JSON delta 但无 completed | 可尝试 parser，失败才 fallback |

是否完整不能只看 completed；如果 bufferedText 能解析为 3 条问题，可以接受。

### 7.2 UseCase 测试

新增：

1. 首次生成返回数字 id JSON 时，不触发 repair，直接成功。
2. 首次生成返回对象序列时，本地 parser 修复成功。

4. 首次失败且 repair 仍失败时，才抛 `parseFailed`。
5. Task 被主动取消时抛 `cancelled`，不抛 `aiGenerationFailed`。
6. 流式缺少 completed 但 bufferedText 是完整 JSON 时，可以解析成功。

### 7.3 Coordinator 测试

1. 同成员 parse failed 后 fallback 能回写为 `.fallback`。
2. 当前 payload meta 丢失但 block 仍为空 generating 时，fallback 能修复。
3. 成员切换后旧 token 的 generated 结果不能覆盖新成员。
4. 成员切换后旧 token 的 fallback 也不能覆盖新成员。
5. fallback 成功后不再反复触发 generation。
6. 同一 thread/block/member 重复 ensure 不取消已有任务。
7. 同一 thread/block 不同 member 重复 ensure 会取消旧任务并启动新任务。
8. 旧任务结束清理 activeTasks 时不能删除新任务。
9. cancellation 不触发 fallback，不写入 `.fallback`。

2. 默认绑定开启但无可绑定成员时，只写 preset，不启动 runtime。
3. 默认绑定成功后马上触发消息刷新，active task 仍保持，不被重复 ensure 取消。
4. 用户主动切换成员时，旧成员任务 cancel，但不 fallback，随后新成员生成成功。

## 8. 验收标准

1. 使用日志中的 AI 输出作为输入，`ChatGuideQuestionJSONParser.parse` 必须成功。
2. AI 输出 `"id": 1`、`"id": "1"`、缺失 `id` 均可解析并归一化。
3. AI 输出对象序列缺少数组外层时可解析。
4. 解析成功时不进入 `generation_fallback`。
5. 解析失败时 fallback 必须稳定回写同一 guide block。
6. fallback 后 UI 展示固定三条问题，不停留在 loading。
7. 成员切换后旧任务结果仍会被 stale 拦截。
8. 生产日志能区分是初次解析失败、repair 失败，还是 stale token 拦截。
9. 默认绑定成员成功进入会话时，同一个 thread/block/member 只出现一次 `generation_start`。
10. 同一成员重复 ensure 不出现 `termination=cancelled`。
11. 本地主动取消只记录 `generation_cancelled`，不记录 `generation_fallback errorCategory=ai_generation_failed`。
12. 用户切换成员时，旧任务取消不会把卡片写成旧成员 fallback。

## 9. 风险与注意事项

1. 解析器不要过度“猜测”不完整内容，例如截断 JSON 或字段缺失严重时仍应 fallback。
2. 数字 id 归一化不能直接保留 `1/2/3`，否则不同生成批次可能产生重复 id。
3. prompt 示例不要包含用户真实资料，避免模型照抄敏感字段到 title。
4. fallback 宽松校验只允许修复同成员或空 meta 的 generating 卡片，不能放宽到其他 memberID。
5. 修复后需要确认 `ChatGuideQuestionRowView` 的发送中状态是否依赖 id；如果依赖，稳定 id 更重要。
6. `activeTasks` 清理要防止旧任务 finally 把新任务删掉，这是 Swift Task 竞态里最容易漏的一处。
7. cancellation 不 fallback 后，要确认新任务一定能继续跑；否则 UI 可能保持 loading。该风险通过 active task 幂等与 taskID 清理共同解决。

## 10. 建议优先级

P0：

1. `ChatGuideQuestionJSONParser` 支持数字 id。
2. 增加日志样例 parser 回归测试。
3. 同一 thread/block/member 的重复生成触发必须幂等，不能取消正在进行的流。
4. 主动 cancellation 不得归类为 `ai_generation_failed`，不得触发 fallback。

P1：

1. `applyFallback` 使用宽松但同成员安全的 token 校验。
2. 对象序列和最大 JSON 片段提取。
3. `activeTasks` 清理增加 taskID/token 校验，避免旧任务清理新任务。
4. 默认绑定成功后的生成入口收口，避免 `handleMemberBindingChanged` 与 `.defaultMemberBindingCompleted` 双启动。

P2：

1. prompt 和 repair prompt 强化 id/string/schema。
2. parse_failed 日志细化。
3. 增加 `generation_cancelled` 日志，区分用户/生命周期取消与真实 AI 失败。
