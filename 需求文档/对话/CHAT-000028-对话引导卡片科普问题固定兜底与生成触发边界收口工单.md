## 1. 模块目标

对话引导卡片科普问题生成策略收口为：

1. AI 输出解析、解码、结构校验失败时，不再反复修复或保留生成中，直接使用第一阶段固定三条科普问题兜底。
2. 用户重新进入已有对话时，不再触发科普问题生成。
3. 科普问题生成只允许在两个业务时机触发：新建对话首次初始化、用户切换当前对话绑定成员。

目标效果：

```text
新建对话
  -> 如有绑定成员，触发一次 AI 生成
  -> 成功展示 AI 问题
  -> 失败/解码失败展示固定问题

重新进入旧对话
  -> 只展示已持久化结果
  -> 不补跑、不重试、不重新生成

切换当前对话成员
  -> 清空旧成员问题并重新生成
  -> 失败/解码失败展示固定问题
```

6. `ChatDetailViewModel` 加载消息后当前仍会通过 `.recoverGeneratingPayload` 触发恢复生成。

### 2.2 当前冲突点

当前代码和新策略存在冲突：

| 当前行为 | 新策略要求 |
| --- | --- |
| 重新进入对话后可能通过 `.enterThread` 触发生成 | 重新进入已有对话不触发生成 |
| 加载消息后可能通过 `.recoverGeneratingPayload` 恢复生成中 payload | 不恢复生成；历史 generating 应固定兜底 |
| 解码失败进入 `parseFailed` 后走 fallback，但仍可能存在 repair 或重试路径 | 解码失败直接固定问题兜底 |
| 生成触发原因包含 `.enterThread`、`.recoverGeneratingPayload`、`.defaultMemberBindingCompleted`、`.memberBindingChanged` | 只保留新建对话初始化、成员切换两个业务触发 |

### 2.3 需要保留的能力

以下能力仍然保留：

1. 新建对话时，如果当前 thread 已绑定成员，允许生成一次个性化科普问题。
2. 默认绑定成员开启时，新建对话等待成员绑定成功后，允许生成一次。
3. 用户切换当前对话绑定成员后，允许重新生成一次。
4. 未绑定成员、AI 失败、解析失败、解码失败、取消后无可用结果时，稳定展示固定三条问题。
5. 成功或固定兜底都需要写回同一个 guide block，并进入本地/服务端同步。

### 2.4 最新日志现象：AI 成功但卡片没有变化

用户补充日志显示，AI 已经生成成功，且输出为可解析的 3 条问题：

```text
AI 流式推理完成，scenario=chat, source=proOverlay, model=doubao-seed-2-1-pro-260628, cost=7.161s
AI输出 ... preview=[
    {
        "id": "daily_steps_standard",
        "title": "每日步数多少更健康",
        "prompt": "对于27岁久坐办公的男性来说，每日步数保持在什么范围更益健康，当前每日1500步左右的活动量有哪些可以调整的方向？",
        "category": "popular_science"
    },
    ...
]
chat.guide.questions.stale_result_ignored thread=9553BE42 block=B45B8495 tokenMember=10
```

但卡片未变化，且日志里没有出现：

```text
chat.guide.questions.generation_success
```

这说明问题不是 AI 生成失败，也不是 UI 不会渲染 `generated`，而是生成结果在 `applyGenerated -> updateGuideBlock -> validateToken` 阶段被拦截，没有进入 `persistPayloadUpdate`。

同一批日志还显示，在 AI 完成前，系统已经把首条 system guide message 上送到服务端：

```text
上送对话完成，requested=1, acceptedMessages=1, acceptedBlockUpdates=0
```

上送 body 中 guide block 仍是生成中空问题：

```json
"question_generation": {
  "source": "current_chat_ai",
  "state": "generating"
},
"questions": []
```

并且该 `question_generation` 缺少 `member_id`。这与当前 strict token 校验存在直接冲突：

```swift
if payloadMemberID != token.memberID {
    return false
}
```

因此当前最高概率链路是：

```text
AI 生成成功
  ↓
applyGenerated 准备回写
  ↓
validateToken 重新 loadMessages
  ↓
当前 payload.questionGeneration.memberID == nil
token.memberID == 10
  ↓
strict validateToken 返回 false
  ↓
stale_result_ignored
  ↓
没有 upsertMessageBlock
  ↓
没有 stateStore.updateMessages
  ↓
没有 block_updates
  ↓
UI 仍显示旧卡片
```

结论：

1. 当前日志已经基本能确定，生成结果没有更新 UI 的直接原因是 `applyGenerated` 被 stale token 校验拦截。
2. 服务端没有更新的原因不是服务端拒绝生成结果，而是客户端根本没有把 generated payload 落本地并标记 pending block sync。
3. 仍需进一步确认 `payload.questionGeneration.memberID` 为什么在生成中状态下为 nil：可能是插入初始卡片时 memberID 未绑定、后续 `markGenerating` 未落库、落库被 revision 拦截，或远端/本地旧 payload 覆盖了带 memberID 的 payload。

## 3. 需求范围

### 3.1 解码失败直接固定兜底

#### 需求说明

当 AI 返回内容无法被 `ChatGuideQuestionJSONParser` 解析为 3 条合法 `ChatGuideQuestion` 时，客户端不再把卡片停留在生成中，也不依赖多轮修复才能落地；本轮直接使用固定三条问题。

“解码失败”包含：

1. 非 JSON。
2. JSON 根结构不符合预期。
3. 字段类型不兼容且本地 parser 无法归一化。
4. 缺少 `title` / `prompt` 等必要展示字段。
5. 去重、过滤、补齐后仍不足 3 条。
6. repair prompt 返回仍不合法。

#### 基础要求与业务规则

1. 解码失败后，`payload.questions = ChatGuideQuestionPreset.phaseOne`。
2. `payload.questionGeneration.state = .fallback`。
3. `payload.questionGeneration.source = "preset"`。
4. `payload.questionGeneration.errorMessage` 写入可观测错误分类，例如 `parse_failed_initial_invalid_json`。
5. 不向用户暴露错误原因。
6. 不重复触发 AI 生成，不反复 repair。
7. fallback 结果必须本地持久化并同步服务端。

#### 主流程

```text
AI 流式返回文本
  ↓
ChatGuideQuestionJSONParser.parse(rawText)
  ↓
解析成功 -> generated
  ↓
解析失败 / 解码失败
  ↓
questions = ChatGuideQuestionPreset.phaseOne
questionGeneration.state = fallback
source = preset
errorMessage = parse_failed_xxx
  ↓
upsertMessageBlock(markPendingForSync: true)
  ↓
UI 展示固定三条问题
```

#### 失败、重试和恢复

1. parser 失败不触发新的 UI loading。
2. parser 失败不触发新对话消息。
3. 如保留 repair，最多一次；repair 失败必须立刻 fallback。
4. 若业务决定完全移除 repair，本工单允许直接删除 repair 调用路径。
5. fallback 回写失败时，下次进入对话也不再启动 AI；只允许做“本地固定兜底修复”。

#### 技术细节与设计代码位置

建议在 `ChatGuideQuestionGenerationUseCase.generate(input:)` 中明确区分：

```text
AI 调用失败 -> throw aiGenerationFailed
解析失败 -> throw parseFailed(...)
主动取消 -> throw cancelled
```

在 `ChatGuideQuestionGenerationCoordinator.runGeneration` 中处理：

```text
parseFailed -> applyFallback(errorCategory)
aiGenerationFailed -> applyFallback(errorCategory)
cancelled -> 不 fallback，由新任务或既有状态接管
```

如果取消发生在新建对话唯一一次生成中，且没有新任务接管，最终应由触发方按新建流程落固定问题，避免卡片永久 loading。

#### 验收标准

1. AI 返回无法解码时，卡片最终展示固定三条问题。
2. 解码失败不会导致卡片永久 loading。
3. 解码失败不会重复发起 AI 请求。
4. fallback 后重新进入对话，不再发起生成。
5. 本地重启后仍展示固定三条问题。

### 3.2 重新进入对话不触发科普问题生成

#### 需求说明

用户打开历史对话、切回对话列表再进入、App 重启后进入旧对话，都不应触发引导卡片科普问题 AI 生成。

重新进入只负责展示当前已持久化的 guide card 状态：

| 已持久化状态 | 重新进入展示 |
| --- | --- |
| `generated` + questions 非空 | 展示 AI 生成问题 |
| `fallback` + questions 非空 | 展示固定问题 |
| `preset` + questions 非空 | 展示固定问题 |
| `generating` + questions 为空 | 不补跑 AI，回写固定问题 |
| payload 旧版本但 questions 非空 | 原样展示 |
| payload 异常且 questions 为空 | 回写固定问题 |

#### 基础要求与业务规则

1. `.enterThread` 不应启动 AI 生成。
2. `.recoverGeneratingPayload` 不应启动 AI 生成。
3. 重新进入对话时，如果发现 guide card 停在 `generating`，只做固定兜底修复。
4. 重新进入对话时，不根据 memberID 重新判断是否需要生成。
5. 重新进入对话时，不因为 `memberProfileDigest` 变化而生成。
6. 重新进入对话时，不因为 AI model 变化而生成。

#### 主流程

```text
用户进入已有对话
  ↓
loadMessagesIfNeeded
  ↓
定位首条 guide card
  ↓
state == generated/fallback/preset 且 questions 非空
  ↓
直接展示，不调用 AI
```

异常修复流程：

```text
用户进入已有对话
  ↓
guide card state == generating 且 questions 为空
  ↓
不调用 AI
  ↓
回写 questions = preset
state = fallback 或 preset
source = preset
errorMessage = recovered_from_stale_generating
  ↓
展示固定三条问题
```

#### 失败、重试和恢复

1. 如果回写 preset 失败，本次 UI 可临时展示 preset，但需记录日志。
2. 不因为回写失败而启动 AI。
3. 下次进入仍可再次尝试本地固定兜底修复。
4. 服务端同步失败不影响本地展示，走现有 outbox 重试。

#### 技术细节与设计代码位置

当前冲突入口：

```swift
// ChatView.swift
await detailViewModel.ensureGuideQuestionsReadyForCurrentThread(reason: .enterThread)

// ChatDetailViewModel.swift
await triggerGuideQuestionGenerationIfNeeded(
    for: threadID,
    reason: .recoverGeneratingPayload
)
```

推荐调整：

1. 将 `ensureGuideQuestionsReadyForCurrentThread(reason: .enterThread)` 改为“只做卡片状态修复，不启动 AI”。
2. 删除或重命名 `.recoverGeneratingPayload`，避免语义误导。
3. 新增更明确的方法：

```swift
func repairGuideQuestionsForReenteredThreadIfNeeded() async
```

该方法只允许：

```text
generating/failed/empty -> preset
generated/fallback/preset with questions -> no-op
```

不允许调用 `generationUseCase.generate`。

#### 验收标准

1. 打开已有 generated 对话，不出现 `chat.guide.questions.generation_start`。
2. 打开已有 fallback 对话，不出现 `generation_start`。
3. 打开已有 preset 对话，不出现 `generation_start`。
4. 打开历史 generating 对话，不出现 `generation_start`，但最终展示固定三条问题。
5. App 重启后进入旧对话，行为一致。

### 3.3 只在新建对话和切换用户时触发生成

#### 需求说明

科普问题 AI 生成是“新上下文初始化”能力，不是“进入页面刷新”能力。触发边界必须明确收口。

允许触发 AI 生成的场景：

1. 新建对话后首次插入 guide card，并且已绑定成员或默认绑定成员成功。
2. 用户切换当前对话绑定成员。

不允许触发 AI 生成的场景：

1. 重新进入已有对话。
2. 下拉刷新或消息重载。
3. App 冷启动恢复旧对话。
4. `recoverGeneratingPayload`。
5. 健康数据滑块刷新。
6. 模型切换。
7. 成员资料 digest 变化。
8. block sync 拉取。

#### 基础要求与业务规则

1. 新建对话时，需要将“本次 guide card 是新建插入”作为触发上下文传给 coordinator。
2. 不能仅凭 `state == generating` 判断要生成，因为旧对话也可能残留 generating。
3. 成员切换时，即使已有旧问题，也允许清空并重新生成。
4. 切换到 nil 成员时，不生成，直接 preset。
5. 默认绑定成员成功属于新建对话初始化链路，只允许触发一次。

#### 推荐触发枚举

当前：

```swift
enum ChatGuideQuestionGenerationReason: Sendable {
    case enterThread
    case defaultMemberBindingCompleted
    case memberBindingChanged
    case recoverGeneratingPayload
}
```

建议收口为：

```swift
enum ChatGuideQuestionGenerationTrigger: Sendable {
    case newlyCreatedThread
    case memberBindingChanged
}
```

如果为了兼容暂时保留旧枚举，应规定：

```text
enterThread -> repair only, never generate
recoverGeneratingPayload -> deprecated / repair only, never generate
defaultMemberBindingCompleted -> 仅当本 thread 是本次新建对话时可生成
memberBindingChanged -> 可生成
```

#### 主流程：新建对话

```text
CreateThreadUseCase.execute
  ↓
创建 thread + 插入首条 system guide card
  ↓
如果 memberID 已存在
  ↓
ChatGuideQuestionGenerationCoordinator.startForNewThread
  ↓
生成成功 -> generated
生成失败/解码失败 -> fallback preset
```

默认绑定开启：

```text
CreateThreadUseCase.execute 插入 guide card
  ↓
进入 ChatView
  ↓
applyComposerStartupMemberBindingIfNeeded
  ↓
updateThreadMemberBinding 成功
  ↓
确认这是新建对话初始化链路
  ↓
触发一次 AI 生成
```

#### 主流程：用户切换成员

```text
用户切换当前对话成员
  ↓
updateThreadMemberBinding(newMemberID)
  ↓
取消旧任务
  ↓
newMemberID == nil -> preset
newMemberID != nil -> generating + startGeneration
  ↓
成功 generated / 失败 fallback preset
```

#### 技术细节与设计代码位置

建议新增“新建对话触发标记”，不要用页面进入推断：

```swift

    var messageID: UUID

```

```text

```

#### 验收标准

1. 新建对话且绑定成员：触发一次 AI 生成。
2. 新建对话且未绑定成员：直接固定问题，不触发 AI。
3. 默认绑定成员成功的新建对话：触发一次 AI 生成。
4. 重新进入同一对话：不触发 AI。
5. 切换成员：触发一次 AI 生成。
6. 切换为空成员：直接固定问题，不触发 AI。
7. 切换成员后再次重新进入：不触发 AI。

### 3.4 AI 成功后卡片未更新的回写链路修复

#### 需求说明

当 AI 已成功生成 3 条科普问题时，客户端必须把生成结果回写到同一个 guide block，并刷新当前消息卡片；如果回写失败，要有足够日志定位失败发生在 token 校验、CoreData revision、stateStore 刷新还是 outbox 同步。

本问题不应通过“重新进入对话再生成一次”来掩盖。按照本工单策略，重新进入不会生成；因此首次生成成功后的本地回写必须可靠。

#### 基础要求与业务规则

1. `applyGenerated` 成功时必须出现 `generation_success` 日志。
2. `applyGenerated` 不能因为 `payload.questionGeneration.memberID == nil` 就直接丢弃同一 thread/block 的成功结果。
3. 只有确认当前 thread.memberID 已变更为其他成员时，才拦截旧结果。
4. 如果 guide block 仍是 `generating`、`questions=[]`，且 thread.memberID 与 token.memberID 一致，即使 payload meta 缺少 memberID，也应允许 generated 回写。
5. generated 回写成功后，必须调用 `upsertMessageBlock(markPendingForSync: true)`。
6. `upsertMessageBlock` 返回 true 后，必须调用 `stateStore.updateMessages`。
7. 本地 pending block 后续应进入 `ChatOutboxPipeline.pushOutbox` 的 block_updates。

#### 主流程

```text
AI 生成成功
  ↓
ChatGuideQuestionJSONParser.parse 成功
  ↓
applyGenerated(token, output)
  ↓
validateTokenForGenerated
  ↓
允许条件：
  thread.memberID == token.memberID
  messageID/blockID 匹配
  payload.questionGeneration.memberID == token.memberID
    或 payload.questionGeneration.memberID == nil 且 state == generating 且 questions 为空
  ↓
payload.questions = output.questions
questionGeneration.state = generated
questionGeneration.memberID = output.memberID
  ↓
upsertMessageBlock(markPendingForSync: true)
  ↓
stateStore.updateMessages
  ↓
UI 从 loading 切到问题列表
  ↓
下次 outbox 同步上送 block_updates
```

#### 失败、重试和恢复

1. 如果 `validateTokenForGenerated` 因 thread.memberID 已切换而失败：丢弃旧结果，记录 stale。
2. 如果 `validateTokenForGenerated` 因 payload meta 缺少 memberID 而失败：不应丢弃；应允许同成员 generating 空卡片修复。
3. 如果 `upsertMessageBlock` 返回 false：记录 revision、oldRevision、newRevision、blockID、messageID，UI 暂不更新。
4. 如果 `upsertMessageBlock` 返回 true 但 UI 不变：重点排查 `stateStore.updateMessages` 的 messageID/blockID 是否匹配当前渲染的数据源。
5. 如果 UI 已变但服务端未同步：重点排查 pending block 是否被加入 outbox、`pendingBlocks(limit:)` 是否能读到、`pushBlockUpdates` 是否发送。

#### 技术细节与设计代码位置

当前直接相关代码：

```swift

            memberProfileDigest: output.memberProfileDigest,
            generatedAt: output.generatedAt
        )
    }
}
```

当前风险点：

```swift
if payloadMemberID != token.memberID {
    return false
}
```

推荐调整为“同 thread 当前绑定成员可信，payload memberID 可修复”：

```text
validateGenerated:
  thread.memberID 必须等于 token.memberID
  message/block 必须匹配
  如果 payload.questionGeneration.memberID == token.memberID -> 允许
  如果 payload.questionGeneration.memberID == nil
     且 state == generating
     且 questions.isEmpty
     -> 允许，并在 generated payload 中补齐 memberID
  如果 payload.questionGeneration.memberID 是其他成员 -> 拦截
```

这与成员切换防覆盖不冲突，因为真正的成员切换以 `thread.memberID != token.memberID` 为第一道硬校验。

| 日志停在哪一步 | 结论 |
| --- | --- |

#### 验收标准

1. AI 生成成功后必须出现 `generation_success`。
2. 同一 thread/block 的卡片从 loading 切换到 3 条 AI 问题。
3. 成功回写后本地重新加载该 thread，guide payload 为 `state=generated` 且 `questions.count == 3`。
4. 成功回写后至少产生一次 pending block sync，服务端 ACK 后 `acceptedBlockUpdates >= 1` 或整消息 push 携带最终 generated payload。
5. 如果 payload 初始缺少 `questionGeneration.memberID`，但 thread.memberID 匹配 token.memberID，仍能成功回写 generated。
6. 如果用户已切换到其他 memberID，旧 AI 成功结果仍被拦截。

## 4. 整体业务流程

```text
新建对话
  ↓
插入 guide card
  ↓
是否绑定成员？
  ├─ 否 -> 固定三条问题，state=preset
  └─ 是 -> AI 生成一次
          ├─ 成功 -> state=generated, questions=AI 输出
          └─ 失败/解码失败 -> state=fallback, questions=preset

重新进入对话
  ↓
读取已持久化 guide card
  ↓
是否已有可展示 questions？
  ├─ 是 -> 直接展示，不生成
  └─ 否 -> 固定三条问题修复，不生成

切换成员
  ↓
是否有新 memberID？
  ├─ 否 -> 固定三条问题，state=preset
  └─ 是 -> AI 重新生成一次
          ├─ 成功 -> state=generated
          └─ 失败/解码失败 -> state=fallback, questions=preset
```

## 5. 状态模型

| 状态 | 进入方式 | 是否允许重新进入时触发 AI | UI |
| --- | --- | --- | --- |
| `generating` | 新建对话或切换成员后短暂状态 | 否 | loading；若为历史残留则修复为 preset |
| `generated` | AI 生成成功 | 否 | AI 问题 |
| `fallback` | AI 失败/解码失败 | 否 | 固定问题 |
| `preset` | 未绑定成员或历史修复 | 否 | 固定问题 |
| `failed` | 不建议停留 | 否 | 立即固定兜底 |

关键原则：

```text
重新进入对话永远不是 AI 生成触发器。
state == generating 也不是 AI 生成触发器。
只有明确的新建对话初始化或成员切换事件，才是 AI 生成触发器。
```

## 6. 数据与持久化

本地持久化：

1. AI 成功、AI 失败、解码失败、历史 generating 修复，都必须写回同一个 guide block。
2. 固定兜底使用 `ChatGuideQuestionPreset.phaseOne`。
3. 解码失败建议写入：

```text
questionGeneration.state = fallback
questionGeneration.source = preset
questionGeneration.errorMessage = parse_failed_xxx
```

4. 历史 generating 修复建议写入：

```text
questionGeneration.state = fallback
questionGeneration.source = preset
questionGeneration.errorMessage = recovered_from_stale_generating
```

服务端同步：

1. 所有最终态都走 `upsertMessageBlock(markPendingForSync: true)`。
2. 重新进入对话触发的“固定兜底修复”也需要同步，避免多端反复看到 generating。
3. 远端拉取不触发 AI，只合并远端 block 状态。

## 7. 错误模型

| 错误 | 处理 |
| --- | --- |
| AI 请求失败 | 固定问题 fallback |
| AI 输出为空 | 固定问题 fallback |
| AI 输出非 JSON | 固定问题 fallback |
| JSON 解码失败 | 固定问题 fallback |
| JSON 不足 3 条且无法补齐 | 固定问题 fallback |
| 主动取消且有新任务接管 | 不 fallback |
| 主动取消且无新任务接管 | 固定问题兜底修复 |
| 重新进入发现 generating | 固定问题兜底修复，不生成 |
| 重新进入发现 payload 损坏 | 固定问题兜底修复，不生成 |
| 成员切换到 nil | 固定问题 preset |

## 8. 与其他模块的接口边界

本模块负责：

1. 控制引导卡片科普问题生成触发时机。
2. 把解析/解码失败稳定收敛到固定问题。
3. 重新进入旧对话时展示或修复已有 guide card。
4. 成员切换后重新生成或固定兜底。

本模块不负责：

1. 生成健康数据滑块内容。
2. 点击问题后的 AI 对话回复。
3. 成员资料 complete-data 的服务端定义。
4. 大模型供应商网关的底层流式协议。

## 11. 当前实现、缺口与演进

当前实现：

1. 已有 `ChatGuideQuestionPreset.phaseOne`。
2. 已有 `questionGeneration.state`。
3. 已有 AI 生成 use case。
4. 已有 coordinator 的 active task 去重、取消和 fallback 回写能力。
5. 当前代码已有 `enterThread`、`recoverGeneratingPayload` 等进入/恢复触发原因。

当前缺口：

1. 重新进入对话仍可能触发生成或恢复生成。
2. `state == generating` 容易被误当作“应该继续生成”的依据。
3. 解码失败策略需要明确为固定兜底最终态，而不是继续扩大修复链路。
4. 缺少“只有新建对话/切换成员可触发 AI”的测试。
5. 缺少历史 generating 固定修复的明确方法。

建议演进：

1. 把 trigger 从页面生命周期中剥离，改成业务事件驱动。
2. 将 `enterThread` 语义改为 `repairOnEnter`，避免误读。
3. 如后续要支持“换一批问题”，应新增显式用户操作触发，不复用重新进入对话触发。

## 12. 整体验收标准

1. 解码失败场景直接展示固定三条问题。
2. 解码失败结果本地持久化并同步服务端。
3. 用户重新进入已有对话，不触发科普问题生成。
4. App 重启恢复旧对话，不触发科普问题生成。
5. 历史 generating 状态重新进入时，固定兜底修复，不调用 AI。
6. 新建对话仍可按绑定成员生成一次。
7. 用户切换当前对话成员仍可重新生成一次。
8. 未绑定成员或切换为空成员时直接固定问题。
9. 日志中能清楚区分 `newly_created_thread`、`member_binding_changed`、`reenter_repair_to_preset`。
10. 不再出现“重新进入旧对话后又发起 AI 流式请求”的行为。
11. 不再出现“AI 输出成功但随后 `stale_result_ignored` 导致卡片不更新”的行为。
12. 如果生成中 payload 缺少 `memberID`，但当前 thread.memberID 仍匹配 token.memberID，generated/fallback 必须能补齐 memberID 并落库。
13. 成功落库后 UI 与服务端同步链路都有日志闭环，能判断问题停在 validate、persist、UI refresh 还是 block_updates。
