## 1. 背景与问题

`CHAT-000015` 已建立首页“制定体检计划”进入 Chat 后自动初始化并发送小任务的流程。当前方案已经有 `payloadVersion` 与 `payloadHash` 的雏形，但后期一旦出现工具列表、Prompt、业务关联参数、结果保存策略变化，仅靠“发现内容不同就覆盖”不够稳。

需要补齐一套通用版本机制，解决以下问题：

1. 内置小任务升级时，如何判断必须更新本地 SmallTask。
2. 用户或调试环境手动改过本地小任务时，是否允许覆盖。
3. 工具列表变更后，当前模型不支持新工具时如何降级或提示。
4. 小任务 Prompt 变化但版本号未升级时，如何防止不可追踪的隐式变更。
5. 后续“报告解读”等业务接入时，是否能复用同一套版本治理。

## 2. 产品与工程目标

1. 每个内置小任务必须有稳定 `business_key`、稳定 `small_task_code` 和显式 `definition_version`。
2. 客户端启动或业务入口触发时，按版本判断是否需要注册、升级或跳过。
3. 升级必须幂等：同一用户、同一业务、同一版本重复执行不重复写入。
4. 版本升级必须可观测：记录升级前后版本、hash、原因和结果。
5. 版本升级不能破坏用户正在编辑的草稿和已经创建的历史任务。
6. 工具能力变化必须纳入兼容判断，避免升级后小任务无法被当前模型执行。

## 3. 推荐方案结论

建议把内置小任务定义拆成三个版本层级：

1. **definition_version**  
   小任务定义版本。只要 name、brief、prompt、tool_list、icon、默认 source 等任一内置配置发生语义变化，就必须递增。

2. **minimum_runtime_version**  
   小任务运行时最低版本。用于声明该小任务依赖的客户端能力，例如 `generate_task` 支持 `business_type/business_id` 后，体检计划小任务应声明最低 runtime。

3. **tool_contract_version**  
   工具契约版本。用于声明小任务依赖的工具参数与返回结构版本，例如 `create_knowledge_document` 必须返回 `business_type/business_id`。

最终判断逻辑：

```text
没有注册记录 -> 插入当前内置定义
已有记录且 definition_version 相同且 payload_hash 相同 -> 跳过
已有记录但 definition_version 更高 -> 本地比当前包新，跳过并记录 warning
已有记录但 definition_version 更低 -> 执行升级
已有记录版本相同但 payload_hash 不同 -> 视为工程错误，记录 warning，并按策略修复
运行时或工具契约不满足 -> 不升级到不可运行版本，保留旧版本并提示或记录日志
```

## 4. 数据模型设计

### 4.1 内置定义模型

建议在 `AutoSmallTaskDefinition` 中补齐以下字段：

```swift
struct AutoSmallTaskDefinition: Codable, Equatable, Sendable {
    let businessKey: ChatAutoSmallTaskBusinessKey
    let smallTaskCode: String
    let name: String
    let brief: String
    let prompt: String
    let icon: String
    let toolList: [String]

    let definitionVersion: Int
    let minimumRuntimeVersion: Int
    let toolContractVersion: Int
    let migrationPolicy: AutoSmallTaskMigrationPolicy
}
```

### 4.2 迁移策略

```swift
enum AutoSmallTaskMigrationPolicy: String, Codable, Sendable {
    case overwriteBuiltInOnly
    case preserveUserEdited
    case forceOverwrite
}
```

推荐默认使用 `overwriteBuiltInOnly`：

| 策略 | 含义 | 适用场景 |
| --- | --- | --- |
| `overwriteBuiltInOnly` | 只覆盖由内置定义生成、且未被用户编辑的小任务 | 大多数 Prompt / 工具升级 |
| `preserveUserEdited` | 用户编辑过就保留，另写待升级状态 | 允许高级用户自定义小任务 |
| `forceOverwrite` | 强制覆盖本地定义 | 安全修复、严重错误 Prompt 修复 |

### 4.3 UserDefaults 注册记录

UserDefaults 仍只存轻量索引和版本状态，不存完整 Prompt。

```json
{
  "user_id": "当前账号ID",
  "business_key": "health_exam_plan",
  "small_task_code": "Service_health_exam_plan_task",
  "local_small_task_id": 10001,
  "definition_version": 2,
  "minimum_runtime_version": 1,
  "tool_contract_version": 1,
  "payload_hash": "sha256-of-definition",
  "last_migration_action": "upgraded",
  "last_migration_reason": "definition_version_increased",
  "created_at": "2026-08-11T00:00:00Z",
  "updated_at": "2026-08-11T00:00:00Z"
}
```

推荐 key 保持不变：

```text
chat.autoSmallTask.registry.{userID}.{businessKey}
```

### 4.4 SmallTask 本地记录扩展建议

如果当前 SmallTask 数据表无法保存版本字段，可先继续通过 UserDefaults 保存版本。后续建议 SmallTask 本地表增加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `source` | enum/string | `.local`、`.remote`、`.builtIn` |
| `built_in_business_key` | string? | 内置业务 key |
| `built_in_definition_version` | int? | 内置定义版本 |
| `built_in_payload_hash` | string? | 内置定义 hash |
| `is_user_edited` | bool | 用户是否手动编辑过 |
| `updated_by` | string | `built_in_migration` / `user` / `remote_sync` |

本期如果不改数据库，至少要在 UserDefaults 中保留这些语义。

## 5. 版本号规则

### 5.1 什么时候必须升级 definition_version

以下任一变化必须递增 `definitionVersion`：

1. `prompt` 语义变化。
2. `toolList` 新增、删除或替换工具。
3. `brief` 或 `name` 改变用户理解。
4. 保存结果策略变化，例如从“只创建任务”变成“先保存知识库再创建任务”。
5. 任务业务关联参数变化，例如新增 `business_type/business_id`。
6. 风险提示、医疗免责声明、红旗症状处理规则变化。

以下变化可以不升级：

1. 纯格式化、空格、换行调整，且 `payloadHash` 归一化后不变。
2. 内部注释变化。
3. 不影响行为的文案微调。

### 5.2 payload_hash 规则

`payloadHash` 必须由规范化后的关键字段计算：

```text
business_key
small_task_code
name
brief
prompt
icon
sorted(tool_list)
definition_version
minimum_runtime_version
tool_contract_version
migration_policy
```

注意：`tool_list` 建议排序后参与 hash，避免仅因数组顺序变化导致误判；但最终写入 SmallTask 时仍保留定义中的展示顺序。

### 5.3 版本与 hash 冲突处理

| 场景 | 处理 |
| --- | --- |
| version 相同，hash 相同 | 跳过 |
| version 升高，hash 不同 | 正常升级 |
| version 升高，hash 相同 | 允许，但记录 `version_only_upgrade` |
| version 相同，hash 不同 | 记录 `definition_hash_changed_without_version_bump`，Debug 环境 warning，Release 按策略修复 |
| 本地 version 高于内置 version | 跳过，记录 `local_version_newer_than_bundle` |

## 6. 自动初始化与升级流程

### 6.1 入口流程

```text
首页点击“制定体检计划”
-> 读取内置 AutoSmallTaskDefinition
-> 检查 runtime/tool contract 是否满足
-> 读取 UserDefaults registry
-> 读取本地 SmallTask 快照
-> 计算 migration decision
-> 执行 insert / upgrade / skip / blocked
-> 写回 registry
-> 创建 pending auto intent
-> 进入 Chat
-> 0.5 秒后自动发送
```

### 6.2 迁移决策枚举

```swift
enum AutoSmallTaskMigrationDecision {
    case insert
    case skip
    case upgrade(fromVersion: Int, toVersion: Int)
    case preserveUserEdited
    case blocked(reason: AutoSmallTaskMigrationBlockedReason)
}
```

### 6.3 阻断原因

```swift
enum AutoSmallTaskMigrationBlockedReason: String {
    case runtimeVersionTooLow
    case toolContractVersionTooLow
    case missingRequiredTools
    case localVersionNewerThanBundle
}
```

如果被阻断：

1. 不创建自动发送 intent。
2. 展示轻提示：`体检计划小任务初始化失败，请稍后更新后重试。`
3. 记录日志，包含 business_key、small_task_code、required version、current version。

## 7. 工具更新兼容策略

### 7.1 工具列表变化

当小任务新增工具时，必须同时确认：

1. AI 设置中的默认模型支持工具调用。
2. 工具场景列表中存在该工具。
3. 当前小任务 Prompt 对旧工具返回结构没有依赖。

如果新增工具是硬依赖，升级时必须检查 `missingRequiredTools`。如果新增工具是可选能力，应在 Prompt 中明确：

```text
如果工具不可用，不要臆造工具结果；可基于已有资料生成保守计划。
```

### 7.2 工具契约变化

例如 `create_knowledge_document` 从只返回保存状态升级为返回：

```json
{
  "ok": true,
  "business_type": "knowledge",
  "business_id": "xxx"
}
```

此时必须递增 `toolContractVersion`，并让体检计划小任务声明：

```text
minimumRuntimeVersion = 1
toolContractVersion = 2
```

升级前检查客户端工具注册表是否达到该契约版本。未达到时保留旧版本，避免 Prompt 要求模型读取不存在的返回字段。

## 10. 关键实现要求

### 10.1 AutoSmallTaskDefinition

需要新增：

1. `definitionVersion`
2. `minimumRuntimeVersion`
3. `toolContractVersion`
4. `migrationPolicy`
5. 规范化 `payloadHash`

### 10.2 AutoSmallTaskRegistry

需要从“注册 if needed”升级为“计划迁移并执行”：

```swift
func registerOrMigrateIfNeeded(
    definition: AutoSmallTaskDefinition,
    userID: Int64

```

返回结果建议：

```swift
struct AutoSmallTaskRegistrationResult {
    let smallTask: SmallTask?
    let action: AutoSmallTaskMigrationAction
    let isRunnable: Bool
    let blockedReason: AutoSmallTaskMigrationBlockedReason?
}
```

### 10.3 MigrationPlanner

只负责纯决策，不执行 IO，便于单元测试：

```swift
func plan(
    definition: AutoSmallTaskDefinition,
    registryRecord: AutoSmallTaskRegistryRecord?,
    existingTask: SmallTask?,
    runtimeCapability: AutoSmallTaskRuntimeCapability
) -> AutoSmallTaskMigrationDecision
```

### 10.4 CapabilityChecker

负责检查：

1. 当前客户端 runtime version。
2. 当前工具契约版本。
3. `definition.toolList` 是否可被注册表识别。
4. 当前默认模型是否支持工具调用。

注意：模型能力检查仍应在自动发送前做一次，因为用户可能在进入 Chat 前后切换模型。

## 12. 测试与验收

### 12.1 单元测试

必须覆盖：

1. 无 registry、无本地任务：返回 `insert`。
2. version/hash 一致：返回 `skip`。
3. registry version 低于内置 version：返回 `upgrade`。
4. registry version 高于内置 version：返回 `blocked(localVersionNewerThanBundle)` 或 `skip`，但必须记录 warning。
5. version 相同但 hash 不同：返回 hash conflict。
6. runtime version 不满足：返回 `blocked(runtimeVersionTooLow)`。
7. tool contract 不满足：返回 `blocked(toolContractVersionTooLow)`。
8. required tools 缺失：返回 `blocked(missingRequiredTools)`。

### 12.2 集成验收

1. 首次点击首页“制定体检计划”，插入 v1 小任务并自动发送。
2. 第二次点击首页“制定体检计划”，不重复插入小任务，但仍为新会话自动发送一次。
3. 把内置定义升到 v2 后，再点击入口，本地小任务被升级为 v2。
4. v2 新增工具但本地工具不可用时，不升级到不可运行版本，展示轻提示。
5. 自动发送前切换到不支持工具的模型时，不发送，保留草稿并提示。
6. 历史已经创建的体检任务不因小任务升级而改变。

## 13. 风险与边界

1. **只靠 UserDefaults 存版本有丢失风险**  
   UserDefaults 被清理后会重新初始化。因为 smallTaskCode 稳定，仍可通过本地 SmallTask 快照找回，风险可控。

2. **用户编辑保护依赖本地 SmallTask 能识别编辑来源**  
   如果当前数据模型没有 `is_user_edited`，本期先按 hash 判断是否仍等于上一版内置定义。等于则可覆盖；不等于则视为疑似用户编辑，默认保留。

3. **工具契约版本需要事实源**  
   如果当前工具注册表没有 contract version，需要先用客户端常量维护，后续再沉淀为工具元数据。

4. **远程小任务配置优先级暂不处理**  
   如果服务端未来下发同 code 小任务，需要再定义 remote 与 built-in 的优先级。本工单建议先保持：业务自动初始化优先保障本地可运行，远程同步不覆盖本地 built-in 版本，除非服务端有更高优先级标识。

1. 第一阶段：补齐版本字段、UserDefaults registry、迁移决策器和单元测试。
2. 第二阶段：接入首页体检计划小任务注册流程，支持 v1 -> v2 升级。

4. 第四阶段：复用到“报告解读小任务”。

## 15. 最终验收口径

本工单完成后，内置小任务不再是“一次插入后永久不变”的本地配置，而是一个可版本化、可升级、可阻断、可观测的业务能力。后续 Prompt、工具列表、知识库保存方式、任务关联方式发生变化时，只需要递增版本并补充迁移策略，客户端即可在用户再次触发业务入口时自动完成安全升级。
