## 工单 `TOOL-CALL-000001`：生成营养数据并在对话内插入营养卡片

### 工单状态

新需求，待实现。

## 1. 背景

### Q：这个工单要解决什么问题？

A：用户在对话中描述饮食后，希望 AI 可以把饮食内容整理成结构化营养数据，并在消息流中生成一张可操作的“营养卡片”。用户确认后，可以把营养数据写入系统健康应用。

典型场景：

1. 用户说：“我早餐吃了两个鸡蛋、一杯牛奶、一片吐司，帮我记录一下营养。”
2. AI 根据文本估算或整理营养数据。
3. AI 调用 `make_nutrition_data` 工具生成营养卡片。
4. 对话消息内展示营养卡片，包含蛋白质、碳水、脂肪、能量、时间。
5. 用户点击“写入健康应用”。
6. App 请求 Apple 健康写入权限，并把对应营养数据写入 HealthKit。
7. 写入成功后，卡片状态更新为“已写入健康”。

### Q：为什么不是只让 AI 回复文本？

A：文本无法承载后续操作和状态。营养数据需要：

1. 结构化展示：蛋白质、碳水、脂肪、能量分别展示。
2. 用户确认：AI 估算值可能不准确，需要用户看到卡片后再写入。
3. 权限处理：写入 Apple 健康必须由客户端触发系统授权。
4. 状态持久化：写入成功后，历史消息里应保留已写入状态，避免重复写入。
5. 后续扩展：未来可以支持编辑数值、选择用餐时间、按成员或账号归属管理。

### Q：参考 hanlin-ai 的哪些能力？

A：hanlin-ai 中已经有一套可参考的营养卡片体验：

| 参考位置 | 可参考点 |
| --- | --- |
| `hanlin-ai/AI_HLY/Services/ChatServices/ChatTools.swift` | `fetch_nutrition_details`、`make_nutrition_data` 工具定义和触发描述 |
| `hanlin-ai/AI_HLY/Services/ChatServices/HealthServices.swift` | `makeNutritionData(...)` 与 `writeNutritionData(...)` 的 HealthKit 写入逻辑 |
| `hanlin-ai/AI_HLY/Views/Components/ChatViewComponents.swift` | 营养卡片 UI：碳水、脂肪、蛋白质、能量，写入健康按钮和已写入状态 |

但 SparkClient 不直接照搬旧项目数据流。SparkClient 应复用现有工具调用、消息块、副作用落库、消息渲染和保存状态体系。

## 2. 现状

### Q：SparkClient 目前已经有什么基础能力？

A：已有基础能力如下：

| 能力 | 当前情况 |
| --- | --- |
| 工具名 | `SparkToolName.makeNutritionData = "make_nutrition_data"` 已存在 |
| 营养模型 | `SparkNutritionCard` 已存在，字段包含 `date/proteinGrams/carbohydratesGrams/fatGrams/energyKilocalories/isWritten` |
| 生成数据 | `SparkHealthTool.makeNutritionData(...)` 已存在 |
| 写入健康 | `SparkHealthTool.writeNutritionData(_:)` 已存在，可写入 `.dietaryProtein`、`.dietaryCarbohydrates`、`.dietaryFatTotal`、`.dietaryEnergyConsumed` |
| 工具执行器 | `ToolHubMakeNutritionData.swift` 已存在 |
| 工具调用框架 | `ToolHub`、`ToolExecutionResult`、`ToolSideEffect`、`MessageRunActor` 已存在 |
| 消息卡片渲染 | `ChatMessageBlock+Render.swift` 已支持多种结构化卡片 |
| 保存状态模式 | `structuredHealthCards` 已有保存中、保存成功、按钮状态等可参考实现 |

### Q：当前缺口是什么？

A：当前 `make_nutrition_data` 工具只把营养卡片 JSON 放进工具输出文本：

```text
nutrition_card={...}
```

这会导致：

1. 消息流里没有真正的营养卡片。
2. 用户不能直接点击“写入健康应用”。
3. `isWritten` 状态无法在消息卡片中持久化更新。
4. 工具结果没有走 SparkClient 现有的消息块插卡逻辑。

本工单的核心就是：**把 `make_nutrition_data` 从“文本工具输出”升级为“工具调用后插入消息卡片”。**

## 3. 目标

### Q：一句话需求是什么？

A：AI 在对话中调用 `make_nutrition_data` 后，客户端应在当前助手消息内插入营养卡片；用户点击卡片按钮后，将营养数据写入 Apple 健康，并把写入状态持久化到当前消息。

### Q：第一期范围是什么？

A：

1. 支持 `make_nutrition_data` 生成单张营养卡片。
2. 营养卡片展示蛋白质、碳水、脂肪、能量、记录时间。
3. 营养卡片支持“写入健康应用”。
4. 写入成功后卡片展示“已写入健康”并禁用按钮。
5. 写入失败时给出轻量错误提示，不改变已写入状态。
6. 历史消息重新加载后，营养卡片和写入状态仍能恢复。
7. 工具插卡走 SparkClient 现有工具 sideEffect / message block / render context 逻辑。

### Q：第一期不做什么？

A：

1. 不做营养数值编辑页面。
2. 不做多餐合并分析。
3. 不做服务端营养记录同步。
4. 不做按家庭成员写入不同成员健康数据，因为 Apple 健康写入是当前设备健康库能力，不等同于医疗成员资料。
5. 不做复杂食物数据库精确计算，第一期只承接 AI 工具给出的估算值或用户明确提供的数值。

## 4. 工具调用设计

### Q：工具名称和参数怎么设计？

A：复用现有工具名：

```swift
SparkToolName.makeNutritionData = "make_nutrition_data"
```

参数建议：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `protein` | number | 否 | 蛋白质，单位 g |
| `carbohydrates` | number | 否 | 碳水化合物，单位 g |
| `fat` | number | 否 | 脂肪，单位 g |
| `energy` | number | 否 | 能量，单位 kcal |
| `date` | string | 否 | 记录时间，ISO8601；不传则使用当前时间 |
| `meal_name` | string | 否 | 餐次/标题，例如“早餐”“午餐”“加餐” |
| `source_text` | string | 否 | AI 解析依据摘要，用于详情或调试 |

第一期可以先只落地现有四个数值字段，`date/meal_name/source_text` 作为推荐扩展字段。如果要避免模型生成的时间不准，`date` 第一版也可以先统一取客户端当前时间。

### Q：工具返回应该是什么？

A：工具返回给模型的文本可以保留简短提示，但 UI 插卡必须通过 `ToolSideEffect` 完成。

推荐：

```swift
ToolExecutionResult(
    toolName: SparkToolName.makeNutritionData,
    outputText: "营养卡片已生成，请在消息内确认后写入健康应用。",
    sensitive: false,
    shouldBypassModel: true,
    sideEffects: [.nutritionCards([card])]
)
```

如果第一期不新增专用 sideEffect，也可以通过现有 `.externalConnectorRichBlocks([ChatMessageBlock])` 插入卡片，但长期建议新增专用类型，原因是：

1. 命名清晰，后续维护更直观。
2. 与 `sleepVisualization/workoutVisualization/structuredHealthCards` 同级。
3. 方便 MessageRunActor 做稳定 blockID、状态更新和日志区分。

推荐新增：

```swift
enum ToolSideEffect {
    case nutritionCards([SparkNutritionCard])
}
```

并在 `ToolSideEffectBlockMapper` 中映射成消息块。

## 5. 消息块与数据模型

### Q：营养卡片应该放在哪种消息块里？

A：建议新增独立消息块类型：

```swift
case nutritionCards
```

对应 payload：

```swift
struct ChatNutritionCardsPayload: Codable, Equatable, Sendable {
    var cards: [ChatNutritionCardPayload]
}

struct ChatNutritionCardPayload: Identifiable, Codable, Equatable, Sendable {
    var id: UUID
    var date: Date
    var proteinGrams: Double?
    var carbohydratesGrams: Double?
    var fatGrams: Double?
    var energyKilocalories: Double?
    var mealName: String?
    var sourceText: String?
    var isWritten: Bool
    var writtenAt: Date?
}
```

也可以直接复用 `SparkNutritionCard` 作为内部卡片模型，但消息块 payload 建议使用 `ChatNutritionCardPayload`，原因是：

1. `SparkNutritionCard` 属于 HealthKit 工具层模型。
2. 消息卡片需要 UI 状态字段，例如 `id/isWritten/writtenAt/mealName/sourceText`。
3. 后续消息持久化字段演进不应反向污染 HealthKit 工具模型。

### Q：为什么不塞进 `structuredHealthCards`？

A：不建议。

`structuredHealthCards` 当前表达的是“从医疗文本抽取出的医疗资料草稿”，用于保存到 SparkClient 医疗资料体系，例如用药计划、药盒、处方、检查报告、病历。营养卡片的目标是写入 Apple 健康，不是保存为医疗资料记录。

如果把营养卡片塞进 `structuredHealthCards`，会导致：

1. 保存按钮语义混乱：一个是保存到医疗资料，一个是写入 Apple 健康。
2. 成员归属混乱：医疗资料需要成员，HealthKit 写入是当前设备健康库。
3. 后续扩展困难：营养卡片需要 HealthKit 授权、写入状态和系统错误处理。

因此建议独立为 `nutritionCards` block。

## 6. 消息流 UI

### Q：营养卡片长什么样？

A：参考 hanlin-ai 的卡片，但适配 SparkClient 当前消息流风格。

卡片内容：

1. 标题：`营养卡片`
2. 图标：`bubbles.and.sparkles` 或更直接的 `fork.knife.circle.fill`
3. 时间：记录时间，例如 `今天 08:32`
4. 四个营养项：
   - 碳水：`popcorn.fill`，单位 `g`
   - 脂肪：`drop.fill`，单位 `g`
   - 蛋白质：`fish.fill`，单位 `g`
   - 能量：`flame.fill`，单位 `kcal`
5. 操作按钮：
   - 未写入：`写入健康应用`
   - 写入中：`写入中...`
   - 已写入：`已写入健康`
   - 失败：保留未写入按钮，并 Toast / 提示错误

### Q：UI 布局建议？

A：

```text
┌──────────────────────────────┐
│ 图标  营养卡片          时间 │
│                              │
│ 碳水  42.0 g   蛋白质 18.0 g │
│ 脂肪  12.0 g   能量   420 kcal│
│                              │
│                [写入健康应用] │
└──────────────────────────────┘
```

设计注意：

1. 卡片宽度跟随消息气泡内容，不要撑满全屏。
2. 每个营养项固定两列布局，避免数值长度变化导致跳动。
3. 缺失字段不展示，不要显示 `0` 冒充未知值。
4. 所有数值保留 0~1 位小数，避免 AI 估算出现过度精确。
5. 已写入状态使用低强调样式，避免用户重复点击。
6. 深色/浅色模式要保持可读性。

### Q：应该放在工具输出卡片里，还是消息正文下方？

A：建议像 `structuredHealthCards` 一样作为独立 message block 渲染在助手消息下方，而不是藏在工具详情 Sheet 里。

原因：

1. 用户核心操作是“写入健康应用”，应该直接可见。
2. 工具详情 Sheet 适合展示调用参数/原始结果，不适合作为主操作入口。
3. 历史消息中卡片应可直接看到写入状态。

## 7. 写入 Apple 健康

### Q：写入健康应用怎么做？

A：复用现有：

```swift
SparkHealthTool.writeNutritionData(_:)
```

它已经支持写入：

| 字段 | HealthKit 类型 | 单位 |
| --- | --- | --- |
| `proteinGrams` | `.dietaryProtein` | g |
| `carbohydratesGrams` | `.dietaryCarbohydrates` | g |
| `fatGrams` | `.dietaryFatTotal` | g |
| `energyKilocalories` | `.dietaryEnergyConsumed` | kcal |

### Q：权限怎么处理？

A：

1. 点击“写入健康应用”时再触发 HealthKit 写权限请求。
2. 如果设备不支持 HealthKit，提示“当前设备不支持健康数据写入”。
3. 如果用户拒绝授权，提示“未获得健康写入权限”。
4. 如果写入失败，提示失败原因，卡片保持未写入。
5. 如果写入成功，更新卡片 `isWritten=true` 和 `writtenAt=Date()`。

不要在 AI 工具调用阶段直接请求写入权限，因为工具调用只生成卡片，不代表用户同意写入。

### Q：如何避免重复写入？

A：

1. `isWritten == true` 时按钮禁用。
2. 写入中状态加入 `savingNutritionCardIDs`，防止重复点击。
3. 写入成功后立即持久化消息块。
4. 如果用户重新打开历史消息，已写入卡片仍显示“已写入健康”。

第一期不要求从 HealthKit 反查去重；以消息卡片状态为准。

## 8. 插卡流程

### Q：完整流程是什么？

A：

```text
用户发送饮食描述
  -> 模型决定调用 make_nutrition_data
  -> ToolHub.runMakeNutritionData
  -> SparkHealthTool.makeNutritionData
  -> ToolExecutionResult.sideEffects = [.nutritionCards([card])]
  -> MessageRunActor 接收 sideEffect
  -> ToolSideEffectBlockMapper 映射 ChatMessageBlock(kind: .nutritionCards)
  -> Repository/CoreData 持久化 block
  -> ChatMessageBlock+Render 渲染 ChatNutritionCardsBlockView
  -> 用户点击写入健康应用
  -> ChatDetailViewModel 处理 action
  -> SparkHealthTool.writeNutritionData
  -> 成功后更新 block payload isWritten/writtenAt
  -> 消息流展示已写入状态
```

### Q：为什么要走 sideEffect，而不是解析工具输出文本？

A：必须走 sideEffect。

解析 `nutrition_card=json` 文本的问题：

1. 文本格式不稳定。
2. 工具输出是给模型看的，不是 UI 数据协议。
3. 无法保证 blockID、toolCallID、消息顺序稳定。
4. 不利于失败恢复和历史消息重建。

SparkClient 现有工具插卡逻辑已经支持工具副作用落库，营养卡片应接入这条链路。

## 9. 保存状态与消息持久化

### Q：写入成功后如何更新消息里的卡片？

A：建议沿用结构化健康卡片的状态更新模式：

1. `ChatRenderContext` 增加：

```swift
let savingNutritionCardIDs: Set<UUID>
let onNutritionCardAction: (ChatNutritionCardAction) -> Void
```

2. 新增 action：

```swift
enum ChatNutritionCardAction: Equatable, Sendable {
    case writeToHealth(blockID: UUID, cardID: UUID)
}
```

3. `ChatDetailViewModel` 处理 action：

```text
标记 savingNutritionCardIDs.insert(cardID)
调用 SparkHealthTool.writeNutritionData(card)
成功：更新当前 message block 中对应 card.isWritten=true/writtenAt
失败：Toast / 错误提示
结束：savingNutritionCardIDs.remove(cardID)
```

4. 更新后的消息块必须写回本地存储，保证重启后状态仍然正确。

### Q：是否要把写入成功后的 HealthKit sample UUID 存起来？

A：第一期可以不做。HealthKit 写入返回的是保存成功与否，当前需求只需要防止 UI 重复点击。

后续如果要支持撤销写入或查看来源，可以扩展：

```swift
var healthKitSampleIDs: [String]?
```

第一期不建议引入，避免把简单卡片做重。

## 11. 数据校验

### Q：工具参数需要做哪些校验？

A：

1. 数值必须是有限数字，不能是 `NaN` / `Infinity`。
2. 数值不能小于 0。
3. 四个营养字段不能全部为空。
4. 能量单位固定 kcal，宏量营养素单位固定 g。
5. 如果模型传入异常大值，第一期可以允许展示，但建议日志记录；后续可加合理范围提醒。

建议：

```text
protein/carbohydrates/fat: 0...1000 g
energy: 0...10000 kcal
```

超过范围时可以拒绝生成卡片，并返回工具错误提示。

### Q：AI 估算值如何向用户表达不确定性？

A：卡片不需要大段说明，但可以在标题或底部加轻量提示：

```text
由 AI 根据描述估算，请确认后写入。
```

如果 UI 空间紧张，可以只在工具详情中保留 `sourceText`，卡片本体保持简洁。

## 12. 权限与隐私

### Q：是否需要工具调用同意？

A：需要沿用现有健康类工具同意策略。

`make_nutrition_data` 属于健康类工具，但它只生成本地卡片，不直接写入 Apple 健康。建议策略：

1. 工具生成卡片：沿用健康工具调用同意。
2. 写入 Apple 健康：用户点击按钮时再触发 HealthKit 系统授权。
3. 不在后台自动写入。
4. 不把 HealthKit 写入结果发给模型，除非用户继续追问。

### Q：卡片数据是否敏感？

A：营养数据属于健康相关数据，应按健康类敏感数据处理。消息持久化在本地聊天记录中，后续如果进入云同步，需要按聊天同步已有隐私策略处理。

## 13. 验收标准

### 工具调用验收

1. 用户描述饮食后，支持模型可调用 `make_nutrition_data`。
2. `make_nutrition_data` 成功后，助手消息内出现营养卡片，而不是只显示 `nutrition_card=json` 文本。
3. 营养卡片与对应 toolCallID 关联，消息顺序稳定。
4. 工具调用失败时显示可理解错误，不插入空卡片。

### UI 验收

1. 营养卡片展示蛋白质、碳水、脂肪、能量和时间。
2. 缺失字段不展示。
3. 数值单位正确：g / kcal。
4. 未写入时显示“写入健康应用”。
5. 写入中按钮不可重复点击。
6. 写入成功后显示“已写入健康”并禁用按钮。
7. 深色/浅色模式下卡片可读。
8. 历史消息重新进入后，卡片仍能正确展示。

### HealthKit 验收

1. 点击写入时，请求 Apple 健康营养写入权限。
2. 授权成功后写入 `.dietaryProtein`、`.dietaryCarbohydrates`、`.dietaryFatTotal`、`.dietaryEnergyConsumed`。
3. 设备不支持 HealthKit 时给出提示，不崩溃。
4. 用户拒绝权限时给出提示，卡片保持未写入。
5. 写入失败时给出提示，卡片保持未写入。
6. 写入成功后，重启 App 仍显示已写入。

### 架构验收

1. 不通过解析工具输出文本插卡。
2. 插卡必须走 `ToolSideEffect` / `MessageRunActor` / `ChatMessageBlock` / render context 现有链路。
3. 写入 HealthKit 的 action 不放在 View 内直接操作存储，应由 ViewModel 处理。
4. 消息 block payload 可 Codable 编解码，历史消息可恢复。
5. 不把营养卡片塞进 `structuredHealthCards`，避免医疗资料保存语义混乱。

## 14. 风险与注意事项

### Q：这个需求最大的风险是什么？

A：最大风险是把“AI 生成卡片”和“写入健康应用”混成一个自动动作。必须明确：

```text
工具调用只生成卡片
用户点击才写入 Apple 健康
写入成功才更新 isWritten
```

### Q：还有哪些注意点？

A：

1. AI 估算营养可能不准确，UI 需要让用户确认后再写入。
2. HealthKit 权限只能由系统弹窗控制，App 不能假设用户一定授权。
3. 同一张卡片不要重复写入。
4. 写入状态要跟随消息持久化，不要只放内存。
5. 后续如果支持编辑，应在写入前编辑，已写入卡片默认不允许再改。

## 工单 `TOOL-CALL-000002`：医疗类风险提示工具卡片与工具详情大文本性能优化

### 工单状态

新需求，待实现。

## 1. 背景

### Q：为什么需要医疗类风险提示？

A：对话中会出现医疗、健康、用药、检查报告、营养、症状判断等内容。这类内容可能影响用户健康决策，需要明确提醒用户：AI 只能提供辅助理解和整理，不能替代医生诊断、处方或紧急处理建议。

但风险提示也不能在所有对话里都出现。普通聊天、日程、知识库、代码、天气等场景不需要医疗风险提示。如果所有对话都展示提示，会造成提示疲劳，用户反而更容易忽略真正重要的风险。

因此需要以工具调用的形式增加一个“医疗风险提示卡片”：

```text
只有当模型判断当前回复涉及医疗/健康风险时，才调用工具插入风险提示卡片。
```

### Q：为什么用工具卡片，而不是固定文案？

A：

1. 工具卡片可以由模型按场景主动调用，不污染所有对话。
2. 卡片可以结构化展示风险级别、提示内容和建议行动。
3. 卡片会进入消息块系统，历史消息可恢复。
4. 可以与问报告、营养卡片、结构化健康卡片等健康工具共存。
5. 后续可以针对高风险场景升级卡片样式，例如“请及时就医”“出现急症请拨打急救电话”。

## 2. 需求一：医疗类风险提示工具卡片

### Q：什么场景需要出现风险提示？

A：建议由模型在以下场景调用风险提示工具：

1. 解读检查、检验、体检、病历、处方、用药计划。
2. 讨论疾病诊断、症状判断、治疗选择、用药调整。
3. 生成营养卡片或饮食建议，且涉及慢病、孕期、儿童、老人、肾病、糖尿病等敏感情况。
4. 用户询问是否需要停药、换药、加量、减量。
5. 用户描述急性或危险症状，例如胸痛、呼吸困难、意识障碍、严重过敏、大出血等。
6. AI 给出具有行动导向的健康建议时。

不建议出现的场景：

1. 普通知识问答，不涉及个人健康行动。
2. 查询天气、日程、位置、代码、知识库。
3. 仅展示用户已选择的报告引用卡片，但 AI 尚未做医学解读。
4. 纯 UI 工具或系统工具调用。

### Q：工具名称怎么设计？

A：建议新增工具：

```swift
SparkToolName.showMedicalRiskNotice = "show_medical_risk_notice"
```

工具参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `risk_level` | string | 是 | `low` / `medium` / `high` / `emergency` |
| `title` | string | 否 | 卡片标题；不传时按风险等级使用默认标题 |
| `message` | string | 是 | 风险提示正文 |
| `recommended_action` | string | 否 | 建议行动，例如“咨询医生”“尽快就医”“急症请呼叫急救” |
| `related_reason` | string | 否 | 触发原因摘要，例如“涉及用药调整” |

### Q：卡片 UI 应该如何展示？

A：建议新增独立消息块：

```swift
case medicalRiskNotice
```

卡片内容：

```text
┌──────────────────────────────┐
│ ⚠ 医疗风险提示        中风险 │
│ AI 解读仅供参考，不能替代医生 │
│ 建议：如症状持续或加重，请就医 │
└──────────────────────────────┘
```

风险级别样式：

| 风险级别 | 展示 |
| --- | --- |
| `low` | 蓝/灰色，普通提示 |
| `medium` | 橙色，强调需要结合医生意见 |
| `high` | 红色，强调尽快就医或联系医生 |
| `emergency` | 红色强提示，文案强调急症处理 |

### Q：默认文案怎么处理？

A：工具可以带 `message`，但客户端必须有兜底文案，避免模型传空或异常内容。

建议默认文案：

```text
AI 提供的信息仅用于辅助理解和整理，不能替代专业医生的诊断、治疗或用药建议。
```

高风险/急症兜底文案：

```text
如果出现胸痛、呼吸困难、意识障碍、严重过敏、大出血等紧急情况，请立即寻求急救帮助。
```

### Q：工具调用结果怎么插入卡片？

A：必须走现有工具插卡链路：

```text
ToolHub.runShowMedicalRiskNotice
  -> ToolExecutionResult.sideEffects = [.medicalRiskNotice(payload)]
  -> MessageRunActor
  -> ToolSideEffectBlockMapper
  -> ChatMessageBlock(kind: .medicalRiskNotice)
  -> ChatMessageBlock+Render
  -> ChatMedicalRiskNoticeCardView
```

不建议把风险提示拼到普通文本里。风险提示属于结构化安全提示，应有独立消息块，便于样式、去重和历史恢复。

### Q：如何避免同一条回复重复插入多个风险提示？

A：建议按助手消息维度去重：

1. 同一条助手消息最多展示一张风险提示卡片。
2. 如果同一轮多次调用，以最高 `risk_level` 为准。
3. 如果后来的工具调用风险更高，可以更新已有卡片，而不是追加第二张。
4. 如果已经有 `emergency`，不再降级。

## 3. 需求二：ToolPreviewSheet 大文本性能优化

### Q：现在 ToolPreviewSheet 有什么问题？

A：`ToolPreviewSheet` 中工具输出使用：

```swift
ToolSheetSection {
    Text(L10n.text("chat.bubble.tool.output", fallback: "输出"))
        .font(.subheadline.weight(.semibold))
    ToolLargeTextPreview(display: toolContentDisplay)
}
```

当前 `ToolLargeTextPreview` 会直接用 `Text(display.displayText)` 展示工具输出。即使有字符截断，长文本仍然会导致 Sheet 打开时布局、测量、文本选择和渲染成本过高，表现为打开页面卡顿。

问题本质：

1. 大文本一次性参与父级 Sheet 布局。
2. `Text` 的高度随内容无限增长。
3. 外层已经是 Sheet 滚动区域，内层没有按最大高度切换滚动。
4. 文本选择和 monospaced 渲染会放大长文本布局成本。

### Q：优化目标是什么？

A：

1. 内容较短时，`ToolLargeTextPreview` 仍按内容自然高度展示，不出现多余滚动框。
2. 内容超过最大高度时，预览区域固定最大高度，并切换为内部滚动模式。
3. 达到最大高度后，滚动内容应采用懒加载或分块渲染，避免一次性渲染超长文本。
4. 保留截断提示和“复制全部”能力。
5. 兼容工具参数和工具输出两个位置。

### Q：最大高度怎么定？

A：建议按设备和内容设置一个上限：

```swift
let maxPreviewHeight: CGFloat = 320
```

或使用响应式规则：

```text
maxPreviewHeight = min(360, screenHeight * 0.35)
```

效果：

1. 短内容：自然高度，例如 80。
2. 中等内容：自然高度，例如 220。
3. 长内容：最大高度 320，内部滚动。

### Q：如何判断是否进入滚动模式？

A：不要只按字符数判断，最好按测量后的内容高度判断：

```text
测量 ToolLargeTextPreview 的自然内容高度
如果 naturalHeight <= maxPreviewHeight:
  直接展示 Text
如果 naturalHeight > maxPreviewHeight:
  frame(height: maxPreviewHeight)
  内部 ScrollView
```

如果第一期不想引入复杂测量，可以用近似规则：

```text
display.displayText.count > 1200 或 display.displayText 行数 > 24
  -> 滚动模式
否则
  -> 自然高度
```

长期建议使用高度测量，因为中英文、换行、JSON 缩进都会影响实际高度。

### Q：懒加载怎么做？

A：长文本滚动模式下，不建议一个 `Text` 渲染全部内容。建议把文本按行或固定字符块切分：

```swift
struct ToolLazyLargeTextPreview: View {
    let lines: [String]

    var body: some View {
        ScrollView {
            LazyVStack(alignment: .leading, spacing: 2) {
                ForEach(lines.indices, id: \.self) { index in
                    Text(lines[index])
                        .font(.caption.monospaced())
                        .textSelection(.enabled)
                }
            }
        }
    }
}
```

分块策略：

1. 优先按换行切分，适合 JSON、日志、工具输出。
2. 单行超长时按 500~1000 字符再切块，避免单个 `Text` 过大。
3. `display.isTruncated` 时只渲染 `display.displayText`，复制全部仍使用 `display.fullText`。

### Q：短内容为什么不能也套滚动？

A：短内容如果也强行固定高度，会让工具详情页显得很空，用户还要在小滚动框里读内容，体验变差。需求是：

```text
未达到最大高度：根据内容自然高度展示
达到最大高度：固定最大高度并改为滚动模式
```

## 6. 风险与注意事项

### Q：风险提示工具最大的注意点是什么？

A：不要变成所有医疗工具的固定噪音。它应该由模型在需要时调用，也可以由关键医疗工具在高风险结果时补充调用，但不应对所有健康类工具无条件插入。

建议原则：

1. 低风险科普可不插卡，或仅低强调提示。
2. 涉及用药、诊断、治疗、检查异常时插卡。
3. 涉及急症时必须高强调提示。
4. 不要用风险提示替代真正回答。

### Q：大文本预览优化最大的注意点是什么？

A：要避免“双层滚动打架”。外层 `AdaptiveToolSheetScrollView` 仍负责整个 Sheet 滚动；只有当某个 `ToolLargeTextPreview` 达到最大高度时，才启用内部滚动。短内容必须保持普通布局。
