## 1. 一句话目标

在每个新建 Chat 会话的第一条消息位置插入一张系统角色的“对话引导卡片”，卡片动态展示当前用户健康数据滑块，并固定展示三个健康科普问题；用户点击问题后，直接按当前会话的正常发送链路向 AI 发送科普请求。

## 2. 背景与问题

当前 Chat 消息渲染已经支持多种结构化消息块，包括健康数据卡片、工具交互卡片、结构化医疗卡片、天气卡片、任务卡片等。相关分发入口位于：

```text
SparkClient/Projects/Features/Chat/Presentation/ChatView/Components/ChatMessageBlock+Render.swift
SparkClient/Projects/Features/Chat/Domain/ChatMessage/ChatMessage.swift
```

但新建会话目前只创建 `ChatThread`，没有自动生成一条首屏引导消息。`CreateThreadUseCase.execute` 调用 `repository.createThread(...)` 后直接返回 thread，尚未追加首条系统消息。

本工单要求把引导卡片纳入正常 Chat 消息体系，而不是作为 ChatView 顶部临时 UI。这样可以保证：

1. 新会话打开后第一屏即可看到健康数据和科普问题。
2. 引导卡片随消息列表本地持久化。
3. 引导卡片可通过现有 outbox / sync 机制同步到服务端。
4. 后续多端或恢复会话时，卡片仍然是第一条系统消息。

## 3. 当前代码事实

### 3.1 消息模型现状

`ChatMessageRole` 已包含：

```swift
case system
case user
case assistant
```

`ChatMessageBlockKind` 当前包含文本、工具、健康卡片、结构化健康卡片、睡眠/步数/能量/营养/运动可视化、任务卡片、风险提示等类型，但没有“对话引导卡片”专用 block kind。

`ChatMessageBlockPayload` 与 `ChatMessageBlockKind` 一一映射，新增卡片必须同步补齐：

```text
ChatMessageBlockKind
ChatMessageBlockPayload
ChatMessageBlock.kind
ChatMessageBlock.makePayload(...)
ChatMessageBlock 便捷 getter
ChatMessageBlock+Render.swift switch payload
```

### 3.2 渲染链路现状

消息块渲染由 `ChatMessageBlock.render(context:)` 分发。新增引导卡片应追加一个独立 case，例如：

```swift
case .chatGuideCard(let payload):
    ChatGuideMessageCardView(
        payload: payload,
        onQuestionTap: context.onGuideQuestionTap
    )
```

对应需要在 `ChatRenderContext`、`ChatMessageBubbleContentView`、会话列表行注入该点击回调。

### 3.3 新会话创建现状

`CreateThreadUseCase.execute(memberID:title:)` 当前流程：

```text
读取 AIConfigCenter 当前快照
  ↓
repository.createThread(memberID:title:imageDeliveryModeRaw:rolePrompt:)
  ↓
返回 ChatThread
```

该流程只创建 thread，不创建 message。因此要满足“第一条系统消息”，需要在 thread 创建成功后立即构造系统消息并 `appendMessage`。

### 3.4 本地持久化与同步现状

本地消息写入：

```text
CoreDataChatRepository.appendMessage(_:)
  ↓
CoreDataChatStore.appendMessage(_:)
  ↓
ChatMessageEntity + ChatMessageBlockEntity
  ↓
post .messagesAppended 通知
```

消息出站同步：

```text
deliveryState == pending
  ↓
ChatOutboxStore.pending(...)
  ↓
ChatOutboxPipeline.pushOutbox()
  ↓
ChatRemoteMessageDTO(blocks: message.blocks, ...)
  ↓
SparkChatRemoteAPI.push(messages:)
  ↓
服务端 ACK 后 applyPushAck / markSent
```

block 更新出站同步：

```text
ChatMessageBlockEntity.isPendingSync == true
  ↓
ChatOutboxPipeline.pushBlockUpdates(...)
  ↓
ChatRemoteMessageBlockUpdateDTO
```

首条引导卡片是完整消息，首选走 `appendMessage` + `deliveryState == .pending` 的整消息同步，而不是只走 block update。

## 4. 需求范围

### 4.1 业务逻辑与代码逻辑梳理

需求说明：

完整梳理对话引导卡片从新会话创建、数据采集、卡片构造、本地落库、UI 渲染、点击问题发送、服务端同步到多端恢复的业务闭环。

基础要求与业务规则：

1. 引导卡片属于 Chat 领域消息，不属于临时 overlay。
2. 引导卡片角色为 `system`，消息种类语义为系统引导。
3. 引导卡片必须是新会话第一条消息。
4. 引导卡片不能进入 AI 上下文，除非后续明确要求；它是 UI 引导，不是系统提示词。
5. 文档和实现必须区分“当前实现事实”和“推荐新增实现”。

主流程：

```text
用户创建新对话
  ↓
CreateThreadUseCase 创建 ChatThread
  ↓
ChatGuideCardPayloadBuilder 读取当前用户可展示数据
  ↓
ChatGuideSystemMessageFactory 构造 system 消息
  ↓
ChatRepository.appendMessage 写入本地 CoreData
  ↓
ChatStateStore / DB 通知刷新消息列表
  ↓
ChatOutboxPipeline 后台上送 pending 消息
  ↓
服务端 ACK 后本地 deliveryState 更新
```

失败、重试和恢复：

1. Thread 创建失败：不创建引导卡片。
2. 健康数据读取失败：仍创建引导卡片，但对应滑块显示“暂无数据”或“未授权”。
3. 引导消息本地写入失败：记录日志，允许用户进入空会话；下一阶段可在 `loadMessagesIfNeeded` 中补偿检测。
4. 服务端同步失败：沿用 outbox 后台重试，不阻塞用户发消息。
5. 账号切换：引导卡片按 owner account 隔离，不能跨账号复用。

验收标准：

1. 新建会话后消息列表第一条为系统引导卡片。
2. 退出重进 App 后，引导卡片仍存在。
3. 网络断开创建会话后，恢复网络可同步到服务端。
4. 已有历史会话不被批量插入引导卡片，除非后续有迁移开关。

### 4.3 用户数据滑块模块

需求说明：

为引导卡片提供动态数据 section。第一阶段展示“可读到的数据”，不强制一次性补齐全部健康指标。

基础要求与业务规则：

| 类别 | 指标 | 推荐数据来源 | 缺失策略 |
| --- | --- | --- | --- |
| 运动数据 | 步数、热量消耗 | `SparkHealthTool.fetchStepVisualization`、`SparkHealthTool.fetchEnergyVisualization` 或更轻量 summary 方法 | 未授权/无数据时显示空态与绑定/授权入口 |
| 身材管理 | 体重、BMI、体脂率 | HealthKit body mass / body mass index / body fat percentage，当前需新增轻量读取能力 | 无数据时显示“暂无记录” |
| 饮食营养 | 已食用、剩余、已消耗 | `SparkHealthTool.fetchNutritionReadVisualization` + 营养目标配置；目标未确认时只展示已食用/已消耗 | 目标缺失时隐藏“剩余”或标记未设置 |
| 医疗数据 | 病历、体检、检查报告、服药计划 | `HealthResourceRepository.fetchMemberCompleteData(memberID:)`、`SparkMedicalQueryAPI` | 无成员或无资料时显示空态 |

```swift
struct ChatGuideCardPayloadBuilder {
```

验收标准：

1. 有 HealthKit 权限和数据时，运动数据展示真实步数与热量。
2. 无 HealthKit 权限时，不触发崩溃，不展示伪造数值。
3. 有成员 complete-data 时，医疗数据能统计病历、体检、检查报告、服药计划数量。
4. 账号切换或成员切换后，新建会话生成的引导卡片使用当前账号/成员的数据。

需求说明：

### 4.5 新对话首条系统消息插入流程

需求说明：

创建新对话时，将引导卡片作为第一条系统消息插入，遵循普通对话消息插入和同步逻辑。

基础要求与业务规则：

1. 插入时机：`CreateThreadUseCase.execute` 创建 thread 成功后。
2. 消息角色：`ChatMessageRole.system`。
3. 消息 deliveryState：首选 `.pending`，以便进入 outbox 同步；服务端 ACK 后更新为 `.sent` 或项目现有语义状态。
4. block status：`.ready`。
5. order：消息 `createdAt` 应早于用户第一条消息；block `orderKey` 可为 `0`。
6. 幂等：同一 thread 不允许出现多条引导卡片系统消息。

推荐插入流程：

```text
CreateThreadUseCase.execute
  ↓
repository.createThread(...)
  ↓
ChatGuideCardPayloadBuilder.build(memberID:)
  ↓
ChatGuideSystemMessageFactory.make(threadID:memberID:payload:)
  ↓
repository.appendMessage(systemGuideMessage)
  ↓
返回 thread
```

推荐 factory 示例：

```swift
enum ChatGuideSystemMessageFactory {
    static func make(
        threadID: UUID,
        payload: ChatGuideCardPayload,
        createdAt: Date = Date()
    ) -> ChatMessage {
        let messageID = UUID()
        let block = ChatMessageBlock.fromPayload(
            .chatGuideCard(payload),
            id: ChatStableBlockID.rich(messageID: messageID, kind: .chatGuideCard),
            orderKey: 0,
            createdAt: createdAt,
            updatedAt: createdAt
        )
        return ChatMessage(
            threadID: threadID,
            role: .system,
            blocks: [block],
            clientMessageID: messageID,
            deliveryState: .pending,
            createdAt: createdAt
        )
    }
}
```

验收标准：

1. 新建会话后，即使用户还没发第一条消息，也能看到引导卡片。
2. 用户第一条消息始终排在引导卡片之后。
3. 服务端拉回相同会话时不会重复插入。
4. 本地已有引导消息时，不再补插第二条。

### 6.1 创建新会话并插入引导卡片

```text
  ↓

  ↓

  ↓
ChatStateStore 收到 DB 变更并刷新 UI
  ↓

  ↓

```

### 6.2 点击科普问题发送

## 7. 状态模型

| 状态 | 场景 | UI 表现 | 数据处理 |
| --- | --- | --- | --- |
| `ready` | payload 构建成功 | 展示可用数据和问题 | message pending/sent 均可渲染 |
| `partial` | 部分数据可用 | 有数据 section 正常展示，缺失 section 显示空态 | payload 保留 section state |
| `unauthorized` | HealthKit 未授权 | 显示授权/绑定入口 | 不写假数值 |
| `empty` | 无健康/医疗数据 | 显示暂无数据 | 可以保留问题列表 |
| `failed` | 数据读取失败 | 展示轻量失败态，问题仍可点击 | 记录错误，不阻塞会话创建 |
| `sendingQuestion` | 用户点击问题后发送中 | 问题按钮置灰 | 防止重复提交 |

## 8. 数据与持久化

### 8.1 本地数据归属

引导卡片 payload 存入 `ChatMessageBlockEntity.payloadData`，随 `ChatMessageEntity` 归属当前 `ownerAccountID` 和 `threadID`。

### 8.2 服务端同步数据

引导卡片作为 `ChatRemoteMessageDTO.blocks` 的一部分同步。服务端需要能接受新增 `ChatMessageBlockKind.chatGuideCard` 和 payload JSON。若服务端当前是 schema-less JSON 存储，主要风险在客户端旧版本解码；若服务端做枚举白名单，需要同步更新服务端。

### 8.3 AI 上下文边界

引导卡片不应默认进入 AI 历史上下文。若 `SendChatMessageUseCase` 或运行时历史构造会把所有 system 消息都发送给模型，需要过滤 `chatGuideCard` 或标记 `metadata.isPresentationOnly = true`。这是本工单的高风险点，必须实现前确认。

## 9. 错误模型

| 错误 | 处理策略 |
| --- | --- |
| HealthKit 不可用 | section state = `unavailable`，展示空态 |
| HealthKit 未授权 | section state = `unauthorized`，展示去绑定/授权操作 |
| 医疗 complete-data 拉取失败 | 医疗 section state = `failed`，不阻塞卡片生成 |
| 本地 appendMessage 失败 | 记录日志，返回已创建 thread；后续可补偿插入 |
| outbox 同步失败 | 沿用现有失败重试 |
| payload 解码失败 | 旧版本应降级隐藏该 block 或显示 fallback 文本 |
| 快速重复点击问题 | ViewModel 以 threadID + questionID 做短时防重 |

## 10. 与其他模块的接口边界

本模块负责：

1. 定义对话引导卡片数据结构。
2. 构造新会话首条系统消息。
3. 渲染健康数据滑块和固定问题。
4. 把问题点击转换为当前会话用户消息发送。

本模块不负责：

1. 新增医疗资料业务模型。
2. 改造完整 HealthKit 授权中心。
3. 改服务端同步接口协议，除非服务端枚举白名单要求。
4. 把引导卡片内容注入 AI 系统提示词。

8. 补测试与本地化文案。

## 13. 当前实现缺口与风险

1. 当前 `CreateThreadUseCase` 只创建 thread，不创建首条 message。
2. 当前 `ChatMessageBlockKind` 没有专用引导卡片类型。
3. 现有 HealthKit 已有步数、能量、营养读取能力，但身材管理指标需要补轻量读取。
4. 饮食“剩余”依赖营养目标来源，当前在已读代码中未确认目标配置模型。
5. system 消息是否进入 AI Runtime 历史需要实现前重点确认，避免把 UI 引导卡片当系统提示词发给模型。
6. 服务端是否允许未知 block kind 未在客户端代码中确认，需要联调验证。

## 14. 整体验收标准

1. 新建会话首条消息是系统引导卡片，且只出现一次。
2. 引导卡片展示四类数据 section；可用数据真实展示，不可用数据有明确空态。
3. 第一阶段固定三条健康科普问题。
4. 点击任一问题可直接向当前 AI 会话发送对应科普 prompt。
5. 引导卡片本地持久化，重启后仍显示。
6. 引导卡片可通过现有 sync push/pull 机制同步和恢复。
7. 引导卡片不污染 AI 系统提示词或历史上下文。
8. 所有新增用户可见文案进入本地化资源。
9. 单元测试覆盖 payload 编解码、新会话插入幂等、问题点击发送和同步映射。
