## 一、模块目标

在病历详情页右下角增加“对话”入口。用户点击后，系统新建一个明确绑定当前病历所属成员的对话 Thread，把当前病历转换为 `HealthResourceRef` 并写入该 Thread 的 `ChatComposerDraft.pendingHealthResourceRefs`，然后通过 `fullScreenCover` 展示 `ChatView`。

用户进入对话后：

1. 当前病历已出现在输入框上方的健康资源预览区。
2. 用户可点击预览卡查看病历详情，也可移除它。
3. 不自动填入提问文字，不自动发送，不自动开始 AI 生成。
4. 用户输入问题并发送后，复用现有“问报告”发送、上下文解析、消息引用卡和预览链路。

本工单的核心不是为病历单独制作一套 Chat 跳转，而是建立“从任意健康资源详情页带入当前资源并开启对话”的公共能力。首期只在病历详情启用，但请求模型、成员绑定、模型/API Key 门控、Thread 创建、草稿注入、全屏路由、关闭和错误恢复必须公共化。

### 1.1 用户价值

- 用户不需再次上传病历或在详情页与对话列表之间往返。
- 对话天然带入正确成员与资源 ID，降低家庭多成员场景下问错人、用错资料的风险。
- 复用已存在的结构化健康资源上下文，避免复制整份医疗数据到 Chat 草稿。

### 1.2 首期范围

| 体检、检查、处方、用药、药箱详情入口 | 不在首期显示；底层公共能力必须可直接复用 |

## 四、公共健康资源对话请求与编排

### 需求说明

建立一个与病历 DTO 解耦的公共请求，代表“从某个详情页为某个成员携带某个健康资源开启新对话”。公共编排器处理模型检查、Thread 创建、成员绑定、引用注入与错误补偿。

### 基础要求与业务规则

1. 请求的最小字段为 `HealthResourceIdentity`、用于预览的非敏感显示快照、入口来源和幂等 token。
2. identity 必须继续使用 `resourceType + resourceID + memberID`，不新增病历专用身份结构。
3. 显示快照只用于 Composer 缩略图与无法取回详情时的兜底；完整病历内容仍由 `ChatHealthResourcePreviewLoader`/上下文 resolver 按 identity 读取。
4. 编排器是账号级、`@MainActor` 的单一事实源，同一时间只处理一个展示请求。
5. 详情页不得依赖 `ChatListViewModel`、`ChatDetailViewModel`、`ChatStateStore` 或 `APIKeysSettingsView`。
6. 编排结果必须是可枚举状态：准备中、需要 AI 设置、已就绪(threadID)、失败，不以多个布尔值拼装。
7. 在编排完成前不展示 `ChatView`，以避免预览卡后置闪现。
8. 页面重算、Cover 重建、设置 Sheet 关闭都不得重复注入资源；幂等 token 在流程完成或取消后清理。
9. 成功后才记录“打开对话”成功埋点；错误日志仅记录 resource type/id、memberID、thread 短 ID 和阶段，不打印诊断、病情摘要或 API Key。

### 验收标准

- [ ] 使用同一公共请求可表达 `medical_case`、`health_exam_report`、`examination_report`、`prescription`、`medication_plan`、`medicine_box` 等已有 `HealthResourceType`。
- [ ] 页面 body 重算不会重复创建 Thread 或重复加入预览。
- [ ] 编排失败不会留下用户无法理解的空 Thread。
- [ ] 医疗详情 Feature 不直接初始化 `ChatView`。

### 技术细节与设计代码位置

- 基础 identity：`SparkClient/Projects/Core/HealthResource/HealthResourceIdentity.swift`。
- 现有资源类型：`SparkClient/Projects/Core/HealthResource/HealthResourceType.swift`。
- 现有 Chat 引用：`SparkClient/Projects/Features/Chat/Domain/HealthResourceRef.swift`。
- 建议新增纯值请求与编排器：见 2.3；这些名称是建议，不得写成“当前已实现”。

## 六、Thread 创建、成员绑定与幂等保证

### 需求说明

为每次详情快捷对话创建一个新 Thread，并在 Thread 创建时就明确绑定当前病历的 `memberID`。

### 基础要求与业务规则

1. 不能直接复用现有无参 `ChatListViewModel.createThread()` 作为最终落地。该方法的初始成员来自 AI 启动偏好和 `memberContextStore.context.selectedMemberID`，可能与当前病历的 `currentItem.member` 不一致。
2. 必须增加可复用的“显式 memberID 建 Thread”入口，直接把病历 memberID 传给 `CreateChatThreadUseCase`；不建议先按默认成员建 Thread，再调用 `updateThreadMemberBinding`补绑。
3. 原因：后置改绑可能触发引导问题重生成、草稿资源 prune，并在短暂窗口内造成 member mismatch。
4. 成功建 Thread 后按固定顺序准备：重载/插入列表读模型 → `markThreadAsNewlyCreated` → `setSelectedThreadID` → 向该 threadID 追加当前资源引用 → 核对草稿与 Thread 成员 → 返回 ready。
5. 引用校验必须通过 `HealthResourceSendValidator`：`resourceID > 0`、类型已知、`ref.memberID == thread.memberID`。
6. 当已有全屏 cover、API Key Sheet 或另一次准备任务时，新请求不并发创建；保留第一次用户操作并拒绝连点。
7. 若 Thread 已创建但引用注入/成员核对失败，优先删除或回滚该未展示、无消息的本地 Thread；无法回滚时记录可恢复错误并确保不展示错误会话。
8. 默认标题继续使用 `chat.default_thread_title`，不把病历标题/诊断直接暴露到对话列表标题；后续发送后由现有会话命名链路处理。

### 验收标准

- [ ] 首页当前选中成员 A，病历属于成员 B 时，新 Thread 绑定 B。
- [ ] 新 Thread 的预览引用 memberID 与 Thread memberID 始终一致。
- [ ] 注入失败不会进入 ChatView，也不会在列表留下可见空会话。
- [ ] 全链路可重入检查通过，不会因连点建立多个 Thread。

### 技术细节与设计代码位置

- 当前创建逻辑：`SparkClient/Projects/Features/Chat/Presentation/ChatListViewModel.swift` 的 `createThread()`。
- Thread 用例与 Repository 契约：`Projects/Features/Chat/Domain/ChatStoreProtocols.swift`、`Projects/Features/Chat/Infrastructure/CoreDataChatRepository.swift`。
- 成员更新及 prune 行为：`ChatDetailViewModel.updateThreadMemberBinding`、`ChatStateStore.pruneHealthResourceRefs`。
- 发送校验：`SparkClient/Projects/Features/Chat/Application/HealthResourceSendValidator.swift`。

## 七、当前病历映射与 Composer 预览自动带入

### 需求说明

将当前 `RemoteMedicalCaseSummary` 映射为一条 `HealthResourceRef(type: .medicalCase, ...)`，在展示 ChatView 前写入新 Thread 的 `pendingHealthResourceRefs`。

### 基础要求与业务规则

1. `resourceType = medical_case`、`resourceID = currentItem.id`、`memberID = currentItem.member`。
2. `displayTitle` 优先使用当前病历非空 `title`，否则使用 `chat.ask_report.resource_type.medical_case`。
3. `displaySubtitle` 优先使用非空 `diagnosisSummary`，其次为医院名称，再其次为格式化的更新/创建日期，最后允许空字符串。
4. `typeBadge` 使用 `HealthResourceType.medicalCase.localizationKey` 的本地化值。
5. 不在 `HealthResourceRef` 中复制完整病历、时间轴子项、附件二进制数据或 OCR 文本。
6. 映射规则必须与 `ChatAskReportTimelineMapper` 的病历规则同源，不在详情页内再写一份 fallback 逻辑。当前 `makeMedicalCase` 是私有方法，实施时应抽取公共 factory 或提供可测试的 overload。
7. 注入使用 `ChatStateStore.appendHealthResourceRefs`，复用现有上限 5 份、canonical id 去重和按 Thread 草稿隔离。
8. 必须在设置 `activeHomeFullScreenCover = .chat(threadID)` 之前完成注入，ChatView 首帧即可见预览。

10. 发送前若资源已被删除或无权访问，由现有预览/上下文解析链路给出明确错误；不能静默换成另一条病历。

## 八、全屏 Chat 展示、加载与右上角关闭

### 需求说明

在 `SignedInMainTabHostView.homeFullScreenCoverContent` 增加 Chat 分支，使用 `CompatibleNavigationContainer` 包裹 `ChatView`，并为全屏场景提供右上角关闭按钮。

### 基础要求与业务规则

1. `HomeFullScreenCover` 增加携带 `threadID` 的 Chat case，`id` 必须包含 threadID，保证 SwiftUI 识别不同会话。
2. `HomeFullScreenCoverKind` 与 `HomeFullScreenCoverKind.init(cover:)` 的 exhaustive switch 需同步增加 chat kind，使 `HomeLaunchIntentConsumer.syncHostState` 能正确识别全屏占用。首期不需把它暴露为外部 `LaunchIntent`。
3. `ChatView` 的依赖按 `MainTabRouteDestinationBuilder` 中的正常 Chat 路由保持一致，包括 stateStore、list/detail ViewModel、knowledge、task、home、AI settings 和 auto small task coordinator。
4. 全屏分支必须复用正常 `.chatThread` 路由的准备任务：`selectAndPrepare(threadID:)` 以及 `loadMessagesIfNeeded(for:lockBottomViewport:)`。仅初始化 `ChatView` 不足以保证选中状态与消息已就绪。
5. `ChatView` 增加可选的全屏展示上下文/关闭回调。普通 push 场景不传时，保持现有返回按钮和导航行为，不显示额外关闭。
6. 全屏场景在右上角已有“新建对话”和设置 Menu；关闭按钮放在同一 `ToolbarItemGroup(.topBarTrailing)` 内且顺序稳定，不覆盖现有两个操作。
7. 关闭只 dismiss 全屏 Cover，不删除 Thread，不清空草稿，不清除已带入资源。关闭后 Thread 在对话列表中可继续打开。
8. 若正在 AI 生成，点击关闭弹出确认，提供“继续对话”和“停止并关闭”；后者先调用现有取消生成能力，再 dismiss。
9. 若只有未发送草稿/病历引用，允许直接关闭并保留当前 App 运行期草稿。草稿跨冷启动持久化不在本工单范围。
10. 关闭后 `activeHomeFullScreenCover = nil`，清理仅用于展示的幂等 token 和 pending request，不清理 Thread 业务状态。

### 验收标准

- [ ] 对话以真正的 `fullScreenCover` 打开，没有切换底部 Tab，也没有在病历 NavigationStack 内 push。
- [ ] 对话首帧已选中正确 Thread，消息与 Composer 均属于该 threadID。

- [ ] 关闭后回到原病历详情页，对话及未发草稿在当前运行期内仍可继续。
- [ ] 生成中关闭不造成悬挂 `isSending` 状态或未收尾 assistant message。

## 十、整体业务流程

```text
用户打开病历详情
  ↓
点击右下角对话按钮
  ↓
MedicalCaseDetailPage 以 currentItem 构造公共请求
  ↓
SignedInMainTabHostView / 公共编排器防重入、校验 identity 与账号上下文
  ↓
ChatDetailViewModel.hasAvailableChatModel()
  ├── 无模型 → alert → APIKeysSettingsView → 重新校验 → 继续/结束
  └── 有模型
        ↓
使用 currentItem.member 显式创建新 Thread
  ↓
更新 Thread 列表读模型并选中新 Thread
  ↓
公共 factory 生成 medical_case HealthResourceRef
  ↓
ChatStateStore.appendHealthResourceRefs(ref, for: threadID)
  ↓
核对 thread.memberID == ref.memberID 且草稿含该 canonical id
  ↓
activeHomeFullScreenCover = .chat(threadID)
  ↓
CompatibleNavigationContainer → ChatView
  ↓
selectAndPrepare + loadMessagesIfNeeded
  ↓
HanlinChatInputView 首帧展示病历预览
  ↓
用户输入问题/直接发送资源引用
  ↓
HealthResourceSendValidator → 现有 AI 上下文与消息引用链路
```

### 10.1 成功路径

- 入口点击后先准备对话，准备成功才打开 Cover。
- 新 Thread 与当前病历成员一致，预览已带入，用户保留发送决定权。

### 10.2 失败、重试与恢复

- 模型不可用：先引导设置，设置后重新校验，不预建 Thread。
- Thread 创建失败：停留病历详情，显示可重试错误。
- 资源注入失败：不打开 Chat，对未展示空 Thread 执行补偿。
- 资源预览加载失败：保留引用快照并显示可重试/资源不可用状态，不替换 identity。

### 10.3 取消、并发和幂等

- alert 取消：清理 pending request，不建 Thread。
- 设置 Sheet 关闭且模型无效：结束本次请求。
- 入口连点：依据 request token 防重，只处理首个。
- Cover 已显示：不再建 Thread。
- 准备任务取消：清理 loading 和 token，若已创建空 Thread 则补偿。

## 十一、状态模型

| 状态 | 进入条件 | 用户可见结果 | 退出条件 |
| --- | --- | --- | --- |
| `idle` | 无待处理请求 | 病历详情可操作 | 点击对话 |
| `validating` | 已收到有效请求 | 入口 loading/禁用 | 模型检查完成 |
| `requiresAISettings` | 无可用 `.chat` 模型 | 无模型 alert | 取消或前往设置 |
| `presentingAISettings` | 用户选择前往设置 | API Key Sheet | 完成/关闭 |
| `creatingThread` | 模型可用 | 入口继续 loading | Thread 成功/失败 |
| `injectingResource` | 已有 threadID | 尚未展示 Chat | 成员与引用核对通过/失败 |
| `ready` | Thread 与草稿已准备 | 全屏 Chat 即将展示 | Cover 已置位 |
| `presentingChat` | Cover 展示 | ChatView + 病历预览 | 关闭 Cover |
| `failed` | 创建/注入/加载失败 | 病历详情上的可理解错误 | 确定/重试 |
| `cancelled` | 用户取消或账号切换 | 回到详情 | 清理后回到 idle |

状态不得同时出现 `showNoModelAlert = true`、`showAPIKeysSettings = true` 和 `activeHomeFullScreenCover != nil`。

## 十二、数据与持久化

| 数据 | 所有者 | 存储位置 | 生命周期 | 清理时机 |
| --- | --- | --- | --- | --- |
| 病历业务数据 | 医疗模块/服务端 | `RemoteMedicalCaseSummary` 及 complete-data/查询 API | 账号与成员数据周期 | 删除、账号清理、缓存刷新 |
| 公共对话请求 | App/Coordinator | 宿主瞬时状态 | 一次启动流程 | 成功、取消、失败、登出 |
| Thread | Chat Repository | 现有 Core Data/同步仓库 | 账号会话周期 | 用户删除/账号清理 |
| `HealthResourceRef` 显示快照 | Chat Composer/Message | 首先写入 `ChatStateStore.composerDrafts[threadID]` | 未发草稿期；发送后进入现有 message block | 用户移除/清空草稿/会话清理 |
| `pendingHealthResourceRefs` | `ChatStateStore` | 当前为内存草稿字典 | App 运行期/按 Thread | 清草稿、切成员 prune、账号切换 |
| API Key | AI Settings 模块 | 现有安全配置存储 | 账号/设备策略 | 由 AI Settings 负责，本模块不读写明文 |
| Cover/alert/Sheet 状态 | `SignedInMainTabHostView` | SwiftUI `@State` | 一次展示 | dismiss 或账号切换 |

关键限制：当前 Composer 草稿不是跨冷启动持久化数据。本工单要求关闭全屏后在当前 App 运行期保留，不承诺杀进程后恢复未发病历引用。

## 十三、错误模型

| 错误类别 | 触发条件 | 是否重试 | 用户反馈 | 清理/补偿 |
| --- | --- | --- | --- | --- |
| 请求无效 | resourceID/memberID ≤ 0 或 type 未知 | 否，刷新页后可再试 | “当前病历暂时无法咨询” | 清 pending request |
| 无可用 Chat 模型 | `.chat` bundle 为空/解析失败 | 配置后重试 | 复用无模型 alert | 不建 Thread |
| Thread 创建失败 | Repository/本地存储异常 | 是 | “新建对话失败，请重试” | 清 loading/token |
| 成员不一致 | thread.memberID ≠ ref.memberID | 不应自动重试 | 不打开 Chat，显示准备失败 | 回滚空 Thread |
| 引用无效 | 类型不受支持/资源不存在 | 刷新后可试 | 显示资源不可用 | 不换成其他资源 |
| 资源越权 | 当前账号无权访问 member/resource | 否 | “无权访问该医疗资料” | 清 pending，不记录敏感内容 |
| Cover 忙 | 已有 fullScreenCover | 否/稍后重试 | 保持当前展示 | 不建新 Thread |
| 预览加载失败 | 缓存与网络都无数据 | 是 | 快照兜底/重试 | 保留 canonical identity |
| 生成中关闭 | `stateStore.isSending == true` | 用户选择 | 关闭确认 | 停止后收尾 assistant message |
| 账号切换/登出 | 宿主依赖域变化 | 否 | 回到登录/新账号 | 取消任务、清请求与 Cover |

## 十四、与其他模块的接口边界

### 14.1 本模块负责

- 从详情页接收结构化健康资源对话请求。
- 检查 Chat 模型可用性并引导 AI 设置。
- 以资源 memberID 新建 Thread，注入引用，展示全屏 Chat。
- 处理关闭、连点、取消、中间失败补偿和账号清理。

### 14.2 本模块不负责

- 不创建、编辑、删除或归档病历。
- 不复制全量病历到 Thread 或草稿。
- 不重新实现健康资源预览、AI context resolver 或消息卡。
- 不保证 AI 医疗结论；继续遵守现有医疗 AI 提示和风险边界。
- 不改动 API Key 安全存储和 Provider 管理规则。

### 14.3 上游调用方

- 首期：`MedicalCaseDetailPage`。
- 后续：体检报告、检查报告、处方、用药计划、药箱等详情页。

### 14.4 下游依赖

- AI Config Center / `ChatDetailViewModel.hasAvailableChatModel()`。
- `ChatListViewModel` / Thread 创建用例。
- `ChatStateStore` / `ChatComposerDraft`。
- `HealthResourceRef`、`HealthResourceSendValidator`。
- `SignedInMainTabHostView`、`HomeFullScreenCover`、`ChatView`。

### 14.5 输入和输出契约

### 17.2 当前缺口

2. `HomeFullScreenCover` 没有 Chat case，`homeFullScreenCoverContent` 没有 `ChatView` 分支。
3. `SignedInMainTabHostView` 没有本入口的无模型 alert 和 `APIKeysSettingsView` 状态。
4. `ChatView` 没有“仅全屏展示时出现”的关闭回调/按钮。
5. `ChatListViewModel.createThread()` 只根据启动偏好和首页当前成员解析初始 memberID，没有供健康资源入口使用的显式 memberID 建立方法。
6. 病历 DTO 到 `HealthResourceRef` 的映射逻辑封装在问报告 mapper 私有方法中，无法被详情快捷入口安全复用。
7. 尚无跨详情页通用的请求与编排器。
8. 尚无本功能专项自动化测试。

### 17.3 建议演进

1. 先抽取纯值请求、ref factory 和 coordinator，再接 UI，避免首期就把病历 DTO 泄漏到 App/Chat 宿主。
2. 为 `ChatListViewModel` 增加显式 memberID 建立语义，保留原无参入口给对话列表。
3. 把普通 route 和 full-screen route 的 ChatView 组装/准备逻辑抽为共用 builder，避免后续依赖参数漂移。
4. 病历入口验证稳定后，按“体检报告 → 检查报告 → 处方/用药计划 → 药箱”顺序扩展；每次扩展只增加页面入口和类型 factory 测试。
5. 若产品后续要求杀进程后恢复未发健康资源，单独建立 Composer draft 持久化工单，不在本需求中隐式扩大范围。

### 17.4 建议实施顺序

1. 纯值请求 + 统一 ref factory + 单元测试。
2. 显式 memberID Thread 创建入口 + coordinator 状态机 + 幂等/补偿测试。
3. App 宿主 alert/API Key Sheet/Cover 互斥状态。
4. ChatView 公共组装、准备任务与可选关闭。
5. 病历详情公共 Action 接入和右下角操作栈。
6. 本地化、无障碍、日志/埋点、集成与 UI 验收。

## 十八、整体验收标准

### 18.1 功能验收

- [ ] 病历详情右下角显示对话按钮，与现有新增记录菜单排列正确。
- [ ] 点击后总是新建 Thread，不复用旧对话。
- [ ] 新 Thread 显式绑定当前病历所属成员。
- [ ] ChatView 以 `fullScreenCover` 展示，并有右上角关闭。
- [ ] 输入框上方自动出现当前病历预览，可查看、移除、发送。
- [ ] 进入后不自动填问题、不自动发送、不自动启动 AI。
- [ ] 无可用模型时先显示提示，可进入 API Key 设置，期间不创建 Thread。

### 18.2 数据与隔离验收

- [ ] `thread.memberID == ref.memberID == currentItem.member`。
- [ ] `ref.resourceType == medical_case`，`ref.resourceID == currentItem.id`。
- [ ] 家庭多成员、首页选中成员与病历成员不同时不会串数据。
- [ ] 登出/切换账号清理 pending request、准备任务与 Cover。
- [ ] 日志不输出病历正文、诊断摘要、附件内容或 API Key。

### 18.3 稳定性与交互验收

- [ ] 连点、页面重算、设置 Sheet 关闭、Cover 重建都不会多建 Thread/多注入引用。
- [ ] 创建成功但注入失败有补偿，不出现可见幽灵会话。
- [ ] 全屏 Chat 完成 select/prepare/load，不显示错 Thread 或空白消息区。
- [ ] 生成中关闭按照确认选项正确收尾，不留悬挂发送状态。
- [ ] 小屏、Dynamic Type、横屏和 VoiceOver 下入口可用。

### 18.4 公共化验收

- [ ] 病历详情不直接持有 Chat ViewModel 或 AI Settings ViewModel。
- [ ] 公共请求与 coordinator 不依赖 `RemoteMedicalCaseSummary`。
- [ ] 后续接入体检/检查/处方/用药/药箱时，无需复制模型门控、Thread 创建、Cover 和 API Key 设置代码。
- [ ] 新类型接入必须通过 factory、preview loader、context resolver 和本地化支持矩阵。
