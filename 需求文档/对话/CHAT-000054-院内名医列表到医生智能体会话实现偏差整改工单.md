## 一、审计结论

当前 iOS 已经存在可编译的 HospitalCare 第一版实现，不再是“尚未开发”状态。对话 Tab 分段、医生目录、科室筛选、医生搜索、开始/继续咨询、医生身份系统卡、轻量详情页、会话内新建并继承智能体等主链路均已有代码。

但当前实现仍存在两类问题：

1. **明确违反已确认需求的偏差**：固定演示医院未落实；患者仍能通过普通对话列表和会话页“对话列表”访问旧医院会话。
2. **部分落地或由客户端自行猜测的偏差**：医院目录失败时自动进入普通对话；搜索范围比确认口径更宽；后台展示顺序没有服务端字段；客户端重复选择“最新智能体”；医院会话身份依赖本地映射；医生详情缺少医院介绍。

20 项确认结果统计：

| 状态 | 数量 | 说明 |
| --- | ---: | --- |
| 已符合 | 12 | 主链路已存在且与确认需求一致 |
| 部分符合 | 6 | 主体存在，但边界、事实来源或异常链路不完整 |
| 明确偏差 | 2 | 当前行为与确认需求直接相反 |

此外发现 1 项未经本轮问答确认的额外行为：院内名医分段右上角“＋”会先切换到普通对话，再创建普通 Thread。该行为应从院内名医分段移除，不应把“新增普通会话”伪装成“院内咨询”。

## 四、P0 明确偏差整改

### 4.1 固定演示医院，不再取第一家医院

#### 当前问题

`LoadHospitalAgentDirectoryUseCase.probeDemoHospital(accountID:)` 当前行为：

```text
医院缓存有值 → 取 first
否则 GET hospitals → 取 first
```

服务端医院列表按名称排序。只要增加第二家启用医院，患者端展示对象就可能变化，无法保证固定为天长市中医院。

#### 目标方案

1. Demo 配置使用稳定医院业务编码，当前天长市中医院默认 `code = 000001`。
2. iOS `HospitalPublicDTO` 补齐服务端已经返回的 `code` 字段。
3. 新增单一的 Demo 医院解析职责，例如 `ResolveDemoHospitalUseCase`；从医院列表中按 code 精确匹配。
4. 未匹配时保持“院内名医”分段并展示“演示医院未配置/不可用 + 重试”，不自动取其他医院。
5. 禁止把医院 UUID 写死在 UI；UUID 属于环境数据，业务 code 才是 Demo 配置键。
6. 固定医院变化必须通过环境配置或统一 Demo 配置入口修改，不能散落到 ViewModel。

#### 失败语义

| 场景 | 目标行为 |
| --- | --- |
| 医院列表请求失败 | 院内名医页显示加载失败与重试 |
| 返回列表没有 `000001` | 显示演示医院未配置，不选其他医院 |
| 固定医院已停用 | 显示医院服务暂停，不创建普通会话 |
| 用户主动切到普通对话 | 才进入普通列表；沿用普通对话既有行为 |

### 4.2 阻断患者端历史医院会话入口

#### 当前泄漏路径

1. 普通对话分段使用 `stateStore.threadItems` 全量列表，没有排除 `ClinicalConversationBinding` 对应 Thread。
2. 医院会话 ChatView 右上角仍显示“对话列表”按钮。
3. 该 Sheet 复用 `ChatConversationListPage(onThreadSelected:)`，可选择任意旧 Thread。
4. 患者新建咨询后，仍可通过以上入口切回旧医院会话，与“本期不提供历史会话入口”相反。

#### 目标方案

1. HospitalCare 启动时调用现有医院会话列表接口，不传成员过滤或覆盖所有可访问成员，获得当前账号全部医院 Thread 的稳定集合。
2. 将返回的 `thread_id + agent_id + member_id + hospital_id` 写入账号级 `HospitalConversationScopeStore`。
3. 普通对话分段只展示不在医院 Thread 集合中的普通 ChatThread。
4. 院内名医目录仍只展示医生卡，不增加医院历史 Thread 列表。
5. 当前 ChatView 属于医院会话时，隐藏右上角“对话列表”按钮；保留右上角既有“新建对话”按钮。
6. 新建医院会话后旧 Thread 保留在服务端和本地聊天存储中，但不提供患者 UI 入口。
7. 普通会话的列表、历史切换、编辑、删除和置顶能力保持原样。

#### 禁止方案

- 不得物理删除或软删旧医院 Thread 来实现“不可见”。
- 不得只按 Thread 标题、首条消息类型或医生姓名猜测医院会话。
- 不得只依赖当前设备曾经打开过医生卡形成的本地映射。
- 不得让旧医院 Thread 混入普通对话搜索结果或对话选择 Sheet。

### 4.3 医院会话身份从服务端 context 恢复

#### 当前问题

`ChatView.isHospitalConversation` 只查询 `HospitalConversationScopeStore`。该映射通常在患者点击医生卡或当前设备创建会话时写入，因此以下场景可能丢失：

- 新设备登录并同步到已有医院 Thread。
- 本地 ScopeStore 被清理，但聊天数据库仍恢复了 Thread。
- 从通知、深链或其他未来入口直接打开医院 Thread。
- 旧版本创建的医院会话升级到新版本后首次打开。

Scope 丢失后的风险：

1. 医院会话被当作普通会话。
2. 普通科普引导卡可能尝试修复或插入。
3. 右上角新建对话创建普通 Thread，而不是继承医生智能体。
4. 旧医院 Thread 出现在普通历史入口。

#### 目标方案

1. iOS 增加服务端现有会话 context 的读取能力：`GET /api/v1/hospital-care/conversations/{thread_id}/context/`。
2. 进入 ChatView 时先查询本地 scope；未命中时异步读取 context 并回填。
3. “是否插入普通引导卡”“是否隐藏历史列表”“新建对话继承哪个 agent”必须等待 scope 判定完成，不能先按普通会话执行后再纠正。
4. context 返回 404 才按普通会话继续；401/403 按既有鉴权流程处理；网络失败保留未知状态和重试，不将医院会话降级成普通会话。
5. 本地 scope 按 `accountID + threadID` 隔离；账号切换时清理内存，持久化数据按既有账号生命周期策略处理。

### 4.4 移除院内名医分段的普通新建入口

#### 当前问题

`ChatConversationListPage` 在院内名医分段点击右上角“＋”时：

```text
切到普通对话
→ 调用普通 createThread
→ 打开无医生智能体绑定的普通会话
```

该行为不是本轮问答确认内容，也与“患者从医生智能体发起院内咨询”的信息架构冲突。

#### 目标方案

- 院内名医分段隐藏列表页右上角“＋”。
- 普通对话分段继续显示并复用原有“＋”。
- 医院会话页内部继续显示“新建对话”，并继承当前医生智能体和输入框当前成员。
- 不新增“随机医生”“默认医院智能体”或无 agent 的医院会话。

## 五、P1 部分符合项整改

### 5.1 搜索字段收敛

已确认搜索范围只有医生姓名、职称和科室。服务端当前还匹配智能体名称。由于服务端分页后客户端无法判断一条结果是由哪个字段命中，禁止用 iOS 本地过滤补救。

推荐处理：

1. 服务端患者目录的 `keyword` 收敛为医生姓名、职称、科室。
2. iOS 保持现有 placeholder，不增加症状、消息或智能体名称的提示。
3. 增加契约测试，分别验证姓名、职称、科室命中，智能体名称单独命中时不返回。

该项属于服务端契约依赖；服务端未收敛前，iOS 只能标记为“接口实际范围更宽”，不能宣告完全验收。

### 5.2 主智能体职责收口到服务端

当前服务端 `published_agents()` 已经按医生去重，返回每位医生最新已发布智能体；iOS 又执行一次按发布时间去重，形成第二套选主逻辑。

本期 Demo 落地口径：

1. 将服务端“每位医生最新已发布智能体”视为当前主智能体规则。
2. iOS 不再按 doctorID/publishedAt 自行去重，只消费服务端返回的一卡一医生结果。
3. 若后续产品改为后台手动指定主智能体，应先修改服务端模型、唯一约束、后台表单和患者目录，再由 iOS 无感消费；不得只在 iOS 增加本地偏好。

说明：本轮问答只确认“同一医生只展示一个主智能体”，没有完成“主智能体由谁指定”的下一题。当前工单不虚构手动指定字段，以已经落地的服务端规则作为 Demo 临时事实。

### 5.3 排序契约补齐

已确认排序：

```text
已咨询医生优先
→ 每组内按医院后台配置顺序
```

当前状态：

- iOS 已完成第一层“已咨询优先”。
- iOS 在每组内保留服务端返回顺序，做法正确。
- 服务端当前按科室 `sort_order` 和智能体名称排序，没有智能体患者端展示顺序字段。

落地要求：

1. iOS 不新增硬编码医生名单或本地 sort 值。
2. 服务端如需严格满足产品口径，应增加并返回患者目录展示顺序，后台智能体维护页可编辑。
3. 服务端变更前，Demo 暂以当前接口顺序作为医院顺序；文档和验收必须明确这是临时规则。
4. iOS 的“已咨询优先”必须使用稳定排序，不能打乱同组服务端顺序。

### 5.4 医生详情补齐医院介绍

当前 `DoctorLightProfileView` 只显示医院名称，没有医院介绍正文。服务端 `hospital_public` 已有 `introduction`，但 iOS `HospitalPublicDTO` 未声明该字段，Agent Detail 也只返回 `hospital_id`。

推荐方案：

1. `HospitalPublicDTO` 补齐 `code` 和 `introduction` 等本功能实际消费字段。
2. 医生详情加载 agent 后，按 `hospital_id` 从固定医院目录缓存解析医院资料；缓存未命中时走统一医院详情/Home API，不在 View 中直接拼第二个请求。
3. `HospitalDoctorLightProfile` 增加 `hospitalIntroduction`。
4. 页面增加“所在医院”区块，显示医院名称和介绍；介绍为空时只显示名称，不展示空标题。
5. 底部仍只有“咨询医生智能体”，不增加挂号、评价、出诊时间或真人问诊。
6. 从当前会话身份卡进入详情时，点击咨询按钮关闭详情并返回当前会话，不重复创建 Thread。

### 5.5 目录和会话分页

当前 iOS 智能体目录固定读取第 1 页最多 50 条，会话读取第 1 页最多 100 条。Demo 数据量较小时可运行，但不能把第一页当作全量事实，否则会影响：

- 科室医生完整展示。
- 已咨询状态判断。
- 普通对话列表排除医院 Thread。
- “最近会话”选择。

整改要求：

1. 医生目录支持服务端分页或明确 Demo 数据上限。
2. 用于构建医院 Thread Scope 的接口必须遍历全部页，或由服务端提供轻量 manifest/ID 集合。
3. 最近会话判断优先由服务端直接返回每个 agent 的最近 Thread，减少客户端拉取全部历史后聚合。
4. 分页未完成前，不得把超过上限的数据场景标记为已验收。

## 七、目标状态机

### 7.1 对话 Tab 首次进入

```text
进入对话 Tab
→ 默认 segment = 院内名医
→ 按固定 hospital code 解析演示医院
   ├─ 成功：加载科室、医生目录和当前成员最近会话状态
   └─ 失败：停留院内名医，显示错误/重试
→ 只有用户主动切换“普通对话”才展示普通 Thread
```

禁止在医院接口失败时触发普通对话的自动复用或自动创建。

### 7.2 点击医生卡

```text
读取输入框体系当前 selectedMemberID
→ 无成员：显示“请先选择就诊人”
→ 有成员：读取该 member + agent 的最近会话
   ├─ 有：保存服务端 scope，打开 thread
   └─ 无：POST conversations(agent_id, member_id)
          → 保存返回 scope
          → 打开 thread
```

### 7.3 进入医院会话

```text
按 accountID + threadID 查本地 scope
├─ 命中：进入医院会话模式
└─ 未命中：GET conversation context
   ├─ 返回医院绑定：回填 scope，进入医院模式
   ├─ 404 非医院绑定：进入普通模式
   └─ 网络/鉴权失败：显示可恢复状态，不先执行普通会话副作用

医院模式：
- 不插入/修复普通 ChatGuideCard
- 渲染服务端 hospitalDoctorIntroCard
- 隐藏“对话列表”历史入口
- 保留“新建对话”
- 新建时继承 agent_id，使用当时 selectedMemberID
```

### 7.4 新建医院咨询

```text
点击 ChatView 右上角新建
→ 校验当前医院 scope
→ 读取输入框当前 selectedMemberID
→ POST conversations(agent_id, member_id)
→ 原地切换到新 thread
→ 旧 thread 留存在服务端和本地，但患者端无入口切回
```

## 十四、具体落地执行方案（开发执行版）

本节将前面的偏差结论转换为可直接分派给 iOS 开发、联调和验收人员的执行方案。实现时只调整现有医院目录、会话路由和会话展示逻辑，不新建第二套对话业务模型。

### 14.1 实施边界与总原则

1. 服务端接口和服务端返回结果是医院目录、医生智能体、会话归属的唯一事实源。
2. Demo 只允许使用固定演示医院：`code=000001`，名称为“天长市中医院”。客户端不从医院列表第一项推断演示医院。
3. 医院智能体会话继续复用现有 `ChatThread`、`ChatMessage`、同步状态和会话详情页；医院范围通过现有 `HospitalConversationScopeStore` 与服务端 context 恢复。
4. 患者端不提供医院历史会话浏览能力。普通对话列表不能出现医院 Thread；医院名医列表只展示医生智能体卡片。
5. “进入对话页”和“服务端创建医院会话”必须是同一个闭环：未找到当前成员下该医生的最近会话时，先调用医院会话创建接口，再进入 ChatView；不能先创建普通 Thread 再补绑定。
6. 本工单不承接医院知识库下载、正文同步、切块、向量状态和本地检索；这些能力只在医院智能体会话 scope 确认后由独立知识库工单接入。

### 14.2 分阶段开发顺序

#### 阶段一：目录入口和固定医院

1. 在 `ChatConversationListPage` 进入“院内名医”分段时，调用现有医院目录接口。
2. 从返回的医院中按 `code=000001` 精确匹配天长市中医院；不匹配时显示“演示医院未配置”，禁止静默切换到其他医院。
3. 医院目录成功后，按现有顺序加载科室和已发布医生智能体。
4. 目录加载失败时保留“院内名医”分段和可重试状态，不自动打开普通对话，也不触发普通会话自动导航。
5. 院内名医分段右上角不显示普通新建按钮；医院会话的新建入口只保留 ChatView 右上角现有“新建对话”按钮。

#### 阶段二：成员范围和医院会话 scope

1. 目录页使用当前 `MemberContextStore.context.selectedMemberID` 作为唯一患者成员。
2. 加载医生卡片时，按当前成员查询医院会话，得到“该成员 + 该医生智能体”的最近会话映射。
3. 已存在最近会话：保存 `threadID -> hospitalID/agentID/doctorID/departmentID/memberID` scope，然后进入该 Thread。
4. 不存在最近会话：调用 `POST /api/v1/hospital-care/conversations/`，传入当前 `agent_id` 和 `member_id`，使用幂等键；服务端成功返回 Thread 后保存 scope，再进入 ChatView。
5. ChatView 发现本地 scope 缺失时，先调用现有 `GET /api/v1/hospital-care/conversations/{thread_id}/context/` 恢复 scope；恢复失败时停止医院专属渲染并展示可重试错误，不能降级为普通对话。
6. 成员切换后清除当前页面的医院目录会话映射并重新加载；不得复用上一个成员的最近会话。

#### 阶段三：会话展示和入口隔离

1. 普通对话列表过滤所有可识别为医院会话的 Thread，过滤依据依次为本地 scope、已恢复的服务端 context、医院绑定信息，不能只依赖标题。
2. 医院 ChatView 隐藏进入历史会话列表的按钮；普通 ChatView 保持现状。
3. 医院 ChatView 右上角“新建对话”复用现有新建流程，但强制沿用当前医院 scope 中的 `agentID` 与当前选中的 `memberID`。
4. 新建医院会话成功后，立即切换到新 Thread；新 Thread 自动收到服务端生成的医生身份卡和风险提示，客户端不再手工拼接医生身份 system message。
5. 医生身份卡展示头像、姓名、职称、科室、“医生智能体”标识；点击进入轻量医生详情页。
6. 医生详情页补充医院介绍；底部继续使用现有“咨询医生智能体”按钮返回或进入当前医生智能体会话，不增加挂号等流程。

#### 阶段四：契约收敛与验证

1. iOS DTO 保留服务端返回的医院 `code`、`introduction` 等字段，不能在映射时丢弃。
2. 医生列表不在 iOS 再次按医生去重或自行选主智能体，直接使用服务端已发布结果。

### 14.4 端到端调用时序

#### A. 进入对话 Tab

```text
ChatConversationListPage
  -> GET /hospital-care/hospitals/
  -> 按 code=000001 解析天长市中医院
  -> GET /hospitals/{hospital_id}/departments/
  -> GET /hospitals/{hospital_id}/agents/
  -> GET /hospital-care/conversations/?member_id={selectedMemberID}
  -> 生成医生卡片的最近会话映射
  -> 展示“院内名医”列表
```

#### B. 点击医生卡片

```text
点击医生卡片
  -> 校验已登录账号和 selectedMemberID
  -> 查找当前成员 + 当前 agent 的最近 Thread
  -> 找到：写入 hospital scope，打开 ChatView
  -> 未找到：POST /hospital-care/conversations/
  -> 服务端创建医院绑定、医生身份卡和风险提示
  -> 写入返回 Thread 的 hospital scope
  -> 打开 ChatView
```

#### C. 已有医院 Thread 直接打开

```text
打开 ChatView(threadID)
  -> 读取本地 scope
  -> 有 scope：进入医院会话模式
  -> 无 scope：GET /conversations/{threadID}/context/
  -> context 成功：写入 scope，进入医院会话模式
  -> context 失败：显示“无法确认院内会话身份”，提供重试，不降级普通会话
```

#### D. 会话页新建咨询

```text
ChatView 右上角新建
  -> 识别当前为医院会话
  -> 读取当前 scope.agentID 和 selectedMemberID
  -> POST /hospital-care/conversations/ 并携带幂等键
  -> 保存新 Thread scope
  -> 切换到新 Thread
  -> 展示服务端医生身份卡
```

### 14.5 关键状态设计

#### 医院目录状态

| 状态 | 页面表现 | 禁止行为 |
| --- | --- | --- |
| `loading` | 骨架屏或加载指示 | 不自动创建普通会话 |
| `ready` | 医生列表和科室筛选 | — |
| `empty` | “暂无院内名医” | 不跳普通会话 |
| `demoHospitalMissing` | “演示医院未配置”+重试 | 不使用医院列表第一项 |
| `failed` | “加载失败”+重试 | 不触发普通列表自动导航 |

#### 医院会话 scope 状态

| 状态 | 处理 |
| --- | --- |
| `localReady` | 直接按医院会话渲染 |
| `recovering` | 请求 context，页面显示恢复中 |
| `serverReady` | 写回本地 scope 后渲染 |
| `missing` | 若来自医生卡片则走创建；若来自已有 Thread 则走 context |
| `failed` | 展示重试，不降级普通 Chat |
| `staleMember` | 当前 Thread 成员与 selectedMemberID 不一致时禁止继续发送，先切换或新建 |

### 14.6 伪代码级业务规则

以下是联调时必须保持一致的业务算法，不是要求直接复制为 Swift 代码。

```text
resolveDemoHospital(hospitals):
    hospital = first hospitals where hospital.code == "000001"
    if hospital is nil:
        return demoHospitalMissing
    return hospital

openHospitalAgent(agent, selectedMember):
    require selectedMember exists
    recent = recentHospitalConversation(agent.id, selectedMember.id)
    if recent exists:
        rememberScope(recent.threadID, agent, selectedMember)
        openChat(recent.threadID)
    else:
        created = createHospitalConversation(agent.id, selectedMember.id, idempotencyKey)
        rememberScope(created.threadID, created.scope)
        openChat(created.threadID)

resolveChatMode(threadID, selectedMember):
    scope = localScope(threadID)
    if scope missing:
        scope = fetchConversationContext(threadID)
    if scope missing or scope.memberID != selectedMember.id:
        return hospitalIdentityError
    return hospitalChat(scope)

ordinaryThreads(allThreads):
    return allThreads where isHospitalThread(threadID) == false
```

### 14.7 并发、幂等和缓存要求

1. 医院目录、医院 context、当前成员会话映射采用 single-flight；同一时间只允许一个相同请求，避免切换页面造成重复请求。
2. 科室筛选、搜索和成员切换时取消旧请求；旧请求返回后不得覆盖新成员或新关键字的结果。
3. 创建医院会话必须复用服务端幂等语义；网络超时重试不得产生两个 Thread。
4. 本地 scope 只作为路由缓存，不作为医院归属的最终证明；scope 与服务端 context 冲突时，以服务端 context 为准并覆盖本地值。
5. scope 的持久化键必须包含账号维度；会话业务判断必须同时校验 `threadID`、`hospitalID`、`agentID`、`memberID`。
6. 退出登录时清除账号 scope、医院目录缓存和未完成医院请求；重新登录不得读取上一个账号的医院会话模式。

### 14.8 数据字段映射和敏感信息边界

| 展示/逻辑 | 服务端来源 | 客户端用途 |
| --- | --- | --- |
| 固定医院识别 | `hospital.code` | 只用于匹配 `000001`，不硬编码 UUID |
| 医院名称 | `hospital.name` / `short_name` | 目录标题和医生详情 |
| 医院介绍 | `hospital.introduction` | 医生轻量详情页 |
| 医生姓名 | `agent.doctor.display_name` | 卡片、身份卡、详情 |
| 职称 | `agent.doctor.title` | 卡片、身份卡、详情 |
| 科室 | `agent.department.name` | 筛选、卡片、身份卡 |
| 智能体身份 | `agent.id`、`agent.name`、发布状态 | 绑定会话和显示“医生智能体” |
| 会话身份 | context 中的 hospital/department/doctor/agent/member | 决定 ChatView 模式和入口隔离 |

客户端不应从医生姓名、会话标题或消息文本猜测医院会话；也不应把服务端身份卡重新拼成另一条本地 system message。

### 14.9 测试与联调用例

#### P0 必测

1. 医院列表第一项不是天长市中医院时，仍只进入 `code=000001`；找不到时显示未配置。
2. 医院目录接口失败时，不自动打开普通对话，不创建 Thread。
3. 当前成员点击未咨询医生，服务端只创建一条医院 Thread，重新点击进入同一最近会话。
4. 当前成员点击已咨询医生，直接进入该医生智能体最近会话。
5. 切换成员后，旧成员的最近会话不再显示为当前医生的最近会话。
6. 普通对话列表不出现医院 Thread。
7. 医院 ChatView 不显示历史会话入口；普通 ChatView 仍显示。
8. 医院 ChatView 新建咨询后，Thread 绑定当前医生 agent 和当前成员。
9. 本地 scope 删除后，context 成功恢复医院会话；context 失败时不会降级普通会话。
10. 新建医院 Thread 首屏显示服务端医生身份卡，点击可进入医生详情。

#### P1 必测

1. 医生详情显示医院介绍，字段为空时布局不出现空白标题。
2. 搜索医生姓名、职称、科室均可命中；输入智能体名称不应绕过服务端搜索口径。
3. 多科室筛选、空结果、清除搜索和重复请求状态正确。
4. 服务端已完成同一医生主智能体选择时，iOS 不再次改变结果顺序或替换 agent。
5. 网络超时重试、重复点击、快速切换成员不会生成重复 Thread 或串会话。
6. 退出登录再登录另一账号，旧账号的医院 scope 和医院缓存不可见。
