## 1. 需求背景

当前对话入口把“院内名医”和“普通对话”作为两个分段处理，并在既有整改口径中要求普通对话列表排除院内医生智能体会话。随着院内医生智能体和后续线上问诊接入，患者的消息记录会来自多种服务形态。如果仍按业务入口拆散历史消息，患者无法在一个稳定位置查看自己最近发生的全部沟通。

本工单重新定义原“普通对话”区域：它不再只是普通 AI Thread 的列表，而是面向患者的统一消息列表。列表需要承载普通 AI 对话、院内医生智能体对话，并为后续线上问诊对话预留明确的类型、状态和展示扩展点。

“院内就诊”保持现有定位和流程不变：它仍是按医院、科室、医生浏览并发起或继续院内医生智能体咨询的服务入口。本工单不会把医生目录改造成历史消息列表。

## 2. 已确认的产品基线

以下内容来自本轮需求原文，视为已确认，不在后续问答中反复讨论：

1. 客户端继续保留“普通对话”和“院内就诊”两个业务区域。
2. “院内就诊”的信息架构、医生目录、科室筛选、医生卡片和发起咨询流程保持不变。
3. 原“普通对话”区域改造成统一消息列表。
4. 统一消息列表必须包含普通 AI 对话和院内医生智能体对话。
5. 统一消息列表需为后期线上问诊对话预留接入能力。
6. 三类会话仍是独立 Thread，不合并消息内容，不把多个服务的消息拼入同一 Thread。
7. 优先复用当前 ChatThread、ChatMessage、Core Data 会话列表投影、搜索、未读数和会话页，不新建第二套消息数据库。

## 3. 目标与非目标

### 3.1 产品目标

- 给患者一个统一、稳定的消息入口，集中查看不同类型的沟通记录。
- 让患者在列表中能够识别对话对象、服务类型、当前状态、最新消息和未读数量。
- 点击任意列表项后，按照会话真实类型进入对应会话体验。
- 院内医生智能体会话继续保持医院、医生、智能体和成员绑定语义。
- 为线上问诊预留可扩展的数据类型和路由协议，未来接入时无需再次推翻列表架构。
- 保留现有缓存优先、后台刷新和本地消息读取能力。

### 3.2 本期非目标

- 不改造“院内就诊”医生发现页面。
- 不实现线上问诊业务、支付、排班、处方、视频或问诊订单。
- 不把普通 AI、医生智能体和线上问诊消息合并到同一会话。
- 不在客户端根据标题、头像或消息文案猜测会话类型。
- 不在本期重写底层 ChatThread 和 ChatMessage 持久化体系。
- 不改变医生接管后 AI 停止回复、取消接管后恢复 AI 回复的既有业务规则。

## 4. 目标信息架构

~~~text
对话 Tab
├── 统一消息列表（原“普通对话”区域）
│   ├── 普通 AI 对话
│   ├── 院内医生智能体对话
│   └── 线上问诊对话（本期只预留，后期接入）
│
└── 院内就诊（保持不变）
    ├── 医院与科室筛选
    ├── 医生智能体列表
    └── 开始咨询 / 继续咨询
~~~

统一消息列表是“历史沟通和未读消息入口”；院内就诊是“发现医生并发起服务入口”。同一条院内医生智能体会话允许同时从两个入口到达，但最终必须打开同一个 thread_id，不复制会话。

## 6. 统一会话分类设计草案

### 6.1 业务分类

建议在列表聚合层引入稳定的会话分类，不直接把 UI 判断散落到页面中：

| conversation_kind | 含义 | 当前来源 | 本期处理 |
| --- | --- | --- | --- |
| ordinary_ai | 普通 AI 对话 | 本地或服务端 ChatThread，且无医院/问诊绑定 | 纳入列表并沿用现有会话页 |
| hospital_agent | 院内医生智能体对话 | 医院 conversation context 或已恢复的 scope | 纳入列表，展示医生与医院身份，进入现有医院智能体会话 |
| telemedicine | 线上问诊对话 | 未来线上问诊服务返回的稳定绑定 | 预留枚举、列表投影和路由协议，本期不产生真实列表项 |
| unknown | 暂时无法判定 | context 尚未恢复、旧数据或协议异常 | 需要通过后续问答确认展示与降级策略 |

### 6.2 推荐分层

~~~text
ChatThread / ChatMessage（既有底层事实）
          +
医院会话 Context / Scope（既有医院业务事实）
          +
未来线上问诊 Binding（后期新增业务事实）
          ↓
UnifiedConversationProjector
          ↓
UnifiedConversationListItem
          ↓
统一消息列表与类型路由
~~~

UnifiedConversationListItem 建议只做展示投影，不成为新的持久化主实体。建议至少包含：

- threadID
- conversationKind
- memberID
- displayTitle
- displaySubtitle
- avatar
- latestMessagePreview
- latestMessageAt
- unreadCount
- isPinned
- serviceStatus
- hospitalID、doctorID、agentID（仅医院类型有值）
- consultationID、consultationStatus（仅未来线上问诊类型有值）
- classificationState（resolved / resolving / unavailable）

## 7. 核心业务流程草案

### 7.1 打开统一消息列表

1. 页面先读取当前账号的本地 ChatThreadListItem 缓存，立即生成可显示的基础列表。
2. 使用已缓存的医院会话 scope 为已知 Thread 标记 hospital_agent。
3. 对尚未分类的 Thread 执行轻量的后台分类恢复，不阻塞首屏。
4. 后台刷新普通会话、医院 conversation context 和未读状态。
5. 刷新成功后合并投影并更新列表；失败时继续展示可用缓存，并按后续确认的异常规则处理。
6. 统一应用搜索、置顶、时间排序和类型筛选规则。

### 7.2 点击普通 AI 对话

1. 读取 conversationKind=ordinary_ai。
2. 使用现有 ChatView 和 threadID 打开会话。
3. 保留普通 AI 的模型、引导卡、知识库与新建对话逻辑。

### 7.3 点击院内医生智能体对话

1. 读取 conversationKind=hospital_agent。
2. 将 threadID 对应的 hospitalID、agentID、memberID 注入医院会话上下文。
3. 若本地 scope 缺失，读取现有 conversation context 接口恢复；网络失败时不得把医院会话误判为普通 AI 对话。
4. 打开现有 ChatView，沿用医生简介首条系统卡、知识库 manifest、成员绑定、医生接管和会话内新建咨询逻辑。
5. 从消息列表进入和从院内就诊进入必须指向同一个 Thread。

### 7.4 后期点击线上问诊对话

1. 读取 conversationKind=telemedicine。
2. 根据服务端问诊状态决定进入文字问诊会话、只读历史或服务状态页。
3. 复用消息渲染和本地缓存，但业务操作由线上问诊路由与权限契约控制。
4. 本期只保留接口和投影扩展点，不展示虚构入口、假数据或不可用按钮。

## 9. 数据与接口原则

1. thread_id 是统一消息列表和会话详情之间的主关联键。
2. conversation_kind 必须来自稳定契约或可验证绑定，不能通过文案推断。
3. 医院会话继续使用现有医院 conversation context 恢复 hospitalID、agentID 和 memberID。
4. 未来线上问诊应提供 consultation_id 与 thread_id 的稳定绑定，并明确状态、参与方和权限。
5. 列表摘要不得请求并解码每个 Thread 的全量消息；继续使用最新消息投影。
6. 账号切换必须隔离列表缓存、医院 scope、未读数和未来问诊绑定。
7. 成员不是列表总隔离键：同一账号管理多个成员时，是否混合展示或筛选由后续问答确认。

## 10. 风险与待确认问题地图

后续按以下方向逐题确认，每题只处理一个产品决策：

1. 原“普通对话”区域的新名称与导航文案。
2. 两个分段的默认选中项。
3. 三类会话是否混排，是否提供类型筛选。
4. 统一消息卡片的信息层级和类型标识。
5. 院内医生智能体列表项显示医生名还是智能体名。
6. 多成员会话的展示与筛选方式。
7. 排序、置顶和未读优先级。
8. 普通 AI 新建入口在统一列表中的位置。
9. 院内医生智能体会话是否允许在统一列表执行删除、置顶和编辑外观。
10. 点击不同会话类型后的路由和未知类型降级。
11. 缓存优先、后台刷新和类型恢复时序。
12. 服务端需要补充的统一会话列表契约，或客户端聚合边界。
13. 线上问诊预留字段、状态机和空实现边界。
14. 搜索、空态、网络失败、下架、无权限和成员权限撤回。
15. 红点、未读数、推送点击和跨入口一致性。
16. 埋点、验收场景和灰度迁移策略。

## 16. Q3 已确认：所有会话统一混排，按最近消息时间排序

### 16.1 产品口径

“消息”页面使用一张连续列表，同时展示普通 AI 对话、院内医生智能体对话，以及后期接入的线上问诊对话。列表不按会话类型分组，不在页面中形成三个独立区块，也不要求患者先选择类型才能看到消息。

基础排序统一使用“最近一条有效消息时间”倒序。会话类型、医院、科室、医生职称和成员身份均不参与基础排序。类型差异通过列表项的头像、标题、副标题、标签和状态表达，具体卡片字段由下一题确认。

### 16.2 统一列表生成流程

~~~text
本地 ChatThreadListItem
        +
医院 conversation scope/context
        +
未来线上问诊 binding/status
        ↓
按 thread_id 聚合、补充类型和身份
        ↓
过滤无权访问、已删除或不可展示的 Thread
        ↓
生成 UnifiedConversationListItem
        ↓
按 latestMessageAt 倒序统一混排
        ↓
输出“消息”列表
~~~

### 16.3 时间字段口径

1. latestMessageAt 优先取当前 Thread 最新一条可见消息的 createdAt。
2. 新创建但尚无消息的 Thread，使用 thread.updatedAt；仍为空时才使用 createdAt。
3. 系统事件是否参与“最近消息时间”应沿用当前 ChatThreadListItem 的最新消息投影，不在列表层重新扫描消息。
4. 医生接管、取消接管、重点标记或知识库同步等纯状态变化，不应自动抬高会话排序，除非服务端同时产生一条患者可见的会话事件消息。
5. 已结束会话仍按最后一条消息时间参与排序，不因结束状态被移动到独立分组。
6. 相同 latestMessageAt 时使用稳定次序，建议按 threadID 字符串升序兜底，避免刷新后列表抖动。
7. 未来线上问诊的业务更新时间不能直接替代消息时间；订单状态变化如需抬高列表，必须形成明确的患者可见消息或通知事件。

### 16.4 跨来源聚合与去重

- thread_id 是唯一去重键。同一医院会话从本地 ChatThread、医院会话列表和医生目录最近会话三个来源出现时，只生成一个列表项。
- 医院 conversation context 只补充 hospital_agent 类型及医院、医生、智能体、成员和服务状态，不复制 Thread 或消息。
- 从“院内就诊”创建或继续咨询后，返回“消息”时应立即看到同一 Thread；若 Thread 已存在则更新该行，不能新增重复行。
- 普通 AI Thread 没有医院或问诊绑定时分类为 ordinary_ai。
- 未来线上问诊服务必须提供 consultation_id 与 thread_id 的唯一绑定；同一 thread_id 不能同时归类为 hospital_agent 和 telemedicine。
- 若两个业务绑定声称拥有同一 thread_id，应标记 classificationState=conflict、停止进入发送态并上报错误，不能由客户端按优先级静默猜测。

### 16.5 当前实现偏差

当前 ChatListViewModel 的普通对话投影会主动排除 HospitalConversationScopeStore 中识别出的医院 Thread，这是 CHAT-000054 的旧要求。该过滤规则与本工单的统一混排目标直接冲突。

本工单落地后：

1. “消息”列表不得过滤 hospital_agent Thread。
2. HospitalConversationScopeStore 从“排除依据”改为“分类与身份补充依据”。
3. 旧测试 HospitalConversationScopeResolutionTests 中“普通对话投影排除医院 Thread”的断言需要由新混合列表断言替代。
4. CHAT-000054 中“普通对话列表排除全部医院 Thread”的要求被本决策明确覆盖；“院内就诊不显示历史 Thread 列表”仍然有效。

### 16.6 客户端落地方案

1. 保留 CoreDataChatStore.loadThreadListItems() 作为 Thread、最新消息、时间、未读和置顶信息的底层读取入口。
2. ChatListViewModel 不再调用“排除医院 Thread”的 ordinaryConversationItems 作为消息列表结果。
3. 新增独立的 UnifiedConversationProjector 或等价应用层组件，输入底层 ChatThreadListItem 和各业务绑定，输出 UnifiedConversationListItem。
4. 投影过程必须是纯函数或可独立测试的确定性逻辑；页面不直接查询 HospitalConversationScopeStore 并临时改变卡片。
5. 首屏可以先使用缓存 scope 完成投影；后台恢复 context 后只更新受影响的行类型和身份，保持 threadID 稳定。
6. 单条新消息到达时沿用当前增量刷新能力，只重新投影对应 threadID，不为一次消息重建或重载全列表。
7. 搜索先作用于统一投影后的可见字段，不能只搜索 ChatThread.title；具体搜索范围后续确认。
8. 列表使用单一 ForEach 数据源，禁止普通 AI、医院和问诊各自维护一套 List 后在 View 中拼接。

### 16.7 关于现有置顶能力

本题确认的是“不同类型不分组，基础顺序按最近消息时间倒序”。当前系统已有 isPinned 与 pinnedAt，并在 CoreDataChatStore 中执行置顶排序。置顶是否继续高于时间排序尚未确认：

- 在确认之前，数据投影必须保留 isPinned 与 pinnedAt，不删除既有字段和用户数据。
- 产品展示规则暂以 latestMessageAt 为基础顺序。
- 是否允许所有类型置顶、置顶是否跨类型统一生效，将在后续独立问题中确认。

### 16.8 性能与一致性要求

- 列表首屏不得为每一条 Thread 串行请求 conversation context。
- 医院 scope 优先通过批量 hydrate 或缓存恢复；单 Thread context 仅用于缺失补偿和打开前校验。
- 列表排序发生在统一投影完成后，禁止每个类型先排序再拼接。
- 后台刷新期间保持已有列表可用，不展示全屏空白或反复改变滚动位置。
- 最新消息到达时，该 Thread 应按新 latestMessageAt 移动到正确位置，并保留稳定动画。
- 被服务端删除或撤权的 Thread 不应仅凭旧缓存永久保留，具体缓存和撤权规则后续确认。

## 17. Q4 已确认：统一卡片骨架，根据类型展示身份信息

### 17.1 产品口径

消息列表只维护一种基础卡片结构，普通 AI、院内医生智能体和未来线上问诊均使用相同的信息层级、间距、点击行为和未读表达。不同会话类型通过真实身份字段和状态字段形成差异，不为每种类型复制一套完整组件。

患者必须在不进入详情的情况下看清两个问题：

1. 我正在和谁沟通。
2. 这是普通 AI、医生智能体，还是真人线上问诊。

因此类型标识属于必要身份信息，不能仅依赖头像、名称或消息内容暗示。

### 17.2 公共卡片骨架

~~~text
┌────────────────────────────────────────────┐
│ [头像]  主标题                 最近时间     │
│         [类型标识] [服务状态]  未读角标     │
│         副标题 / 身份补充                   │
│         最新一条消息摘要                   │
└────────────────────────────────────────────┘
~~~

公共字段从上到下的优先级：

1. 头像：识别对话对象。
2. 主标题：对话对象或服务名称。
3. 最近时间：列表排序时间的可读展示。
4. 类型标识：普通 AI、医生智能体、线上问诊。
5. 服务状态：仅在状态会影响是否可继续交流时展示。
6. 副标题：医院、科室、职称、成员等辅助身份。
7. 最新消息摘要：当前 Thread 最新一条患者可见消息。
8. 未读角标：显示当前患者账号尚未阅读的消息数量或未读点。

卡片整行作为主点击区域，进入该 threadID 对应的会话。类型标签、状态标签和文本不单独拦截主点击；只有后续明确增加的辅助操作才允许独立点击。

### 17.3 三类会话字段矩阵

| 字段 | 普通 AI 对话 | 院内医生智能体对话 | 线上问诊对话（预留） |
| --- | --- | --- | --- |
| 头像 | Thread 自定义图标或默认 AI 图标 | 真实医生头像；缺失时使用医生姓名占位头像 | 真人医生头像或问诊服务头像 |
| 主标题 | Thread 的 listDisplayTitle | 医生姓名 | 医生姓名优先；具体规则后期问诊工单确认 |
| 类型标识 | AI 对话 | 医生智能体 | 线上问诊 |
| 服务状态 | 通常不显示 | AI 服务中、医生接管中、已结束、已下架等必要状态 | 待接诊、问诊中、待回复、已结束、已取消等预留状态 |
| 副标题 | 可显示绑定成员；是否显示待后续确认 | 智能体名称；医院、科室、职称、成员按后续确认规则组合 | 医院、科室、接诊方式、成员按未来契约组合 |
| 会话标题 | Thread 的 listDisplayTitle | 保留 Thread.title，作为本次具体会话标题 | 后期按问诊会话主题规则提供 |
| 消息摘要 | 最新一条可见消息 | 最新一条可见消息 | 最新一条可见消息或患者可见问诊事件 |
| 时间 | latestMessageAt | latestMessageAt | latestMessageAt，不直接使用订单更新时间 |
| 未读 | 当前 Chat 未读投影 | 当前 Chat 未读投影，包含医生或 AI 新消息 | 未来统一未读协议 |

### 17.4 身份与状态约束

- 院内医生智能体必须明确显示“医生智能体”，不能只显示“医生”或“在线医生”，避免患者误认为全部回复都由真人实时发送。
- 医生接管后，卡片状态可显示“医生接管中”；该状态不能把会话类型改成线上问诊。
- 线上问诊类型必须建立在真实问诊服务绑定上，不能因为医生发送过一条消息就把 hospital_agent 改成 telemedicine。
- 普通 AI 卡片不得使用真实医生头像、医院名称或“医生”身份标签制造医疗主体误认。
- 已结束、已下架、无权限等状态优先于“AI 服务中”等普通运行状态。
- 服务状态只显示对患者当前操作有影响的一个主状态，避免一行堆叠多个标签。

### 17.5 最新消息摘要规则

1. 摘要只展示患者有权查看的最新消息，不因列表展示重新请求完整消息流。
2. 文本消息展示截断后的纯文本，换行压成单行。
3. 图片、附件、工具卡片等非纯文本消息使用已有本地化摘要，例如“[图片]”“[附件]”或对应工具结果名称。
4. 系统内部调试事件、同步日志、模型调用信息不得进入患者列表摘要。
5. 医生接管、结束会话等事件如果本身是患者可见消息，可以作为摘要；否则仅更新状态标签。
6. 消息解密或解析失败时显示受控兜底文案，不展示原始 JSON、内部类型名或错误堆栈。

## 18. Q5 已确认：医生姓名为主标题，智能体名称为副标题，并保留 Thread 标题

### 18.1 产品口径

院内医生智能体会话在统一消息列表中同时表达三层信息：

1. **医生姓名**：主标题，先让患者确认真实服务主体。
2. **智能体名称**：身份副标题，说明患者当前使用的是哪一个医生智能体服务。
3. **Thread 标题**：该次具体会话的标题，继续保留，不被医生姓名或智能体名称替代。

医生姓名解决“我在和哪位医生的智能体沟通”；智能体名称解决“这是什么服务”；Thread 标题解决“这一次在聊什么”。三者不是同义字段，必须分别取数和展示。

### 18.2 院内医生智能体卡片信息顺序

~~~text
┌────────────────────────────────────────────────┐
│ [医生头像]  张医生                        10:26  │
│             [医生智能体] 开开心内科智能体  [AI 服务中] │
│             会话：近期血压波动咨询               │
│             请问我这两天头晕，需要马上就医吗？  │
└────────────────────────────────────────────────┘
~~~

字段顺序固定如下：

| 层级 | 字段 | 来源 | 展示规则 |
| --- | --- | --- | --- |
| 主标题 | 医生姓名 | 医院 conversation context / 医生资料 | 必填展示；缺失时降级为“院内医生智能体” |
| 第一副行 | 类型标签 + 智能体名称 + 主服务状态 | 分类投影 + ClinicalAgentProfile | 先显示“医生智能体”，再显示智能体名称；状态仅显示一个最高优先级状态 |
| 第二副行 | Thread 标题 | ChatThread.title / listDisplayTitle | 加“会话：”前缀；为空时隐藏整行，不用医生名或智能体名回填 |
| 消息摘要 | 最新可见消息 | ChatThreadListItem 最新消息投影 | 保留既有截断和隐私规则 |

Thread 标题不与最新消息摘要合并：标题用于描述会话主题，摘要用于显示最后一条沟通内容。即使两者文本相同也保留其各自语义，UI 可通过截断规则避免卡片过高。

### 18.3 Thread 标题生成与编辑边界

1. 本工单不新增医院会话专用标题生成器，继续复用已有 ChatThread 标题来源和既有自动命名逻辑。
2. 医生智能体创建会话时，如果服务端或客户端已有默认标题，可先显示默认标题；后续自动摘要或患者/医生已有改名流程更新 title 后，统一消息列表自动刷新。
3. 不允许将医生姓名写入 ChatThread.title 作为替代方案，避免标题重复、改医生资料时历史标题被污染，以及跨类型投影出现歧义。
4. 不允许把智能体名称写入 ChatThread.title 代替服务身份；智能体改名后历史会话仍需按当前或快照策略显示身份，具体版本快照规则由服务端契约确认。
5. 当前普通 AI Thread 的标题逻辑保持不变；普通 AI 卡片仍以 Thread 标题作为主标题。
6. 当前医院会话是否允许患者编辑 Thread 标题、是否允许医生编辑，以及编辑后是否同步到患者端，属于会话操作权限问题，后续单独确认。

### 18.4 字段获取与缓存规则

- 医生姓名和智能体名称必须来自医院会话 context 或医院目录/智能体资料，不能从 Thread.title 解析。
- Thread 标题始终来自 ChatThread.title；列表展示优先复用 ChatThreadListItem 已提供的 listDisplayTitle 规则，避免 View 再做标题清洗。
- 身份资料缓存与 Thread 数据分开：Thread 标题变化只刷新该 Thread 行；医生或智能体资料变化只刷新关联医院会话的身份投影。
- context 尚未恢复时，保留 Thread 标题和最新消息，但主身份进入加载/中性状态；不得把 Thread 标题误显示成医生姓名。
- 医生已离职、智能体下架或资料被撤回时，保留历史 Thread 标题和消息；身份区域按服务端状态显示“服务已结束”“智能体已下架”等受控状态。

### 18.5 多行与可访问性要求

1. 小屏默认优先保证医生姓名、类型标签、智能体名称和时间可读。
2. Thread 标题最多一行，过长时尾部截断；最新消息摘要最多一行，超长时尾部截断。
3. Dynamic Type 放大后，医生姓名与智能体名称可以换行；Thread 标题和摘要按系统布局可各自增加一行，但不可遮挡时间或未读数。
4. VoiceOver 的朗读顺序：医生姓名、医生智能体、智能体名称、服务状态、会话标题、最新消息、时间、未读数。
5. “会话：”仅是视觉和语义前缀，不把“Thread”或内部 ID 直接暴露给患者。

## 19. Q6 已确认：展示当前账号下全部成员会话，并标识患者成员

### 19.1 产品口径

“消息”是当前登录账号的统一收件箱，不是当前选中成员的单人收件箱。账号管理本人和家庭成员时，普通 AI、院内医生智能体和未来线上问诊的全部可见会话都进入同一时间序列。

### 19.2 成员标识规则

| Thread 绑定状态 | 卡片成员标识 | 数据来源 | 说明 |
| --- | --- | --- |
| memberID 等于账号本人成员 | 本人 | Member / MemberContextStore | 使用“本人”而不是重复显示登录账号姓名 |

| memberID 存在但成员资料尚未加载 | 正在加载成员信息 | memberID + 成员资料异步恢复 | 不显示裸露数字 ID |
| memberID 存在但成员已删除或授权撤回 | 成员信息不可用 | 服务端成员状态 | 历史会话按权限规则处理；不得伪造为本人 |
| memberID 为空 | 未关联成员 | ChatThread 通用事实 | 仅普通 AI 旧 Thread 可出现；医院和线上问诊 Thread 不允许为空 |

成员标识放在类型身份区域，不抢占主标题：

~~~text
普通 AI：    [AI 对话] · 本人
医生智能体： [医生智能体] 开开心内科智能体 · 母亲
线上问诊：   [线上问诊] 问诊中 · 父亲
~~~

如果同一行同时需要展示医院、科室、职称和成员，优先顺序为：服务类型与服务状态 → 智能体名称/问诊身份 → 成员。视觉上可分成两行，但成员名称必须始终可见，不能在小屏被静默省略。

### 19.3 打开会话时的成员恢复流程

~~~text
患者点击账号级消息列表某一行
        ↓
读取 UnifiedConversationListItem.memberID
        ↓
验证该成员当前仍对账号可见
        ↓
恢复该 Thread 的成员上下文
        ↓
按 conversationKind 打开普通 AI / 医生智能体 / 线上问诊会话
~~~

具体规则：

1. 列表页不修改全局 selectedMemberID，只显示归属。
2. 进入普通 AI 会话时，ChatView 使用 Thread.memberID 恢复会话内成员上下文；如果 Thread 未关联成员，沿用普通 AI 的既有未绑定逻辑。
3. 进入医院医生智能体会话时，memberID 必须同时与 HospitalConversationScope.memberID 一致；不一致视为 context 异常，停止发送并重新读取服务端 conversation context。
4. 从某成员会话返回消息列表时，不应改变另一个页面、首页或输入框已选成员；消息列表只是查看账号级历史。
5. 用户在会话输入框内按既有功能切换成员时，不能直接把已有 Thread 的 memberID 改成另一个成员。切换后如何新建或复用会话继续沿用既有会话创建规则。
6. 医生智能体会话的成员由服务端创建会话时的 agent_id + member_id 绑定决定；从统一消息列表打开只恢复，不重新选择成员。

### 19.4 数据加载、缓存与隐私边界

- 会话列表按 accountID 隔离加载；memberID 只用于标识和详情上下文，不作为列表第一层过滤条件。
- 成员名称、本人标识和成员状态复用现有 Member / 健康档案缓存；首屏有缓存则立即显示，后台静默刷新。
- 缓存键至少包含 accountID + memberID；不得把成员名称或可见关系缓存到无账号命名空间。
- 切换账号、退出登录或成员授权撤回后，必须清理或失效该账号下对应成员的列表身份缓存、医院 scope 和可见 Thread 投影。
- 若服务端返回成员不可见或 403，客户端不可继续展示该成员的完整姓名、病情摘要、医生身份或本地消息正文；最终清理策略依赖服务端权限契约并在异常问题中细化。
- 不在消息列表展示身份证号、手机号、就诊号、病历号、诊断或其他患者基础资料；成员标识仅用于区分会话归属。

### 19.5 搜索与排序影响

1. 所有成员的 Thread 继续按 D-006 的最近消息时间统一混排，不按成员分组。
2. 成员身份不改变基础排序和未读计数规则。
3. 后续消息搜索应支持成员姓名或“本人”匹配，以帮助家庭账号定位会话；具体搜索字段和隐私提示单独确认。
4. 本期不增加按成员筛选的顶部控件、二级页面或“家庭成员消息”入口，避免破坏连续消息列表；后续有大量家庭会话时可在筛选问题中评估。
5. 置顶、删除、已读等会话操作是否跨成员允许，仍需要结合会话类型和权限另行确认。

## 20. Q7 已确认：保留置顶，全部类型统一置顶并排在最前

### 20.1 产品口径

统一消息列表继续支持患者主动置顶会话。普通 AI、院内医生智能体和后期线上问诊使用相同的置顶能力与排序规则：

1. 所有 isPinned=true 的会话先组成置顶区。
2. 置顶区内部按 latestMessageAt 倒序排列。
3. 其余会话组成普通区，按 latestMessageAt 倒序排列。
4. 同一排序键相同则按稳定 threadID 兜底，避免刷新抖动。

置顶是患者的个人消息整理偏好，不代表医疗优先级、病情严重程度、医生接管状态、线上问诊是否待回复，也不会通知医生或改变服务端会话状态。

### 20.2 排序算法

~~~text
全部可见 UnifiedConversationListItem
        ↓
按 isPinned 分为置顶区 / 普通区
        ↓
每个区内按 latestMessageAt 倒序
        ↓
时间相同按 threadID 稳定兜底
        ↓
置顶区在前 + 普通区在后
~~~

建议排序比较器：

1. isPinned：true 优先于 false。
2. latestMessageAt：新的优先于旧的。
3. threadID：升序作为确定性兜底。

已有 pinnedAt 可继续用于审计或未来“按置顶时间排序”能力，但本期确认的可见排序不使用 pinnedAt 作为置顶区内第一排序键。新消息进入已置顶会话时，该会话在置顶区内上移；进入未置顶会话时，仅在普通区内上移。

### 20.3 操作范围与边界

| 会话类型 | 是否允许置顶 | 排序效果 | 额外约束 |
| --- | --- | --- | --- |
| ordinary_ai | 允许 | 进入统一置顶区 | 复用现有 Thread metadata 更新 |
| hospital_agent | 允许 | 进入统一置顶区 | 不影响智能体、医生接管、重点患者或风险状态 |
| telemedicine | 后期允许 | 进入统一置顶区 | 不影响问诊订单、接诊队列、医生端优先级或 SLA |

- 置顶作用域为当前账号。账号 A 的置顶不应影响账号 B，即使两者都能查看同一家庭成员。
- 置顶作用域为 Thread，不按医生、智能体、医院或成员批量置顶。
- 不自动置顶新建的医院会话、接管会话、重点患者会话或待回复线上问诊；所有置顶必须由患者显式操作。
- 一条已结束、已下架或只读会话仍保留其置顶状态，但卡片同时显示实际服务状态；置顶不恢复发送能力。
- 服务端若撤销会话可见权限，置顶元数据与本地缓存必须一并清理，不能通过置顶区继续暴露会话。

### 20.4 客户端落地方案

1. 复用 ChatThread.isPinned 与 pinnedAt，避免为医院或线上问诊新增平行置顶表。
2. UnifiedConversationProjector 将 isPinned 带入 UnifiedConversationListItem；排序在统一投影层执行，不在各类型列表分别置顶后拼接。
3. ChatConversationListPage 保留现有滑动或长按“置顶/取消置顶”入口；操作文案对所有可操作类型一致。
4. 置顶元数据更新成功后，只局部更新对应 threadID 的列表项和排序位置，避免整表刷新造成滚动跳动。
5. 网络失败时沿用当前 metadata 更新的乐观更新/回滚策略；最终以服务端或既有同步事实为准。
6. 列表可选择是否渲染“置顶”区头部；即使不显示区头部，也必须以无障碍信息说明该会话已置顶。视觉样式在 UI 原型工单中统一确定。
7. 不在 HospitalConversationScopeStore 或未来问诊 binding 中重复保存 isPinned；这些绑定只提供业务身份。

### 20.5 与其他能力的关系

- D-006 的“按最近消息时间排序”在置顶区和普通区内部成立；D-010 增加置顶区优先级。
- 消息搜索结果是否保留置顶排序还是按相关度排序，后续搜索问题单独确认。
- 会话删除、归档、已读、编辑 Thread 标题等操作不因置顶自动发生；操作权限下一题单独确认。
- 推送和未读数不因会话置顶而增加或消失。
- 医生工作台中的重点患者标记与患者端置顶完全独立：前者是医生服务管理状态，后者是患者个人整理状态。

## 21. Q8 已确认：普通 AI 保留全部操作；医疗类仅允许“从消息列表移除”

### 21.1 产品口径

统一消息列表不以“所有类型操作完全相同”为目标，而是以“身份真实、医疗记录不可被患者端误删”为边界：

| 操作 | 普通 AI 对话 | 院内医生智能体 | 线上问诊（预留） |
| --- | --- | --- |
| 置顶 / 取消置顶 | 保留 | 保留 | 保留 |
| 编辑 Thread 标题 | 保留既有能力 | 不提供 | 不提供 |
| 编辑图标或颜色 | 保留既有能力 | 不提供 | 不提供 |
| 删除会话 | 保留既有能力 | 不提供 | 不提供 |
| 从消息列表移除 | 可选沿用删除或提供同名隐藏入口，最终以普通 AI 既有交互为准 | 提供 | 提供 |

医疗类包括 hospital_agent 和未来 telemedicine。医疗类会话不能使用当前普通 Thread 的“删除”语义，也不能允许患者把医生姓名、智能体名称、医院头像或线上问诊身份编辑成自定义外观。

### 21.2 “从消息列表移除”的严格语义

“从消息列表移除”只改变当前患者账号在消息列表中的可见性，不执行以下任何动作：

- 不删除服务端 ChatThread。
- 不删除 ChatMessage、医院 conversation context、医生接管记录、风险结果、知识库引用或线上问诊订单。
- 不结束医生智能体服务，不取消线上问诊，不改变医生工作台可见的服务记录。
- 不调用普通 AI 的 deleteThreadUseCase。
- 不将 ChatThread.isDeleted 置为 true。

操作完成后，该 Thread 从当前账号的统一消息列表投影中隐藏；通过院内就诊医生入口再次进入该医生智能体时，是否复用该隐藏 Thread 或创建/定位最新 Thread，遵循既有医院会话创建与续聊规则，不能为了“移除”而创建重复服务记录。

### 21.3 数据模型与持久化方案

医疗类“移除”必须采用独立的账号级可见性偏好，不污染 ChatThread 的通用生命周期。建议概念模型如下：

~~~text
ConversationListVisibilityPreference
- accountID
- threadID
- visibility = visible / hidden
- hiddenAt
- source = patient_message_list
- updatedAt
~~~

实现原则：

1. 唯一键为 accountID + threadID；同一家庭成员的不同账号不共享隐藏状态。
2. 该偏好只影响 UnifiedConversationProjector 的输出，不影响 CoreDataChatStore 中 Thread 与消息的原始保存。
3. 不能复用 isDeleted、deletedAt，也不能放进 HospitalConversationScopeStore 或未来问诊 binding。
4. 本地应使用独立可清理命名空间保存；是否同步到服务端及跨设备一致性，需要以服务端用户偏好契约为准。服务端未支持前，不得伪造“已跨设备同步”的产品承诺。
5. 用户退出登录、账号切换、服务端撤权或 Thread 真正删除时，清理对应可见性偏好。
6. 隐藏会话在出现新患者可见消息后的处理规则尚未确认，下一题单独决定，避免静默错过医生或线上问诊回复。

### 21.4 用户交互与确认

1. 医疗类卡片长按或滑动操作显示“置顶/取消置顶”和“从消息列表移除”。
2. “从消息列表移除”必须二次确认，明确提示：“仅从您的消息列表隐藏，不会删除医院服务记录或咨询记录。”
3. 确认后立即从当前列表移除，并写入账号级隐藏偏好；写入失败时恢复卡片并展示受控错误提示。
4. 不把按钮叫“删除会话”“删除病历”或“结束咨询”，避免患者误解。
5. 本期不在卡片上提供编辑医生身份、修改智能体名称、修改医院头像或编辑问诊服务状态的入口。
6. 普通 AI 的现有长按/滑动、标题和外观编辑流程保持不变；其删除语义以当前 Chat 模块既有行为为准，不被医疗类隐藏机制改变。

### 21.5 服务端与跨入口边界

- 医疗类移除是患者端收件箱偏好，医生工作台仍可按授权看到会话；不能把患者隐藏行为同步为医生端“会话已结束”。
- 医院智能体会话从院内就诊入口进入时，服务端仍以 agent_id + member_id + thread_id 的真实绑定为准；客户端隐藏偏好没有权限影响该绑定。
- 未来线上问诊在患者列表中被隐藏后，订单、支付、待接诊、医生回复、处方和售后入口都不能被错误取消。
- 推送点击、深链或医生主动消息到达时，是否恢复隐藏会话由下一题确认；在确认前，路由层必须保留 threadID 与权限校验，不能因列表隐藏而丢弃业务事件。
- 医疗会话服务端真正关闭、下架或权限撤回时，客户端可以显示或清理历史的具体规则以服务端状态为准，不能用隐藏偏好覆盖强制安全状态。

- 普通 AI 会话仍可使用现有置顶、编辑标题、编辑外观和删除能力。
- 医疗类会话只展示置顶和“从消息列表移除”，不显示编辑标题、编辑图标或删除会话。
- 移除医疗会话后，该行从当前账号消息列表消失，但服务端 Thread、消息和医院/问诊业务记录不被删除。
- 移除操作的确认文案明确说明“仅隐藏，不删除服务记录”。
- 医生工作台不会因为患者移除消息列表而显示会话结束、取消接管或丢失记录。
- 普通 AI 删除不会被误实现成“仅隐藏”；医疗类移除不会调用 deleteThreadUseCase 或写 isDeleted。
- 账号切换后，隐藏偏好不泄露到其他账号。

## 22. Q9 已确认：隐藏医疗会话收到新的患者可见消息后自动恢复

### 22.1 产品口径

患者把院内医生智能体或线上问诊会话从消息列表移除后，该操作只隐藏当前已有历史。只要该 Thread 出现一条新的、成功落库且患者有权查看的消息，客户端必须自动撤销该账号对此 Thread 的隐藏偏好，并将会话重新投影到统一消息列表。

恢复后的排序遵循 D-010：若该会话原本置顶，回到置顶区并按最新消息时间排序；未置顶则进入普通区并按最新消息时间排序。恢复不是创建新 Thread、不是恢复服务状态、更不是重新发起问诊。

### 22.2 哪些事件触发自动恢复

| 事件 | 是否恢复 | 原因 |
| --- | --- | --- |
| 医生接管后发送的患者可见文字、图片或服务消息 | 是 | 患者需要看到新的医生沟通 |
| 医生智能体生成并成功保存的患者可见回复 | 是 | 对患者是新的服务消息 |
| 线上问诊医生回复或患者可见问诊事件 | 是 | 防止漏看诊疗服务进展 |
| 患者自己成功发送的新消息 | 是 | 会话已经重新发生沟通，应回到消息列表 |
| 患者正在输入、草稿、发送失败或本地未确认消息 | 否 | 不应因为未成功消息改变隐藏偏好 |
| 内部同步日志、模型调用日志、后台向量任务 | 否 | 不属于患者可见消息 |
| 医生接管、重点标记等无患者可见消息的状态变更 | 否 | 仅更新服务状态，不应打破隐藏选择 |
| 服务端撤权、会话下架或删除 | 否 | 进入权限/状态处理，不应恢复为可访问卡片 |

“患者可见”以服务端消息可见性与当前账号/成员授权为准。客户端不得仅因为收到推送壳、背景同步成功或医院 context 更新时间变化就恢复隐藏会话。

### 22.3 恢复流程

~~~text
收到或成功发送一条新消息
        ↓
消息完成持久化与权限校验
        ↓
确认该 threadID 属于隐藏医疗会话
        ↓
清除 accountID + threadID 的 hidden 偏好
        ↓
重新投影该单条会话
        ↓
按置顶区 / 普通区与 latestMessageAt 插入消息列表
~~~

恢复必须在消息事实成功写入后发生：

1. 先完成消息同步、去重、可见性校验和 Thread 最新时间更新。
2. 再执行隐藏偏好清除，保证 app 被杀死或同步重试时仍可幂等恢复。
3. 对同一 threadID 的重复推送、消息重放或多端同步，只执行一次恢复；恢复操作必须可重入。
4. 当前消息页面正在展示时，插入恢复的卡片应使用稳定动画，不能重置滚动位置或强制跳转详情。
5. 若患者当前停留在院内就诊分段，仅更新消息分段的缓存与未读提示，不强制切换页面。

### 22.4 推送、离线与跨入口约束

- 推送点击可直接路由到该 Thread；路由前仍需按现有契约校验会话、成员与医院/问诊权限。
- 仅收到推送但尚未拉到可验证消息正文时，不提前清除 hidden 偏好；待增量同步确认新消息后再恢复。
- 弱网下消息同步失败时，保持隐藏状态和既有缓存，不能凭通知内容假设恢复成功。
- 患者从院内就诊入口重新进入并成功发送消息后，隐藏会话同样应恢复；入口不同不改变规则。
- 医生工作台或服务端收到患者移除操作的任何记录，都不得把它当成“勿扰”或“拒收回复”；新消息依然按正常服务链路触达患者。
- 多设备登录同一账号时，若隐藏偏好未来支持服务端同步，恢复事件也应同步清除；当前未具备该契约时，文档和 UI 不承诺跨设备一致恢复。

### 22.5 客户端落地方案

1. UpdateConversationListVisibilityUseCase 增加 restoreOnVisibleMessage(threadID, accountID) 或等价幂等能力。
2. Chat 同步完成新消息落库后，由统一消息协调层判断 conversationKind 与 hidden 状态，不能在 ChatView UI 层零散处理。
3. 需要把“新消息已成功持久化”和“患者有权可见”作为恢复前置条件；发送管线、推送管线、下拉同步管线都调用同一个恢复入口。
4. 恢复后只重新投影受影响 threadID 并更新排序，避免全量清空和重载消息列表。
5. 若清除隐藏偏好写入失败，保留原隐藏状态并重试；不能让 UI 显示已恢复但重启后再次消失。
6. 通用普通 AI 的删除语义不受本规则影响：已删除 Thread 收到不可能的后续消息时应走既有数据完整性处理，而不是自动恢复。

- 患者自己成功发送新消息后，隐藏医疗会话也恢复；发送失败不恢复。
- 接管、重点标记、后台任务等非消息状态变化不恢复隐藏会话。
- 已置顶会话恢复后回到置顶区；未置顶会话按最新消息时间进入普通区。
- 重复推送、重复同步或 App 重启不会产生重复卡片或错误排序。
- 无权限、已下架、已删除会话不会借由“自动恢复”重新暴露。
- 自动恢复不会切换患者当前所在分段或强制打开会话详情。

## 23. Q10 已确认：仅搜索会话身份与标题字段

### 23.1 产品口径

“消息”列表的搜索是会话定位能力，不是病情全文检索能力。患者可以通过认识的人、服务名称、医院科室、家庭成员或会话主题找到 Thread；搜索不会读取、索引、匹配或展示消息正文、病历内容、AI 回答、风险结论和附件文本。

该边界同时适用于普通 AI、院内医生智能体和后期线上问诊。搜索结果仍是统一消息卡片，不进入独立的医疗资料搜索页面。

### 23.2 可搜索字段矩阵

| 会话类型 | 可搜索字段 | 不可搜索字段 |
| --- | --- | --- |
| ordinary_ai | Thread.title / listDisplayTitle；可选 Thread 自定义外观名称 | 历史消息正文、工具参数、图片 OCR、附件正文、系统提示词 |
| hospital_agent | 医生姓名、智能体名称、医院名称、科室、职称、成员姓名、Thread 标题 | 患者/医生/AI 消息正文、医生简介全文、知识库正文、风险评估、病历内容 |
| telemedicine | 医生姓名、问诊服务名称、医院名称、科室、成员姓名、问诊会话标题 | 问诊消息、处方、诊断、订单备注、图片、附件和病历内容 |

“本人”作为成员显示文案可被搜索；搜索登录账号姓名时，若与本人映射一致，也可命中本人相关会话。memberID、hospitalID、agentID、consultationID、就诊号等内部标识不得作为患者端可输入或展示的搜索键。

### 23.3 匹配与结果规则

1. 支持不区分大小写的包含匹配；中文按连续文字匹配，不要求拼音、首字母或语义召回。
2. 多字段采用 OR 匹配：任一允许字段命中即可展示该 Thread。
3. 不做跨字段词语拼接猜测；例如“张医生 心内科”是否支持组合检索，后续若需要应定义明确 token 规则。
4. 搜索结果继续遵循 D-010 的置顶区/普通区排序，不按相关度重排，保证列表位置稳定可预期。
5. 隐藏的医疗会话不出现在搜索结果；收到新患者可见消息自动恢复后才可被搜索。
6. 无权限、已撤权、已删除或分类冲突的 Thread 不得仅因本地索引命中而重新展示。
7. 搜索仅在当前账号可见会话范围内执行；不得跨账号、跨家庭授权范围或跨医院读取身份资料。

### 23.4 输入、空态与隐私提示

- 搜索框占位文案建议为“搜索医生、智能体、成员或会话”。
- 用户输入时实时在本地已加载的 UnifiedConversationListItem 中过滤，避免为每个字符请求服务端或扫描完整历史消息。
- 首屏身份资料尚未恢复时，结果可先显示已知字段；恢复后增量补充命中项，避免全屏加载阻塞。
- 无结果时使用“未找到相关消息”空态；不得提示“未搜索到病情内容”或暗示已检索消息正文。
- 搜索结果卡片继续只显示 D-007/D-008 已确认的身份、会话标题和最新消息摘要；摘要不是命中证据，也不应高亮或暴露正文检索片段。
- 搜索文本属于短期 UI 状态，不写入消息正文、聊天模型上下文、医院审计日志或服务端病历系统。

### 23.5 本地索引与性能原则

1. 不新建消息全文索引，不把 ChatMessage 正文写入 Core Data 搜索字段或用户偏好缓存。
2. UnifiedConversationListItem 在投影时可生成 normalizedSearchTokens，只包含已批准的身份与标题字段。
3. normalizedSearchTokens 必须按 accountID 隔离，并在成员撤权、医院会话撤权、账号退出、Thread 删除或身份资料更新时失效。
4. 医生姓名、医院、科室和智能体名称更新后，重新投影对应 Thread 的搜索 token；不扫描历史消息。
5. 搜索结果数量较大时继续使用现有列表虚拟化；不因为过滤而对每一项拉取 context。
6. 后期如需拼音、模糊匹配或服务端搜索，必须单独评审医疗隐私、索引生命周期与权限过滤，不能在本期隐式引入。

## 24. Q11 已确认：保留“＋”，只新建普通 AI 对话

### 24.1 产品口径

“消息”页面右上角保留既有“＋”新建入口，但其语义明确为“新建 AI 对话”。点击后只创建或打开普通 AI Thread，不显示医生、医院、智能体、线上问诊或服务类型选择菜单。

## 25. Q12 已确认：“消息”分段显示未读数字角标，超过 99 显示 99+

### 25.1 产品口径

对话 Tab 默认停留在院内就诊时，“消息”分段必须显示当前账号的未读消息总数。角标使患者在不自动切换分段的前提下，意识到普通 AI、医生智能体或未来线上问诊存在未处理回复。

角标数字是所有当前账号可见、且应展示在统一消息列表中的 Thread 的 unreadCount 之和。显示范围为 1–99；总数大于 99 时展示“99+”；总数为 0 时隐藏角标，不保留空白占位或红点。

### 25.2 聚合范围

| 会话状态 | 是否计入消息分段角标 | 说明 |
| --- | --- | --- |
| 普通 AI 可见 Thread | 是 | 复用 ChatThreadListItem.unreadCount |
| 院内医生智能体可见 Thread | 是 | 包含 AI 或医生发来的未读患者可见消息 |
| 未来线上问诊可见 Thread | 是 | 后期接入统一未读契约后纳入 |
| 已置顶 Thread | 是 | 置顶不改变未读计数 |
| 已隐藏医疗 Thread，尚无新消息 | 否 | 患者已主动从列表移除，且没有新沟通 |
| 已隐藏医疗 Thread，收到新可见消息 | 是 | D-012 自动恢复后重新纳入 |
| 无权限、已撤权、已删除 Thread | 否 | 不能从本地旧缓存继续计入 |
| 当前打开中的 Thread | 是否计入取决于已读状态 | 不以“页面打开”直接清零，已读时机由下一题确认 |

成员不影响聚合范围：本人和家庭成员的可见会话未读数共同计入当前账号“消息”分段角标。卡片内仍保留单条未读数，供患者识别具体是哪位成员的会话需要处理。

### 25.3 计算与更新流程

~~~text
消息落库 / 同步完成 / 已读状态变更
        ↓
更新受影响 Thread 的 unreadCount
        ↓
统一消息投影过滤不可见、隐藏、撤权 Thread
        ↓
对可见 Thread 的 unreadCount 求和
        ↓
clamp 到 99+ 展示值
        ↓
刷新“消息”分段角标与列表行角标
~~~

实现要求：

1. 角标以统一消息投影后的可见集合计算，而不是直接对本地所有 ChatMessage 或 ChatThread 全表求和。
2. 单条 Thread 的 unreadCount 变化只触发增量聚合，不需要重新加载全部消息正文。
3. 列表尚未打开、医院 scope 尚未完全恢复时，可先使用已知可见 Thread 计算；分类恢复后修正汇总值。不得把未知医院 Thread 误排除或误加为普通 AI。
4. 同一消息的重复推送、重复拉取或多端同步不能重复增加未读数。
5. 角标与应用图标 Badge、推送数量若后期需要联动，必须共用同一账号级聚合事实，不能各自计数。

### 25.4 视觉与无障碍规则

- “消息”分段名称右侧显示圆形数字角标；不影响分段文本的可点击区域。
- 1–99 显示实际数字，100 及以上统一显示“99+”。
- 角标使用系统语义颜色，但数字文本本身必须可读，不能仅靠颜色表示有未读。
- VoiceOver 朗读“消息，X 条未读消息”；99+ 朗读“消息，99 条以上未读消息”。
- 未读为 0 时移除角标与对应无障碍附加描述，不朗读“0 条未读”。
- 卡片中的未读数与分段总数保持一致；患者不要求手动核算，但两者不能出现明显不同步。
- 应用在院内就诊分段时只更新消息角标，不自动切换、弹窗或打断医生目录操作。

### 25.5 推送、缓存与权限边界

1. 收到新推送后，仅在消息完成拉取、去重、权限校验并写入本地后更新未读数；不能直接信任推送 payload 的未读总数覆盖本地事实。
2. 离线期间保持上一次已计算角标；网络恢复后按增量同步结果修正。
3. 账号切换、退出登录时立即清空上一账号消息角标；新账号完成本地加载后重新计算。
4. 成员授权撤回、医院会话撤权、服务端删除或医疗会话被移除时，必须从角标聚合集合中剔除对应 Thread。
5. 医疗会话被患者隐藏后不计入总数；收到新可见消息自动恢复时，D-012 先恢复可见性，再纳入未读聚合。
6. 不把医生工作台的“重点患者”“待处理”数量、医院服务通知或系统公告混入患者端消息未读角标。

## 26. Q13 已确认：进入会话且消息成功加载后标记该会话已读

### 26.1 产品口径

消息列表仅用于浏览和定位，不改变未读状态。患者点击任意卡片后，只有在对应会话的消息已成功加载、当前账号和成员授权校验通过、且页面真正进入可阅读状态时，才将该 Thread 当前全部患者可见未读消息标为已读。

该规则统一适用于 ordinary_ai、hospital_agent 和后期 telemedicine。已读的范围是“进入时已成功加载的可见未读消息”；会话打开后新到达的消息仍应按正常规则产生新的未读，除非当前会话处于前台可读状态并由既有实时阅读机制即时确认。

### 26.2 已读状态机

~~~text
消息列表浏览
    └─ 不改变 unreadCount

点击会话卡片
    ↓
校验 threadID、账号、成员和业务权限
    ↓
加载消息成功且 ChatView 进入可读态
    ↓
标记进入时已加载的患者可见未读消息为已读
    ↓
更新单条卡片 unreadCount 与“消息”分段聚合角标
~~~

以下场景不得标记已读：

- 仅卡片出现在屏幕可见区域。
- 搜索结果展示、长按菜单、滑动操作或列表预览。
- ChatView 仍在加载、网络失败、鉴权失败、成员不可见或医院 context 未完成校验。
- 推送到达但患者没有进入目标会话。
- 只打开医生详情、智能体详情或院内就诊目录。

### 26.3 分类会话的前置校验

| 会话类型 | 标记已读前必须成立的条件 |
| --- | --- |
| ordinary_ai | Thread 存在、当前账号可见、消息加载成功 |
| hospital_agent | Thread 存在、HospitalConversationScope/context 已确认、memberID 一致、医院服务仍允许读取、消息加载成功 |
| telemedicine | Thread 存在、问诊 binding 与参与方权限有效、消息加载成功 |
| unknown / conflict | 不标记已读 | 

医院会话不能因为本地 ChatThread 有缓存就提前清未读。若 scope 丢失或 context 请求失败，列表应保留未读，等待身份与权限恢复；不得先当作普通 AI 会话标记已读。

### 26.4 读状态同步与幂等性

1. 已读更新唯一范围为 accountID + threadID + 已读消息游标/消息集合；不通过成员姓名或标题匹配。
2. 本地消息库先以单条 Thread 为粒度更新未读投影，再触发消息分段角标的增量重算。
3. 若当前系统已有服务端已读回执或消息 cursor，继续复用；不得为医院或问诊另建与普通 Chat 不一致的已读协议。
4. 已读提交应幂等：重复打开、视图重建、网络重试和多端拉取不能导致计数负数或重复请求副作用。
5. 网络离线时，若现有架构支持本地已读 outbox，则按既有队列暂存；若不支持，客户端必须明确最终一致策略，不能在 UI 已清零后永久丢失服务端同步。
6. 服务端拒绝已读更新（撤权、会话关闭或成员不匹配）时，客户端重新拉取事实并按权限规则更新，不继续保留错误已读状态。
7. 新消息与已读提交并发时，以消息版本/createdAt/cursor 为边界：只确认进入会话时已加载的消息，新到消息不应被误清。

### 26.5 前台实时消息规则

- 患者正在查看某 Thread 且应用处于前台、会话内容可见时，后续新到消息可按既有实时已读策略立即确认；该策略必须以真实视图可读状态为准，不能仅看导航栈存在。
- 患者切换到后台、打开 Sheet 遮挡会话、切换到另一条 Thread 或离开页面后，新到消息重新计入未读。
- 医生接管中与 AI 服务中不影响已读规则；两者均按患者可见消息处理。
- 线上问诊后期的服务状态事件只有在以患者可见消息形式进入 Thread 时才参与已读；订单后台状态更新本身不应改变 unreadCount。

### 26.6 客户端落地方案

1. ChatView 在消息加载成功、会话身份确认完成且视图实际展示后，调用统一的 MarkConversationReadUseCase。
2. MarkConversationReadUseCase 输入应包含 threadID、accountID、memberID、conversationKind 和已读边界；UseCase 负责选择既有消息已读存储/同步链路。
3. ChatConversationListPage 只观察投影后的 unreadCount，不在点击卡片时提前清零。
4. ChatStateStore 接收已读成功后的单条 Thread 更新，ChatListViewModel 重新计算该行和 D-015 的总角标。
5. HospitalCare context 未解析完成时，ChatView 处于身份确认中；普通引导卡、新消息发送与已读提交均不得抢跑。
6. 测试使用可控时钟和消息 cursor，覆盖进入时消息、进入后新增消息、重复进入、离线回执、撤权与多成员 Thread。

## 28. Q15 已确认：先显示本地缓存，再后台静默刷新

### 28.1 产品口径

患者进入“消息”分段时，应用优先读取当前账号本地已保存的 Thread、最新消息投影、未读数、医院会话 scope、成员资料和可用身份缓存，尽快展示可用消息列表。随后在后台静默刷新各类事实，并只对发生变化的行进行增量更新。

刷新不是页面门禁：网络慢、医院 context 恢复慢或未来线上问诊服务暂不可用时，已缓存的消息列表仍可浏览。没有任何本地列表数据时才显示首次加载骨架或加载态。缓存不是永久授权证明，进入医疗会话和发送消息仍必须执行各自既有的服务端权限校验。

### 28.2 首屏与后台刷新流程

~~~text
进入“消息”分段
        ↓
读取 accountID 命名空间的本地 Thread / 未读 / scope / 成员缓存
        ↓
生成首屏 UnifiedConversationListItem（立即渲染）
        ↓
后台并行 single-flight 刷新
├── 通用 Chat Thread 与消息增量
├── 医院会话 scope / context / 服务状态
├── 成员资料与成员可见关系
└── 后期线上问诊 binding / 状态 manifest
        ↓
按 threadID 增量合并、权限过滤、重新投影、稳定排序
~~~

刷新任务必须按账号隔离、可取消且单飞：同一账号多次切入消息分段、下拉刷新、推送唤醒和恢复前台不能并发启动多套相同全量同步。

### 28.3 本地缓存读取范围

| 数据 | 首屏是否读取缓存 | 后台是否刷新 | 备注 |
| --- | --- | --- | --- |
| ChatThread 与最新消息投影 | 是 | 是 | 复用 CoreDataChatStore 和既有增量同步 |
| 未读数 | 是 | 是 | 首屏显示上次已知值，刷新后按 D-015 修正 |
| 置顶/隐藏偏好 | 是 | 视持久化契约刷新 | 账号级偏好先用于投影，不能影响服务端事实 |
| 医院 conversation scope | 是 | 是 | 缓存命中可立即显示医生身份；后台 context 作为最终校验 |
| 医生、智能体、医院、科室资料 | 是 | 是 | 仅使用已授权身份字段；变更后局部更新卡片和搜索 token |
| 成员姓名与本人映射 | 是 | 是 | 用于 D-009 成员标识；撤权后必须清理 |
| 线上问诊 binding/status | 后期是 | 后期是 | 未接入时不制造缓存或模拟数据 |
| 消息正文全文 | 不为列表额外读取 | 不为列表额外刷新 | 列表只使用最新消息摘要投影 |

### 28.4 缓存分类与安全降级

1. 已缓存为 hospital_agent 的 Thread 可先按医生智能体身份展示；后台刷新失败不将其降级为 ordinary_ai。
2. 未分类 Thread 可先使用中性“正在加载会话信息”状态，不能因为缺少 scope 就直接假设为普通 AI。
3. 本地缓存显示的是上次已知可见数据；服务端刷新返回撤权、删除、成员不可见、智能体下架或绑定冲突后，必须立即移除或更新对应行、未读聚合和搜索 token。
4. 医疗会话卡片即使来自缓存，点击进入时仍按现有 hospital conversation context / 未来问诊权限协议校验；校验失败禁止继续读取受限内容或发送消息。
5. 网络不可用且本地有消息缓存时，沿用既有本地消息阅读和输入发送失败处理；不能把离线缓存自动转为普通 AI 会话或跳过身份边界。
6. 网络不可用且本地无缓存时，显示“消息加载失败/请重试”空态；不伪造演示会话，不从院内就诊目录反推历史消息。
7. 所有缓存键至少带 accountID；成员、医院和智能体子数据继续按既有 accountID + memberID / hospitalID / agentID 命名空间隔离。

### 28.5 增量合并与稳定 UI

- 后台刷新以 threadID 为主键与本地投影合并；同一 Thread 不产生重复卡片。
- 身份资料变化只重投影关联 Thread 的头像、名称、标签和搜索字段；不重新读取全部消息。
- 新消息、已读更新、置顶、隐藏恢复或撤权只更新受影响的 Thread，并按 D-010 重新定位。
- 大批量刷新后使用稳定排序和差量动画，避免每次进入消息页所有行跳动。
- 当前患者正在搜索或处于某类型筛选时，刷新仍在完整后台数据上执行；UI 只重绘当前过滤结果，不重置搜索文本或筛选选择。
- 当前用户已打开某个 Thread 时，消息列表后台刷新不得替换 ChatView 正在使用的会话上下文；只更新返回列表时可见的投影。

### 28.6 刷新状态表达

| 场景 | 页面表现 |
| --- | --- |
| 有缓存，后台刷新中 | 直接展示缓存；不显示全屏加载；允许下拉刷新 |
| 有缓存，后台刷新失败 | 保留缓存；顶部轻量“部分消息可能不是最新”提示与重试入口 |
| 无缓存，首次加载中 | 显示列表骨架/加载态，不显示空列表结论 |
| 无缓存，首次加载失败 | 显示消息加载失败、重试和返回院内就诊 |
| 某一医院 context 刷新失败 | 对应卡片保留已知身份或中性状态；不阻塞其他 Thread |
| 成员资料刷新失败 | 保留上次已知成员称呼或中性“成员信息暂不可用”；不显示 memberID |

## 29. Q16 已确认：服务端提供统一“消息会话 Manifest”

### 29.1 产品口径

服务端新增账号级统一消息会话 Manifest，作为“这条 Thread 是什么会话、属于哪个成员、当前是否可见、服务状态如何”的唯一业务事实源。客户端继续以既有 ChatThread、ChatMessage、Core Data 和消息增量同步作为消息内容、最新消息摘要、未读数和本地离线阅读的事实源。

Manifest 不复制 ChatMessage，不返回完整消息正文，不替代现有聊天同步接口。它只负责为现有 thread_id 附加稳定的 conversation_kind、成员归属、医疗服务身份、访问状态、版本和删除/撤权语义。

~~~text
服务端 Unified Conversation Manifest
          ↓  类型、权限、身份、状态、版本
客户端本地 ChatThread / ChatMessage
          ↓  标题、摘要、时间、未读、置顶、消息正文
UnifiedConversationProjector
          ↓
统一消息列表 / 类型筛选 / 路由
~~~

### 29.2 服务端职责边界

| 服务端负责 | 客户端负责 |
| --- | --- |
| 根据当前登录账号与成员授权筛出可见 Thread | 缓存优先显示、后台同步、离线状态表达 |
| 为每个 thread_id 判定 ordinary_ai / hospital_agent / telemedicine | 以 Manifest 类型投影卡片与筛选，不自行猜测类型 |
| 返回医院、医生、智能体、线上问诊等必要身份引用 | 从已授权资料缓存解析头像、名称、副标题与本地化文案 |
| 返回服务状态、撤权、删除、下架和绑定版本 | 控制列表可见性、路由、发送/已读前置校验与错误提示 |
| 提供完整快照与增量游标能力 | 保存 cursor、幂等合并 upsert/delete、清理缓存 |
| 未来接入线上问诊时注册 telemedicine binding | 复用同一投影、筛选和路由框架 |
| 保证 thread_id 与业务绑定的唯一性 | 保留 ChatThread、ChatMessage 及既有消息同步，不创建第二套消息表 |

### 29.3 建议接口契约

以下为建议契约，接口路径和字段名称需在 SparkService 实现工单中正式冻结；本文档不代表当前接口已经存在。

~~~text
响应：
{
  "schema_version": 1,
  "next_cursor": "opaque-cursor",
  "has_more": false,
  "changes": [

      "conversation_kind": "ordinary_ai | hospital_agent | telemedicine",
      "member_id": 123,
      "service_status": "active | doctor_taken_over | ended | unavailable | ...",

    },
~~~

建议响应字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| schema_version | 是 | 客户端协议兼容控制，不使用隐式字段猜测 |
| next_cursor / has_more | 是 | 增量或分页同步游标；具体同步语义下一题确认 |

| service_status | 是 | 仅返回患者列表和路由所需的受控状态值 |
| identity | 是 | 类型专属最小身份引用，不携带病历或消息正文 |
| binding_revision | 是 | 单 Thread 业务绑定版本，供幂等合并与乱序防护 |
| updated_at | 是 | 服务端业务更新时间，不代替 latestMessageAt 排序 |
| reason | delete 必填 | 供客户端执行撤权、下架、绑定删除等安全清理 |

### 29.4 identity 最小字段原则

Manifest 的 identity 只返回渲染和路由不可缺少的、已授权的最小字段：

| conversation_kind | 建议 identity 字段 |
| --- | --- |
| ordinary_ai | 可为空；普通 Thread 身份主要来自现有 ChatThread |
| hospital_agent | hospital_id、doctor_id、agent_id、doctor_display_name、agent_display_name、department_display_name、hospital_display_name、avatar_version 或头像引用 |
| telemedicine | consultation_id、hospital_id、doctor_id、consultation_display_name、service_mode、参与方最小身份引用、头像版本 |

禁止放入 Manifest 的数据：

- 消息正文、聊天附件、病历、处方、诊断、风险详情、知识库正文或嵌入向量。
- 患者身份证号、手机号、就诊号、病历号等敏感标识。
- 医生工作台内部待办、重点患者标记、审计备注、模型参数或系统提示词。
- 仅服务端使用的权限策略明细、数据库主键或调试异常堆栈。

### 29.5 业务规则与冲突处理

1. 每个可见 thread_id 在同一 Manifest 版本下只能有一个 conversation_kind。
2. hospital_agent 必须同时提供 agent_id、hospital_id 和 member_id；缺任一字段视为无效 upsert，客户端进入受控错误态并不上升为 ordinary_ai。
3. telemedicine 必须同时提供 consultation_id、member_id 和可验证服务状态；不能仅因医生发送消息就归类为线上问诊。
4. ordinary_ai 不应携带医院或问诊绑定；若同时出现，服务端必须修复数据，客户端以 binding_revision 最新的受控结果为准并上报冲突。
5. delete 事件使客户端从统一消息投影、未读聚合、搜索 token 和医院/问诊身份缓存中移除该 Thread；不由 Manifest 删除本地 ChatMessage，具体本地历史保留/清理以权限 reason 决定。
6. binding_revision 单调递增；客户端仅接受比本地版本更新的变化，防止离线回包覆盖撤权或下架状态。
7. 服务端输出必须先完成账号、成员、医院和问诊权限过滤；客户端不应收到“存在但无权显示”的占位业务记录。

### 29.6 客户端合并与路由

1. 客户端新增 UnifiedConversationManifestRepository，负责请求、分页/增量、schema 校验和按 accountID 持久化。
2. Manifest change 以 threadID + bindingRevision 幂等写入独立的业务绑定缓存，不塞进 ChatThread 以避免污染通用聊天模型。
3. UnifiedConversationProjector 以 Manifest 为类型事实、以 ChatThreadListItem 为消息事实，只有两者关联成功才输出完整卡片。
4. Manifest 有 upsert 但本地尚无 ChatThread 时，可显示受控加载占位或触发现有 Thread 元数据同步；不得构造空白假会话。
5. 本地有 ChatThread 但 Manifest 尚未到达时，保持 classificationState=unknown；不得按标题猜测类型，也不得在不确认情况下发送。
6. 点击医疗卡片后，仍可使用现有医院 conversation context 或未来问诊详情接口做最终权限校验；Manifest 是列表事实源，不替代详情级安全校验。
7. 推送、深链和后台同步必须先用 threadID 查询/刷新 Manifest，再决定该线程路由为普通 AI、医院智能体还是线上问诊。

### 29.7 与现有接口的迁移关系

- 现有医院 conversations 列表、创建接口、context 接口继续承担医院目录、创建/续聊与会话详情校验。
- 现有 HospitalConversationScopeStore 迁移为 Manifest 的本地医院绑定投影/兼容缓存，逐步不再是列表分类唯一来源。
- 现有 Chat 同步、Core Data 和 ChatThreadListItem 继续承担消息与未读，不在 Manifest 中重复返回最新消息摘要。
- 未来线上问诊服务只需向 Manifest 提供其 thread_id binding 和状态，不应再要求 iOS 在消息页面分别拉取完整问诊列表后自行拼接。
- 旧客户端未升级 Manifest 协议时，继续按当前医院 scope/context 兼容运行；服务端变更需要 schema version、灰度和回滚策略。

### 29.8 服务端安全与审计要求

- Manifest 必须使用当前用户登录态鉴权，并以账号可见成员集合、医院授权和问诊参与方关系过滤。
- 所有 delete / permission_revoked 变化需可追溯业务原因和更新时间；不把敏感审计内容直接返回客户端。
- 接口不得因为客户端传入 thread_id、member_id 或 hospital_id 而扩大可见范围；游标也必须与 accountID 绑定，跨账号复用返回 400/403 或受控重新全量同步。
- 需要速率限制、分页上限和幂等游标语义，避免消息列表成为跨服务枚举接口。
- 返回医生、医院和成员展示字段时遵守最小必要原则与脱敏策略。

## 30. Q17 已确认：Manifest 使用 cursor / revision 增量同步，并支持必要时全量重建

### 30.1 产品口径

统一消息会话 Manifest 不采用每次全量拉取。客户端为每个登录账号保存独立同步 cursor，服务端根据 cursor 返回本账号自上次确认以来的 upsert/delete 变化。每条 change 还携带 binding_revision，用于防止分页、重试、推送与前后台并发导致的乱序覆盖。

首次登录、首次安装、账号切换、cursor 过期、协议不兼容或本地绑定缓存损坏时，客户端执行受控全量重建。全量重建是恢复机制，不应成为正常每次进入消息页的默认网络行为。

### 30.2 同步状态机

~~~text
无本地 cursor / 要求重建
        ↓
分页获取全量 Manifest 快照
        ↓
原子写入 binding 缓存 + final cursor
        ↓
后续进入、前后台恢复、推送或下拉刷新
        ↓
携带 accountID 对应 cursor 请求增量 changes
        ↓
按 threadID + bindingRevision 幂等应用 upsert/delete
        ↓
持久化 next_cursor
~~~

所有状态转换在账号维度独立进行。账号 A 的 cursor、快照、分页 token、in-flight 任务、错误状态和回滚逻辑不得被账号 B 复用。

### 30.3 建议同步协议

建议 Manifest 响应补齐以下字段：

| 字段 | 用途 |
| --- | --- |
| sync_mode | snapshot / delta，明确本次是全量快照还是增量变化 |
| snapshot_id | 全量重建时固定快照边界，防止分页期间新增/删除造成漏项 |
| cursor | 本次请求使用的账号级游标，可为空表示首次全量 |
| next_cursor | 本批成功应用后保存的下一游标 |
| has_more | 是否需继续分页；客户端必须拉完当前同步链才能提交 final cursor |
| reset_required | 服务端要求客户端丢弃旧绑定缓存并重建的受控信号 |
| schema_version | 协议版本；不兼容时不得静默解析 |
| changes | 按业务变化序列返回的 upsert/delete 列表 |
| binding_revision | 每条变更的单 Thread 单调版本，用于乱序幂等 |

建议错误语义：

| HTTP/业务结果 | 客户端处理 |
| --- | --- |
| 200 delta | 幂等合并 changes，完成后提交 next_cursor |
| 200 snapshot | 在 snapshot_id 边界内重建，完成后替换绑定缓存与 cursor |
| 409 / reset_required | 保留当前 UI 缓存，后台启动全量重建；重建成功后原子切换 |
| 410 cursor_expired | 旧 cursor 失效，触发全量重建，不把它当普通网络失败 |
| 401 | 走登录失效流程，清理账号内存投影 |
| 403 | 按当前权限收缩可见集合，不能使用旧 cursor 继续扩展访问 |
| 网络超时 / 5xx | 保留已知缓存与旧 cursor，按退避重试，不清空可用会话 |
| schema 不支持 | 停止应用变更，保留受控缓存状态并提示升级/重试，不按未知字段猜测类型 |

### 30.4 全量重建触发条件

以下条件允许或要求全量重建：

1. 当前账号首次使用统一 Manifest，尚无 cursor。
2. 客户端 schema_version 不兼容或服务端返回 reset_required。
3. 服务端明确返回 cursor_expired / 410。
4. 本地 binding 缓存解码失败、校验失败或发现无法恢复的 revision 断层。
5. 账号切换后加载的是新账号，不能继承旧账号 cursor。
6. 开发/灰度迁移期间由受控 feature flag 指定一次性重建。

以下场景不应直接全量重建：

- 普通网络超时、单次 5xx、下拉刷新重复点击。
- 单个医院 context 请求失败。
- 单条 Thread 缺失 ChatMessage 或头像资料。
- 患者切换筛选、搜索文本、置顶或隐藏偏好。

全量重建期间继续显示当前账号的上次可用列表；只有完成快照校验和原子替换后才更新 UI。不得先清空列表再等待全量网络返回。

### 30.5 客户端持久化与原子性

建议新增账号级同步状态：

~~~text
UnifiedConversationManifestSyncState
- accountID
- schemaVersion
- appliedCursor
- activeSnapshotID (optional)
- lastSuccessfulSyncAt
- lastErrorCode (optional)
- needsFullRebuild
~~~

落地规则：

1. Manifest binding 缓存与 appliedCursor 在同一持久化事务或等价提交边界内更新；不能先推进 cursor 再在崩溃后丢失 changes。
2. delta 分页时仅在所有页成功合并后提交最终 next_cursor；中断时下次从上一个已提交 cursor 重试，依靠 binding_revision 幂等。
3. snapshot 重建写入临时命名空间或事务；完成后原子替换旧 binding 集合，防止列表短暂为空。
4. delete change 必须和对应 binding_revision 一起保存，防止旧 upsert 回包把已撤权 Thread 恢复。
5. cursor 不存入 UserDefaults 的全局未命名键；必须按 accountID 命名空间隔离并在退出时清理。
6. 隐藏偏好、置顶、ChatThread 与消息正文使用自己的存储生命周期；Manifest 全量重建不等于清空这些本地事实，但 delete/撤权 reason 可触发定向安全清理。

### 30.6 触发时机与 single-flight

| 触发源 | 默认动作 |
| --- | --- |
| 进入消息分段 | 缓存首屏后启动一次 delta；无 cursor 则 snapshot |
| App 从后台回到前台 | 若超过刷新阈值或有推送提示，启动 delta |
| 收到消息/服务状态推送 | 推送去重后启动 delta，不直接信任 payload 变更类型 |
| 下拉刷新 | 请求立即 delta；复用同一 single-flight，不并行重复拉取 |
| 医院目录创建/续聊成功 | 触发轻量 delta 或写入已验证 binding，再由后续 delta 校验 |
| 账号登录/切换 | 取消旧任务；新账号按自身 cursor 或 snapshot 启动 |
| cursor 失效/协议重置 | 调度一次 snapshot，期间禁止并行 delta |

UnifiedConversationRefreshCoordinator 是唯一同步入口。所有触发源只提交 reason，不直接各自调用 Manifest API 或修改 cursor。

### 30.7 服务端实现要求

- cursor 必须是不透明、不可伪造、账号绑定的服务端令牌，客户端不得构造或解析业务含义。
- 服务端需保证同一 snapshot_id 分页结果一致，且最终 next_cursor 代表快照完成后的安全继续点。
- delta 必须包含 delete / permission_revoked / binding_changed 等收缩事件，不能只返回新增和更新。
- hospital_care 与未来 telemedicine 的业务变更应写入统一 Manifest 变更流；不要求 iOS 轮询多个业务列表寻找变化。
- binding_revision 与变化日志应具有事务一致性：业务绑定提交成功后才能对 Manifest 可见。
- 服务端保留 cursor 历史窗口；过期时明确返回可识别错误，不返回部分错误数据冒充完整 delta。
- 对分页、并发和重试设置合理上限与速率保护，防止恶意枚举账号会话关系。

| 工程 | 文件/目录建议 | 落地内容 |
| --- | --- | --- |
| SparkService | 统一 Manifest API 与同步服务 | snapshot/delta、cursor、snapshot_id、change log、reset 语义和账号权限过滤 |
| SparkService | hospital_care / 后期 telemedicine | 业务变更事务中写入 Manifest change；提供递增 binding_revision |

### 30.9 验收标准

- 首次账号同步获取完整 Manifest 快照，后续刷新优先使用 cursor delta。
- 同一变更重复到达不会生成重复卡片或覆盖更高 revision。
- delete / permission_revoked 变更可通过 delta 及时移除列表、搜索 token、未读与身份投影。
- cursor 失效、schema reset 或缓存损坏时，在保留旧 UI 的情况下完成全量重建。
- 网络失败不会清空可用缓存或错误推进 cursor。
- 全量重建和增量同步不会与下拉刷新、推送、前后台切换并行重复执行。
- 账号切换后，旧账号 cursor、回包、快照和 binding 不会污染新账号。
- 线上问诊接入只需写入同一 change log，即可被现有客户端同步与显示。

## 31. Q18 已确认：医疗服务暂停或下架时历史可读，禁止继续咨询

### 31.1 产品口径

院内医生智能体下架、暂停、结束服务或不再接受新咨询时，患者已授权的历史 Thread 仍保留在统一消息列表中。患者可以进入会话查看已经同步且当前仍有权读取的历史消息；会话输入区禁用，不能再发送新消息、触发 AI 回复、发起知识库同步或把会话降级为普通 AI。

这是“服务不可继续”状态，不是“患者无权查看”。只有服务端明确返回 member_access_revoked、account_access_revoked、permission_revoked 或等价 delete/revoke 事件时，客户端才从列表、搜索、未读聚合、身份缓存和可访问本地内容中移除该会话。

### 31.2 服务状态分层

| Manifest 状态/原因 | 列表是否保留 | 历史是否可读 | 是否可发送 | 卡片主状态 | 会话页行为 |
| --- | --- | --- | --- | --- | --- |
| active | 保留 | 是 | 是 | AI 服务中 | 正常会话 |
| doctor_taken_over | 保留 | 是 | 是，发送给当前接管医生；AI 不自动回复 | 医生接管中 | 复用既有接管逻辑 |
| ended | 保留 | 是 | 否 | 服务已结束 | 历史只读，输入禁用 |
| suspended | 保留 | 是 | 否 | 服务暂停 | 历史只读，输入禁用 |
| agent_unpublished / agent_offline | 保留 | 是 | 否 | 智能体暂不可用 | 历史只读，输入禁用 |
| hospital_service_unavailable | 保留 | 是 | 否 | 医院服务暂不可用 | 历史只读，输入禁用 |
| consultation_completed（未来问诊） | 保留 | 是 | 否，除非后续业务开放追问 | 问诊已结束 | 历史只读 |
| permission_revoked / member_access_revoked | 不保留 | 否 | 否 | 不展示 | 清理可访问投影并退出详情 |
| binding_deleted / thread_deleted | 不保留 | 按服务端删除原因 | 否 | 不展示 | 终止当前详情并受控返回 |

服务端应返回受控 status code 与患者可见 display reason；客户端不根据中文文案、HTTP 错误说明或医生资料缺失猜测“已下架”。

### 31.3 列表与会话页交互

1. 不可继续的医疗会话仍按 D-006/D-010 正常参与混排、筛选、搜索与置顶；卡片显示一个最高优先级的服务状态。
2. 点击卡片后进入同一 ChatView，但以 readOnlyServiceState 渲染：保留历史、隐藏或禁用输入框发送、附件和新建服务操作。
3. 禁用提示需写明原因，例如“该医生智能体当前已结束服务，您仍可查看历史咨询记录”。不得使用模糊的“发生错误”。
4. 不在会话页自动弹出普通 AI 接续、重新挂号、切换医生或线上问诊创建入口；避免在服务边界不明时替患者做医疗路径决策。
5. 患者仍可从院内就诊目录自行选择其他可用医生智能体；该行为创建/续聊的是另一条真实服务 Thread，不会重启已结束历史 Thread。
6. 已结束或暂停会话若后来被服务端恢复为 active，Manifest upsert 更新状态后卡片和会话页恢复发送能力；恢复不创建新 Thread，不改变历史消息。
7. 医生接管中不是只读状态：沿用既有确认，患者可发送消息，AI 不自动回复，取消接管后才恢复 AI 回复。

### 31.4 缓存、权限与本地数据清理

- ended、suspended、agent_unpublished 等非撤权状态保留当前账号已缓存的历史消息，后台不再尝试同步新知识库或生成新 AI 回复。
- permission_revoked 等撤权状态优先于缓存优先策略：Manifest delete/撤权确认后，立即从统一投影、搜索 token、未读聚合和医院 scope 中剔除。
- 需要清除多少本地消息正文、附件、知识库离线快照和向量缓存，必须由服务端 delete reason 明确指示；不可对“服务结束”误执行不可恢复的本地清理。
- 当前会话正打开时收到撤权：停止发送、取消未完成任务、清除受限内存内容，展示受控“已无权访问此会话”提示并返回消息列表；不得继续显示新缓存或将其路由普通 AI。
- 当前会话正打开时收到服务暂停：保留已加载历史，立即切 read-only，不强制退出。

### 31.5 服务端契约要求

1. Manifest upsert 必须返回明确 service_status 和可选患者展示原因码；delete 必须返回删除/撤权 reason。
2. 医院智能体发布状态、医院服务状态、医生接管状态和成员授权变更都应写入统一 Manifest change log。
3. 服务端详情接口在会话打开与发送时必须再次校验状态；不能只依赖列表曾经收到的 active 状态。
4. 发送接口应返回稳定业务错误码，例如 conversation_read_only、agent_unavailable、member_access_revoked，而非让客户端解析错误文本。
5. 线上问诊后期需以同一状态模型表达 completed、cancelled、closed、permission_revoked，避免独立的患者端例外逻辑。
6. 状态由 active 变为只读时，不应删除历史 ChatMessage 或覆盖 Thread.title；变化仅影响当前可发送性与患者可见状态。

### 31.6 客户端落地方案

1. UnifiedConversationListItem 增加结构化 serviceStatus 与 isReadOnly，不由 View 解析服务端字符串。
2. ChatView 在加载 HospitalConversationScope/Manifest 后统一计算 canRead、canSend、shouldUseAIReply；普通 AI、医生接管、只读医疗会话分别走明确状态。

## 32. Q19 已确认：本地“新建 AI 对话”创建的 Thread 可立即按普通 AI 显示

### 32.1 产品口径

患者在消息分段点击“＋”后，客户端通过已确认的普通 AI 创建流程生成的 Thread，具有可信的创建来源。该 Thread 即使尚未被服务端 Manifest 首次回传、设备离线或后台同步尚未完成，也可以立即在统一消息列表中以 ordinary_ai 身份显示、发送和排序。

此规则只适用于本地明确由“新建 AI 对话”入口创建的 Thread。任何从旧缓存、跨设备同步、推送、深链、医院目录、未来线上问诊或无法确认来源的 Thread，在 Manifest/context 未确认前都不能默认显示为普通 AI。

### 32.2 分类优先级

~~~text
1. Manifest 最新 binding（最高优先级）
2. 可验证本地创建来源：manual_ordinary_ai
3. hospital / telemedicine 已验证详情 context
4. unknown（中性待确认，禁止猜测）
~~~

Manifest 返回 hospital_agent 或 telemedicine binding 时，服务端事实优先于本地普通创建标记。此类“本地普通来源与服务端医疗绑定冲突”必须记录诊断信息并重新校验，不得静默把会话混合为两种类型。

### 32.3 创建来源模型

建议建立独立、账号级的 ThreadCreationProvenance，而不是用标题、scenario、头像或首条消息内容推断：

~~~text
ThreadCreationProvenance
- accountID
- threadID
- origin = manual_ordinary_ai | hospital_agent_flow | telemedicine_flow | imported | unknown
- createdAt
- sourceVersion
~~~

规则如下：

| origin | Manifest 未到达时的列表类型 | 是否允许发送 | 说明 |
| --- | --- | --- | --- |
| manual_ordinary_ai | ordinary_ai | 是 | 仅消息页＋及等价已验证普通 AI 创建路径可写入 |
| hospital_agent_flow | 不以 provenance 直接显示普通 AI | 按医院 context/Manifest 确认 | 继续使用医院创建返回的真实绑定 |
| telemedicine_flow | 不以 provenance 直接显示普通 AI | 按问诊 binding 确认 | 后期接入 |
| imported / unknown | unknown | 否 | 展示与打开策略由下一题确认 |

ThreadCreationProvenance 是过渡和安全辅助事实，不替代服务端 Manifest：

- Manifest 成功确认后，投影以 Manifest 为准。
- 普通 AI Manifest 记录可不存在或延迟到达，不影响 manual_ordinary_ai 的正常本地使用。
- provenance 必须按 accountID 隔离，在账号退出和真正 Thread 删除时清理。
- 不允许任意页面、迁移脚本或测试数据随意写 manual_ordinary_ai；写入点必须限定为已验证的普通 AI 创建 use case。

### 32.4 业务流程

~~~text
消息页点击“＋”
        ↓
普通 AI 创建 use case 成功创建 ChatThread
        ↓
原子写入 ThreadCreationProvenance.manual_ordinary_ai
        ↓
立即投影为 ordinary_ai 并打开 ChatView
        ↓
后台 Manifest delta 到达
        ↓
普通 binding / 无医疗 binding → 保持 ordinary_ai
医疗 binding 冲突 → 停止普通发送，进入受控校验与诊断
~~~

对比：医院目录创建会话时，服务端创建接口应直接返回 agent_id、hospital_id、member_id 和 thread_id；客户端写 hospital_agent_flow 并尽快写入/刷新 Manifest，而不是把新会话暂时显示成普通 AI。

### 32.5 缓存、离线与异常边界

1. 离线创建普通 AI Thread 后，列表立即显示普通 AI 卡片；消息发送依旧遵循现有离线/失败队列语义。
2. App 重启后，只要 provenance 与 accountID 匹配且 Thread 未删除，本地普通 AI Thread 仍可安全显示，不要求每次等待 Manifest。
3. Manifest 拉取失败不会隐藏已验证 manual_ordinary_ai Thread；但不会把 unknown Thread 借此提升为普通 AI。
4. Manifest delete / permission_revoked 若明确指向该 Thread，优先执行撤权/删除安全规则，不能以本地 provenance 继续显示或发送。
5. Manifest 返回与 provenance 冲突的医疗 binding 时，保留本地历史供受控校验，不继续按 ordinary_ai 自动回复或使用普通知识库；上报 accountID、threadID、origin、bindingRevision 的脱敏诊断事件。
6. 不以 ChatThread.scenario=chat、默认标题、无 memberID、头像图标或消息作者角色作为 manual_ordinary_ai 的替代判定条件。

### 32.6 客户端落地方案

1. 普通 AI createThread 成功的同一事务中写入 ThreadCreationProvenance.manual_ordinary_ai；失败时回滚或清理 provenance，避免孤儿记录。
2. UnifiedConversationProjector 先读取最新 Manifest binding；未命中时仅对白名单 provenance 输出 ordinary_ai，其余输出 unknown。
3. ChatListViewModel 不再用“Manifest 缺失 = 普通对话”的默认分支。
4. ChatView 对 manual_ordinary_ai 可沿用普通模型、引导卡和发送逻辑；对 unknown 则使用下一题确认的受控路由。
5. HospitalCare 的 ResolveOrCreateHospitalConversationUseCase 创建成功后，应写入医院绑定缓存或触发 Manifest 同步，确保医院 Thread 尽快脱离 unknown。
6. ThreadCreationProvenanceStore 应有账号切换清理、Thread 删除清理、过期迁移和测试注入能力，不能使用无命名全局 UserDefaults 键。

## 33. Q20 已确认：来源不明 Thread 显示“正在确认会话信息”，发送等待确认

### 33.1 产品口径

当客户端存在一个 Thread，但既没有最新 Manifest binding，也没有可验证的 manual_ordinary_ai 创建来源或已确认医院/问诊 context 时，该 Thread 的 conversationKind 为 unknown。unknown Thread 不被隐藏、不被默认归类为普通 AI，也不被放入“AI 对话”“医生智能体”或“线上问诊”任一具体筛选。

在“全部”筛选中，unknown Thread 以中性卡片显示“正在确认会话信息”。患者可以点击卡片尝试打开已有历史；客户端必须先发起 Manifest 增量同步与适当的详情/权限校验。确认前禁止发送消息、上传附件、触发 AI 回复、加载医院知识库、执行线上问诊操作或标记已读。

| 头像 | 使用中性会话/加载占位图，不使用 AI、医生或医院头像 |

### 33.3 打开与确认流程

~~~text
患者点击 unknown 卡片
        ↓

        ↓

        ↓

        ├─ ordinary_ai → 恢复普通 ChatView 能力
        ├─ delete / revoke → 终止打开并执行安全清理
        └─ 仍 unknown / 网络失败 → 保持只读确认态，后续策略见下一题
~~~

流程约束：

1. 未确认前 ChatView 只展示“正在确认会话信息”，不立即插入普通引导卡、医生身份卡或线上问诊服务卡。
2. 本地已有历史消息时，患者可在确认流程内尝试查看；最终是否展示正文必须经过当前账号、成员和服务端可见性校验。校验失败时不得继续用旧缓存绕过权限。
3. D-016 已读动作延后到类型、成员和读取权限确认成功、消息实际可读之后；点击 unknown 卡片本身不能清未读。
4. Manifest 或详情校验确认类型后，同一 threadID 的卡片原位切换为正式类型；不得关闭页面、创建新 Thread 或要求患者重新点击。
5. 若确认结果为医院/问诊会话，必须走对应 context/binding 校验；不能仅因 Manifest kind 已知就跳过详情级权限检查。
6. 若确认结果为 ordinary_ai，但没有 manual provenance，服务端 Manifest 应作为普通 AI 类型事实；此时才开放普通发送和既有功能。

### 33.4 与缓存、未读和安全的关系

- unknown 不是错误类别，而是同步中的受控安全状态。缓存优先策略允许先显示卡片，不允许先假定业务能力。
- unknown Thread 在“全部”筛选可见并计入未读，是为了不让患者错过可能的重要新消息；一旦服务端确认撤权/删除，立即从列表、未读和搜索中清除。
- unknown 不生成搜索 type token，不命中医生、智能体、医院或线上问诊筛选；可按 Thread 标题参与已确认的标题搜索。
- 不执行医院知识库 manifest 同步、本地向量检索、医生接管状态恢复或未来线上问诊订单操作，直到类型确认。
- 推送或深链命中 unknown Thread 时，先进入同一受控确认流程；不得直接启用普通消息发送。
- current account 与 Thread 所属成员无法确认时，禁止显示敏感成员名称、医生身份或新增消息正文。

## 34. Q21 已确认：unknown Thread 长时间无法确认时保留只读卡片并允许重试

### 34.1 产品口径

unknown Thread 的确认请求因网络、服务端暂时异常、旧数据迁移或 Manifest 延迟而未完成时，客户端不自动隐藏该 Thread，也不把它超时降级成 ordinary_ai。卡片从“正在确认会话信息”转为“暂无法确认，可重试”，继续在“全部”筛选中保留。

该状态是只读、不可发送的安全降级：患者仍能看见会话存在、最后已知标题/摘要/时间和未读提示，并可主动触发重试；任何 AI、医院智能体、线上问诊、知识库和附件操作保持禁用，直到服务端确认真实类型、成员和权限。

### 34.2 状态转换

~~~text
unknown + 首次确认请求
        ↓
确认中（正在确认会话信息）
        ├─ resolved → ordinary_ai / hospital_agent / telemedicine 正式卡片
        ├─ revoked/delete → 安全清理并移除
        └─ 超时/网络/5xx/暂时异常 → 暂无法确认，可重试（只读）
                                      ↓
                              后台退避或患者点击重试
                                      ↓
                                 回到确认中
~~~

unknown 不因时间阈值改变类型。状态转换只能由 Manifest upsert、医院/问诊详情级校验、Manifest delete/revoke 或明确的同步错误驱动。

| 发送/附件/AI | 禁用 | 禁用 |
| 置顶 | 保留既有状态 | 保留既有状态 |
| 移除医疗会话 | 未确认类型时不显示医疗专属移除操作 | 同样不显示，避免误用类型规则 |

患者点击“重试确认”时，只重试该 Thread 关联的 Manifest delta/详情确认任务或复用账号级 single-flight；不清空整个消息列表、搜索文本、筛选条件和其他 Thread 缓存。

进入 unknown 会话页后：

1. 顶部显示“正在确认会话信息”或“暂无法确认”的受控横幅。
2. 输入区、附件、快捷问题、知识库同步和医生/问诊服务操作均禁用。
3. 若当前账号和本地缓存策略允许展示历史，历史仅以只读方式呈现；无法通过当前授权校验时，展示“暂时无法加载会话内容”，不绕过权限读取正文。
4. 重试成功后原位更新为真实类型和能力，不丢失当前阅读位置；重试失败继续只读，不弹出反复打断的错误框。

### 34.4 重试、退避与网络策略

- 首次确认失败后由 UnifiedConversationRefreshCoordinator 使用指数退避调度后台重试，并设置合理上限，避免弱网下无限请求。
- 患者手动重试可在冷却窗口内合并到同一 in-flight 请求；按钮显示“正在重试”，防止重复点击。
- 进入消息分段、下拉刷新、App 回前台、收到对应 threadID 推送时，可提前唤醒一次确认，但仍受账号级 single-flight 和速率限制保护。
- 网络不可用时显示“网络不可用，请检查网络后重试”；服务端 5xx 显示“服务暂不可用，可稍后重试”；不得暴露 HTTP 原文、内部错误码或绑定字段。
- Manifest schema 不兼容或 cursor reset 时，优先执行 D-020 的全量重建；重建期间 unknown 卡片保持只读，不直接隐藏。
- 服务端明确 delete/revoke 后停止全部重试并立即安全清理，不能因本地 retry 队列再次恢复该会话。

### 34.5 未读、搜索、筛选与缓存

1. unknown 卡片只在“全部”筛选显示；在具体类型筛选中隐藏但不删除本地状态。
2. unknown 仍按 D-015 计入账号级未读角标，防止患者错过潜在重要回复；无法确认不等于消息不存在。
3. 不因重试、超时或状态文案切换清未读；D-016 的已读确认仅在权限与类型 resolved 后执行。
4. 仅可用 Thread 标题参与 D-013 搜索；不能用摘要正文、推测医院/医生或内部 ID 搜索 unknown。
5. 本地缓存和 retry 状态按 accountID + threadID 隔离；账号退出、Thread 真删除、权限撤回时清理。
6. unknown 缓存不应无限增长：当服务端已确认不存在且无本地未同步任务时，按明确 delete reason 清理；不能以时间过期为由静默删除仍可能可读的历史。

### 34.6 客户端落地方案

1. UnifiedConversationListItem 增加 confirmationStatus：resolving、retryableFailure、resolved、revoked。
2. UnifiedConversationProjector 对 retryableFailure 输出中性卡片与只读 capability，不输出 ordinary_ai 兜底。
3. UnifiedConversationRefreshCoordinator 支持按 threadID 的确认请求、退避、手动重试合并和 revoke 取消。
4. ChatConversationListPage 在卡片或行级辅助操作展示“重试确认”；不把重试入口放入普通 AI 发送按钮位置。
5. ChatView 根据 confirmationStatus 显示横幅和只读输入态；确认成功后由状态驱动原位更新。
6. 监控记录 unknown 的持续时长、重试次数、最终 resolved/revoked 比例和错误类别，用于发现 Manifest 漏数或迁移问题，但日志不得包含消息正文或敏感身份资料。

### 34.8 验收标准

- 未读数、置顶、标题和可允许的只读历史在确认失败期间保持一致，不暴露未授权内容。

## 35. Q22 已确认：不迁移既有旧 Thread，旧 Thread 永久保持确认中

### 35.1 产品口径

本期不对历史既有 ChatThread 做服务端 Manifest 回填，也不在 iOS 升级时批量把旧 Thread 标注为 ordinary_ai。统一 Manifest 只覆盖功能上线之后新创建的普通 AI 会话，以及后续由医院医生智能体/线上问诊服务产生的真实业务绑定。

在上线前已经存在、且没有新 Manifest binding 或可信 manual_ordinary_ai provenance 的 Thread，永久归为 unknown：在“全部”筛选中保留中性确认卡片，允许按 D-023/D-024 尝试只读访问与重试确认，但不开放发送、AI、知识库、医疗服务、类型筛选归类或已读确认。

这是一项明确接受的历史体验边界：优先保证类型与医疗权限不被错误猜测，而不是把旧历史完整接入新统一消息能力。

### 35.2 上线分界规则

~~~text

        ↓

        ↓
上线前既有 Thread
        ↓
没有有效 Manifest / provenance → 永久 unknown / 只读确认卡片
~~~

服务端不需要扫描、推断或批量写入旧普通 ChatThread。客户端也不得把“创建时间早于上线日期”“没有医院 scope”“标题像普通聊天”“消息来自 AI”等信号作为迁移判据。

### 35.4 数据、缓存与版本边界

1. Manifest schema 不增加“legacy ordinary auto-fill”或客户端迁移开关；新 Manifest 只流转新业务变化。
2. 客户端新增 feature rollout version / manifestEligibleAt 仅用于记录何时开始期待新 Thread 有 Manifest/provenance，不能用于给旧 Thread 赋类型。
3. 旧 Thread 的 ChatThread、ChatMessage、标题、置顶和本地历史继续由现有存储维护；新 Manifest 缓存不覆盖或删除它们，除非服务端后续明确 delete/revoke。

## 36. Q23 已确认：永久 unknown 的旧 Thread 允许直接删除

### 36.1 产品口径

对于上线前遗留、无 Manifest、无可信创建来源且按 D-025 永久维持 unknown 的旧 Thread，患者允许执行“删除会话”。这是实际 Thread 删除，不是 D-011 医疗会话使用的“从消息列表移除/隐藏”。

此决定只作用于**永久 legacy unknown**，不作用于：

- 已由 Manifest 确认的 hospital_agent 或 telemedicine。
- 已由 Manifest 或可信创建来源确认的 ordinary_ai。
- 正在确认中的新 Thread、医院新建会话、线上问诊新建会话。
- 已显示为服务暂停/结束但仍有授权历史的医疗会话。

产品接受的边界是：旧 Thread 即使可能包含历史医疗沟通，也不会进行自动迁移或身份猜测；患者可选择按既有真实删除语义清理它。删除后不提供“自动恢复旧会话”的假承诺。

### 36.2 删除交互与数据语义

| 项目 | 最终规则 |
| --- | --- |
| 可见操作 | 长按/滑动中的“删除会话”，不显示“从消息列表移除” |
| 提示 | 沿用既有删除确认；明确“删除后将无法在本设备消息列表中查看此会话” |
| 删除实现 | 调用既有 deleteThreadUseCase / ChatThread 删除生命周期 |
| 数据效果 | 由既有 Thread 删除语义处理 ChatThread、消息投影、搜索 token、未读、置顶与本地缓存 |
| Manifest | 不为旧 Thread 创建 Manifest delete；它本来不在 Manifest 中 |
| 重试任务 | 取消该 threadID 的 unknown 确认、退避与详情加载任务 |
| 恢复 | 不提供专用恢复入口；后续仅可按既有同步事实重新出现，且必须受删除墓碑保护 |

“直接删除”不等同于绕过确认弹窗。若当前普通 Thread 删除流程已有系统确认或可撤销交互，可复用；关键是删除的业务语义必须是实际删除，而不是仅写入消息列表可见性偏好。

### 36.3 删除一致性与防复活

1. 删除成功后立即从 UnifiedConversationProjector 输入集合中移除该 Thread，并同步扣减未读角标、删除搜索 token 和置顶信息。
2. 必须复用或补齐既有 isDeleted/deletedAt 的删除墓碑语义，避免旧 Chat 同步、旧推送或 App 重启后把已删除 legacy Thread 重新插回列表。
3. 如果本地消息库支持软删除，同步层继续传递删除墓碑；如果支持服务端删除，则遵循当前普通 Chat 的已有协议，本文档不新增医疗服务端删除接口。
4. 删除期间取消 Manifest retry、医院 context 请求、附件/知识库本地任务和未完成已读回执；任何延迟回包都必须检查 Thread 是否已删除。
5. 已删除 legacy Thread 不会因 D-012 新消息自动恢复：D-012 只针对已隐藏的**医疗类可见 Thread**，不覆盖真实删除。
6. 账号切换后删除墓碑仍按账号隔离；账号 A 删除旧 Thread 不影响账号 B 的本地数据。

| 会话业务类型 | 服务端 Manifest；可信本地普通创建来源仅作临时白名单 | 从标题、头像、scenario 或消息内容猜测 |

| 线上问诊详情权限 | 后期问诊详情/发送接口最终校验 | 仅信任订单展示字段 |
| 患者列表隐藏 | accountID + threadID 可见性偏好 | isDeleted / 医院 scope |
| 真实删除 | 既有 ChatThread 删除墓碑 | 医疗会话隐藏偏好 |
| 类型筛选 | 纯 UI MessageListTypeFilter | 修改 Thread 或服务端业务状态 |

## 39. 服务端落地方案

### 39.1 新增能力边界

服务端需要新增的是“统一会话业务绑定与 Manifest 同步”能力，不需要新增第二套消息表，不需要把 ChatMessage、知识库正文或病历复制进 Manifest。

建议将其组织为 chat/conversation 领域的独立模块或现有 chat 模块下的子域，由 hospital_care 与后期 telemedicine 通过适配器注册业务绑定。

~~~text
chat / conversation_manifest
├── models.py          # 账号可见绑定、版本、变更日志（建议）
├── services.py        # 绑定写入、权限过滤、delta/snapshot
├── api.py             # Manifest API
├── serializers.py     # 严格 schema 输出
├── permissions.py     # 账号、成员、医院、问诊授权
└── adapters/
    ├── ordinary_ai.py
    ├── hospital_care.py
    └── telemedicine.py（后期）
~~~

### 39.2 建议服务端数据模型

~~~text
ConversationManifestBinding
- id
- account_id
- thread_id (UUID)
- conversation_kind
- member_id (nullable only for legacy-compatible ordinary_ai)
- service_status
- identity_payload (最小、可版本化 JSON；禁止消息正文)
- binding_revision (单 Thread 单调递增)
- is_active / deleted_at
- created_at / updated_at

ConversationManifestChange
- id / sequence
- account_id
- binding_id / thread_id
- op = upsert | delete
- binding_revision
- payload_snapshot (最小投影)
- reason_code (delete 时必填)
- created_at
~~~

关键数据库约束：

- active binding 的唯一约束为 account_id + thread_id。
- 同一 thread_id 不能同时存在两个 active conversation_kind。
- binding_revision 在单个 thread_id 更新时递增，变更写入与业务绑定变更处于同一数据库事务。
- change sequence/cursor 必须按 account_id 可安全消费；游标为不透明令牌，不把数据库 sequence 直接暴露给客户端。
- 索引至少覆盖 account_id + updated_at/sequence、account_id + thread_id、thread_id + binding_revision。

### 39.3 Manifest API 契约

建议接口：

~~~text
GET /api/v1/chat/conversations/manifest/?cursor=<opaque>&limit=<n>
Authorization: 当前登录账号
~~~

服务端处理顺序：

1. 认证当前账号。
2. 解析并校验 cursor 是否属于该账号、schema 是否兼容、是否过期。
3. 根据账号当前可见成员、医院服务关系和线上问诊参与方关系过滤绑定。
4. 返回 snapshot 或 delta changes；delete/revoke 必须作为 change 返回。
5. 输出最小 identity payload 与受控 service_status，不输出消息正文、病历、知识库或审计数据。
6. 在分页结束后给出可提交的 next_cursor。

状态与业务错误码建议：

~~~text
manifest_cursor_expired
manifest_reset_required
manifest_schema_unsupported
conversation_read_only
conversation_permission_revoked
conversation_binding_conflict
agent_unavailable
telemedicine_unavailable
~~~

### 39.4 业务模块写入要求

| 事件来源 | 必须写入 Manifest 的变化 |
| --- | --- |
| 新建普通 AI Thread（后期服务端已知时） | ordinary_ai upsert；客户端本地 provenance 可先兜底 |
| 医院医生智能体创建/续聊 | hospital_agent upsert，含 hospital/doctor/agent/member 身份引用 |
| 医生接管/取消接管 | service_status upsert |
| 智能体发布、下架、暂停、恢复 | service_status upsert |

| 医院服务停用 | read-only status 或 delete，按业务授权决定 |
| 线上问诊创建/接诊/结束/取消 | telemedicine upsert |
| Thread 真删除 | delete(thread_deleted) |

- 不扫描、不回填、不按内容推断旧 ChatThread，遵守 D-025。

### 41.3 Swift：统一投影伪代码

~~~swift
func project(
~~~

### 41.4 Swift：排序、筛选与搜索伪代码

~~~swift
func visibleItems(
    all: [UnifiedConversationListItem],
    filter: MessageListTypeFilter,
    query: String
) -> [UnifiedConversationListItem] {
    let typeMatched = all.filter { item in
        filter.matches(item.conversationKind)
    }
    let searched = typeMatched.filter { item in
        item.normalizedSearchTokens.matches(query)
    }
    return searched.sorted {
        if $0.isPinned != $1.isPinned { return $0.isPinned }
        if $0.latestMessageAt != $1.latestMessageAt {
            return $0.latestMessageAt > $1.latestMessageAt
        }
        return $0.threadID.uuidString < $1.threadID.uuidString
    }
}
~~~

unknown 项仅由 all 筛选匹配；搜索 token 只来自已允许的 Thread 标题，不包含消息正文或猜测出的医疗身份。

### 41.5 Swift：Manifest 增量应用伪代码

~~~swift
func applyDelta(
    response: UnifiedConversationManifestResponse,
    accountID: Int64
) async throws {
    try validate(response)
    try await store.transaction(accountID: accountID) {
        for change in response.changes {
            let current = loadBinding(change.threadID)
            guard current?.bindingRevision ?? -1 < change.bindingRevision else {
                continue
            }
            switch change.operation {
            case .upsert:
                try save(change.asBinding())
            case .delete:
                try saveDeleteTombstone(change)
                try removeIdentityAndSearchTokens(change.threadID)
            }
        }
        if response.hasMore == false {
            try saveCommittedCursor(response.nextCursor)
        }
    }
}
~~~

若 hasMore=true，不能提交最终 cursor；任何中途失败从上一个已提交 cursor 重试。delete 的 revision 必须持久化，防止旧 upsert 回包复活撤权会话。

任何深链或推送必须先从 Manifest/缓存解析 RouteDescriptor。禁止 URL 参数直接决定 hospitalID/agentID 并绕开当前账号与成员授权。

### 42.3 本地持久化命名空间

| 存储 | 推荐键/唯一键 | 清理时机 |
| --- | --- | --- |
| Manifest binding | accountID + threadID | delete/revoke、账号退出、数据损坏重建 |
| Manifest sync state | accountID | 账号退出、schema 重置 |
| 创建来源 | accountID + threadID | Thread 删除、账号退出 |
| 医疗会话隐藏偏好 | accountID + threadID | 新可见消息恢复、撤权、Thread 删除、账号退出 |
| legacy 删除墓碑 | accountID + threadID | 遵循既有普通 Chat 删除生命周期 |
| 搜索 token | accountID + threadID | binding/身份变化、隐藏、撤权、删除、账号退出 |
| 成员展示缓存 | accountID + memberID | 授权撤回、账号退出、资料刷新 |

所有本地表/Key 必须有 schema version 和迁移策略；禁止使用账号无关的单例内存字典保存医疗绑定或成员名称。

## 43. 异常与降级矩阵

| 场景 | 消息列表 | 进入会话 | 发送 | 同步/清理 |
| --- | --- | --- | --- | --- |
| Chat 同步失败，有缓存 | 显示缓存与轻提示 | 可按既有离线策略打开 | 依既有发送队列；不伪造成功 | 后台退避 |
| Manifest 同步失败，有缓存 binding | 显示已知类型；不把医院降级普通 AI | 医疗详情仍校验 | 按详情校验结果 | 保留旧 cursor，重试 |
| Manifest 无缓存/未知 Thread | 中性确认卡片 | 受控确认页 | 禁止 | delta/详情确认 |
| cursor 过期 | 保留旧 UI | 不打断已打开会话 | 由详情校验 | 后台 snapshot 重建 |
| schema 不兼容 | 中性或受控缓存态 | 禁止未确认能力 | 禁止 | 停止应用并提示升级/重试 |
| 医院服务暂停 | 卡片保留状态 | 历史只读 | 禁止 | status upsert |
| 医生接管 | 卡片“医生接管中” | 正常 | 允许，AI 不回 | status upsert |
| 智能体恢复 | 同一行状态更新 | 同一 Thread 恢复 | 允许 | status upsert |
| 成员/账号撤权 | 移除卡片/未读/搜索 | 退出并清理 | 禁止 | delete/revoke 原子处理 |
| 医疗会话被隐藏后新消息 | 自动恢复并排序 | 可按状态打开 | 依状态 | 清除隐藏偏好 |
| legacy unknown 删除 | 移除并写墓碑 | 关闭详情 | 禁止 | 取消 retry，防复活 |
| 线上问诊未上线 | 筛选可见但空态 | 无假入口 | 不适用 | 不制造 DTO |

## 44. 测试与验收方案

### 44.1 单元测试

- UnifiedConversationProjector：Manifest 优先、普通 provenance 白名单、unknown 兜底、hide/delete/revoke、成员显示、身份缺失、revision 乱序。
- 排序与筛选：置顶区、时间稳定排序、全部/三类筛选、unknown 只在全部、搜索交集、正文不命中。
- 未读：多类型、多成员聚合、99+、打开后已读、新消息竞态、隐藏恢复、撤权清理。
- Manifest 同步：snapshot、多页 delta、重复 change、delete 覆盖旧 upsert、cursor 过期、崩溃恢复、账号隔离。
- unknown：确认成功、超时、手动重试、退避、撤权、legacy 永久 unknown、删除墓碑。
- 能力状态：普通 AI、医生接管、服务结束、恢复、权限撤回、线上问诊预留。

### 44.2 集成测试

| 场景 | 验证重点 |
| --- | --- |
| 从消息＋创建普通 AI | provenance 写入、即时可见、返回消息列表、无医院绑定 |
| 从院内就诊发起医生智能体 | 同一 threadID 出现在消息列表，医生身份与成员正确 |
| 医生接管/取消接管 | 卡片状态、AI 回复停启、发送能力正确 |
| 智能体暂停/恢复 | 历史只读、同 Thread 恢复、无普通 AI 降级 |
| 隐藏医疗会话后医生回复 | 自动恢复、未读与排序正确 |
| 家庭成员混合列表 | 成员标识、进入会话成员恢复、不修改全局当前成员 |
| Manifest 撤权 | 列表/搜索/未读/当前会话安全清理 |
| 冷启动弱网 | 缓存首屏、后台失败轻提示、不清空历史 |
| 账号切换 | cursor、绑定、成员、未读、隐藏偏好不串号 |
| 旧 Thread | 永久 unknown、不可发送、允许删除且不复活 |

### 44.3 UI/可访问性验收

- iPhone 小屏、横屏与 Dynamic Type 最大字号下，医生名、智能体名、Thread 标题、成员、状态、时间与未读不重叠。
- VoiceOver 正确朗读“会话对象、类型、服务状态、会话标题、最新消息、时间、未读”。
- 未读数字不是仅色彩区别；99+ 可识别。
- unknown、服务暂停、撤权和网络失败有明确患者文案，不暴露内部术语、HTTP 文本、UUID 或调试信息。
- 上下文菜单只展示该类型允许的操作，医疗类不出现编辑身份/删除会话，legacy unknown 不出现医疗隐藏操作。

## 45. 实施阶段与发布顺序

### 阶段 0：契约冻结与基线测试

1. 冻结 conversation_kind、service_status、identity、delete reason、cursor、revision 与 schema_version。

### 阶段 1：服务端 Manifest 最小闭环

1. 实现 account 级 Manifest snapshot/delta、cursor、binding_revision、delete/revoke。
2. hospital_care 新建/状态变化写入 binding change。
3. 普通 AI 新 Thread 允许客户端 provenance 先行；服务端后续可对新服务端已知 Thread 输出 ordinary_ai binding。
4. 开关控制，先不替换患者端现有普通对话列表。

### 阶段 2：iOS 数据层与投影层

1. 新增 Manifest Repository、Sync UseCase、Projector、RefreshCoordinator、provenance/visibility stores。
2. 接入缓存优先、single-flight、账号隔离、revision 合并和测试。
3. 在内部调试开关下输出统一列表诊断，不改变正式入口。

### 阶段 3：消息 UI 改造

1. “普通对话”文案改为“消息”。
2. 维持院内就诊默认和目录不变。
3. 接入统一混排、卡片、筛选、搜索、未读角标、＋、操作菜单和 unknown 状态。

### 阶段 5：未来线上问诊接入

1. 线上问诊模块实现真实 consultation_id + thread_id binding。
