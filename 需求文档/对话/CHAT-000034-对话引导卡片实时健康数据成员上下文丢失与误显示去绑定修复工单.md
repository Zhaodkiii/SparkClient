# CHAT-000034 对话引导卡片实时健康数据成员上下文丢失与误显示去绑定修复工单

## 工单类型

- 类型：缺陷修复 / 健康数据滑块成员上下文治理
- 优先级：P1
- 影响范围：对话引导卡片健康数据滑块
- 不在范围：健康科普问题生成、解析、兜底、持久化与点击发送流程
- 本工单阶段：问题分析与落地方案，不修改现有代码

## 问题描述

当前对话已经绑定成员，且该成员已经绑定 Apple Health 设备数据，但引导卡片在重新渲染或滑动切换后仍展示「去绑定」。

用户实际状态：

```text
thread.memberID = 2
成员 2 已绑定 Apple Health
HealthDataAccessGate(member=2) = granted
```

错误展示状态：

```text
运动数据：未授权 / 去绑定
身材管理：未授权 / 去绑定
饮食营养：未授权 / 去绑定
```

## 日志结论

现有日志已经足以确定问题，不需要先增加临时日志。

### 1. 会话成员和设备绑定状态正常

```text
新会话本地创建完成，thread=6A3993EF member=2
chat.guide.metrics.initial_access thread=6A3993EF member=2 granted=true reason=granted
```

说明：

- 新建线程已经成功绑定成员 `2`。
- 成员 `2` 的 Apple Health 绑定与授权检查通过。
- 问题不是成员未绑定、设备记录缺失或 HealthKit 未授权。

### 2. 使用正确成员读取时数据正常

```text
chat.guide.metrics.reload_start member=2 reason=task
chat.guide.metrics.page_access member=2 granted=true reason=granted
chat.guide.metrics.reload_done member=2 reason=task states=movement:ready,body:empty,nutrition:failed,medical:ready
```

说明：

- 使用 `member=2` 时运动数据为 `ready`。
- 医疗数据为 `ready`。
- `body:empty` 表示最近 90 天没有身材数据，不是授权失败。
- `nutrition:failed` 来自“没有查到任何营养摄入记录”，也不是绑定失败。

### 3. 消息更新后卡片成员变成 nil

```text
chat.guide.metrics.reload_start member=nil reason=task
chat.guide.metrics.page_access member=nil granted=false reason=no_binding
chat.guide.metrics.reload_done member=nil reason=task states=movement:unauthorized,body:unauthorized,nutrition:unauthorized,medical:empty
```

说明：

- 同一个对话中出现了使用 `member=2` 和 `member=nil` 的两次卡片刷新。
- 后一次 `member=nil` 将之前正确的实时数据覆盖为未授权状态。
- UI 展示「去绑定」是成员上下文丢失后的结果，不是设备绑定判断错误。

### 4. 滑动刷新持续使用错误成员

```text
chat.guide.metrics.page_changed section=body
chat.guide.metrics.reload_start member=nil reason=page_changed
chat.guide.metrics.page_access member=nil granted=false reason=no_binding

chat.guide.metrics.page_changed section=movement
chat.guide.metrics.reload_start member=nil reason=page_changed
chat.guide.metrics.page_access member=nil granted=false reason=no_binding
```

说明：

- 滑动刷新功能已经触发。
- 但刷新入口继续使用 `payload.memberID`，因此每次滑动都稳定读取 `nil`。
- 增加刷新次数无法解决问题，必须修正成员上下文来源。

## 根因分析

### 直接根因：实时滑块错误依赖消息 payload 的 memberID

当前页面刷新链路：

```text
ChatGuideMessageCardView.reloadMetricSections
  ↓
metricSectionsProvider(payload.memberID)
  ↓
ChatDetailViewModel.loadGuideMetricSections(memberID:)
  ↓
memberID == nil
  ↓
HealthDataAccessResult.noBinding(.appleHealth)
  ↓
运动 / 身材 / 饮食全部变成 unauthorized
```

健康滑块已经定义为“页面实时读取、不持久化”，但成员上下文仍来自持久化消息 payload。这个数据所有权不一致：

- 健康数据来源是当前线程绑定成员。
- 当前线程成员的权威来源是 `ChatThread.memberID`。
- `ChatGuideCardPayload` 是消息快照，主要承载科普问题状态。
- 消息快照不应成为实时健康数据的成员路由来源。

### 编解码根因：memberID 在统一 snake_case 解码策略下丢失

`ChatGuideCardPayload` 使用动态 `CodableKey`：

```swift
memberID = try container.decodeIfPresent(
    Int.self,
    forKey: .key("memberID")
)
```

项目统一解码器配置为：

```swift
decoder.keyDecodingStrategy = .convertFromSnakeCase
```

实际转换过程：

```text
Swift 编码键 memberID
  ↓ JSONEncoder.convertToSnakeCase
JSON 字段 member_id
  ↓ JSONDecoder.convertFromSnakeCase
动态解码键 memberId
```

当前代码查询的是 `memberID`，而解码容器实际持有的是 `memberId`，两者不相等，因此 `decodeIfPresent` 返回 `nil`。

已按项目相同策略做最小复现：

```text
编码结果：{"member_id":2}
解码容器 allKeys：["memberId"]
查询 memberID 的结果：nil
```

### 触发时序

```text
新建线程完成，thread.memberID = 2
  ↓
初始引导卡片在内存中构建，payload.memberID = 2
  ↓
首次实时读取成功，movement = ready
  ↓
科普问题进入 generating / generated，更新同一消息 block
  ↓
消息 block 经过 Core Data payloadData 编解码并重新进入 UI
  ↓
payload.memberID 解码为 nil
  ↓
ChatGuideMessageCardView 因 payload 变化重新执行 task
  ↓
以 member=nil 刷新并覆盖正确数据
  ↓
后续滑动继续以 member=nil 刷新，卡片展示「去绑定」
```

## 相关但不是根因的日志

### thread_not_found 404

```text
拉取跳过：服务端尚无该会话，thread=6A3993EF
```

新会话先在本地创建，服务端尚未收到 thread push 时发生首次 pull 404，随后 thread push 成功。这不是健康卡片误显示的原因。

### No symbol named '123'

```text
No symbol named '123' found in system symbol set
```

这是其他 UI 使用了无效 SF Symbol 名称，与成员绑定、HealthKit 权限及健康滑块刷新无关，应另建工单处理。

## 优化目标

1. 引导卡片实时健康数据始终使用当前线程的权威 `thread.memberID`。
2. 消息 payload 是否包含 `memberID`，不得影响实时健康数据展示。
3. 科普问题更新、Core Data 重载和服务端同步后，不得把正确健康数据覆盖为未授权。
4. 用户滑动切页时，按当前线程最新成员刷新一次数据。
5. 用户切换对话成员后，旧成员请求结果不得回写到新成员卡片。
6. 线程或成员上下文暂时无法解析时，保留上一次成功展示，不错误降级为「去绑定」。
7. 不修改健康科普问题流程，不恢复 `metric_sections` 持久化。

## 推荐方案

### 方案原则

健康滑块以 `threadID` 为输入，由业务层实时解析成员：

```text
消息卡片 message.threadID
  ↓
ChatDetailViewModel.loadGuideMetricSections(threadID:)
  ↓
ChatRepository.loadThread(id: threadID)
  ↓
thread.memberID
  ↓
HealthDataAccessGate.checkAccess(memberID)
  ↓
ChatGuideCardPayloadBuilder 读取实时缓存
  ↓
只更新页面 realtimeMetricSections
```

不得继续采用：

```text
payload.memberID → HealthDataAccessGate
```

也不得使用以下临时兜底：

```text
payload.memberID ?? payload.questionGeneration?.memberID
```

原因是 `questionGeneration.memberID` 同样属于消息持久化数据，也存在 acronym 字段在 snake_case 解码中的丢失风险，并且会重新耦合科普问题与健康滑块。

### 1. 调整实时数据 Provider 契约

当前：

```swift
typealias ChatGuideMetricSectionsProvider =
    (Int?) async -> [ChatGuideMetricSection]
```

推荐调整为：

```swift
typealias ChatGuideMetricSectionsProvider =
    (UUID) async -> ChatGuideMetricReloadResult?
```

建议结果模型：

```swift
struct ChatGuideMetricReloadResult: Sendable {
    let threadID: UUID
    let memberID: Int?
    let sections: [ChatGuideMetricSection]
}
```

返回 `nil` 表示线程上下文暂不可用，页面不覆盖现有展示。

### 2. 卡片显式接收 threadID

`ChatMessageBlock+Render` 渲染 `chatGuideCard` 时，从 `context.message.threadID` 传入：

```swift
ChatGuideMessageCardView(
    threadID: context.message.threadID,
    payload: payload,
    ...
)
```

`ChatGuideMessageCardView` 的刷新入口统一改为：

```swift
metricSectionsProvider(threadID)
```

以下触发场景全部使用同一 `threadID`：

- 卡片首次显示；
- 滑动切换 section；
- HealthKit 绑定完成；
- 当前线程成员切换。

### 3. ViewModel 从线程仓储解析成员

新增或替换为：

```swift
func loadGuideMetricSections(
    threadID: UUID
) async -> ChatGuideMetricReloadResult?
```

处理顺序：

```text
repository.loadThread(threadID)
  ↓ 失败
返回 nil，保留页面现有数据

repository.loadThread(threadID)
  ↓ 成功
读取 thread.memberID
  ↓ nil
生成真正的未绑定状态
  ↓ 非 nil
检查该成员 Apple Health 绑定与授权
  ↓
读取实时缓存并返回 sections
```

只有线程仓储明确返回 `thread.memberID == nil` 时，才允许展示「去绑定」。

### 4. 防止失败结果覆盖成功数据

当前 `reloadMetricSections` 无条件执行：

```swift
realtimeMetricSections = sections
```

推荐增加以下应用条件：

- provider 返回 `nil` 时不更新 UI；
- 返回结果的 `threadID` 必须等于当前卡片 `threadID`；
- 返回结果的 `memberID` 必须仍等于当前线程成员；
- 快速滑动产生多个请求时，只允许最新请求应用结果；
- 成员切换后，旧成员在途请求完成时必须丢弃。

可使用页面请求序号或 reload token：

```text
token = threadID + resolvedMemberID + requestSequence
```

### 5. 保持实时数据不持久化

本工单不得恢复以下字段写入：

```text
metric_sections
```

实时健康数据仅保存在：

```swift
@State private var realtimeMetricSections
```

消息 payload、Core Data 和服务端继续只保存科普问题相关内容。

### 6. 科普问题流程保持不变

不得修改：

- `ChatGuideQuestionGenerationUseCase`；
- `ChatGuideQuestionGenerationCoordinator` 的生成、fallback 与过期回写拦截；
- `question_generation` 服务端同步；
- 固定三条问题兜底；
- 问题点击发送逻辑。

本工单只改变健康滑块的成员上下文来源。

## 不推荐方案

### 直接把 nil 当作当前选中成员

不能使用全局 `selectedThread` 或首页当前成员兜底，因为列表复用、线程切换和详情页内部新建对话期间可能读到其他线程成员。

### 只修复 payload.memberID 解码

即使单独修复解码，实时健康滑块继续依赖消息快照，成员切换、历史消息兼容和异步更新仍容易产生状态漂移。可以另行治理 Codable acronym 字段，但不应作为本工单的唯一方案。

### 重新持久化 metric_sections

持久化会重新引入过期健康数据、跨设备同步覆盖和授权状态失真的问题，违反 CHAT-000031 已确定的实时读取原则。

### 滑动时重复查询 payload

当前滑动刷新已经正常触发，问题在成员参数错误。增加刷新次数只会重复得到 `no_binding`。

## 验收场景

### 场景 1：新建对话，成员已绑定设备

1. 新建线程绑定成员 `2`。
2. 成员 `2` 已绑定 Apple Health。
3. 首次进入卡片。
4. 等待科普问题从 generating 更新为 generated。
5. 滑动运动、身材、饮食和医疗 section。

预期：

- 每次刷新均从 `thread=当前线程` 解析出 `member=2`。
- 运动数据不出现「去绑定」。
- 科普问题更新后健康数据不降级。

### 场景 2：历史卡片 payload 没有 member_id

1. 打开已有引导卡片消息。
2. payload 顶层 `member_id` 缺失。
3. 当前线程 `memberID=2`。

预期：

- 滑块仍按线程成员 `2` 加载。
- 不要求迁移历史消息 payload。

### 场景 3：当前线程确实未绑定成员

1. 当前线程 `memberID=nil`。
2. 打开或滑动卡片。

预期：

- 运动、身材和饮食展示「去绑定」。
- 不读取 HealthKit。
- 不使用全局成员或其他线程成员兜底。

### 场景 4：用户切换当前对话成员

1. 当前线程由成员 `2` 切换到成员 `3`。
2. 成员 `2` 的旧请求仍在进行。
3. 成员 `3` 已绑定或未绑定设备。

预期：

- 立即按成员 `3` 重新判断。
- 成员 `2` 的过期结果不能覆盖页面。
- 科普问题按原流程重新生成。

### 场景 5：线程上下文短暂不可用

1. 卡片已有成功健康数据。
2. 一次刷新中仓储暂时未返回 thread。

预期：

- 本次结果记为 skipped。
- 保留上一次成功数据。
- 不展示错误的「去绑定」。

### 场景 6：快速连续滑动

1. 连续切换多个 section。
2. 多次异步读取返回顺序与发起顺序不同。

预期：

- 只应用最新有效请求。
- 不发生旧成员、旧线程或旧授权状态覆盖。

## 验收标准

1. 当前线程成员已绑定 Apple Health 时，卡片不再误显示「去绑定」。
2. 科普问题状态更新和消息 block 重载后，健康数据保持正确。
3. 滑动切页每次都按当前线程最新成员读取一次。
4. `payload.memberID=nil` 不影响实时滑块。
5. 只有 `thread.memberID=nil` 或绑定/授权门控明确失败时才展示「去绑定」。
6. 临时线程读取失败不会覆盖已有成功数据。
7. 成员切换和快速滑动时不存在过期结果回写。
8. `metric_sections` 仍不进入 Core Data 和服务端消息 payload。
9. 不新增 `CodingKeys`，继续使用项目统一 Codable 基础设施。
10. 健康科普问题生成、兜底、同步与点击发送行为完全不变。

## 完成定义

- 完成 provider 从 `memberID` 入参到 `threadID` 入参的改造。
- 完成线程权威成员解析、失败不覆盖与过期结果拦截。
- 完成首次展示、滑动刷新、绑定返回和成员切换四类触发验证。
- 补齐针对历史 payload 缺少 `member_id` 的回归测试。
- 真机日志证明同一线程不再出现 `thread.memberID` 非空但滑块刷新 `member=nil`。
