## 1. 模块目标

新建对话流程改造为：

```text
如果默认绑定开启：创建 thread 本地完成时就完成成员绑定
  ↓
后台同步新会话元数据
  ↓
进入会话页面
  ↓
插入首条 system guide card 本地完成
  ↓
后台启动科普问题生成
  ↓
AI 成功/失败
  ↓
本地回写 guide block，刷新 UI
  ↓
后台 block_updates 同步服务端
```

核心目标：

1. 默认绑定成员前置到本地 thread 创建阶段，避免进入会话页后再补绑。
2. 进入会话页面不等待 AI 科普问题生成完成。
3. 首条 system guide card 先本地插入并展示，科普问题后台生成。
4. AI 生成结果只要求本地回写成功后立即刷新 UI，服务端同步继续后台处理。
5. 新建会话元数据同步和后续 block_updates 同步解耦。

### 2.4 当前服务端同步事实

最新日志显示，新会话元数据同步和 guide message/outbox 同步是分开的：

```text
上送单会话元数据，thread=CFDD637C
Chat.Sync.ThreadPush ... body={"threads":[... "member_id":10 ...]}
会话元数据上送完成（单会话），accepted=1
```

随后 guide card 初始 generating payload 通过 outbox 上送：

```text
准备上送对话，count=1
body={"messages":[{"role":"system","blocks":[{"payload":{"chat_guide_card":{... "state":"generating","questions":[]}}}]}]}
acceptedMessages=1, acceptedBlockUpdates=0
```

AI 成功后再通过 block update 上送：

```text
chat.guide.questions.persist_result didApply=true ... state=generated questionsCount=3
chat.guide.questions.ui_update_enqueued ... state=generated questionsCount=3
chat.guide.questions.generation_success ...
准备上送对话块，blocks=1
body={"block_updates":[{"block":{"payload":{"chat_guide_card":{... "state":"generated","questions":[...]}}}}]}
```

结论：

1. 进入会话不需要等待 AI 生成完成。
2. 进入会话不需要等待 block_updates 服务端 ACK。
3. 但本地 thread 创建和 memberID 确定必须在进入会话前完成，才能减少页面进入阶段补绑和重复触发。

## 3. 需求范围

### 3.1 默认绑定前置到本地 thread 创建阶段

#### 需求说明

开启默认绑定成员时，新建对话应在本地 thread 创建时就写入 memberID，而不是进入 ChatView 后再通过 `applyComposerStartupMemberBindingIfNeeded` 补绑。

新建对话入口应先解析默认绑定策略：

```text
chatComposerStartupPreferences.memberProfileEnabled == true
  且 首页当前选中成员存在
  -> createThread(memberID: selectedMemberID)

否则
  -> createThread(memberID: nil)
```

#### 基础要求与业务规则

1. 普通新建对话和快捷新建对话都必须走同一套默认绑定解析逻辑。
2. 本地 `repository.createThread(memberID:)` 完成后，thread.memberID 应已经是最终初始值。
3. 如果默认绑定开启但没有 selectedMemberID，则创建未绑定 thread。
4. 如果用户显式从其他入口指定 memberID，则显式参数优先。
5. 进入 ChatView 后不再对“本次新建对话”执行默认补绑。
6. 重新进入旧对话不因为默认绑定开启而补绑。

#### 主流程

```text
用户点击新建对话
  ↓
ChatListViewModel 读取 chatComposerStartupPreferences
  ↓
解析 initialMemberID
  ↓
CreateThreadUseCase.execute(memberID: initialMemberID)
  ↓
repository.createThread 写入 memberID
  ↓
返回 thread
  ↓
标记 newlyCreatedThread
  ↓
setSelectedThreadID(thread.id)
```

#### 失败、重试和恢复

1. 默认绑定偏好读取失败：按未绑定创建，不阻塞新建。
2. selectedMemberID 为空：按未绑定创建。
3. thread 创建成功但后续服务端 thread-push 失败：仍进入会话，本地 outbox 后台重试。
4. thread 创建成功但 guide card 插入失败：仍进入会话，允许显示空会话或后续本地补插。

#### 技术细节与设计代码位置

建议将默认绑定解析放在 `ChatListViewModel` 或新建对话编排层，而不是 `ChatView`：

```swift
private func resolveInitialMemberIDForNewThread() -> Int? {
    let startup = aiSettingsViewModel.snapshot.chatComposerStartupPreferences
    guard startup.memberProfileEnabled else { return nil }
    return memberContextStore.context.selectedMemberID
}
```

如果 `ChatListViewModel` 当前没有 `aiSettingsViewModel`，可通过依赖注入传入 `AISettingsRepository` 或当前 startup preferences snapshot。不要让 `CreateThreadUseCase` 直接读取 SwiftUI ViewModel。

`CreateThreadUseCase.execute(memberID:title:)` 保持纯应用层输入：调用方传入最终初始 memberID。

#### 验收标准

1. 默认绑定开启且首页有选中成员，新建 thread 本地 `memberID` 非空。
2. 进入 ChatView 后不再调用 `updateThreadMemberBinding` 做初始补绑。
3. 默认绑定关闭时，新建 thread `memberID == nil`。
4. 默认绑定开启但无选中成员时，新建 thread `memberID == nil`。
5. 快捷新建对话与普通新建对话行为一致。

### 3.2 新会话元数据后台同步

#### 需求说明

本地 thread 创建完成并写入 memberID 后，应触发新会话元数据后台同步，但不阻塞进入会话页面。

同步目标：

```text
Chat.Sync.ThreadPush
  body.threads[0].member_id == 本地 thread.memberID
```

#### 基础要求与业务规则

1. thread-push 可以在创建后立即后台启动。
2. thread-push 成功与否不影响进入会话页面。
3. thread-push 失败应走现有同步重试或下次全量/单会话同步。
4. 不因为 thread-push 未完成而延迟 guide card 本地插入或页面跳转。
5. 如果后续用户切换成员，再按成员变更同步 thread 元数据。

#### 主流程

```text
repository.createThread 成功
  ↓
返回本地 thread
  ↓
Task 后台调用 chatSyncSupervisor.pushSingleThread(threadID)
  ↓
成功：服务端保存新 thread 元数据
失败：记录日志，后台重试
```

#### 技术细节与设计代码位置

当前相关代码：

```text
SparkClient/Projects/Features/Chat/Infrastructure/ChatSyncEngine.swift
SparkClient/Projects/Features/Chat/Infrastructure/ChatOutboxPipeline.swift
```

如果已有外部触发 `pushSingleThread(threadID:)`，本工单只要求确认它不阻塞 `setSelectedThreadID`。如果当前没有稳定触发点，建议在新建对话编排层启动 fire-and-forget Task。

#### 验收标准

1. 新建对话后可立即进入会话页面。
2. 日志中可看到 thread-push body 携带正确 `member_id`。
3. thread-push 失败时不影响本地会话可用。

### 3.3 进入会话页面后插入首条 system guide card

#### 需求说明

按本工单目标，首条 system guide card 的本地插入发生在进入会话页面之后，并且必须在启动科普问题生成前完成。

这样做的好处：

1. 页面生命周期掌握首屏 guide card 的展示时机。
2. 默认绑定已经在 thread 创建阶段完成，builder 可直接使用 thread.memberID。
3. 科普问题生成拿到稳定的 messageID/blockID，避免先生成后找不到目标 block。

#### 基础要求与业务规则

1. guide card 插入仍然是本地优先。
2. 插入成功后立即展示卡片。
3. 插入 payload 初始状态：
   - 有 memberID：`questions=[]`、`state=generating`、`source=current_chat_ai`、`memberID=thread.memberID`
   - 无 memberID：`questions=preset`、`state=preset`、`source=preset`
4. 插入必须幂等：已有 guide card 不重复插入。
5. 插入失败不阻塞整个会话页面，但需要记录日志。

#### 主流程

```text
进入 ChatView
  ↓
loadMessagesIfNeeded
  ↓
ensureFirstGuideCardInsertedForNewThread
  ↓
检查当前 thread 首条 system guide card 是否存在
  ├─ 已存在 -> no-op
  └─ 不存在 -> build payload -> append system guide message
  ↓
stateStore 更新消息列表
  ↓
UI 展示 guide card
```

#### 技术细节与设计代码位置

当前 `CreateThreadUseCase.appendGuideMessageIfNeeded` 已负责插入 guide card。如果改为进入页面后插入，建议抽出独立用例：

```swift
struct EnsureChatGuideSystemMessageUseCase: Sendable {
    func execute(threadID: UUID) async -> ChatGuideGuideCardTarget?
}
```

该用例负责：

1. loadThread 获取稳定 memberID。
2. loadMessages 判断是否已有 guide card。
3. 调用 `ChatGuideCardPayloadBuilder.build(memberID:defaultMemberBindingEnabled:)`。
4. 调用 `ChatGuideSystemMessageFactory.make(threadID:payload:)`。
5. `repository.appendMessage(message)`。
6. 返回生成后的 message/block target，供后续生成使用。

如果短期不移动插入时机，也必须满足“thread 创建本地完成时 memberID 已确定”，避免 guide payload 初始 memberID 为空。

#### 验收标准

1. 进入新建会话页面后，首条 system guide card 本地插入完成。
2. 已有 guide card 的 thread 不重复插入。
3. guide payload 中 `questionGeneration.memberID` 与 `thread.memberID` 一致。
4. 未绑定成员的新会话直接展示固定问题。

### 3.4 后台启动科普问题生成

#### 需求说明

guide card 本地插入成功后，后台启动科普问题生成。该过程不阻塞页面进入、不阻塞用户输入。

#### 基础要求与业务规则

1. 只有新建对话和用户切换成员触发生成。
2. 新建对话生成必须发生在 guide card 插入成功之后。
3. 生成任务需要绑定 threadID、messageID、blockID、memberID。
4. 同一 thread/block/member 只允许一个 active task。
5. AI 成功后回写 generated；失败或解码失败回写 fixed fallback。
6. 未绑定成员不启动 AI，直接 preset。

#### 主流程

```text
guide card 插入成功
  ↓
thread.memberID 是否存在？
  ├─ 否 -> preset，结束
  └─ 是 -> startGuideQuestionGenerationForNewlyCreatedThread
          ↓
          fetch complete-data
          ↓
          AIRuntimeService.generateTextStream
          ↓
          parse
          ↓
          applyGenerated/applyFallback
```

#### 技术细节与设计代码位置

当前可复用：

```text
ChatDetailViewModel.startGuideQuestionGenerationForNewlyCreatedThread()
ChatGuideQuestionGenerationCoordinator.startForNewThread(...)
ChatGuideQuestionGenerationUseCase.generate(...)
```

需要调整：

1. 不再从 `ChatView.applyComposerStartupMemberBindingIfNeeded` 启动默认绑定生成。
2. 使用 `EnsureChatGuideSystemMessageUseCase` 返回的 target 或重新读取 stateStore 中的 guide card target。
3. 若插入 guide card 失败，不启动生成。

#### 验收标准

1. 用户进入新会话后立即看到卡片 loading 或 preset。
2. 有绑定成员时后台出现一次 `generation_start`。
3. AI 完成后出现 `generation_success` 或 fallback。
4. 页面进入不等待 AI 请求耗时。

### 3.5 本地回写与 UI 刷新

#### 需求说明

AI 生成成功或失败后，必须先以本地数据为准刷新 UI，再后台同步服务端。

#### 基础要求与业务规则

1. `upsertMessageBlock(markPendingForSync: true)` 成功后立即 `stateStore.updateMessages`。
2. UI 不等待服务端 `accepted_block_updates`。
3. 如果本地回写失败，必须记录日志并保持当前 UI 状态或固定兜底展示。
4. 生成成功后 payload 必须包含：
   - `questions.count == 3`
   - `questionGeneration.state == generated`
   - `questionGeneration.memberID == thread.memberID`
   - `questionGeneration.source == current_chat_ai`
5. 生成失败后 payload 必须包含：
   - `questions == ChatGuideQuestionPreset.phaseOne`
   - `questionGeneration.state == fallback`
   - `questionGeneration.source == preset`

#### 主流程

```text
AI 成功/失败
  ↓
构造 updated payload
  ↓
target.block.replacingPayload(... revision + 1)
  ↓
repository.upsertMessageBlock(markPendingForSync: true)
  ↓
didApply == true
  ↓
stateStore.updateMessages
  ↓
UI 刷新
```

#### 验收标准

1. AI 成功后 UI 从 loading 变成 3 条 AI 问题。
2. AI 失败后 UI 从 loading 变成固定三条问题。
3. 本地重载消息后仍是最终态。
4. 没有服务端 ACK 时，UI 仍展示本地最终态。

### 3.6 后台 block_updates 同步服务端

#### 需求说明

guide block 本地回写成功后，由现有 outbox/block_updates 后台同步服务端。

#### 基础要求与业务规则

1. generated/fallback 回写时必须 `markPendingForSync: true`。
2. block update 只更新同一个 guide block，不新增消息。
3. 服务端 ACK 后清理 pending 状态。
4. 服务端同步失败不回滚 UI。
5. 如果首条 system message 尚未上送成功，可由整消息 push 携带最新 payload；如果已上送成功，则走 block_updates。

#### 主流程

```text
upsertMessageBlock(markPendingForSync: true)
  ↓
ChatOutboxPipeline.pendingBlocks
  ↓
Chat.Sync.Push block_updates
  ↓
accepted_block_updates
  ↓
markMessageBlocksSynced
```

#### 验收标准

1. generated/fallback 后可看到 pending block 被读取。
2. 日志出现 `准备上送对话块，blocks=1`。
3. 请求 body 中 `block_updates[0].block.payload.chat_guide_card` 是最终态。
4. 服务端 accepted 后本地 pending 清理。

## 5. 状态模型

| 阶段 | 是否阻塞进入会话 | 用户可见状态 | 失败处理 |
| --- | --- | --- | --- |
| 本地 thread 创建 | 是 | 仍在列表/入口 loading | 创建失败则不进入 |
| 默认绑定初始 memberID 解析 | 是，轻量同步 | 无独立 UI | 失败按 nil |
| 新会话元数据 thread-push | 否 | 不影响页面 | 后台重试 |
| guide card 本地插入 | 建议是 | 卡片出现 | 失败记录日志，允许空会话 |
| 科普问题 AI 生成 | 否 | 卡片 loading | fallback 固定问题 |
| 本地 guide block 回写 | 否，但必须尽快完成 | UI 切换最终态 | 失败记录日志 |
| block_updates 同步 | 否 | UI 不等待 | 后台重试 |

关键原则：

```text
只有本地 thread 创建和初始 memberID 决策需要挡住进入。
AI、message push、block_updates 都不能挡住进入。
```

## 6. 数据与持久化

本地数据：

1. `ChatThread.memberID` 在创建时写入初始默认绑定结果。
2. `ChatMessage(role: system)` 进入页面后插入首条 guide card。
3. `ChatGuideCardPayload.questionGeneration.memberID` 必须与 `ChatThread.memberID` 一致。
4. generated/fallback 回写同一个 block，revision 递增。
5. pending sync 由 block row 的 `isPendingSync` 承担。

服务端数据：

1. `thread-push` 同步 thread 元数据和 `member_id`。
2. 首条 guide system message 可通过 outbox message push 同步。
3. AI 结果通过 block_updates 同步。
4. 服务端同步不参与 UI 首屏决策。

## 7. 错误模型

| 错误 | 处理 |
| --- | --- |
| 初始 memberID 解析失败 | 按未绑定创建 |
| createThread 本地失败 | 不进入会话，提示创建失败 |
| thread-push 失败 | 进入会话，后台重试 |
| guide card 插入失败 | 进入会话，记录日志；可后续重试插入 |
| complete-data 失败 | 固定问题 fallback |
| AI 失败/取消/解析失败 | 固定问题 fallback 或由新任务接管 |
| 本地 block 回写失败 | 记录日志，保留当前 UI |
| block_updates 失败 | 不回滚 UI，后台重试 |

## 8. 与其他模块的接口边界

本模块负责：

1. 新建对话时确定初始 memberID。
2. 控制 guide card 插入时机。
3. 后台启动科普问题生成。
4. 本地回写 guide block 并刷新 UI。

## 11. 当前实现、缺口与演进

当前实现：

1. `ChatListViewModel.createThread()` 已把当前 selectedMemberID 传入 `CreateThreadUseCase`。
2. `CreateThreadUseCase` 已能创建 thread 并插入 guide message。
3. `ChatView` 已有新建 marker 消费逻辑。
4. `ChatDetailViewModel` 已有 `startGuideQuestionGenerationForNewlyCreatedThread()`。
5. `ChatOutboxPipeline` 已支持 message push 和 block_updates。

当前缺口：

1. 默认绑定解析仍分散在列表创建入口和 ChatView 页面进入补绑入口。
2. guide card 插入仍在 `CreateThreadUseCase` 内，不符合本工单“进入页面后插入”的目标时序。
3. 页面进入后仍保留 `applyComposerStartupMemberBindingIfNeeded`，需要收口为旧数据兼容或移除新建补绑职责。
4. thread-push 是否阻塞 UI 跳转需要明确为后台任务。
5. 缺少新建流程端到端测试。

建议演进：

1. 把“新建对话编排”抽成单独 coordinator/use case，集中处理默认绑定、thread 创建、新建 marker、后台 thread-push。
2. 将 guide card 插入从 `CreateThreadUseCase` 拆到 `EnsureChatGuideSystemMessageUseCase`，使 thread 创建和首屏卡片更清晰解耦。
3. 保留 `CreateThreadUseCase` 只做 thread 创建，不做 UI 首屏消息副作用。

## 12. 整体验收标准

1. 默认绑定开启时，本地 thread 创建完成即已写入 memberID。
2. 新会话元数据同步在后台进行，不阻塞进入会话页面。
3. 进入会话页面后首条 system guide card 本地插入完成。
4. guide card 插入成功后后台启动科普问题生成。
5. AI 成功后本地回写 guide block 并立即刷新 UI。
6. AI 失败或解码失败后本地回写固定三条问题并刷新 UI。
7. generated/fallback 后通过 block_updates 后台同步服务端。
8. 服务端同步失败不影响本地 UI 最终态。
9. 重新进入已有对话不触发默认绑定、不触发科普问题生成。
10. 普通新建和快捷新建流程一致。
