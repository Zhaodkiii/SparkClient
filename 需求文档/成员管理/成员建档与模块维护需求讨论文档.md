# 成员建档与模块维护需求讨论文档

> 文档性质：需求讨论稿。本文讨论“新建成员”的完整客户端流程、模块启用策略、首页展示规则、服务端数据边界和后续扩展方向。本文不涉及代码改动。

## 一、背景

当前成员基础模型已经支持姓名、性别、出生日期、血型、过敏史、慢病摘要、备注、头像、是否主档案等字段。

服务端当前成员模型参考：

```text
SparkService/medical/models.py

Member:
- name
- gender
- birth_date
- blood_type
- allergies
- chronic_conditions
- notes
- avatar_url
- is_primary

UserMemberBinding:
- relationship
- role
- status
```

但“新建成员”不应该只停留在姓名、关系、年龄。用户创建成员的真实目的通常是后续持续管理：

1. 给父母维护慢病和用药。
2. 给自己维护饮食目标和体重目标。
3. 给孩子或家人维护日常健康、睡眠、运动或照护提醒。
4. 让首页只展示这个成员真正启用的模块，减少空白和噪音。

因此建议把新建成员流程升级为：

```text
基础信息
-> 提交基础信息，创建成员
-> 模块选择
-> 点击模块去完善，Sheet 打开分页面维护
-> 至少完成一个模块
-> 保存模块配置
-> 首页按启用模块展示
```

## 二、核心目标

### Q：这个新建成员流程要解决什么问题？

A：要解决三个问题。

1. **成员不是空壳**：创建后至少有一个明确管理方向。
2. **首页不展示无关模块**：只展示用户为该成员开启的模块。
3. **AI 有更准确上下文**：成员的医疗、饮食、生活方式信息可以成为 AI 分析依据。

### Q：为什么需要模块化？

A：不同成员的管理需求不一样。

| 成员 | 可能启用模块 |
| --- | --- |
| 本人 | 饮食健康、医疗 |
| 妈妈 | 医疗、饮食健康 |
| 爸爸 | 医疗 |
| 孩子 | 医疗 |
| 临时就诊成员 | 医疗 |

如果所有成员都展示医疗、饮食、日常健康，会让首页变得空而杂。模块化后首页更像“按成员定制的健康工作台”。

## 三、整体流程

### 3.1 流程总览

```text
入口：添加成员
-> Step 1 基本信息
-> Step 2 提交基础信息并创建成员
-> Step 3 选择维护模块
-> Step 4 点击模块去完善，Sheet 打开分页面维护
-> 模块 Sheet 完成时立即保存对应模块
-> Step 5 完成确认
-> 刷新成员列表和首页
```

### 3.2 页面流转

```text
AddMemberBasicInfoView
  -> MemberNameBirthStepView
  -> MemberRelationshipGenderStepView
  -> 提交基础信息，创建 Member
  -> MemberModuleSetupView
      -> sheet: MemberMedicalSetupSheet
          -> MemberMedicalChronicConditionStepView
          -> MemberMedicalMedicationStepView
              -> sheet: MedicationPlanStepperView
          -> MemberMedicalExamIndicatorStepView
          -> MemberMedicalSymptomFollowUpStepView
      -> sheet: MemberNutritionSetupSheet
          -> MemberNutritionBodyInfoStepView
          -> MemberNutritionGoalStepView
          -> MemberNutritionMacroGoalStepView
      -> MemberLifestyleSetupSheet       // 代码预留，第一期不展示
  -> MemberSetupSummaryView
  -> 完成
```

说明：

1. 基础信息点击下一步时必须先创建成员，进入 `MemberModuleSetupView` 时已经有真实 `memberID`。
2. `去完善` 不做 push，统一使用 sheet 打开分步页面。
3. 分步维护形态参考 `MedicationPlanStepperView`：顶部步骤、底部主按钮、每一步只维护一类信息。
4. 用药计划不在新建成员页面内重做，直接 sheet 打开 `MedicationPlanStepperView`。
5. 日常健康第一期只保留代码预留，不在 UI 展示。
6. `成长发育` 和 `照护安全` 第一阶段不做。
7. 医疗模块、饮食健康模块各自完成时立即调用对应接口保存，不等待最后统一提交。

### 3.3 最小完成条件

规则：

1. 基础信息必须完成。
2. 至少启用一个模块。
3. 如果用户只填基础信息但没有启用模块，不允许完成；可以提示“至少选择一个要维护的健康模块”。
4. 如果用户启用了模块但未完成必要字段，可以保存为“待完善”，但该模块首页展示应显示轻量引导态。

建议第一期规则：

```text
基础信息完成 = 创建成员
成员已创建 + 至少启用一个模块 = 可以完成建档流程
模块详细预填可以允许部分跳过
```

原因：降低建档阻力，不要强迫用户一次性填完大量健康数据。

### 3.4 保存策略

核心原则：

```text
成员先创建
模块独立保存
最终完成只收口
```

具体规则：

1. 用户完成姓名/出生日期、关系/性别后，客户端立即调用创建成员接口。
2. 创建成功后进入模块选择页，此时页面必须持有 `memberID`。
3. 用户开启/关闭模块时，可以立即保存模块启用状态，或在点击下一步时保存模块启用状态。
4. 用户点击某个模块的 `去完善`，sheet 内填写完成后立即调用该模块对应接口保存。
5. 医疗模块保存成功后，更新 `MemberModuleSetting(module_code=medical)` 的 `status`。
6. 饮食健康保存成功后，更新 `MemberModuleSetting(module_code=nutrition)` 的 `status`。
7. 最后 `完成` 不再提交所有表单，只校验至少启用一个模块、刷新成员首页数据并关闭流程。
8. 如果某个模块保存失败，只影响该模块，不重复创建成员。

保存流程：

```text
Step 1 姓名生日
-> Step 2 关系性别
-> POST 创建成员
-> 获得 memberID
-> Step 3 模块选择
-> 点击医疗 去完善
-> Medical Sheet 完成
-> PUT/POST 保存 MemberMedicalProfile
-> PUT/POST 保存 MemberModuleSetting medical 状态
-> 关闭 Medical Sheet
-> 点击饮食健康 去完善
-> Nutrition Sheet 完成
-> PUT/POST 保存 NutritionGoal
-> PUT/POST 保存 MemberModuleSetting nutrition 状态
-> 关闭 Nutrition Sheet
-> 点击完成
-> 刷新成员首页配置
```

## 四、Step 1 基本信息

### 4.1 字段

基础信息建议字段：

| 字段 | 必填 | 来源/说明 |
| --- | --- | --- |
| 姓名 | 是 | `Member.name` |
| 关系 | 是 | `UserMemberBinding.relationship`，当前用户视角 |
| 性别 | 建议 | `Member.gender`，也可由关系推断默认值 |
| 年龄/出生日期 | 建议 | 最终只通过 `birth_date` 推导年龄 |
| 头像 | 否 | `Member.avatar_url` |
| 是否本人 | 自动 | 关系为 `self` 时推导 |

用户提到“姓名、关系、年龄”，建议实现上仍然存出生日期：

```text
用户输入年龄
-> 客户端换算为近似 birth_date 或传 age_years 给服务端
-> 服务端最终以 birth_date 为准
```

如果用户只知道年龄，不知道生日：

1. 第一阶段 UI 可以允许选择年龄。
2. 保存时仍转换为 `birth_date`。
3. 不新增 `Member.age` 主字段，年龄统一由 `birth_date` 推导。
4. 身高不属于成员基础信息，只属于饮食健康目标计算。

3. 如果用户只知道年龄，UI 可以提供年龄选择，但保存时仍转换为近似 `birth_date`。

3. 点击下一步后，客户端创建成员并获得 `memberID`。
4. 后续模块维护都基于这个真实 `memberID`。

```text

│                       去完善 >│
├────────────────────────────┤
│ ☑ 饮食健康                  │
│   饮食目标、营养、体重管理    │

├────────────────────────────┤
│                            │

└────────────────────────────┘
```

### 4.3 需要补充的细节

1. 关系选择后可以推断性别，例如母亲/妻子/女儿默认女，父亲/丈夫/儿子默认男。
2. 性别仍允许用户手动修改。
3. 年龄和出生日期不要同时强制填写，避免用户困惑。
4. 新建“本人”时需要检查是否已有本人主档案。
5. 如果已有本人档案，再创建 `self` 关系成员时需要提醒。
6. 家庭共享成员和自己创建成员的权限不同，需要在流程中区分。
7. 医疗模块和饮食健康的 `去完善` 都使用 sheet 打开各自的分步维护页。
8. 模块分步维护支持跳过，不强迫用户一次性填完所有内容。

## 五、Step 2 模块选择

### 5.1 模块设计

建议三个大模块：

| 模块 | 定位 | 首页 Section |
| --- | --- | --- |
| 医疗模块 | 病历、慢病、用药、检查体检、症状随访 | `medicalInfoSection` |
| 饮食健康 | 饮食记录、营养目标、体重目标、BMI、理想体重 | `nutritionInfoSection` |
| 日常健康/生活方式 | 运动、睡眠、体重、饮水、习惯、照护提醒 | `lifestyleInfoSection` |

后续可扩展两个差异化模块：

| 模块 | 定位 | 首页 Section |
| --- | --- | --- |
| 成长发育 | 身高体重趋势、阶段成长、儿童/青少年/老人变化观察 | `growthInfoSection` |
| 照护安全 | 紧急联系人、跌倒/独居风险、家属协作和照护提醒 | `careSafetyInfoSection` |

### Q：为什么不把五个模块第一期全部做成主入口？

A：第一期不建议全部主入口化。

原因：

1. 用户刚新建成员时选择太多，会增加理解成本。
2. 医疗、饮食健康已经覆盖第一期最核心用户诉求。
3. 成长发育更适合儿童、青少年、产后、老人衰弱观察，并非每个成员都需要。
4. 照护安全更适合老人、术后、行动不便、远程照护成员，也不是通用刚需。
5. 五个模块可以作为架构预留，但产品首屏第一期只呈现医疗和饮食健康。

推荐做法：

```text
第一期 UI：
医疗模块
饮食健康
日常健康不展示，仅代码预留

第一期数据结构：
预留 growth/care safety 模块状态字段，或使用通用 module_code 表达

后续 UI：
根据成员关系、年龄、用户选择，渐进展示成长发育/照护安全
```

### Q：第三个模块叫什么合适？

A：建议叫 **日常健康**，副标题可叫“运动、睡眠、体重和照护习惯”。但第一期只做代码预留，不进入新建成员 UI 和首页。

原因：

1. “医疗”偏疾病和就诊。
2. “饮食健康”偏营养、食物和体重目标。
3. 还缺一类日常长期数据：运动、睡眠、体重、饮水、习惯、照护提醒。
4. “日常健康”比“生活方式”更容易让普通用户理解。

不建议叫：

| 名称 | 问题 |
| --- | --- |
| 健康管理 | 太泛，和整个 App 重名 |
| 运动健康 | 范围太窄，不包含睡眠、饮水、照护 |
| 照护模块 | 偏护理场景，对本人用户不自然 |

### 5.2.1 模块推荐规则

模块可以根据基础信息给出默认推荐，但不能强制。

| 条件 | 推荐模块 | 说明 |
| --- | --- | --- |
| 关系为本人 | 饮食健康 | 本人更可能管理体重、营养目标和 Apple 健康 |
| 关系为本人且已有 Apple 健康权限 | 饮食健康 | 自动建议开启饮食健康；日常健康第一期不展示 |
| 年龄大于 60 岁 | 医疗模块 | 老年人更可能有慢病、用药、检查指标维护需求 |
| 关系为父母/祖父母 | 医疗模块 | 家庭成员常见需求是慢病和用药管理 |
| 用户选择慢病标签 | 医疗模块、饮食健康 | 慢病管理常需要饮食控制 |
| 用户选择减重/增肌目标 | 饮食健康 | 饮食目标第一期直接进入饮食目标计算 |

UI 表达建议：

```text
推荐开启
```

不要使用“必须开启”，避免用户认为系统替他做决定。

### 5.3 交互规则

1. 点击开关只表示启用模块。
2. 点击 `去完善` 使用 sheet 打开对应模块分步维护页。
3. 启用模块但不完善时，模块状态为 `enabled_pending`。
4. 完善至少一项核心信息后，模块状态为 `enabled_completed`。
5. 用户关闭模块时，如果已填写信息，需要二次确认：关闭后首页不展示，但数据不删除。
6. 日常健康第一期不展示开关和 `去完善`，仅保留模块代码、路由和数据结构预留。
7. 模块推荐由客户端根据年龄、关系、Apple 健康权限等本地计算，不由服务端返回。

## 六、医疗模块

### 6.1 定位

医疗模块用于维护疾病、用药、检查指标和症状随访，是成员的“医疗背景档案”。

用户开启医疗模块后，进入信息预填页。

### 6.2 预填内容

建议预填分组：

| 分组 | 内容 |
| --- | --- |
| 慢病档案 | 糖尿病、高血压、高血脂、痛风、脂肪肝、肾病、心脑血管疾病等 |
| 用药 | 是否长期用药、用药计划、处方、是否需要提醒 |
| 体检指标 | 血糖、血脂、尿酸、肝功能、肾功能、血压、体重 |
| 症状/随访 | 胃肠不适、浮肿、血压波动、血糖波动、复诊计划 |
| 风险信息 | 过敏史、禁忌、重要备注 |

### 6.3.1 分步维护页面

医疗模块 Sheet 内建议分为四步：

```text
MemberMedicalSetupSheet
├─ Step 1 慢病档案
├─ Step 2 用药
├─ Step 3 体检指标
└─ Step 4 症状/随访
```

页面行为：

| 步骤 | 页面 | 维护内容 | 保存方式 |
| --- | --- | --- | --- |
| Step 1 | `MemberMedicalChronicConditionStepView` | 慢病标签、过敏史、风险备注 | 保存到 `MemberMedicalProfile` |
| Step 2 | `MemberMedicalMedicationStepView` | 是否长期用药、是否需要提醒、添加用药计划 | 用药计划直接打开 `MedicationPlanStepperView` |
| Step 3 | `MemberMedicalExamIndicatorStepView` | 关注指标和最新指标值 | 保存到 `MemberMedicalProfile` 或后续指标记录表 |
| Step 4 | `MemberMedicalSymptomFollowUpStepView` | 症状关注、随访计划、复诊提醒 | 保存到 `MemberMedicalProfile` |

交互规则：

1. 每一步底部都有 `下一步`。
2. 非必填步骤提供 `跳过`。
3. 用户点击 `跳过` 后进入下一步，不清空已填写内容。
4. 最后一步展示 `完成`，保存医疗模块摘要并关闭 sheet。
5. 已完成的步骤再次进入时回显已有草稿。
6. sheet 关闭前如果有未保存修改，需要二次确认。

用药计划流程：

```text
MemberMedicalMedicationStepView
-> 点击 添加用药计划
-> sheet 打开 MedicationPlanStepperView
-> 保存用药计划
-> 回到医疗模块 Step 2
-> 更新 medication_summary
```

体检指标规则：

1. 第一阶段允许手动录入最新指标值。
2. 指标值不是体检报告本体，不替代正式体检报告。
3. 后续如果有结构化指标表，应迁移为独立指标记录。
4. `MemberMedicalProfile.exam_indicator_focus` 保存关注项，`extra` 可暂存最新手动值。

### 6.3.2 医疗模块数据存储位置

医疗模块页面里展示的是“成员医疗概览 + 正式业务入口”的组合，不是所有字段都存在同一张表里。

总体规则：

1. `MemberMedicalProfile` 保存新建成员阶段的医疗概览、关注项和手动摘要。
2. 用药计划、处方、体检报告、检查报告、症状、随访等正式业务数据仍进入各自已有业务表。
3. 模块启用、完成状态和首页排序保存到 `MemberModuleSetting(module_code=medical)`。
4. `MemberMedicalProfile` 不替代正式业务表，只负责成员建档时的快速预填和首页摘要。

字段映射：

| UI 区域 | UI 内容 | 存储位置 | 说明 |
| --- | --- | --- | --- |
| 慢病档案 | 糖尿病、高血压、高血脂、痛风、脂肪肝、肾病等标签 | `MemberMedicalProfile.chronic_conditions` | 建档阶段的慢病摘要；可同步到 `Member.chronic_conditions` 作为成员基础摘要 |
| 慢病档案 | 其他慢病说明 | `MemberMedicalProfile.extra["other_chronic_condition"]` 或 `risk_notes` | 第一阶段不单独建慢病详情表 |
| 用药 | 是否有长期用药 | `MemberMedicalProfile.medication_summary.has_long_term_medication` | 仅摘要，用于首页和建档状态 |
| 用药 | 是否需要提醒 | `MemberMedicalProfile.medication_summary.reminder_enabled` | 仅摘要；真实提醒以用药计划为准 |
| 用药 | 添加用药计划 | 现有用药计划表 | 通过 `MedicationPlanStepperView` 创建正式用药计划，不保存到 `MemberMedicalProfile` |
| 用药 | 用药计划数量 | `MemberMedicalProfile.medication_summary.medication_plan_count` | 可由正式用药计划表聚合后回写或实时计算 |
| 体检指标 | 关注血糖、血脂、尿酸、肝肾功能等 | `MemberMedicalProfile.exam_indicator_focus` | 保存用户关注哪些指标 |
| 体检指标 | 手动录入最新指标值 | `MemberMedicalProfile.exam_indicator_latest_values` | 第一阶段临时保存最新值；不替代正式体检报告 |
| 体检指标 | 上传/选择体检报告 | 体检报告正式表 | 后续从体检报告详情读取结构化指标 |
| 症状/随访 | 症状关注项 | `MemberMedicalProfile.symptom_follow_up_focus` | 建档阶段只保存关注摘要 |
| 症状/随访 | 正式症状记录 | 症状记录正式表 | 如果用户创建具体症状记录，进入正式症状表 |
| 症状/随访 | 正式随访/复诊计划 | 随访/就诊正式表 | 如果用户创建具体随访计划，进入正式随访或就诊表 |
| 风险信息 | 过敏、禁忌 | `MemberMedicalProfile.allergy_notes`，必要时同步 `Member.allergies` | 成员基础摘要和医疗概览都可引用 |
| 风险信息 | 重要风险备注 | `MemberMedicalProfile.risk_notes` | 仅医疗概览摘要 |
| 模块状态 | 医疗模块开启、待完善、已完成 | `MemberModuleSetting` | `module_code=medical` |

保存时机：

1. 用户点击医疗模块 `去完善` 后进入 `MemberMedicalSetupSheet`。
2. 每一步先保存在本地草稿中。
3. 最后一步点击 `完成` 后，客户端一次性保存 `MemberMedicalProfile`。
4. 保存成功后同步更新 `MemberModuleSetting(module_code=medical)`。
5. 如果用户在用药步骤内创建用药计划，`MedicationPlanStepperView` 自己调用用药计划接口立即保存正式用药计划。

为什么不全部放到 `MemberMedicalProfile`：

1. 用药计划有复杂的剂量、提醒、周期和服药记录，必须使用正式用药计划模型。
2. 体检报告、检查报告有附件、OCR、结构化指标和详情页，不能用一个 JSON 摘要替代。
3. 症状和随访后续会形成时间线记录，也不适合塞进建档概览表。
4. `MemberMedicalProfile` 只解决“新建成员时快速建立医疗背景”的问题。

### 6.4.1 服务端新增表：MemberMedicalProfile

建议归属：

```text
SparkService/medical/models.py
```

模型用途：

1. 保存成员级医疗模块的概览和预填信息。
2. 作为首页医疗模块摘要的数据来源之一。
3. 作为 AI 普通上下文摘要的数据来源之一。
4. 不替代正式病历、处方、用药计划、体检报告。

建议 Django 模型：

```python
class MemberMedicalProfile(models.Model):
    class Status(models.TextChoices):
        PENDING = "enabled_pending", "enabled_pending"
        COMPLETED = "enabled_completed", "enabled_completed"

    user = models.ForeignKey(
        User,
        related_name="member_medical_profiles",
        on_delete=models.CASCADE,
        db_index=True,
        db_comment="当前账号 ID，用于权限边界和数据归属",
    )
    member = models.ForeignKey(
        Member,
        related_name="medical_profiles",
        on_delete=models.CASCADE,
        db_index=True,
        db_comment="关联成员 ID",
    )
    enabled = models.BooleanField(default=True, db_index=True, db_comment="医疗模块是否开启")
    status = models.CharField(max_length=32, choices=Status.choices, default=Status.PENDING, db_index=True, db_comment="医疗模块维护状态")
    chronic_conditions = models.JSONField(default=list, blank=True, db_comment="慢病标签列表，例如 hypertension、diabetes")
    medication_summary = models.JSONField(default=dict, blank=True, db_comment="用药摘要，例如是否长期用药、用药计划数量、是否需要提醒")
    exam_indicator_focus = models.JSONField(default=list, blank=True, db_comment="体检指标关注项，例如 blood_glucose、blood_lipid、uric_acid")
    exam_indicator_latest_values = models.JSONField(default=dict, blank=True, db_comment="第一期手动录入的最新指标值；后续可迁移为结构化指标记录")
    symptom_follow_up_focus = models.JSONField(default=list, blank=True, db_comment="症状和随访关注项")
    allergy_notes = models.TextField(blank=True, default="", db_comment="过敏和禁忌备注")
    risk_notes = models.TextField(blank=True, default="", db_comment="医疗风险备注")
    last_completed_at = models.DateTimeField(null=True, blank=True, db_index=True, db_comment="最近一次完成核心信息维护时间")
    extra = models.JSONField(default=dict, blank=True, db_comment="扩展字段，例如跳过步骤、来源页面、推荐原因")
    created_at = models.DateTimeField(auto_now_add=True, db_index=True, db_comment="创建时间")
    updated_at = models.DateTimeField(auto_now=True, db_index=True, db_comment="更新时间")

    class Meta:
        constraints = [
            models.UniqueConstraint(fields=["user", "member"], name="uniq_member_medical_profile_user_member"),
        ]
        indexes = [
            models.Index(fields=["user", "member", "status"]),
        ]
```

保存规则：

1. 医疗 sheet 点击 `完成` 后，客户端调用医疗模块保存接口。
2. 服务端 upsert `MemberMedicalProfile`。
3. 如果至少有一个核心字段完成，状态写为 `enabled_completed`。
4. 如果用户全部跳过，状态写为 `enabled_pending`。
5. 同步 upsert `MemberModuleSetting(module_code=medical)`。

## 七、饮食健康模块

### 7.1 定位

饮食健康模块用于维护：

1. 饮食目标。
2. BMI 和理想体重范围。
3. 卡路里目标。
4. 营养目标。
5. 餐次分布。
6. Apple 健康关联规则。

这部分复用《NUTRITION-000023 饮食目标与身体指标统一计算工单》。

### 7.2 预填内容

| 分组 | 内容 |
| --- | --- |
| 当前身体信息 | 身高、当前体重、性别、年龄；身高只属于饮食健康目标计算 |
| 目标模式 | 减重、保持体重、增重、打造肌肉、自定义 |
| 活跃水平 | 低、中、高 |
| 每周目标 | -0.50kg/周等 |
| 卡路里目标 | 系统计算或用户手动 |
| 营养目标 | 默认、低碳水、高蛋白、自定义 |
| 餐次分布 | 早餐、午餐、晚餐、小吃 |

### 7.2.1 目标模式选项

目标模式建议面向用户使用自然文案，内部再映射到稳定枚举。

第一期适合项目的目标选项：

| 用户文案 | 内部值 | 适合人群 | 对计算的影响 |
| --- | --- | --- | --- |
| 减重 | `lose_weight` | 希望降低体重、控制体脂 | 每日热量低于维持热量，每周目标为负数 |
| 保持体重 | `maintain_weight` | 体重基本满意，希望稳定饮食 | 每日热量接近维持热量，每周目标为 0 |
| 增重 | `gain_weight` | 偏瘦、恢复期、希望增加体重 | 每日热量高于维持热量，每周目标为正数 |
| 打造肌肉 | `build_muscle` | 健身、增肌、提高蛋白质摄入 | 轻度热量盈余，提高蛋白质比例 |
| 自定义 | `custom` | 有明确营养目标或医生/营养师建议 | 用户手动设置卡路里和营养比例 |

说明：

1. `增重` 和 `打造肌肉` 不建议合并。增重更偏体重增加，打造肌肉更偏高蛋白和训练配合。
2. `保持体重` 比 `维持` 更适合 UI 文案，普通用户更容易理解。
3. 第一阶段 UI 展示这五个即可。
4. 控糖、控盐、控脂可以作为后续“健康专项目标”，不要和第一期基础目标混在一起导致选择困难。

后续可扩展健康专项目标：

| 用户文案 | 内部值 | 说明 |
| --- | --- | --- |
| 控糖 | `control_sugar` | 控制碳水比例和餐次碳水波动 |
| 控盐 | `control_salt` | 关注钠、盐摄入，适合高血压等场景 |
| 控脂 | `control_fat` | 关注脂肪、饱和脂肪、胆固醇 |
| 降尿酸 | `control_uric_acid` | 后续可结合低嘌呤饮食 |
| 养肝护肾 | `liver_kidney_care` | 后续结合肝肾功能指标，不在第一期做强规则 |

## 八、日常健康模块

### 8.1 定位

日常健康模块补足医疗和饮食之外的长期生活数据。

第一期决策：

```text
日常健康只做代码预留
不在新建成员模块选择页展示
不在首页展示 lifestyleInfoSection
不做每日记录
```

建议包含：

1. 运动习惯。
2. 睡眠习惯。
3. 体重记录。
4. 饮水习惯。
5. 吸烟/饮酒。
6. 情绪/压力。
7. 照护提醒。
8. 重要日程，例如复诊、体检、运动计划。

### 8.2 为什么需要它？

如果只有医疗和饮食，成员档案会偏“生病后管理”。日常健康模块让 App 能覆盖：

1. 健康人群的日常管理。
2. 老人的照护提醒。
3. 慢病用户的生活方式干预。
4. AI 对话里的运动、睡眠、饮水建议。

### 8.2.1 还可以考虑的两个差异化模块

除了 `日常健康`，还可以额外考虑两个不和医疗、饮食健康重叠的模块，用来适配更多人群。

### 建议模块一：成长发育

定位：面向儿童、青少年、孕产后恢复、老人衰弱观察等“阶段性成长/变化”场景。

它和医疗模块的区别：

1. 医疗模块关注疾病、用药、检查、症状。
2. 成长发育关注长期变化趋势，例如身高、体重、发育阶段、能力变化。
3. 它不强调“生病”，更适合健康儿童和家庭成长记录。

它和饮食健康模块的区别：

1. 饮食健康关注吃什么、吃多少、营养目标。
2. 成长发育关注身体变化是否符合阶段预期。
3. 饮食可以影响成长，但不是成长发育模块的主体。

适合人群：

## 九、统一模块设置

### Q：模块启用状态放哪里？

A：建议新增统一成员模块设置表，归属 `medical` app 内，使用通用 `module_code` 表，不使用固定列。

建议模型：`MemberModuleSetting`

字段建议：

```text
user
member
module_code
enabled
status
display_order
setup_completed_at
last_opened_at
extra
created_at
updated_at
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `user` | 当前账号，用于权限边界 |
| `member` | 关联成员 |
| `module_code` | 模块编码，例如 `medical`、`nutrition` |
| `enabled` | 是否开启该模块 |
| `status` | `disabled`、`enabled_pending`、`enabled_completed` |
| `display_order` | 首页展示排序，由服务端控制 |
| `setup_completed_at` | 模块首次完成核心信息的时间 |
| `last_opened_at` | 用户最近一次打开该模块维护页的时间 |
| `extra` | 模块配置扩展字段，例如推荐原因、跳过步骤 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

状态建议：

| 状态 | 说明 |
| --- | --- |
| `disabled` | 未开启 |
| `enabled_pending` | 已开启但未完善 |
| `enabled_completed` | 已开启且已完成核心信息 |

### 9.1 完成规则

```text
completed_module_count >= 1
```

满足后允许完成成员建档。

如果模块只是 `enabled_pending`，是否算完成？

建议：

1. 第一阶段：启用模块即可算完成，降低门槛。
2. 后续：关键模块可要求填写最小核心字段，例如饮食健康必须有当前体重和目标模式。

### 9.2 模块状态字段是否要固定列？

模块状态使用通用 `module_code` 表，不使用固定列：

```text
MemberModuleSetting:
- user
- member
- module_code
- enabled
- status
- display_order
- setup_completed_at
- last_opened_at
- extra
- created_at
- updated_at
```

`module_code` 建议枚举：

| module_code | UI 名称 |
| --- | --- |
| `medical` | 医疗模块 |
| `nutrition` | 饮食健康 |
| `lifestyle` | 日常健康 |
| `growth` | 成长发育 |
| `care_safety` | 照护安全 |

更推荐通用表的原因：

1. 新增模块不需要反复给 `MemberModuleSetting` 加字段。
2. 首页模块展示可以按 `display_order` 排序。
3. 不同成员可以开启不同模块组合。
4. 首页排序由服务端通过 `display_order` 控制。
5. 第一阶段即按通用表设计，避免后续迁移固定列。

### 9.3 服务端新增表：MemberModuleSetting

建议归属：

```text
SparkService/medical/models.py
```

建议 Django 模型：

```python
class MemberModuleSetting(models.Model):
    class ModuleCode(models.TextChoices):
        MEDICAL = "medical", "medical"
        NUTRITION = "nutrition", "nutrition"
        LIFESTYLE = "lifestyle", "lifestyle"
        GROWTH = "growth", "growth"
        CARE_SAFETY = "care_safety", "care_safety"

    class Status(models.TextChoices):
        DISABLED = "disabled", "disabled"
        PENDING = "enabled_pending", "enabled_pending"
        COMPLETED = "enabled_completed", "enabled_completed"

    user = models.ForeignKey(
        User,
        related_name="member_module_settings",
        on_delete=models.CASCADE,
        db_index=True,
        db_comment="当前账号 ID，用于权限边界和数据归属",
    )
    member = models.ForeignKey(
        Member,
        related_name="module_settings",
        on_delete=models.CASCADE,
        db_index=True,
        db_comment="关联成员 ID",
    )
    module_code = models.CharField(max_length=32, choices=ModuleCode.choices, db_index=True, db_comment="模块编码，例如 medical、nutrition")
    enabled = models.BooleanField(default=False, db_index=True, db_comment="是否开启该模块")
    status = models.CharField(max_length=32, choices=Status.choices, default=Status.DISABLED, db_index=True, db_comment="模块维护状态")
    display_order = models.IntegerField(default=0, db_index=True, db_comment="首页展示排序，由服务端控制")
    setup_completed_at = models.DateTimeField(null=True, blank=True, db_index=True, db_comment="模块首次完成核心信息的时间")
    last_opened_at = models.DateTimeField(null=True, blank=True, db_comment="用户最近一次打开模块维护页的时间")
    extra = models.JSONField(default=dict, blank=True, db_comment="模块扩展配置，例如推荐原因、跳过步骤")
    created_at = models.DateTimeField(auto_now_add=True, db_index=True, db_comment="创建时间")
    updated_at = models.DateTimeField(auto_now=True, db_index=True, db_comment="更新时间")

    class Meta:
        constraints = [
            models.UniqueConstraint(fields=["user", "member", "module_code"], name="uniq_member_module_setting_user_member_code"),
        ]
        indexes = [
            models.Index(fields=["user", "member", "enabled", "display_order"]),
            models.Index(fields=["user", "member", "module_code", "status"]),
        ]
```

数据边界：

1. `MemberModuleSetting` 只保存模块启用、状态和展示排序。
2. 医疗模块详情保存到 `MemberMedicalProfile`。
3. 饮食健康详情保存到 `NutritionGoal` 等饮食营养表。
4. 不在 `MemberModuleSetting.extra` 里塞完整业务表单。
5. 第一阶段只创建 `medical`、`nutrition` 两类可见模块记录。
6. `lifestyle` 可以作为代码预留，但不需要为所有成员提前创建记录。

3. 各模块 `SetupSheet` 内部采用分页面维护，交互参考 `MedicationPlanStepperView`。
4. `Lifestyle` 目录仅做第一期代码预留，不接入 UI。
5. 不新增 `Growth`、`CareSafety` 目录，第一期明确不做。
6. `MemberSetupSkipButton` 用于医疗和饮食健康 sheet 内的非必填步骤。

### 12.2 ViewModel 草稿

建议草稿：

```swift
struct MemberSetupDraft: Equatable, Sendable {
    var basicInfo: MemberBasicInfoDraft
    var createdMemberID: Int?
    var modules: MemberModuleSetupDraft
    var medical: MemberMedicalPrefillDraft
    var nutrition: MemberNutritionPrefillDraft
    var lifestyle: MemberLifestylePrefillDraft?

```

模块草稿建议：

```swift
struct MemberModuleSetupDraft: Equatable, Sendable {
    var medicalEnabled: Bool
    var nutritionEnabled: Bool
    var lifestyleEnabled: Bool
    var recommendedModuleCodes: [String]
```

服务端使用通用 `module_code` 表时，客户端最终建议改为：

```swift
struct MemberModuleDraft: Equatable, Sendable {
    var code: String
    var enabled: Bool
    var status: String
    var isRecommended: Bool
}
```

第一期也建议使用通用数组，避免固定字段后续迁移。

## 十三、权限和共享

### Q：共享成员如何处理？

A：如果成员来自分享绑定，当前用户未必有管理权限。

规则：

| 权限 | 是否可修改模块 |
| --- | --- |
| owner/admin/manage | 可修改模块 |
| editor | 可新增记录，但是否可改模块需确认 |
| viewer | 只读，不可改模块 |

如果用户没有权限：

1. 首页仍按模块展示。
2. 模块设置入口置灰或隐藏。
3. 提示“你没有管理该成员模块的权限”。

## 十四、AI 对话影响

第一期不设计 AI 工具调用权限，也不设计“模块关闭后 AI 是否读取历史数据”的规则。

本需求只保留一个轻量影响：

1. 模块设置可以作为普通会话上下文摘要的一部分。
2. 不作为 AI 工具权限判断。
3. 不作为历史数据读取开关。
4. 不新增独立 AI 权限模型。

示例：

```text
如果成员开启医疗模块：
AI 可以在普通上下文中看到医疗摘要，例如慢病、用药、体检指标关注项。

如果成员开启饮食健康：
AI 可以在普通上下文中看到饮食目标摘要，例如减重、卡路里目标、营养目标。

如果模块未开启：
第一期不额外设计 AI 读取历史数据的规则。
```

建议上下文摘要：

```json
{
  "member_modules": [
    {
      "code": "medical",
      "status": "enabled_completed",
      "summary": "高血压、糖尿病，用药提醒 2 个"
    },
    {
      "code": "nutrition",
      "status": "enabled_completed",
      "summary": "目标：减重；卡路里目标 1584 kcal"
    }
```

## 十五、实施分期建议

### 15.1 第一期必须做

第一期目标是把“新建成员不是空壳”跑通，重点做三件事：

1. 基础信息建档，点击下一步后立即创建成员。
2. 医疗、饮食健康两个可见模块选择和分步维护。
3. 首页按启用模块展示，排序由服务端 `display_order` 控制。

第一期范围：

| 范围 | 是否做 | 说明 |
| --- | --- | --- |
| 基础信息 | 做 | 姓名、关系、性别、年龄/出生日期；年龄由 `birth_date` 推导 |
| 创建成员 | 做 | 姓名生日页、关系性别页完成后创建真实成员 |
| 模块选择 | 做 | 只展示医疗、饮食健康 |
| 至少开启一个模块 | 做 | 不允许只创建空成员 |
| 医疗分步维护 | 做 | 慢病、用药、体检指标、症状/随访 |
| 用药计划 | 做 | 医疗用药步骤内 sheet 打开 `MedicationPlanStepperView` |
| 体检指标 | 做 | 支持手动录入最新指标值 |
| 饮食健康分步维护 | 做 | 对接饮食目标和身体指标计算 |
| 日常健康 | 仅代码预留 | 不展示、不落地、不做每日记录 |
| 成长发育 | 不做 | 第一阶段不做 |
| 照护安全 | 不做 | 第一阶段不做 |
| AI 工具权限 | 不做 | 不设计模块级 AI 工具权限 |

### 15.2 第二期建议做

第二期可以继续增强已有模块，不急于扩展新模块：

1. 医疗指标从 `extra` 迁移为结构化指标记录表。
2. 饮食健康和 Apple 健康数据联动更完善。
3. 首页模块排序和展示样式由服务端配置。
4. 日常健康根据产品节奏决定是否从代码预留变成可见模块。

### 15.3 第三期可做

第三期再评估新增模块：

1. 成长发育是否独立成模块。
2. 照护安全是否独立成模块。
3. 家属协作、通知、确认状态是否进入成员模块体系。
4. 是否需要模块级权限控制。

### 15.4 不建议第一期做的内容

1. 不建议一开始做五个模块全量配置，会让新建成员流程过重。
2. 不建议第一期做成长发育。
3. 不建议第一期做照护安全。
4. 不建议第一期展示日常健康模块。
5. 不建议第一期设计 AI 工具权限和历史数据读取规则。
6. 不建议为每个模块都新建复杂记录表，第一期先做“模块配置 + 摘要”即可。

## 十六、验收要点

1. 新建成员必须先填写基础信息。
2. 新建成员基础信息分为姓名生日页、关系性别页。
3. 姓名生日页点击下一步进入关系性别页。
4. 关系性别页点击下一步后创建真实成员，并获得 `memberID`。
5. 模块选择页只展示医疗模块和饮食健康。
6. 至少开启一个模块后才能完成。
7. 点击 `去完善` 使用 sheet 打开对应模块分步维护页。
8. 医疗模块 sheet 分为慢病、用药、体检指标、症状/随访多个页面。
9. 饮食健康 sheet 分为身体信息、目标设置、营养目标多个页面。
10. 医疗和饮食健康 sheet 的非必填步骤支持跳过。
11. 医疗用药步骤可以 sheet 打开 `MedicationPlanStepperView` 创建用药计划。
12. 体检指标支持手动录入最新指标值。
13. 饮食健康模块可以进入目标计算和营养目标预填。
14. 日常健康仅代码预留，不在 UI 和首页展示。
15. 成长发育、照护安全第一期不做。
16. 完成后首页只展示该成员开启的模块。
17. 首页模块排序由服务端控制。
18. 成员共享权限不足时不能编辑模块设置。
19. 进入模块选择页前必须已经创建成员，并持有 `memberID`。
20. 模块启用状态独立保存到 `MemberModuleSetting`。
21. 医疗模块完成时立即保存 `MemberMedicalProfile`，并更新 `MemberModuleSetting(module_code=medical)`。
22. 饮食健康完成时立即保存 `NutritionGoal`，并更新 `MemberModuleSetting(module_code=nutrition)`。
23. 最后完成建档流程不再一次性提交所有模块，只做校验、刷新和关闭。
24. 失败时不产生半创建脏数据；如果模块保存失败，需要可重试，不重复创建成员。
25. 模块推荐由客户端根据年龄、关系和 Apple 健康权限本地计算。

## 十七、已决策结论

| 问题 | 结论 |
| --- | --- |
| 年龄是否作为 `Member` 主字段 | 不新增年龄主字段，年龄只通过 `birth_date` 推导 |
| 身高是否属于成员基础信息 | 不属于基础信息，只属于饮食健康目标计算 |
| `MemberMedicalProfile` 归属 | 放在 `medical` app 内 |
| `MemberModuleSetting` 归属 | 放在 `medical` app 内 |
| 用药计划如何创建 | 基础信息下一步先创建成员；医疗模块用药步骤内 sheet 打开 `MedicationPlanStepperView` |
| 体检指标如何处理 | 支持手动录入最新指标值 |
| 日常健康第一期是否展示 | 不展示，只保留代码预留 |
| 模块启用是否参与 AI 工具权限 | 不设计 AI 工具权限 |
| 模块关闭后 AI 是否读取历史数据 | 不设计 AI 历史数据规则 |
| 本人已有 Apple 健康权限时是否推荐饮食健康 | 是，客户端自动建议开启饮食健康 |
| 成长发育第一期是否做 | 不做 |
| 照护安全第一期是否做 | 不做 |
| 模块推荐来源 | 客户端根据年龄、关系、Apple 健康权限本地计算 |
| 模块状态结构 | 使用通用 `module_code` 表 |
| 首页排序 | 服务端控制 |
