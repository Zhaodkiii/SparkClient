## 一、背景

当前“医疗模块”在成员维度是一个整体开关：

```text
MemberModuleSetting(module_code=medical)
```

但医疗内部实际包含多个不同目的、不同数据源、不同开通门槛的子模块：

```text
病历
体检报告
医疗报告
用药
```

如果只用一个总开关，会出现几个问题：

1. 用户只是想上传一份病历，也被要求走完整医疗引导，阻力过高。
2. 用户只完成体检问答，不代表已经愿意维护用药计划。
3. 用药、体检报告、医疗报告的事实源不同，不能用同一套完成状态表达。
4. 首页和成员详情页无法准确展示“哪些医疗能力已经开通，哪些还未开通”。

因此需要在“医疗总模块”下面增加“医疗子模块独立开通”能力。

---

## 二、目标

### 2.1 核心目标

医疗模块内部每一个子模块都可以单独开通、单独完善、单独展示状态。

第一期子模块：

| 子模块 | module_code 建议 | 主要能力 |
| --- | --- | --- |
| 病历 | `medical_case` | 门诊病历、住院病历、出院小结等病例资料 |
| 体检报告 | `health_exam_report` | 体检报告上传、体检问答、异常指标、体检计划 |
| 医疗报告 | `medical_report` | 检查报告、检验报告、影像报告等非体检类报告 |
| 用药 | `medication` | 用药计划、服药提醒、药箱候选、长期用药摘要 |

### 2.2 设计原则

1. 成员基础信息是所有医疗子模块的前置条件。
2. 医疗子模块之间不互相强制依赖。
3. 子模块开通不等于数据完整，只表示用户已明确启用该能力。
4. 子模块完成状态由该模块自己的事实源决定。
5. 医疗总模块状态由子模块聚合，不再要求用户一次性完成所有医疗问答。

---

## 三、开通门槛

### 3.1 统一前置：用户基本信息

所有医疗子模块开通前，必须先有真实 `memberID` 和基础信息。

基础信息最小字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 姓名 | 是 | 用于病历、报告、用药归属 |
| 关系 | 是 | 当前用户与成员的关系 |
| 性别 | 建议必填 | 影响体检计划、报告解释、部分用药/检查提示 |
| 出生日期或年龄 | 建议必填 | 影响体检计划、报告参考范围、风险评估 |

如果用户从某个医疗入口直接进入，但当前还没有成员基础信息，应先进入轻量建档流程：

```text
医疗入口
-> 选择已有成员或新建成员
-> 补齐基础信息
-> 创建/确认 memberID
-> 回到目标医疗子模块开通流程
```

### 3.2 子模块开通策略

| 子模块 | 开通前置 | 开通动作 | 完成条件 |
| --- | --- | --- | --- |
| 病历 | 成员基础信息 | 用户确认启用病历模块，或首次保存病历 | 至少保存一条病例，或用户确认“暂无病历，稍后补充” |
| 体检报告 | 成员基础信息 + 体检问答 | 走完体检问答并保存体检档案状态 | 问答保存成功，或至少保存一份体检报告 |
| 医疗报告 | 成员基础信息 | 用户确认启用医疗报告模块，或首次保存报告 | 至少保存一份检查/检验/影像报告 |
| 用药 | 成员基础信息 | 用户确认启用用药模块，或首次保存用药计划 | 至少保存一条有效用药计划，或用户确认“暂无长期用药” |

## 四、各子模块流程

### 4.1 病历

病历走成员基础信息，不强制走完整体检问答。

推荐流程：

```text
点击病历
-> 校验 memberID 和基础信息
-> 未建档则补齐基础信息
-> 开通 medical_case 子模块
-> 进入病历列表/上传/手动录入
-> 保存病例后更新子模块 completed 状态
```

开通原因：

1. 病历核心是就诊事件和病例材料归属，基础信息即可建立归属关系。
2. 病历可能发生在体检之前，不应要求用户先完成体检问答。
3. 病历可以反向补充医疗画像，例如既往疾病、手术史、过敏史。

### 4.2 体检报告

体检报告需要走完体检问答。

推荐流程：

```text
点击体检报告
-> 校验 memberID 和基础信息
-> 进入体检问答
-> 保存体检档案摘要、关键指标、风险评估基础数据
-> 开通 health_exam_report 子模块
-> 进入体检报告上传/历史体检档案
```

开通原因：

1. 体检报告的价值不只是保存 PDF，而是生成异常指标、趋势和体检计划。
2. 体检计划依赖年龄、性别、病史、家族史、生活方式、过往体检情况。
3. 体检问答完成后，AI 才能更稳定地解释报告和推荐复查/随访任务。

第一期可以允许“先上传报告，后补问答”，但开通状态建议区分：

```text
enabled = true
status = pending_profile
completed = false
```

用户完成体检问答后再变更为：

```text
status = completed
completed = true
```

### 4.3 医疗报告

医疗报告指非体检类检查、检验、影像、病理等报告。

第一期建议医疗报告走成员基础信息，不强制走体检问答。

推荐流程：

```text
点击医疗报告
-> 校验 memberID 和基础信息
-> 开通 medical_report 子模块
-> 进入报告上传/识别
-> 用户选择或 AI 识别报告类型
-> 保存结构化报告
-> 更新子模块 completed 状态
```

开通原因：

1. 医疗报告通常来自一次就医或检查，不一定与年度体检相关。
2. 检查报告可能是用户当前最紧急的需求，不应被完整体检问答阻塞。
3. 报告解读可以基于基础信息和报告自身内容先完成，后续再提示补充病史和用药。

需要注意：

1. 如果报告类型会明显依赖性别、年龄，应在提交前提示补齐对应字段。
2. 如果报告解读需要病史、症状、用药背景，可以在结果页给出“补充背景信息后重新解读”的入口。
3. 医疗报告不自动代表体检报告开通，二者状态独立。

### 4.4 用药

用药走成员基础信息，并以真实 `MedicationPlan` 作为事实源。

推荐流程：

```text
点击用药
-> 校验 memberID 和基础信息
-> 开通 medication 子模块
-> 进入用药计划列表
-> 添加用药计划/处方识别/药箱候选确认
-> 保存 MedicationPlan
-> 服务端聚合长期用药摘要
-> 更新子模块 completed 状态
```

开通原因：

1. 用药计划可以独立于病历和体检存在。
2. 用药事实源应该是 `MedicationPlan`，不是 `MemberMedicalProfile.long_term_medications`。
3. 用户可以没有长期用药，仍然需要一个明确状态表达“已确认暂无用药”。

用药完成状态建议：

```text
有有效 MedicationPlan
或用户确认 no_current_medication = true
```

如果用户只是进入页面但没有添加计划，也没有确认暂无用药：

```text
enabled = true
status = pending
completed = false
```

## 五、数据模型建议

### 5.1 新增医疗子模块设置

可以复用 `MemberModuleSetting` 的设计思路，也可以新增子模块设置表。推荐新增子模块设置，避免把医疗总模块和医疗内部模块混在一个字段里。

建议模型：

```text
MemberMedicalSubmoduleSetting
- id
- user_id
- member_id
- submodule_code
- is_enabled
- status
- completed_at
- last_opened_at
- source
- extra
- created_at
- updated_at
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `submodule_code` | `medical_case` / `health_exam_report` / `medical_report` / `medication` |
| `is_enabled` | 用户是否启用该子模块 |
| `status` | `not_started` / `pending_basic_info` / `pending_profile` / `pending_data` / `completed` |
| `source` | `manual` / `upload` / `guide_qa` / `import` / `ai` |
| `extra` | 保存轻量状态，例如 `no_current_medication`、`skip_reason` |

### 5.2 医疗总模块聚合

医疗总模块仍保留：

```text
MemberModuleSetting(module_code=medical)
```

聚合规则：

```text
任意医疗子模块 is_enabled = true
-> medical.is_enabled = true

任意医疗子模块 status = completed
-> medical 可展示为已开通

所有已启用子模块都未完成
-> medical 展示为待完善
```

不要因为用药未完成而阻止病历、报告展示；也不要因为体检问答未完成而隐藏已上传的医疗报告。

## 六、页面与入口

### 6.1 成员详情页

成员详情页医疗区域应展示子模块级入口：

```text
医疗档案
├─ 病历
├─ 体检报告
├─ 医疗报告
└─ 用药
```

每个入口展示独立状态：

| 状态 | 展示建议 |
| --- | --- |
| 未开通 | 显示“去开通” |
| 待补基础信息 | 显示“补充基础信息” |
| 待完善 | 显示“继续完善” |
| 已完成 | 显示数量或摘要 |

### 6.2 医疗上传入口

从上传入口进入时，应根据文档类型自动路由到对应子模块：

| 文档类型 | 子模块 |
| --- | --- |
| `caseDocument` | 病历 |
| `healthExamReport` | 体检报告 |
| `medicalReport` | 医疗报告 |
| `prescription` | 用药 |
| `medicationPlan` | 用药 |
| `medicineBox` | 用药或家庭药箱，按当前业务入口决定 |

如果 AI 类型识别结果和用户入口不一致，优先让用户确认最终保存类型，再开通对应子模块。

## 七、接口建议

### 7.1 查询子模块状态

```text
GET /api/v1/medical/members/{member_id}/submodule-settings/
```

返回示例：

```json
{
  "member_id": 100,
  "items": [
    {
      "submodule_code": "medical_case",
      "is_enabled": true,
      "status": "completed",
      "summary": "病历 3 份"
    },
    {
      "submodule_code": "health_exam_report",
      "is_enabled": true,
      "status": "pending_profile",
      "summary": "待完成体检问答"
    },
    {
      "submodule_code": "medical_report",
      "is_enabled": false,
      "status": "not_started",
      "summary": ""
    },
    {
      "submodule_code": "medication",
      "is_enabled": true,
      "status": "completed",
      "summary": "长期用药 2 项"
    }
  ]
}
```

### 7.2 开通或更新子模块

```text
POST /api/v1/medical/members/{member_id}/submodule-settings/
PATCH /api/v1/medical/members/{member_id}/submodule-settings/{submodule_code}/
```

请求示例：

```json
{
  "submodule_code": "medication",
  "is_enabled": true,
  "status": "pending_data",
  "source": "manual",
  "extra": {}
}
```

### 7.3 聚合详情

成员详情页可以继续使用聚合接口返回医疗概览，但需要增加子模块状态：

```text
GET /api/v1/medical/members/{member_id}/detail-dashboard/
```

建议增加：

```json
{
  "medical_overview": {
    "medical_case_count": 3,
    "health_exam_report_count": 1,
    "medical_report_count": 5,
    "medication_plan_count": 2,
    "submodule_settings": []
  }
}
```

## 八、验收标准

1. 新建成员后，可以只开通病历、体检报告、医疗报告、用药中的任意一个子模块。
2. 开通任意医疗子模块前，系统必须确保成员基础信息已存在。
3. 病历开通只依赖成员基础信息，不强制体检问答。
4. 体检报告开通需要完成体检问答；如果先上传报告，状态必须是待补体检问答。
5. 医疗报告开通只依赖成员基础信息，不强制体检问答。
6. 用药开通只依赖成员基础信息，用药完成状态以 `MedicationPlan` 或“暂无用药确认”为准。
7. 医疗总模块根据子模块状态聚合展示，不阻塞已完成子模块。
8. 上传识别保存成功后，能自动开通或更新对应子模块状态。
9. 删除最后一条模块数据时，子模块不自动关闭，但状态应回退为 `pending_data` 或展示“暂无数据”。
10. 成员详情页能展示四个子模块的独立状态和数量摘要。

## 九、待确认问题

1. 体检报告是否允许“先上传报告，后完成体检问答”？建议允许，但状态为 `pending_profile`。
2. 医疗报告是否需要一个轻量问答，例如症状、就诊科室、检查原因？建议第一期不作为开通门槛，只在报告解读页提示补充。
3. 用药模块是否需要区分“药箱”和“用药计划”两个子模块？建议第一期用药子模块只以 `MedicationPlan` 为完成事实源，药箱作为辅助能力。
4. 病历和医疗报告是否需要共享同一个“就诊事件”主表？如果服务端已有病例主表，第一期可先不强制改造。
5. 医疗子模块设置是新增表，还是扩展现有 `MemberModuleSetting` 支持层级 module_code？建议新增表，避免影响现有成员模块配置。
