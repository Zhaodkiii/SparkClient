# 成员详情页重设计需求工单

> 文档性质：独立需求工单与 UI 设计稿。本文讨论 `MemberDetailView` 的重设计方向、页面信息架构、交互文案、数据整合方式、接口调用顺序与服务端配合项；本文不做代码实现。

- 项目：SparkClient
- 对应页面：`SparkClient/Projects/Features/MemberContext/Presentation/MemberDetailView.swift`
- 文档版本：v1.0
- 生成日期：2026-06-19

---

## 一、背景

当前成员详情页的职责已经从“简单资料展示”扩展为“成员管理入口”。

现状页面能展示基础资料、绑定关系、医疗概览、共享用户，也支持编辑、分享、删除/解绑等操作。但整体呈现方式偏信息堆叠，存在以下问题：

1. 头部层级不够清晰，用户不容易第一眼识别“这个成员是谁、我和他的关系是什么、当前可做什么”。
2. 信息分区虽然齐全，但缺少主次之分，医疗数据、绑定关系、共享用户和危险操作并列出现，阅读压力偏大。
3. 更多操作入口集中在右上角，但页面主体没有明确的动作引导，容易让用户只看到“资料表”而不是“管理页”。
4. 详情页缺少更适合 iOS 的卡片化层次、视觉节奏与状态表达。
5. 当前页面在功能上是完整的，但在视觉和信息编排上还可以更明确地围绕“功能优先、阅读顺序清楚、操作风险可感知”重新设计。

本工单目标不是增加新业务，而是把现有功能重新组织成更适合成员管理的详情页。

---

## 二、目标

### 2.1 页面目标

成员详情页需要回答四个问题：

1. 这个成员是谁？
2. 我和这个成员是什么关系？
3. 这个成员有哪些关键健康信息？
4. 我现在能对这个成员做什么？

### 2.2 设计目标

1. 用更强的层级表达成员身份与绑定关系。
2. 用卡片化分区承载现有功能，不增加额外复杂度。
3. 将“常用操作”和“危险操作”明确分层。
4. 保留当前功能完整性，不删功能，不改业务语义。
5. 在视觉上更贴近 iOS 原生详情页，但更精致、更清楚。

### 2.3 非目标

第一期不做：

1. 不新增新的成员业务能力。
2. 不改接口字段语义。
3. 不改分享、编辑、删除/解绑的业务规则。
4. 不做复杂动效，只做必要的轻量状态反馈。
5. 不引入非系统风格的重型视觉元素。

## 三、设计原则

### 3.1 以功能为主

页面的视觉设计必须服务于功能，而不是只追求装饰感。

原则：

1. 先让用户看懂身份与关系，再看其他信息。
2. 高价值信息前置，低频信息后置。
3. 危险操作收在底部独立区域，避免误触。
4. 所有区块都应能对应到明确功能，不做纯展示凑数。

### 3.2 iOS 原生感

建议保持以下方向：

1. 使用 `NavigationStack` / `ScrollView` / 卡片式 `Section`。
2. 主要内容采用系统语义颜色。
3. 卡片使用圆角连续风格与轻阴影。
4. 顶部可以使用轻量玻璃材质强化层次，但不做过重拟物。

### 3.3 信息层级

层级建议如下：

1. 成员身份卡
2. 模块总览卡
3. 关系与权限卡
4. 健康概览卡
5. 绑定成员卡
6. 饮食设定与数据卡
7. 操作区
8. 危险操作区

### 3.4 文案原则

1. 文案尽量短，避免长句堆叠。
2. 重要状态要可读，例如“已绑定 2 位用户”“我的权限：管理员”。
3. 危险操作文案必须明确影响范围。

## 四、现有功能保留范围

本次重设计必须保留的功能：

1. 查看成员基础资料。
2. 查看“我与成员”的绑定关系与角色。
3. 查看成员医疗概览。
4. 查看共享用户列表。
5. 分享成员。
6. 编辑成员。
7. 删除/解绑成员。

本次重设计不新增的功能：

1. 不新增成员标签体系。
2. 不新增独立时间轴。
3. 不新增独立统计图表。
4. 不新增复杂筛选或搜索。

### 5.2 页面阅读路径

推荐阅读顺序：

1. 顶部身份卡
2. 模块总览卡
3. 我的绑定卡
4. 医疗概览卡
5. 饮食设定与数据卡
6. 共享用户卡
7. 危险操作区

这样用户先理解“对象是谁”和“自己能做什么”，再看数据和共享关系。

### 5.3 数据来源与口径

这部分必须在需求里说清楚，避免实现时对“卡片上这些数字从哪里来”产生歧义。

#### 5.3.1 基础资料数据

来源：

1. `Member` 基础资料。
2. 当前用户视角下的 `UserMemberBinding`。

展示口径：

1. 性别、出生日期、血型、过敏史、慢病、备注均来自 `Member`。
2. “我与成员的关系”“我的权限”“是否默认成员”来自 `UserMemberBinding`。
3. 顶部身份卡中的“共享状态摘要”来自当前成员的绑定人数或共享用户数量。

#### 5.3.2 医疗概览数据

来源：

1. 成员医疗资源聚合接口返回的统计字段。
2. 或页面加载详情时顺带返回的 `medicalOverview` 聚合对象。

展示口径：

1. 病历数 = 当前成员关联的病例总数。
2. 体检报告数 = 当前成员关联的体检报告总数。
3. 检查报告数 = 当前成员关联的检查报告总数。
4. 服药计划数 = 当前成员关联的用药计划总数。
5. 最近更新时间 = 医疗模块相关资源的最新更新时间，优先使用服务端汇总时间。

#### 5.3.3 饮食设定与数据

来源：

1. 饮食模块配置接口，返回目标模式、活跃水平、摄入目标、体重目标。
2. 饮食目标计算结果，返回 BMR、TDEE、三大营养素目标。
3. 当天或近期开启的饮食记录汇总，用于展示记录进度。

展示口径：

1. 目标模式 = 当前成员饮食目标模式，例如保持、减重、增重。
2. 活跃水平 = 饮食目标计算时使用的活动强度档位。
3. 每日摄入目标 = 服务端返回的最终建议值或用户保存后的当前值。
4. BMR / TDEE = 由饮食计算结果直接返回，只读展示。
5. 三大营养素 = 按当前摄入目标和计算模型生成的目标值。
6. 当前体重 / 目标体重 = 饮食目标草稿或已保存目标中的数值。
7. 记录进度 = 例如近 7 天已记录几天、今日三餐是否已记录、或当前周期内已完成几餐。第一期必须在接口里固定一种口径，避免客户端自算。

#### 5.3.4 模块总览数据

来源：

1. 医疗模块是否开通，来自成员模块开关状态。
2. 饮食模块是否开通，来自成员模块开关状态。
3. 每个模块的快捷入口状态，来自当前用户权限与模块状态。

展示口径：

1. 模块总览卡只负责告诉用户“开了什么”和“能点什么”。
2. 不在模块总览里展示完成度百分比，避免弱化页面的功能重心。
3. 如果模块未开通，显示“未开通”和对应引导入口。
4. 如果模块已开通但数据未完善，显示“去完善”入口即可，不强行做百分比。

### 5.4 进入详情页的数据调用说明

详情页需要展示的数据已经跨了成员、绑定、模块、医疗、饮食五类信息。为了避免客户端在页面里散落并发请求，建议第一期优先由服务端提供一个聚合详情接口。

#### 5.4.1 推荐调用方式

推荐新增：

```text
GET /api/v1/medical/members/{member_id}/detail-dashboard/
```

用途：

1. 返回成员详情页首屏需要的完整展示数据。
2. 服务端统一做权限校验、模块状态聚合、医疗统计聚合、饮食摘要聚合。
3. 客户端只负责渲染，不在详情页内自行计算业务口径。

页面进入时调用：

```text
进入 MemberDetailView
-> GET /api/v1/medical/members/{member_id}/detail-dashboard/
-> 成功后渲染：身份卡 / 模块总览 / 基础资料 / 我的绑定 / 医疗概览 / 饮食设定与数据 / 共享用户
-> 用户下拉刷新或分享/解绑/编辑后，再重新请求 detail-dashboard
```

#### 5.4.2 兼容现有接口的短期方案

如果服务端短期不新增聚合接口，客户端可临时并发调用现有接口，但这只是过渡方案。

```text
进入 MemberDetailView
-> GET /api/v1/medical/members/{member_id}/
   获取成员基础资料、我的绑定、权限、共享用户、medicalOverview
-> GET /api/v1/medical/members/{member_id}/module-settings/
   获取 medical / nutrition 模块开通状态
-> GET /api/v1/nutrition/goals/?member_id={member_id}
   获取饮食目标设定、默认宏量目标
-> GET /api/v1/nutrition/dashboard/?member_id={member_id}&date={today}
   获取今日摄入、餐次、饮食记录摘要
```

说明：

1. `GET /api/v1/medical/members/{member_id}/` 当前已有成员详情能力，可继续作为基础数据来源。
2. `GET /api/v1/nutrition/goals/` 当前已有目标状态能力，可作为饮食设定来源。
3. `GET /api/v1/nutrition/dashboard/` 当前已有看板能力，可作为今日饮食数据来源。
4. `module-settings` 如果服务端尚未提供，需要补齐；否则模块总览无法稳定展示开通状态。
5. 医疗概览优先使用成员详情返回的 `medicalOverview`，不要为了统计数量拉取完整 `complete-data`。

#### 5.4.3 调用策略

1. 首屏优先展示聚合接口返回的数据。
2. 分享、编辑、解绑、共享用户管理完成后刷新聚合接口。
3. 饮食模块“去完善”保存成功后刷新聚合接口。
4. 医疗模块新增病例、报告、用药计划后刷新聚合接口。
5. 任一子模块数据获取失败时，页面保留基础成员信息，并在对应卡片显示轻量错误态。

#### 5.5.2 Swift DTO 建议

```swift
struct MemberDetailDashboardResponse: Decodable, Sendable {
    let member: MemberSummary
    let myBinding: MyBinding
    let capabilities: Capabilities
    let modules: [MemberModuleSummary]
    let medicalOverview: MedicalOverview?
    let nutritionOverview: NutritionOverview?
    let sharedUsers: [SharedUser]
}

struct MemberModuleSummary: Decodable, Sendable, Identifiable {
    var id: String { moduleCode }
    let moduleCode: String
    let enabled: Bool
    let status: String
    let displayOrder: Int
    let summaryText: String?
    let primaryAction: String?
    let secondaryAction: String?
}

struct NutritionOverview: Decodable, Sendable {
    let goalMode: String?
    let activityLevel: String?
    let dailyEnergyTargetKcal: Double?
    let bmrKcal: Double?
    let tdeeKcal: Double?
    let carbohydrateTargetG: Double?
    let proteinTargetG: Double?
    let fatTargetG: Double?
    let currentWeightKg: Double?
    let targetWeightKg: Double?
    let recordProgressText: String?
    let lastRecordedAt: Date?
}
```

客户端展示模型可以在 ViewModel 内从该 DTO 映射为更稳定的 UI State：

```text

-> MemberDetailViewState
   -> HeaderState
   -> ModuleOverviewState
   -> ProfileState
   -> BindingState
   -> MedicalOverviewState
   -> NutritionOverviewState
   -> SharedUsersState
```

### 5.6 服务端配合项

本次详情页重设计建议服务端配合增加或确认以下能力。

#### 5.6.1 必须确认

1. `GET /api/v1/medical/members/{member_id}/` 是否稳定返回 `medicalOverview`。
2. `MemberModuleSetting` 是否已经有可读接口。
3. 饮食模块是否能通过 `GET /api/v1/nutrition/goals/?member_id=` 返回当前目标设定。
4. 饮食看板是否能通过 `GET /api/v1/nutrition/dashboard/?member_id=&date=` 返回当天记录摘要。

#### 5.6.2 建议新增

1. 新增 `GET /api/v1/medical/members/{member_id}/detail-dashboard/`，作为成员详情页聚合接口。
2. 新增或补齐 `GET /api/v1/medical/members/{member_id}/module-settings/`，返回该成员对当前用户的模块开通状态。
3. 如果不希望 medical 服务依赖 nutrition 服务，可由客户端短期并发拉 nutrition；但长期建议服务端提供聚合接口减少页面调用复杂度。

#### 5.6.3 权限要求

1. 聚合接口必须先校验当前用户是否拥有该成员有效绑定。
2. 医疗概览和饮食概览只能返回当前用户有权限访问的成员数据。
3. 共享用户列表按 `can_manage_bindings` 决定是否返回完整用户信息。
4. 删除、解绑、编辑、分享入口必须以服务端返回的能力位为准。

#### 5.6.4 失败与降级

1. 成员基础信息拉取失败，整个页面进入错误态。
2. 医疗概览拉取失败，只影响医疗概览卡。
3. 饮食概览拉取失败，只影响饮食卡。
4. 模块状态缺失时，模块总览不展示对应模块的操作入口，只展示“状态未知，请稍后重试”。
5. 聚合接口内部某个子模块失败时，建议服务端返回局部 `error_code`，不要直接让整个详情页 500。

4. 可在头像旁加入 SF Symbols，如 `person.crop.circle.fill`，增强识别度与层次感。

### 7.1 右上角菜单

### 7.3 菜单与页面主体的关系

建议：

1. 菜单保留高频动作。

## 八、交互设计

### 8.1 页面进入

1. 进入时先显示骨架屏或加载态。
2. 加载成功后卡片顺序渐进呈现。
3. 顶部身份卡优先出现，其余卡片随后布局。

### 8.2 状态切换

1. 卡片展开、收起、操作切换使用平滑 spring 动画。
2. 共享用户列表变更后，页面局部刷新，不整页闪烁。
3. 删除/解绑前后有明确确认流程。

### 8.3 重点反馈

建议在以下交互中加入触觉反馈提示：

1. 分享成功。
2. 编辑保存成功。
3. 解绑成功。
4. 删除成员档案成功。
5. 饮食模块开通或完善成功。

### 8.4 危险操作确认

确认弹窗必须根据实际语义变化：

说明：删除后将移除该成员及相关健康资料，所有绑定用户都可能受到影响。

## 十、样式建议

> 本节是视觉方向建议，不是代码实现要求。

### 10.1 字体

1. 全面使用语义化字体层级。
2. 标题建议使用 `.title2` 或 `.title3`。
3. 分区标题建议使用 `.headline` 并搭配 semibold。
4. 说明文字使用 `.subheadline` / `.footnote`。
5. 数字建议使用等宽数字，增强对齐感。

### 10.2 颜色

1. 以系统语义色为主。
2. 主要文本使用 `.primary`。
3. 辅助说明使用 `.secondary`。
4. 背景建议使用系统分组背景。
5. 强调按钮使用系统 tint，不要自定义固定色值。
6. 模块状态可用系统蓝、系统绿、系统橙表达开通、正常、待完善等状态。

### 10.3 材质

1. 右上角菜单、顶部浮层或轻量悬浮元素可使用系统材质。
2. 不建议整页大面积高强度磨砂，避免削弱健康管理场景的清晰度。
3. 如果顶部身份卡需要更精致，可以少量使用 `.regularMaterial` 作为背景层。

### 10.4 圆角与阴影

1. 统一使用连续圆角。
2. 阴影要轻、淡、柔。
3. 卡片间距遵循 8pt 网格，主边距建议 16 或 20。
