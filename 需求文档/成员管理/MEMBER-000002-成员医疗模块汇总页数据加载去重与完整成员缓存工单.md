## 一、是否支持该方案

建议支持。

当前问题不是“某个接口慢”，而是页面进入时多个 ViewModel 分别加载同一个成员的医疗资料，导致同一批成员级数据被拆成多次请求：

```text
member-guidance 1 次
nutrition goals 1 次
member-module-settings 1 次
symptoms 1 次
member-medical-profiles 4 次
medication-plans 1 次
surgeries 1 次
```

总计 10 次请求，其中 `member-medical-profiles` 重复 4 次，症状、用药、手术又和 `RemoteMemberCompleteData` 能承载的数据重叠。

更合理的方向是：

```text
以成员为单位加载 RemoteMemberCompleteData
将 MemberMedicalProfile、模块配置、症状、用药计划、手术记录纳入成员完整数据快照
模块汇总页只消费快照，不再各自重复拉列表
用户提交成功后回写快照缓存
```

这样可以把“页面级碎请求”收敛成“成员级快照 + 必要刷新”。

## 二、当前问题

### 2.1 进入页面请求次数过多

一次进入成员医疗模块汇总页，日志显示实际请求：

```text
GET /api/v1/medical/member-guidance/?member_id=597                         1次
GET /api/v1/nutrition/goals/?member_id=597                                  1次
GET /api/v1/medical/resources?kind=member-module-settings...                1次
GET /api/v1/medical/resources?kind=symptoms&member_id=597                   1次
GET /api/v1/medical/resources?kind=member-medical-profiles&member_id=597    4次
GET /api/v1/medical/resources?kind=medication-plans&member_id=597           1次
GET /api/v1/medical/resources?kind=surgeries&member_id=597                  1次
```

总计：

```text
10 次请求
```

即使部分是 304，也仍然有网络调度、缓存判断、日志、解码和状态刷新成本。

### 2.2 MemberMedicalModuleSummaryViewModel 内部重复构造引导 ViewModel

当前 `MemberMedicalModuleSummaryViewModel` 初始化时会创建：

```text
MemberMedicalSetupViewModel
```

并在 `loadIfNeeded()` 中：

```text
先请求 sectionProgressMap
再调用 medicalSetupViewModel.loadIfNeeded()
```

这会让“汇总页展示摘要”复用“完整医疗引导流程 ViewModel”的加载逻辑。

问题：

```text
汇总页只需要展示摘要和完成状态
但完整引导 ViewModel 会加载更多表单所需数据
```

因此请求放大。

### 2.3 资源列表和完整成员数据重复

以下列表本质是成员维度数据：

```text
症状记录列表
用药计划列表
手术记录列表
成员医疗档案
模块配置
```

它们不应该在进入汇总页后再分别请求。

更好的方式是作为 `RemoteMemberCompleteData` 的一部分，随成员切换或模块页进入时一次加载。

## 三、目标设计

### 3.1 目标一句话

```text
成员医疗模块汇总页以 RemoteMemberCompleteData 作为唯一初始数据快照；
进入选择维护模块后预热一次成员完整数据；
进入医疗模块汇总页时只做缺失补齐或刷新；
所有分组提交成功后回写 RemoteMemberCompleteData 缓存。
```

### 3.2 目标请求数量

理想首进流程：

```text
进入选择维护模块
  -> 加载一次 RemoteMemberCompleteData(member_id)

进入医疗模块汇总页
  -> 如果缓存存在，直接渲染
  -> 如果缺少 memberMedicalProfile 或 moduleSettings，补一次医疗引导汇总/complete-data
```

目标：

```text
从 10 次请求降低到 1-2 次请求
```

### 3.3 数据职责

```text
RemoteMemberCompleteData
    = 成员级医疗数据快照
    = 页面初始渲染和模块汇总页摘要来源

MemberMedicalProfile
    = 成员医疗画像投影
    = 基础档案、健康病史、生活习惯、体检档案、症状/用药/手术摘要

MemberModuleSetting
    = 成员模块开关与分组完成进度

MemberMedicalModuleSummaryViewModel
    = 只从快照推导卡片状态，不单独拉症状/用药/手术列表
```

## 四、RemoteMemberCompleteData 扩展

### 4.1 当前模型

当前 `RemoteMemberCompleteData` 已包含：

```text
member
medicalCases
healthExamReports
examinationReports
medicineBoxes
familyMedicineBoxes
prescriptions
medicationPlans
todayMedicationRecords
medicationSummary
symptoms
visits
surgeries
followUps
```

位置：

```text
MedicalSyncAPI.swift:668-720
```

### 4.2 建议新增字段

建议补充：

```swift
/// 成员医疗画像投影；用于基础档案、病史、生活习惯、体检档案等摘要展示，不作为症状/用药/手术明细事实源。
var memberMedicalProfile: RemoteMemberMedicalProfile?
/// 成员模块开关与分组进度；用于判断首页展示哪些模块，以及模块汇总页各分组的完成状态。
var memberModuleSettings: [RemoteMemberModuleSetting]?
/// 饮食目标轻量快照；用于饮食模块汇总页基础信息展示，也可为医疗基础档案提供身高/体重初始值。
var nutritionGoalState: RemoteNutritionGoalState?
```

如果服务端希望按模块返回，也可以：

```swift
var medicalModuleSetting: RemoteMemberModuleSetting?
```

但从扩展性看，建议使用列表：

```text
memberModuleSettings
```

原因：

```text
RemoteMemberCompleteData 是成员完整数据；
一个成员可能同时有 medical、nutrition、daily_health 等模块配置；
列表比单个 medicalModuleSetting 更通用。
```

### 4.2.1 medicalGuidance 是否合并到 memberMedicalProfile

建议合并，不再作为 `RemoteMemberCompleteData` 的独立字段。

当前独立接口：

```text
GET /api/v1/medical/member-guidance/?member_id=597
```

作用：

```text
医疗模块汇总页首页数据
医疗引导分组完成状态
基础档案、健康病史、生活习惯、体检档案、风险评估的摘要
AI 体检计划和风险提示的轻量结果
```

这类数据本质上是“成员医疗模块摘要快照”，和 `memberMedicalProfile`、`symptoms`、`medicationPlans`、`surgeries` 强相关。

如果继续独立请求，会出现：

```text
completeData 有成员明细
member-guidance 又有医疗汇总
页面需要同时理解两套数据
```

因此建议把 `member-guidance` 的输出合并到 `RemoteMemberMedicalProfile` 的结构化投影字段内：

```swift
struct RemoteMemberMedicalProfile: Codable, Sendable, Equatable {
    ...

    /// 医疗引导分组摘要；由服务端基于 profile + 症状/用药/手术/体检档案聚合生成，用于医疗模块汇总页。
    var guidanceSections: [RemoteMemberMedicalProfileSectionSummary]?
    /// 风险评估摘要；用于医疗模块汇总页风险评估卡片和 AI 体检计划上下文。
    var riskAssessmentSummary: String?
    /// 下一次体检计划摘要；用于过往体检档案分组和医疗模块汇总页展示。
    var examPlanSummary: String?
    /// 医疗引导摘要更新时间；用于判断缓存新鲜度和调试数据来源。
    var guidanceUpdatedAt: Date?
}
```

目标用途：

```text
MemberMedicalModuleSummaryView 优先从 completeData.memberMedicalProfile.guidanceSections 渲染卡片摘要
风险评估读取 completeData.memberMedicalProfile.riskAssessmentSummary
下一次体检计划读取 completeData.memberMedicalProfile.examPlanSummary
只有 memberMedicalProfile 缺失或过期时，才补齐一次 profile/guidance 数据
```

建议结构：

```swift
struct RemoteMemberMedicalProfileSectionSummary: Codable, Sendable, Equatable {
    var sectionCode: String
    var title: String
    var summary: String
    var status: String
}
```

设计边界：

```text
Symptom / MedicationPlan / Surgery / HealthExamReport 仍然是明细事实源。
RemoteMemberMedicalProfile 内的 guidanceSections / riskAssessmentSummary / examPlanSummary 只是画像投影。
客户端不要同时维护 RemoteMemberMedicalGuidance 和 RemoteMemberMedicalProfile 两套医疗摘要模型。
```

### 4.2.2 nutritionGoalState 是否放入 RemoteMemberCompleteData

建议放入，但定位为“饮食模块轻量快照”，不要让医疗模块强依赖它。

当前独立接口：

```text
GET /api/v1/nutrition/goals/?member_id=597
```

作用：

```text
饮食健康模块基础信息
身高、体重、目标模式、热量目标、营养目标
饮食模块汇总页完成状态和摘要
医疗基础档案中身高/体重的可复用来源
```

这个接口不属于医疗模块本身，但属于“成员建档模块汇总页”的初始数据。

如果选择维护模块页面需要同时判断：

```text
医疗模块完成度
饮食健康完成度
```

那么饮食目标也应该随着成员完整快照一起预加载。

建议在 `RemoteMemberCompleteData` 内新增：

```swift
var nutritionGoalState: RemoteNutritionGoalState?
```

用途：

```text
MemberNutritionModuleSummaryView 使用 nutritionGoalState 渲染基础信息卡片
MemberMedicalSetupSheet 的身高/体重默认值可以复用 nutritionGoalState.goal
避免进入医疗页时再额外请求 nutrition goals
```

注意：

```text
医疗汇总页不应为了渲染医疗卡片主动请求 nutrition goals。
如果 completeData 内有 nutritionGoalState，可作为身高/体重补充来源。
如果没有，医疗页仍应正常工作。
```

### 4.3 建议目标结构

```swift
struct RemoteMemberCompleteData: Codable, Sendable, Equatable {
    var memberId: Int
    var member: RemoteMember

    /// 成员医疗画像投影；用于基础档案、病史、生活习惯、体检档案等摘要展示，不作为症状/用药/手术明细事实源。
    var memberMedicalProfile: RemoteMemberMedicalProfile?
    /// 成员模块开关与分组进度；用于判断首页展示哪些模块，以及模块汇总页各分组的完成状态。
    var memberModuleSettings: [RemoteMemberModuleSetting]?
    /// 饮食目标轻量快照；用于饮食模块汇总页基础信息展示，也可为医疗基础档案提供身高/体重初始值。
    var nutritionGoalState: RemoteNutritionGoalState?

    var symptoms: [RemoteSymptom]?
    var medicationPlans: [RemoteMedicationPlan]?
    var surgeries: [RemoteSurgery]?

    var medicalCases: [RemoteMedicalCaseSummary]?
    var healthExamReports: [RemoteHealthExamReportWithAttachments]?
    var examinationReports: [RemoteExaminationReportWithAttachments]?
    var medicineBoxes: [RemoteMedicineBox]?
    var prescriptions: [RemotePrescription]?
    var followUps: [RemoteFollowUp]?
}
```

### 4.4 编码解码要求

继续使用项目统一编码解码：

```text
JSONDecoder.default
JSONEncoder.default
convertToSnakeCase
ISO8601 日期
```

不要为这些字段手写 `CodingKeys`。

## 五、服务端接口设计

### 5.1 complete-data 增强

目标：

```text
GET /api/v1/medical/members/{member_id}/complete-data/
```

或现有 complete-data 接口按当前路径保持不变。

需要返回：

```text
member_medical_profile
member_module_settings
symptoms
medication_plans
surgeries
```

其中：

```text
symptoms / medication_plans / surgeries
```

用于医疗模块汇总页和分组页初始展示，不再进入页面后单独拉。

### 5.2 member-guidance 接口定位

当前：

```text
GET /api/v1/medical/member-guidance/?member_id=597
```

建议定位：

```text
医疗引导聚合接口
用于进入医疗模块汇总页时补齐 memberMedicalProfile 与分组摘要
```

但如果 `complete-data` 已能返回全部引导所需字段，则 `member-guidance` 可以减少使用，避免成为第二套事实快照。

### 5.2.1 member-guidance 合入 complete-data 的目标

建议将 `member-guidance` 的结果合并进 complete-data 内的 `member_medical_profile` 返回：

```text
RemoteMemberCompleteData.memberMedicalProfile.guidanceSections
RemoteMemberCompleteData.memberMedicalProfile.riskAssessmentSummary
RemoteMemberCompleteData.memberMedicalProfile.examPlanSummary
RemoteMemberCompleteData.memberMedicalProfile.guidanceUpdatedAt
```

服务端策略：

```text
complete-data 内部复用 member-guidance 的构建逻辑
不要在客户端进入页面后再并发请求 member-guidance
member-guidance 可以保留为调试/fallback 接口，但响应结构应与 memberMedicalProfile 内的投影字段保持一致
```

响应示例：

```json
{
  "member_id": 597,
  "member": {},
  "member_medical_profile": {
    "guidance_sections": [
      {
        "section_code": "basic_profile",
        "title": "基础档案",
        "summary": "女 · 58岁 · 160cm · 60kg",
        "status": "completed"
      },
      {
        "section_code": "health_history",
        "title": "健康病史与症状记录",
        "summary": "发热 · 二甲双胍 · 阑尾切除术",
        "status": "completed"
      }
    ],
    "risk_assessment_summary": "心血管风险中等",
    "exam_plan_summary": "建议年度体检并复查血糖",
    "guidance_updated_at": "2026-06-21T10:00:00Z"
  },
  "member_module_settings": []
}
```

客户端使用优先级：

```text
优先 completeData.memberMedicalProfile.guidanceSections
其次从 memberMedicalProfile + symptoms + medicationPlans + surgeries 本地推导
最后才补请求 member-guidance
```

### 5.2.2 nutrition goals 合入 complete-data 的目标

建议将营养目标状态作为 complete-data 的一个可选子节点返回：

```text
RemoteMemberCompleteData.nutritionGoalState
```

服务端策略：

```text
如果 SparkService 与 nutrition 模块同服务同库：
    complete-data 可直接聚合 nutrition goal

如果 nutrition 属于独立服务或边界较重：
    可先由客户端在选择维护模块页统一加载一次并写入同一个缓存模型
```

响应示例：

```json
{
  "nutrition_goal_state": {
    "member_id": 597,
    "goal": {
      "goal_type": "maintain",
      "height_cm": "160.00",
      "current_weight_kg": "60.00",
      "daily_energy_target_kcal": "1995.00",
      "carbohydrate_target_g": "244.39",
      "protein_target_g": "99.75",
      "fat_target_g": "55.42"
    },
    "defaults": {
      "goal_type": "maintain",
      "energy_kcal": 1995
    }
  }
}
```

客户端使用优先级：

```text
饮食汇总页：
    优先 completeData.nutritionGoalState
    缺失时补请求 /api/v1/nutrition/goals/

医疗基础档案：
    如果 completeData.nutritionGoalState.goal 有 height/currentWeight
    则作为身高/体重初始值来源
    不因为缺失 nutritionGoalState 阻塞医疗流程
```

### 5.3 模块配置列表纳入 complete-data

当前单独请求：

```text
GET /api/v1/medical/resources?kind=member-module-settings&member_id=597&module_code=medical
```

目标：

```text
RemoteMemberCompleteData.memberModuleSettings
```

切换成员或进入选择维护模块时一起加载。

医疗模块汇总页从缓存读取：

```text
memberModuleSettings.first(where: moduleCode == "medical")
```

### 5.4 不再单独加载的资源

医疗模块汇总页不再单独请求：

```text
GET /api/v1/medical/resources?kind=symptoms&member_id=597
GET /api/v1/medical/resources?kind=medication-plans&member_id=597
GET /api/v1/medical/resources?kind=surgeries&member_id=597
GET /api/v1/medical/resources?kind=member-medical-profiles&member_id=597
```

改为：

```text
从 RemoteMemberCompleteData 读取
```

只有用户进入某个分组详情且需要分页/深加载时，才按需请求单独列表。

## 六、客户端加载流程

### 6.1 进入选择维护模块页

位置：

```text
MemberModuleSetupView.swift
```

目标：

```text
进入页面后加载一次当前成员 RemoteMemberCompleteData
```

流程：

```text
MemberModuleSetupView.onAppear / task
    -> flowViewModel.preloadMemberCompleteDataIfNeeded(memberID)
    -> 写入 MemberCompleteDataStore / memberContextStore 缓存
```

UI：

```text
如果正在加载：
    可展示轻量 loading

如果已有缓存：
    先展示缓存，再后台刷新
```

### 6.2 进入医疗模块汇总页

位置：

```text
MemberMedicalModuleSummaryView
```

目标：

```text
优先读取 RemoteMemberCompleteData 缓存
如果缓存不存在或缺少医疗 profile，再加载一次医疗汇总数据
```

加载策略：

```text
1. 从缓存读取 completeData(memberID)
2. 如果有 memberMedicalProfile + moduleSettings：
      直接 rebuildSections()
3. 如果缺字段：
      显示“正在加载医疗资料”
      请求 complete-data 或 profile 补齐接口
      成功后写入缓存
      rebuildSections()
```

页面文案：

```text
正在加载医疗资料
```

### 6.3 分组提交成功后

用户在任意分组 sheet 中保存成功：

```text
服务端返回最新 MemberMedicalProfile / moduleSetting / mutation response
```

客户端必须：

```text
更新 RemoteMemberCompleteData.memberMedicalProfile
更新 RemoteMemberCompleteData.memberModuleSettings
按 mutation 类型更新 symptoms / medicationPlans / surgeries
刷新医疗模块汇总页 sections
```

示例：

```text
保存症状成功：
    applySymptomMutation(response)
    completeData.symptoms = 更新后的症状列表
    completeData.memberMedicalProfile.symptomFollowUpFocus = response.memberProfile.symptomFollowUpFocus

保存用药成功：
    applyMedicationMutation(response)
    completeData.medicationPlans = 更新后的用药计划
    completeData.memberMedicalProfile.medicationFocus = response.memberProfile.medicationFocus

保存手术成功：
    applySurgeryMutation(response)
    completeData.surgeries = 更新后的手术记录
    completeData.memberMedicalProfile.surgeryFocus = response.memberProfile.surgeryFocus
```

## 七、缓存设计

### 7.1 缓存对象

建议使用已有成员完整数据缓存：

```text
MemberCompleteDataStore
```

如果当前项目中命名不同，以实际已有 store 为准，不新增平行缓存。

### 7.2 缓存 key

```text
memberID
```

### 7.3 缓存写入时机

```text
选择维护模块页预加载成功
医疗模块汇总页补齐加载成功
分组保存成功
症状/用药/手术 mutation 成功
模块配置保存成功
```

### 7.4 缓存读取时机

```text
MemberModuleSetupView
MemberMedicalModuleSummaryView
MemberMedicalSetupSheetView 分组模式
MemberNutritionModuleSummaryView
首页成员模块摘要
```

### 7.5 缓存更新原则

```text
局部 mutation 优先局部更新缓存
完整刷新成功后整体覆盖缓存
缓存存在时先展示，再后台刷新
```

避免：

```text
每次回到页面都重新请求所有 kind
```

## 八、MemberMedicalModuleSummaryViewModel 调整

### 8.1 当前问题

当前 ViewModel：

```text
初始化 MemberMedicalSetupViewModel
loadIfNeeded 中调用 medicalSetupViewModel.loadIfNeeded()
```

这会让汇总页加载完整引导 ViewModel 的数据。

### 8.2 目标职责

`MemberMedicalModuleSummaryViewModel` 只做：

```text
读取 completeData 缓存
读取 moduleSetting / sectionProgress
推导 sections
打开分组 sheet
完成/跳过模块
```

不再直接拥有完整 `MemberMedicalSetupViewModel`。

### 8.3 建议输入

```swift
init(
    member: Member,
    flowViewModel: MemberSetupFlowViewModel,
    completeDataStore: MemberCompleteDataStore
)
```

或通过：

```text
flowViewModel.homeDependencies
```

获取统一 store。

### 8.4 section 推导来源

```text
基础档案
    -> completeData.member + completeData.memberMedicalProfile

健康病史与症状记录
    -> completeData.memberMedicalProfile
    -> completeData.symptoms
    -> completeData.medicationPlans
    -> completeData.surgeries

生活习惯
    -> completeData.memberMedicalProfile.extra

过往体检档案
    -> completeData.memberMedicalProfile
    -> completeData.healthExamReports
    -> completeData.examinationReports

风险评估
    -> completeData.memberMedicalProfile.riskAssessmentSummary
    -> completeData.memberMedicalProfile.extra.risk_assessment
    -> AI 结果缓存

饮食健康基础信息
    -> completeData.nutritionGoalState
    -> nutrition goals 补齐请求
```

## 十、请求去重策略

### 10.1 页面级 in-flight 去重

同一 memberID 同一时间只能有一个 completeData 加载任务。

```text
如果已有请求进行中：
    复用当前 Task
```

### 10.2 缓存命中策略

```text
缓存存在且字段完整：
    直接渲染

缓存存在但缺字段：
    渲染已有内容 + 后台补齐

缓存不存在：
    显示 loading + 请求
```

### 10.3 禁止重复 kind 请求

医疗模块汇总页不应再发：

```text
kind=symptoms
kind=medication-plans
kind=surgeries
kind=member-medical-profiles
```

除非用户进入对应详情页且需要分页/深加载。

## 十二、验收标准

### 12.1 请求数量

进入选择维护模块页：

```text
最多 1 次成员 completeData 加载
如果 completeData.memberMedicalProfile 已包含 guidanceSections，且 completeData 已包含 nutritionGoalState，则不再额外请求 member-guidance / nutrition goals
```

进入医疗模块汇总页：

```text
缓存完整：0 次网络请求
缓存缺失：最多 1 次补齐请求
```

不再出现：

```text
member-medical-profiles 重复 4 次
symptoms / medication-plans / surgeries 在汇总页重复单独加载
member-guidance 与 completeData 同时重复拉取同一份医疗汇总
nutrition goals 在选择维护模块页和医疗汇总页重复拉取
```

### 12.2 页面展示

1. 有缓存时医疗模块汇总页立即展示卡片。
2. 无缓存时展示“正在加载医疗资料”。
3. 加载成功后写入缓存并刷新卡片。
4. 加载失败时展示错误和重试。
5. 有旧缓存但刷新失败时继续展示旧缓存。

### 12.3 数据一致性

1. 保存基础档案后，`completeData.memberMedicalProfile` 更新。
2. 新增/编辑/删除症状后，`completeData.symptoms` 与 profile 投影更新。
3. 新增/编辑/删除用药后，`completeData.medicationPlans` 与 profile 投影更新。
4. 新增/编辑/删除手术后，`completeData.surgeries` 与 profile 投影更新。
5. 返回医疗模块汇总页后，不再重新触发 10 次请求。

## 十三、阶段拆分

### 阶段一：数据模型扩展

1. `RemoteMemberCompleteData` 增加 `memberMedicalProfile`。
2. `RemoteMemberCompleteData` 增加 `memberModuleSettings`。
3. `RemoteMemberMedicalProfile` 增加 `guidanceSections`、`riskAssessmentSummary`、`examPlanSummary`、`guidanceUpdatedAt`。
4. `RemoteMemberCompleteData` 增加 `nutritionGoalState`。
5. 服务端 complete-data 返回上述字段；不新增顶层 `medicalGuidance` 字段。

### 阶段二：缓存与预加载

1. 选择维护模块页进入时预加载当前成员 completeData。
2. completeData 成功后写入缓存。
3. 同 memberID 请求做 in-flight 去重。

### 阶段三：医疗模块汇总页去重

1. `MemberMedicalModuleSummaryViewModel` 不再构造完整 `MemberMedicalSetupViewModel` 作为加载来源。
2. 从 completeData 推导 sections。
3. 缺字段时只补齐一次。

### 阶段四：保存后回写缓存

1. 基础档案保存后更新 profile 缓存。
2. 症状 mutation 后更新 symptoms/profile 缓存。
3. 用药 mutation 后更新 medicationPlans/profile 缓存。
4. 手术 mutation 后更新 surgeries/profile 缓存。
5. 模块配置保存后更新 memberModuleSettings 缓存。

## 十四、已确认方案与剩余问题

以下问题已确认部分方案；实现时按确认方案执行，不再作为开放问题处理。

### 问题一：member-guidance 是否保留为独立接口？

确认方案：方案 B。

```text
member-guidance 的聚合结果合并进 completeData.memberMedicalProfile。
MemberMedicalModuleSummaryView 只读 completeData.memberMedicalProfile.guidanceSections。
不再新增 RemoteMemberCompleteData.medicalGuidance 顶层字段。
```

方案 A：保留 `member-guidance`

```text
completeData 负责成员全量资源
member-guidance 负责医疗引导聚合摘要
医疗模块汇总页缺少 profile/summary 时调用 member-guidance
```

优点：

```text
改动较小
医疗引导汇总逻辑可以独立演进
```

缺点：

```text
仍然存在 completeData 与 member-guidance 两套聚合模型
需要严格规定谁是缓存事实源
```

方案 B：把 member-guidance 合并进 completeData

```text
completeData 返回医疗引导所需全部摘要
医疗模块汇总页只读 completeData
```

优点：

```text
请求最少
缓存事实源最清晰
```

缺点：

```text
服务端 completeData 变重
后续字段增多时需要注意懒加载边界
```

修订建议：

```text
已确认选择方案 B：
将 member-guidance 的聚合结果合并到 completeData.memberMedicalProfile 返回。

为了降低改动风险，可以保留 member-guidance 路径作为 fallback；
但 MemberMedicalModuleSummaryView 首选 completeData.memberMedicalProfile.guidanceSections。
```

### 问题二：module settings 放 completeData 还是独立接口？

确认方案：方案 A。

```text
module settings 放入 RemoteMemberCompleteData.memberModuleSettings。
进入选择维护模块页、切换成员、医疗/饮食模块汇总页均优先读取 completeData.memberModuleSettings。
不再由 MemberMedicalModuleSummaryView 单独请求 member-module-settings。
```

方案 A：放入 `RemoteMemberCompleteData.memberModuleSettings`

优点：

```text
切换成员和进入建档页时一次拿齐
医疗/饮食/日常健康都能复用
```

缺点：

```text
completeData 需要关心模块配置
```

方案 B：继续独立接口，但由 `MemberModuleSetupView` 统一加载一次

优点：

```text
边界更清晰
服务端改动较少
```

缺点：

```text
仍多一次请求
需要额外缓存 module settings
```

建议：

```text
已确认选择方案 A。
模块配置是成员首页展示和建档流程的基础状态，放入成员完整快照更自然。
```

### 问题三：completeData 是否默认返回症状、用药、手术全量？

当前确认：客户端与服务端现状均为方案 B。

客户端现状：

```text
RemoteMemberCompleteData.symptoms          -> [RemoteSymptom]?
RemoteMemberCompleteData.medicationPlans   -> [RemoteMedicationPlan]?
RemoteMemberCompleteData.surgeries         -> [RemoteSurgery]?
```

服务端现状：

```text
MemberCompleteDataAPI
    symptoms         -> SymptomSerializer(symptoms, many=True)
    medicationPlans  -> MedicationPlanSerializer(medication_plans, many=True)
    surgeries        -> SurgerySerializer(surgeries, many=True)
```

因此当前不是轻量摘要 DTO，而是直接返回完整远端模型。

方案 A：默认返回轻量列表

```text
symptoms / medicationPlans / surgeries 返回摘要字段
详情页再深加载
```

优点：

```text
汇总页够用
数据量可控
```

缺点：

```text
详情页可能仍需二次请求
```

方案 B：默认返回完整列表

优点：

```text
详情页打开更快
```

缺点：

```text
成员数据多时 completeData 过重
```

建议：

```text
已确认当前实现为方案 B，本工单先沿用方案 B。
不要在本工单内额外新增 SymptomSummary / MedicationPlanSummary / SurgerySummary DTO。
后续如果成员数据量明显增大，再单独创建“completeData 轻量化”优化工单。
```

### 问题四：nutrition goals 是否应该放入 RemoteMemberCompleteData？

确认方案：方案 B。

```text
营养模块未来会独立服务，因此 nutrition goals 不放入服务端 RemoteMemberCompleteData。
MemberModuleSetupView 负责统一预热 nutrition goals，并在客户端缓存层组合 completeData + nutritionGoalState。
医疗服务端 completeData 保持医疗资源边界，不跨域聚合营养目标。
```

方案 A：放入 `RemoteMemberCompleteData.nutritionGoalState`

```text
选择维护模块页一次拿到医疗与饮食两个模块的初始状态
饮食汇总页不再额外请求 nutrition goals
医疗基础档案可复用身高/体重
```

优点：

```text
请求最少
模块选择页完成度判断最直接
身高/体重跨医疗和饮食复用更自然
```

缺点：

```text
RemoteMemberCompleteData 会跨到营养领域
如果 nutrition 未来独立服务，服务端聚合边界会变重
```

方案 B：不放入 completeData，但由 MemberModuleSetupView 统一加载并写入同一缓存上下文

```text
completeData 仍只负责医疗资源
nutrition goals 由模块选择页统一预热
缓存层把 completeData + nutritionGoalState 组合给页面使用
```

优点：

```text
服务端边界清晰
nutrition API 可独立演进
```

缺点：

```text
仍会多一次接口
客户端缓存组合逻辑更复杂
```

建议：

```text
已确认选择方案 B。
nutrition goals 由 MemberModuleSetupView 统一加载并写入客户端成员模块缓存上下文。
服务端 RemoteMemberCompleteData 不新增 nutritionGoalState 字段。
```

## 十五、最终结论

本工单建议支持并实施：

```text
进入选择维护模块时预加载 RemoteMemberCompleteData
RemoteMemberCompleteData 扩展 MemberMedicalProfile、module settings
RemoteMemberMedicalProfile 承载医疗引导分组摘要、风险评估摘要、下一次体检计划摘要
MemberModuleSetupView 统一预热 nutritionGoalState，并与 completeData 组成客户端页面缓存上下文
医疗模块汇总页从缓存推导 sections
症状、用药、手术列表不再重复单独加载
提交成功后局部更新 completeData 缓存
```

最终目标：

```text
把一次进入医疗模块汇总页的 10 次请求压缩到 1-2 次；
让成员医疗模块汇总页成为缓存驱动页面；
让 RemoteMemberCompleteData 成为成员级医疗数据快照；
避免 ViewModel 之间各自加载同一批成员资料。
```
