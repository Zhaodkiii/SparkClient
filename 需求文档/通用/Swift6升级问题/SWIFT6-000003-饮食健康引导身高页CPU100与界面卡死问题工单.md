# SWIFT6-000003：饮食健康引导身高页 CPU 100% 与界面卡死问题工单

## 工单摘要

| 项目 | 内容 |
| --- | --- |
| 问题类型 | SwiftUI 状态/布局反馈循环，主线程持续占用 |
| 触发场景 | 饮食健康引导 → 开始流程 → 打开身高页面 |
| 现象 | CPU 接近 100%、Energy Impact 为 High、0 FPS、页面无响应 |
| 已知进程 | SparkClient，PID 9197 |
| 内存表现 | 约 65.1 MB，未表现为持续内存膨胀 |
| 网络/磁盘 | 约 0 KB/s，不像网络等待或磁盘阻塞 |
| 严重程度 | P0，核心引导流程不可用 |
| 初步结论 | 身高刻度选择器的滚动位置与数据 Binding 形成高频反馈循环；导航容器的全局 TabBar modifier 可能放大循环 |
| 结论置信度 | 中高；静态代码与现象吻合，仍需一次主线程采样确认调用栈 |

## 用户影响

用户进入饮食健康引导的身高页面后无法继续操作，也无法稳定返回。持续满载会增加发热、耗电，并可能触发系统 watchdog 终止应用。

## 现象判断

该现象更像主线程上的无限或近无限 SwiftUI 更新循环，而不是以下问题：

- 不是内存泄漏主导：卡死时内存仅约 65.1 MB，未提供持续上涨证据。
- 不是网络请求阻塞：网络为 0 KB/s，且 CPU 已满载。
- 不是磁盘 I/O 阻塞：磁盘为 0 KB/s。
- 不是单次复杂绘制：简单身高页持续 0 FPS，说明主线程无法完成稳定的一帧提交。

典型循环如下：

```text
NavigationStack / Sheet 首次布局
        ↓
SparkHorizontalWheelPicker 计算 scrollPosition
        ↓
scrollPosition Binding setter 回写 @State
        ↓
setter 同时更新外部 @Published heightCm
        ↓
MemberNutritionSetupSheet 整体重新计算 body
        ↓
滚动目标与 toolbar/safeArea 重新布局
        └───────────────────────────────┐
                                        ↓
                              再次设置 scrollPosition
```

## 根因分析

### 根因候选 1：滚动位置 Binding 的 setter 内产生双重状态写入

身高页在 iOS 17 以上使用 `SparkHorizontalWheelPicker`。当前实现把 `.scrollPosition(id:)` 连接到一个手工构造的 Binding：

```swift
.scrollPosition(id: Binding<Int?>(
    get: { scrollPosition },
    set: { newValue in
        // 回写组件自身 @State
        scrollPosition = resolvedIndex
        // 同时回写外部 @Published value
        updateValue(for: resolvedIndex)
    }
))
```

SwiftUI 在布局和滚动对齐过程中会多次写入该 Binding。setter 又立即更新 `@State` 与 `@Published heightCm`，导致两个观察系统同时失效并重建视图。

此外，组件还有三条并行同步路径：

- `.onAppear` 写入 `value` 和 `scrollPosition`；
- `.task(id: config)` 先把 `scrollPosition` 设为 `nil`，连续两次 `Task.yield()` 后再次写入 `value` 和 `scrollPosition`；
- `.onChange(of: value)` 再把外部值同步回 `scrollPosition`。

这构成了多源双向同步。Swift 6 本身不是业务循环的直接原因，但升级后的工具链、默认 MainActor 隔离和新版 SwiftUI 调度会改变更新时序，使原本偶发的反馈变成持续卡死。

### 根因候选 2：零宽度滚动目标无法稳定对齐

每个刻度使用：

```swift
Divider()
    .frame(width: 0, height: ...)
```

外层又使用：

```swift
.scrollTargetLayout()
.scrollTargetBehavior(.viewAligned)
```

即滚动系统需要把大量零宽度 target 与中心位置对齐。结合动态 `safeAreaPadding` 和手工 `scrollPosition` 回写，可能使 SwiftUI 反复解析相邻 target，无法收敛到稳定布局。

### 放大因素：通用导航容器对所有 destination 隐藏 TabBar

`CompatibleRouteNavigationContainer` 无条件为每一个 destination 添加：

```swift
.hidesMainTabBarWhenPushed()
```

其实际实现是：

```swift
.toolbar(.hidden, for: .tabBar)
```

饮食引导本身位于 Sheet 内部，Sheet 的内部 `NavigationStack` 并不拥有外层主 TabBar。让通用容器在每次 destination 重算时修改外层 toolbar preference，会增加 NavigationStack、toolbar 与 safe-area 的布局失效次数。

这不是根身高页首次显示时的唯一解释：根页面没有经过 `navigationDestination`。但当身高页通过 `.height` route push，或者导航树在 Sheet 中重新装配时，它可能与选择器反馈循环叠加。因此它应从通用容器移除或改成显式配置。

### 次要因素：Sheet 根页面和 destination 重复声明身高页

`MemberNutritionSetupSheetView` 同时把 `heightStep` 用作根页面，又允许 `.height` route 构造同一页面：

```swift
CompatibleRouteNavigationContainer(path: $path) {
    heightStep
} destination: { route in
    switch route {
    case .height:
        heightStep
    // ...
    }
}
```

该结构支持从总结页再次进入身高编辑，语义上可以成立，但会让同一绑定和滚动控件出现在不同导航身份中。它不是 CPU 100% 的首要根因，却增加了状态恢复和滚动定位的复杂度。

### 次要因素：加载任务缺少“已完成”状态

Sheet 根视图使用无 id 的 `.task` 调用 `loadIfNeeded()`。方法只用 `isLoading` 防止同时请求，没有记录“已经成功加载”。如果导航/Sheet 身份在反馈循环中被反复重建，任务可能再次启动并发布多项 `@Published` 状态，进一步放大刷新。

## 推荐修复

### 第一阶段：快速隔离问题

临时让身高页统一使用现有 `SparkCustomRulerSlider`，跳过 iOS 17+ 的 `SparkHorizontalWheelPicker`。如果 CPU 与 FPS 立即恢复，可确认热点来自新的横向滚轮，而不是网络加载或 NavigationStack 本身。

该改动只用于定位，不建议直接作为最终结论；需要同时验证医疗引导中复用的身高页面。

### 第二阶段：将滚动位置改成单一状态源

移除 `.scrollPosition` 自定义 Binding setter 内的副作用，直接绑定组件状态，并在独立 `onChange` 中做带相等判断的单向同步：

```swift
.scrollPosition(id: $scrollPosition)
.onAppear {
    guard didApplyInitialPosition == false else { return }

    let index = config.index(for: value)
    let normalizedValue = config.value(for: index)
    scrollPosition = index
    if abs(value - normalizedValue) > 0.0001 {
        value = normalizedValue
    }
    didApplyInitialPosition = true
}
.onChange(of: scrollPosition) { _, newPosition in
    guard didApplyInitialPosition, let newPosition else { return }

    let index = min(max(newPosition, 0), config.totalSteps)
    let newValue = config.value(for: index)
    if abs(value - newValue) > 0.0001 {
        value = newValue
    }
}
.onChange(of: value) { _, newValue in
    guard didApplyInitialPosition else { return }

    let index = config.index(for: newValue)
    if scrollPosition != index {
        scrollPosition = index
    }
}
```

同时删除以下初始化抖动：

```swift
.task(id: config) {
    scrollPosition = nil
    await Task.yield()
    await Task.yield()
    scrollPosition = resolvedIndex
}
```

首次定位应该只由一个生命周期入口负责，不应主动经历 `目标 → nil → 目标`。

### 第三阶段：给刻度稳定的布局宽度

把零宽度滚动 target 改为具有确定宽度的容器，例如：

```swift
Rectangle()
    .fill(isMajor ? Color.primary : Color.gray)
    .frame(width: 1, height: isMajor ? 20 : 10)
    .frame(width: max(config.spacing, 1), height: 20, alignment: .bottom)
```

对应的 `HStack` 使用 `spacing: 0`，确保每个 target 的布局 frame 唯一、非零且间距可预测。

### 第四阶段：去除通用导航容器的隐式 TabBar 副作用

不要让 `CompatibleRouteNavigationContainer` 自动决定所有业务 destination 是否隐藏主 TabBar。建议增加显式参数，Sheet 传入 `false`：

```swift
struct CompatibleRouteNavigationContainer<...>: View {
    private let hidesMainTabBarOnPush: Bool
    // ...
}
```

也可以完全从通用容器移除 `.hidesMainTabBarWhenPushed()`，只在真正由主 TabView push 的业务页面显式添加。饮食引导 Sheet 内部不应向外层 TabBar 发布隐藏 preference。

### 第五阶段：让加载任务真正幂等

在 `MemberNutritionSetupViewModel` 增加 `hasLoaded`，成功加载后置为 `true`；`loadIfNeeded()` 同时检查 `hasLoaded` 与 `isLoading`。这样即使视图生命周期意外重新进入，也不会重复发起加载和批量发布状态。

## 验证根因的方法

修复前先完成一次采样，避免只凭 UI 文件栈顶下结论：

1. 卡死时在 Xcode 点击暂停，连续截取 3 次主线程调用栈。
2. 使用 Instruments → Time Profiler 录制进入身高页前后 10 秒。
3. 如果热点持续出现 `AttributeGraph`、`NavigationStack`、`ScrollPosition`、`ScrollView`、`ViewGraph` 或 `SparkHorizontalWheelPicker.body`，即可确认反馈循环。
4. 临时替换为 `SparkCustomRulerSlider` 后重复测试；若 CPU 恢复且 FPS 正常，形成对照证据。
5. 分别关闭 `.hidesMainTabBarWhenPushed()` 与 `.task { loadIfNeeded() }` 做二分验证，判断两者是否为放大因素。

`CompatibleNavigationContainer.swift` 与 `MemberNutritionSetupSheet.swift` 很可能出现在采样栈的上层，因为它们承载整个泛型视图树；栈顶显示这些文件不等于循环由它们直接产生。应以重复出现的最深层状态写入或布局函数作为根因证据。

## 实施顺序

1. 用旧版 ruler slider 做 A/B 验证并保存 Time Profiler 结果。
2. 重构 `SparkHorizontalWheelPicker`，保留单一滚动位置状态源。
3. 将滚动 target 改为非零宽度。
4. 移除或参数化通用导航容器的 TabBar 隐藏行为。
5. 为 `loadIfNeeded()` 增加成功加载幂等标记。
6. 回归所有复用身高、体重选择组件的医疗和饮食流程。

## 验收标准

- [ ] 连续 10 次进入饮食健康身高页均能在 1 秒内完成首帧。
- [ ] 页面静止时 CPU 回落到正常空闲区间，不再持续接近 100%。
- [ ] 身高页保持 50–60 FPS（按设备刷新率校准），不再显示 0 FPS。
- [ ] 拖动身高刻度时数值与滚动位置一一对应，无来回跳动。
- [ ] 已保存身高可以正确定位，且不会先跳到边界再回到目标值。
- [ ] 点击“下一步”和“跳过”只向 path 追加一次 route。
- [ ] 从总结页返回身高编辑、再返回总结页时导航栈稳定。
- [ ] 饮食引导 Sheet 不错误修改主页面 TabBar 可见性。
- [ ] `loadIfNeeded()` 在一次 Sheet 生命周期内最多成功执行一次。
- [ ] 医疗引导复用的身高和体重页面无回归。
- [ ] Debug、Release 真机及当前最低支持系统均完成验证。

## 风险与回滚

- 选择器重构可能影响初始滚动位置和吸附手感，应重点验证范围两端与非整数 step。
- 导航容器行为调整会影响主 Tab 页的详情页面，应逐个确认其 TabBar 隐藏需求。
- 若发布窗口紧急，可临时让身高页使用已存在的 `SparkCustomRulerSlider`；该回滚不应伴随关闭 Swift 6 或全局关闭 MainActor 隔离。

## 与 Swift 6 的关系

该问题发生在 Swift 6 升级后，但现有证据更支持“SwiftUI 状态反馈循环被新工具链/新 SDK 调度暴露”，而不是 Swift 6 语言运行时计算变慢。修复重点应放在状态单向流、稳定 View identity 和减少隐式导航环境副作用，而不是降低 Swift 语言版本。
