## 工单 `APP-STARTUP-000001`：冷启动必须刷新最新 UserSession

### 1. 背景

### Q：现在冷启动出现了什么问题？

A：用户实际已经存在 Pro 权限，但 App 冷启动恢复会话后，客户端没有拿到最新 Pro 状态，也没有拉取服务端 Pro 模型配置，导致启动阶段解析 `chat` 场景模型失败。

典型日志：

```text
用户档案引导已结束（降级）：missingModelForScenario(SparkClient.AIScenario.chat)
用户档案引导已结束（降级）：场景「chat」暂无可用的 AI 模型
```

调试时的会话快照：

```text
session.accountID = 265
session.isPro = false
```

但服务端实际已经给该账号发放 Pro，设备注册也已上送：

```json
{
  "user_id": 265,
  "country_code": "CN",
  "region_code": "CN"
}
```

### 2. 当前启动链路

### Q：冷启动时相关链路是什么？

A：关键链路如下：

1. `AppCoordinatorView` 在 loading 态触发启动任务。

```text
SparkClient/Projects/App/Sources/App/AppCoordinatorView.swift:44-50
```

2. `AppLifecycleCoordinator.bootstrapLaunchAfterNetworkEvaluation(...)` 在网络可用后执行应用级启动和会话恢复。

```text
SparkClient/Projects/App/Sources/App/Architecture/AppLifecycleCoordinator.swift:44-50
```

当前顺序：

```text
bootstrapAppLaunchIfNeeded()
checkOnLaunchIfNeeded()
sessionStore.restoreIfNeeded()
prepareSignedInSessionIfNeeded(session)
```

3. `AppLifecycleCoordinator.prepareSignedInSessionIfNeeded(_:)` 进入账号运行时准备。

```text
SparkClient/Projects/App/Sources/App/Architecture/AppLifecycleCoordinator.swift:68-88
```

当前顺序：

```text
activateUser(accountID)
onboardingStore.activate(session)
appBootstrapper.bootstrapIfNeeded(for: session)
homeViewModel.loadInitialIfNeeded(syncRemote: true)
taskRuntime.syncIncremental(...)
preparedAccountID = session.accountID
```

4. `AppBootstrapper.bootstrapIfNeeded(for:)` 预热 AI 配置。

```text
SparkClient/Projects/App/Sources/App/AppBootstrapper.swift:55-75
```

当前核心逻辑：

```swift
await aiConfigCenter.prewarm(ownerAccountID: session.accountID)
if session.isPro {
    await aiConfigCenter.refreshRemoteConfig()
}
...
for scenario in AIScenario.allCases {
    _ = try await aiConfigCenter.resolve(for: scenario)
}
```

### 3. 问题根因

### Q：问题出在哪里？

A：问题本质是：**启动阶段把本地持久化的 `UserSession.isPro` 当成是否拉取远端 Pro 配置的唯一依据，但这个值在冷启动会话恢复时可能是旧值。**

具体原因：

1. `UserSession.isPro` 是登录/上次保存时的快照，不是实时权限。

```text
SparkClient/Projects/Core/Domain/Entities/UserSession.swift:14
```

2. 冷启动恢复会话时，`SessionSnapshotStore.load()` 只从本地 `UserDefaults` 读取旧 session。

```text
SparkClient/Projects/Features/Auth/Infrastructure/SessionSnapshotStore.swift:15-18
```

3. 服务端后来可能已经通过登录自动 Pro、后台发放权限、试用申请审核通过等方式改变了权限，但本地 session 快照不会自动更新。

4. `AppBootstrapper.bootstrapIfNeeded(for:)` 使用 `session.isPro` 决定是否调用 `aiConfigCenter.refreshRemoteConfig()`。

```text
SparkClient/Projects/App/Sources/App/AppBootstrapper.swift:59-62
```

当 `session.isPro == false` 时，会直接跳过远端 Pro 配置刷新。

5. 跳过 `refreshRemoteConfig()` 后，`AIConfigCenter` 只有本地 `prewarm` 得到的本地配置。

```text
SparkClient/Projects/Core/AI/AIConfigCenter.swift:94-104
```

6. 后续启动阶段马上遍历所有场景并解析模型。

```text
SparkClient/Projects/App/Sources/App/AppBootstrapper.swift:65-66
```

如果本地配置没有可用 `chat` 模型，且 Pro 配置没有拉下来，就会报：

```text
missingModelForScenario(.chat)
```

### Q：为什么设备注册成功也不能解决这个问题？

A：设备注册只证明服务端知道当前设备和国家信息：

```text
POST /api/v1/device/register/
country_code = CN
```

但设备注册接口不会返回当前 Pro 权限，也不会自动拉取 AI Pro bootstrap。当前客户端仍然依赖本地 `session.isPro` 决定是否调用 `refreshRemoteConfig()`，所以设备注册成功不能修正启动阶段的权限判断。

### Q：为什么不能只依赖登录接口返回的 `is_pro`？

A：登录接口返回 `is_pro` 对“刚登录”有效，但冷启动恢复会话不一定重新登录。用户可能在上次登录后由服务端异步获得 Pro 权限，例如：

1. 自动发放 Pro。
2. 后台人工发放权限。
3. 试用申请审核通过。
4. 另一个设备触发权限变化。

因此冷启动时必须有一条“刷新当前账号权限/试用状态”的链路，不能只信本地 session。

### 4. 目标

### Q：本工单要达成什么目标？

A：

1. 冷启动恢复已登录账号后，即使本地 `UserSession.isPro == false`，也能获取服务端最新 Pro 权限。
2. 如果服务端返回当前账号已是 Pro，启动阶段必须拉取远端 Pro AI 配置。
3. `chat` 等场景解析不能因为本地旧 session 未标记 Pro 而缺少服务端模型。
4. 启动流程需要区分：
   - 本地会话快照：网络异常时用于恢复账号和 token。
   - 服务端最新 UserSession：网络可用冷启动时的优先事实源，包含最新 Pro 状态。
5. 最新 UserSession 刷新失败时可以降级读取本地 `SessionSnapshotStore`，但必须有明确日志，不能静默使用过期 Pro 状态。

### 5. 解决方案

### Q：推荐方案是什么？

A：方案改为：**App 冷启动时必须请求一遍服务端最新用户会话信息 `UserSession`，响应中必须包含最新 Pro 状态；请求成功后立即更新内存会话状态，并写回 `SessionSnapshotStore(UserDefaults)`。**

不采用以下方案：

```text
冷启动已登录后先请求 /api/v1/ai/trial/status/，用服务端实时 is_active 决定是否 refreshRemoteConfig()
```

原因：

1. `trial/status` 只解决 Pro/试用状态，不解决用户基础信息、账号状态、会员状态等完整会话信息刷新。
2. 冷启动真正需要恢复的是“最新用户会话”，Pro 只是 `UserSession` 的一个字段。
3. 启动链路应有一个统一事实源，避免 `UserSession.isPro`、`AITrialState.isActive`、设置页快照各自刷新导致状态散落。

推荐流程：

```text
bootstrapLaunchAfterNetworkEvaluation
  -> bootstrapAppLaunchIfNeeded()
  -> sessionStore.restoreIfNeeded()
       -> 先读取本地 SessionSnapshotStore，确认是否有 token / accountID
       -> 网络可用时请求最新 UserSession
       -> 请求成功：保存最新 UserSession 到 SessionSnapshotStore(UserDefaults)
       -> 请求成功：AppSessionStore.state = signedIn(latestSession)
       -> 请求失败：回退使用本地 cachedSession
  -> prepareSignedInSessionIfNeeded(latestOrCachedSession)

prepareSignedInSessionIfNeeded(session)
  -> activateUser(accountID)
  -> onboardingStore.activate(session)
  -> appBootstrapper.bootstrapIfNeeded(for: session)

bootstrapIfNeeded(for latestOrCachedSession)
  -> aiConfigCenter.prewarm(ownerAccountID)
  -> if session.isPro == true:
       aiConfigCenter.refreshRemoteConfig()
  -> resolve scenarios
```

关键点：

1. 网络可用冷启动时，`SessionSnapshotStore` 不能直接作为最终会话事实源，只能作为请求最新会话前的本地凭证/兜底。
2. 服务端最新 `UserSession.isPro` 才是启动阶段是否拉取 Pro 配置的依据。
3. 最新 `UserSession` 请求成功后必须写回 `SessionSnapshotStore(UserDefaults)`，否则下次网络波动时仍会读到旧值。
4. 远端 Pro 配置刷新必须发生在 `resolve(for:)` 之前。
5. 网络失败时，才允许从 `SessionSnapshotStore(UserDefaults)` 读取上次保存的 `UserSession` 继续启动。

### Q：应在哪里加这个逻辑？

A：优先放在会话恢复层，而不是放在 `AppBootstrapper` 内。

推荐位置：

```text
AppSessionStore.restoreIfNeeded()
RestoreSessionUseCase.execute()
```

原因：

1. “获取最新 UserSession”属于认证/会话恢复职责，不属于 AI 启动预热职责。
2. `AppBootstrapper.bootstrapIfNeeded(for:)` 应继续消费已经确定的 `UserSession`，不要自己再判断用户身份是否最新。
3. `AppLifecycleCoordinator.prepareSignedInSessionIfNeeded(_:)` 收到的 session 应已经是最新会话，或明确是网络失败后的本地兜底会话。

建议新增能力：

```swift
protocol AuthSessionAPI {
    func fetchCurrentSession() async throws -> UserSession
}
```

服务端建议提供或复用一个接口：

```text
GET /api/v1/auth/session/
```

或：

```text
GET /api/v1/auth/me/
```

返回字段至少包含：

```json
{
  "user_id": 265,
  "email": "97621528@qq.com",
  "display_name": "Apple User",
  "is_pro": true,
  "is_new_user": false,
  "sign_in_method": "apple"
}
```

客户端转换为：

```swift
struct UserSession {
    let accountID: Int64
    let email: String
    let displayName: String
    let signedInAt: Date
    let signInMethod: SignInMethod
    let isPro: Bool
    let isNewUser: Bool
}
```

### Q：`RestoreSessionUseCase` 应如何调整？

A：建议改为“两阶段恢复”：

```text
RestoreSessionUseCase.execute()
  -> load cachedSession from SessionSnapshotStore
  -> if cachedSession == nil:
       return nil
  -> ensure token available / refresh token if needed
  -> try fetchCurrentSession()
       success:
         merge signedInAt/signInMethod if server does not return them
         SessionSnapshotStore.save(latestSession)
         return latestSession
       failure:
         log warning
         return cachedSession
```

要求：

1. 网络可用时必须尝试请求最新 UserSession。
2. 请求成功后必须更新 `SessionSnapshotStore(UserDefaults)`。
3. 请求失败时才允许使用本地 cached session。
4. 如果服务端返回账号禁用/鉴权失效，应清空本地 session 并进入 signedOut。
5. 如果只是网络波动、超时、服务端临时错误，可以使用 cached session 进入 App，并记录降级日志。

### Q：`AppBootstrapper` 应如何调整？

A：`AppBootstrapper.bootstrapIfNeeded(for:)` 不需要请求 `trial/status`。它只需要信任传入的 `UserSession` 是“最新或明确降级后的会话”。

调整后：

```swift
await aiConfigCenter.prewarm(ownerAccountID: session.accountID)
if session.isPro {
    await aiConfigCenter.refreshRemoteConfig()
}
for scenario in AIScenario.allCases {
    _ = try await aiConfigCenter.resolve(for: scenario)
}
```

这里的 `session.isPro` 来自：

```text
优先：冷启动请求服务端最新 UserSession
兜底：网络失败时上次保存的 SessionSnapshotStore(UserDefaults)
```

### Q：为什么不再使用 `/api/v1/ai/trial/status/` 作为启动判断？

A：本工单明确不采用该方案。`trial/status` 可以继续用于 AI 设置页展示试用详情，但不作为 App 冷启动恢复会话的主链路。

启动阶段只认一条主链路：

```text
刷新最新 UserSession -> 更新 SessionSnapshotStore -> 用 UserSession.isPro 决定是否拉 Pro 配置
```

### Q：`UserSession.isPro` 是否还需要保留？

A：需要保留，并且应成为冷启动主链路里的 Pro 状态字段。但它必须来自“最新 UserSession”刷新结果，不能长期停留在旧本地快照里。

语义调整：

1. 登录接口返回的 `is_pro`：登录成功时的最新状态。
2. 冷启动 `fetchCurrentSession()` 返回的 `is_pro`：冷启动时的最新状态。
3. `SessionSnapshotStore` 中的 `isPro`：上一次成功刷新保存的状态，仅作为网络失败兜底。
4. AI 设置页的 `AITrialState`：用于展示试用详情，不负责冷启动会话恢复。

### 6. 数据与状态同步

### Q：刷新后的权限状态要写到哪里？

A：

1. `AppSessionStore.state`：使用最新 `UserSession` 进入 `.signedIn(latestSession)`。
2. `SessionSnapshotStore(UserDefaults)`：必须保存最新 `UserSession`，包含最新 `isPro`。
3. `AIRuntimeConfigStore`：如果 `latestSession.isPro == true`，必须通过 `refreshRemoteConfig()` 写入远端 Pro overlay。
4. `AISettingsSnapshot.trial`：不要求在冷启动主链路中强制刷新；设置页仍可按现有逻辑自行拉取试用详情。

建议流程：

```text
fetchCurrentSession()
  -> latestSession
  -> SessionSnapshotStore.save(latestSession)
  -> AppSessionStore.state = signedIn(latestSession)
  -> if latestSession.isPro:
       refreshRemoteConfig()
```

### Q：如何避免启动阶段重复请求？

A：

1. `AppSessionStore.didRestore` 保证冷启动会话恢复只执行一次。
2. `AppBootstrapper.bootstrappedAccounts` 仍可用于账号级运行时引导去重。
3. `AIConfigCenter.refreshRemoteConfig()` 本身可继续只写内存 overlay，不必每次持久化远端 Pro 配置。
4. 前台恢复是否刷新最新 UserSession 可另开工单，不放在本工单强制范围。

### 7. 错误处理

### Q：最新 UserSession 刷新失败怎么办？

A：不能阻断 App 进入主界面，但需要分级降级：

1. `fetchCurrentSession()` 失败：
   - 记录 warning，说明本次使用 `SessionSnapshotStore` 兜底。
   - 如果 cached session 的 `isPro == true`，仍可尝试 `refreshRemoteConfig()`。
   - 如果 cached session 的 `isPro == false`，继续本地配置启动，但日志要明确“未能确认最新 UserSession，使用本地旧会话”。
2. `refreshRemoteConfig()` 失败：
   - 记录 warning/error。
   - 不阻断医疗、首页、任务等非 AI 主流程启动。
3. `resolve(for:)` 失败：
   - 不建议整个账号启动视为失败。
   - 应记录具体缺失场景，并允许 UI 在发送消息前提示“当前没有可用对话模型”。

当前 `AppBootstrapper` 已在 `do/catch` 内降级，但它把 AI 场景解析失败和其他启动失败混在一起：

```text
用户档案引导已结束（降级）：missingModelForScenario(...)
```

建议进一步拆分日志：

```text
AI 启动预热：chat 场景暂无可用模型，等待用户配置或 Pro 配置刷新
```

避免误导为整个用户档案启动失败。

### 9. 验收标准

1. 冷启动网络可用且本地存在登录态时，客户端必须请求最新 UserSession。
2. 最新 UserSession 响应必须包含 `is_pro`，客户端映射到 `UserSession.isPro`。
3. 请求最新 UserSession 成功后，必须更新 `SessionSnapshotStore(UserDefaults)`。
4. 请求最新 UserSession 成功后，`AppSessionStore.state` 使用最新 session，而不是旧 cached session。
5. 如果最新 `UserSession.isPro == true`，启动阶段会调用 `AIConfigCenter.refreshRemoteConfig()`。
6. `refreshRemoteConfig()` 完成后，`chat` 场景能解析到服务端 Pro 模型，不再因本地旧 session 报 `missingModelForScenario(.chat)`。
7. 如果最新 `UserSession.isPro == false`，启动不请求 Pro 配置或可接受服务端空配置，但不能错误展示 Pro 模型。
8. 如果请求最新 UserSession 因网络波动失败，App 从 `SessionSnapshotStore(UserDefaults)` 读取上次保存的 UserSession 继续启动。
9. 网络失败兜底时必须输出明确日志，说明使用本地旧 session。
10. 如果本地 cached session 的 `isPro == true`，即使最新 UserSession 请求失败，也可以继续尝试拉取 Pro 配置作为兜底。
11. 账号切换后，最新 UserSession、SessionSnapshotStore 和 Pro overlay 按账号隔离，不复用上一个账号结果。
12. 网络不可用时不触发远端会话刷新；网络恢复后只执行一次冷启动会话刷新。

### 10. 补充说明

### Q：本问题和服务端是否有关？

A：当前日志显示服务端设备注册成功，并且请求中已经包含：

```json
"country_code": "CN"
```

问题主要发生在客户端启动判断链路：本地 session 快照没有实时更新，导致跳过远端 Pro 配置刷新。服务端需要提供“获取当前最新 UserSession”的接口，客户端冷启动时必须主动查询并回写本地快照。

### Q：为什么日志里 `session.isPro=false`，但用户实际有 Pro？

A：因为 `session.isPro` 来自本地保存的 `UserSession`。它是在登录或上次保存时写入的快照，不会因为服务端后台发放/自动发放/审核通过而自动变化。冷启动恢复不是重新登录，因此不会重新拿登录响应里的 `is_pro`。

### Q：网络波动时怎么办？

A：网络波动时允许降级读取 `SessionSnapshotStore(UserDefaults)` 中上一次保存成功的 `UserSession`。这是兜底能力，不是网络可用时的主路径。

### Q：最终原则是什么？

A：

```text
启动先刷新最新 UserSession；成功后写回 SessionSnapshotStore；失败时才使用上次保存的 UserSession；再用 UserSession.isPro 决定是否拉 Pro 模型配置。
```

不要把“身份恢复成功”和“权益状态最新”混为一件事。

## 工单 `APP-STARTUP-000002`：移除冗余 UserProfileRepository，统一使用 UserSession

### 1. 背景

### Q：为什么要讨论 `UserSession` 是否能代替 `UserProfile`？

A：当前项目里同时存在两套很相近的账号摘要模型：

```swift
struct UserSession: Codable, Equatable, Sendable {
    let accountID: Int64
    let email: String
    let displayName: String
    let signedInAt: Date
    let signInMethod: SignInMethod
    let isPro: Bool
    let isNewUser: Bool
}
```

```swift
struct UserProfile: Equatable, Sendable {
    let id: Int64
    let email: String
    let displayName: String
    let createdAt: Date
    let lastSignedInAt: Date
}
```

`UserProfile` 目前的注释是“当前登录用户在应用内的档案摘要”，但它的字段基本都可以从 `UserSession` 推导出来。

当前实现里：

```text
SparkClient/Projects/Features/Home/Infrastructure/SessionBackedUserProfileRepository.swift
```

`SessionBackedUserProfileRepository` 并没有独立存储 Profile，也没有请求服务端 Profile，而是直接读取 `SessionSnapshotStore.load()` 后拼出 `UserProfile`。

### 2. 结论

### Q：`UserSession` 能不能直接代替 `UserProfileRepository` 内的 `UserProfile`？

A：按当前代码职责看，**可以代替，而且建议代替**。

原因：

1. `UserProfile` 没有独立生命周期。
2. `UserProfile` 没有独立服务端接口。
3. `UserProfile` 没有独立持久化表或缓存。
4. `SessionBackedUserProfileRepository` 只是从 `UserSession` 派生数据。
5. 登录时调用 `userProfileRepository.upsertProfile(...)` 返回了 `UserProfile`，但结果没有被后续使用，也没有保存到独立存储。
6. 冷启动新方案已经要求最新 `UserSession` 必须从服务端刷新并写回 `SessionSnapshotStore`，因此 `UserSession` 已经是账号摘要的统一事实源。

### Q：保留 `UserProfile` 有什么问题？

A：主要问题是重复模型和假仓储：

1. 字段重复：`id/accountID`、`email`、`displayName`、`signedInAt/lastSignedInAt` 表达的是同一类信息。
2. 命名容易误导：`UserProfileRepository` 听起来像独立档案仓储，但实际只是读 session。
3. 状态容易不一致：如果后续有人只更新 `UserSession`，忘记更新 `UserProfile`，首页展示就可能滞后。
4. 增加启动链路复杂度：登录成功既保存 session，又 upsert profile，但 profile 不是事实源。
5. 不利于 `APP-STARTUP-000001`：冷启动已经要求刷新最新 `UserSession`，此时再通过 ProfileRepository 派生一层没有必要。

### 3. 目标

### Q：本工单要达成什么目标？

A：

1. 账号维度的当前用户摘要统一使用 `UserSession`。
2. 删除或废弃 `UserProfileRepository` 及 `SessionBackedUserProfileRepository`。
3. 首页 `HomeDashboard` 不再依赖 `UserProfile`，改为直接持有 `UserSession` 或轻量展示模型。
4. 登录成功只需要保存 `UserSession` 到 `SessionSnapshotStore`，不再额外 upsert profile。
5. 减少重复模型、重复字段和假仓储。

### 4. 推荐改造方案

### Q：如何替换最合理？

A：推荐直接让首页加载用例消费 `UserSession`。

当前：

```swift
struct LoadHomeMedicalOverviewUseCase {
    let userProfileRepository: any UserProfileRepository

    func execute(accountID: Int64, ...) async throws -> HomeMedicalLoadResult {
        guard let profile = try await userProfileRepository.fetchProfile(id: accountID) else {
            throw ...
        }
        ...
        return HomeMedicalLoadResult(profile: profile, ...)
    }
}
```

建议：

```swift
struct LoadHomeMedicalOverviewUseCase {
    func execute(session: UserSession, selectedMemberID: Int?, refreshRemoteSnapshot: Bool) async throws -> HomeMedicalLoadResult {
        ...
        return HomeMedicalLoadResult(session: session, ...)
    }
}
```

或如果不希望 Home 层直接依赖完整 `UserSession`，可以定义纯展示模型：

```swift
struct CurrentAccountSummary: Equatable, Sendable {
    let accountID: Int64
    let email: String
    let displayName: String
    let signedInAt: Date
    let isPro: Bool
}
```

但不建议再为它创建 `Repository`。它应从 `UserSession` 直接 map 出来。

### Q：是否需要保留 `createdAt` 和 `lastSignedInAt`？

A：当前 `UserProfile.createdAt` 和 `lastSignedInAt` 都来自 session：

```swift
createdAt = session.signedInAt
lastSignedInAt = session.signedInAt
```

这两个字段没有真实的独立含义：

1. `createdAt` 不是账号创建时间，只是本地首次/当前登录时间。
2. `lastSignedInAt` 也只是 `UserSession.signedInAt`。
3. 如果未来真的需要“账号创建时间”或“最近登录时间”，应由服务端 UserSession/Profile 接口返回明确字段，而不是当前本地 Profile 模型伪造。

因此第一期可以不保留；首页如果只是问候展示，用 `session.displayName` 足够。

## 工单 `APP-STARTUP-000003`：登录自动发放 Pro 后响应 is_pro 必须返回最新值

> **实现说明（2026-05）**：`LoginService._prepare_login_entitlements` 统一「设备关联 → 自动发放 → `_apply_is_pro`」顺序；Apple / 密码登录已调整；邮箱 / 手机 OTP 将 `DeviceLinkingService` 提前至自动发放之前；`_issue_tokens` 不再内置 `is_pro`。覆盖测试见 `SparkService/accounts/tests_login_is_pro_after_auto_grant.py`。

### 1. 背景

### Q：现在出现了什么问题？

A：新用户登录时，服务端已经完成自动发放 Pro 权限，后台也能看到试用申请状态为已通过，但登录接口同一个响应里仍返回：

```json
{
  "is_pro": false
}
```

典型现象：

```text
POST /api/v1/auth/apple/login/ status=200
data.is_pro = false
```

但后台试用记录已经是：

```text
状态 = 已通过
授权来源 = auto
country_code = CN
申请流水 source=auto status=已通过
```

客户端随后会按登录响应保存 `UserSession.isPro = false` 到 `SessionSnapshotStore(UserDefaults)`。登录后进入启动引导时，`AppBootstrapper` 会认为当前账号不是 Pro，跳过远端 Pro 模型配置刷新，最终出现：

```text
AI 启动预热：场景「chat」暂无可用模型，等待 Pro 配置刷新或用户配置
```

### Q：这是不是客户端解码问题？

A：不是。客户端日志已经显示 `AppleLoginResult` 正常解码到了服务端返回的 `is_pro=false`：

```text
认证解码：Apple 登录响应解析成功 userId=265 email=... isPro=false
认证仓储：Apple 登录远端上下文已返回 ... isPro=false
会话快照：保存成功 accountID=265
```

问题在服务端登录响应组装顺序：数据库里的权限已经变了，但响应里的 `is_pro` 是发放前的旧值。

### 2. 根因分析

### Q：为什么自动发放成功了，响应仍然是 false？

A：根因是：**部分登录链路先计算并写入响应 `is_pro`，后执行设备关联和自动发放 Pro。**

以 Apple 登录为例，当前链路表现为：

```text
1. 校验 Apple identity token
2. 创建或获取用户
3. 组装登录响应 result
4. result["is_pro"] = TrialService.is_pro_user(user=user)
5. 关联 TrustedDevice
6. 根据 TrustedDevice.country_code 自动发放 Pro
7. 返回第 3~4 步已经组装好的 result
```

因此在同一次请求内会出现时间差：

```text
计算响应 is_pro 时：TrialApplication 还没 active，所以 is_pro=false
请求结束前：TrialApplication 已经 active
最终返回：仍然是旧的 is_pro=false
```

这解释了为什么后台能看到权限已通过，但登录响应仍然不是 Pro。

### Q：哪些登录链路需要重点检查？

A：

1. Apple 登录：需要重点修复。当前日志已经证明 Apple 登录会返回旧 `is_pro`。
2. 账号密码登录：如果 `_issue_tokens(user)` 内部提前写入 `is_pro`，且自动发放在 `_issue_tokens` 之后执行，也会有同类问题。
3. 邮箱 OTP / 手机 OTP：如果当前已经是“先自动发放，再计算 `is_pro` 并返回”，可以不改，但必须补测试防止后续回归。

### 3. 目标

### Q：本工单要达成什么目标？

A：

1. 登录接口返回的 `is_pro` 必须是本次登录、设备关联、自动发放 Pro 后的最新结果。
2. 中国大陆设备首次登录自动发放 Pro 后，同一个登录响应必须返回 `is_pro=true`。
3. 非中国大陆设备、国家为空、没有可信设备信息时，不自动发放，响应保持 `is_pro=false`。
4. 客户端登录成功后保存到 `SessionSnapshotStore` 的 `UserSession.isPro` 必须与服务端最终权限一致。
5. 登录后进入 `AppBootstrapper.bootstrapIfNeeded(for:)` 时，如果本次登录已经自动发放 Pro，必须能立即触发 Pro AI 配置刷新。

### 4. 推荐解决方案

### Q：服务端应该怎么改？

A：统一调整登录响应组装顺序：**先完成设备关联和自动发放，再计算最终 `is_pro` 并组装响应。**

推荐顺序：

```text
login
  -> 校验登录凭证
  -> 创建或获取 User
  -> 关联当前 TrustedDevice（bundle_id + device_id）
  -> TrialService.try_grant_auto_trial_for_login_device(...)
  -> latestIsPro = TrialService.is_pro_user(user=user)
  -> 生成 token
  -> 返回 is_pro = latestIsPro
```

Apple 登录修复方式：

```text
DeviceLinkingService.try_attach_user_to_trusted_device(...)
LoginService._try_grant_auto_trial(...)
result = LoginService._issue_tokens(user)
result["is_pro"] = TrialService.is_pro_user(user=user)
```

或在不大改结构的情况下，至少保证自动发放后重算：

```text
LoginService._try_grant_auto_trial(...)
result["is_pro"] = TrialService.is_pro_user(user=user)
```

账号密码登录修复方式：

```text
如果 _issue_tokens(user) 会写入 is_pro：
  方案 A：把设备关联和自动发放移动到 _issue_tokens(user) 之前
  方案 B：拆分 token 生成与权益字段，token 生成只负责 token，is_pro 在自动发放后统一写入
```

更推荐方案 B，因为 `is_pro` 是业务权益快照，不应该隐藏在 token 生成 helper 里。`_issue_tokens` 如果同时负责 token、用户权益、登录响应业务字段，会让后续增加会员等级、订阅状态、试用到期时间时继续膨胀。

### Q：客户端需要怎么改？

A：客户端不需要为这个问题改解码逻辑。客户端应该继续信任登录响应里的 `is_pro`，但前提是服务端必须返回最终值。

客户端侧只需要保证：

1. `AuthAPI.AppleLoginResult` / 其他登录结果继续正常解码 `is_pro`。
2. `DefaultAuthRepository` 登录成功后用响应创建 `UserSession(isPro:)`。
3. `SessionSnapshotStore` 保存修正后的 `UserSession`。
4. `AppSessionStore` 切换登录态时使用修正后的 `UserSession`。
5. `APP-STARTUP-000001` 的冷启动最新 UserSession 刷新继续保留，作为网络恢复、后台人工发放、跨设备权限变化的兜底链路。

### Q：为什么不能只靠冷启动刷新最新 UserSession 解决？

A：不能只靠冷启动刷新，因为这个问题发生在“刚登录后的同一次会话”：

1. 用户登录成功后马上进入应用，不一定经历下一次冷启动。
2. 登录响应已经被保存到 `SessionSnapshotStore`，如果是旧值，会立即污染本地会话快照。
3. 启动引导和 AI 配置刷新发生在登录成功之后立刻执行，不能等下次冷启动再修正。
4. 登录接口作为创建会话的事实源，必须自己返回最终权益状态。

所以正确关系是：

```text
APP-STARTUP-000003：保证登录响应本身正确
APP-STARTUP-000001：保证冷启动恢复时再次刷新最新 UserSession
```

两者互补，不互相替代。

## 工单 `APP-STARTUP-000004`：登录后通知授权与设备登记流程收敛

### 1. 背景

### Q：登录成功进入首页后，点击通知授权为什么触发两遍设备登记？

A：从日志看，同一次通知授权动作触发了两次 `POST /api/v1/device/register/`。

第一遍发生在系统通知权限返回 `granted=true` 后：

```text
业务=远程推送 请求系统通知权限 granted=true
业务=远程推送 已调用 registerForRemoteNotifications，等待 APNs token 回调
POST /api/v1/device/register/
body.notifications_enabled = true
body.push_token = nil
```

第二遍发生在 APNs token 回调后：

```text
业务=远程推送 收到 APNs device token 待上报 byteLen=32
POST /api/v1/device/register/
body.notifications_enabled = true
body.push_token = "bc714c..."
```

也就是说，当前链路把“通知权限状态”和“APNs token”拆成了两次全量设备登记：

```text
requestAuthorization(granted=true)
  -> registerForRemoteNotifications()
  -> onRemoteNotificationAuthorizationResolved(true)
  -> RegisterDevice(pushToken:nil, notificationsEnabled:true)

APNs token callback
  -> onApnsTokenHex(token)
  -> RegisterDevice(pushToken:token, notificationsEnabled:true)
```

### Q：这是不是问题？

A：是问题，但不是会立刻造成数据重复的严重问题。

从响应看，服务端两次都返回同一个设备：

```text
id=447
created=false
```

说明当前服务端大概率按 `device_id + bundle_id` 做了幂等更新，不会创建两条设备记录。但客户端一次用户动作触发两次全量设备登记，仍然有几个问题：

1. 网络请求重复：同一秒内发两次完整终端画像。
2. 日志噪音明显：排查登录、自动授权、推送问题时容易误判。
3. 状态窗口不稳定：第一遍登记 `notifications_enabled=true` 但没有 `push_token`，服务端会短暂保存“已开启但无 token”的中间态。
4. 未来副作用风险：如果设备登记后续触发自动 Pro、通知订阅、审计流水、风控统计，两次登记会放大副作用。
5. 与启动设备登记叠加：`AppBootstrapper.bootstrapAppLaunchIfNeeded()` 和 `bootstrapIfNeeded(for:)` 也会执行设备登记，登录进入首页后整体登记次数更容易超出预期。

因此需要收敛成一个有状态、可去重的设备登记流程。

### 2. 当前代码位置

| 文件 | 当前职责 |
| --- | --- |
| `SparkClient/Projects/Core/Notification/Infrastructure/PushAdapter.swift` | 请求系统通知权限；调用 `registerForRemoteNotifications()`；收到 APNs token 后回调上报 |
| `SparkClient/Projects/App/Sources/App/Architecture/AssemblyProducts.swift` | 组装 `PushAdapter`，在授权结果和 APNs token 回调中分别调用 `RegisterDeviceUseCase.execute(...)` |

### 3. 根因分析

### Q：为什么会重复？

A：根因是：**设备登记是一个“全量状态上报”动作，但当前被多个事件源直接调用，缺少合并、去重和最终状态聚合。**

当前至少有三类事件会触发设备登记：

1. App 冷启动：上送匿名或登录后的基础设备画像。
2. 登录后账号引导：上送带 `user_id/JWT` 的可信设备画像。
3. 通知授权流程：
   - 授权结果返回后上送 `notifications_enabled`。
   - APNs token 返回后再上送 `push_token`。

问题不在于某一个调用点一定错误，而在于这些调用点都直接打全量接口，没有一个统一的 `DeviceRegistrationCoordinator` 管理“当前已知设备状态”和“最后一次已上报状态”。

### 4. 目标

### Q：本工单要达成什么目标？

A：

1. 同一次通知授权成功后，优先只产生一次包含 `notifications_enabled=true + push_token` 的设备登记。
2. 如果 APNs token 长时间未返回，允许降级上报 `notifications_enabled=true`，但要有延迟窗口和去重策略。
3. 拒绝通知权限时，必须立即上报 `notifications_enabled=false` 并清空 `push_token`。
4. App 启动、登录、通知授权、APNs token 更新都通过统一协调器合并成最少次数的设备登记。
5. 相同 `device_id + bundle_id + user_id + push_token + notifications_enabled + country_code/region_code` 状态不重复上报。
6. 日志能区分触发来源：启动登记、登录后绑定、通知权限更新、APNs token 更新、去重跳过。

### 5. 推荐解决方案

### Q：通知授权成功时应该怎么处理？

A：推荐把授权成功后的立即上报改成“等待 APNs token 的短暂合并窗口”：

```text
requestAuthorization(granted=true)
  -> registerForRemoteNotifications()
  -> DeviceRegistrationCoordinator.markNotificationAuthorized()
  -> 等待 APNs token，最多 1~2 秒

APNs token callback 在窗口内返回：
  -> 上报一次 notifications_enabled=true + push_token=token

APNs token 超时未返回：
  -> 上报一次 notifications_enabled=true + push_token=nil
  -> 后续 token 返回时，如果 token 与已上报状态不同，再补一次 token 更新
```

这样既避免常规路径的两次登记，也保留 APNs token 异步返回失败或很慢时的后端状态同步能力。

### Q：是否需要新增协调器？

A：建议新增轻量的设备登记协调器，例如：

```swift
@MainActor
final class DeviceRegistrationCoordinator {
    func requestRegister(reason: DeviceRegistrationReason)
    func updateNotificationAuthorization(granted: Bool)
    func updateApnsToken(_ token: String)
}
```

内部维护：

```text
currentState：当前已知设备状态
lastSubmittedState：最近一次成功提交状态
pendingTask：等待合并的提交任务
```

去重规则：

```text
如果 currentState == lastSubmittedState：跳过
如果短时间内连续变更：debounce 后只提交最后一次
如果 notifications_enabled=false：立即提交并清空 push_token
如果 notifications_enabled=true 但 push_token 还没到：等待短窗口
```

### Q：服务端需要怎么配合？

A：服务端仍应保持 `/api/v1/device/register/` 幂等，因为客户端去重不能替代服务端幂等。

建议服务端继续按以下键更新同一设备：

```text
device_id + bundle_id
```

并注意：

1. `push_token=nil` 表示本次不知道 token，不应覆盖已有有效 token，除非明确传空字符串。
2. `push_token=""` 表示用户拒绝通知或关闭通知，应清空服务端 token。
3. `notifications_enabled=false` 必须关闭推送。
4. `notifications_enabled=true + push_token=nil` 只能表示权限已开启但 token 暂未得到。

### 6. Apple 登录按钮约束问题

### Q：进入登录页面为什么会出现 Auto Layout 报错？

A：报错来自 `ASAuthorizationAppleIDButton` 的宽度约束冲突：

```text
SwiftUI UIKitPlatformViewHost width == 380
ASAuthorizationAppleIDButton.width <= 375
Will attempt to recover by breaking constraint ASAuthorizationAppleIDButton.width <= 375
```

也就是说，SwiftUI 容器给 Apple 登录按钮分配了 380pt 宽度，但系统的 `ASAuthorizationAppleIDButton` 内部存在 `width <= 375` 的约束。两者冲突后，UIKit 只能打断其中一个约束。

当前相关位置：

```text
SparkClient/Projects/Features/Auth/Presentation/LoginView.swift
```

当前按钮只限制了高度：

```swift
SignInWithAppleButton(...)
    .signInWithAppleButtonStyle(.black)
    .frame(height: 48)
    .clipShape(RoundedRectangle(cornerRadius: 12))
```

如果父容器宽度超过 375，就可能触发系统按钮内部宽度约束冲突。

### Q：如何修复这个约束问题？

A：给 Apple 登录按钮一个明确的最大宽度，不让 SwiftUI 容器把它撑到系统按钮约束之外。

建议：

```swift
SignInWithAppleButton(...)
    .signInWithAppleButtonStyle(.black)
    .frame(maxWidth: 375)
    .frame(height: 48)
```

如果外层希望整体视觉居中：

```swift
SignInWithAppleButton(...)
    .signInWithAppleButtonStyle(.black)
    .frame(maxWidth: 375)
    .frame(height: 48)
    .frame(maxWidth: .infinity, alignment: .center)
```

同时不建议用 `clipShape` 强行裁切系统按钮来实现圆角。`SignInWithAppleButton` 本身是系统控件，圆角和高度应尽量遵循系统控件能力，避免 SwiftUI 外层裁切和 UIKit 内部约束叠加产生不可预期布局。

## 工单 `APP-STARTUP-000005`：登录流程接入公共通知提示

### 3. 推荐交互策略

### Q：成功和失败分别怎么提示？

A：推荐按场景使用公共通知等级：

| 场景 | 推荐提示 | 展示形态 |
| --- | --- | --- |
| Apple 登录成功 | 登录成功 | success toast |
| Apple 登录失败 | Apple 登录失败，请稍后重试 | error banner |
| Apple 登录取消 | 已取消 Apple 登录 | info toast，可选不提示 |
| 手机验证码发送成功 | 验证码已发送 | success toast |
| 手机验证码发送失败 | 验证码发送失败，请稍后重试 | error banner |
| 手机验证码重发成功 | 验证码已重新发送 | success toast |
| 手机验证码重发失败 | 验证码重发失败，请稍后重试 | error banner |
| 手机验证码登录成功 | 登录成功 | success toast |
| 手机验证码登录失败 | 验证码错误或已过期，请重新输入 | error banner |
| 网络不可用/超时 | 网络连接异常，请稍后重试 | warning banner |

注意：

1. 输入校验类错误可以继续在按钮禁用、输入框状态中体现，但接口返回错误必须走公共通知。
2. Apple 用户主动取消不应当作为错误红色提示，避免制造焦虑。
3. 登录成功后页面会切到首页，成功 toast 应通过全局 `NotificationHostView` 展示，确保路由切换后仍能看到。

### 4. 推荐实现方式

### Q：通知能力应该接在哪里？

A：建议把 `NotificationClient` 注入 `LoginViewModel`，由 ViewModel 在业务流程节点发布通知。

原因：

1. 登录成功/失败发生在 ViewModel 调用用例之后，ViewModel 最清楚业务结果。
2. View 不应该解析错误类型，也不应该直接拼接接口错误文案。
3. `DefaultAuthRepository` 不应该直接发 UI 通知，它属于基础设施层，负责请求、持久化 token 和 session。
4. 用例层也不建议直接依赖 UI 通知，避免应用服务和展示反馈耦合。

推荐依赖方向：

```text
AppContainer.makeLoginViewModel()
  -> LoginViewModel(..., notificationClient: notificationClient)

LoginViewModel
  -> signInWithApple(...)
      success: notificationClient.success(...)
      failure: notificationClient.error(...)
      cancel: notificationClient.info(...) 或不提示
  -> sendOTP(...)
      success: notificationClient.success(...)
      failure: notificationClient.error(...)
  -> phoneLogin(...)
      success: notificationClient.success(...)
      failure: notificationClient.error(...)
```

### Q：是否还需要保留 `errorMessage`？

A：第一期可以保留，但不能再作为唯一反馈来源。

建议：

1. `errorMessage` 仅用于调试、辅助无障碍、或未来输入框附近的局部错误文案。
2. 用户可感知的全局反馈统一通过 `NotificationClient`。
3. 如果后续没有页面内错误文案需求，可以再移除 `errorMessage`，避免状态冗余。

### Q：错误文案如何处理？

A：建议新增登录错误到用户文案的映射方法，避免直接展示 `localizedDescription`。

示例：

```swift
private func userFacingAuthMessage(for error: Error, fallback: String) -> String
```

映射原则：

1. 网络错误：提示网络连接异常。
2. 验证码错误/过期：提示验证码错误或已过期。
3. Apple credential 缺失：提示 Apple 登录凭证无效，请重试。
4. 服务端业务错误：优先展示后端已本地化、可给用户看的 `msg`。
5. 未识别错误：使用通用失败文案。

## 工单 `APP-STARTUP-000006`：配合单账号单设备有效登录

### 1. 背景

### Q：为什么客户端也需要配合服务端 `ACCOUNTS-000001`？

A：服务端 `ACCOUNTS-000001` 要实现“一个用户同一时间只有一个有效设备登录”。服务端是唯一事实源，负责判断当前有效设备、让旧设备 refresh token 失效、APNs 只投递当前有效设备。

但客户端仍需要配合完成体验闭环：

1. 任意需要登录态的客户端请求被服务端以设备会话失效原因拒绝后，客户端必须清理本地登录态。
2. 旧设备被新设备顶掉后，客户端需要展示明确提示，而不是静默掉线。
3. 登录、refresh、设备登记请求需要稳定携带 `device_id + bundle_id`，方便服务端做设备会话校验。
4. 旧设备退出后不能继续以登录态上报设备登记和 push token。
5. 新设备重新登录后，需要重新完成设备登记、通知权限状态同步和会话启动引导。

本工单与服务端文档配合：

```text
SparkService/accounts/账户需求文档.md
ACCOUNTS-000001：单账号仅允许一个有效设备登录
```

### 2. 目标

### Q：客户端要达成什么目标？

A：

1. A1 登录后，A1 正常刷新 token 和使用 App。
2. A2 登录同一账号后，A2 正常使用。
3. A1 再次打开 App 或提交任何需要登录态的客户端请求时，如果服务端返回 `401 device_session_revoked / device_session_replaced`，A1 必须强制退出登录。
4. A1 强制退出时展示公共通知提示：账号已在另一台设备登录，请重新登录。
5. A1 本地 token、`SessionSnapshotStore`、账号级缓存状态必须清理，不能继续进入首页。
6. A1 退出后不再带登录态执行设备登记、聊天同步、医疗同步、AI 配置刷新等账号级请求。
7. A1 重新登录后，A2 下次提交任意登录态请求被服务端拒绝，A2 按同样逻辑退出。

### 3. 客户端职责边界

### Q：客户端是否需要判断哪台设备有效？

A：不需要。当前有效设备只能由服务端判定。

客户端只做四件事：

1. 所有认证相关请求携带本机 `device_id + bundle_id`。
2. 收到服务端 401 认证失效后，识别是否为设备会话失效；该规则适用于 refresh token、设备登记、用户会话刷新、聊天同步、医疗同步、AI 配置刷新等所有登录态请求。
3. 调用现有登出/会话失效流程清理本地状态。
4. 使用公共通知提示用户原因。

不要在客户端做：

1. 不要本地保存“当前有效设备”并自行判断。
2. 不要因为本机有 push token 就认为自己仍是有效设备。
3. 不要绕过服务端重新刷新 Pro、AI 配置或用户会话。
4. 不要在旧设备被踢后继续静默重试 refresh。

### 4. 请求字段配合

### Q：哪些请求需要带设备标识？

A：至少以下请求需要稳定携带：

| 请求 | 设备字段要求 |
| --- | --- |
| Apple 登录 | 已有 `device_id` / `bundle_id`，继续保持 |
| 手机号验证码登录 | 已有 `device_id` / `bundle_id`，继续保持 |
| 密码登录（如保留） | 需要带 `device_id` / `bundle_id` |
| refresh token | 建议新增 `device_id` / `bundle_id` |
| 设备登记 `/device/register/` | 已有 `device_id` / `bundle_id`，继续保持 |
| 冷启动最新 UserSession 刷新 | 如服务端要求，可带 `device_id` / `bundle_id` 作为校验辅助 |

### Q：为什么 refresh token 也要带 `device_id + bundle_id`？

A：服务端可以从 refresh token claim 判断设备会话，但请求体带设备标识有两个收益：

1. 能防止 refresh token 被复制到另一台设备后继续使用。
2. 服务端日志能直接看到“哪个安装实例触发了设备会话失效”。

服务端仍是事实源，客户端只是提供当前设备上下文。

### 5. 401 处理策略

### Q：客户端收到什么响应要强制退出？

A：只要任意需要登录态的客户端请求返回 401，且服务端 `msg/code` 表示设备会话失效，就走强制退出。

必须覆盖的请求包括：

1. refresh token。
2. 冷启动最新 `UserSession` 刷新。
3. 登录态 `/device/register/`。
4. 聊天同步、附件同步、医疗同步等账号级同步。
5. AI 配置刷新、Pro 配置刷新、用户档案引导等账号级启动请求。
6. 其他所有带 Authorization 的业务 API。

这条规则的核心是：**旧设备只要再次和服务端发生任何登录态交互，就应该被服务端拒绝，并由客户端立即进入强制退出流程。**

建议识别：

```text
device_session_revoked
device_session_replaced
device_session_not_found
device_mismatch
token_not_valid
```

其中：

1. `device_session_revoked` / `device_session_replaced`：展示“账号已在另一台设备登录，请重新登录”。
2. `device_mismatch`：展示“当前设备验证失败，请重新登录”。
3. `token_not_valid`：使用通用“登录已过期，请重新登录”。

如果底层网络层已经有统一认证失效事件，应复用现有链路，不新增并行退出机制。

### 6. 本地状态清理

### Q：强制退出时要清理哪些状态？

A：至少需要清理：

1. Keychain 中的 `accessToken` / `refreshToken` / `expiresAt` / `tokenType`。
2. `SessionSnapshotStore(UserDefaults)` 中的 `UserSession`。
3. `AppSessionStore` 内存登录态。
4. 账号级 ViewModel / route graph / sync runtime。
5. 文件传输运行时凭证。
6. 账号级 AI 配置运行时缓存、聊天同步、医疗同步等正在执行的账号任务。

优先复用现有认证失效事件和 `AccountSessionRuntime` 清理流程，避免登录退出逻辑分叉。

### 7. 用户提示

### Q：用户应该看到什么提示？

A：使用项目公共通知体系，不新增局部 toast。

推荐文案：

```text
账号已在另一台设备登录，请重新登录
```

展示形态：

```text
warning banner 或 info banner
```

原因：

1. 这是预期安全策略，不是系统崩溃。
2. 用户需要知道为什么被退回登录页。
3. 提示应在切换到登录页后仍能看到，因此必须走全局 `NotificationHostView`。

### 8. 与设备登记 / 推送的关系

### Q：旧设备被踢后，还能继续上报 push token 吗？

A：不能继续以登录态上报。

建议：

1. 强制退出后停止账号级设备登记。
2. 如果 App 冷启动仍需要匿名设备登记，只能走匿名登记，不带用户 token。
3. APNs token 本身可以保留在系统侧，但服务端只会向当前 ACTIVE 设备投递。
4. 重新登录后再执行登录态设备登记，并同步通知权限和 push token。

### 9. 不需要考虑的数据迁移

### Q：客户端是否需要做本地数据迁移？

A：不需要。

原因：

1. 当前项目按全新项目处理，不要求兼容历史旧会话数据迁移。
2. 单设备有效登录的事实源在服务端，客户端只按 401 清理本地状态。
3. 本地 `SessionSnapshotStore` 不需要迁移，只需要在强制退出时清理。
4. `device_id` 仍使用现有稳定设备标识，不新增客户端历史映射。

### 11. 验收标准

1. A1 登录用户1后，A1 正常进入首页并 refresh token 成功。
2. A2 登录同一用户后，A2 正常进入首页并 refresh token 成功。
3. A1 未手动退出，再次打开 App 触发 refresh token，收到服务端 401 后强制退出。
4. A1 未手动退出，如果先触发的是设备登记、聊天同步、医疗同步、AI 配置刷新或任意登录态业务 API，收到设备会话失效 401 后同样强制退出。
5. A1 被强制退出后清理 token、`SessionSnapshotStore` 和账号级运行时状态。
6. A1 被强制退出后展示公共通知“账号已在另一台设备登录，请重新登录”。
7. A1 退出后不会继续以登录态调用设备登记、聊天同步、医疗同步、AI 配置刷新。
8. A1 重新登录后，A2 下次提交任意登录态请求被服务端拒绝，A2 按同样逻辑退出。
9. refresh token 请求携带当前 `device_id + bundle_id`，并与服务端 token claim 校验口径一致。
10. 不新增客户端本地“有效设备判断”逻辑，有效性以服务端 401 为准。
11. 不做客户端数据迁移；全新项目只保证新逻辑下的会话清理和重新登录体验。
