# 冷启动目标页面公共调度需求文档

> 范围说明：本文描述 SparkClient 在冷启动、会话恢复、登录后进入主界面之前收到“打开特定页面”的外部事件时，如何通过一套公共调度组件完成暂存、等待、消费和页面展示。本文只新增需求工单，不修改任何代码。第一期重点覆盖：外部 PDF 打开医疗文档上传页、APNs 推送通知点击打开成员邀请列表页。成员邀请深链链路不纳入本次改造，保持现状。

## 工单 `APP-COLD-ROUTE-000001`：冷启动目标页面公共调度组件

### 1. 背景

### Q：为什么要做这个公共组件？

A：当前项目里已经出现多种“App 被外部事件拉起后，需要打开某个特定页面”的场景：

1. 系统文件 / 微信 / 浏览器中选择“用 SparkClient 打开 PDF”，App 冷启动后需要进入首页，再打开 `MedicalDocumentUploadHostView`，并把 PDF 放进 `selectedFiles`。
2. 用户点击 APNs 成员邀请通知，App 冷启动后需要进入首页，再打开 `PendingMemberInvitesView`，并高亮对应邀请。
3. 未来还会有任务提醒、AI 试用审核通知、聊天消息通知、医疗资料详情通知、模型设置引导等入口。

这些场景的共同点是：外部事件到达时，App 可能还处在以下任一状态：

```text
进程未启动
  -> iOS 传入 URL / launchOptions / scene connection options / notification response
  -> AppContainer 尚未完全可用
  -> AppCoordinatorView 仍在 loading
  -> 网络门禁未完成
  -> sessionStore 尚未恢复
  -> 用户未登录或刚登录
  -> signedIn 但 account runtime 尚未 prepared
  -> onboarding 未结束
  -> MainTabCoordinatorView 尚未构建
  -> HomeView 尚未挂载 sheet/fullScreenCover
```

如果每个入口都各自尝试“收到事件后马上打开页面”，就会重复写大量生命周期判断，并出现以下问题：

1. 页面承载点还没进 SwiftUI 视图树，弹层或导航不会出现。
2. 事件被路由到了 `AppRouteStore`，但首页还没开始监听。
3. 文件 URL 在 security scope 未开启前被判断为不可读。
4. 推送点击已经被解析为 route，但冷启动时 route signal 被 HomeView 首次挂载前错过。
5. 每个功能都各自做 pending store，产生历史代码和状态不一致。
6. 前台、后台、冷启动、未登录登录后四种路径行为不一致。

因此需要把这类需求抽象为一套 App 级“冷启动目标页面公共调度组件”，统一处理外部事件的暂存、就绪判断、消费与页面打开。

### Q：市面上最通用的处理方法是什么？

A：移动端 App 通用做法是 **Deferred Navigation Intent / Pending Launch Intent** 模式：

```text
外部事件入口
  -> 解析成标准化 LaunchIntent
  -> 立即保存到 App 级 pending store / coordinator
  -> 不直接操作具体 ViewModel 或 SwiftUI 页面
  -> 等待 App readiness gate 全部满足
  -> 主界面宿主消费 LaunchIntent
  -> 通过目标页面适配器打开具体页面
  -> 消费成功后清空 pending intent
```

核心原则：

1. 外部入口层只负责解析事实，不负责展示 UI。
2. 页面展示必须等主界面 ready，而不是等 URL / 推送回调 ready。
3. 冷启动事件要先持久化或至少进程内暂存，避免 View 未挂载时丢失。
4. 所有入口统一进入 typed intent，不再让不同功能私自穿透到 `HomeViewModel`。
5. 消费动作必须具备幂等性，同一个 intent 只能打开一次。
6. 登录态相关 intent 必须绑定账号或延迟到账号确定后再消费。
7. 前台收到通知和用户点击通知要区分：前台只提示，点击才打开目标页。

### 2. 当前现状

### Q：外部 PDF 当前链路是什么？

A：外部 PDF 已经实现了一套相对独立的 coordinator：

```text
系统 openURL / launchOptions / sceneConnection / applicationOpen
  -> ExternalMedicalDocumentImportCoordinator
  -> 校验 PDF
  -> security-scoped copy 到临时目录
  -> pendingDocument
  -> HomeView 监听 pendingDocument
  -> consumePendingExternalMedicalDocumentIfNeeded()
  -> medicalDocumentUploadViewModel.prepareForExternalImport(files:)
  -> activeFullScreenCover = .medicalDocumentUpload
  -> MedicalDocumentUploadHostView
```

涉及关键文件：

```text
SparkClient/SparkClient/Projects/App/Sources/App/ExternalMedicalDocumentImportCoordinator.swift
SparkClient/SparkClient/Projects/App/Sources/App/SparkApplicationDelegate.swift
SparkClient/SparkClient/Projects/App/Sources/ContentView.swift
SparkClient/SparkClient/Projects/Features/Home/Presentation/HomeView.swift
SparkClient/SparkClient/Projects/Features/MedicalDocumentUpload/Presentation/MedicalDocumentUploadViewModel.swift
```

问题是：这套 coordinator 只服务 PDF，不能复用给推送通知点击、任务提醒、聊天消息等其他冷启动目标页面。

### Q：成员邀请推送点击当前链路是什么？

A：成员邀请通知点击当前走 `AppRouteStore` 信号栈，最后由 `HomeView` 监听 `routeStacks` 再打开 Sheet。

当前链路：

```text
APNs payload(type=member_invite, route=member_invite, invite_id=...)
  -> PushAdapter.userNotificationCenter(_:didReceive:)
  -> HandleRemoteNotificationUseCase.execute(entryPoint: .interaction)
  -> RemoteNotificationPayload.mapRoute
  -> AppRoute.memberInvite(inviteID:)
  -> RouteCoordinator.routeRemoteNotification
  -> AppRouteStore.route(to: .memberInvite, replaceStack: true)
  -> selectedTab = .home
  -> routeStacks[.home].append(.memberInvite)
  -> HomeView.onReceive(routeStore.$routeStacks)
  -> HomeViewModel.handleRoute(.memberInvite)
  -> fetchPendingInvitesIfNeeded()
  -> highlightInviteID = inviteID
  -> activeSheet = .pendingInvites
  -> HomeView.sheet
  -> PendingMemberInvitesView
```

最终页面位置：

```text
SparkClient/SparkClient/Projects/Features/Home/Presentation/HomeView.swift:150-163
```

当前页面代码：

```swift
case .pendingInvites:
    PendingMemberInvitesView(
        items: viewModel.pendingInvites,
        highlightInviteID: viewModel.highlightInviteID,
        onAccept: { item in
            viewModel.openInviteAccept(item)
        },
        onReject: { item in
            await viewModel.rejectPendingInvite(item)
        },
        onAppearRefresh: {
            await viewModel.fetchPendingInvitesIfNeeded()
        }
    )
```

### Q：成员邀请深链当前链路是什么？

A：成员邀请深链不走 `AppRoute.memberInvite`，而是先暂存 inviteID，再让首页首次 task 消费。

当前链路：

```text
spark://member-invite?id=...
  -> ContentView.onOpenURL
  -> RouteCoordinator.handleDeepLink
  -> PendingMemberInviteStore.save(inviteID)
  -> route .home
  -> HomeView.task
  -> HomeViewModel.consumePendingInviteIfNeeded()
  -> PendingMemberInviteStore.consume(forAccountID:)
  -> fetchPendingInvitesIfNeeded()
  -> highlightInviteID = inviteID
  -> activeSheet = .pendingInvites
  -> PendingMemberInvitesView
```

本工单明确要求：**成员邀请深链不要改造。**  
原因是深链现有链路承担“未登录或首页未就绪时按账号暂存 7 天”的历史能力，当前产品诉求只要求推送通知点击冷启动进入邀请页走公共调度组件。

### 3. 当前问题

### Q：为什么成员邀请推送点击冷启动仍然需要改造？

A：成员邀请推送点击目前依赖 `AppRouteStore.routeStacks` 作为“信号”。这个方案在前台或主界面已挂载时能工作，但冷启动时存在天然脆弱点：

1. `RouteCoordinator.routeRemoteNotification` 在推送回调中立即写入 `routeStore`。
2. 写入时 `MainTabCoordinatorView` 和 `HomeView` 可能还没有被创建。
3. `HomeView.onReceive(routeStore.$routeStacks)` 只在 HomeView 已经挂载后接收后续变化。
4. 如果 routeStacks 的变化发生在 HomeView 挂载前，HomeView 首次出现时可能不会触发这段逻辑。
5. `.memberInvite` 在 `MainTabCoordinatorView.routeDestination` 中实际渲染为 `EmptyView()`，真正页面依赖 HomeView 的 side effect 打开 Sheet。
6. 这导致“路由图中有 memberInvite，但 UI 没打开”的状态不容易观测，也不容易恢复。

换句话说，当前 `AppRouteStore` 被同时用作：

```text
Tab 切换状态
Navigation stack 状态
一次性 Sheet 打开信号
推送点击事件载体
```

这几种职责混在一起，冷启动场景下最容易丢失“一次性事件”。

### Q：为什么不能继续给每个功能加一个自己的 pending coordinator？

A：外部 PDF 已经有 `ExternalMedicalDocumentImportCoordinator`，成员邀请深链已有 `PendingMemberInviteStore`，成员分享还有 `PendingMemberShareTicketStore`。如果推送通知再新增一套自己的 pending store，后续任务提醒、聊天通知、体检报告通知都会继续复制类似逻辑。

长期会变成：

```text
ExternalMedicalDocumentImportCoordinator
PendingMemberInviteStore
PendingMemberShareTicketStore
PendingTaskNotificationStore
PendingChatRouteStore
PendingMedicalReportRouteStore
...
```

问题：

1. 每个 store 都各自判断登录态和首页 ready。
2. 每个 store 都各自决定消费时机。
3. 每个 store 都各自清理和去重。
4. 每个页面宿主都堆满 `consumePendingXXXIfNeeded()`。
5. 出现多个 pending 事件时没有统一优先级。
6. 后续排查冷启动问题时无法知道事件在哪个阶段丢失。

因此需要公共组件负责“事件生命周期”，具体业务只提供“如何打开页面”的 adapter。

### 4. 目标

### Q：本工单要达成什么目标？

A：

1. 建立 App 级公共 `LaunchIntent` / `PendingLaunchIntentCoordinator` 能力，统一承接冷启动打开特定页面的外部事件。
2. 外部 PDF 打开医疗文档上传页改造为公共 intent 的一个目标类型，不再是医疗 PDF 专属冷启动流程。
3. APNs 推送通知点击打开成员邀请列表页改造为公共 intent 的一个目标类型。
4. 成员邀请推送点击冷启动时，必须在 App 完成启动、登录态恢复、账号准备、首页挂载后打开 `PendingMemberInvitesView`。
5. 成员邀请推送点击进入邀请页后，必须拉取待处理邀请并高亮 `invite_id` 对应行。
6. 成员邀请前台推送仍然只刷新角标和展示可点击 Banner，不自动打开 Sheet。
7. 成员邀请深链 `spark://member-invite?id=...` 不纳入本次改造，保持 `PendingMemberInviteStore` 现有链路。
8. 公共组件要支持未来扩展任务提醒、聊天通知、AI 设置页、医疗资料详情页等目标。
9. 清理成员邀请推送链路中把 `AppRouteStore.routeStacks` 当一次性 Sheet 信号的历史代码。
10. 清理外部 PDF 专属 coordinator 中与“冷启动目标页面调度”重复的职责，只保留 PDF 文件接收和复制能力。

### 5. 非目标

1. 不改造成员邀请深链链路。
2. 不改变 `PendingMemberInvitesView` 的 UI 结构。
3. 不改变成员邀请接受、拒绝、刷新接口。
4. 不改变 APNs payload 字段格式，继续支持 `type=member_invite`、`route=member_invite`、`invite_id`。
5. 不把前台收到推送改成自动打开页面。
6. 不在本工单内实现所有未来通知类型，只设计可扩展接口并落地 PDF 与成员邀请推送点击。
7. 不要求跨 App 重启持久化外部 PDF 文件意图；但推送点击类 intent 需要在当前启动流程内不丢失。

### 6. 总体方案

### Q：推荐架构是什么？

A：新增一个 App 级公共目标页面调度器：

```text
LaunchIntentCoordinator
  ├─ receive(intent, source)
  ├─ 暂存 pending intent
  ├─ 等待 readiness gate
  ├─ 按优先级选择可消费 intent
  ├─ 调用目标页面 adapter
  └─ 消费成功后清理
```

推荐链路：

```text
外部入口
  -> 入口专属解析器
  -> LaunchIntent
  -> LaunchIntentCoordinator.receive(...)
  -> AppCoordinatorView 进入 signedIn + preparedAccountID
  -> MainTabCoordinatorView 已构建
  -> HomeView 已挂载 sheet/fullScreenCover
  -> HomeLaunchIntentConsumer.consumeIfReady()
  -> LaunchIntentHandler 打开具体页面
```

PDF 链路：

```text
PDF URL
  -> ExternalDocumentImportReceiver
  -> security-scoped copy
  -> LaunchIntent.medicalDocumentUpload(files: [MedicalUploadLocalFile])
  -> LaunchIntentCoordinator
  -> HomeLaunchIntentConsumer
  -> medicalDocumentUploadViewModel.prepareForExternalImport(files:)
  -> activeFullScreenCover = .medicalDocumentUpload
```

成员邀请推送点击链路：

```text
APNs notification response
  -> PushAdapter.didReceive
  -> HandleRemoteNotificationUseCase(entryPoint: .interaction)
  -> LaunchIntent.memberInviteFromPush(inviteID)
  -> LaunchIntentCoordinator
  -> HomeLaunchIntentConsumer
  -> viewModel.openPendingInvitesFromPush(inviteID)
  -> fetchPendingInvitesIfNeeded()
  -> highlightInviteID = inviteID
  -> activeSheet = .pendingInvites
  -> PendingMemberInvitesView
```

成员邀请深链链路保持不变：

```text
spark://member-invite?id=...
  -> PendingMemberInviteStore.save
  -> HomeViewModel.consumePendingInviteIfNeeded
  -> activeSheet = .pendingInvites
```

### 7. 核心模型设计

### `LaunchIntent`

建议新增 App 级 intent 枚举：

```swift
enum LaunchIntent: Equatable, Sendable, Identifiable {
    case medicalDocumentUpload(ExternalMedicalDocumentUploadIntent)
    case memberInviteFromPush(MemberInvitePushLaunchIntent)
    case appRoute(AppRouteLaunchIntent)
}
```

说明：

| case | 说明 |
| --- | --- |
| `medicalDocumentUpload` | 外部文档导入后打开医疗文档上传页，第一期来源为 PDF |
| `memberInviteFromPush` | 用户点击成员邀请 APNs 通知后打开待处理邀请页 |
| `appRoute` | 未来给普通 tab / navigation route 使用，如聊天线程、设置页 |

### `ExternalMedicalDocumentUploadIntent`

```swift
struct ExternalMedicalDocumentUploadIntent: Equatable, Sendable, Identifiable {
    let id: UUID
    let files: [MedicalUploadLocalFile]
    let receivedAt: Date
    let source: LaunchIntentSource
    let originalURLDescription: String?
}
```

字段要求：

| 字段 | 说明 |
| --- | --- |
| `files` | 已复制到 App 可访问目录的文件，不能保存外部 security-scoped 原始 URL |
| `receivedAt` | 用于日志和优先级判断 |
| `source` | `documentOpen` / `onOpenURL` / `sceneConnection` 等 |
| `originalURLDescription` | 日志用，不作为后续读取依据 |

### `MemberInvitePushLaunchIntent`

```swift
struct MemberInvitePushLaunchIntent: Equatable, Sendable, Identifiable {
    let id: UUID
    let inviteID: Int
    let receivedAt: Date
    let actionIdentifier: String
    let notificationRequestID: String?
}
```

字段要求：

| 字段 | 说明 |
| --- | --- |
| `inviteID` | APNs payload 中的邀请 ID，用于高亮 |
| `actionIdentifier` | 系统通知点击 action，用于区分默认点击/自定义 action |
| `notificationRequestID` | 系统通知 request identifier，用于日志追踪 |

### `LaunchIntentSource`

```swift
enum LaunchIntentSource: String, Sendable {
    case launchOptions
    case sceneConnection
    case applicationOpen
    case onOpenURL
    case remoteNotificationInteraction
    case inAppNotificationBannerTap
}
```

说明：

1. 外部 PDF 冷启动可能来自 `launchOptions` / `sceneConnection`。
2. 前台 Banner 点击可以选择进入公共 intent，但第一期成员邀请前台 Banner 可继续调用通知交互路由；最终也应落到 `remoteNotificationInteraction` 或 `inAppNotificationBannerTap`。
3. 深链来源不纳入成员邀请本次改造。

### 8. Readiness Gate 设计

### Q：什么时候可以消费 intent？

A：必须满足以下条件：

```text
App 进程已完成依赖容器初始化
网络门禁不阻断主界面
sessionState == .signedIn(session)
lifecycle.preparedAccountID == session.accountID
onboardingStore 不处于 needsOnboarding
MainTabCoordinatorView 已构建
目标 root tab 已存在
目标页面宿主 View 已挂载
目标页面宿主能展示 sheet/fullScreenCover/navigation
```

建议抽象为：

```swift
struct LaunchIntentReadiness: Equatable, Sendable {
    let accountID: Int64?
    let isSignedIn: Bool
    let isAccountPrepared: Bool
    let isOnboardingBlocking: Bool
    let mainTabReady: Bool
    let homeHostReady: Bool
}
```

公共调度器不应该直接读取所有 UI 状态，而是由 `AppCoordinatorView`、`MainTabCoordinatorView`、`HomeView` 在生命周期节点上报 readiness。

### Q：为什么必须等 HomeView host ready？

A：成员邀请页是 `HomeView.sheet(item:)` 展示的 `PendingMemberInvitesView`，PDF 上传页是 `HomeView.fullScreenCover(item:)` 展示的 `MedicalDocumentUploadHostView`。这两个目标都不是真正的 tab navigation destination，而是首页宿主上的弹层。

如果只等 `MainTabCoordinatorView` ready，而 HomeView 的 `.sheet` / `.fullScreenCover` 尚未挂载，打开动作仍可能丢失。因此第一期至少需要 `homeHostReady`。

### 9. 消费策略

### Q：多个 pending intent 同时存在时如何处理？

A：第一期建议只消费一个最高优先级 intent，其他保留或覆盖，规则如下：

| 优先级 | Intent | 原因 |
| --- | --- | --- |
| P0 | 用户点击的推送通知 | 用户刚刚明确点击，期望最高 |
| P1 | 外部文档打开 | 用户刚刚从系统文件/其他 App 打开，期望较高 |
| P2 | 前台 Banner 点击 | 已在 App 内，仍是用户主动行为 |
| P3 | 普通 tab route | 可延后 |

同类型去重：

1. `memberInviteFromPush(inviteID)`：同一个 inviteID 只保留最新一次。
2. `medicalDocumentUpload(files)`：第一期保留最后一次外部打开的文件，避免多次冷启动重复弹页。
3. 消费成功后必须从 pending 队列移除。
4. 消费失败但可重试时保留，例如首页未 ready。
5. 消费失败且不可恢复时清理并提示，例如文件不存在。

### Q：如何避免重复弹页？

A：

1. 每个 intent 有唯一 `id`。
2. coordinator 维护 `consumedIntentIDs` 或状态机。
3. handler 返回消费结果：

```swift
enum LaunchIntentConsumeResult {
    case consumed
    case notReady
    case failedRecoverable(String)
    case failedTerminal(String)
}
```

4. `consumed` 后立即清理。
5. `notReady` 不清理，下次 readiness 变化再尝试。
6. `failedTerminal` 清理并展示错误。

### 10. 目标页面 Handler 设计

### Q：PDF 上传页如何作为 handler 接入？

A：PDF handler 的宿主是 `HomeView`，因为上传页由首页 `fullScreenCover` 展示。

消费动作：

```text
routeStore.route(to: .home, replaceStack: false)
medicalDocumentUploadViewModel.prepareForExternalImport(files:)
activeFullScreenCover = .medicalDocumentUpload
```

约束：

1. 不自动开始识别。
2. 保持 `.picking` 阶段。
3. 如果当前上传页处于 `.processing` 或 `.result`，返回 `notReady` 或排队，不能打断当前流程。
4. 如果当前上传页处于 `.picking`，第一期可替换文件；后续可做合并。

### Q：成员邀请推送如何作为 handler 接入？

A：成员邀请推送 handler 的宿主也是 `HomeView`，因为邀请页由首页 `sheet(item:)` 展示。

消费动作：

```text
routeStore.route(to: .home, replaceStack: false)
await homeViewModel.openPendingInvitesFromPush(inviteID)
```

`openPendingInvitesFromPush(inviteID)` 建议封装现有逻辑：

```text
fetchPendingInvitesIfNeeded()
highlightInviteID = inviteID
activeSheet = .pendingInvites
```

约束：

1. 如果已有其他 sheet 正在展示，第一期建议延迟消费，避免覆盖用户正在操作的 sheet。
2. 如果 `pendingInvites` 中没有对应 inviteID，也仍然打开列表；列表 onAppear 继续刷新。
3. 高亮逻辑继续交给 `PendingMemberInvitesView`。
4. 接受/拒绝流程不改。
5. 前台收到推送不自动打开；只有用户点击系统通知或 App 内 Banner 才创建 intent。

### 11. 推送通知改造边界

### Q：成员邀请推送通知哪些地方要改？

A：只改“用户点击通知”的路由落点：

当前：

```text
HandleRemoteNotificationUseCase
  -> routeCoordinator.routeRemoteNotification
  -> AppRouteStore.route(.memberInvite)
  -> HomeView.onReceive(routeStacks)
  -> HomeViewModel.handleRoute(.memberInvite)
```

目标：

```text
HandleRemoteNotificationUseCase
  -> LaunchIntentCoordinator.receive(.memberInviteFromPush(inviteID))
  -> HomeLaunchIntentConsumer
  -> HomeViewModel.openPendingInvitesFromPush(inviteID)
```

保留：

```text
foreground member_invite
  -> NotificationCenter.post(.memberInvitePendingRefresh)
  -> 展示可点击 Banner
  -> 用户点击 Banner 后进入公共 intent 或保留 interaction 入口
```

不改：

```text
spark://member-invite?id=...
  -> PendingMemberInviteStore
  -> HomeViewModel.consumePendingInviteIfNeeded()
```

### Q：为什么深链不改？

A：本工单要求明确“不改造深链”。此外深链已有账号维度 7 天暂存能力，适合短信/邮件场景：用户可能未登录、可能隔天再打开、可能先登录另一个账号。推送点击是一次当前设备上的用户交互，适合走本次新的冷启动 intent。

### 12. 历史冗余代码清理

### Q：哪些历史代码需要清理？

A：第一期落地后，需要清理或收敛以下职责：

#### 成员邀请推送链路

1. `AppRoute.memberInvite(inviteID:)` 不再作为推送通知点击打开 Sheet 的通道。
2. `AppRouteStore.route(to:)` 中针对 `.memberInvite` 的特殊压栈逻辑，需要确认是否只剩深链或其他入口依赖；如果无依赖，应删除。
3. `HomeView.onReceive(dependencies.routeStore.$routeStacks)` 中监听 `.memberInvite` 并调用 `viewModel.handleRoute` 的逻辑，应迁移到 `HomeLaunchIntentConsumer`。
4. `HomeViewModel.handleRoute(_:)` 中处理 `.memberInvite` 的方法，如果只服务推送点击，应删除或改名为更明确的内部方法。
5. `MainTabCoordinatorView.routeDestination` 中 `.memberInvite` 渲染 `EmptyView()` 的历史兼容，需要确认移除。

#### 外部 PDF 链路

1. `ExternalMedicalDocumentImportCoordinator` 不再同时承担“冷启动页面调度”职责。
2. 它应只保留：接收 URL、校验文件、security-scoped copy、生成 `LaunchIntent.medicalDocumentUpload`。
3. `HomeView` 中 `consumePendingExternalMedicalDocumentIfNeeded()` 应迁移为公共 `HomeLaunchIntentConsumer` 的一个 handler。
4. PDF 专属 pendingDocument 状态应被公共 pending intent 队列替代。

#### 首页宿主

1. 首页不应继续堆叠多个 `consumePendingXXXIfNeeded()`。
2. 目标状态应变为：

```text
HomeView.task
  -> 标记 homeHostReady
  -> 请求 LaunchIntentCoordinator.consumeIfReady()
```

3. 首页只保留具体页面展示能力：

```text
activeSheet = .pendingInvites
activeFullScreenCover = .medicalDocumentUpload
```

### 14. 验收标准

### PDF 验收

1. App 未启动时，从系统文件 App 用 SparkClient 打开 PDF，登录态恢复并进入首页后自动打开 `MedicalDocumentUploadHostView`。
2. 上传页保持 `.picking` 阶段，`selectedFiles` 包含外部 PDF。
3. App 已在后台时，从外部 PDF 打开 SparkClient，同样进入上传页。
4. App 前台时，从外部 PDF 打开 SparkClient，同样进入上传页。
5. 当前上传流程正在 `.processing` 或 `.result` 时，不打断当前流程。

### 成员邀请推送验收

1. App 未启动时，点击成员邀请 APNs 通知，完成冷启动、登录态恢复、账号准备后，自动打开首页的 `PendingMemberInvitesView`。
2. 页面打开后，对应 `invite_id` 的邀请行被高亮并滚动到可见位置。
3. 如果待处理邀请列表暂时没有该 ID，仍打开邀请列表，并在 `onAppearRefresh` 后尽量刷新。
4. App 后台时，点击成员邀请通知，同样打开 `PendingMemberInvitesView`。
5. App 前台收到成员邀请通知时，不自动打开 Sheet，只刷新角标并展示可点击 Banner。
6. 用户点击前台 Banner 后，可以进入同一套公共 intent 流程。
7. 成员邀请深链 `spark://member-invite?id=...` 行为保持不变。

### 公共组件验收

1. 外部 PDF 与成员邀请推送点击都进入同一个 `LaunchIntentCoordinator`。
2. 所有 intent 都有日志：receive、pending、readiness blocked、consume start、consume success、consume failed。
3. 冷启动时，intent 不依赖 HomeView 先挂载，不会因为 `onReceive(routeStacks)` 错过而丢失。
4. 同一个 intent 不会重复打开页面。
5. 当首页还不能展示 sheet/fullScreenCover 时，消费返回 `notReady`，不会清空 pending。
6. 当用户退出登录或账号切换时，不应把旧账号 intent 打开到新账号页面。

### 回归验收

1. 首页手动点击铃铛打开邀请页不受影响。
2. 成员邀请接受、拒绝、刷新、绑定流程不受影响。
3. 成员邀请深链不受影响。
4. 外部 PDF 文件选择器内手动选择 PDF/图片不受影响。
5. 原有 tab 导航、聊天路由、设置路由不受影响。

公共组件必须输出结构化日志，建议格式：

### 16. 风险与处理

### Q：如果冷启动时用户未登录怎么办？

A：公共 coordinator 保留 pending intent，等待用户登录并完成账号准备后再消费。成员邀请推送类 intent 可绑定“未知账号”，登录后按当前账号消费；如果服务端返回该账号没有该邀请，则打开列表但不高亮，或提示邀请不可用。

### Q：如果用户登录了另一个账号怎么办？

A：

1. PDF intent 与账号无强绑定，可在当前账号打开上传页。
2. 成员邀请推送 intent 需要服务端校验；如果当前账号不是受邀账号，列表里不会出现该邀请，应展示空态或错误提示。
3. 后续可在 payload 中加入 recipient user id，用于提前判断账号不匹配。

### Q：如果同时点击推送通知又打开 PDF 怎么办？

A：按优先级处理。用户最后一次明确交互可以覆盖前一次；第一期可保留最近一条 P0/P1 intent。后续如果需要多任务，可扩展为队列。

### Q：如果首页已有 sheet 正在展示怎么办？

A：第一期不要强行覆盖。handler 返回 `notReady`，等当前 sheet 关闭后重新消费。若是同类 sheet，例如已经在 pending invites，可直接更新 highlightInviteID 并刷新。

### Q：如果前台 Banner 点击如何接入？

A：前台 Banner 点击属于用户主动交互，可创建 `LaunchIntent.memberInviteFromPush` 或新增 source `inAppNotificationBannerTap`。但前台收到通知本身仍不创建打开页面的 intent。

### 17. 推荐实施顺序

1. 新增 `LaunchIntent` 数据模型和 `LaunchIntentCoordinator`，先只支持进程内 pending。
2. 在 App 启动生命周期中上报 readiness：signedIn、prepared、onboarding、mainTabReady、homeHostReady。
3. 把外部 PDF 的 pendingDocument 改造成 `LaunchIntent.medicalDocumentUpload`。
4. 新增首页 intent consumer，消费 PDF intent 打开上传页。
5. 把成员邀请推送点击 `.interaction` 改造成 `LaunchIntent.memberInviteFromPush`。
6. 新增首页 intent consumer，消费成员邀请 push intent 打开 `PendingMemberInvitesView`。
7. 保留成员邀请深链 `PendingMemberInviteStore`，不改造。
8. 清理 `AppRoute.memberInvite` 作为推送 Sheet 信号的历史链路。
9. 清理 HomeView 中 PDF 专属 `consumePendingExternalMedicalDocumentIfNeeded()`。
10. 补充冷启动、后台、前台、未登录登录后四类手工验收。
