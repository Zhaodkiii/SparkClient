## 工单 `MEDICINE-CABINET-000001`：家庭药箱入口与跨成员药品汇总设计

### 工单状态

设计中。

## 1. 背景

### 设计背景

当前“药箱/药品”更像是附着在某个成员、用药计划或处方里的辅助数据。用户实际使用时，经常是以“家里有哪些药”为中心：

1. 家里常备药不一定属于某个固定成员，例如退烧药、创可贴、碘伏。
2. 同一种药可能多人共用，例如布洛芬、感冒药、维生素。
3. 用户需要快速查看全家药品是否过期、是否库存不足。
4. 新增药品时，不一定马上知道给谁用，也不一定要创建用药计划。
5. 家庭成员共享后，被授权用户也可能需要查看这个家庭范围内的药品。

因此需要一个“家庭药箱”模块，用于汇总查询所有可访问家庭成员下的药品，并支持新增不绑定成员的药品。

### 现有系统基础

当前项目已有以下基础能力：

| 能力 | 当前情况 |
| --- | --- |
| 药箱模型 | `RemoteMedicineBox` 已存在，但当前字段 `member: Int` 是必填 |
| 药箱查询 | `MedicalQueryAPI.listMedicineBoxes(memberID: Int? = nil, ...)` 已支持可选成员过滤 |
| 药箱创建 payload | `MedicalWorkflowAPI.MedicineBoxPayload` 已存在，但通常在成员/用药上下文下使用 |
| 用药页面 | 已有 `MedicationsListPage`、`MedicationExecutionCenterPage`、`MedicineBoxDetailPage`、`MedicineBoxFormView` 等能力 |
| 成员共享 | 已有“成员多用户绑定与分享”设计，权限由用户与成员绑定关系决定 |

### 当前缺口

当前药箱仍以“成员药箱”为主，本工单设计目标是补齐“家庭药箱”：

```text
成员药箱：某个 member 下的药品
家庭药箱：按入口成员反查其创建用户后，汇总该创建用户名下全部成员药品和未绑定成员药品
```

本设计需要解决以下问题：

1. 药品支持不绑定家庭成员。
2. 家庭药箱需要明确按入口成员推导家庭范围的规则。
3. 共享成员进入时，需要明确是否可见其他成员药品。
4. 家庭药箱权限需要避免药品隐私泄漏。
5. 家庭药箱入口与医疗档案入口并列展示。

## 2. 核心目标

### 核心设计目标

新增“家庭药箱”模块，作为与“医疗档案”并列的家庭级入口。进入后以前端传入的当前成员 ID 为入口，由后端汇总该成员创建用户名下所有成员及未绑定成员的药品，并可新增不绑定成员的药品。

### 第一期目标

1. 新增家庭药箱入口。
2. 支持按当前成员 ID 查询对应创建用户名下的药品汇总。
3. 支持按成员筛选：全部、未绑定成员、成员 1、成员 2、成员 3。
4. 支持新增药品，成员绑定可选。
5. 支持药品详情、编辑、删除或停用。
6. 支持过期、库存不足、药品类型筛选。
7. 支持从与“医疗档案”并列的家庭药箱入口进入。
8. 明确共享用户的家庭药箱可见范围和权限。

### 第一期边界

1. 不做复杂药品条码识别。
2. 不做药品价格、购买渠道管理。
3. 不做多家庭范围切换的完整管理台，第一期基于当前成员 ID 推导创建用户和成员集合。
4. 不做“药品消耗自动扣库存”的强规则，只保留后续扩展点。
5. 不把家庭药箱等同于处方或用药计划；它只是库存。

## 3. 入口设计

### 入口位置

只保留当前设计方案：`家庭药箱` 作为与 `医疗档案` 并列的家庭级入口。

当前设计方案：

```text
🏥 医疗档案                    家庭药箱
├─ 病例
├─ 检查
├─ 体检
└─ 用药（内部不改动）
AI 智能整理报告
```

“家庭药箱”应作为与“医疗档案”并列的家庭级入口，不放进“用药”模块内部。原因：

1. 用户找“家里有哪些药”时，不一定想到用药计划。
2. 药箱是库存，处方是来源，用药计划是规则，三者职责不同。
3. 家庭药箱需要跨成员汇总，比单成员用药计划更接近家庭级入口。
4. 现有用药模块内部不要改动；用药模块右上角进入的药箱保持现有语义，仍然是“成员药箱”。
5. “AI 智能整理报告 / AI 抽取”继续服务医疗档案资料整理，不与家庭药箱入口混在一起。

现有用药模块内部不纳入本工单入口改造。

## 4. 家庭药箱范围设计

### 家庭药箱定义

家庭药箱不新增独立空间模型，不新增药箱归属字段。第一期直接复用现有成员创建者关系来推导家庭范围：

```text
入口传入当前成员 ID
后端校验当前登录用户是否可访问该成员
后端读取该成员的创建用户 / 归属用户
后端查询该创建用户名下所有成员
后端汇总这些成员下的药品 + 该用户下未绑定成员的公共药品
```

也就是说，“家庭药箱”在第一期不是一张新表，而是一个查询视图：

```text
家庭药箱 = 成员创建用户名下所有成员药品 + 创建用户名下 member_id 为空的公共药品
```

### 药品归属设计

药品不强制绑定家庭成员。

因此药品需要支持三种归属：

| 归属方式 | 含义 | 示例 |
| --- | --- | --- |
| 绑定成员 | 主要给某个成员使用 | 爸爸的降压药 |
| 不绑定成员 | 家庭公共药品 | 退烧药、创可贴 |
| 多成员共享 | 后续扩展 | 儿童退烧药可给两个孩子 |

第一期设计：

```text
member_id 可为空
不新增 family_scope_id / cabinet_scope_id
不新增 owner_user_id
```

无成员绑定药品通过现有用户归属关系表达：`member_id = null`，创建用户为当前药品所有者。后端汇总时把“传入成员所属创建用户”的未绑定药品一起纳入结果。

## 5. 共享权限与可见范围

### 创建者家庭药箱可见范围

用户 1 作为成员创建者/药品创建者，进入家庭药箱后，应能看到：

```text
用户 1 名下家庭药箱汇总
├─ 未绑定成员的家庭公共药品
├─ 成员 1 绑定药品
├─ 成员 2 绑定药品
└─ 成员 3 绑定药品
```

查询时支持：

```text
全部
未绑定成员
成员 1
成员 2
成员 3
```

### 共享用户家庭药箱可见范围

共享场景目标：

```text
用户 2 关联用户 1 下的成员 3 后，
用户 2 进入家庭药箱，
前端传入成员 3 ID，
后端根据成员 3 找到创建用户 1，
汇总用户 1 名下所有成员药品 + 用户 1 下未绑定成员药品。
```

本设计由后端统一做权限判断：当前登录用户必须对传入成员 ID 有有效访问权限，才允许触发该成员创建者维度的家庭药箱汇总。

### 共享权限处理

第一期不新增家庭药箱权限字段，不改造分享权限模型。家庭药箱汇总复用现有成员访问权限：

1. 前端必须传入一个当前用户可访问的成员 ID。
2. 后端先校验当前用户是否可查看该成员。
3. 校验通过后，后端根据该成员找到创建用户。
4. 后端查询创建用户名下所有成员 ID。
5. 后端查询这些成员绑定的药品。
6. 后端同时查询该创建用户下 `member_id = null` 的公共药品。
7. 后端合并返回汇总结果。

## 6. 数据模型设计

### 数据模型约束

本工单不新增数据模型，不新增业务字段。第一期只复用现有成员、用户、药箱关系完成家庭药箱汇总。

允许调整现有 `MedicineBox.member` / `RemoteMedicineBox.member` 的可空语义，用于表达“不绑定成员的家庭公共药品”；这不是新增字段。

### `RemoteMedicineBox.member` 可空设计

当前客户端模型：

```swift
struct RemoteMedicineBox {
    var id: Int
    var member: Int
    var medicineName: String
    ...
}
```

为了支持不绑定家庭成员的公共药品，需要调整：

```swift
var member: Int?
```

服务端 Django 模型也需要同步调整。当前类似：

```python
member = models.ForeignKey(
    Member,
    related_name="medicine_boxes",
    on_delete=models.CASCADE,
    db_index=True,
    db_comment="所属家庭成员 ID",
)
```

需要改为可为空：

```python
member = models.ForeignKey(
    Member,
    related_name="medicine_boxes",
    on_delete=models.CASCADE,
    null=True,
    blank=True,
    db_index=True,
    db_comment="所属家庭成员 ID，可为空；为空表示家庭公共药品",
)
```

注意：`on_delete=models.CASCADE` 在 `member=null` 的情况下只影响已绑定成员的药品。公共药品没有成员外键，不会因成员删除而级联删除。

### 服务端模型处理

服务端不新增 `MedicineCabinetScope`、`MedicineCabinetScopeMember` 等模型，不新增 `scope_id`、`cabinet_scope_id`、`owner_user_id` 等字段。

第一期服务端处理方式：

1. 继续使用现有 `Member` 表表达成员归属。
2. 继续使用现有 `MedicineBox` 表表达药品。
3. `MedicineBox.member` 改为可空，`member = null` 表示该药品为创建用户下的家庭公共药品。
4. 家庭药箱汇总不依赖新增表，而是在查询时根据传入成员 ID 动态推导创建用户和成员集合。

## 7. 汇总查询设计

### 客户端查询接口

家庭药箱汇总接口由前端传入当前成员 ID，后端根据该成员 ID 推导家庭药箱汇总范围。

设计：

```text
GET /api/v1/medical/medicine-cabinet/summary/
```

查询参数：

| 参数 | 说明 |
| --- | --- |
| `member_id` | 必填；当前入口成员 ID，用于后端定位成员创建用户 |

第一期接口不增加筛选参数，不在接口层处理成员筛选、公共药品筛选、药品类型筛选、库存筛选、有效期筛选和关键字搜索。页面需要筛选时，先基于返回的药品数组在客户端本地处理。

后端处理流程：

```text
1. 接收 member_id
2. 校验当前登录用户是否可访问该 member_id
3. 根据 member_id 查询该成员的创建用户 owner_user
4. 查询 owner_user 名下所有成员 member_ids
5. 查询 member_id in member_ids 的全部药品
6. 查询 owner_user 下 member_id = null 的公共药品
7. 合并、排序后按现有药箱列表结构返回
```

返回：

```json
{"code":0,"msg":"success","data":[{"id":108,"user":265,"member":100,"medicine_type":"皮肤用药","medicine_name":"复方黄柏液涂剂","brand_name":"舜圣堂","dosage_form":"涂剂","strength":"100ml","dose_unit":"","total_quantity":null,"expire_date":null,"notes":"","extra":{"source":"typed_upload"},"attachments":[],"created_at":"2026-06-01T14:01:56.103228Z","updated_at":"2026-06-01T14:01:56.103278Z"},{"id":107,"user":265,"member":100,"medicine_type":"皮肤用药","medicine_name":"达林克林霉素磷酸酯凝胶","brand_name":"达林","dosage_form":"凝胶剂","strength":"10克装","dose_unit":"","total_quantity":null,"expire_date":null,"notes":"","extra":{"source":"typed_upload"},"attachments":[],"created_at":"2026-06-01T14:01:55.994235Z","updated_at":"2026-06-01T14:01:55.994247Z"},{"id":87,"user":265,"member":100,"medicine_type":null,"medicine_name":"泼尼松片（信谊）","brand_name":"","dosage_form":"","strength":"5mg*10片/包","dose_unit":"","total_quantity":null,"expire_date":null,"notes":"Migrated from ZhaodkDream","extra":{"migration_legacy_id":"201","migration_legacy_table":"aera_medication_box"},"attachments":[],"created_at":"2026-06-01T08:52:59.707163Z","updated_at":"2026-06-01T08:52:59.707166Z"}]}
```

返回结构说明：

1. 外层继续使用现有接口统一结构：`code`、`msg`、`data`。
2. `data` 直接返回药品数组，不额外包裹 `source_member`、`owner`、`members`、`summary`、`items`。
3. 药品 item 结构复用现有药箱列表返回结构，避免客户端新增一套汇总响应模型。
4. 公共药品通过 `member = null` 表达。

### 不直接复用 `listMedicineBoxes(memberID:nil)` 的原因

可作为第一期临时方案，但语义不够。

`memberID:nil` 当前可能表示“当前用户全部可见药箱”，但家庭药箱设计需要明确：

1. 当前入口成员是谁。
2. 该成员的创建用户是谁。
3. 应汇总该创建用户名下哪些成员。
4. 应纳入该创建用户下哪些未绑定成员药品。
5. 当前登录用户是否有权限通过该成员进入该汇总范围。

因此设计新增专门的家庭药箱汇总接口，避免把“当前用户全部可见药箱”和“某个成员创建者名下家庭药箱汇总”混在一个 `member_id=nil` 语义里。

## 8. 页面设计

### 家庭药箱首页

首页参考图片中的“药品盒子”视觉结构，采用浅色背景、顶部横向分类、双列药品卡片和底部固定主操作按钮。

```text
家庭药箱
顶部分类：
  - 全部
  - 系统已有药品分类，例如感冒发烧、胃肠消化、咳嗽咽痛
  - 用户自定义药品分类
  - 分类过多时横向滚动

内容区：
  - 双列网格药品卡片
  - 每张卡片展示药盒/药品图片、药品名称、规格数量、状态角标、查看更多按钮

底部：
  - 固定主按钮：拍照添加药品
  - 辅助入口文案：拍药盒正面图
```

页面不在顶部展示复杂统计概览，避免和参考图里的轻量药箱浏览体验冲突。药品类型筛选使用顶部胶囊 Tabs，本地基于接口返回数组过滤。

分类展示规则：

1. `全部` 固定展示在第一位。
2. 后续分类来自系统已有药品分类和用户自定义分类。
3. 系统已有分类按产品定义顺序展示，例如感冒发烧、胃肠消化、咳嗽咽痛等。
4. 用户自定义分类追加展示，分类名称直接使用用户创建的名称。
5. 分类数量超过一屏时横向滚动，不换行。

### 药品列表卡片

```text
┌──────────────────────┐
│        药品图片       │
│                    已过期 │
│ 达林 克林霉素磷...     │
│ 1% * 10g * 1支/盒  ×1 │
│                      │
│      查看更多  >      │
└──────────────────────┘
```

卡片展示规则：

1. 图片区居中展示药盒图片或药品图片，图片放在浅色圆角底板上。
2. 药品名称最多展示一行，超出省略，例如“达林 克林霉素磷...”。
3. 规格行展示 `strength`、包装/单位和数量，例如 `1% * 10g * 1支/盒  ×1`。

第一期不采用自动扣库存，原因：

1. 实际服药剂量和库存单位可能不一致。
2. 用户可能没有维护库存数量。
3. 自动扣错会降低信任。


或在用药计划里开启“自动扣减库存”。

## 10. 权限与生命周期规则

### 公共药品可见规则

前端传入当前成员 ID 后，后端根据该成员找到创建用户，并返回该创建用户下 `member_id = null` 的公共药品。

只要当前登录用户可访问传入成员，就能在家庭药箱汇总中看到该创建用户下的公共药品。

### 公共药品新增权限

复用现有成员/药品写入权限，不新增家庭药箱权限字段。

后端需要基于传入成员 ID 判断当前用户是否具备新增药品权限；具备写权限时允许创建 `member_id = null` 的公共药品。

### 成员解绑后的药品处理

1. 绑定成员药品仍归属于原成员。
2. 被解绑用户失去该成员访问权限后，不能再通过该成员 ID 查询家庭药箱汇总。
3. 公共药品仍归属于创建用户，不因成员解绑被删除。
4. 如果成员被删除，绑定该成员的药品按现有成员删除策略处理；公共药品不受成员删除影响。

## 12. 验收标准

### 入口验收

1. “家庭药箱”作为与“医疗档案”并列的入口展示。
2. 医疗档案下的“用药”模块内部不改动。
3. 用药模块右上角药箱入口仍进入成员药箱，不变成家庭药箱。

### 查询验收

1. 前端传入成员 1 ID 后，后端能汇总成员 1 创建用户名下所有成员药品。
2. 汇总结果包含该创建用户下未绑定成员的公共药品。
3. 接口返回完整药品数组，页面基于本地数据支持按成员、公共药品、过期、库存不足筛选。
4. 搜索在客户端本地按药品名、品牌、规格命中。

### 新增药品验收

1. 新增药品时可以不绑定成员。
2. 用户可以选择绑定某个成员，也可以选择家庭公共药品。
3. 保存后家庭药箱列表立即出现新药品。
4. 服务端 `MedicineBox.member` 允许为空，`member=null` 的药品可正常创建、查询、编辑。

### 共享验收

1. 用户 2 传入其可访问的成员 3 ID 时，后端能根据成员 3 找到创建用户 1。
2. 后端返回用户 1 名下所有成员药品和用户 1 下未绑定成员药品。
3. 用户 2 传入无权访问的成员 ID 时，接口返回无权限，不返回药品数据。
4. 用户 2 无编辑权限时不能新增/编辑/删除药品。

## 13. 设计结论

### 入口设计结论

1. 信息架构上“家庭药箱”与“医疗档案”并列，不放进“用药”模块内部。
2. 用药模块内部保持现有设计；右上角药箱仍为成员药箱。

### 汇总设计结论

家庭药箱第一期不新增数据模型，不新增业务字段，不新增家庭药箱权限字段。前端进入家庭药箱时传入当前成员 ID，后端基于该成员 ID 完成权限校验、创建用户反查、成员集合查询和药品汇总。

用户 2 通过成员 3 进入用户 1 的家庭药箱时，后端根据成员 3 找到创建用户 1，并返回用户 1 名下所有成员药品和用户 1 下未绑定成员的公共药品。

## 1. 设计目标与边界

新增药箱专用 AI 拍照识别流程，用于引导用户拍摄药盒正面、保质期图片、说明书，并进入后续药品识别/补全流程。

## 4. 响应式取景框尺寸与位置

取景框尺寸不写死，按屏幕尺寸比例计算。

设计原则：

1. 取景框宽度跟随屏幕宽度变化。
2. 取景框高度按屏幕可用高度计算。
3. 取景框位置使用相对位置，不使用固定绝对 y 值。
4. 需要兼容小屏、标准屏和大屏设备。
5. 取景框不能被顶部工具栏、提示文案、底部槽位面板遮挡。

推荐计算方式：

```swift
let availableWidth = proxy.size.width
let availableHeight = proxy.size.height
let safeTop = proxy.safeAreaInsets.top
let safeBottom = proxy.safeAreaInsets.bottom
let bottomPanelHeight = max(220, availableHeight * 0.26)
let topToolbarHeight = safeTop + 64
let promptHeight: CGFloat = 52
let verticalGap: CGFloat = 16

let cameraAreaTop = topToolbarHeight + verticalGap
let cameraAreaBottom = availableHeight - safeBottom - bottomPanelHeight - promptHeight - verticalGap
let cameraAreaHeight = max(220, cameraAreaBottom - cameraAreaTop)

let viewfinderWidth = min(availableWidth * 0.92, 460)
let viewfinderHeight = min(cameraAreaHeight * 0.92, viewfinderWidth * 1.18)
let viewfinderY = cameraAreaTop + cameraAreaHeight * 0.48
```

布局要求：

| 屏幕类型 | 取景框策略 |
| --- | --- |
| 小屏 | 优先保证底部槽位完整展示，取景框高度按可用区域压缩 |
| 标准屏 | 取景框宽度约屏幕 92%，高度为宽度 1.05 到 1.18 倍 |
| 大屏 | 限制最大宽度，避免取景框过宽；位置保持在相机预览主体区域 |

3. 首次进入家庭药箱页面时，如果首页完整成员数据缓存没有家庭药箱数据，则页面内请求家庭药箱列表。
4. 家庭药箱页面加载成功后，把列表写入首页完整成员数据缓存。
5. 后续再次进入家庭药箱页面时，如果首页已有缓存，则先展示缓存，避免重复等待。
6. 用户主动刷新家庭药箱列表时，更新页面数据并回写首页完整成员数据缓存。
7. 家庭药箱内新增、编辑、删除药品后，同步更新首页完整成员数据缓存。
8. 用药计划详情内匹配关联药箱数据时，优先使用首页完整成员数据缓存内的家庭药箱列表。

设计原因：

1. 首页初始加载已经承担成员、用药计划、病历等数据，不再额外加载家庭药箱，避免首屏请求过多。
2. 切换成员时不自动请求家庭药箱，减少无效数据请求。
3. 家庭药箱属于低频入口，按需加载更适合。
4. 一旦用户进入过家庭药箱，再把结果写入首页完整成员数据缓存，供页面回退、再次进入和用药计划详情匹配使用。

涉及当前页面数据：

```swift
var filteredBoxes: [SparkMedicalSyncAPI.RemoteMedicineBox]
```

`filteredBoxes` 的数据来源来自 `FamilyMedicineCabinetViewModel.allBoxes`。`allBoxes` 初始值优先使用首页完整成员数据中的 `familyMedicineBoxes` 缓存；缓存不存在时，进入家庭药箱页面后再加载。

## 2. 首页完整成员数据缓存规则

首页需要在 `RemoteMemberCompleteData` 这套完整成员数据里维护家庭药箱汇总缓存，但不在首页初始加载或切换成员时主动填充。

对应模型位置：

```text
SparkClient/Projects/Core/Networking/API/Medical/MedicalSyncAPI.swift:424-471
```

在 `RemoteMemberCompleteData` 内增加按成员入口加载后的家庭药箱汇总字段：

```swift
struct RemoteMemberCompleteData: Codable, Sendable, Equatable {
    ...

    /// 家庭药箱汇总列表；首页首次加载/切换成员不主动返回。
    /// 只有进入家庭药箱模块后按 entryMemberID 加载成功，再写入首页完整成员数据缓存。
    var familyMedicineBoxes: [RemoteMedicineBox]?
}
```

字段语义：

1. `medicineBoxes`：当前成员个人药箱数据，保持原语义。
2. `familyMedicineBoxes`：按当前成员 ID 进入家庭药箱后，后端返回的家庭药箱汇总列表。
3. 首页首次加载和切换成员时，`familyMedicineBoxes` 可以为 `nil`，表示尚未加载。
4. 进入家庭药箱页面加载成功后，把结果写回当前成员的 `RemoteMemberCompleteData.familyMedicineBoxes`。

缓存粒度：

```text
key = entryMemberID / 当前成员 ID
value = [RemoteMedicineBox]
```

规则：

1. 首页初始加载不请求家庭药箱接口。
2. 首页切换成员不请求家庭药箱接口。
3. 首页只保存“已经进入过家庭药箱页面后加载成功”的家庭药箱数据。
4. 不同成员的 `RemoteMemberCompleteData.familyMedicineBoxes` 缓存不能互相覆盖。
5. 首页完整成员数据中的 `familyMedicineBoxes` 缓存需要与个人药箱缓存区分，避免家庭汇总数据污染个人成员药箱数据。
6. 如果用户从未进入过家庭药箱页面，首页完整成员数据中的 `familyMedicineBoxes` 缓存可以为空。

## 3. 页面进入加载规则

`FamilyMedicineCabinetPage` 家庭模式需要接收首页完整成员数据缓存和回写闭包。

推荐设计：

```swift
struct FamilyMedicineCabinetPage: View {
    let entryMemberID: Int
    let mode: MedicineBoxMode
    let memberCompleteData: SparkMedicalSyncAPI.RemoteMemberCompleteData?
    let onMemberCompleteDataChanged: ((SparkMedicalSyncAPI.RemoteMemberCompleteData) -> Void)?
    let initialMedicineBoxes: [SparkMedicalSyncAPI.RemoteMedicineBox]
    let onMedicineBoxesChanged: (([SparkMedicalSyncAPI.RemoteMedicineBox]) -> Void)?
    let dependencies: HomeFeatureDependencies
}
```

模式区分：

| 模式 | 初始数据 | 是否页面内加载 | 回写闭包 |
| --- | --- | --- | --- |
| `.family` | `memberCompleteData?.familyMedicineBoxes` | `familyMedicineBoxes` 为空时页面内加载 | `onMemberCompleteDataChanged` |
| `.personal` | `initialMedicineBoxes` | 按 000006 个人药箱规则 | `onMedicineBoxesChanged` |

页面进入规则：

1. `mode == .family` 且 `memberCompleteData?.familyMedicineBoxes` 非空时，`allBoxes` 使用 `familyMedicineBoxes`，页面不立即请求接口。
2. `mode == .family` 且 `memberCompleteData?.familyMedicineBoxes` 为 `nil` 或空数组时，页面进入后调用家庭药箱接口加载。
3. 加载成功后更新 `allBoxes`，并把 `latestBoxes` 写回 `RemoteMemberCompleteData.familyMedicineBoxes`，再通过 `onMemberCompleteDataChanged(updatedCompleteData)` 更新首页完整成员数据缓存。
4. `filteredBoxes` 只基于当前 `allBoxes` 做本地筛选、搜索、分类过滤。
5. `mode == .personal` 继续使用 000006 的个人药箱缓存规则。

## 4. 家庭药箱页面加载流程

首次进入且无缓存：

```text
进入家庭药箱页面
→ memberCompleteData?.familyMedicineBoxes 为空
→ 页面显示 loading
→ 调用 listFamilyMedicineCabinet(memberID: entryMemberID)
→ 加载成功后更新 allBoxes
→ 写入 memberCompleteData.familyMedicineBoxes，并调用 onMemberCompleteDataChanged(updatedCompleteData)
→ 首页完整成员数据中的 `familyMedicineBoxes` 缓存写入 latestBoxes
```

再次进入且有缓存：

```text
进入家庭药箱页面
→ memberCompleteData?.familyMedicineBoxes 不为空
→ 页面立即展示缓存数据
→ 不自动请求家庭药箱接口
```

加载失败：

1. 如果已有缓存，保留缓存展示。
2. 如果没有缓存，展示加载失败态和重试入口。
3. 不写入首页完整成员数据缓存。

## 5. 刷新同步规则

家庭药箱页面主动刷新时，重新请求服务端，并同步更新首页完整成员数据缓存。

流程：

```text
用户下拉刷新家庭药箱
→ 调用 listFamilyMedicineCabinet(memberID: entryMemberID)
→ 更新 FamilyMedicineCabinetViewModel.allBoxes
→ 写入 memberCompleteData.familyMedicineBoxes，并调用 onMemberCompleteDataChanged(updatedCompleteData)
→ 首页完整成员数据中的 `familyMedicineBoxes` 缓存同步更新
```

要求：

1. 刷新成功后以服务端最新家庭药箱列表为准。
2. 刷新成功后回写当前 `entryMemberID` 对应的首页完整成员数据中的 `familyMedicineBoxes` 缓存。
3. 刷新失败时保留已有缓存数据，不清空当前页面。
4. 刷新失败时给用户提示，但不影响当前缓存展示。

## 6. 新增/编辑/删除同步规则

家庭药箱页面内修改药箱药品数据后，需要同步更新首页完整成员数据中的 `familyMedicineBoxes` 缓存。

新增成功：

```text
服务端保存成功
→ allBoxes 插入/更新新药品
→ onMemberCompleteDataChanged(updatedCompleteData)
```

编辑成功：

```text
服务端保存成功
→ allBoxes 替换对应 id 药品
→ onMemberCompleteDataChanged(updatedCompleteData)
```

删除成功：

```text
服务端删除成功
→ allBoxes 移除对应 id 药品
→ onMemberCompleteDataChanged(updatedCompleteData)
```

排序规则：

1. 回写前按 `updatedAt` 倒序排序。
2. 与个人药箱和 `MedicineBoxListPage.sortedBoxes` 语义保持一致。

## 7. 用药计划详情药箱匹配

当前用药计划详情内通过药箱列表匹配关联药箱：

```text
SparkClient/Projects/Features/Home/Presentation/MedicalLists/Medications/MedicationPlanDetailPage.swift:83-89
```

现有逻辑：

```swift
private var medicineBox: SparkMedicalSyncAPI.RemoteMedicineBox? {
    currentPlan.medicineBox.flatMap { id in
        medicineBoxes.first(where: { $0.id == id })
    }
}
```

调整为：

1. `MedicationPlanDetailPage` 所使用的 `medicineBoxes` 优先来自首页完整成员数据缓存内的家庭药箱列表。
2. 如果用户尚未进入过家庭药箱、首页完整成员数据中的 `familyMedicineBoxes` 缓存为空，用药计划详情不主动请求家庭药箱列表。
3. 缓存中匹配不到关联药箱时，展示未匹配/不可用态。
4. 用户进入家庭药箱并加载成功后，首页完整成员数据缓存有家庭药箱数据，后续进入用药计划详情即可用缓存匹配。
5. 首页完整成员数据中的 `familyMedicineBoxes` 缓存刷新后，后续进入详情页使用最新缓存。

原因：

1. 避免用药计划详情为了匹配药箱而额外拉取大量家庭药箱数据。
2. 家庭药箱数据只在用户进入家庭药箱页面后按需加载。
3. 保证已加载后的首页、家庭药箱页面、用药计划详情使用同一份药箱缓存。

## 8. 与 000006 的关系

000006 约束个人药箱缓存同步；000007 约束家庭药箱按需加载后的缓存同步。

最终缓存策略：

| 模式 | 首页初始/切换成员是否加载 | 页面初始数据 | 页面内加载 | 刷新回写 | 修改回写 |
| --- | --- | --- | --- | --- | --- |
| `.personal` | 使用成员首页已有个人药箱缓存 | `initialMedicineBoxes` | 按 000006 规则 | `onMedicineBoxesChanged` | `onMedicineBoxesChanged` |
| `.family` | 不加载 | `memberCompleteData?.familyMedicineBoxes` | `familyMedicineBoxes` 为空时页面内加载 | `onMemberCompleteDataChanged` | `onMemberCompleteDataChanged` |

两个缓存不能混用：

1. 个人药箱缓存只代表当前成员药箱。
2. `RemoteMemberCompleteData.familyMedicineBoxes` 缓存代表当前入口成员反查创建用户后的家庭药箱汇总。
3. 用药计划详情匹配关联药箱优先使用 `RemoteMemberCompleteData.familyMedicineBoxes` 缓存，但不主动触发家庭药箱加载。

## 10. 补充详细设计

### 10.1 缓存加载判断

家庭药箱页面按 `RemoteMemberCompleteData.familyMedicineBoxes` 是否为空决定是否加载。

规则：

| 状态 | 页面行为 |
| --- | --- |
| `familyMedicineBoxes == nil` | 进入页面后请求家庭药箱接口 |
| `familyMedicineBoxes?.isEmpty == true` | 进入页面后请求家庭药箱接口 |
| `familyMedicineBoxes` 有数据 | 直接展示缓存，不自动请求 |

该规则与当前需求保持一致：只有进入家庭药箱模块后才加载家庭药箱数据，并写入首页 `RemoteMemberCompleteData`；首页首次加载和切换成员都不主动加载家庭药箱数据。

### 10.2 缓存位置与重复缓存

当前家庭药箱缓存放在当前成员的 `RemoteMemberCompleteData.familyMedicineBoxes` 内。

接口仍然通过 `entryMemberID` 反查创建用户，再汇总创建用户名下全部成员药品和公共药品。

需要注意：

1. `RemoteMemberCompleteData` 是按当前成员缓存的完整数据。
2. 如果用户从同一创建用户下的不同成员进入家庭药箱，理论上返回的是同一个家庭药箱汇总。
3. 第一阶段不额外引入 owner 级缓存，也不在首页切换成员时主动同步其他成员的 `familyMedicineBoxes`。
4. 因此同一家庭不同成员入口可能各自拥有一份 `familyMedicineBoxes` 缓存，这是可接受的实现取舍。
5. 后续如果服务端或首页已有稳定 owner 标识，再考虑把家庭药箱缓存提升为 owner 维度。

### 10.3 缓存失效策略

当前设计是不在首页和切换成员时自动加载家庭药箱。为了避免缓存长期陈旧，需要明确失效策略。

可选策略：

| 策略 | 说明 |
| --- | --- |
| 手动刷新为准 | 进入页面只展示缓存，用户下拉刷新才更新 |
| 前后台恢复不刷新 | App 回前台不自动刷新家庭药箱，避免隐式请求 |
| 账号切换清空 | 切换账号时清空 `RemoteMemberCompleteData.familyMedicineBoxes` 缓存 |
| 登出清空 | 登出时清空 `RemoteMemberCompleteData.familyMedicineBoxes` 缓存 |
| 成员解绑/删除清理 | 当前成员失去访问权限时清理对应缓存 |

第一期建议采用“手动刷新为准 + 账号切换/登出清空 + 成员权限变更清理”的保守策略。

### 10.4 首次进入加载中的 UI 状态

首次进入家庭药箱且缓存未加载时，页面应该展示明确 loading，而不是空态。

状态规则：

1. `memberCompleteData?.familyMedicineBoxes 为空` 且正在请求：展示 loading。
2. `memberCompleteData?.familyMedicineBoxes 为空` 且请求失败：展示失败态和重试按钮。
3. 页面内请求成功但返回空数组：当前页面展示空药箱态，并把空数组写入 `familyMedicineBoxes`。
4. 再次进入时如果 `familyMedicineBoxes` 仍为空数组，按“空就加载”的规则再次请求。
5. `memberCompleteData?.familyMedicineBoxes` 有数据：展示药品网格。

### 10.5 并发和重复请求控制

需要避免连续进入页面或多次触发 `.task` 导致重复请求。

规则：

1. ViewModel 内增加 `isLoading` 防重入。
2. 同一个 `entryMemberID` 正在加载时，不再发起第二个请求。
3. 下拉刷新可以打断或等待当前加载，但不能并发写入两份结果。
4. 如果用户快速切换成员后进入不同家庭药箱，回写缓存时必须校验 key，避免旧请求覆盖新成员缓存。

### 10.6 新增/编辑/删除后的缓存范围

家庭药箱是汇总列表，药品变更后需要判断是否仍属于当前家庭药箱范围。

规则：

1. 新增公共药品：插入当前 `RemoteMemberCompleteData.familyMedicineBoxes` 缓存。
2. 新增绑定当前家庭成员集合内的成员药品：插入当前 `RemoteMemberCompleteData.familyMedicineBoxes` 缓存。
3. 编辑药品后仍属于当前家庭范围：替换缓存中的同 id 药品。
4. 编辑药品后成员归属变化，且不再属于当前家庭范围：从当前缓存移除。
5. 删除药品：从当前缓存移除。

如果服务端保存返回的数据不足以判断归属范围，保存成功后可以选择刷新家庭药箱列表，再回写缓存。

### 10.7 用药计划详情的不可用态

用药计划详情使用首页完整成员数据中的 `familyMedicineBoxes` 缓存匹配关联药箱，但缓存为空时不主动请求。

需要设计不可用态：

1. 如果 `currentPlan.medicineBox` 有 id，但缓存未加载：展示“关联药箱待加载”或隐藏药箱卡片。
2. 如果缓存已加载但找不到该药箱：展示“关联药品已删除或不可访问”。
3. 如果缓存命中：展示现有药箱详情入口。

避免用户误以为用药计划没有关联药箱。

### 10.8 日志与调试

建议增加轻量日志，方便排查缓存是否按预期工作：

```text
`RemoteMemberCompleteData.familyMedicineBoxes` 缓存命中 entryMemberID=xx count=xx
`RemoteMemberCompleteData.familyMedicineBoxes` 缓存未加载，页面内请求 entryMemberID=xx
家庭药箱刷新成功，回写首页完整成员数据缓存 entryMemberID=xx count=xx
`RemoteMemberCompleteData.familyMedicineBoxes` 缓存跳过首页预加载 reason=avoid_home_overfetch
```

日志只记录数量和 key，不记录药品名称等隐私内容。

当前设计只用于进入家庭药箱页面和用药计划详情匹配，不要求首页展示家庭药箱列表或数量。

请确认：

```text

```

## 12. 验收标准

1. 首页初始加载不请求家庭药箱列表。
2. 首页切换成员不请求家庭药箱列表。
3. 首次进入家庭药箱页面且无缓存时，页面内请求家庭药箱列表。
4. 首次进入家庭药箱页面加载成功后，首页完整成员数据中的 `familyMedicineBoxes` 缓存被写入。
5. 再次进入家庭药箱页面且已有缓存时，页面立即展示缓存，不自动重复请求。
6. 家庭药箱页面下拉刷新成功后，页面数据和首页完整成员数据中的 `familyMedicineBoxes` 缓存同时更新。
7. 家庭药箱新增药品成功后，首页完整成员数据中的 `familyMedicineBoxes` 缓存包含新增药品。
8. 家庭药箱编辑药品成功后，首页完整成员数据中的 `familyMedicineBoxes` 缓存同步为编辑后的药品。
9. 家庭药箱删除药品成功后，首页完整成员数据中的 `familyMedicineBoxes` 缓存同步移除该药品。
10. 刷新失败时保留当前缓存数据，不清空家庭药箱列表。
11. 用药计划详情内关联药箱匹配优先使用首页完整成员数据缓存内的家庭药箱列表。
12. 用药计划详情不因为匹配药箱而单独请求家庭药箱列表。
13. 个人药箱缓存和 `RemoteMemberCompleteData.familyMedicineBoxes` 缓存互不污染。

## 1. 设计定位

本工单新增一套从药箱/药品入口发起的“用药计划新增/编辑”多步页面。

需要特别区分两个概念：

| --- | --- | --- |

用户描述中的 `Mode` 使用的是 `SparkMedicalSyncAPI.RemoteMedicationPlan` 和 `MedicationPlanDraft`，因此本工单不替代药箱库存编辑页，而是新增“药箱入口下的用药计划多步表单”。它可以从药箱药品详情、处方识别结果、本地识别草稿等场景进入。

3. 页面按步骤拆分：药品名称 → 药品规格 → 用药时间 → 检查详细信息。
4. 使用页面级导航切换，不使用一个大表单一次性堆满字段。
5. iOS 17 使用 `navigationDestination(item:)`；旧系统使用兼容的隐藏 `NavigationLink` 或本地 wrapper。
6. 最终确认页接入用药提醒开关与非本人提醒协同。

| 非本人、本地已同意代提醒 | 展示“本机已为该成员开启提醒”，允许关闭 |

### 7.2 与 000004 用药通知协同关系

本工单不重新实现通知规则，复用用药通知工单中的协同能力：

1. 保存服务端计划成功后，调用现有 `MedicationReminderPostSaveController.handlePlanChanged(...)`。
2. 非本人归属判断复用 `MedicationReminderOwnershipCoordinator`。
3. 本机代提醒 consent 复用 `MedicationReminderConsentStore`。
4. 邀请成员复用现有 `ShareSheet`。
5. 本页面只负责展示入口和用户意图，不直接创建系统通知。

### 7.3 本地编辑模式特殊处理

`localEdit` 不能立即判断最终服务端计划 ID，也不应直接触发本地通知重建。

规则：

1. `localEdit` 点击完成只回传 `MedicationPlanDraft`。
2. 上层批量保存成功后，再统一触发用药提醒协同。
3. 检查页可以展示提醒开关，但提示“保存后生效”。
4. 不在本地草稿阶段请求系统通知权限。

## 8. 保存与数据流

### 8.1 create

```text
用户完成四步
→ draft.payload(memberID)
→ workflowAPI.create medication plan
→ 返回 RemoteMedicationPlan
→ 上层插入/更新列表
→ 触发用药提醒协同

```

### 8.2 serverEdit

```text
RemoteMedicationPlan -> MedicationPlanDraft

→ draft.payload(memberID)

→ 返回 RemoteMedicationPlan
→ 上层替换列表中的旧计划
→ 触发用药提醒协同
→ dismiss
```

### 8.3 localEdit

```text
MedicationPlanDraft -> 用户编辑
→ 点击完成
→ onSubmit(draft)
→ dismiss
```

### 8.4 保存前校验

| 校验项 | 触发步骤 | 规则 |
| --- | --- | --- |
| 药品名称必填 | Step 1 / 完成 | 为空不能下一步 |
| 规格可跳过 | Step 2 | 不阻塞 |
| 单位缺省 | Step 2 / Step 3 | 空值回退默认单位 |
| 时间必填 | Step 3 / 完成 | 至少一个有效 `HH:mm` |
| 频次完整 | Step 3 / 完成 | 每几天/每周需要完整选择 |
| 日期合法 | Step 3 / 完成 | 结束日期不能早于开始日期 |
| 剂量建议必填 | Step 3 / 完成 | 建议必填；若不填可给“按医嘱”兜底需确认 |
| 非本人提醒 | Step 4 / 保存后 | 不阻塞计划保存 |

## 10. 代码实现建议

### 10.1 不建议直接复用现有 `MedicationPlanFormView`

原因：

1. 现有表单是“单页完整表单”，不是步骤式页面。
2. 当前文件已经承担保存、sheet、剂量同步、提醒频次等职责。
3. 若继续追加多步导航，会让一个 View 同时支持两套布局和两套交互。
4. 后续很难测试，也很难局部改 UI。

建议：

1. 复用 `MedicationPlanDraft`、`MedicationReminderFrequencySheet`、`MedicationPlanDoseDetailSheet` 等底层能力。
2. 新建 `MedicationPlanStepperView` 作为新的页面壳。
3. 新页面提交后仍复用现有 payload 生成逻辑。

### 10.2 协议与依赖

建议 `MedicationPlanStepperView` 依赖现有服务：

```text
SparkMedicalWorkflowAPI
FileTransferService
NotificationClient
HomeFeatureDependencies 或更窄的提醒协同依赖
```

不建议在 View 内直接创建：

1. `SparkMedicalWorkflowAPI`
2. `MedicationReminderSyncCoordinator`
3. `MedicationReminderOwnershipCoordinator`
4. `NotificationClient`

依赖应由上层传入，保持可测试。

### 10.3 日志

关键流程需要日志：

| 日志点 | 内容 |
| --- | --- |

## 12. 需要补充考虑的问题

### 12.1 药箱药品与用药计划的字段映射

药箱药品字段：

```text
medicine_name
brand_name
dosage_form
strength
dose_unit
total_quantity
expire_date
```

用药计划字段：

```text
drug_name
dose_per_time
dose_value
dose_unit
frequency_type
reminder_times
```

需要避免把库存规格误当作每次剂量：

```text
药箱规格：100ml/瓶
用药剂量：每次 10ml
```

确认页需要同时展示“药品规格”和“每次用量”，并允许用户返回修改。

### 12.2 关联药品变更

如果用户先关联药箱药品 A，又手动把药品名称改成 B，提交时有两种选择：

```text
A. 保留 medicineBoxID，但提示名称不一致
B. 自动清空 medicineBoxID
```

建议第一期选择 A，但在检查页展示黄色提示：

```text
药品名称与关联药箱药品不一致，请确认是否继续关联。
```

### 12.3 本地编辑保存时机

`localEdit` 页面只能编辑草稿，不知道最终服务端保存是否成功。

因此：

1. 不请求通知权限。
2. 不创建本地通知。
3. 不调用服务端归属判断。
4. 只把 `reminderEnabled`、`memberID`、提醒时间等信息交给上层。

### 12.4 草稿恢复

如果用户进入多步流程后中途退出，第一期可不做自动恢复。

但需要二次确认，避免误关：

```text
是否放弃本次编辑？
```

后续可增加本地草稿恢复，但不纳入第一期。

### 12.5 无障碍与键盘

1. 输入框需要明确 accessibility label。
2. 单位列表支持 VoiceOver 读出选中状态。
3. 底部按钮需要随键盘避让。
4. 字号放大时，底部按钮不能遮挡内容。
5. 页面内容需要可滚动，不能只按参考图固定布局。

## 14. 验收标准

1. 从药箱入口可打开新的多步用药计划页面。
2. `create` 模式可完成四步并创建服务端用药计划。
3. `serverEdit` 模式能正确回填已有用药计划并保存更新。
4. `localEdit` 模式只回传草稿，不请求服务端。
5. Step 1 药品名称为空时不能进入下一步。
6. Step 2 规格可跳过。
7. Step 3 至少需要一个有效时间，且结束日期不能早于开始日期。
8. Step 4 展示完整摘要、提醒开关、备注输入。
9. 非本人场景按归属展示“邀请他人通知用药”和“在本机开启通知”。
10. 本人成员场景不展示非本人协同入口。
11. iOS 17 使用 `navigationDestination(item:)` 跳转。
12. 旧系统使用兼容导航方案，不出现无法返回或重复 push。
13. 右上角关闭在草稿变更后弹出放弃确认。
14. 保存失败保留当前草稿和页面位置。
15. 保存成功后上层列表/缓存能收到更新结果。
