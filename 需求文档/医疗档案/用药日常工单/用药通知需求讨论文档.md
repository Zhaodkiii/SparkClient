## 2. 方案一：服务端触发 iOS APNs 推送通知

### 2.1 实现方式

服务端根据 `MedicationPlan` 生成待提醒任务，在提醒时间到达后通过 APNs 推送到用户设备。

典型流程：

```text
用户创建/编辑用药计划
  -> 客户端保存 MedicationPlan 到服务端
  -> 服务端根据 frequencyType / reminderTimes / startDate / endDate 生成提醒计划
  -> 服务端调度任务到点触发
  -> 服务端通过 APNs 推送到设备
  -> 用户点击通知进入 App
  -> App 根据 payload 中的 member_id / plan_id / scheduled_at 加载用药详情
```

### 2.2 优点

| 优点 | 说明 |
| --- | --- |
| 跨设备一致 | 同一个账号多台设备登录时，由服务端统一调度，不需要每台设备分别推导提醒 |
| 服务端可审计 | 可以记录通知是否生成、是否发送、失败原因、推送设备 |
| 对换机友好 | 新设备只要登录并上报 APNs token，服务端可继续提醒 |
| 对后台/卸载边界更可控 | App 长期不打开时，服务端仍能尝试推送 |
| 便于运营扩展 | 后续可扩展短信、家属代提醒、家庭成员共享提醒等 |
| 与现有 APNs 基础设施一致 | SparkClient 已有 `PushAdapter`、设备登记、通知路由，SparkService 也已有任务通知雏形 |

### 2.3 缺点

| 缺点 | 说明 |
| --- | --- |
| 强依赖网络和 APNs | 用户离线、APNs token 失效、系统通知关闭时无法保证到达 |
| 服务端复杂度高 | 服务端需要理解用药计划频次、起止日期、时区、跳过、暂停、修改、删除、补服等规则 |
| 高频调度压力 | 用药提醒是日常高频通知，多用户多药品会带来大量定时任务或扫表任务 |
| 计划变更一致性难 | 用户编辑计划后，旧调度任务必须取消或失效，否则容易重复提醒 |
| 时区和夏令时风险 | 服务端若按 UTC 生成未来多天提醒，用户旅行或系统时区变化后容易错点 |
| 前台体验不一定好 | App 正在使用时，系统 banner 通常不是最佳体验，需要转应用内提醒 |
| 隐私风险更高 | APNs payload 如果带药品名、病情、剂量，会在锁屏暴露敏感健康信息 |
| iOS 不保证准时送达 | 远程推送不是强实时机制，尤其省电、弱网、系统策略下可能延迟 |

### 2.4 适合场景

1. 账号多设备共用，希望所有设备都能收到提醒。
2. 用户长期不打开 App，但仍希望服务器兜底提醒。
3. 需要家属、照护人、共享成员收到提醒。
4. 后台需要通知记录、触达统计、失败重试。
5. 未来要支持 Web、Android、iOS 统一提醒中心。

### 2.5 不适合单独承担的原因

用药提醒属于“按本地时间准点提醒”的强体验场景，只靠服务端 APNs 会有三个硬伤：

1. iOS 不承诺远程推送准点到达。
2. 没有网络时无法触发新通知。
3. 用户临时调整时区、当天已服药、临时跳过后，服务端和客户端状态可能短时间不一致。

所以 APNs 更适合作为“跨端/兜底/共享提醒”，不建议作为首版唯一方案。

## 3. 方案二：客户端应用内创建本地通知

### 3.1 实现方式

客户端在创建或更新 `MedicationPlan` 后，根据计划规则生成本地 `UNNotificationRequest`。通知到点由 iOS 系统本地触发，不依赖服务端实时调度。

典型流程：

```text
用户创建/编辑用药计划
  -> 客户端保存 MedicationPlan 到服务端
  -> 保存成功后客户端本地编译提醒计划
  -> 注册未来一段时间的 UNNotificationRequest
  -> 用户收到本地通知
  -> 点击通知进入 App
  -> App 根据本地 payload 中的 plan_id / scheduled_at 打开用药执行中心或计划详情
```

### 3.2 优点

| 优点 | 说明 |
| --- | --- |
| 准时性更适合用药 | 本地日历触发比 APNs 更适合“每天 08:00 吃药” |
| 离线可用 | 没网络也能提醒 |
| 服务端压力小 | 不需要服务端为每个剂次调度大量任务 |
| 隐私更可控 | 可以只在本地生成通知内容，服务端不需要持有每次提醒 payload |
| 响应计划变更快 | 用户编辑、暂停、删除计划后，本机可立即取消和重建通知 |
| 符合 HealthClient 参考方向 | HealthClient 文档也将本地通知作为当日提醒主路径 |
| 可先低成本落地 | SparkClient 已有 `TaskNotificationManager` 可参考拆出通用本地通知注册能力 |

### 3.3 缺点

| 缺点 | 说明 |
| --- | --- |
| 单设备生效 | 用户换手机或另一台设备登录后，需要重新同步计划并注册本地通知 |
| App 被删除后不可用 | 本地通知随 App 删除消失 |
| iOS 待通知数量有限 | iOS 对 pending local notifications 有数量限制，不能无限注册未来所有剂次 |
| 需要本地编译器 | 客户端需要稳定实现 daily / every_n_days / weekly 等频次展开 |
| 多设备可能重复 | 同一账号多设备都注册本地通知时，用户可能多台设备同时响 |
| 权限状态仍需处理 | 本地通知也依赖系统通知权限，用户拒绝后无法弹系统提醒 |
| 数据同步后要重建 | 服务端返回计划变更、删除、停用后，本地必须及时重建通知 |

### 3.4 适合场景

1. 单设备主要使用。
2. 需要准时、离线、低延迟提醒。
3. 首版希望快速形成闭环。
4. 通知内容希望尽量留在本地生成。
5. 用药计划变动频繁，需要本机快速取消旧提醒。

### 3.5 不适合单独承担的原因

只做本地通知会在跨端场景下变弱：

1. 换机后未打开 App 或未完成同步，就不会注册提醒。
2. 家属照护、共享成员提醒无法自然覆盖。
3. 服务端没有通知登记状态，排查“为什么没提醒”会比较困难。

所以本地通知适合做“主提醒”，但长期最好补一层服务端通知登记和状态可观测。

## 4. 已确认方案：只做客户端本地通知闭环

### 4.1 确认结论

本工单首版只做客户端本地通知闭环：

```text
客户端本地通知 = 唯一提醒通道
服务端 APNs = 本工单不做
服务端调度 = 本工单不做
跨设备统一去重 = 本工单不做
```

理由：

1. 用药提醒最核心的是准时和离线，本地通知更合适。
2. 用药计划规则在客户端表单里已经完整表达，客户端可以直接编译提醒。
3. SparkService 的 `task_system` 目前只是任务通知雏形，APNs 发送还未真正接入，不适合把首版用药提醒压到服务端。
4. 服务端调度会引入时区、重复通知、计划变更失效、APNs 延迟等复杂度，和当前目标不匹配。
5. 首版目标是先把“本机准时提醒、离线可用、点击跳转、打卡后不重复提醒”做稳。

### 4.2 本工单目标

目标：

1. 创建/编辑/删除/停用用药计划后，本机通知立即同步。
2. 用药提醒能在无网情况下触发。
3. 点击通知进入用药执行中心，并定位到对应成员、计划、剂次时间。
4. 服药打卡后，当前剂次的提醒不再重复出现。

不做：

1. 不新增服务端调度。
2. 不做家属代提醒。
3. 不做跨设备统一去重。
4. 不做长期未来所有通知一次性注册。

### 4.3 暂不纳入范围

以下能力本工单不设计为必须交付项，只保留为后续演进方向：

1. 服务端通知登记表。
2. 服务端 APNs 兜底提醒。
3. 家属代提醒、共享成员提醒。
4. 多设备主设备策略。
5. 服务端通知触达统计和失败重试。

## 5. 用药通知需要考虑的核心问题

### 5.1 提醒时间规则

需要明确支持哪些规则：

| 规则 | 当前字段支持 | 需要注意 |
| --- | --- | --- |
| 每天 | `frequencyType = daily` | 按 `reminderTimes` 每天生成剂次 |
| 每几天 | `frequencyType = every_n_days` + `everyNDays` | 必须以 `startDate` 作为周期锚点 |
| 每周指定星期 | `frequencyType = weekly` + `weeklyWeekdays` | 需要统一 1=周一...7=周日 |
| 多个时间点 | `reminderTimes` | 同一天多个剂次要有稳定 `doseSequence` |
| 开始/结束日期 | `startDate` / `endDate` | 结束日期当天是否包含，需要明确为“包含结束日” |
| 暂停/停用 | `status` / `reminderEnabled` | 关闭后必须取消本地 pending 通知 |

### 5.2 本地通知注册窗口

不建议一次性注册整个用药周期的所有通知，因为 iOS pending notification 数量有限。

建议：

1. 每次只注册未来 7 天或 14 天的用药提醒。
2. App 冷启动、进入前台、用药计划变更后重新滚动刷新。
3. 每个通知 request identifier 必须可重复计算，便于取消和覆盖。

建议 identifier：

```text
medication_plan_{planID}_{yyyyMMdd_HHmm}_{doseSequence}
```

如果同一计划同一时间可能有多剂量，增加 `doseSequence` 或 `reminderTimeIndex`。

### 5.2.1 一次创建多少通知

首版建议采用“滚动窗口注册”，不要一次创建长期用药的全部通知。

建议策略：

| 项 | 建议 |
| --- | --- |
| 默认窗口 | 未来 7 天 |
| 最大窗口 | 不超过未来 14 天 |
| 单次注册上限 | 建议控制在 48 条以内 |
| 全 App pending 上限保护 | 建议预留系统余量，不要逼近 iOS pending notification 上限 |
| 重建时机 | 冷启动、前台恢复、用药计划保存成功、打卡、账号切换、时区变化 |

原因：

1. iOS 对每个 App 的 pending local notifications 数量有限，长期用药如果按半年或一年一次性注册，很容易超限。
2. 长期计划变化概率很高，一次性注册太多会导致取消和重建成本高。
3. 只注册未来 7 天，用户体验上已经足够覆盖日常提醒，同时可通过前台恢复滚动补齐。
4. 如果用户长期不打开 App，本地通知最多只能覆盖已注册窗口，这属于首版本地通知方案的已知边界。

计算示例：

| 计划规模 | 未来 7 天通知数 | 说明 |
| --- | --- | --- |
| 1 个药，每天 1 次 | 7 条 | 安全 |
| 3 个药，每天 2 次 | 42 条 | 仍可控 |
| 5 个药，每天 3 次 | 105 条 | 可能接近或超过合理上限，需要截断或按优先级注册 |

首版建议：

1. 以账号维度统一重建未来 7 天通知。
2. 如果未来 7 天待注册通知超过 48 条，按时间从近到远截断。
3. 被截断的远期通知不报错，只在 Debug 日志记录。
4. 前台恢复时继续滚动补齐新的未来 7 天。

### 5.2.2 长期用药的滚动补齐

长期用药不代表一次性生成全部通知，而是每次根据当前日期重新编译未来窗口：

```text
今天 2026-06-15 打开 App
  -> 注册 2026-06-15 到 2026-06-21 的通知

2026-06-18 再次打开 App
  -> 清理过期/失效通知
  -> 注册 2026-06-18 到 2026-06-24 的通知
```

这样既避免 iOS 上限，又能让计划变更及时生效。

### 5.2.3 通知创建/更新的触发时机

需要把“通知同步”理解为一个独立动作，而不是只在保存表单时做一次。

建议触发点：

| 触发点 | 行为 |
| --- | --- |
| 创建用药计划成功 | 编译该计划未来窗口，注册本地通知 |
| 编辑用药计划成功 | 先取消该计划旧通知，再注册新通知 |
| 删除用药计划成功 | 取消该计划所有 pending / delivered 通知 |
| 停用计划成功 | 取消该计划通知 |
| 开启/关闭 `reminderEnabled` | 开启则注册，关闭则取消 |
| 用药打卡完成/跳过 | 取消当前剂次通知，必要时刷新当天后续通知 |
| 撤销打卡 | 若该剂次仍在未来，重新注册该剂次通知 |
| App 冷启动且已登录 | 重建当前账号未来窗口 |
| App 进入前台 | 轻量重建未来窗口，补齐滚动窗口 |
| 账号切换/退出登录 | 清理上一个账号本地通知 |
| 系统时区变化 | 清理并重建未来窗口 |
| 从服务端同步到计划变更 | 按最新计划重建对应通知 |

需要注意：

1. 不要在 View 内到处直接调用 `UNUserNotificationCenter.add`。
2. 页面只发出“计划已变更/记录已变更”的事件。
3. 统一由 `MedicationReminderSyncCoordinator` 做通知重建，避免重复和遗漏。
4. 所有通知 identifier 要可推导，才能安全覆盖和删除。

### 5.3 点击通知后的路由

建议本地和远程通知 payload 统一路由字段：

```json
{
  "type": "medication_reminder",
  "route": "medication_execution",
  "member_id": 100,
  "plan_id": 12,
  "scheduled_at": "2026-06-15T08:00:00+08:00",
  "dose_sequence": 1
}
```

点击目标建议：

1. 优先进入 Home。
2. Home 先切换到 `member_id` 对应成员。
3. 等目标成员的首页数据加载完成后，再路由到 `MedicationExecutionCenterPage`。
4. 用药执行中心自动切到 `scheduled_at` 对应日期。
5. 如果能定位到计划剂次，直接打开记录用药 Sheet。
6. 如果计划已删除、停用、成员无权限，展示“该提醒已失效”。

### 5.3.1 用户点击通知后的详细行为

用户点击本地通知后，不建议直接进入用药计划详情页。更好的目标是进入“用药执行中心”，因为提醒的核心动作是“记录是否已服药”。

推荐行为：

```text
点击用药提醒通知
  -> App 启动或前台激活，走冷启动目标页面公共调度组件
  -> 解析 notification userInfo
  -> 进入 Home
  -> Home 先切换到 member_id 对应成员
  -> 等待该成员首页数据加载完成
  -> 再路由到 Home / 用药执行中心
  -> 切换到 scheduled_at 对应日期
  -> 定位 plan_id + dose_sequence 对应剂次
  -> 直接设置 logSheet，打开用药记录 Sheet
```

这里不要新增一套单独的推送点击路由链路，应复用：

```text
SparkClient/需求文档/启动/冷启动目标页面公共调度需求文档.md
```

也就是：

1. 通知入口只负责把 `medication_reminder` 解析成标准化 LaunchIntent。
2. LaunchIntent 先进入 App 级 pending / queue。
3. 等登录态、账号运行时、首页、目标宿主就绪后再消费。
4. Home 消费 intent 后，先切换 `member_id` 对应成员。
5. 等目标成员首页完整数据加载完成，确保 `medicationPlans`、`medicineBoxes`、`todayMedicationRecords` 等上下文来自目标成员。
6. 再打开 `MedicationExecutionCenterPage`。
7. `MedicationExecutionCenterPage` 加载目标日期记录后定位剂次并打开记录 Sheet。

### 5.3.2 直接打开 `logSheet`

现有用药执行中心已经有记录用药的 Sheet：

```text
SparkClient/SparkClient/Projects/Features/Home/Presentation/MedicalLists/Medications/MedicationExecutionCenter/MedicationExecutionCenterPage.swift:32-33
SparkClient/SparkClient/Projects/Features/Home/Presentation/MedicalLists/Medications/MedicationExecutionCenter/MedicationExecutionCenterPage.swift:156-166
```

当前页面状态：

```swift

```

当前展示：

```swift
.sheet(item: $logSheet) { context in
    MedicationExecutionLogSheet(...)
}
```

通知点击定位成功后，不再只高亮卡片，而是直接构造 `MedicationExecutionLogSheetContext`：

```text
title = 当前时间组标题，例如 08:00
date = scheduled_at 对应日期
doses = plan_id + dose_sequence 命中的剂次；如果同一分钟聚合通知，则传入同一时间组的多条 doses
```

然后：

```swift

    title: targetTitle,
    date: targetDate,
    doses: targetDoses

```

需要注意：

1. `MedicationExecutionCenterPage` 不能用当前 Home 已选成员的旧数据直接打开，必须等通知 `member_id` 对应成员的数据加载完成。
2. `MedicationExecutionCenterPage` 首次进入后要先切换 `selectedDate`。
3. 等目标日期 `loadRecordWindow(centeredAt:)` 完成后再计算 `scheduledDoses`。
4. 如果 `scheduledDoses` 中已存在对应已完成记录，不再打开待记录 Sheet，改为展示已完成状态或 Toast。
5. 如果同一时间聚合多条用药，Sheet 内应直接展示多条剂次，方便一次记录。
6. 如果数据加载失败但本地 payload 有最小信息，不建议伪造剂次提交；应提示“数据加载失败，请稍后重试”。

异常处理：

| 场景 | 行为 |
| --- | --- |
| 计划已删除 | 进入用药执行中心，Toast “该用药提醒已失效” |
| 计划已停用 | 进入用药执行中心，Toast “该用药计划已停用” |
| 成员无权限 | 回到医疗档案首页，Toast “当前成员不可访问” |
| 该剂次已打卡 | 进入对应日期，不打开 Sheet，展示已完成记录 |
| 本地数据缺失但有网络 | 拉取当天用药计划/记录后再定位 |
| 本地数据缺失且无网络 | 展示通知内的简要信息和离线提示 |

路由 payload 建议本地通知也带完整定位字段：

```json

  "route": "medication_execution",
  "account_id": 265,
  "member_id": 100,
  "plan_id": 12,
  "scheduled_at": "2026-06-15T08:00:00+08:00",
  "dose_sequence": 1,
  "notification_id": "medication_plan_12_20260615_0800_1"
```

### 5.4 通知内容隐私

用药通知属于敏感健康信息，锁屏文案要谨慎。

可选文案策略：

| 策略 | 示例 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 隐私优先 | 该记录一项用药了 | 锁屏不暴露药名 | 用户不知道吃哪种 |
| 平衡策略 | 妈妈有一项用药提醒 | 暴露较少，能区分成员 | 不显示药名 |
| 明确策略 | 妈妈该服用阿莫西林了 | 行动明确 | 锁屏暴露药品 |

建议首版默认使用平衡策略，并在设置里允许用户选择是否显示药品名称。

### 5.4.1 首版通知内容建议

首版建议默认文案：

```text
标题：用药提醒
内容：妈妈有一项用药需要记录
```

如果当前成员是本人：

```text
标题：用药提醒
内容：你有一项用药需要记录
```

如果用户在系统通用设置的医疗模块中开启“通知中显示药品名称”：

```text
标题：用药提醒
内容：妈妈该记录 阿莫西林 的用药了
```

如果同一时间有多项用药：

```text
标题：用药提醒
内容：妈妈有 3 项用药需要记录
```

首版不建议在通知里展示：

1. 诊断名称。
2. 病情描述。
3. 医院、医生信息。
4. 详细剂量和用法，除非用户明确开启。

原因是通知可能出现在锁屏、车机、手表和通知摘要中，默认必须保护隐私。

### 5.4.2 “通知中显示药品名称”设置入口

该设置不要放在单个用药计划表单里，也不要只藏在用药执行中心。它是医疗隐私类通用偏好，建议放到系统通用设置内新增的“医疗模块”。

现有设置页位置：

```text
SparkClient/SparkClient/Projects/Features/Settings/GeneralSettings/Presentation/GeneralSettingsView.swift:1-74
```

建议在 `GeneralSettingsView` 中增加医疗模块 Section：

```text
List {
    versionSection
    homeNutritionEntrySection
    medicalSection
    MedicalExtractionRetrySettingsSection()
    cacheSection
}
```

`medicalSection` 建议包含：

| 设置项 | 默认值 | 说明 |
| --- | --- | --- |
| 通知中显示药品名称 | 关闭 | 关闭时只显示“你/成员有一项用药需要记录”；开启后通知内容可显示药品名称 |

建议文案：

```text
Section：医疗
Toggle：通知中显示药品名称
Footer：开启后，用药提醒可能会在锁屏、通知中心、手表或车机中显示药品名称。
```

存储建议：

1. 使用本地偏好存储，不需要服务端字段。
2. 按账号隔离更稳妥，避免多人共用设备时偏好串号。
3. 设置变更后不需要重建所有通知也可以，但为了让未来 pending 通知文案立即生效，建议触发一次用药通知滚动窗口重建。
4. 默认关闭，保护隐私。

### 5.5 权限请求时机

不建议在 App 启动时直接弹通知权限。

推荐触发时机：

1. 用户第一次开启某个用药计划的提醒。
2. 用户保存带 `reminderEnabled = true` 的用药计划。
3. 用户进入“用药通知设置”并主动开启。

如果权限未决定：

1. 先弹应用内说明页，说明“我们会在用药时间提醒你”。
2. 用户确认后调用系统通知权限。

如果权限被拒绝：

1. 提示去系统设置开启。
2. 用药计划仍可保存，但提醒状态展示“系统通知未开启”。
3. 本地保存通知配置，权限恢复后自动注册。

### 5.5.1 设置与开关层级

首版建议有三层开关：

| 开关 | 位置 | 作用 |
| --- | --- | --- |
| 系统通知权限 | iOS 系统设置 | 决定 App 是否能发通知 |
| 用药通知总开关 | 用药模块设置或后续医疗设置 | 决定当前账号是否启用用药本地通知 |
| 单个计划提醒开关 | 用药计划表单 `reminderEnabled` | 决定该计划是否参与提醒 |
| 通知中显示药品名称 | 系统通用设置 / 医疗模块 | 只影响通知文案隐私，不影响是否提醒 |

最终是否注册通知的判断：

```text
系统通知已授权
AND 用药通知总开关开启
AND 计划 reminderEnabled = true
AND 计划 status = active
AND 当前账号/成员仍可访问
AND 计划在未来窗口内存在待提醒剂次
```

建议交互：

1. 用户第一次保存开启提醒的计划时，如果系统通知未决定，先展示应用内说明，再请求系统权限。
2. 如果系统通知被拒绝，计划可以保存，但计划卡片上展示“通知未开启”状态。
3. 用药通知总开关关闭时，不改变计划本身的 `reminderEnabled`，只是不注册本机通知。
4. 再次开启总开关后，按当前所有有效计划重建未来窗口。
5. 单个计划关闭提醒时，只影响该计划，不影响其他计划。

### 5.5.2 权限与开关状态展示

建议页面展示状态不要只显示一个布尔值，而是能区分：

| 状态 | 含义 | 用户动作 |
| --- | --- | --- |
| 可提醒 | 系统已授权，总开关开启，计划开启 | 无需处理 |
| 系统通知未开启 | iOS 权限拒绝或关闭 | 引导去设置 |
| 用药通知已关闭 | 应用内总开关关闭 | 可在用药设置开启 |
| 当前计划未开启提醒 | `reminderEnabled = false` | 编辑计划开启 |
| 无未来提醒 | 计划已结束或暂停 | 检查计划日期/状态 |

### 5.6 用药记录与通知取消

用户完成或跳过某次用药后，需要处理后续通知：

1. 当前剂次未触发的 pending 通知应取消。
2. 已触发但仍在通知中心的 delivered 通知应移除。
3. 同一计划当天其他剂次不受影响。
4. 如果用户撤销打卡，需要可重新注册未来对应剂次。

### 5.7 多设备重复提醒

首版只做客户端本地通知，因此多设备不做统一去重，只明确边界：

| 场景 | 建议 |
| --- | --- |
| 只有本地通知 | 每台已登录设备都可注册提醒，可能重复，但实现简单 |
| 只选主设备提醒 | 本工单不做，需要服务端记录 active reminder device，复杂度更高 |
| 跨设备兜底 | 本工单不做，后续再讨论服务端登记或 APNs |

首版建议：

1. 本地通知默认在当前设备生效。
2. 多设备重复提醒先作为已知限制。
3. 当前设备退出登录时必须清理本账号本地通知，避免遗留提醒。

### 5.8 时区与旅行

用药计划通常应按用户当前本地时间提醒，例如每天 08:00。

建议：

1. 本地通知使用 `UNCalendarNotificationTrigger` 的本地 calendar 语义。
2. 计划保存时保留 `timezone` 或在通知登记中保留 `timezone_identifier`。
3. App 发现系统时区变化后，重建未来通知窗口。
4. 后续如果做服务端兜底，需要根据最近设备时区计算 `next_fire_at`，不能永久使用创建计划时的时区。

### 5.9 勿扰与安静时段

需要确认是否做应用内勿扰：

1. 系统勿扰由 iOS 控制，App 不需要绕过。
2. 应用内可设置“安静时段”，例如 22:00-07:00 不提醒或延后提醒。
3. 医疗用药是否允许延后需要谨慎，首版建议只提示，不自动改药。

### 5.10 计划变更一致性

以下操作必须重建通知：

1. 新增用药计划。
2. 编辑药名、剂量、频次、提醒时间、开始日期、结束日期。
3. 关闭 `reminderEnabled`。
4. 停用或删除计划。
5. 成员解绑或权限失效。
6. 服务端同步到远端变更。
7. 登录账号切换。
8. App 时区变化。

### 5.11 通知状态可观测

为了排查“为什么没提醒”，建议在客户端保留诊断信息：

1. 最近一次通知重建时间。
2. 当前成员/计划注册了多少条 pending 通知。
3. 系统通知权限状态。
4. 最近一次注册失败原因。
5. 当前账号本地通知总开关状态。

这些信息可以先只做 Debug 日志，后续再进入设置页诊断。

### 5.12 前台提醒如何展示

本地通知在 App 前台时，系统默认不会像后台一样弹出完整通知；需要决定前台策略。

建议：

1. App 在前台且用户正在用药执行中心：不弹系统 banner，只在页面内刷新/高亮待服药剂次。
2. App 在前台但不在用药页面：展示应用内 banner，点击进入用药执行中心。
3. App 在后台或锁屏：走系统本地通知。
4. 前台展示和系统通知不能重复，避免用户看到两次提醒。

需要补充的能力：

| 能力 | 说明 |
| --- | --- |
| 前台拦截 | `UNUserNotificationCenterDelegate.willPresent` 识别 `medication_reminder` |
| 应用内 banner | 复用 `NotificationClient` / `NotificationHostView` 的应用内提示 |
| 页面刷新 | 如果当前已在用药执行中心，需要触发当天记录刷新 |
| 去重 | 同一 `notification_id` 前台应用内提示只展示一次 |

### 5.13 错过提醒后的处理

用户可能没有点击通知，也可能错过多个提醒。系统不能只依赖“点击通知”。

建议：

1. 用药执行中心按 `MedicationExecutionPlanner` 计算当天所有应服剂次。
2. 当前时间已超过 `scheduledAt` 且未打卡的剂次，在页面中展示“已错过/待记录”状态。
3. 错过提醒不自动创建“漏服”记录，仍由用户选择“已服用 / 跳过 / 稍后”。
4. 通知本身只是提醒，不是用药事实；事实仍以 `RemoteMedicationRecord` 为准。

### 5.14 是否支持稍后提醒

用药场景常见“稍后提醒我”，但首版是否做需要确认。

可选方案：

| 方案 | 说明 | 建议 |
| --- | --- | --- |
| 不做稍后提醒 | 用户点击进入页面后手动处理 | 首版最简单 |

### 5.15 同一时间多条用药如何聚合

如果同一成员同一时间有多条用药，逐条注册通知会导致用户同时收到多条通知。

建议首版采用“同一成员 + 同一分钟聚合为一条通知”：

```text
妈妈 08:00 有 3 项用药需要记录
```

聚合通知 payload 内保存多个计划定位：

```json
{
  "type": "medication_reminder",
  "route": "medication_execution",
  "member_id": 100,
  "scheduled_at": "2026-06-15T08:00:00+08:00",
  "items": [
    { "plan_id": 12, "dose_sequence": 1 },
    { "plan_id": 15, "dose_sequence": 1 }
  ]
}
```

聚合收益：

1. 减少 iOS pending notification 数量。
2. 减少同一分钟多条通知打扰。
3. 点击后更自然进入当天待服药列表，而不是单个计划详情。

风险：

1. 单条通知无法直接显示每个药品名，除非文案拼接。
2. 取消某一剂次时，需要判断聚合通知内是否还有其他待提醒项。
3. 实现上需要 `MedicationReminderScheduleCompiler` 输出聚合后的提醒事件，而不是每个计划一条通知。

### 5.16 本地通知与账号/成员隔离

本地通知是设备级资源，如果不做隔离，账号切换后可能出现上个账号的用药提醒。

建议：

1. notification identifier 必须包含 `accountID`。
2. userInfo 也必须包含 `account_id`。
3. App 启动处理通知时，如果 `account_id` 与当前登录账号不一致，不进入详情，只提示“该提醒属于其他账号”或直接忽略。
4. 退出登录时，清理当前账号所有 `medication_reminder` 通知。
5. 切换账号时，先清理旧账号通知，再注册新账号通知。

建议 identifier：

```text
medication_{accountID}_{memberID}_{yyyyMMdd_HHmm}_{groupHash}
```

如果仍按计划粒度：

```text
medication_{accountID}_{memberID}_{planID}_{yyyyMMdd_HHmm}_{doseSequence}
```

### 5.17 删除/停用后的历史通知处理

用户删除或停用计划后，既要删除未触发通知，也要清理通知中心已展示的旧通知。

建议：

1. 删除计划：移除该计划未来 pending 通知和 delivered 通知。
2. 停用计划：同删除通知，但保留计划数据。
3. 修改提醒时间：旧通知全部取消，新窗口重新注册。
4. 关闭总开关：清理所有用药本地通知。
5. 重新开启总开关：按当前有效计划重建。

注意：

1. delivered 通知不清理的话，用户可能在通知中心点击到已失效提醒。
2. 即使清理失败，点击时也必须做二次校验，不能直接信任通知 payload。

### 5.18 数据源与离线能力

本地通知能离线触发，但点击后的页面不一定有最新数据。

建议：

1. 生成通知时，在 userInfo 内只放定位 ID 和最小展示信息。
2. 点击后优先使用本地已有缓存展示。
3. 有网络时刷新当天计划和记录。
4. 无网络时仍能进入用药执行中心，展示本地已知计划，并提示“离线模式，数据可能不是最新”。
5. 如果本地完全没有该计划数据，只展示失效/离线提示，不创建记录。

### 5.19 通知调度失败如何处理

`UNUserNotificationCenter.add` 可能失败，不能静默吞掉。

建议记录：

1. 失败的 notification identifier。
2. 失败原因。
3. 计划 ID、成员 ID、scheduledAt。
4. 当前系统通知权限状态。
5. 当前 pending 数量。

用户侧：

1. 普通用户不展示技术错误。
2. 计划卡片可以展示“部分提醒注册失败”。
3. Debug 模式或诊断页展示详细原因。

### 5.20 本地通知测试场景

用药通知必须补测试，否则边界很容易漏。

建议覆盖：

| 场景 | 验证点 |
| --- | --- |
| 每日一次 | 未来 7 天生成 7 条或聚合后正确数量 |
| 每日多次 | 同一天多个时间点顺序正确 |
| 每几天 | 以 `startDate` 为锚点，不被当前日期偏移 |
| 每周指定日 | 只在指定 weekday 生成 |
| 有结束日期 | 结束日期之后不生成 |
| 关闭提醒 | 不生成通知 |
| 停用计划 | 不生成通知 |
| 编辑时间 | 旧通知取消，新通知存在 |
| 打卡完成 | 当前剂次通知被移除 |
| 账号切换 | 旧账号通知清理 |
| 时区变化 | 未来窗口重建 |
| 超过上限 | 按时间从近到远截断，不崩溃 |

### 5.21 不建议首版做的能力

这些能力看起来好用，但首版容易把范围拉大：

1. 通知 Action：已服用、跳过、稍后提醒。
2. 家属代提醒。
3. Apple Watch 独立交互。
4. 服务端兜底推送。
5. 多设备主设备策略。
6. 复杂勿扰规则。
7. 药品级重要性排序。
8. 自动判断漏服并生成记录。
9. AI 自动调整提醒时间。

首版应该把基础闭环做稳：

```text
计划保存 -> 本地注册 -> 到点提醒 -> 点击进入执行中心 -> 用户打卡 -> 当前剂次不再提醒
```

## 8. 风险与注意点

| 风险 | 说明 | 建议 |
| --- | --- | --- |
| 重复通知 | 编辑计划后旧通知未取消 | 使用稳定 identifier，更新前先批量移除旧计划通知 |
| 漏通知 | App 同步到新计划但未重建本地通知 | 在同步完成、前台恢复、账号切换后触发重建 |
| 通知数量超限 | 长期计划每天多次提醒 | 只注册未来 7/14 天滚动窗口 |

| 时区错乱 | 用户旅行后提醒时间异常 | 检测时区变化后重建 |
| 多设备打扰 | 多台设备同时提醒 | 首版记录已知限制，后续服务端主设备策略 |
| 服务端过度设计 | 一开始做完整调度系统 | 本工单明确不做服务端调度 |
| 业务职责泄漏 | 页面直接计算提醒规则 | 抽出 schedule compiler 和 notification manager |
| 医疗安全 | AI 或规则自动改提醒 | 不自动改变医嘱时间，用户确认后保存 |

## 11. 验收标准草案

### 11.1 首版本地通知验收

1. 保存开启提醒的用药计划后，本机能在指定时间收到通知。
2. 关闭提醒后，该计划未来通知全部取消。

4. 删除或停用计划后，不再收到该计划通知。
5. App 无网时，本地通知仍能触发。

## 工单 `MEDICATION-NOTIFICATION-000002`：共享成员用药通知协同与服务端辅助接口讨论

### 工单状态

需求讨论中。

### 1. 需求背景

`MEDICATION-NOTIFICATION-000001` 已确认首版以客户端本地通知为主，不做服务端用药剂次调度。但进入共享成员场景后，会出现新的归属问题：

```text
用户 A 维护自己本人的用药计划：
  -> 应该在用户 A 当前设备创建本地通知

用户 A 维护“非本人”成员的用药计划：
  -> 这个成员可能是用户 A 自己管理的家人
  -> 也可能是其他用户分享给用户 A 的成员
  -> 是否应该在用户 A 当前设备创建本地通知，需要额外确认
  -> 如果该成员属于其他“本人用户”，更合理的是通知该本人用户：有人维护了你的用药计划
```

因此本工单不是把用药提醒改成服务端调度，而是在本地通知闭环外补一层“共享成员协同”：

1. 客户端创建本地提醒前，能知道哪些成员/计划适合在本机补齐通知。
2. 服务端提供轻量接口，返回当前用户可访问成员下已开启提醒的用药计划。
3. 服务端提供成员所属本人用户/可推送能力判断，避免客户端自己猜关系。
4. 当非本人维护了他人“本人成员”的用药计划时，服务端只发一次 APNs 告知，不定时调度每个剂次。
5. 是否允许为他人成员在本机创建提醒，需要有可解释的用户授权策略。

### 2. 设计原则

| 原则 | 说明 |
| --- | --- |
| 本地提醒仍是主路径 | 到点吃药提醒继续由 iOS 本地通知触发，不依赖服务端实时调度 |
| 服务端只做查询和告知 | 服务端新增接口只返回开启提醒计划、成员归属和 APNs 能力；不展开未来剂次 |
| 一次性告知不同于用药提醒 | “某某维护了你的用药计划”是协同通知，不是“08:00 该吃药”的剂次通知 |
| 不重复拉取 | 客户端补齐通知时不再逐成员循环 `listMedicationPlans`，改用一个聚合接口 |
| 非本人默认不打扰 | 非本人计划不应默认在本机创建提醒，除非用户明确同意过 |
| 分享优先 | 如果成员属于其他本人用户，优先引导分享/通知本人用户，而不是默默在维护者本机长期提醒 |
| 隐私最小化 | APNs 文案不暴露药品名、剂量、病情；点击后进入 App 再查看详情 |

### 3. 服务端接口设计

#### 3.1 新增接口一：当前用户开启提醒用药计划汇总

在 `SparkService/medical/urls.py` 下新增独立接口，建议路径：

```text
GET /api/v1/medical/medication-reminders/enabled-plans/
```

用途：

1. 客户端补齐本地通知时，一次性拿到当前用户可访问成员下“开启提醒”的用药计划。
2. 替代 `MedicationReminderSyncCoordinator.loadSnapshots(accountID:members:)` 中对每个成员重复调用 `listMedicationPlans(memberID:)` 的逻辑。
3. 后续通知管理页、诊断页也可以复用这个接口判断“哪些计划理论上应该有提醒”。

建议 URL 注册：

```python
path(
    "medication-reminders/enabled-plans/",
    MedicationReminderEnabledPlansAPI.as_view(),
    name="medical-medication-reminder-enabled-plans",
)
```

#### 3.2 是否需要有效期过滤

建议：需要。

原因：

1. 客户端只注册未来 7 天左右的滚动窗口，本地通知不需要拿到很久以前已经结束的计划。
2. 长期用药计划很多时，如果不做有效期过滤，补齐通知接口会越来越重。
3. 有效期过滤是服务端最适合做的粗筛，不涉及剂次展开，不会把复杂调度搬到服务端。

建议过滤规则：

```text
reminder_enabled = true
status in ["active"]
start_date <= window_end_date
end_date is null OR end_date >= window_start_date
is_deleted = false
member_id in 当前用户可访问成员
```

请求参数建议：

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `window_start_date` | 否 | 默认服务端当前日期；客户端可传本地今天 |
| `window_end_date` | 否 | 默认 `window_start_date + 7 days`；最大不超过 14 或 30 天 |
| `include_records` | 否 | 默认 `true`；是否一起返回窗口内用药记录，供客户端排除已打卡剂次 |

不建议开放复杂筛选：

```text
不做 keyword；
不做药品类型；
不做单成员 filter_member_id；
不做所有状态；
不做历史数据导出。
```

这个接口服务于“通知补齐”，不是用药计划列表页。

#### 3.3 是否需要状态过滤

建议：需要，但首版固定由服务端内部过滤，不暴露任意状态参数。

首版只返回：

```text
MedicationPlan.status == active
MedicationPlan.reminder_enabled == true
```

不返回：

```text
paused / completed / cancelled
reminder_enabled == false
已删除计划
有效期完全不在窗口内的计划
```

原因：

1. 本地通知只关心未来还需要提醒的计划。
2. 如果把 `status` 暴露成查询参数，客户端容易把通知接口当成计划列表接口复用，导致边界变乱。
3. 暂停、完成、取消计划的提醒应被取消，不应该进入补齐集合。

#### 3.4 返回结构建议

接口返回按成员分组，不让客户端再拼接成员关系：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "window_start_date": "2026-06-15",
    "window_end_date": "2026-06-22",
    "members": [
      {
        "member": {
          "id": 100,
          "name": "妈妈",
          "relationship": "mother",
          "is_self_member": false,
          "binding_role": "editor",
          "can_share": true,
          "can_write": true
        },
        "owner": {
          "user_id": 265,
          "display_name": "用户A",
          "is_current_user": true,
          "has_apns": true,
          "notifications_enabled": true
        },
        "self_owner": null,
        "plans": [],
        "records": []
      }
    ]
  }
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `member` | 当前可访问成员信息，至少包含本地编译提醒所需的 `id/name/relationship` |
| `owner` | 该成员创建者/Owner 用户，用于判断是不是当前用户自己的成员体系 |
| `self_owner` | 如果该成员存在“本人关系”的其他用户绑定，则返回该用户的最小通知能力信息；没有则为 `null` |
| `plans` | 窗口内可能产生提醒的开启提醒计划 |
| `records` | 窗口内用药记录，用于本地排除已完成/已跳过剂次 |

`self_owner` 建议只返回最小信息：

```json
{
  "user_id": 300,
  "display_name": "赵*",
  "has_apns": true,
  "notifications_enabled": true
}
```

不要返回邮箱、手机号、完整设备信息、push token。

### 4. 服务端接口二：成员通知归属探测

新增轻量接口，用于保存/编辑非本人用药计划后判断提示流程。

建议路径：

```text
GET /api/v1/medical/members/{member_id}/notification-ownership/
```

用途：

1. 判断当前成员是不是当前用户自己的本人。
2. 判断是否存在其他“本人用户”。
3. 判断其他本人用户是否开启 APNs。
4. 返回当前用户是否可分享该成员。
5. 给客户端决定弹窗文案和按钮。

返回示例：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "member_id": 100,
    "member_name": "妈妈",
    "current_user_relationship": "mother",
    "is_current_user_self_member": false,
    "can_share": true,
    "has_other_self_owner": true,
    "other_self_owner": {
      "user_id": 300,
      "display_name": "赵*",
      "has_apns": true,
      "notifications_enabled": true
    }
  }
}
```

权限：

```text
必须 require_access(member_id)；
只返回当前用户有权访问的成员；
不能通过该接口探测任意 member_id 是否存在；
other_self_owner 只返回脱敏展示名和通知能力，不返回敏感账号信息。
```

### 5. 服务端接口三：资源协同 APNs 告知

这不是用药剂次提醒接口，而是公共“健康资源被他人维护”通知接口。建议做成公共方法，当前只接入用药计划，后续病例、体检、检查报告、药箱都可复用。

建议服务层方法：

```python
HealthResourceChangeNotificationService.notify_owner_resource_changed(
    *,
    actor_user,
    member_id: int,
    resource_type: str,
    resource_id: int,
    action: str,
    request_id: str = "",
)
```

当前支持：

```text
resource_type = "medication_plan"
action = "created" / "updated"
```

后续可扩展：

```text
medical_case
health_exam_report
examination_report
prescription
medicine_box
symptom
visit
follow_up
```

实现原则：

1. 通过 `member_id` 找该成员的“本人用户”绑定。
2. 如果本人用户就是当前操作者，不发 APNs。
3. 如果本人用户不存在，不发 APNs。
4. 如果本人用户存在但没有可用 APNs 设备，记录 skipped，不报错阻塞保存。
5. 使用 `accounts.services.notification_service.NotificationService.send_to_user_sync` 或 campaign 队列，只走 `NotificationMessage.Channel.APNS`。
6. payload 带 `type/resource_type/resource_id/member_id/action`，不带药名、剂量、病情。

建议 payload：

```json
{
  "type": "health_resource_changed",
  "resource_type": "medication_plan",
  "resource_id": "123",
  "member_id": "100",
  "action": "updated",
  "actor_user_id": "265"
}
```

建议文案：

```text
标题：用药计划已更新
内容：有人维护了你的用药计划，打开应用查看详情
```

如果需要显示操作者，可用脱敏名：

```text
{actor_display_name} 维护了你的用药计划
```

不建议首版显示药品名称。

### 6. 客户端业务流程设计

#### 6.1 本人开启通知保存计划

本人关系：

```text
用户保存用药计划
  -> plan.reminder_enabled = true
  -> 当前成员 relationship == self
  -> 走当前 000001 流程
  -> 询问/检查系统通知权限
  -> 创建或重建本机本地通知
```

这个流程不变。

#### 6.2 非本人维护用药计划：成员不属于其他本人用户

场景：

```text
用户 A 管理妈妈/孩子等成员；
该成员没有其他账号以 relationship=self 绑定；
```

保存开启提醒的计划后，建议优先走分享流程：

```text
客户端调用 notification-ownership
  -> has_other_self_owner = false
  -> 当前成员没有其他用户绑定为本人
  -> 打开或引导打开 ShareSheet
  -> 用户完成分享：结束本次流程，不立即创建本机通知
  -> 用户取消分享：再询问是否需要“为他通知用药”
```

用户取消分享后的二次确认：

```text
标题：是否在本机提醒这个成员的用药？
内容：该成员还没有绑定为本人的用户。你可以临时在本机接收提醒，后续也可以重新分享给本人或家人共同管理。
按钮：
  - 在本机提醒
  - 暂不提醒
```

二次确认按钮行为：

| 操作 | 行为 |
| --- | --- |
| 在本机提醒 | 记录“同意为该成员创建本机提醒”，然后重建本地通知 |
| 暂不提醒 | 不创建本机通知；用药计划仍保存成功 |

这里的“分享成员”是优先流程：没有本人绑定时，应先引导建立成员共享关系；只有用户取消分享后，才进入“是否本机代提醒”的选择。

#### 6.3 非本人维护用药计划：成员属于其他本人用户

场景：

```text
用户 A 通过分享拥有成员 X 的编辑权限；
成员 X 对用户 B 是 relationship=self；
用户 A 维护了 X 的用药计划；
```

保存开启提醒的计划后建议流程：

```text
客户端调用 notification-ownership
  -> has_other_self_owner = true
  -> other_self_owner.has_apns = true
  -> 服务端发送一次 APNs 给用户 B
  -> 客户端提示：已通知成员本人
  -> 直接结束，不走分享流程
  -> 默认不在用户 A 本机创建长期用药提醒
```

建议首版提示：

```text
标题：已通知成员本人
内容：该成员已绑定为其他用户本人，我们会通知对方查看用药计划。
按钮：
  - 好的
```

如果 `other_self_owner.has_apns = false`：

```text
标题：成员本人暂未开启通知
内容：该成员已绑定为其他用户本人，但对方可能无法收到系统通知。用药计划已保存。
按钮：
  - 好的
```

#### 6.4 非本人未同意过为他人通知

用户明确选择“暂不提醒”时：

```text
不在本机创建通知；
不弹系统通知权限；
不阻塞计划保存；
只在页面轻提示：用药计划已保存，未创建本机提醒。
```

### 7. 补全通知流程调整

当前 `MedicationReminderSyncCoordinator.loadSnapshots(accountID:members:)` 是按成员循环：

```text
for member in members:
  listMedicationPlans(memberID)
  listMedicationRecords(memberID)
```

建议改为：

```text
rebuildAll
  -> 调用 GET /medical/medication-reminders/enabled-plans/
  -> 服务端返回当前用户可访问成员 + 开启提醒计划 + 窗口内记录
  -> 客户端按规则过滤是否允许在本机创建
  -> 编译未来 7 天本地通知
  -> rebuild 到 UNUserNotificationCenter
```

补全规则：

| 成员关系 | 是否补全本机通知 |
| --- | --- |
| 当前用户本人 `relationship == self` | 默认补全 |
| 非本人，但本地已同意为该成员提醒 | 补全。这里包含“没有本人绑定时用户取消分享后选择在本机提醒”，也包含“其他场景下用户曾明确同意本机代提醒” |
| 非本人，未同意过 | 不补全 |
| 非本人，属于其他本人用户，且本地未同意 | 不补全；保存流程只做服务端 APNs 告知并结束 |
| 无访问权限或成员已解绑 | 不补全，并清理旧通知 |

### 8. “是否为他人创建通知”存储方案

#### 8.1 方案 A：存在服务端

形式：

```text
MedicationReminderConsent
user_id
member_id
enabled
created_at
updated_at
```

优点：

| 优点 | 说明 |
| --- | --- |
| 跨设备一致 | 用户换设备后仍知道曾同意为该成员提醒 |
| 可审计 | 后台可解释为什么某个用户会收到他人成员提醒 |
| 便于共享治理 | 后续可做家庭成员提醒权限、撤销、家属代提醒 |

缺点：

| 缺点 | 说明 |
| --- | --- |
| 容易扩大需求 | 会自然演变成服务端提醒授权体系 |
| 需要迁移和接口 | 增加模型、接口、权限、测试 |
| 和首版本地通知目标冲突 | 首版本机提醒是设备级能力，服务端存用户级同意不一定准确 |
| 多设备仍会重复 | 服务端同意后，多台设备都可能创建本地通知，除非再做主设备策略 |

#### 8.2 方案 B：存在客户端本地

形式：

```text
UserDefaults / 本地偏好
key = medication_reminder_consent_{accountID}_{memberID}
value = true / false
```

也可以记录更多信息：

```json
{
  "member_id": 100,
  "enabled": true,
  "decided_at": "2026-06-15T10:00:00Z",
  "source": "save_plan_prompt"
}
```

优点：

| 优点 | 说明 |
| --- | --- |
| 符合本地通知定位 | 本机通知本来就是设备级行为，放本地最自然 |
| 实现简单 | 不增加服务端模型和迁移 |
| 用户体验清晰 | “是否在这台手机提醒我”是本地选择 |
| 不影响其他设备 | 当前设备同意，不会让另一个设备也突然提醒 |

缺点：

| 缺点 | 说明 |
| --- | --- |
| 换机丢失 | 新设备需要重新确认 |
| 不可后台审计 | 服务端不知道用户是否同意本机提醒 |
| 账号卸载重装丢失 | 除非写入 Keychain 或同步设置 |

#### 8.3 建议结论

首版建议：存在客户端本地。

原因：

1. “为他人成员创建通知”本质是“是否在这台设备提醒我”，属于设备级偏好。
2. 首版不做跨设备统一去重，服务端存同意会制造“看似跨设备一致，实际多设备重复”的假一致。
3. 服务端已经承担成员归属和 APNs 告知，没必要再承担本机提醒授权。
4. 后续如果要做家属代提醒、主设备、跨设备提醒，再升级为服务端模型。

建议本地类型：

```swift
struct MedicationReminderMemberConsent: Codable, Equatable, Sendable {
    let accountID: Int64
    let memberID: Int
    var allowsLocalReminder: Bool
    var decidedAt: Date
    var source: String
}
```

建议封装：

```text
MedicationReminderConsentStore
  -> allowsLocalReminder(accountID:memberID:)
  -> setAllowsLocalReminder(_:accountID:memberID:source:)
  -> removeConsent(accountID:memberID:)
```

不要散落在 View 或 ViewModel 的 `UserDefaults` 字符串里。

### 11. 边界与风险

| 风险 | 说明 | 建议 |
| --- | --- | --- |
| 服务端接口过重 | 一次返回所有成员、计划、记录可能变大 | 默认 7 天窗口；只返回开启提醒且有效的计划；记录只返回窗口内 |
| 非本人通知打扰 | 用户维护家人资料后自己手机长期响 | 非本人必须明确同意，默认不创建 |
| 分享语义混淆 | 用户以为分享后对方一定会收到剂次提醒 | 文案明确：分享是共同管理，剂次提醒仍取决于对方设备通知设置 |
| APNs 告知误认为用药提醒 | “维护了计划”不是“该吃药” | 服务端 payload type 区分 `health_resource_changed`，不进入本地提醒列表 |
| 隐私泄漏 | 锁屏显示药名/病情 | 首版 APNs 不带药品名、剂量、病情 |
| 多设备重复 | 同一账号多设备本地都补齐 | 000001 已明确首版不做跨设备去重，管理页可提示“本机通知” |
| 权限探测 | 通过 member_id 探测其他人信息 | 所有接口必须先 `require_access`，返回脱敏最小字段 |

### 12. 待确认问题

#### Q1：非本人且不属于其他本人用户时，弹窗是否必须给“分享成员”按钮？

已确认：先走分享流程；用户取消分享后，再询问是否需要为该成员创建本机用药通知。

实现方向：

```text
保存开启提醒的非本人计划后：
  -> notification-ownership 判断没有其他本人绑定
  -> 打开或引导打开 ShareSheet
  -> 用户完成分享：结束
  -> 用户取消分享：弹出“是否在本机提醒这个成员的用药”
  -> 选择“在本机提醒”：写入本地 consent 并创建/补全通知
  -> 选择“暂不提醒”：不创建本机通知
```

备注：

```text
分享是优先流程，不在第一层弹窗直接给“在本机提醒”。
```

#### Q2：非本人且属于其他本人用户时，是否默认通知本人用户？

已确认：是。仅发一次资源变更 APNs，不调度剂次提醒；客户端不走分享流程，提示后直接结束。

实现方向：

```text
服务端在保存/更新 medication_plan 成功后，判断存在 other_self_owner 且 has_apns；
异步或同步调用公共通知服务发送 APNs；
客户端展示“已通知成员本人”；
流程结束，不再询问是否分享，也不再询问是否本机提醒。
```

备注：

```text
如果 APNs 不可用，保存不失败，只提示对方可能无法收到通知；仍不进入分享流程。
```

#### Q3：是否同意为他人成员创建本机通知，存在服务端还是本机？

建议：首版存在本机。

实现方向：

```text
新增 MedicationReminderConsentStore；
按 accountID + memberID 存储 allowsLocalReminder；
补全通知时非本人只读取本地 consent。
```

备注：

```text
这是设备级提醒授权，不是家庭权限；后续做家属代提醒/主设备再升级服务端模型。
```

#### Q4：开启提醒计划汇总接口是否返回 records？

建议：返回窗口内 records。

实现方向：

```text
同一个接口返回 plans + records，减少客户端补齐通知时的 N+1 请求；
records 只返回 window_start_date ~ window_end_date + 1 天内数据。
```

备注：

```text
如果担心返回过大，可保留 include_records=false，但默认 true。
```

#### Q5：用药计划保存接口是否直接触发 APNs 告知？

建议：触发，但应封装为公共服务方法。

实现方向：

```text
MedicationPlanViewSet / MedicationPlanWorkflowSaveView 保存成功后调用：
HealthResourceChangeNotificationService.notify_owner_resource_changed(...)
```

备注：

```text
公共方法以后也接病例、体检、检查报告等资源，不要写死在用药计划里。
```

### 13. 验收标准草案

1. 补全通知时，客户端只请求一次开启提醒用药计划汇总接口，不再按成员循环请求计划。
2. 汇总接口只返回当前用户可访问成员的数据。
3. 汇总接口默认只返回 `reminder_enabled=true`、`status=active`、有效期覆盖窗口的计划。
4. 汇总接口返回窗口内用药记录，客户端可排除已完成/跳过剂次。
5. 本人用药计划开启提醒后，仍走原本本机通知创建流程。
6. 非本人计划保存后，未同意为该成员提醒时，不自动创建本机通知。
7. 非本人且没有其他本人绑定时，保存开启提醒计划后优先进入成员分享流程。
8. 非本人计划保存后，用户选择“暂不提醒”，不弹系统通知权限，不创建本机通知。
9. 非本人且没有其他本人绑定时，用户取消分享后再询问是否需要在本机提醒；选择“在本机提醒”后，后续补全通知会包含该成员。
10. 成员属于其他本人用户且对方 APNs 可用时，服务端发送一次“用药计划已更新”APNs。
11. 成员属于其他本人用户时，客户端不走分享流程，不弹“是否本机提醒”，服务端通知后流程直接结束。
12. APNs payload 不包含药名、剂量、病情等敏感内容。
13. 当前操作者就是本人用户时，不给自己发送“资源被他人维护”的 APNs。
14. 成员解绑或失去访问权限后，本机补全不再包含该成员，并清理旧通知。
15. 服务端公共资源变更通知方法可被未来病例、体检、检查报告复用。
